01The ID in the URL that was never checked

Senior Security issue found and fixed

(a) Worked example EXAMPLE — replace with your own

I was reviewing a small pull request on a B2B billing API — someone was adding a "download this invoice as PDF" endpoint next to the existing JSON one. The new handler looked exactly like its neighbour, which is what made me stop: it took an invoiceId from the route, loaded the invoice, rendered it. Nowhere in either handler was there a sentence that said "…and this invoice belongs to the caller". The authentication middleware was doing its job perfectly — every request had a valid access token, every token had a tenant claim — and then the handler ignored the claim entirely. That is the whole shape of broken object-level authorization, and it is why Broken Access Control has been A01 in the OWASP Top 10 in both 2021 and 2025: authentication answers "who are you", and everyone remembers to do it, because if you forget the app stops working. Authorization answers "may you have this row", and if you forget it, nothing visibly breaks.

I did not report it as a theory. On a staging tenant with my own account I walked the ID space — the invoice IDs were sequential integers — and pulled about 200 invoices belonging to eleven other staging tenants in under a minute with a shell loop. Then I checked production access logs for the JSON endpoint over 90 days, joining request path against the caller's tenant claim, to see whether anyone had ever done this for real. Nobody had; the highest anomaly was a customer's own integration retrying its own IDs. That log query was the single most useful thing I did, because it turned "we have a catastrophic vulnerability" into "we have a catastrophic vulnerability that has not been exploited", which is a completely different conversation with a CISO at 6pm on a Thursday.

The fix people wanted was to add an if to both handlers. I argued for pushing the check down to the data-access layer instead, because a check you can forget is a check you will forget — there were 60-odd endpoints in that service and I had just proved that two of them were wrong. We made the repository tenant-aware: the tenant came from the request's security context, not from a parameter any caller could set, and there was no way to construct a query without it. Then we added a contract test that ran every route with tenant A's token against tenant B's fixtures and asserted a 404 on all of them. That test found three more endpoints the same week. What I would do differently: I would not have switched to UUIDs at the same time, because it let two people on the team believe the unguessable ID was the fix. It is not a fix, it is a speed bump — and mixing a real control with a cosmetic one in the same PR made the postmortem muddier than it needed to be.

What the interviewer is really probing. Not "do you know what IDOR is" — everyone does. They want to see whether you verified the finding before escalating it, whether you thought about blast radius and prior exploitation, and whether your fix was structural or a patch. The common failures on this archetype: describing the bug for four minutes and the fix for twenty seconds; claiming solo credit for a fix a team shipped; saying "we switched to UUIDs" as though obscurity were access control; and having no answer for "how do you know it never happened".

(c) Recall prompts

When did you last find a security bug in a code review rather than from a scanner or a report?

Hint: it is often a "copy the neighbouring handler" PR, a new export/report endpoint, a mobile-only API, or a v2 route that skipped a middleware the v1 route had. Also check: admin impersonation features, bulk endpoints, and anything with ?userId= in a query string.

Have you ever had to prove a vulnerability was not exploited? How did you do it?

Hint: access logs joined against identity claims, database audit tables, CDN/WAF logs, object-storage access logs, or an application audit trail. The interesting part of the answer is what you could not prove and how you handled that honestly — most log retention is 30–90 days.

Where does authorization live in a system you have worked on — and could you draw it on a whiteboard right now?

Hint: name the layer (gateway, middleware, service, repository, database RLS), the source of truth for the subject (token claim, session, header) and the one place where it is bypassed on purpose. Every real system has that one place.

Have you introduced a test that encodes a security invariant rather than a feature?

Hint: cross-tenant fixtures, an unauthenticated smoke run over the full route table, a "no route may be added without an authorization attribute" reflection test, or an archunit-style rule. If you have not, this is the cheapest thing you can build before your next interview and talk about honestly as recent work.

(d) Follow-up drill chain

Why 404 and not 403?

A 403 confirms the object exists, which hands an attacker a free enumeration oracle: they can map your ID space without ever reading a record. So for object-level authorization failures on resources the caller cannot see at all, I return 404. The exception is when the caller demonstrably knows the object exists — a shared document they were invited to and then removed from — where a 403 is more honest and generates a better support ticket. It is a deliberate trade of usability against enumeration, and I write the reasoning down, because someone always "fixes" it later.

You moved the check into the repository. What did you trade away?

Discoverability and flexibility. A reader of a controller can no longer see the rule that protects the endpoint, so it has to be documented and it has to be tested loudly, or the next team assumes there is no rule. It also makes legitimate cross-tenant work awkward — support tooling, billing rollups, migration jobs — so we added an explicit withElevatedScope(reason) path that is logged and alerted on. That escape hatch is now the highest-value target in the service, and I treat it that way: it is reviewed by two people and has its own tests.

At what scale does the tenant-scoped repository stop being enough?

It breaks down when the data model stops being a tree rooted at one tenant. As soon as you have shared objects, delegated access, partner tenants or per-object ACLs, "filter by tenant_id" is the wrong shape and you need a relationship-based authorization model — a Zanzibar-style tuple store or a policy engine with a decision API — plus caching, because you have just added a network hop to every read. It also strains when reporting and analytics bypass the application entirely; that is where I would move enforcement into the database with row-level security so the guarantee survives whichever client is talking to it.

How would you find every other instance of this bug class across the estate, not just in this service?

Three passes, cheapest first. A static pass: a query over the route table for handlers that take an ID parameter and never touch the security context — imperfect, but it ranks the review queue. A dynamic pass: the cross-tenant contract test generalised into a shared test package that any service can adopt, run in CI against seeded fixtures. And a runtime pass: log the tenant claim alongside the tenant of every row returned and alert on mismatches in staging first, then production — that catches the cases the other two miss because it observes real behaviour rather than intent.

The team wants to ship the fix silently. Do you disclose?

My default is that the disclosure decision is not mine to make alone, but the escalation is: I take it to whoever owns risk with the evidence — reproduction, exposure window, exploitation evidence — the same day. If there is no evidence of access, many regimes do not require customer notification, but that is a legal judgement made by people with that job, not an engineering shortcut. What I will not accept is a fix that ships without an incident record, because the record is what makes the "how do we prevent this class" work fundable next quarter. Since 11 September 2026 there is also a hard external clock in the EU for actively exploited vulnerabilities in products in scope of the Cyber Resilience Act — 24-hour early warning, 72-hour notification — which makes "let us think about it for a week" an unavailable option.

02The thumbnail service that read the metadata endpoint

Senior Production incident / outage

(a) Worked example EXAMPLE — replace with your own

The page was "paste a link and we'll show a preview card". A user pastes a URL, a small service fetches it server-side, extracts the Open Graph tags, renders a thumbnail. It had been in production for two years. What woke us at 02:40 was not the vulnerability — it was the symptom: cloud provider anomaly detection flagged an access key belonging to the preview service's instance role being used from an address in another country. The key had never left the VPC in its life.

The chain was textbook server-side request forgery, which in the 2025 Top 10 is no longer its own category — it was absorbed into A01 Broken Access Control, which is a better description of what it actually is: the server making a request on the attacker's behalf with the server's own privileges. Someone submitted a URL that resolved to the instance metadata service. Our allowlist checked the hostname against a regex for public schemes and blocked obvious private literals, but it did the DNS resolution twice — once in the validator, once in the HTTP client — so a DNS name that answered public on the first lookup and 169.254.169.254 on the second walked straight through. Classic time-of-check to time-of-use. Worse, the instance was still allowing IMDSv1, so a single unauthenticated GET returned role credentials; IMDSv2's PUT-then-token handshake plus a hop limit of 1 would have made the same request useless, because a fetch originating from a container one hop away cannot complete it.

Incident command was mine. First fifteen minutes: revoke the role session (not just the key — session tokens outlive key deletion if you get that wrong), then block egress from that service's security group to link-local, then turn the preview feature off behind a flag. That order mattered — I killed the credential's power before killing the feature, because the feature being off does not help if the attacker already has a session. Only then did we start reading logs. The real fix took three weeks: resolve the hostname once, pin the resulting IP, pass that IP to the HTTP client with the Host header set, reject every non-public address after resolution including the redirect target of every hop, cap redirects at two, and move all outbound user-controlled fetching behind an egress proxy in its own account with no instance role at all. What I would do differently: we had a Jira ticket saying "enforce IMDSv2" from fourteen months earlier, sized at two points. I would trade a lot of clever validation code for having simply closed that ticket.

(d) Follow-up drill chain

Why revoke the session before disabling the feature?

Because the feature flag only closes the door the attacker came through; it does nothing about the keys already in their hands. A role session token stays valid until it expires no matter what you do to the underlying key or the code path that leaked it, so the highest-value first action is to invalidate the session itself — a deny-all policy attached to the role with a "tokens issued before now" condition, or however your provider expresses it. Once the credential is inert, I can take my time on the feature. The general rule I apply in these incidents: revoke the capability first, then remove the access path, then investigate — investigating first feels rigorous and costs you the window.

Your allowlist was a regex. What would you write instead, and why is that still not enough?

I would not validate the URL string at all beyond scheme and length; I would validate the resolved address, resolve exactly once, connect to that address explicitly with the Host header set, and re-run the check on every redirect hop with a small hop cap. That kills rebinding and redirect abuse. It still is not enough, because an attacker can point you at a perfectly public host that happens to be an open proxy into someone's network, and because internal services that trust the network are reachable from anything that can make an HTTP request. That is why the durable control is architectural — an egress proxy with no credentials, in an account that cannot see anything worth stealing.

At what scale does an egress proxy become the problem?

When it becomes a shared, credentialed choke point. If every service in the estate fetches through one proxy and that proxy accumulates allowlists, custom headers and eventually authentication material for partner APIs, you have rebuilt the vulnerable service at higher privilege and with more customers. I keep it dumb on purpose: no credentials, no per-tenant configuration in the proxy, decisions expressed as policy delivered from outside. It also becomes a latency and availability question — a single proxy in the path of every outbound call needs the same SLO thinking as a database, and I have seen teams discover that during an unrelated outage.

How did you decide when the feature could go back on?

I wrote down the exit criteria before the fix work started, so the decision was not made by whoever was most tired. Ours were: the fetcher runs with no instance role at all; metadata v2 enforced with hop limit 1 on the whole account, verified by a config rule rather than by someone looking; per-hop validation covered by tests including a rebinding case with a real short-TTL DNS name; and detection in place — an alert on any outbound connection from that service to a non-public address. Two of those were platform changes other teams owned, which is why the feature stayed off for eleven days rather than three.

What did the postmortem change beyond this service?

Three things, in ascending order of value. A rule in the cloud configuration baseline that fails any instance still permitting metadata v1 — mechanical, done once, protects everything. A shared HTTP client library with the resolve-once behaviour built in, so a team has to work to get it wrong. And a change to how we rank "security debt" tickets: anything that removes a credential from a blast radius jumps the queue over anything that adds a detection, because detections tell you about damage and reductions in blast radius prevent it. That last one is the answer I would lead with at staff level.

03The worm in the lockfile

Staff On-call firefighting

(a) Worked example EXAMPLE — replace with your own

A Tuesday morning notification from our registry proxy: a package four levels deep in our front-end dependency tree had published a patch version 40 minutes earlier that contained a preinstall script. We had already pulled it, because a scheduled dependency-update job had run at 06:00 and CI had happily built the branch. This is the shape of the self-replicating npm campaigns that have been running since September 2025 — the Shai-Hulud family and its successors, which spread by harvesting a maintainer's credentials from a CI environment and using them to publish trojanised versions of every other package that maintainer can touch. The August 2026 wave alone backdoored packages with well over a billion monthly downloads between them. Software Supply Chain Failures entering the OWASP Top 10 as A03:2025 was not a fashion decision.

What the malware wanted was not our source. It wanted the environment of the build: registry tokens, cloud OIDC assertions, anything in ~/.npmrc, ~/.aws, the CI runner's own token, and the cloud metadata endpoint. So the incident question was never "is our code compromised" but "what could that runner reach, and for how long". We had a partial answer ready because we had done the audit six months earlier, and a terrible answer for one repo: an old release pipeline still used a long-lived publishing token stored as a repository secret. Everything else had already moved to short-lived OIDC after npm revoked all classic tokens on 9 December 2025 and capped granular tokens at 90 days — that forced migration turned out to be the single control that saved us the most work, and we had grumbled about it at the time.

The response was mechanical because we had rehearsed the credential half of it: freeze the registry proxy to deny all versions published in the last 24 hours, rotate every secret the affected runners could see, invalidate the runner images, and diff the lockfile against the last known-good commit to establish exactly which versions landed on which branches. The slow part was the boring part — proving the malicious version never reached a production artefact. That took eight hours and would have taken twenty minutes if our build provenance had been complete; we had SBOMs for services but not for the front-end bundle, so we were reading CI logs to reconstruct what had been built from what. What I would do differently: I would have insisted, a year earlier, on a registry proxy with a cooldown — no version younger than 48 hours may be resolved unless a human overrides it. It costs nothing, it would have made this a non-event, and I lost that argument the first time because I framed it as security rather than as build reproducibility.

Whether you can run an incident whose blast radius is credentials rather than data, and whether you understand that supply-chain response is mostly an inventory problem. They are listening for: the order of rotation, how you decided what was and was not affected, evidence rather than assertion, and one honest sentence about the control you did not have. Rambling doom about "the supply chain is broken" with no specific control you personally shipped is the failure mode here.

(d) Follow-up drill chain

Why rotate secrets before you know whether the code actually executed?

Because the cost asymmetry is enormous. Rotation is hours of annoyance; a stolen publishing token or cloud credential that stays valid for another week is an unbounded loss, and these worms are specifically built to exfiltrate and then use credentials quickly and quietly. So I rotate on plausible exposure, not on proven exposure, and I say so explicitly in the incident channel so nobody waits for certainty. The corollary is that rotation has to be cheap and rehearsed — if rotating a secret takes a change-advisory board, teams will delay it, and that delay is the actual vulnerability.

Would trusted publishing with OIDC have prevented this?

For our own packages, largely yes — there is no durable token in the runner to steal, which is exactly why npm pushed the ecosystem onto it. But it does not protect us as a consumer: the compromise happened in someone else's pipeline, and their adoption of OIDC is not something I control. It also is not a free win. OpenJS publicly cautioned in 2026 that OIDC trusted-publisher workflows introduce their own misconfiguration failure modes — an over-broad workflow claim, a fork that can trigger the publishing job — and recommended critical projects harden what they have rather than migrate reflexively. So my honest answer is: adopt it, and threat-model the adoption.

At what scale does "pin everything and review every bump" stop working?

Almost immediately, if you mean human review of every transitive change. A mid-sized front end pulls a four-figure number of transitive packages and sees dozens of updates a week; nobody reads that diff, and pretending otherwise produces rubber-stamping, which is worse than no review because it manufactures false assurance. What scales is a small set of mechanical properties — a cooldown window, no install scripts, provenance verified for the packages that have it, an inventory that answers containment questions in seconds — plus deep human review reserved for the twenty packages that actually sit in a trust-critical path, like your crypto, auth and serialisation libraries.

How do you handle the update-latency trade-off a cooldown introduces?

A cooldown delays patches as well as attacks, so it needs a bypass with a clear trigger: a fix for a vulnerability that is on the CISA KEV catalogue or has a high EPSS score gets an immediate, named override. In practice the exposure is tiny — the window where you are unpatched is measured in a day or two, whereas the malicious-version window it closes is where the overwhelming majority of these campaigns live — but it is a real trade and I would not pretend otherwise to an interviewer. What I would not do is set the cooldown so long that people route around it; a control everyone bypasses is worse than no control, because it also lies to you.

What if the compromised package had reached production?

Then it changes from an inventory exercise into a full incident with a customer-impact question, and the clock starts: since 11 September 2026, an actively exploited vulnerability in a product in scope of the EU Cyber Resilience Act carries a 24-hour early warning and a 72-hour full notification obligation, so legal and comms are in the room from the first hour, not the second day. Technically I would treat every credential the running workload could see as burnt, redeploy from a known-good digest rather than rebuild from source, and preserve the compromised artefact and the runner image for forensics before deleting anything. And I would resist the pressure to declare it over at the moment the bad version is gone — persistence in these campaigns has included self-hosted runners and repository backdoors, so "we removed the package" is not the same statement as "we removed the attacker".

I ran it as an explicit trade-off exercise rather than an opinion contest, because the team had already split into camps. (d) Follow-up drill chain

Why not just isolate everyone? Isolation is strictly safer.

It is strictly safer per tenant and strictly worse in aggregate at the scale we were heading for. Every schema change becomes an orchestration problem with partial-failure states, tenants drift apart in version, connection counts and idle capacity multiply, and your operational tooling has to grow up overnight. At what scale does row-level security break?

Two places. Query planning: policies are predicates, and on large partitioned tables a policy that the planner cannot push down turns index scans into sequential scans — we caught a report going from 40 ms to 6 s in load testing, and fixed it by making tenant_id the leading column of the index and partitioning on it. And connection reuse: any pooling layer that multiplexes sessions — an external pooler in transaction mode, a serverless driver, an ORM that caches prepared statements across contexts — is a potential leak of the session variable, so the pool integration is the part I test hardest and the part I would rewrite first if we changed database technology.

What would make you revisit the decision?

I wrote the triggers into the design document so it would not be a matter of mood: a regulated customer whose contract requires physical separation as a matter of law rather than preference; a tenant whose data volume distorts the shared cluster's performance for everyone else; or a second cross-tenant leak after RLS, which would mean the mechanism itself is not holding and my central assumption was wrong. Absent one of those, we do not reopen it — I am as interested in preventing relitigating as in making the right call, because architectural churn has its own cost and it is usually paid by the newest person on the team.

How do you prove the isolation to an auditor or a customer?

Not with a diagram. I demonstrate it: a test in CI that authenticates as tenant A and attempts every read path against tenant B's seeded data, including the raw SQL paths, and fails the build on any row returned. That artefact — a named, versioned, continuously running test with output an auditor can read — has ended more questionnaire threads for me than any amount of prose. I pair it with the policy definitions themselves, because "the guarantee is in the database and here is the DDL" is a much stronger claim than "our services always filter", and any competent auditor knows the difference.

Staff Migration / platform rollout

(a) Worked example EXAMPLE — replace with your own

A pentest report landed with three reflected XSS findings in an admin area, and the recommendation attached to all three was "implement a Content Security Policy". The application was a nine-year-old server-rendered app with a jQuery era underneath and a React island bolted on top: roughly 180 inline <script> blocks, four analytics vendors, an embedded chat widget that injected its own scripts, and a templating layer that concatenated HTML strings in about forty places. The existing header was the header everyone has: script-src 'self' 'unsafe-inline' 'unsafe-eval', which is a policy in the same sense that an unlocked door is a lock.

The first thing I did was set expectations, because "implement CSP" had been written on a ticket as if it were a configuration change. CSP does not fix XSS; it is the second layer that makes an injection non-exploitable, and it only does that if the policy is strict — nonce-based with strict-dynamic, not an allowlist of hostnames, because host allowlists are routinely bypassable through JSONP endpoints and open redirects on the allowed hosts. The first layer still has to be contextual output encoding at the templating level, which meant fixing the forty string-concatenation sites regardless. I made that explicit in writing so nobody could later say the CSP work had failed because a new XSS was found.

We ran it in three phases over about four months. Phase one: emit the strict policy in Content-Security-Policy-Report-Only alongside the existing enforced weak one, with a report endpoint of our own — with sampling, because the first day produced 1.2 million reports, the great majority from browser extensions injecting scripts into our pages, which is the noise everybody discovers and nobody warns you about. Phase two: work the real violations down, which meant a per-request nonce plumbed through the template layer, moving inline handlers to attached listeners, and one hard negotiation with the chat vendor whose loader used eval. Phase three: enforce, starting with the admin area (small audience, high value), then a percentage rollout on the main app with a kill switch, watching JavaScript error rates as the real signal rather than the reports. Then we did the same dance again for require-trusted-types-for 'script', which is the control that actually kills DOM XSS by making the dangerous sinks refuse plain strings — worth knowing that this only became genuinely cross-browser in early 2026 when Firefox shipped it, so "Chromium-only" is a stale objection now. What I would do differently: I would have started with Trusted Types in report-only on day one rather than after CSP, because its violation reports are a free, precise inventory of every DOM sink in your codebase, and I spent weeks building a worse inventory by hand.

(d) Follow-up drill chain

Why is 'unsafe-inline' in your policy next to a nonce?

Backwards compatibility, and it is deliberate. Browsers that understand nonces ignore 'unsafe-inline' when a nonce is present, and browsers that understand strict-dynamic ignore the https: host source; so the fallbacks only apply to old engines that would otherwise get no policy at all. It looks alarming in a scanner report and I have had to explain it more than once — which is a genuine cost, because a control that looks wrong to auditors generates recurring work. If my traffic no longer includes those engines, I drop the fallbacks and take the simpler header.

You cache pages at the CDN. What does that do to your nonce?

It breaks it, unless you handle it explicitly: a nonce reused across cached responses is not a nonce, and an attacker who can read one response knows the value to inject into another. The options are to make the nonce vary per response at the edge — an edge function or ESI that substitutes a fresh value into both the header and the markup — or to switch to hashes for the static script set and reserve nonces for dynamic pages, or to exclude the pages with injectable content from full-page caching. I have shipped the third and regretted it, because "which pages have injectable content" drifts; the edge substitution is more work up front and stays correct.

At what point is CSP not worth the effort?

When the application already has no inline script and a modern framework escaping by default, the marginal benefit is smaller and the honest answer is that the same weeks are better spent elsewhere — on authorization, for example, which is where the actual breaches are. I would still ship object-src 'none', base-uri 'none' and frame-ancestors, because those are one line and prevent real attacks, and I would still take Trusted Types because DOM XSS survives modern frameworks perfectly well. What I would not do is spend a quarter making a strict nonce policy work on an app with four ad vendors whose contracts I cannot change; there I would say plainly that the control is not achievable and put the effort into reducing what an XSS could reach — short sessions, sensitive actions re-authenticated, cookies scoped and HttpOnly.

How do you know the policy is actually protecting anyone rather than just being present?

I test it as an attacker would: take the original pentest payloads, replay them against the enforced policy, and confirm they now fail to execute rather than trusting that the header implies it. Beyond that, the report endpoint is a live detector — a sudden spike of violations from a single page is either a new third-party script or someone probing, and both are worth a look. And I track a boring operational metric, the ratio of violations from our own origin versus from extensions, because that ratio tells me whether the policy is drifting out of date as the app changes.

What did you trade away?

Developer velocity on the front end, honestly. Adding a script tag is no longer free, inline event handlers are gone, and a few third-party integrations are now a conversation with the security-minded person instead of a copy-paste. I tried to make that cost small rather than pretend it did not exist: a helper in the template layer that emits the nonce so nobody hand-writes it, a documented path for adding a vendor, and a report-only mode developers can flip locally. The trade I would defend to anyone is Trusted Types, where the constraint is genuinely narrow — it only bites at the DOM sinks, which is exactly where you want people to slow down.

06The token that validated and shouldn't have

Senior Nasty debugging session

(a) Worked example EXAMPLE — replace with your own

A support engineer mentioned in passing that a test account from the staging environment appeared in a production audit log. Nobody believed it — the environments had separate identity providers, separate signing keys, separate everything — so it sat for two days as "probably a log-shipping mistake". It was not. A staging-issued access token was being accepted by a production service, and the reason took most of a day to find because every individual piece of the system was behaving exactly as documented.

The service validated JWTs with a well-regarded library, fetched the issuer's JWKS, and cached keys by kid. Two things combined. First, the cache was a process-wide map keyed only on kid, with no association back to the issuer it came from — and staging and production had, through a copy-pasted key generation script, produced key IDs that collided. Second, and this is the part that actually mattered, the validation call checked signature, expiry and issuer format but never checked aud. So a correctly signed, unexpired token from a different environment satisfied every check the code performed. The library was not wrong; nobody had told it what audience to require, and the default for that option was "do not check".

Finding it took a token-by-token diff. I pulled a sample of accepted tokens from the request log — header and claims only, never the signature — and grouped them by iss. A small number had an issuer nobody recognised, which is when the "log-shipping mistake" theory died. Then I wrote a twelve-line script that took a real staging token and replayed it against a production endpoint, and got a 200. That is the moment to stop investigating and start containing: rotate production signing keys, add the audience check, deploy, and only then finish understanding. The durable fixes were three. Validate aud, iss and the algorithm against an explicit allowlist, never against whatever the token asserts. Key the JWKS cache on (issuer, kid) and never fetch a key for an issuer that is not on the allowlist — that closes both the collision and the classic "fetch the key from the URL in the header" hole. And add a contract test per service that asserts a token from every other environment is rejected. What I would do differently: I would treat an unexplained anomaly in an audit log as an incident from the first hour. Two days of "probably nothing" is the actual failure in that story, and it is the part interviewers find most interesting.

(d) Follow-up drill chain

Why is validating the signature not enough?

Because a signature answers "was this issued by a key I have", not "was this meant for me, and is it still valid". Audience is what binds a token to a specific resource server; without it, any service that trusts the same issuer accepts every token, so a token minted for a low-value internal tool works against the payments API. That is why I treat aud as the load-bearing claim in a service-to-service estate and give every resource server its own audience value. The other half of the answer is that a bearer token grants power to whoever holds it, which is why sender-constrained tokens — DPoP or mTLS binding — are the real hardening rather than more claim checking.

What if the JWKS endpoint is down when a key rotates?

You have to decide fail-open or fail-closed before it happens, and I fail closed on validation while caching aggressively so the situation is rare: keys are cached well past their fetch interval, a background refresh keeps them warm, and a fetch failure serves the stale key rather than skipping validation. The one thing I will not do is accept an unvalidated token because the key server is unreachable — that converts an availability incident into an authentication bypass, and I have seen exactly that shipped as a "resilience improvement". Worth stating the operational consequence honestly: this means your identity provider is in the critical path of every request, so it needs the availability budget to match.

At what scale does per-service audience validation become a burden?

At the point where you have enough services that issuing and rotating audiences is manual. The failure I have seen is teams sharing one audience value across a dozen services because managing them was annoying, which quietly recreates the original bug. The fix is to make audience allocation part of service creation in your platform tooling — a new service gets an identity, an audience and a scope set automatically — so nobody ever has to think about it. Above that scale you generally also want a token exchange pattern, where a coarse user token is exchanged for a narrowly scoped, short-lived token per downstream hop, rather than passing one powerful token through the whole call graph.

How would you detect this class of problem rather than stumble on it?

Log the issuer and audience of every accepted token as structured fields, then alert on any value that has not been seen before for that service. It is a cheap anomaly detector with a naturally low cardinality, and it would have fired within minutes in this story instead of surfacing in a support conversation two days later. I would pair it with a periodic synthetic check — a job that fires a deliberately wrong token, from another environment, at each service and alerts if the response is not a 401 — because a detector that only watches real traffic tells you nothing about a path nobody is currently attacking.

Would you move off JWTs entirely?

For internal service-to-service traffic I have argued for it more than once: opaque tokens with introspection put revocation back in your hands and stop developers reading claims they should not depend on, at the cost of a network call per validation and a hard dependency on the introspection endpoint. For user-facing APIs at scale the stateless verification of a JWT is usually worth keeping, but I shorten lifetimes aggressively and add a revocation list for the sessions that matter. So my honest position is that the choice is about revocation latency versus availability coupling, not about which format is "secure" — and anyone who answers this question with a blanket "JWTs are bad" has not run the introspection endpoint at three thousand requests per second.

Staff Scaling challenge

(a) Worked example EXAMPLE — replace with your own

The trigger was a routine question from an auditor: "when was this database password last changed?" I refused to start with a tool. The first two weeks were inventory: a scan of every repository's full git history for high-entropy strings and known credential formats, plus a survey of what each service actually read at startup. The history scan is the part people skip and it is the part that matters, because a secret committed in 2019 and "removed" in the next commit is still sitting in the object store of every clone. We found 63 live credentials in history, including a cloud key that still worked. Those got rotated in the first sprint, before anything architectural happened, because a leaked-and-valid credential outranks every design discussion.

Then the ladder, deliberately in this order. Rung one: get every secret out of files and into a managed secret store, injected at runtime. That is not much of a security improvement on its own — a secret in memory is still a static shared secret — but it is a huge operational improvement, because it makes rotation a one-place change and that is the prerequisite for everything else. Rung two: make services reload secrets without a deploy, which turned rotation from a change-management event into a background job. Rung three, the real prize: delete the secret entirely wherever an identity could replace it — workload identity federation to the cloud APIs, short-lived database credentials issued per pod, OIDC in CI instead of stored publishing tokens. Each of those removes a value that can be stolen rather than protecting it better. We got about 60% of the 400 to rung three within two quarters; the remainder were partner API keys where the other side only supported static credentials, and those got documented as accepted risk with a rotation schedule. What I would do differently: I let "rotate everything quarterly" become a calendar ritual for a while. Scheduled rotation of a secret nobody can rotate safely is theatre; I should have measured time-to-rotate as the metric from the start, because that number is what you actually need on an incident day.

(d) Follow-up drill chain

Why not start with the vault? It is the obvious first move.

Because moving 400 unknown secrets into a store gives you a tidier inventory of a problem you have not reduced, and it consumes the political capital you need for the actual change. Rotating the credentials that were already leaking was both more urgent and much easier to justify to leadership — it produced a number that went down. It also taught us which secrets were genuinely load-bearing, which shaped the migration order. The general principle I would state at staff level: sequence the work so each phase produces evidence that funds the next one, especially in security programmes where the benefit is invisible when everything goes right.

Rotating a database password mid-flight breaks connections. How did you handle that?

Two-slot rotation: the database accepts two valid credentials simultaneously, you introduce the new one, wait for all consumers to pick it up, then retire the old. That requires the secret store and the application to agree on a version, and it requires connection pools to re-authenticate rather than hold a session forever — which was the part that actually needed code changes in three services. Once you have two-slot rotation working, the frequency question becomes uninteresting, which is the point: I would rather rotate quarterly with a mechanism that works than monthly with a mechanism that risks an outage each time.

At what scale does a central secret store become a liability?

When it is in the request path and becomes a single point of failure — every pod starting at once after a zone failure can hammer it hard enough to slow your recovery, so caching and graceful degradation on read are not optional. It also concentrates risk: a compromise of the store or of its authentication is a compromise of everything, so its own access policy, audit log and break-glass path deserve more scrutiny than any individual service. That concentration is another argument for the workload-identity rung — the fewer secrets that exist at all, the less the store matters, and the best outcome is that it holds only the partner keys you cannot eliminate.

What about the secrets you could not eliminate?

They went on a register with an owner, a rotation interval, a documented rotation procedure that had actually been executed once, and a review date. The discipline that made it real was requiring a rehearsal: an unrehearsed rotation procedure is a wish, and I have watched a "documented" rotation fail at 2am because the runbook referenced a tool that had been decommissioned. For partner keys specifically I also asked for a contractual note in the next renewal that we expect OIDC or mTLS support, which is slow but it is how the ecosystem actually moves.

How do you stop it from regressing?

Detection at the point of introduction rather than after: a secret scanner in the pre-receive hook and in CI so a committed credential fails the push, plus provider-side push protection where the registry supports it. But detection alone regresses, because people route around friction, so the other half is making the good path easier — a library that fetches credentials with three lines and templates that ship with workload identity already wired up. When I review a security programme now, the question I ask is not "what does the policy say" but "what is the path of least resistance for someone in a hurry", because that is the path everyone takes.

Senior Technical disagreement with a colleague

(a) Worked example EXAMPLE — replace with your own

A code review disagreement that turned into a three-week argument. A senior colleague had built a reporting feature where the user picks columns and a sort order, and the service assembles SQL by concatenating strings. He had escaped quotes and added a regex that rejected a list of SQL keywords, and when I asked for parameterisation he made the argument I have now heard a dozen times: the endpoint is behind a WAF with SQL-injection rules, it is authenticated and internal-only, and parameterising identifiers is not even possible in the driver. Two of those three statements were true, which is what made it a real disagreement rather than a teaching moment.

He was right that you cannot parameterise a column name — placeholders bind values, not identifiers — and that is exactly why the answer for identifiers is an allowlist mapping, not escaping: the user sends sort=recent, and a lookup table turns that into the literal string created_at DESC that your code owns. Values, meanwhile, go through placeholders every time, no exceptions. I did not win by asserting this. I wrote a test that got through his filter: the keyword regex was case- and whitespace-sensitive in ways that comments and inline /**/ separators trivially defeat, and because the filter ran before a Unicode normalisation step elsewhere in the stack, a homoglyph got through untouched. Then I showed the second-order case, which is the one that ends these debates: a value stored earlier by a legitimate user, re-read from the database, and concatenated into a later query. The WAF never sees that request at all, because it originates inside the datacentre.

The part I got wrong was social, not technical. I ran the demo in a team channel, which made a correct argument feel like an ambush, and he defended the position harder than he otherwise would have. What worked was pairing with him the next morning to convert the endpoint together and letting him present the pattern at the next guild session, which is also how it spread to four other services. On the substance we ended up with a genuinely better design than my original ask: parameterised values, an allowlist for identifiers, and the query builder wrapped so that raw string SQL requires an explicit, greppable rawUnsafe() call that trips a lint rule. What I would do differently: demonstrate privately, credit publicly. The WAF stayed, by the way — as detection and as a stopgap for emergency virtual patching, which is what it is genuinely good at, and I say so rather than sneering at it, because dismissing a control your colleague values is how you lose the next argument.

(d) Follow-up drill chain

He said the endpoint was internal-only. Why is that not a mitigation?

Because it assumes the network is a trust boundary, and in any estate with more than a handful of services it is not one — an SSRF, a compromised sidecar, a partner integration, or a single stolen employee session puts an attacker inside that boundary, and then "internal" means "undefended". It also ignores second-order injection entirely: data stored by an ordinary user through a legitimate path becomes the payload when a later query concatenates it, and no perimeter sees that request. I do not dismiss the point entirely — internal-only genuinely lowers likelihood, and likelihood matters for prioritisation — but it changes the ranking of the fix, not whether the fix is needed.

Is there ever a case for dynamic SQL?

Yes, and pretending otherwise loses credibility. Complex search, dynamic reporting and admin tooling genuinely need query shapes assembled at runtime, and the answer is not to ban it but to constrain it: build the query from a typed structure rather than strings, bind every value, map every identifier through an allowlist your code owns, and make the raw path explicit and greppable so review can find it. I would rather have one clearly marked rawUnsafe() call site that three people have read than a codebase where every repository quietly concatenates. The same reasoning applies to NoSQL and to ORMs — an ORM does not save you, because most of them expose a raw method and someone will reach for it.

At what scale does "review will catch it" stop working?

Immediately, for a rule that depends on a reviewer noticing an absence. Humans are good at spotting wrong code and bad at spotting missing code, which is why every durable fix in this story is mechanical: a lint rule, a wrapper type, a build failure. Above a couple of dozen engineers you also lose the shared context that made review effective — new joiners have not seen the incident, and the norm decays. So my staff-level answer is that a disagreement resolved only in a review thread has not been resolved; it has been postponed until the person who cared about it leaves.

What would you have done if he had refused?

I would have written the risk down plainly — the specific attack, the data reachable, what makes the mitigation insufficient — and taken it to whoever owns that risk, naming him as the design author without editorialising. Escalation is a legitimate move and I would not apologise for it, but it costs relationship capital and it is a one-shot tool, so I use it after I have genuinely tried to be convinced myself. In practice I have had to escalate twice in my career, and both times the process was more useful than the outcome, because writing the risk down forced me to be precise about likelihood and impact instead of relying on the word "insecure".

Injection has been in the OWASP Top 10 forever and dropped to A05 in 2025. Does that change your priority?

The movement reflects that frameworks and ORMs now do the right thing by default, so the base rate is genuinely lower — that is real progress and worth acknowledging rather than performing alarm. What it does not mean is that injection is solved, because the remaining cases cluster exactly where the frameworks stop helping: dynamic reporting, admin tools, migration scripts, and now prompt construction for LLM features, which is structurally the same mistake with a new interpreter. So I read the ranking as a hint about where to spend review attention, not as a licence to skip the control — and I would push back on anyone using the 2025 list to justify closing injection findings without a fix.

09The encryption we wrote ourselves in 2017

Staff Tech-debt paydown / refactor

(a) Worked example EXAMPLE — replace with your own

Every application that has been alive long enough has a file called something like CryptoHelper, written by someone who has left, and ours encrypted about 14 million rows of sensitive customer fields. Reading it was educational in the worst way: AES in CBC mode, a key loaded from an environment variable, a 16-byte initialisation vector that was a constant in the source file, and no authentication tag anywhere. Three separate mistakes, each of which is a textbook example, which is why this became a teaching artefact for the whole team rather than just a refactor.

The static IV is the one people underestimate. CBC with a fixed IV means identical plaintexts produce identical ciphertexts, so the encrypted column leaks equality — you can group rows by ciphertext and learn which customers share a value without decrypting anything, which for a field like a national identifier or a status flag is most of the information you wanted to protect. The missing authentication tag is worse and less visible: unauthenticated CBC is malleable, so an attacker who can modify stored ciphertext can flip bits in a controlled way, and if your decryption path distinguishes "padding error" from "parse error" anywhere — a log line is enough — you have a padding oracle and the whole record can be recovered without the key. I demonstrated that against a copy of the data in a sandbox, which is what turned this from a backlog item into a funded quarter of work.

The replacement was deliberately boring: AES-256-GCM through the platform's vetted library with a per-record random nonce, envelope encryption with data keys wrapped by a KMS master key so the key never sits in an environment variable, and the record's identifier bound in as additional authenticated data so a ciphertext cannot be moved from one row to another. The migration was the actual engineering. You cannot stop a live system to re-encrypt 14 million rows, so we versioned the ciphertext with a one-byte prefix, taught the read path to handle both formats, wrote only the new format, and ran a background re-encryption job with a resumable cursor at a rate the database could absorb — eleven days, throttled deliberately. Only when a counter of remaining v1 rows hit zero did we delete the old code path, and that deletion was its own celebrated pull request. What I would do differently: I would have built the ciphertext version prefix before I needed it. We spent two weeks retrofitting a discriminator onto data that had none, and that is a cost I now pay up front in every design that stores ciphertext, because there will always be a next migration — the visible one on the horizon is post-quantum, and the estate that can roll its algorithm forward without an archaeology project is the one that will handle it calmly.

(d) Follow-up drill chain

Why AES-GCM rather than CBC with an HMAC?

Encrypt-then-MAC with a separate HMAC is cryptographically sound and I would accept it in review, but it is a construction you have to assemble correctly — two keys, the right order, a constant-time comparison — and every one of those is a place a future maintainer gets it wrong. An AEAD gives you one primitive that cannot be assembled incorrectly in the same ways, and the platform libraries make it hard to misuse. The one real hazard I flag is nonce reuse, because GCM fails catastrophically if you repeat a nonce with the same key: at high write volumes with random 96-bit nonces I would either use a counter-based nonce with a per-worker prefix, or move to a nonce-misuse-resistant mode like AES-GCM-SIV, which is exactly the sort of "it depends, because" the interviewer wants.

How do you handle key rotation with envelope encryption?

The point of the envelope is that rotating the master key means rewrapping the data keys, not touching the ciphertext — so a rotation is a small job over a key table rather than a rewrite of 14 million rows. Rotating a data key does require re-encrypting the records it covers, so the granularity of data keys is a real design decision: one per record maximises isolation and costs you a KMS call per read unless you cache, one per tenant or per day is the usual compromise. I size that by asking what I would have to re-encrypt after a suspected compromise; if the answer is "everything", the granularity is wrong.

What is your post-quantum position on this data?

Different for data at rest and data in transit, and conflating them is a common mistake. Symmetric encryption at rest — AES-256-GCM — is not meaningfully threatened by known quantum algorithms, so the 14 million rows are fine; the exposure is anywhere we use public-key cryptography for key exchange or signatures. In transit is where the harvest-now-decrypt-later concern is real, and the ecosystem has already moved: hybrid X25519 with ML-KEM-768 is on by default in Chrome and Firefox and widely supported by CDNs, so I would verify our termination points negotiate it and treat anything long-lived and confidential as a priority. The bigger organisational task is inventory — knowing every place we use asymmetric crypto and how quickly we could change the algorithm — which is exactly the crypto-agility argument the version prefix in this story is a small example of.

At what scale does per-record encryption become a problem?

At the point where it collides with querying. Encrypted columns cannot be range-queried or sorted, and equality search only works if you deliberately introduce a deterministic, keyed index — a blind index over an HMAC of the value — which reintroduces exactly the equality leak we were trying to remove, so it is a conscious trade for specific fields, not a default. Throughput is the other wall: a KMS call per record does not survive a bulk export, so you cache unwrapped data keys with a short TTL and accept that they sit in memory. If both constraints bite hard, the honest answer is that field-level encryption may be the wrong tool and the protection should come from access control and tokenisation instead.

How did you verify the migration was correct?

A shadow-read phase before we trusted anything: for a sampled percentage of reads, decrypt with both paths and compare, alerting on any mismatch, which caught a subtle bug where a field had been stored with trailing whitespace that the old padding hid. Then a monotonic counter of remaining v1 rows published as a metric, so "are we done" was a dashboard rather than an opinion, and a scheduled job that scanned for v1 rows for a month after the counter hit zero, because a rarely used write path had been resurrecting them. That last one is the lesson I repeat: a backfill is not finished when the count reaches zero, it is finished when it stays at zero without you watching.

How do you keep threat modelling from becoming a compliance ritual?

Time-box it hard, attach it to a real design that is still changeable, and require that it produces owned tickets rather than a document. The moment a threat model becomes an artefact filed to satisfy a gate, it is worse than nothing because it generates false assurance — so I judge the practice by whether design decisions actually changed, and if three sessions in a row change nothing, either we are modelling the wrong things or the timing is too late. I also rotate the facilitator deliberately; when it is always the security-minded person, the team learns to wait for them rather than to think.

What if the mentee had disagreed with a finding?

Then we would test the disagreement instead of resolving it by seniority — usually by asking what evidence would settle it, then getting that evidence. On the presigned URL, for instance, the question "what does a one-hour window actually let someone do" has a measurable answer, and if it had turned out to be nothing, I would have been wrong and said so in front of the room. That is not politeness; it is the only way the practice survives me, because a session where the senior person is always right teaches people to guess what I think rather than to reason.

At what scale does this stop working?

Facilitated sessions do not scale past a couple of dozen teams with one or two experienced facilitators — you get a queue, and queued security review turns into rubber-stamping. Beyond that I would invest in three things: a security section in the design template with prompts specific to our architecture, a small set of trained facilitators embedded in teams rather than in a central function, and hard triggers so we spend the scarce facilitation on the designs that matter — anything that crosses a trust boundary, handles money or credentials, or introduces a new external dependency. Everything else gets the template and a review, and I am at peace with that, because uniform coverage at low quality is worse than concentrated coverage at high quality.

How do you measure whether the mentoring worked?

Not with a survey. I look for behaviour I did not prompt: a design document that arrives with the trust boundaries already drawn, a review comment that catches an authorization gap, someone volunteering to facilitate for another team. The counter-metric I watch is how often things route through me — if I am still the person every security question goes to a year later, the mentoring did not work no matter how good the individual sessions felt. At lead level I would rather have five people who can each do 70% of what I do than be the only person who can do 100%.

This is the most common shape of security work at staff level — not finding a vulnerability, but negotiating a trust boundary with people whose constraints are real and whose incentives are not yours.

I started by separating what they actually needed from what they had asked for. Their constraint was not "static credential"; it was "we cannot deploy configuration changes quickly". Those are different problems: a client-credentials flow with a private key that they generate once and never change satisfies both — nothing in their configuration rotates, but the credential on the wire is a short-lived token they mint themselves, and if it leaks it is worthless in minutes. I sketched three options with the honest cost of each against their constraint, and gave them a working sandbox and a code sample in their language the same week, because in cross-company integrations the team that produces something runnable first sets the design. That is a tactic, and I would say so to an interviewer.

The direction they were pushing updates to us was the more interesting half. Their webhooks needed authentication we could verify without them holding a secret of ours, so we signed in the other direction: they sign each callback with their own key, we verify against their published JWKS, we require a timestamp within a small window and reject replays by nonce, and — the part teams forget — we made the endpoint idempotent by event ID, because retries are indistinguishable from replays and a status update applied twice is a real business bug. We also scoped their credential to exactly two operations and a set of accounts, so the compromise story is bounded and describable. What I would do differently: I let the credential provisioning live in a spreadsheet shared between two commercial teams for the first three months. When a second partner arrived, we had no self-service, no rotation path and no visibility into who was using what — the integration was secure and completely unmanageable, and that gap took longer to fix than the protocol design took to build.

(d) Follow-up drill chain

Why not just accept the static key and monitor it?

Because monitoring a credential you cannot rotate quickly gives you awareness without agency — you find out you are compromised and then negotiate a six-week change window while the attacker keeps working. I would accept a static key in one situation: a genuinely low-value, read-only scope where the compromise is embarrassing rather than damaging, with a documented expiry date and an owner. What makes that acceptable is the scope, not the monitoring, which is the general principle I would state: bound what a credential can do before you invest in watching how it is used.

Why DPoP rather than plain bearer tokens for the partner?

Because a bearer token is exactly as strong as the least careful place it is written down — a log line, an error report, a proxy access log — and sender-constraining it makes theft alone insufficient, since the attacker also needs the private key that signs the proof. It cost the partner very little because they already had a key registered for the assertion. I would not pretend it is universal: plenty of partner stacks cannot do it, and RFC 9449 support in off-the-shelf gateways is still patchy, so I treat it as the preferred option and mTLS-bound tokens as the equally good alternative when the client is a server rather than a browser.

At what scale does per-partner bespoke integration break down?

Around the fifth partner, in my experience — that is where bespoke terms, bespoke scopes and a spreadsheet stop being viable and you need a real partner platform: self-service key registration, scopes as a published catalogue, per-partner rate limits, usage visibility and a revoke button that someone on support can press at 2am. The security argument for building that is not primarily security; it is that the alternative is a human in the loop for every change, and humans in the loop are how credentials end up permanent. I would fund it by counting the hours the current process consumes across commercial, support and engineering, because that number is usually large and nobody has ever added it up.

Their webhook signing key is compromised. What happens?

We revoke that key from our copy of their JWKS and stop accepting anything signed with it, which is a configuration change on our side and does not require them to deploy — that asymmetry is deliberate and is why I preferred published-key verification to a shared secret. The harder question is what we do about updates already applied while the key was in the attacker's hands, and that is why the idempotency and event-ID design matters: we can replay the partner's authoritative event log to reconcile state rather than guess. I would also expect to detect it, because we alert on signature failures and on events whose ordering or volume departs from the partner's normal pattern.

How did you handle the fact that commercial had already promised something?

I did not treat it as a betrayal, because from their side they promised an integration, not a credential design — the API key detail came from the partner's engineers, and nobody in the commercial conversation knew it was load-bearing. So I took the options table to our own commercial lead first, in their language: same launch date, less risk of a customer-visible incident, and one extra week of partner engineering time that I would supply the sample code for. Getting internal alignment before talking to the partner is the part I would emphasise; going to an external party with an internally contested position is how you end up being overruled in front of a customer.

What if he had insisted?

Then the shape of my job changes from persuading to documenting: I write the risk down in plain language — what data, who can read it, what a breach of the log platform would mean, what regulation it touches — name him as the accepting owner, and get that acknowledged in writing. Why an allowlist rather than redaction?

Because redaction is a denylist and denylists rot: someone adds a field to a DTO six months later, nobody updates the redaction rules, and the field flows into the logs with no error and no alarm. An allowlist projection fails in the safe direction — a new field is simply absent until someone deliberately adds it, and that addition shows up in a code review as a diff that a human can question. The cost is real and I would name it: developers occasionally cannot see the field they wanted during an incident, which is exactly why the short-retention full-capture vault exists as the escape hatch. Safe by default, with a deliberate and audited way to get more.

At what scale does the break-glass vault become the risk?

When access to it becomes routine. A break-glass path used twice a year with a written reason is a control; the same path used weekly is just a slower version of the thing you refused, and it will drift there naturally unless someone watches. So I attach a review to the access log itself — a monthly look at who opened it and why, in front of the team — and I treat a rising trend as a signal that the primary logging is inadequate rather than as a discipline problem. That reframing matters: if engineers keep needing raw payloads, the schema is wrong, and fixing the schema is the durable answer.

How does this change with LLM features in the product?

It gets sharper, because prompts and responses are the new unbounded free-text field and teams log them wholesale for evaluation and debugging — which means customer data, and sometimes credentials a user pasted in, land in a store built for telemetry rather than for sensitive data. I apply the same rule: log identifiers, token counts, model version, latency, tool calls and outcomes by default, and treat the prompt body as a payload that goes to the short-retention, access-controlled store if it is kept at all. The extra wrinkle is that the vendor may retain it too, so the data-flow question extends past your own systems and belongs in the contract, not just the code.

Concretely, it meant that a burst of authorization failures — the exact signature of someone probing object identifiers — would have produced perfect log entries that nobody looked at. That is the failure the 2025 rename is pointing at: the industry got good at collection and stayed bad at detection, and a log you never query is a compliance artefact, not a control. We ended up with a small number of high-signal alerts — a spike in 403s per identity, first-time-seen token issuers, break-glass access, and any failure of the cross-tenant contract test in production — and I deliberately kept the list short, because the fastest way to have no detection is to have eighty noisy alerts and an on-call engineer who mutes the channel.

(a) Worked example EXAMPLE — replace with your own

The dependency scanner had been on for two years and had produced a dashboard with 4,100 open findings, 380 of them "critical". Nobody looked at it. The team's honest position — which I agreed with — was that the tool had never once told them something they could act on, and the one time it had blocked a release, the finding turned out to be in a code path the application does not call. A control everyone has learned to ignore is worse than no control, because it occupies the space where a real one would go and it lets everyone say the box is ticked.

I treated it as a signal-to-noise problem with a measurable target rather than a discipline problem. First, establish what the findings actually were: about 60% were in transitive development dependencies that never ship in a runtime artefact, roughly 25% were in code paths the application demonstrably does not reach, and the remainder were real. Reachability analysis is what collapses that middle chunk — most applications use a small fraction of any dependency's API surface, so "the CVE is in a function nobody calls" is the common case, not the exception. Then rank what is left by exploitation likelihood rather than by CVSS alone: anything on the CISA KEV catalogue is an automatic escalation because there is evidence of real-world exploitation, EPSS gives a probability of exploitation in the next 30 days, and CVSS tells you the ceiling of impact if it happens. Using CVSS severity as a queue is what produced the 380 "criticals" that nobody believed.

The gate we shipped, and the reason the team accepted it, is that it only ever fails a build on something new and actionable: a dependency the change actually introduces or upgrades, in a runtime scope, reachable from application code, and either on KEV or above an EPSS threshold. Everything else becomes a ticket with an SLA by tier rather than a broken build. We also published a VEX statement for the not-reachable findings, so the answer to a customer questionnaire became a document instead of a conversation. The numbers that mattered: build failures from the gate dropped to a handful a month, median time-to-remediate for KEV items went from "never" to under five days, and — the one I would lead with — the team started opening the dashboard voluntarily. What I would do differently: I ran the first two weeks of the new gate in report-only and declared success too early, because a gate that has never blocked anyone has not been tested. The real test was the first time it blocked a release the day before a launch, and I should have rehearsed that conversation before it happened rather than during it.

(d) Follow-up drill chain

Reachability analysis has false negatives. Are you not just hiding risk?

Yes, it has false negatives, and I say so explicitly rather than selling reachability as truth: reflection, dynamic dispatch, configuration-driven code paths and native calls all defeat a static call graph, so "unreachable" means "not reachable by the analysis", not "safe". That is why unreachable findings go to a backlog with periodic review rather than being closed, and why anything on KEV escalates regardless of reachability — when there is evidence of active exploitation I do not trust my own analysis enough to bet on it. The trade I am making is explicit: I accept a small chance of under-reacting to an unreachable finding in exchange for a control the team actually acts on, and I would rather defend that trade than defend 4,100 ignored tickets.

Why gate only on newly introduced dependencies?

Because a gate that fails on the pre-existing backlog blocks every change to a service until an unrelated cleanup is finished, and the reliable outcome of that is a bypass mechanism that becomes the norm. Ratcheting — new code must meet the bar, existing debt is worked down on an SLA — keeps the build meaningful and makes the trend monotonic. It also puts the fix next to the person who has context: the engineer bumping a library is the right person to deal with what that bump brings in, whereas the engineer who happens to touch the service on Tuesday is not.

At what scale does this model break?

It strains when one dependency graph is shared by hundreds of services, because then remediation is a coordination problem rather than a ticket — you need to know which services are affected, which is an SBOM inventory question, and you need to be able to roll a version across the estate quickly, which is a platform capability. It also breaks if the scanner is the only inventory: at that scale you want artefact-level SBOMs stored centrally so "who ships this version" is a query. And it breaks culturally if the SLA has no teeth — an SLA nobody reports on is a suggestion, so I would publish per-team compliance and let the visibility do the work rather than adding an enforcement mechanism.

How do you handle a critical vulnerability with no patch available?

Treat it as an incident-shaped problem rather than a ticket: establish exposure precisely with reachability and with logs, then reach for compensating controls — a WAF virtual patch, disabling the feature that reaches the code, network restrictions, or forking and patching the dependency ourselves, which I have done twice and would do again for something on KEV. In parallel I would file upstream and, if the project is unmaintained, treat that as a supply-chain decision: an unmaintained dependency in a trust-critical path is a design problem, not a patching problem. And I would set a review cadence rather than letting it sit, because "no patch" findings are the ones that quietly become permanent.

Does the EU Cyber Resilience Act change how you run this?

It changes the clock and the paperwork more than the engineering. From 11 September 2026 a manufacturer of an in-scope product must report an actively exploited vulnerability with a 24-hour early warning and a 72-hour full notification, with a final report after remediation — which means the question "is this being exploited in our product" needs an answer in hours, not at the next triage meeting. Practically that pushes three things up my list: an artefact-level SBOM so scope is a query, telemetry good enough to tell exploitation from noise, and a named path to legal that does not start with someone finding the right person on a Sunday. The Act also expects a documented handling process and coordinated disclosure, which is a good forcing function for work most teams have been deferring.

14Argon2id at 900 ms and a login queue

Senior Performance problem diagnosed

(a) Worked example EXAMPLE — replace with your own

We had migrated password hashing from an ancient scheme to Argon2id, which was unambiguously the right move, and three weeks later the login endpoint fell over during a Monday morning peak. The symptom was ugly and misleading: p99 latency on unrelated endpoints climbed to seconds, health checks began failing, and instances were being replaced by the orchestrator while the actual error rate on login was low. It looked like a memory leak or a noisy neighbour. It was neither.

Two things were happening. The parameters had been copied from a blog post — memory 256 MiB, three iterations, parallelism 4 — giving about 900 ms per verification on our instance size, roughly nine times the OWASP-referenced starting point of 19 MiB with two iterations and parallelism 1. And the hashing ran on the same thread pool that served every other request, so each login occupied a request-handling thread for the better part of a second and held a large memory allocation while doing it. At 60 logins a second across the fleet that is not a login problem, it is a capacity problem for the whole service: the pool saturated, queuing delay appeared everywhere, and health checks — which shared the pool — timed out, so the orchestrator killed healthy instances and concentrated the load on the survivors. That last loop is the part I now look for first in any "everything is slow" incident: a shared resource plus an automated remediation that makes it worse.

The fix had three parts and only one of them was tuning. We picked a latency budget first — 250 ms at p50 on our production instance type, measured on that hardware rather than a laptop — and chose the highest memory cost that fit, because with Argon2id memory is the parameter that actually costs an attacker with GPUs, and lowering iterations while keeping memory is a better trade than the reverse. We moved hashing onto a bounded, dedicated pool so a login surge could never starve the rest of the service, and gave health checks their own path. And we added rate limiting per account and per source with progressive delay, which was the real security improvement hiding inside a performance ticket: the reason the parameters mattered so much was that we had nothing else slowing down an attacker who got hold of a leaked hash dump or ran credential stuffing against us. What I would do differently: I would have benchmarked on production hardware during the migration, and I would have argued harder for passkeys at the same time — the strongest answer to "how do we make password verification fast and safe" is to have fewer passwords, and with passkeys now widely deployed for workforce sign-in that argument is much easier to make in 2026 than it was.

(d) Follow-up drill chain

Why not just reduce the work factor and move on?

Because the work factor is the only thing standing between a stolen hash database and a list of plaintext passwords, and the attacker's hardware improves every year while your convenience does not. So I treat the work factor as a floor set by the threat model and the latency budget as the thing I engineer around it — dedicated pools, right-sized instances, admission control. If the budget genuinely cannot accommodate the floor, the honest answer is that we need different hardware or fewer password logins, not a weaker hash. The one legitimate reduction is when you are demonstrably above the recommended baseline for no reason, which was exactly our case: going from 256 MiB to 64 MiB was correcting a copied number, not weakening a control.

How do you migrate work-factor parameters for existing users?

Rehash on successful login: the stored hash carries its own parameters, so you verify with the old ones, and if they are below the current policy you recompute with the new ones inside the same request while you legitimately hold the plaintext. That gives you a gradual, zero-friction migration for active users; the tail of dormant accounts never migrates, so I pair it with a policy — force a reset, or step up to a second factor, for accounts that have not logged in since before the change. Same mechanism works for algorithm changes, which is why I insist the stored format is self-describing rather than implied by a column.

At what request rate does this design stop working?

The hard limit is memory bandwidth and RAM: at 64 MiB per concurrent verification, a hundred simultaneous logins is over six gigabytes of transient allocation, so concurrency has to be bounded and the queue has to reject rather than grow. Past a few hundred logins a second, I would stop scaling the general service and split authentication into its own deployment, sized and scaled independently — which also gives it its own blast radius and its own rate-limit state. And at that scale the strategic answer is the same one I keep landing on: reduce password logins through SSO and passkeys, because the cheapest verification is the one you do not perform.

What did rate limiting buy you that tuning did not?

It defends the case the work factor cannot: an attacker guessing online against a real endpoint, which is credential stuffing and is by far the most common way accounts are actually taken over. Per-account limits with progressive delay slow a targeted attack, per-source limits blunt broad ones, and a global limit protects the service itself; layered like that they cost legitimate users nothing measurable. The design detail I would raise unprompted is that rate limiting must not become an enumeration oracle or a denial-of-service tool against a real user — so the response is uniform, and lockout is a delay rather than a permanent block that an attacker could trigger deliberately on someone else's account.

What was the health-check loop, exactly, and how do you prevent it generally?

Health checks were served by the same thread pool that hashing had saturated, so a slow instance failed its check, the orchestrator removed it, and the load redistributed onto the remaining instances, which then saturated faster — a textbook metastable failure where the remediation is the amplifier. Generally I prevent it by giving liveness checks a path that shares as little as possible with request serving and by making liveness mean "the process is alive" rather than "the process is fast", leaving readiness to shed load without killing anything. The wider lesson I carry into design reviews is to ask what the automated response does when the cause is systemic rather than local — automation that assumes independent failures makes correlated failures worse.

(d) Follow-up drill chain

The premise was right and remains right: a flat internal network where every service can reach every other, authenticated only by being on the network, is a large risk, and lateral movement is how most breaches become expensive. We rebuilt part of it with tracing, but tracing depends on instrumentation being present and correct, so the picture has holes exactly where the code is oldest, which is where I would most like to see. I ask three questions at each checkpoint and I write the answers down. Has the risk this addresses changed — did something else already reduce it, or did the threat model move? Is the marginal cost per unit of risk reduced still falling, or have we hit the expensive tail? And is there a cheaper control that gets most of the way, which for us was namespace default-deny at a fraction of the price? If two of those come back badly, I stop, and I would rather be the person known for stopping things early than the person whose programmes all finished.

I inherited a security function whose largest line item was not tools — it was people closing tickets. The distribution was brutally uneven: about 55% of findings fell into four causes. Missing object-level authorization on new endpoints; sensitive data reaching logs; unvalidated redirect and file-path handling; and misconfigured defaults on newly provisioned infrastructure. None of those are hard problems intellectually. All of them were being solved one ticket at a time, by different people, forever, because the paved road did not exist and every team built the same thing slightly wrong.

So we spent two quarters building four things instead of closing tickets. An authorization primitive in the shared service template where a route without a declared policy fails to start — not a lint warning, a startup failure. How do you attribute the 80% reduction to your work rather than to chance?

I would not claim causation from the aggregate number alone. They must be able to, or they will fork the library and you will lose visibility entirely — so every primitive has a documented, greppable escape hatch that requires an explicit call and an annotation naming the reason. 17Production data in the staging database

Staff Data-loss / exposure scare

(a) Worked example EXAMPLE — replace with your own

We found out the way these things are usually found out: a customer replied to an email they should never have received. Only then do you decide about notification, and that decision belongs to the people who own legal and privacy, with engineering supplying facts. My job in that meeting was to be precise about what we did and did not know, and to resist the pull to give a reassuring answer.

The durable fix had a boring technical half and a harder cultural half. Technically: a masking pipeline so that a restore into a lower environment goes through irreversible transformation of personal fields — deterministic pseudonyms so joins and referential integrity survive and the data stays useful for debugging — plus outbound mail in non-production hard-wired to a sink at the infrastructure level rather than by configuration a developer can change, and a control that simply refuses a restore from a production snapshot into a non-production account. Culturally, the harder part: the engineer who did the restore had done it because reproducing the bug with synthetic data was genuinely impossible, and if I had punished that, the next person would have done it quietly. What I would do differently: I would have looked at what our non-production environments contained a year earlier. (d) Follow-up drill chain

How did you decide whether this was notifiable?

I did not decide it; I made the decision possible. Deterministic pseudonymisation can be reversed if the mapping leaks. Is it enough?

It is a trade, and I would describe it as one. Deterministic masking keeps joins and referential integrity intact, which is what makes the data useful for reproducing real bugs, but it means the same input always yields the same output, so an attacker with the key or a large sample of known values can re-identify. We mitigated with a key held only by the pipeline and never in the target environment, and by treating high-cardinality rare values — an unusual name, a unique amount — as quasi-identifiers to be generalised rather than pseudonymised. For a genuinely regulated dataset I would not rely on masking alone; I would keep the environment inside the same control boundary as production and use break-glass production access instead.

When the dataset is large enough that the transformation adds hours to every refresh, teams stop refreshing and go back to stale or unmasked copies — so the pipeline's throughput is a security property, not just an operational one. Past that point the answer changes shape: mask on write into a continuously maintained parallel dataset, or drop the copy entirely in favour of a controlled read path into production for the narrow cases that need it. It also gets harder with many data stores — masking one relational database is a project, masking a relational store plus a search index plus an event log plus three caches is a programme, and I have seen teams mask the database and forget the search index that held the same names.

Then it is a different investigation with different rules, and the first thing I would do is stop investigating it myself: preserve evidence, avoid tipping off, and hand it to whoever owns insider-threat and HR processes, because an engineer improvising a forensic investigation into a colleague creates legal exposure and destroys evidence. The technical controls that helped here would be the same ones — access logging on the data store, alerting on bulk reads and on cross-environment restores — which is a useful point to make: controls designed for accidents are largely the same controls that detect intent, and they are far easier to fund when framed as the former.

Alongside it, the preventive control at the account boundary, because policy alone loses to a deadline. And I keep the masked-refresh pipeline's usage as a health metric: if refresh requests fall to zero, either nobody needs it or everyone has found a way around it, and I want to know which.

The EU Cyber Resilience Act applies to products with digital elements placed on the EU market; its reporting obligations bite on 11 September 2026 and the main body of obligations follows on 11 December 2027. That is the kind of requirement that is simultaneously urgent, vague, and outside the competence of everyone in the room, which is the most common shape of a genuinely ambiguous requirement at principal level — not "we do not know what the user wants" but "we do not know what the word means".

I refused two tempting failure modes. The first was to wait for legal to hand down a specification; they were waiting for guidance themselves, and the calendar was not. The second was to buy a "compliance platform", which is how organisations convert an unclear obligation into an expensive unclear obligation. Instead I did the least glamorous thing available: read the actual text with the person from legal, and translate each obligation into an engineering capability we could build and test regardless of how the interpretation settled. The reporting duty needs to know, within 24 hours, that a vulnerability in our product is being actively exploited — that is a detection and inventory capability. The full notification at 72 hours needs precise scope — that is an SBOM per released artefact, queryable. The duty to handle vulnerabilities and provide security updates through the support period needs a coordinated disclosure process and a patch pipeline that can ship to an old release branch, which we could not do at all.

Then I ranked by "useful even if the interpretation changes", which is the technique I would want an interviewer to take away. (d) Follow-up drill chain

How did you avoid over-building for an interpretation that might not hold?

By asking one question of every proposed item: would we still want this if the regulation were repealed tomorrow? SBOMs, a disclosure inbox, a patch pipeline and a runbook all pass — they are ordinary good practice with a deadline attached. The 24-hour clock starts when you "become aware". What does that mean operationally?

That is exactly the ambiguity that keeps lawyers busy, and my job was to make it not matter much by being consistent: we defined an internal trigger — a confirmed report or telemetry indicating exploitation of a vulnerability in a product we place on the market — logged the timestamp when that determination was made, and started the clock there. The important engineering consequence is that determination must be fast and documented, because a slow triage does not stop the clock, it just means you spend the first eighteen hours deciding. We rehearsed it with a tabletop exercise, which surfaced the genuinely useful finding that nobody knew who could authorise a regulatory submission on a Sunday.

At what point does this stop being an engineering problem?

At the submission itself and at the interpretation of scope — whether a given product is in scope, what counts as a severe incident, which authority receives what. Those belong to legal and to product management, and I would resist engineering answering them, because a well-meaning engineer's guess in a regulatory filing is a serious liability. Where engineering must stay involved is in making the factual content accurate and fast to assemble; the failure mode I would warn about is a wall between the two functions, where legal writes a submission from a summary nobody technical read. We fixed that by naming a single engineer as the technical reviewer of any submission, with an alternate.

What if your product is not placed on the EU market?

Then this specific instrument may not bind you, and I would say so rather than manufacturing urgency — but I would still make the same argument for most of the capabilities, because the same expectations are arriving through other doors: customer questionnaires, procurement requirements, secure-development attestations, and sector regulation. The generalisable point is that the industry has converged on a small set of demands — know what you ship, be reachable for disclosure, be able to patch old releases, detect exploitation — and being able to satisfy those is now a commercial capability, not a legal one. That framing has survived every jurisdictional argument I have had about it.

How did you keep this from becoming a permanent compliance team?

By insisting the capabilities live with the teams that own the systems, and that the central function owns only the process and the evidence collection. The SBOM comes out of the build pipeline the platform team already owns; the disclosure inbox is triaged by the on-call rota rather than by a specialist; the runbook lives with incident response. What I kept central was the calendar, the relationship with legal, and the tabletop exercises — small, and hard to justify duplicating. Compliance functions grow because nobody defines what they stop owning, so I wrote that boundary down at the start and revisited it once.

19The agent that had write access

Principal Introducing a new tool

(a) Worked example EXAMPLE — replace with your own

The proposal was popular and sensible-sounding: an internal assistant that reads a customer's support history, searches the knowledge base, and drafts or applies account changes — refunds, plan switches, address corrections — through a set of tools wired up over the Model Context Protocol. The prototype was impressive and had been built in a fortnight. It also had a service account with the permissions of a senior support agent, ambient in the process, and it read untrusted text: ticket bodies written by customers, and knowledge-base articles that anyone in the company could edit.

That combination is the whole problem, and it is worth stating precisely because the industry now has vocabulary for it. OWASP's Top 10 for Agentic Applications, published on 9 December 2025, puts Agent Goal Hijack at ASI01: an attacker redirects the agent's objective through content the agent reads, so it pursues their goal while looking like it is working normally. Prompt injection is not a filtering problem you can solve with a better system prompt, because the model has no reliable channel separation between instructions and data — everything is tokens. So my position in the design review was not "do not ship this"; it was that the security boundary cannot be inside the model. It has to be around the tools.

We shipped it with four changes, and I would defend each of them at any tier. Every tool got its own narrowly scoped credential, obtained per invocation on behalf of the requesting human, so the agent had no ambient authority — the refund tool could refund, up to a limit, on the account currently in context, and nothing else. Anything that changed state and exceeded a threshold required explicit human confirmation showing the exact parameters, not a summary the model wrote, because a model that has been hijacked will happily describe an action other than the one it is proposing. Untrusted content was labelled and quarantined in the context, and the tool layer refused actions on accounts that had not been established through a trusted path — so a ticket body saying "also refund account 88213" had no way to reach a tool call. And everything was logged as a decision trail: prompt version, model version, tool calls with parameters, and the human who approved. Then we red-teamed it, which is how we found that a knowledge-base article was a far better injection vector than a ticket, because the agent treated internal content as more trustworthy — exactly the mistake a person makes. What I would do differently: I let the pilot run with the pre-existing service account for three weeks while we built the per-tool credentials. Nothing happened, but I was trading a real risk against a schedule and I did not write that trade down anywhere, which meant nobody but me knew it existed.

(d) Follow-up drill chain

Why not solve prompt injection with a guardrail model?

Because a classifier in front of a model is a probabilistic filter on an unbounded input space, and defenders have to be right every time while an attacker only needs one phrasing — the same asymmetry that made input filtering the wrong answer to SQL injection. Guardrails are worth having as a cost-raiser and as telemetry, and I run them, but I will not let a design depend on one. The structural answer is the same one that works everywhere else in security: assume the interpreter can be confused, and make sure that a confused interpreter cannot do much, which means privileges at the tool layer, confirmation for consequential actions, and identifiers that cannot come from untrusted text.

Human confirmation degrades into click-through. How do you keep it meaningful?

By spending it carefully. Confirmation is a scarce resource, so it goes only on actions that are consequential and irreversible, with thresholds tuned so a support agent sees a handful a day rather than dozens — below the threshold the action is allowed and reversible, above it there is a second pair of eyes. The presentation matters as much as the frequency: the dialogue shows the literal parameters the tool will receive, not the model's prose description, because a hijacked agent writes a persuasive summary of the wrong action. And I monitor approval latency, since a median of under two seconds means nobody is reading and the control has quietly become decorative.

At what scale does per-invocation, on-behalf-of credentialing break?

Latency and token-service load are the first walls — minting a scoped credential per tool call is fine at human speed and unpleasant at thousands of calls per second, so at that scale you cache short-lived credentials per session and accept a slightly coarser boundary. The harder problem is multi-agent systems, where one agent calls another and the chain of delegation has to carry constraints rather than accumulate privileges; that is genuinely unsolved in most deployments, and my current position is to forbid agent-to-agent delegation of write capability entirely rather than to pretend I have a model for it. If pushed, I would put a human or a deterministic workflow at every point where authority would otherwise widen.

How would you detect a hijacked agent in production?

Behavioural baselines on the tool layer rather than on the text: actions per session, refunds per hour per operator, accounts touched per session, and any tool call whose parameters reference an entity that was never in the trusted context — that last one is close to a definitive signal and it is cheap to compute. I would also sample and review the decision trail routinely, not only after incidents, because these systems drift as prompts and models change. And I keep a kill switch that disables the write tools while leaving the read-only assistant working, since the useful containment action is almost never "turn the whole feature off".

What would make you say no outright?

If the actions were irreversible and high-value with no human in the loop — moving money externally, deleting customer data, changing authentication settings — I would refuse until those specific tools were removed from the agent's reach, because there is no compensating control for an irreversible action taken by a system that can be confused by its input. I would also refuse if the untrusted content and the privileged tools could not be separated at all, or if nobody would own the decision trail. Saying no to a subset is much more effective than saying no to a project; the version of this I would be embarrassed by is the blanket refusal that gets routed around by a team who then ships it with no controls at all.

20Nineteen pentest findings, eleven days

Staff Scope / deadline negotiation

(a) Worked example EXAMPLE — replace with your own

The external penetration test finished eleven days before a launch that had a marketing campaign, a customer event and a partner announcement attached to it. Nineteen findings: two critical, five high, the rest medium and low. The engineering manager's first message to me was "can we launch?", and the honest answer was "that is not my decision alone, and I can tell you what each option costs by tomorrow morning" — which is a better answer than either yes or no, and it is the one I would give again.

The work was triage, and the discipline was to rank by exploitability and impact in our deployment rather than by the report's severity labels. A tester assigns severity without knowing that an endpoint is behind an allowlist or that a feature is off for all customers, so a "critical" can be unreachable in production and a "medium" can be a straight path to customer data. Two things moved sharply on our reading. One critical — a deserialisation issue in an admin tool — turned out to require a role only four employees held, and dropped in priority. One medium, a rate-limit gap on a password reset endpoint, moved up to launch-blocking because combined with a second finding about a verbose error it allowed account enumeration and then unlimited guessing, and the tester had reported the two separately. That is a thing worth saying out loud in an interview: pentest reports are lists, but attacks are chains, and re-reading the findings as a chain is where the value is added.

We landed on four must-fix items, six with compensating controls in place at launch and proper fixes within thirty days, and the rest on the normal backlog with dates. The compensating controls were specific rather than hopeful — a WAF rule as a temporary block with an owner and an expiry, a feature flag turning off a non-essential path, tightened rate limits, extra alerting on two endpoints — and each was written down with the finding it covered and the date it would be removed. Then I did the thing that actually made the launch decision possible: I put the residual risk in one page of business language for the launch decision-maker — what an attacker could do, what it would cost us, how likely it was — and let her decide, because launch is a business decision and my job was to make it an informed one, not to make it for her. We launched. The retest at day 30 closed everything, and one compensating control had quietly become permanent, which is the failure mode I now specifically diary for. What I would do differently: I would have scheduled the pentest four weeks earlier. Booking it eleven days out guaranteed this conversation, and the scheduling was something I had influence over and did not use.

(d) Follow-up drill chain

Who made the launch decision, and why not you?

The product leader who owned the launch made it, because the decision traded a security risk against revenue, reputation and partner commitments, and only one of those four is mine to weigh. My accountability was the quality of the input: an accurate description of what an attacker could do, an honest likelihood, and no hedging that pushes the decision back to me disguised as advice. I would push back hard on the framing that security "approves" launches, because it produces exactly the wrong behaviour on both sides — teams optimising to get past a gatekeeper rather than to reduce risk, and a security function that owns outcomes it cannot control. The one exception is a legal or regulatory prohibition, where there is no business trade to make.

How did you find the chain the report missed?

By reading the findings as an attacker's path rather than as a list — literally laying them out and asking, for each one, what it gives you and what it needs. The enumeration finding gave valid account identifiers; the rate-limit gap gave unlimited attempts; separately each was a medium and together they were an account-takeover pipeline. Testers usually report atomically because that is how their tooling and their scope work, and the deployment context that makes a chain real is knowledge you have and they do not. I now make this an explicit step in triage — a half-hour with two engineers asking "can any of these be combined" — and it has changed the ranking on roughly a third of the reports I have handled.

At what point would you have recommended not launching?

If any blocking finding had been remotely exploitable by an unauthenticated actor with a path to customer data or money, and no compensating control could close it before the date — that is where the risk stops being a business trade and becomes a near-certain incident with a legal tail. I would also have recommended delay if we could not have detected exploitation, because launching with a known hole and no telemetry means you find out from a customer or a journalist. In this case neither applied: the two genuinely severe items were fixable in the time, and everything else was either bounded or controllable.

What stops the 30-day fixes from slipping to 90?

Three mechanics, none of which rely on goodwill. The compensating controls carry an expiry date that fires as an alert rather than a calendar reminder, so the temporary control breaks visibly if the real fix has not landed. The retest is booked and paid for before launch, which creates an external date nobody wants to move. And the items sit in the team's own sprint plan rather than in a security tracker, because work that lives in a separate system is work that belongs to nobody. The failure I have lived through is the fourth mechanic I now add: someone senior asks about them in a regular forum, because visibility outperforms process almost every time.

What would you change about how the test was scoped?

Timing first — booking a test that lands eleven days before a launch guarantees the negotiation I have just described, and four weeks would have removed it entirely. On scope, I would give the testers more context rather than less: a whitebox test with our architecture, roles and threat model finds deeper issues than a blackbox test that spends half its budget rediscovering the attack surface, and I would rather pay for depth than for reconnaissance. I would also ask for the report to include an exploitation chain narrative rather than only atomic findings, which is a thing you can simply put in the statement of work and most people never do.

Ambiguity & prioritisation

How do you prioritise vulnerabilities when everything is critical?

Deploy: story 13. They want: exploitation evidence over severity labels — KEV as near-automatic escalation, EPSS as likelihood, CVSS as the impact ceiling, reachability for your specific code — plus honesty about the false negatives in reachability analysis and what you do about them.

Tell me about working against a requirement that kept changing.

Deploy: story 18 (the CRA). They want: the invariant-core technique — build what is worth having under any interpretation, defer what depends on it — and evidence you read the primary source instead of a vendor summary.

How do you balance shipping speed against security?

Deploy: story 20 (launch triage) and story 13 (a gate that fails rarely). They want: that you treat it as a genuine trade with owners rather than as a moral position. Concrete tools: risk-based bucketing, compensating controls with expiry dates, ratcheting gates on new code, and handing go/no-go to the person who owns the business risk.

What do you do when there is no clear owner for a risk?

Deploy: the platform baseline change in story 02, or the partner provisioning gap in story 11. They want: that you take temporary ownership to prevent drift, then engineer a permanent owner — and that you can tell the difference between a gap you should fill and a gap you should escalate.

How do you decide when a risk is acceptable?

Deploy: story 20's accepted findings and story 07's partner-key register. They want: a repeatable shape — named owner, written rationale, compensating control, review date — and an example where you accepted something rather than fighting it. Candidates who claim they never accept risk are telling you they have never operated at scale.

Values & motivation

Why application security?

Deploy: whichever story genuinely hooked you — for many people it is the first time they saw a small flaw turn into unlimited access, as in story 01. They want: authentic motivation and an absence of the two clichés: the "hacker mindset" performance, and the compliance-driven answer. Tie it to something you keep choosing to do rather than something you once found exciting.

How do you keep current?

Deploy: name specifics and be current — the OWASP Top 10:2025 changes (supply chain at A03, misconfiguration at A02, SSRF folded into A01), ASVS 5.0, the CRA reporting date of 11 September 2026, the npm classic-token revocation in December 2025, the agentic Top 10 from December 2025. They want: primary sources, a habit rather than a list of newsletters, and one thing you changed at work because of something you read.

What is your biggest weakness in this discipline?

Deploy: something true and bounded — for many leads it is that they over-index on the classes they have personally been burned by, or that they under-invest in detection relative to prevention. They want: self-knowledge plus a compensating habit, such as deliberately asking "how would we detect this" in every design review because it is not your instinct.

Where do you think application security is going?

Deploy: story 19 (agentic systems) and story 03 (supply chain). They want: a view with reasoning, not a trend list. A defensible one: the perimeter has moved to identity and to the build pipeline, the interesting new trust boundary is between a model and the tools it can call, and the regulatory floor is rising fast enough that response capability — inventory, disclosure, patching old branches — is becoming a commercial requirement rather than a security one.

22Night-before cheat sheet

10 speakable rules read this last

Ten sentences to read the night before, and to say out loud once each so they are in your mouth rather than on the page.

  1. Open with the situation in one line, then stop. "A multi-tenant billing API where authorization was per-handler and inconsistent" buys you thirty seconds of the interviewer's full attention; three minutes of company background spends it.
  2. Say what the risk actually was, in business terms, within the first minute. "Any customer could read any other customer's invoices" is worth more than any amount of vocabulary about the vulnerability class.
  3. Quantify the result and quantify the exposure. Endpoints found, records reachable, minutes to containment, time-to-remediate before and after. Security stories drift into vagueness faster than any other kind, and numbers are the anchor.
  4. Separate "I" from "we" deliberately and out loud. Say what you personally decided, wrote or argued, and hand the rest to the team by name. Interviewers are calibrated for inflation on exactly this and they will drill it.
  5. Own the failure in the same breath as the fix. The ignored ticket, the two days of disbelief, the pilot on the broad service account. A security story without a mistake in it sounds rehearsed, because real security work is full of them.
  6. Name the trade-off, never just the control. Every answer should contain a sentence of the form "that bought us X and cost us Y" — latency, developer friction, an escape hatch that became the new target. Controls without costs signal someone who has read about this rather than shipped it.
  7. Prefer structural fixes and say why. "A check you can forget is a check you will forget" is the through-line of half the stories here: repositories that cannot query without a tenant, routes that will not start without a policy, logs that project rather than redact.
  8. Have one very recent, checkable fact ready. CRA reporting obligations from 11 September 2026 with the 24/72-hour clocks; the OWASP Top 10:2025 shape; ASVS 5.0; npm classic tokens revoked in December 2025; the agentic Top 10 from the same month. One fact, used once, dated correctly — not a recital.
  9. Give the go/no-go decision back to whoever owns the business risk. Your accountability is the quality of the input; claiming that security "approves" launches makes you a gatekeeper, and gatekeepers get routed around.
  10. Finish every story with the thing you would do differently, and make it a change of method. Not "I would be more careful" but "I now write the log query before the escalation", "I now agree stop conditions at kick-off", "I now sequence by value rather than by coverage".

The last check before you walk in. Pick five stories from the coverage table that are genuinely yours, and for each one be able to say in ten seconds: the situation, the number, the trade-off, and the thing you would do differently. Five stories you can tell cold beat twenty you half-remember, and the drill chains are what let you improvise the sixth.
