01 Hosting, startup & the middleware pipeline

Everything in ASP.NET Core is a host plus a pipeline: WebApplicationBuilder builds a DI container and a configuration tree, WebApplication composes an ordered chain of middleware, and a request walks that chain to an endpoint and back. Interviewers start here because it is the one part every candidate has touched, and because ordering bugs (auth after routing, CORS in the wrong place, exception handler too late) are the most common production defect in the framework. At mid level you are expected to name the components; at senior to explain ordering consequences and the difference between middleware, filters and endpoint filters; at principal to talk about the host lifecycle under an orchestrator — graceful shutdown, readiness, and what happens to in-flight requests during a rolling deploy.

docs: ASP.NET Core Middleware · Generic Host

Walk me through what happens from the TCP connection to my controller action. screener

Kestrel accepts the connection and runs the connection middleware chain (TLS, then the HTTP/1.1, HTTP/2 or HTTP/3 protocol handler), parses a request into an HttpContext backed by feature interfaces, and hands it to the application pipeline. The pipeline is the ordered list of middleware you registered with Use…: each one gets the context and a RequestDelegate for "the rest of the pipeline", so it can do work before and after calling next. UseRouting matches the request against the endpoint table and stores the selected Endpoint on the context without executing it; the auth middleware then sees that endpoint's metadata, and UseEndpoints (implicit at the end of the pipeline since .NET 6) actually invokes it. For MVC the endpoint is an action invoker that runs the filter pipeline, model binding and the action; for a minimal API it is your lambda wrapped in endpoint filters. The response then unwinds back out through every middleware in reverse order.

Example 
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddControllers();
var app = builder.Build();

app.UseExceptionHandler();   // outermost: sees everything below it
app.UseHttpsRedirection();
app.UseStaticFiles();
app.UseRouting();            // selects the endpoint, does not run it
app.UseCors();
app.UseAuthentication();     // needs the endpoint to read [Authorize] metadata
app.UseAuthorization();
app.UseOutputCache();
app.MapControllers();        // terminal: executes the selected endpoint
app.Run();

Follow-ups

  • Where does the response actually get written? — Whenever anything writes to HttpContext.Response.Body; the first write flushes the headers, after which nothing upstream can change the status code.
  • What is HttpContext.Features for? — It is the extension point between the server and the framework: IHttpRequestFeature, IHttpResponseBodyFeature, IHttpUpgradeFeature and so on, so Kestrel, IIS and TestServer can all present the same abstraction.
  • Is HttpContext thread-safe? — No. It is not safe to use after the request completes and not safe to touch from a background task; copy what you need.

Wrong answer: "Routing matches the URL and calls the controller." Conflating endpoint selection with endpoint execution is exactly the misunderstanding that produces the classic bug where [Authorize] is ignored because UseAuthorization was placed before UseRouting.

Why does middleware order matter? Give me an ordering bug you have actually seen. mid

Order is the pipeline: middleware registered earlier wraps everything registered after it, so it sees the request first and the response last. The classic bugs are all "the wrapper is on the wrong side": exception handling registered after the middleware that throws, so errors escape as raw 500s with a stack trace; UseCors after UseResponseCaching, so a cached response is served without CORS headers to a different origin; static files before authentication, so anything under wwwroot is public (usually correct, occasionally a leak); and UseAuthorization before UseRouting, so no endpoint is selected yet and [Authorize] metadata is invisible. In .NET 6+ WebApplication auto-inserts UseRouting and UseEndpoints if you did not, which hides some of these but not all — an explicit UseRouting anchors where CORS and auth go.

Example 
// BROKEN: response compression sits inside static files, so pre-compressed
// files are compressed twice and the Content-Encoding is wrong.
app.UseStaticFiles();
app.UseResponseCompression();

// FIXED: compression must wrap what it compresses.
app.UseResponseCompression();
app.UseStaticFiles();

Follow-ups

  • Which middleware must come first, always? — Exception handling / UseDeveloperExceptionPage and anything that must observe the whole request (W3C logging, UseForwardedHeaders behind a proxy).
  • Why does UseForwardedHeaders have to be near the top? — Because it rewrites Scheme, Host and RemoteIpAddress; anything registered before it (HTTPS redirection, rate limiting by IP) sees the proxy's values.
  • How do you branch the pipeline? — app.Map("/admin", …) for path prefixes, app.UseWhen(pred, …) for a conditional segment that rejoins, app.MapWhen for one that does not.

Wrong answer: "Order does not really matter because the framework sorts it out." It does not — WebApplication only guarantees that routing and endpoint execution exist, and nothing warns you that CORS is in the wrong place.

Middleware, MVC filters, endpoint filters — when do you reach for which? senior

Middleware is cross-cutting for the whole server: it runs for every request including static files and 404s, it has no idea what an action or a model is, and it is the right place for correlation IDs, forwarded headers, compression, rate limiting and global exception handling. MVC filters (IActionFilter, IResultFilter, IAuthorizationFilter, IExceptionFilter) run inside the MVC endpoint, after model binding, and can see the action arguments, the ModelState and the IActionResult — that is what you want for validation short-circuits, per-action caching attributes or transforming a result. Endpoint filters (AddEndpointFilter, .NET 7+) are the minimal-API equivalent: a small, allocation-light hook around the handler with access to the bound arguments, composable per route or per RouteGroupBuilder. The rule of thumb: if the logic needs to know about the action or its arguments, it is a filter; if it must apply even when no endpoint matched, it is middleware.

Example 
// Endpoint filter: sees the bound arguments, can short-circuit.
app.MapPost("/orders", (Order o, IOrderService s) => s.CreateAsync(o))
   .AddEndpointFilter(async (ctx, next) =>
   {
       var order = ctx.GetArgument<Order>(0);
       if (order.Quantity <= 0)
           return Results.ValidationProblem(new Dictionary<string, string[]>
               { ["quantity"] = ["must be positive"] });
       return await next(ctx);
   });

Follow-ups

  • Cost difference? — Middleware runs on every request; a filter runs only on matched endpoints. On a high-QPS API that is a real difference if the work is non-trivial.
  • How do filters get dependencies? — [ServiceFilter] / [TypeFilter] or IFilterFactory; a plain attribute cannot take scoped services because attributes are cached per action.
  • What order do filters run in? — Authorization → resource → action → exception → result, each grouped by scope (global, controller, action) and ordered by Order, with the "before" halves outside-in and the "after" halves inside-out.

Wrong answer: "They are the same thing, filters are just middleware for controllers." Filters can short-circuit with an IActionResult and see model state; middleware cannot, and a filter never sees a request that did not match an endpoint.

Write a piece of middleware. What is the correct shape and what are the traps? mid

The conventional shape is a class with a constructor taking RequestDelegate next plus singleton dependencies, and an InvokeAsync(HttpContext) method; the class is instantiated once, so scoped services must be injected as method parameters on InvokeAsync, not in the constructor. Since .NET 8, implementing IMiddleware and registering it in DI gives a per-request instance instead (factory-based middleware), at the cost of a container resolve per request. The traps: forgetting to await next(context) (silently terminating the pipeline), writing to the response after next has already flushed headers, and swallowing exceptions so downstream diagnostics see nothing.

Example 
public sealed class CorrelationIdMiddleware(RequestDelegate next, ILogger<CorrelationIdMiddleware> log)
{
    private const string Header = "X-Correlation-Id";

    public async Task InvokeAsync(HttpContext ctx, ITenantContext tenant) // scoped: method-injected
    {
        var id = ctx.Request.Headers[Header].FirstOrDefault() ?? Activity.Current?.TraceId.ToString()
                 ?? Guid.NewGuid().ToString("n");
        ctx.Response.OnStarting(() => { ctx.Response.Headers[Header] = id; return Task.CompletedTask; });
        using (log.BeginScope(new Dictionary<string, object> { ["CorrelationId"] = id }))
            await next(ctx);
    }
}

Follow-ups

  • Why Response.OnStarting rather than setting the header directly? — Headers can only be set before the first byte is written; OnStarting runs at the last safe moment.
  • Convention-based vs IMiddleware? — Convention-based is singleton and allocation-free per request; IMiddleware is DI-resolved per request, which is convenient for scoped state but costs a resolve.
  • How do you unit-test middleware? — Construct it with a stub RequestDelegate and a DefaultHttpContext; no server needed.

Wrong answer: Injecting a DbContext or any scoped service into the middleware constructor. It compiles, it works in dev, and it produces a captive dependency: one DbContext shared by every concurrent request, which fails under load with "A second operation was started on this context".

How does graceful shutdown work, and what breaks it in Kubernetes? senior

On SIGTERM (or Ctrl+C) the generic host triggers IHostApplicationLifetime.ApplicationStopping, stops accepting new connections, waits up to HostOptions.ShutdownTimeout (default 30 seconds — 5 seconds in older templates) for in-flight requests and IHostedService.StopAsync to complete, then fires ApplicationStopped. The failure mode in Kubernetes is not the timeout, it is the race: the pod is removed from the Service endpoints asynchronously, so for a second or two after SIGTERM the kube-proxy rules on some nodes still send traffic to a pod that has stopped listening, producing connection-refused errors. The fix is a preStop sleep (or a readiness probe that fails immediately while the app keeps serving) so the endpoint removal propagates before the listener closes, plus a terminationGracePeriodSeconds comfortably larger than your shutdown timeout, which itself must exceed your longest request.

Example 
builder.Services.Configure<HostOptions>(o =>
{
    o.ShutdownTimeout = TimeSpan.FromSeconds(45);            // > longest request, < grace period
    o.BackgroundServiceExceptionBehavior =
        BackgroundServiceExceptionBehavior.StopHost;          // default since .NET 6: crash loudly
});

builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"]);
app.MapHealthChecks("/health/live",  new() { Predicate = r => r.Tags.Contains("live") });
app.MapHealthChecks("/health/ready", new() { Predicate = r => r.Tags.Contains("ready") });

Follow-ups

  • What token should long-running handlers observe? — HttpContext.RequestAborted for client disconnects; for shutdown, a token linked to ApplicationStopping.
  • What happens to a BackgroundService at shutdown? — Its stoppingToken is cancelled and StopAsync is awaited within the shutdown timeout; work that ignores the token is killed mid-flight.
  • Difference between liveness and readiness? — Liveness answers "should you restart me"; readiness answers "should you route to me". Never put a database check in liveness or a dependency blip becomes a restart storm.

Wrong answer: "Kubernetes waits for the app to finish, so nothing is lost." It waits only for the grace period, and it starts closing the door before it stops sending traffic — the errors happen in the first second, not at the end.

What is the difference between IHostedService and BackgroundService, and how do you run periodic work correctly? mid

IHostedService is the raw contract: StartAsync and StopAsync, both awaited by the host — StartAsync runs before the server starts listening, so blocking there delays startup. BackgroundService is the base class that gives you a single ExecuteAsync(CancellationToken), started in the background so it does not block the host. Since .NET 8 you also have IHostedLifecycleService with Starting/Started/Stopping/Stopped hooks for ordering. For periodic work, use PeriodicTimer rather than System.Timers.Timer: it is async, non-reentrant and takes the cancellation token, so ticks cannot overlap and shutdown is clean. And because the service is a singleton, resolve scoped dependencies per iteration from IServiceScopeFactory.

Example 
public sealed class OutboxPublisher(IServiceScopeFactory scopes, ILogger<OutboxPublisher> log)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromSeconds(5));
        while (await timer.WaitForNextTickAsync(ct))
        {
            try
            {
                await using var scope = scopes.CreateAsyncScope();
                var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
                await PublishBatchAsync(db, ct);
            }
            catch (Exception ex) when (ex is not OperationCanceledException)
            {
                log.LogError(ex, "outbox batch failed");   // never let the loop die on a transient error
            }
        }
    }
}

Follow-ups

  • What happens if ExecuteAsync throws? — Since .NET 6 the default BackgroundServiceExceptionBehavior.StopHost stops the whole application; before that it was silently swallowed, which is why old codebases have zombie workers.
  • How do you make sure only one instance runs across replicas? — External coordination: a distributed lock (Redis, blob lease), a leader-election sidecar, or a queue with competing consumers so it does not matter.
  • Where do you run migrations? — Not in a hosted service in a multi-replica deployment; use an init container or a deploy step, otherwise N replicas race on the same schema.

Wrong answer: "Use Task.Run with a while(true) loop in StartAsync." Nothing observes the task, exceptions vanish, and shutdown cannot wait for it — the two symptoms candidates then blame on "the framework killing my worker".

What did the minimal hosting model in .NET 6 change, and what does Startup.cs still buy you? mid

Before .NET 6, Program.cs built an IHostBuilder that pointed at a Startup class with ConfigureServices(IServiceCollection) and Configure(IApplicationBuilder, IWebHostEnvironment); the container was built between them, and Startup's constructor could take IConfiguration. The minimal hosting model collapses that into one file: WebApplicationBuilder exposes Services, Configuration, Logging, Environment and Host/WebHost for the escape hatches, and builder.Build() returns a WebApplication that is simultaneously the IHost, the IApplicationBuilder and the IEndpointRouteBuilder. The practical consequences are that the container is built exactly at Build() (so you cannot register services afterwards — it throws), and that the default builder already wires configuration sources, logging, DI scope validation in Development, and routing/endpoints. Startup.cs still exists in plenty of real codebases and is perfectly supported via ConfigureWebHostDefaults; the only real argument for keeping it is a large team with per-feature Startup partials, and the modern equivalent is extension methods on IServiceCollection/WebApplication.

Example 
// Modern equivalent of a per-feature Startup: extension methods, one per module.
public static class OrdersModule
{
    public static IServiceCollection AddOrders(this IServiceCollection s, IConfiguration cfg) => s
        .AddScoped<IOrderService, OrderService>()
        .Configure<OrderOptions>(cfg.GetSection("Orders"));

    public static IEndpointRouteBuilder MapOrders(this IEndpointRouteBuilder app)
    {
        var g = app.MapGroup("/orders").RequireAuthorization().WithTags("Orders");
        g.MapGet("/{id:guid}", (Guid id, IOrderService s) => s.GetAsync(id));
        return app;
    }
}

Follow-ups

  • Can you still use a third-party container? — Yes: builder.Host.UseServiceProviderFactory(new AutofacServiceProviderFactory()), then builder.Host.ConfigureContainer.
  • What is WebApplication.CreateSlimBuilder? — A .NET 8+ builder that omits the heavier defaults (no appsettings file watching by default, no IIS integration, no debug/eventsource logging) for AOT and container scenarios; CreateEmptyBuilder adds nothing at all.
  • Where do top-level statements put your code? — In a generated Program class with an internal Main; that is why integration tests need public partial class Program; or InternalsVisibleTo.

Wrong answer: "Startup.cs is removed / no longer supported in .NET 6+." It is not; the templates changed, the API did not.

How do you short-circuit the pipeline, and why does Response.HasStarted matter? senior

You short-circuit by simply not calling next — write the response and return. That is how UseStaticFiles, rate limiting rejections and authentication challenges work. Response.HasStarted is the tripwire: once the first byte of the body (or an explicit StartAsync/flush) has gone out, the status code and headers are on the wire and any attempt to change them throws InvalidOperationException. This is why a global exception handler cannot rescue a failure that happens halfway through streaming a large JSON payload — the 200 has already been sent, and the client sees a truncated body. In .NET 8+ ShortCircuit() / MapShortCircuit() on endpoints goes further: it tells routing to skip the remaining middleware entirely for matched routes, which is how you keep health checks and /favicon.ico out of the auth and logging path.

Example 
// .NET 8+: these never touch auth, logging or output caching middleware.
app.MapShortCircuit(404, "robots.txt", ".well-known/appspecific");
app.MapGet("/health/live", () => Results.Ok()).ShortCircuit();

// Guarding a late write:
if (!ctx.Response.HasStarted)
{
    ctx.Response.StatusCode = StatusCodes.Status503ServiceUnavailable;
    await ctx.Response.WriteAsJsonAsync(new ProblemDetails { Title = "Draining" });
}

Follow-ups

  • How do you buffer the response so you can rewrite it? — Swap Response.Body for a MemoryStream (or use IHttpResponseBodyFeature), but you lose streaming and pay the memory — only for small responses.
  • What does UseExceptionHandler do when headers have started? — It logs and rethrows/aborts; it explicitly checks HasStarted and gives up, which is why you sometimes see a partial body with no error page.
  • Why is ShortCircuit a performance feature? — On a health endpoint hit every second by three probes, skipping auth, CORS, output caching and request logging is measurable at scale.

Wrong answer: "Just set the status code in the exception handler." Only works before the response starts; the interesting half of the question is what you do when it already has (abort the connection, and make sure the client can tell a truncated stream from a complete one).

A request takes 3 seconds in production and 30 ms locally. How do you find where the time goes without a profiler? senior

Start with the framework's own telemetry rather than guessing: ASP.NET Core emits http.server.request.duration as a histogram tagged by route, method and status, and dotnet-counters monitor Microsoft.AspNetCore.Hosting System.Runtime gives you request rate, queue length, thread-pool thread count and GC pause time live against a running process — no restart, no code change. Those three numbers separate the three usual causes immediately: high thread-pool queue length with low CPU means thread-pool starvation from sync-over-async; high % time in GC or a growing gen 2 means allocation pressure; flat CPU and flat GC with a long duration means you are waiting on I/O. If distributed tracing is on, the Activity spans for the outbound HttpClient and database calls tell you which dependency; if it is not, that is the first thing to fix. Only then do you attach dotnet-trace or take a dotnet-dump and inspect with dotnet-dump analyze/clrstack.

Example 
# attach to a running container, no restart
dotnet-counters monitor -p 1 --counters Microsoft.AspNetCore.Hosting,System.Runtime
# capture 30s of CPU + allocation events and open in PerfView / SpeedScope
dotnet-trace collect -p 1 --profile cpu-sampling --duration 00:00:30
# hung requests? dump and look at what the thread pool threads are doing
dotnet-dump collect -p 1 && dotnet-dump analyze core_dump
> clrthreads
> parallelstacks

Follow-ups

  • Which single counter most often explains it? — ThreadPool Queue Length. If it is non-zero and growing while CPU is low, you are starved, not slow.
  • How do you get these tools into a distroless container? — Ship them in the image, side-load via an ephemeral debug container (kubectl debug), or enable the diagnostic socket and use dotnet-monitor as a sidecar.
  • What if it is only slow for one tenant? — Look at cardinality-safe dimensions on your metrics; if tenant is not a tag anywhere, use exemplars or trace sampling biased to slow requests.

Wrong answer: "Add Stopwatch logging around everything and redeploy." It is slow, it changes the system you are measuring, and it will miss the two most likely causes (thread-pool starvation and GC), both of which show up as time that is not inside any of your stopwatches.

You own the platform. Two hundred services, and you want every one to have the same pipeline. How? principal

The answer is a shared bootstrap library plus enforcement, not a wiki page. Ship an internal NuGet package with one extension method (AddPlatformDefaults/UsePlatformPipeline) that composes auth, ProblemDetails, OpenTelemetry, health checks, forwarded headers, rate limiting and the outbound HttpClient resilience handler in the correct order, versioned semantically and rolled out through a bot-driven dependency update. Then close the loopholes: an analyzer or an architecture test that fails the build if UseAuthorization is called without UsePlatformPipeline, a startup self-check that logs (or in non-production, throws) when required middleware is missing, and a synthetic probe per service that asserts the platform behaviours end-to-end — a 401 shape, a trace header propagating, a /health/ready that flips. Keep the package thin and opinionated at the edges but escapable in the middle: teams must be able to insert their own middleware without forking, or they will fork. The organisational half matters more than the technical half — a shared pipeline only survives if upgrading it is cheaper than ignoring it.

Example 
public static WebApplicationBuilder AddPlatformDefaults(this WebApplicationBuilder b)
{
    b.Services.AddProblemDetails();
    b.Services.AddHealthChecks();
    b.Services.ConfigureHttpClientDefaults(h => h.AddStandardResilienceHandler());
    b.Services.AddOpenTelemetry()
        .WithTracing(t => t.AddAspNetCoreInstrumentation().AddHttpClientInstrumentation().AddOtlpExporter())
        .WithMetrics(m => m.AddAspNetCoreInstrumentation().AddRuntimeInstrumentation().AddOtlpExporter());
    b.Logging.AddOpenTelemetry(o => { o.IncludeScopes = true; o.ParseStateValues = true; });
    return b;
}

Follow-ups

  • How do you roll out a breaking change to the pipeline? — Feature-flag it inside the package, ship it off by default, measure adoption with a version metric per service, then flip the default in the next major.
  • What do you deliberately not centralise? — Business middleware and anything with per-service tuning (timeouts, cache TTLs); centralise the shape, not the values.
  • Service mesh instead? — A mesh gives you mTLS, retries and traces without touching code, but it cannot give you ProblemDetails shapes, auth policy semantics or structured logging fields. Most platforms end up with both.

Wrong answer: "A template repository." Templates drift the moment they are used; the failure mode is 200 services on 200 versions of the pipeline and no way to ship a security fix.

02 Dependency injection & lifetimes

ASP.NET Core's container is deliberately small — constructor injection, three lifetimes, no property injection, no interception — and that smallness is exactly why interviewers use it: there is nowhere to hide. Almost every DI question is really a lifetime question, and almost every lifetime bug is the same bug (something long-lived captured something short-lived). Mid level: name the lifetimes and resolve them correctly. Senior: captive dependencies, scope validation, disposal, and how DbContext and HttpClient fit. Principal: registration strategy across a large codebase, keyed services, and when you deliberately do not use the container.

docs: Dependency injection in ASP.NET Core · DI guidelines

Singleton, scoped, transient — what are they and what is a scope in a web app? screener

A singleton is created once per container and shared for the process lifetime. A scoped service is created once per scope and reused within it; in ASP.NET Core the framework creates one scope per HTTP request, so "scoped" means "per request" — but only because someone creates the scope, which is why a BackgroundService has to create its own. A transient is created every time it is requested, including twice within the same request if two classes ask for it. The container also owns disposal: it disposes the IDisposable/IAsyncDisposable instances it created, scoped and transient ones when the scope ends, singletons when the root provider is disposed at shutdown — and that last part is the memory-leak trap, because transients resolved from the root provider are tracked until the process exits.

Example 
builder.Services.AddSingleton<IClock, SystemClock>();          // stateless, thread-safe
builder.Services.AddScoped<IUnitOfWork, EfUnitOfWork>();       // per request, holds a DbContext
builder.Services.AddTransient<IEmailBuilder, EmailBuilder>();  // cheap, stateful, short-lived

// Background work has no request, so make a scope yourself:
await using var scope = scopeFactory.CreateAsyncScope();
var uow = scope.ServiceProvider.GetRequiredService<IUnitOfWork>();

Follow-ups

  • Is scoped the same as per-request? — Only in the request pipeline. In a worker, a gRPC stream or a SignalR hub circuit the scope boundaries differ; SignalR, for instance, scopes per hub method invocation.
  • Which lifetime for a stateless service with no dependencies? — Singleton, unless it depends on something scoped. Transient is the safe default only because it is hard to get wrong.
  • Who disposes a service you registered with a pre-built instance? — Nobody: AddSingleton<T>(instance) means you own its lifetime, the container will not dispose it.

Wrong answer: "Transient is created per request." Transient is per resolution. Getting this backwards is the tell that the candidate has never debugged a lifetime problem.

What is a captive dependency, and how does the framework help you catch it? mid

A captive dependency is a service held by something that outlives it: a singleton injecting a scoped service captures the very first request's instance and keeps it forever, so every later request silently shares it. With a DbContext that means concurrent use of a non-thread-safe object ("A second operation was started on this context…"), with a scoped tenant or user context it means cross-tenant data leakage — a security bug, not just a bug. The default container catches the obvious case at Build() when scope validation is on, which the default builder enables in the Development environment only; ValidateOnBuild plus ValidateScopes should be turned on explicitly for all environments so you fail at startup instead of under load. It cannot catch the case where you resolve from the root IServiceProvider at runtime, which is why IServiceProvider in a singleton constructor deserves a code-review comment every time.

Example 
builder.Host.UseDefaultServiceProvider((ctx, o) =>
{
    o.ValidateScopes  = true;   // scoped resolved from root/singleton throws
    o.ValidateOnBuild = true;   // every registration is checked at startup, not first use
});

// The bug it catches:
builder.Services.AddSingleton<CacheWarmer>();      // singleton
builder.Services.AddScoped<AppDbContext>();        // scoped
// CacheWarmer(AppDbContext db) -> InvalidOperationException at Build()

Follow-ups

  • How do you fix it properly? — Inject IServiceScopeFactory (or IDbContextFactory<T> for EF) and create a scope per unit of work; never widen the DbContext to singleton.
  • Why is ValidateOnBuild off by default in production? — It costs startup time proportional to the registration count and it eagerly walks constructors; the trade is a slower cold start for a guaranteed-valid graph. Take the trade.
  • Does it catch transient-into-singleton? — No, and that is legal but leaky: a transient IDisposable captured by a singleton lives until shutdown.

Wrong answer: "Just make the DbContext a singleton and add a lock." It serialises the entire application on one connection and still corrupts EF's change tracker across requests.

How do you resolve a scoped service inside a singleton or a background service? mid

Inject IServiceScopeFactory — it is a singleton, safe to hold — and create a scope for each logical unit of work, disposing it when the work finishes. Use CreateAsyncScope() rather than CreateScope() whenever anything in the graph implements IAsyncDisposable (EF Core's DbContext does): disposing an IAsyncDisposable from a synchronous Dispose throws InvalidOperationException at runtime. The scope should match the unit of work, not the process: one scope per timer tick, per message consumed, per batch — not one scope held for the life of the service, which is a captive dependency wearing a disguise.

Example 
public sealed class QueueConsumer(IServiceScopeFactory scopes) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        await foreach (var msg in _bus.ReadAllAsync(ct))
        {
            await using var scope = scopes.CreateAsyncScope();   // one scope per message
            var handler = scope.ServiceProvider.GetRequiredService<IMessageHandler>();
            await handler.HandleAsync(msg, ct);
        }
    }
}

Follow-ups

  • What if you need the scoped service in the constructor? — You do not; restructure so the constructor takes the factory and the method takes the resolved service. If that is painful, the class is doing two jobs.
  • Is IServiceProvider injection acceptable? — As a last resort (framework code, plugin dispatch). It is service location: it hides dependencies from the constructor and from your tests.
  • What about IHttpContextAccessor in a background service? — It will be null; there is no request. Anything the work needs from the request must be captured and passed explicitly.

Wrong answer: "Create one scope in ExecuteAsync and reuse it for the lifetime of the worker." That is exactly the captive dependency again — the DbContext never resets its change tracker and grows until the process dies.

What are keyed services and when would you actually use them? senior

Keyed services (.NET 8) let you register several implementations of the same interface under distinct keys and resolve them with [FromKeyedServices("key")] or GetRequiredKeyedService<T>(key). Before .NET 8 the idiom was to inject IEnumerable<T> and filter, or to introduce a factory delegate; keyed registration removes that ceremony for genuinely parallel implementations — two cache backends, a primary and a fallback payment gateway, per-tenant strategies chosen by name. The judgment part is knowing when it is the wrong tool: if the key is a runtime value that varies per request, you want a factory or a strategy resolver, because keys must be known at resolution time and keyed lookups do not compose with options binding or with most third-party containers. Keyed services also do not participate in IEnumerable<T> injection, so registering something keyed silently removes it from "give me all implementations".

Example 
builder.Services.AddKeyedSingleton<IBlobStore, S3BlobStore>("s3");
builder.Services.AddKeyedSingleton<IBlobStore, AzureBlobStore>("azure");

app.MapGet("/files/{id}", (string id, [FromKeyedServices("azure")] IBlobStore store)
    => store.OpenReadAsync(id));

// Runtime-selected key: resolve through the provider, not the constructor.
public sealed class BlobRouter(IServiceProvider sp)
{
    public IBlobStore For(Tenant t) => sp.GetRequiredKeyedService<IBlobStore>(t.StorageKind);
}

Follow-ups

  • What is KeyedService.AnyKey? — A wildcard registration that matches any key, useful for a generic factory implementation.
  • How did you do this before .NET 8? — IEnumerable<T> + a discriminator property, a Func<string, T> factory registration, or a named-registration container like Autofac.
  • Do keyed services work with IOptions? — Not directly; the parallel mechanism is named options (IOptionsMonitor<T>.Get(name)), and pairing the two names by hand is a common source of drift.

Wrong answer: "Use keyed services for per-tenant configuration." Tenants are runtime data; keys are registration-time identifiers. You end up registering at startup for tenants that do not exist yet.

What happens when you register the same interface twice? How do you get all implementations? mid

Registrations are a list, not a dictionary: the last one wins for GetRequiredService<T>, and all of them are returned, in registration order, for IEnumerable<T>. That is the mechanism behind pipelines like validators, health checks, and IConfigureOptions<T>. The intent-revealing helpers are TryAdd* (register only if the service type is absent — what a library should use so the application can override it), TryAddEnumerable (add only if that exact implementation type is not already present, which is how you avoid duplicate registrations when AddX() is called twice), and Replace (swap the existing registration, the standard trick in integration tests).

Example 
services.TryAddSingleton<IClock, SystemClock>();                       // app can override
services.TryAddEnumerable(ServiceDescriptor.Singleton<IValidator, OrderValidator>());
services.Replace(ServiceDescriptor.Scoped<IPaymentGateway, FakeGateway>()); // in tests

public sealed class ValidationPipeline(IEnumerable<IValidator> validators) { /* runs all */ }

Follow-ups

  • Why does order matter for IEnumerable<T>? — Because many pipelines execute in order (IConfigureOptions, IPostConfigureOptions, exception handlers since .NET 8).
  • How do you remove a registration? — services.RemoveAll<T>(), or manipulate the IServiceCollection directly — it is just a List<ServiceDescriptor> until Build().
  • What does open-generic registration look like? — services.AddScoped(typeof(IRepository<>), typeof(EfRepository<>)); the container closes it per request.

Wrong answer: "The second registration throws / the first one wins." Last-wins is a deliberate design choice, and it is exactly what test overrides and Replace rely on.

How should DbContext be registered, and when is AddDbContextPool or IDbContextFactory the right answer? senior

AddDbContext<T> registers the context as scoped, which is right for a request/response app: one context per request, one change tracker, disposed at the end. AddDbContextPool<T> keeps a pool of context instances and resets them between uses, which removes the per-request construction and model-lookup cost — worth a few percent on very high-throughput APIs, but it forbids per-instance state in the constructor (no injected tenant id or connection string chosen per request) because the instance is recycled. AddDbContextFactory<T> gives you an explicit factory for cases where the scope is not the request: background services, Blazor Server components whose lifetime is the circuit, and any place you need two contexts alive at once (parallel queries). In Blazor Server specifically, scoped means "per circuit", which can be hours — the factory is the recommended pattern there.

Example 
builder.Services.AddDbContextPool<AppDbContext>(o => o
    .UseNpgsql(cs, npg => npg.EnableRetryOnFailure(3))
    .UseQueryTrackingBehavior(QueryTrackingBehavior.NoTrackingWithIdentityResolution));

builder.Services.AddDbContextFactory<AppDbContext>(o => o.UseNpgsql(cs)); // for workers/Blazor

// parallel reads need two contexts, never one shared instance
await using var a = await factory.CreateDbContextAsync(ct);
await using var b = await factory.CreateDbContextAsync(ct);
var (orders, invoices) = (await a.Orders.ToListAsync(ct), await b.Invoices.ToListAsync(ct));

Follow-ups

  • Why can't you share one DbContext across parallel awaits? — It is not thread-safe and enforces one active operation; the second concurrent call throws.
  • What does pooling actually reset? — Change tracker, query cache state and most ChangeTracker/Database configuration; anything you set in the constructor from injected state is not re-run per use.
  • Retry policy + explicit transactions? — EnableRetryOnFailure makes the execution strategy refuse user-initiated transactions; you must wrap them in Database.CreateExecutionStrategy().ExecuteAsync(...).

Wrong answer: "Use AddDbContextPool everywhere, it is strictly faster." It changes construction semantics; a multi-tenant app that sets the tenant in the constructor will happily serve tenant A's filter to tenant B.

Who disposes what? Explain the disposal rules and a leak they cause. senior

The container disposes only the instances it created. Scoped and transient disposables are tracked by the scope that created them and disposed when the scope is disposed; singleton disposables are tracked by the root scope and disposed at host shutdown. The leak follows directly: a transient IDisposable resolved from the root provider — for example inside a singleton that captured IServiceProvider, or in a library that calls GetService on the application's root — is added to the root's disposal list and never released until the process exits, so the heap grows for the life of the app. Two other rules matter: instances you register with AddSingleton(instance) are yours to dispose, and if a type implements both IDisposable and IAsyncDisposable, an async scope calls DisposeAsync, while a sync scope resolving an IAsyncDisposable-only type throws.

Example 
// LEAK: every call adds a tracked disposable to the ROOT provider.
public sealed class Reporter(IServiceProvider root)
{
    public void Run() => root.GetRequiredService<TempFileWriter>().Write(); // transient IDisposable
}

// FIX: scope it.
public sealed class Reporter(IServiceScopeFactory scopes)
{
    public void Run()
    {
        using var scope = scopes.CreateScope();
        scope.ServiceProvider.GetRequiredService<TempFileWriter>().Write();
    }
}

Follow-ups

  • How would you spot this in production? — A dotnet-gcdump showing thousands of instances rooted by ServiceProviderEngineScope; that root name is the fingerprint.
  • Does the container dispose services it did not create? — No, and that includes anything produced by a factory delegate returning a cached instance you own.
  • What about HttpClient? — IHttpClientFactory hands out clients whose handler it owns; disposing the client is harmless and does not dispose the pooled handler.

Wrong answer: "The GC handles it." Disposal is not collection: the container holds a strong reference precisely so it can call Dispose, which is why these objects are unreachable-by-your-code yet permanently alive.

Constructor injection only — how do you handle a dependency you need lazily or conditionally? senior

Options in rough order of preference: inject a factory delegate (Func<T> registered explicitly, since the built-in container does not synthesise them), inject IServiceScopeFactory when the dependency is scoped, inject Lazy<T> if construction is genuinely expensive and often unused, or split the class so the expensive path lives behind its own abstraction. The reflex answer "inject IServiceProvider" is available and sometimes correct — plugin dispatch, message-type-to-handler routing — but it hides the dependency from the signature, so the constructor no longer documents what the class needs and tests must build a container instead of passing fakes. At principal level the real answer is usually that a lazily-needed dependency signals a class with two responsibilities; the refactor beats the workaround.

Example 
// Explicit factory registration: the dependency stays visible in the signature.
builder.Services.AddSingleton<Func<ReportKind, IReportRenderer>>(sp => kind => kind switch
{
    ReportKind.Pdf  => sp.GetRequiredService<PdfRenderer>(),
    ReportKind.Xlsx => sp.GetRequiredService<XlsxRenderer>(),
    _ => throw new ArgumentOutOfRangeException(nameof(kind))
});

public sealed class ReportEndpoint(Func<ReportKind, IReportRenderer> renderers) { }

Follow-ups

  • Does the built-in container support Func<T> automatically? — No (Autofac does). You register the delegate yourself, which is a feature: it is one place to see the mapping.
  • Is Lazy<T> thread-safe here? — Lazy<T> is, by default; the service it creates is only as thread-safe as you made it, and a lazily-created singleton is still shared.
  • What about property injection? — Not supported, deliberately. Optional dependencies are usually a null-object or a default implementation, not a nullable property.

Wrong answer: "Use a static service locator so anything can get anything." It makes lifetimes invisible, breaks parallel test isolation, and is the pattern that keeps 15-year-old codebases untestable.

When would you replace the built-in container, and what do you lose? principal

You replace it for features it deliberately lacks: interception/decoration at scale (Autofac, Castle, or Scrutor on top of the built-in container), assembly scanning with conventions, child containers with different lifetimes, or property injection required by a legacy framework. What you lose is uniformity — a large chunk of the .NET ecosystem assumes IServiceCollection/IServiceProvider semantics, and features like ValidateOnBuild, keyed services and the ASP.NET Core scope contract have to be honoured by the adapter. In practice the pragmatic answer at principal level is: keep the built-in container, add Scrutor for scanning and decoration (it produces plain ServiceDescriptors, so nothing else changes), and treat a full third-party container as a decision that needs a written justification, because it is very hard to reverse once 200 registrations depend on its semantics.

Example 
// Decoration without swapping containers (Scrutor):
services.AddScoped<IOrderService, OrderService>();
services.Decorate<IOrderService, CachingOrderService>();
services.Decorate<IOrderService, LoggingOrderService>();   // outermost registered last

// Full replacement, if you must:
builder.Host.UseServiceProviderFactory(new AutofacServiceProviderFactory());
builder.Host.ConfigureContainer<ContainerBuilder>(b => b.RegisterModule<DomainModule>());

Follow-ups

  • Why is assembly scanning controversial? — Registration becomes invisible: nothing in the code says why a type is registered, and a rename silently drops a service. Scan narrowly, by marker interface, or not at all.
  • Does the built-in container support decoration? — Not natively; you can do it manually with a factory registration that resolves the inner type, which is what Scrutor generates.
  • AOT implications? — Reflection-heavy containers fight trimming and Native AOT; the built-in container plus explicit registrations is the AOT-friendly path.

Wrong answer: "The built-in container is not production-grade." It is; it is intentionally minimal and it is what the entire framework is built on. Naming a missing feature is a good answer; calling it a toy is not.

Your service graph has 900 registrations and startup takes 4 seconds. Where does the time go and what do you do? principal

Startup cost splits into three buckets and they are fixed differently. First, JIT: on a cold start most of the 4 seconds is compiling framework and application code, not container work — ReadyToRun (or Native AOT) and reducing the assembly graph moves the needle far more than trimming registrations. Second, container work: ValidateOnBuild walks every descriptor and compiles resolution delegates eagerly, and any registration whose factory does real work (reading configuration, opening a connection, calling GetAwaiter().GetResult()) runs at build or first resolve — those are the ones to find. Third, eager initialisation: IHostedService.StartAsync implementations that warm caches or run migrations block the server from listening at all. The measurement discipline matters more than the fixes: turn on Microsoft.Extensions.Hosting event counters or take an EventPipe startup trace (dotnet-trace collect --providers Microsoft-Windows-DotNETRuntime:0x1F000080018:5) and look at JIT time versus managed startup time before touching anything.

Example 
<PropertyGroup>
  <PublishReadyToRun>true</PublishReadyToRun>
  <PublishReadyToRunComposite>true</PublishReadyToRunComposite>
  <TieredPGO>true</TieredPGO>
  <InvariantGlobalization>true</InvariantGlobalization>
</PropertyGroup>

Follow-ups

  • Does registration count itself matter? — Barely; resolution is compiled per closed type on first use. Nine hundred descriptors cost microseconds, nine hundred eager factories cost seconds.
  • Would you move work out of StartAsync? — Yes: warm caches after the server starts listening (ApplicationStarted) and let readiness gate traffic, so the pod becomes live quickly and ready when warm.
  • Where does this bite hardest? — Autoscaling and serverless, where cold start is user-visible latency; that is the argument that gets AOT funded.

Wrong answer: "Switch everything to transient / singleton to speed up DI." Lifetimes are a correctness decision; the speedup is noise and the correctness cost is unbounded.

Interviewers use it to check that you understand endpoint routing as a two-phase system (match, then execute), that you can justify minimal APIs versus controllers on something other than taste, and that you know how parameters get bound — because binding surprises cause a disproportionate share of production bugs. Minimal APIs or controllers? Defend your choice. mid

Minimal APIs are the default for new HTTP APIs since .NET 7 or so: less ceremony, lower per-request overhead (no action invoker, no filter pipeline unless you add endpoint filters), first-class support for Native AOT via the request-delegate generator, and route groups that make cross-cutting configuration explicit. Controllers still earn their place when you want the machinery they bring: model binding conventions and [ApiController] behaviours, action filters and result filters, model-level validation, API versioning conventions, content negotiation and formatters, or when the app also serves Razor views. The real answer in an interview is a criterion, not a preference: pick minimal APIs unless you need MVC's conventions or already have hundreds of controllers, in which case mixing is fully supported — they share routing, DI, auth and OpenAPI — and rewriting working controllers for style points is not an engineering decision.

Example 
var v1 = app.MapGroup("/api/v1")
            .RequireAuthorization("api")
            .AddEndpointFilter<TenantFilter>()
            .WithTags("v1");

v1.MapGet("/orders/{id:guid}", async (Guid id, IOrderService s, CancellationToken ct)
        => await s.GetAsync(id, ct) is { } o ? Results.Ok(o) : Results.NotFound())
  .WithName("GetOrder")
  .Produces<OrderDto>()
  .ProducesProblem(StatusCodes.Status404NotFound);

Follow-ups

  • Can you mix them in one app? — Yes, freely; MapControllers() and MapGet register into the same endpoint table.
  • What is measurably faster? — Minimal APIs skip the MVC action invoker and filter pipeline; on a trivial endpoint that is worth a meaningful percentage of the request, on a database-bound endpoint it is noise.
  • What do you lose without [ApiController]? — Automatic 400 on invalid model state, inference of [FromBody], and automatic ProblemDetails — minimal APIs got their own validation story only in .NET 10.

Wrong answer: "Minimal APIs are only for demos and toy projects." They are the AOT-supported, template-default path for APIs; saying this signals you stopped reading after .NET 6.

How does routing pick between two candidate routes? senior

Endpoint routing builds a DFA-like tree over route templates at startup, so matching is O(segments) rather than a linear scan. When more than one template matches, precedence is decided by specificity, segment by segment: literals beat constrained parameters, constrained parameters beat plain parameters, plain parameters beat catch-all, and shorter/more-literal templates win overall. If two candidates are still tied, the framework throws AmbiguousMatchException at request time rather than guessing — the error you see when two controllers claim [HttpGet("items")]. You can override the outcome with Order on an endpoint (lower runs first) or with a custom MatcherPolicy/IEndpointSelectorPolicy, which is how HTTP method matching and CORS preflight selection are implemented. Route constraints ({id:int}, {slug:regex(…)}, {page:min(1)}) participate in matching, so they disambiguate as well as validate — but they are not input validation: they only decide which endpoint runs.

Example 
app.MapGet("/items/new",      () => "literal wins");
app.MapGet("/items/{id:int}", (int id) => $"int route {id}");
app.MapGet("/items/{slug}",   (string slug) => $"string route {slug}");
// GET /items/new -> "literal wins"; /items/42 -> int route; /items/blue -> string route

Follow-ups

  • Is a route constraint validation? — No. A failed constraint means "this endpoint does not match", so the client gets 404, not 400 — a real API-design consideration.
  • How do you debug a routing problem? — Enable Microsoft.AspNetCore.Routing debug logs, or hit the /debug/routes pattern by injecting EndpointDataSource and dumping the endpoint table.
  • What is a catch-all route? — {**rest}, which matches remaining segments including slashes; used for SPA fallbacks (MapFallbackToFile).

Wrong answer: "The first registered route wins." Registration order is irrelevant except as a tiebreaker via explicit Order; specificity decides.

How are parameters bound in a minimal API, and what is the inference order? mid

For each handler parameter the framework infers a source: explicit attributes first ([FromRoute], [FromQuery], [FromHeader], [FromBody], [FromForm], [FromServices], [AsParameters]); then special types (HttpContext, HttpRequest, ClaimsPrincipal, CancellationToken, Stream, IFormFile); then types registered in DI; then a type with a static TryParse or BindAsync — BindAsync takes over the whole binding for that type; then, if the name matches a route parameter, route, else query string. Anything left that is a complex type is bound from the JSON body, and only one parameter can come from the body. The two gotchas worth naming: a string parameter that matches nothing binds from the query and is simply null if absent (no 400 unless you check), and adding a service registration for a type you were binding from the body silently changes the source to DI.

Example 
// Group many query/route parameters into one record without losing binding:
public record ListQuery(int Page = 1, int Size = 20, string? Sort = null);

app.MapGet("/orders", ([AsParameters] ListQuery q, IOrderService s, CancellationToken ct)
    => s.ListAsync(q.Page, q.Size, q.Sort, ct));

// Custom binding for a domain type:
public readonly record struct TenantId(Guid Value)
{
    public static bool TryParse(string? s, out TenantId r)
        => (r = Guid.TryParse(s, out var g) ? new(g) : default) != default;
}

Follow-ups

  • TryParse vs BindAsync? — TryParse converts a single string value; BindAsync(HttpContext, ParameterInfo) owns the whole parameter and can read headers or the body.
  • How do you accept form data and files? — [FromForm] and IFormFile/IFormFileCollection; note antiforgery is required for browser form posts, and since .NET 8 minimal APIs validate the token when AddAntiforgery+UseAntiforgery are present.
  • What changed in .NET 10 for forms? — Empty form values now bind to null for nullable value types instead of failing, which removes a long-standing papercut.

Wrong answer: "Complex types always come from the body." Not if the type is in DI, has BindAsync, or is decorated — and the DI case is the one that silently breaks an endpoint when someone registers a new service.

What does [ApiController] actually do? mid

It opts a controller into a bundle of API-specific conventions: automatic 400 responses when ModelState is invalid (so you never write if (!ModelState.IsValid)), binding-source inference (complex types from the body, simple types from route/query, so [FromBody] becomes unnecessary), a requirement that every action has an attribute route, automatic ProblemDetails (RFC 7807/9457) for error status codes, and multipart/form-data inference for IFormFile. You can tune all of it through ApiBehaviorOptions — most usefully SuppressModelStateInvalidFilter when you want to shape validation errors yourself, and InvalidModelStateResponseFactory when you want to keep automatic 400s but change their body. The trade-off is implicitness: the 400 happens in a filter before your action runs, so a candidate who has never turned it off is often surprised that their custom validation never executes.

Example 
builder.Services.Configure<ApiBehaviorOptions>(o =>
{
    o.InvalidModelStateResponseFactory = ctx =>
    {
        var pd = new ValidationProblemDetails(ctx.ModelState)
        {
            Type = "https://errors.example.com/validation",
            Extensions = { ["traceId"] = Activity.Current?.Id ?? ctx.HttpContext.TraceIdentifier }
        };
        return new BadRequestObjectResult(pd) { ContentTypes = { "application/problem+json" } };
    };
});

Follow-ups

  • What is ProblemDetails and why standardise on it? — RFC 9457's machine-readable error shape (type, title, status, detail, instance + extensions); one shape means clients write one error handler.
  • Does it apply to minimal APIs? — No. Minimal APIs get ProblemDetails via AddProblemDetails() and Results.Problem/Results.ValidationProblem, and validation only from .NET 10's AddValidation().
  • What if you want per-controller behaviour? — The attribute is applicable at assembly, controller or base-class level; a shared ApiControllerBase is the usual pattern.

Wrong answer: "It just marks the class as an API controller for Swagger." Swagger does not need it; it changes binding and error behaviour at runtime.

How do you version a public HTTP API, and what breaks first? senior

Pick one transport for the version and be consistent: URL segment (/api/v2/orders) is the most cache- and log-friendly and the easiest to route; a header or media-type parameter (Accept: application/json;v=2) is purer REST but invisible in logs and CDNs; a query parameter is the worst of both. The mechanics in ASP.NET Core come from Asp.Versioning (the community-maintained successor to Microsoft.AspNetCore.Mvc.Versioning), which supports all three readers plus deprecation metadata, version-aware OpenAPI documents and route groups for minimal APIs. What actually breaks first is never routing — it is the shared model: a DTO reused by v1 and v2 quietly changes v1's contract when someone adds a required field or renames a property in the serializer. The defensible position is that versions get their own DTOs and their own contract tests, and that "additive changes do not need a version" is only true if you have a test that proves the old shape still round-trips.

Example 
builder.Services.AddApiVersioning(o =>
{
    o.DefaultApiVersion = new ApiVersion(1, 0);
    o.AssumeDefaultVersionWhenUnspecified = true;
    o.ReportApiVersions = true;                       // api-supported-versions header
    o.ApiVersionReader = new UrlSegmentApiVersionReader();
}).AddApiExplorer(o => o.GroupNameFormat = "'v'VVV");

var set = app.NewApiVersionSet().HasApiVersion(1.0).HasApiVersion(2.0).Build();
app.MapGroup("/api/v{version:apiVersion}").WithApiVersionSet(set)
   .MapGet("/orders", GetOrdersV2).MapToApiVersion(2.0);

Follow-ups

  • How do you retire a version? — Announce with Deprecated = true and the api-deprecated-versions header, measure per-version traffic with a metric tag, then brown-out (fail a growing percentage) before removal.
  • Do you version internal service-to-service APIs? — Usually not by URL; you use additive-only schema evolution and consumer-driven contract tests, because you control both sides and can deploy them independently.
  • What about gRPC? — Protobuf's field numbering gives you additive evolution for free; you version the package namespace only for breaking changes.

Wrong answer: "We version by adding v2 methods to the same controller and sharing the models." That is the exact mechanism by which v1 breaks without anyone changing v1.

How is OpenAPI generated in .NET 10, and what changed from Swashbuckle? senior

Since .NET 9 the templates ship Microsoft.AspNetCore.OpenApi instead of Swashbuckle: AddOpenApi() plus MapOpenApi() generates the document from the endpoint metadata at runtime, with IOpenApiDocumentTransformer, IOpenApiOperationTransformer and schema transformers as the extension points. .NET 10 moved the default output to OpenAPI 3.1 (built on Microsoft.OpenApi 2.0), which is a real breaking change for tooling: nullable types are expressed as oneOf [T, null] rather than nullable: true, and OpenApiAny was replaced by JsonNode — pin OpenApiVersion = OpenApiSpecVersion.OpenApi3_0 if your client generator has not caught up. .NET 10 also added YAML output (request the .yaml suffix), XML doc-comment inclusion via a source generator, and IOpenApiDocumentProvider so you can produce the document outside an HTTP request — which is how you generate the spec at build time for contract tests. Swashbuckle and NSwag are still perfectly viable and still ahead on some UI features; the shipped package is not a Swagger UI, so most teams add Scalar or Swagger UI on top.

Example 
builder.Services.AddOpenApi("v1", o =>
{
    o.OpenApiVersion = Microsoft.OpenApi.OpenApiSpecVersion.OpenApi3_1;   // .NET 10 default
    o.AddDocumentTransformer((doc, ctx, ct) =>
    {
        doc.Info.Title = "Orders API";
        doc.Info.Contact = new() { Name = "platform", Email = "platform@example.com" };
        return Task.CompletedTask;
    });
});
app.MapOpenApi();                       // /openapi/v1.json and /openapi/v1.yaml

Follow-ups

  • Where does the description text come from? — Endpoint metadata (WithSummary, WithDescription, Produces) and, since .NET 10, XML comments picked up by a source generator.
  • How do you keep the spec in source control? — Generate at build with dotnet run --project … -- --openapi or the Microsoft.Extensions.ApiDescription.Server MSBuild target, then diff it in CI to catch accidental breaking changes.
  • Does it work with Native AOT? — Yes for minimal APIs, and the .NET 10 webapiaot template includes it by default.

Wrong answer: "Swagger is built in, you just call AddSwaggerGen." That is a third-party package that the templates dropped in .NET 9; naming it as the built-in dates you by two releases.

Explain route groups and why they are more than syntactic sugar. mid

MapGroup returns a RouteGroupBuilder that prefixes the route pattern and, crucially, applies metadata and filters to every endpoint added to it — including nested groups. That makes cross-cutting concerns declarative and local: one group carries the auth policy, the rate-limiting policy, the OpenAPI tag and the tenant filter, so a new endpoint cannot forget them. It is more than sugar because the filters registered on a group are compiled once per endpoint at startup, not resolved per request, and because a group's metadata participates in endpoint selection and in OpenAPI generation. The structural benefit is what matters at review time: "which endpoints are anonymous?" becomes a question you can answer by reading the group declarations rather than grepping for [AllowAnonymous].

Example 
var api    = app.MapGroup("/api").AddEndpointFilter<CorrelationFilter>();
var secure = api.MapGroup("/orders").RequireAuthorization("orders:read")
                .RequireRateLimiting("per-tenant").WithTags("Orders");

secure.MapGet("/",         ListOrders);
secure.MapGet("/{id:guid}", GetOrder);
secure.MapPost("/",         CreateOrder).RequireAuthorization("orders:write");

api.MapGet("/ping", () => Results.Ok()).AllowAnonymous();   // the one exception, visibly

Follow-ups

  • Can you nest groups? — Yes, and metadata accumulates outermost-first; a nested RequireAuthorization adds a policy rather than replacing one.
  • What is the equivalent in MVC? — Controller-level attributes and conventions (IControllerModelConvention), applied at model-building time.
  • How do filters on a group differ from middleware? — They run only for matched endpoints in the group and see the bound arguments.

Wrong answer: "It is just string concatenation on the route prefix." Then you would not be able to attach filters or auth policies, which is most of the value.

Your endpoint returns IAsyncEnumerable<T>. What actually happens on the wire, and when is that wrong? senior

ASP.NET Core streams it: System.Text.Json serialises each element as it is produced and writes into the response body without buffering the whole collection, so memory stays flat for a million rows and the client sees the first bytes immediately. The costs are real, though. Once the first chunk is flushed the status code is fixed, so an exception on row 500,000 cannot become a 500 — the client gets a truncated JSON array and must detect that itself. You are also holding a database reader (and a connection, and possibly a transaction) open for the entire duration of the client's read, so a slow consumer pins a pooled connection; and with EF Core the DbContext lives for the whole stream, which conflicts with anything that disposes it per operation. Streaming is right for large exports and for server-sent events; for a normal paged API it trades an error-handling guarantee for latency you do not need.

Example 
app.MapGet("/export", (AppDbContext db, CancellationToken ct) =>
    db.Orders.AsNoTracking().OrderBy(o => o.Id).AsAsyncEnumerable());   // streamed, not buffered

// .NET 10: server-sent events as a first-class result
app.MapGet("/prices", (IPriceFeed feed, CancellationToken ct) =>
    TypedResults.ServerSentEvents(feed.StreamAsync(ct), eventType: "price"));

Follow-ups

  • How does the client know the stream failed? — It cannot from the status code; use SSE with an explicit error event, chunked framing with a terminator record, or trailers on HTTP/2.
  • Does response buffering help? — It restores error handling but reintroduces the memory cost; that is exactly the trade you are being asked to name.
  • What about back-pressure? — The PipeWriter applies it: your enumerator is throttled by FlushAsync when the client reads slowly, which is why a slow client holds the DB reader.

Wrong answer: "It works exactly like returning a List<T>, just lazier." The difference in failure semantics and in resource holding is the entire point of the question.

Fifteen teams, one API surface. How do you keep it coherent without becoming the bottleneck? principal

Encode the standard as code and tests, not as review. That means a shared package with the group conventions (error shape, pagination envelope, versioning, auth policy names, correlation and tenancy filters), an OpenAPI spec generated in CI and diffed against the previous build so breaking changes fail the pipeline rather than the customer, and a small set of linting rules — spectral or a custom analyzer over the generated spec — that check naming, required ProblemDetails responses, and that no endpoint is anonymous unless it is on an allowlist. Then choose your governance model deliberately: a design review only for new resources and breaking changes, with everything else self-service; an API guild that owns the standard rather than a central team that owns approvals. The failure mode you are guarding against is not inconsistency, it is the queue: if every endpoint needs your signature, teams will route around you and the standard dies quietly.

Example 
# CI: fail on an accidental breaking change
dotnet run --project src/Api -- --generate-openapi > openapi.new.json
oasdiff breaking openapi.baseline.json openapi.new.json --fail-on ERR
spectral lint openapi.new.json --ruleset .spectral.yaml

Follow-ups

  • How do you handle a team that needs to break the standard? — Make the exception explicit and time-boxed (an allowlist entry with an owner and a date); silent exceptions are how standards rot.
  • Consumer-driven contract tests or spec diffing? — Spec diffing catches syntactic breaks cheaply; contract tests catch semantic ones. Start with diffing, add contracts for the top consumers.
  • What is the one convention you would enforce hardest? — The error shape. Clients write error handling once, and every inconsistent endpoint costs every consumer.

Wrong answer: "Publish an API style guide and review every PR." It scales to about three teams and then becomes the release bottleneck everyone learns to bypass.

04 Async, the thread pool & concurrency

The runtime half of the topic that gets asked most, because it is where "works on my machine" turns into a 3 a.m. page. The framework question is not "what does await do" (that is C#) but what the thread pool does under load, why sync-over-async collapses a server, and how cancellation actually propagates through a request. Mid: no blocking calls, propagate CancellationToken. Senior: diagnose starvation from counters, explain the injection rate, know why ConfigureAwait is a no-op here. Principal: concurrency limits as a design tool — where you shed load, and why a queue in front of a database beats a bigger thread pool.

What is thread-pool starvation, how does it present, and how do you confirm it? senior

Starvation is when every pool thread is blocked on something that will only complete when other work runs, so the pool cannot make progress and new work queues. It presents as latency that climbs with load while CPU stays low, timeouts on healthy dependencies, and often a step function: fine at 200 rps, catastrophic at 250. The confirmation is two counters: ThreadPool Queue Length growing and ThreadPool Thread Count climbing slowly — slowly because after the initial free threads (roughly ProcessorCount) the hill-climbing algorithm injects only about one or two extra threads per second, which is far slower than requests arrive. The classic causes are .Result/.Wait()/GetAwaiter().GetResult() on an async call, synchronous I/O (File.ReadAllText, a sync database driver), and lock contention on a hot singleton. Raising ThreadPool.SetMinThreads is a mitigation that buys time, not a fix — it hides the blocking until the next traffic step.

Example 
dotnet-counters monitor -p 1 --counters System.Runtime[threadpool-queue-length,threadpool-thread-count,cpu-usage]
# queue-length climbing + cpu-usage ~30% == starvation, not saturation
// The line that causes it, in the wild:
public IActionResult Get() => Ok(_service.GetAsync().Result);   // blocks a pool thread on I/O
// The fix is boring and total:
public async Task<IActionResult> Get() => Ok(await _service.GetAsync());

Follow-ups

  • Does SetMinThreads ever belong in production? — Yes as a stopgap during a burst-heavy cold start, but log it and treat it as debt; it converts a starvation cliff into a memory cost (1 MB stack per thread by default).
  • How do you find the blocking call from a dump? — dotnet-dump analyze, then clrthreads and parallelstacks; blocked pool threads all sit in the same ManualResetEventSlim/Monitor.Wait frame.
  • Do async methods use pool threads while awaiting I/O? — No; that is the point. The continuation is scheduled on the pool when the I/O completes.

Wrong answer: "The server was out of CPU / we needed bigger machines." Low CPU with rising latency is the signature of starvation, and scaling out only moves the cliff.

Is ConfigureAwait(false) needed in ASP.NET Core? mid

Not in application code: ASP.NET Core has no SynchronizationContext (unlike ASP.NET Framework, which had one and made sync-over-async deadlock), so continuations already resume on a thread-pool thread and ConfigureAwait(false) changes nothing. It still matters in library code that might run under a UI or legacy ASP.NET context, which is why framework and NuGet libraries use it everywhere. The nuance worth adding: ConfigureAwait(false) does not stop AsyncLocal flow, so ILogger scopes, Activity.Current and HttpContext via IHttpContextAccessor still work; and .NET 8 added ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing) and ForceYielding, which are about exception and scheduling behaviour rather than contexts.

Example 
// In a shared library, still correct:
public async Task<Order> GetAsync(Guid id, CancellationToken ct)
{
    using var res = await _http.GetAsync($"/orders/{id}", ct).ConfigureAwait(false);
    return (await res.Content.ReadFromJsonAsync<Order>(ct).ConfigureAwait(false))!;
}
// In an ASP.NET Core controller, noise:
public async Task<IActionResult> Get(Guid id, CancellationToken ct) => Ok(await _svc.GetAsync(id, ct));

Follow-ups

  • Why did it deadlock on ASP.NET Framework? — The request context allowed one thread at a time; blocking on the outer task held it while the continuation waited for the same context.
  • Does removing it break HttpContext access? — No; IHttpContextAccessor uses AsyncLocal, which flows regardless.
  • What is ConfigureAwaitOptions.SuppressThrowing for? — Awaiting a task purely to wait for completion, ignoring faults — a targeted replacement for the try { await t; } catch { } idiom.

Wrong answer: "You must use it everywhere or you get deadlocks." That is ASP.NET Framework advice repeated for a decade after it stopped applying.

How does cancellation flow through a request, and what should you actually do with the token? mid

HttpContext.RequestAborted is signalled when the client disconnects (Kestrel detects the reset/closed stream); a CancellationToken parameter on a controller action or minimal API handler is bound to that token automatically. You pass it down to every async call — the database driver, HttpClient, the cache — so a client that gave up stops costing you a connection and a query. Two subtleties separate a mid from a senior answer. First, cancellation is cooperative and observed at await points: a CPU-bound loop must check ThrowIfCancellationRequested() itself. Second, cancelling a write is dangerous — cancelling midway through a database transaction or an outbound POST leaves ambiguous state, so for non-idempotent work you often deliberately use CancellationToken.None after the point of no return and rely on idempotency keys instead. And do not let OperationCanceledException pollute your error rate: it is a 499-style client abort, not a 500.

Example 
app.MapPost("/orders", async (CreateOrder cmd, IOrderService svc, HttpContext ctx) =>
{
    // read path: fully cancellable
    var quote = await svc.QuoteAsync(cmd, ctx.RequestAborted);

    // write path: past the point of no return, do not abandon half-done work
    var id = await svc.CommitAsync(quote, CancellationToken.None);
    return Results.Created($"/orders/{id}", new { id });
});

// combining shutdown + request cancellation
using var linked = CancellationTokenSource.CreateLinkedTokenSource(ctx.RequestAborted, appStopping);

Follow-ups

  • How do you keep cancellations out of your error budget? — Filter OperationCanceledException when RequestAborted.IsCancellationRequested in the exception handler and record it as a distinct outcome.
  • Does a timeout use the same mechanism? — Yes: CancellationTokenSource.CancelAfter, or .NET 8's RequestTimeouts middleware (WithRequestTimeout) which links a policy timeout into RequestAborted.
  • What if a library ignores the token? — You cannot cancel it; wrap it with Task.WaitAsync(ct) to stop waiting, and understand the work keeps running.

Wrong answer: "Pass the token everywhere including the commit." Cancelling a partially applied write is how you get orders that were charged but not recorded.

Fire-and-forget: I need to send an email after responding. What do you do? senior

Nothing that starts with _ = Task.Run(...). An unobserved task in a request handler can be killed by shutdown, loses its exception into the void, keeps a reference to a disposed DbContext or HttpContext, and has no back-pressure — under load you create unbounded work. The escalation ladder is: for cheap in-process work, a Channel<T> written by the request and drained by a BackgroundService, which gives you a bounded queue, a real cancellation token and one place to log failures; for anything that must not be lost, a durable queue plus the transactional outbox pattern, so the intent is committed in the same transaction as the business change and a worker publishes it. .NET also gives you IHostApplicationLifetime to drain the channel at shutdown. The framing that impresses is durability: "does the email have to survive a pod restart?" decides between the two, and nothing else does.

Example 
builder.Services.AddSingleton(Channel.CreateBounded<EmailJob>(
    new BoundedChannelOptions(10_000) { FullMode = BoundedChannelFullMode.Wait }));
builder.Services.AddHostedService<EmailWorker>();

app.MapPost("/signup", async (Signup s, Channel<EmailJob> q, CancellationToken ct) =>
{
    await SaveAsync(s, ct);
    await q.Writer.WriteAsync(new EmailJob(s.Email), ct);   // back-pressure, not fire-and-forget
    return Results.Accepted();
});

Follow-ups

  • What does BoundedChannelFullMode buy you? — An explicit overload policy: wait (back-pressure into the request), drop oldest, or fail fast. Unbounded means OOM under a spike.
  • Why an outbox rather than publishing directly? — Because "save the order" and "publish the event" are two systems; the outbox makes them one transaction plus an at-least-once relay.
  • How do you drain at shutdown? — Complete the writer on ApplicationStopping and let the worker finish the queue inside the shutdown timeout.

Wrong answer: "Task.Run and log any exception in a continuation." The continuation does not run if the process exits, and there is still no bound on how many you start.

How do you run several I/O calls concurrently in a handler, and what limits you? mid

Task.WhenAll over already-started tasks is the mechanism, and in .NET 9+ Task.WhenEach lets you process results as they land. The limits are the interesting part: HttpClient throttles per server via SocketsHttpHandler.MaxConnectionsPerServer (and HTTP/2 multiplexes over one connection with its own stream limit), the database throttles via the ADO.NET pool Max Pool Size (default 100 in SQL Server), and EF Core will simply throw if you fan out on one DbContext. Unbounded fan-out is the classic self-inflicted outage: 500 concurrent requests each firing 20 parallel calls is 10,000 in-flight operations against a dependency sized for a few hundred. Bound it explicitly — Parallel.ForEachAsync with MaxDegreeOfParallelism, or a SemaphoreSlim — and remember exceptions: await Task.WhenAll(t) rethrows only the first, so inspect t.Exception or the task list if you need all of them.

Example 
var opts = new ParallelOptions { MaxDegreeOfParallelism = 8, CancellationToken = ct };
var results = new ConcurrentBag<Detail>();
await Parallel.ForEachAsync(ids, opts, async (id, token) =>
    results.Add(await client.GetDetailAsync(id, token)));

// Two independent calls: fine to just fan out.
var (user, prefs) = (client.GetUserAsync(id, ct), client.GetPrefsAsync(id, ct));
await Task.WhenAll(user, prefs);

Follow-ups

  • Why not Parallel.For for I/O? — It is designed for CPU work on pool threads and will block them on I/O; Parallel.ForEachAsync (.NET 6+) is the async-aware version.
  • How do you surface all failures? — Task.WhenAll returns a task whose Exception is an AggregateException; await unwraps only the first, so read the property when you need the rest.
  • What is the effect on tail latency? — Fan-out makes you as slow as your slowest dependency; hedging or per-call timeouts are the countermeasure.

Wrong answer: "Just Task.WhenAll over all 5,000 items — async is cheap." Async tasks are cheap; the connections, sockets and dependency capacity behind them are not.

What is ValueTask, and when is it the wrong choice? senior

ValueTask<T> avoids allocating a Task object when the operation usually completes synchronously — a cache hit, a buffered read, a pooled channel take. It matters on very hot paths (Stream.ReadAsync, ChannelReader.ReadAsync, IValueTaskSource-backed APIs) where the allocation shows up in a profile. It is the wrong choice as a default return type for ordinary application code, because it is a struct with sharp edges: you may await it exactly once, you may not await it concurrently, and you may not block on .Result before it completes — violate any of these with a pooled IValueTaskSource implementation and you get corruption rather than an exception. The rule that reads as senior: return Task by default; return ValueTask when you have measured a hot synchronous-completion path; and if a caller needs to await twice, call AsTask() once and share that.

Example 
public ValueTask<User> GetAsync(int id, CancellationToken ct)
    => _cache.TryGetValue(id, out User? u)
        ? ValueTask.FromResult(u!)          // no allocation on the common path
        : new ValueTask<User>(LoadAsync(id, ct));

// Caller that needs it twice:
var vt = GetAsync(1, ct);
Task<User> t = vt.AsTask();                 // now safe to await/store/await again

Follow-ups

  • What does Task.CompletedTask save? — The same idea for the non-generic case: a cached singleton, so a synchronous Task-returning method allocates nothing.
  • Does async ValueTask allocate? — Yes when it completes asynchronously, unless you use [AsyncMethodBuilder(typeof(PoolingAsyncValueTaskMethodBuilder))], which pools the state machine.
  • What is runtime async? — A .NET 11 preview feature where the runtime, not the compiler, generates the async state machine; ASP.NET Core's shared framework is already compiled with it in preview builds, reducing per-await allocations.

Wrong answer: "Use ValueTask everywhere, it is always faster." When the operation completes asynchronously it is a larger struct copied through the state machine and is often marginally worse, plus you inherit the single-await constraint for no gain.

How do you protect a downstream dependency from your own traffic? senior

Two layers, and they are not interchangeable. Inbound: the rate-limiting middleware (.NET 7+) with a policy that matches your fairness requirement — fixed window for simple quotas, sliding window for smoother enforcement, token bucket for burst tolerance, and concurrency limiter when the constraint is simultaneous work rather than rate. Partition by whatever unit you actually want to protect (tenant, API key, user), give it a bounded queue so short bursts wait instead of failing, and always return 429 with Retry-After. Outbound: a bulkhead plus circuit breaker (Microsoft.Extensions.Http.Resilience / Polly v8) so one slow dependency cannot consume all your concurrency. The judgment is in what you do when the limit is hit: shed load early and cheaply at the edge, prefer queueing only when the wait is shorter than the client's timeout, and make sure the 429 path is far cheaper than the success path — otherwise the limiter itself becomes the outage.

Example 
builder.Services.AddRateLimiter(o =>
{
    o.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
    o.OnRejected = async (ctx, ct) =>
    {
        if (ctx.Lease.TryGetMetadata(MetadataName.RetryAfter, out var after))
            ctx.HttpContext.Response.Headers.RetryAfter = ((int)after.TotalSeconds).ToString();
        await ctx.HttpContext.Response.WriteAsJsonAsync(new ProblemDetails { Title = "Too many requests" }, ct);
    };
    o.AddPolicy("per-tenant", ctx => RateLimitPartition.GetTokenBucketLimiter(
        ctx.User.FindFirstValue("tenant") ?? "anon",
        _ => new TokenBucketRateLimiterOptions
        { TokenLimit = 100, TokensPerPeriod = 50, ReplenishmentPeriod = TimeSpan.FromSeconds(1), QueueLimit = 20 }));
});
app.UseRateLimiter();

Follow-ups

  • Why is the limiter in-process a problem? — With N replicas your effective limit is N × the configured limit; for a real quota you need a shared store (Redis) or enforcement at the gateway.
  • Queue or reject? — Queue only if the expected wait is well under the client timeout; otherwise you convert fast failures into slow failures and hold resources.
  • Where does the concurrency limiter beat a rate limiter? — When the dependency's constraint is simultaneous work (database connections, a licensed service), not requests per second.

Wrong answer: "Autoscale — if we get more traffic we add pods." Scaling the caller multiplies the pressure on the dependency that is already the bottleneck.

Where does per-request state live, and what are the traps with AsyncLocal and IHttpContextAccessor? senior

IHttpContextAccessor is an AsyncLocal<HttpContext> under the hood, so the context flows into awaited continuations but not backwards into the caller, and it is not valid after the request ends. The traps follow from that: capturing the accessor's value in a fire-and-forget task gives you a context whose response has been disposed; setting AsyncLocal state inside a method does not affect the caller, because the copy-on-write semantics only push values down the async flow; and holding it in a singleton means whatever request happened to run last. It also has a cost — enabling it makes the framework flow the execution context on every request — so the guidance is to inject what you need (a scoped ICurrentUser populated once by middleware) rather than reaching for the ambient context everywhere. For cross-cutting values that must reach logs and traces, the right vehicle is a logging scope and Activity baggage/tags, not your own AsyncLocal.

Example 
// Preferred: an explicit scoped abstraction, populated once.
public interface ICurrentUser { string TenantId { get; } string UserId { get; } }

public sealed class CurrentUser : ICurrentUser
{
    public string TenantId { get; private set; } = "";
    public string UserId  { get; private set; } = "";
    internal void Set(ClaimsPrincipal p)
        => (TenantId, UserId) = (p.FindFirstValue("tenant") ?? "", p.FindFirstValue(ClaimTypes.NameIdentifier) ?? "");
}
builder.Services.AddScoped<CurrentUser>();
builder.Services.AddScoped<ICurrentUser>(sp => sp.GetRequiredService<CurrentUser>());

Follow-ups

  • Why does AsyncLocal flow down but not up? — Each async operation gets a copy of the execution context; a child's mutation is invisible to the parent by design.
  • What is the cost of AddHttpContextAccessor? — Small but not zero; it forces execution-context flow. In hot paths it is measurable.
  • How does Activity.Current avoid the same trap? — It has the same trap, and it is why a background task started from a request keeps the parent trace unless you deliberately start a new Activity.

Wrong answer: "Use a static [ThreadStatic] field for the current user." Async continuations resume on different threads; you will read another request's user under load, which is a security incident.

Design the concurrency model for a service that must never overwhelm a legacy backend allowing 20 concurrent calls. principal

Start from the constraint and work outwards: 20 concurrent calls is a semaphore, not a rate. So the outbound path gets a bulkhead of 20 (plus a small queue), the inbound path gets an admission control policy that rejects rather than queues once the expected wait exceeds the client's timeout, and every layer between them is sized so the queue lives in exactly one place — multiple queues in series is how you get 30-second latencies with an idle backend. Then decide the shape of failure: fast 429/503 with Retry-After for interactive traffic, and a durable queue for anything that can be asynchronous, which converts a capacity problem into a latency problem you can measure. Add a circuit breaker so a backend that starts timing out is not fed 20 doomed calls at a time, and hedge only for idempotent reads. Finally, make the limit observable: emit queue depth, wait time and rejection rate as metrics with the backend as a dimension, and alert on saturation of the semaphore, not on the resulting user-visible errors — by then it is late. Little's law is the sanity check you should quote unprompted: with 20 concurrent slots and a 100 ms backend, your ceiling is 200 rps, and no amount of pod scaling changes it.

Example 
builder.Services.AddHttpClient<LegacyClient>()
  .AddResilienceHandler("legacy", b => b
      .AddConcurrencyLimiter(permitLimit: 20, queueLimit: 40)
      .AddCircuitBreaker(new() { FailureRatio = .5, SamplingDuration = TimeSpan.FromSeconds(30),
                                 MinimumThroughput = 20, BreakDuration = TimeSpan.FromSeconds(15) })
      .AddTimeout(TimeSpan.FromSeconds(2)));

Follow-ups

  • Why is the limit per pod a problem? — Ten replicas × 20 = 200 concurrent calls. Either divide the budget, or enforce centrally (a proxy/sidecar with a shared semaphore).
  • What do you monitor to know it is working? — Semaphore wait time p99 and rejection rate; a healthy bulkhead shows queueing before it shows errors.
  • When is a queue the wrong answer? — When the work is only valuable while the user is waiting; then shedding is kinder than queueing.

Wrong answer: "Retry with exponential backoff until it succeeds." Retries against a saturated dependency add load exactly when it can least take it; without a circuit breaker and a concurrency cap, retry is an amplifier.

05 Configuration, options & secrets

Configuration looks trivial and is asked constantly, because the wrong answer is a production incident with a very short blast radius to explain: a secret in appsettings.json, a feature flag that never refreshes, an options object read once at startup. The interesting depth is the options pattern — three interfaces with different lifetimes — and validation, because "the app started and then failed on the first request with a null connection string" is a story every interviewer has lived. Mid: the provider chain and the options interfaces. Senior: reload semantics, validation, secret management. Principal: configuration as a deployment concern and how you stop a bad value from taking down a fleet.

docs: Configuration in ASP.NET Core · Options pattern

What is the default configuration provider order, and how do you override a nested value from an environment variable? screener

CreateBuilder adds, in order: appsettings.json, appsettings.{Environment}.json, user secrets (Development only), environment variables, then command-line arguments — later sources win, because the configuration root is an ordered list queried last-to-first. Nested keys are flattened with : as the separator (Logging:LogLevel:Default), and because : is illegal in environment-variable names on some platforms, __ (double underscore) is the portable substitute. Arrays are just indexed keys (Cors:Origins:0). The consequence people forget: an environment variable overrides only the exact key it names, so setting ConnectionStrings__Default replaces one string but setting Cors__Origins__0 replaces only the first element of an array while leaving the rest from JSON — arrays merge by index rather than being replaced wholesale.

Example 
# These are equivalent to {"Logging":{"LogLevel":{"Default":"Warning"}}}
export Logging__LogLevel__Default=Warning
export ConnectionStrings__Default="Host=db;Database=orders"
dotnet run --Logging:LogLevel:Default=Debug          # command line wins over both

Follow-ups

  • How do you see the effective configuration? — Cast to IConfigurationRoot and call GetDebugView(); it lists every key with the provider that supplied it. Never expose it on a public endpoint.
  • Where do user secrets actually live? — Outside the repo, in the user profile keyed by UserSecretsId; they are a dev convenience with no encryption, not a production mechanism.
  • How do you add a provider? — builder.Configuration.AddJsonFile(...) / AddAzureKeyVault(...); order of the Add calls is the precedence.

Wrong answer: "appsettings.json wins because it is the app's own config." It is the lowest-precedence source; the whole design assumes deployment-time override.

IOptions, IOptionsSnapshot, IOptionsMonitor — which one and why? mid

IOptions<T> is a singleton computed once on first access: use it for values that cannot change at runtime, and it is the only one you can inject into a singleton without thinking. IOptionsSnapshot<T> is scoped and recomputed per request, so a configuration reload takes effect on the next request — it supports named options and it is the usual choice for anything reloadable in request handling, but it cannot be injected into a singleton. IOptionsMonitor<T> is a singleton that exposes CurrentValue plus OnChange callbacks; it is what you use in a singleton or background service that must react to changes, and it is the only one with change notifications. The gotcha that shows experience: OnChange fires more than once per file write on many platforms (editors write in several steps), so debounce it, and dispose the returned registration or you leak the callback.

Example 
builder.Services.AddOptions<PricingOptions>()
    .Bind(builder.Configuration.GetSection("Pricing"))
    .ValidateDataAnnotations()
    .Validate(o => o.MaxDiscount <= 0.5m, "MaxDiscount must be <= 50%")
    .ValidateOnStart();                       // fail at startup, not on first request

public sealed class PriceWorker(IOptionsMonitor<PricingOptions> opts) : BackgroundService
{
    protected override Task ExecuteAsync(CancellationToken ct)
    {
        using var _ = opts.OnChange(o => _log.LogInformation("pricing reloaded: {Max}", o.MaxDiscount));
        return Loop(() => opts.CurrentValue, ct);
    }
}

Follow-ups

  • Which one supports named options? — Snapshot and monitor via Get(name); IOptions<T> always returns the default (Options.DefaultName, the empty string).
  • Why does injecting IOptionsSnapshot into a singleton fail? — It is scoped; scope validation catches it, and without validation you get the first request's values forever.
  • What does ValidateOnStart change? — Validation runs during host startup instead of lazily on first resolve, turning a 3 a.m. 500 into a failed deployment.

Wrong answer: "They are the same, just different lifetimes for convenience." The lifetime is the semantics: it decides whether a config change ever reaches your code.

How do you validate configuration so a bad value never reaches production? senior

Three layers, in increasing strength. In the app: AddOptions<T>().Bind(...).ValidateDataAnnotations().Validate(predicate).ValidateOnStart(), so an invalid value fails the host at startup and the deployment rolls back rather than serving errors; in .NET 8+ you can add [OptionsValidator] source-generated validators to keep this AOT-friendly and allocation-free. In the pipeline: schema-validate the configuration artefact (a JSON Schema for appsettings, or typed Helm values) so a typo is caught before it is deployed anywhere. In the platform: treat configuration as a versioned, reviewed artefact with the same rollout controls as code — canary the config change to one replica, watch the health signal, then roll forward. The extra point worth making is that binding is forgiving by default: an unknown key is silently ignored and a mistyped key simply leaves the property at its default, so BinderOptions.ErrorOnUnknownConfiguration and a required-property model are what turn a typo into a failure.

Example 
public sealed class SmtpOptions
{
    [Required] public required string Host { get; init; }
    [Range(1, 65535)] public int Port { get; init; } = 587;
    [Required, MinLength(1)] public required string From { get; init; }
}

[OptionsValidator]                                   // source-generated, no reflection
public sealed partial class SmtpOptionsValidator : IValidateOptions<SmtpOptions> { }

builder.Services.AddSingleton<IValidateOptions<SmtpOptions>, SmtpOptionsValidator>();
builder.Services.AddOptions<SmtpOptions>()
    .Bind(builder.Configuration.GetSection("Smtp"), o => o.ErrorOnUnknownConfiguration = true)
    .ValidateOnStart();

Follow-ups

  • What does required do for binding? — The binder must supply it or throw; combined with nullable reference types it makes "missing config" a compile-visible concept.
  • How do you validate cross-field rules? — IValidateOptions<T> with ValidateOptionsResult.Fail, or a .Validate delegate; data annotations alone cannot express them.
  • What about validating on reload? — Validation runs when options are recomputed, so a bad hot reload fails on the next Get; make sure you catch and keep serving the old value rather than crashing every request.

Wrong answer: "We check for nulls where we use the config." That distributes one startup failure across a hundred call sites and fails on the first user request instead of the deployment.

Where do secrets live, and how do they get rotated without a redeploy? senior

Not in the repository and not in the image: the ladder is user secrets in development, then the platform's secret store in every other environment — Key Vault, Secrets Manager, or Kubernetes secrets fed by an external-secrets operator. The configuration system supports this directly (AddAzureKeyVault with a reload interval, or file-based providers over a mounted secret volume with reloadOnChange: true), and the strongly preferred variant is to have no long-lived secret at all: managed identity / workload identity so the token is issued to the pod and rotated by the platform. For rotation without a redeploy the app must actually re-read: IOptionsMonitor or a client that resolves its credential per call, plus a dual-secret window (accept both old and new) so rotation is not a synchronised cutover. The failure everyone has seen: the secret rotates, the app holds the old value in a singleton captured at startup, and the outage starts the moment the old credential expires — not at rotation time, which makes it hard to correlate.

Example 
builder.Configuration.AddAzureKeyVault(
    new Uri($"https://{vault}.vault.azure.net/"),
    new DefaultAzureCredential(),               // workload identity: no secret to rotate
    new AzureKeyVaultConfigurationOptions { ReloadInterval = TimeSpan.FromMinutes(5) });

// Kubernetes secret mounted as files, reloaded on change:
builder.Configuration.AddKeyPerFile("/mnt/secrets", optional: true, reloadOnChange: true);

Follow-ups

  • How do you detect a secret in the repo? — Push protection / secret scanning in the forge plus a pre-commit hook; and treat any leaked secret as compromised even if the commit was amended.
  • Are environment variables safe for secrets? — Better than files in the image, worse than a store: they appear in /proc, crash dumps and many diagnostic endpoints, and they cannot rotate without a restart.
  • What protects the ASP.NET Core data-protection keys? — Persist the key ring to shared storage and encrypt it at rest (Key Vault, DPAPI, certificate); otherwise every pod has its own ring and cookies break on restart.

Wrong answer: "We encrypt appsettings.Production.json and ship it in the image." The decryption key ships with it; you have obfuscation, not secrecy, and rotation still needs a deploy.

How does reloadOnChange actually work, and what does it not reload? mid

The JSON file provider watches the file with a FileSystemWatcher-based IFileProvider; on change it reparses and raises a change token, which invalidates IOptionsMonitor/IOptionsSnapshot caches and fires OnChange. What it does not reload is anything that read IConfiguration once and kept the value: constructor-captured strings, IOptions<T>, connection strings already handed to a pooled DbContext, Kestrel endpoint bindings, or the logging filters unless you used the configuration-based logging provider. In containers there is an extra wrinkle: a Kubernetes ConfigMap mounted as a volume is updated by swapping a symlink, and some watchers miss that, so many teams poll or restart on config change instead; CreateSlimBuilder also disables file watching by default. Knowing the difference between "config reloaded" and "the object that read it was rebuilt" is the whole question.

Example 
// Reloads:
builder.Configuration.AddJsonFile("appsettings.json", optional: false, reloadOnChange: true);
var monitor = sp.GetRequiredService<IOptionsMonitor<FeatureOptions>>();  // sees new values

// Does not reload:
public sealed class Legacy(IConfiguration cfg)
{
    private readonly string _url = cfg["Api:Url"]!;   // captured once, forever
}

Follow-ups

  • How do you reload log levels at runtime? — They already are, if levels come from Logging configuration: ILoggerFactory subscribes to the change token, so you can raise verbosity for one incident without a restart.
  • Can Kestrel endpoints reload? — Yes since .NET 6 for Kestrel:Endpoints configuration including certificates, but not all options are re-applied; verify rather than assume.
  • Cost of watching? — A watcher per file plus reparsing; trivial normally, but on some container filesystems the watcher polls, which is why slim builders opt out.

Wrong answer: "Changing appsettings.json restarts the app." It does not; nothing restarts, which is precisely why stale captured values are so confusing to debug.

Feature flags: how would you add them, and what changes at scale? senior

The minimum viable version is Microsoft.FeatureManagement over configuration: IFeatureManager.IsEnabledAsync("X"), [FeatureGate] on controllers, MapGet(...).WithFeatureGate(...)-style filters, and built-in filters for percentage rollout and time windows. That works because configuration already reloads, so flipping a flag is a config change rather than a deploy. What changes at scale is everything around the switch: you need targeting (per user, per tenant) that is consistent — hash the subject id so the same user does not flap between variants on every request — a central store with an audit trail (Azure App Configuration, LaunchDarkly, Unleash), a kill switch that is independent of the normal config path so you can disable a feature when the config service itself is degraded, and expiry, because the real cost of flags is the combinatorial explosion of untested code paths. The senior framing: a flag is a branch in production; treat removing it as part of the feature's definition of done.

Example 
builder.Services.AddFeatureManagement()
    .AddFeatureFilter<TargetingFilter>()          // consistent %-rollout by user id
    .AddFeatureFilter<TimeWindowFilter>();

app.MapGet("/checkout", async (IFeatureManager f, IOldCheckout oldC, INewCheckout newC) =>
    await f.IsEnabledAsync("NewCheckout") ? await newC.RunAsync() : await oldC.RunAsync());

Follow-ups

  • Why does consistency matter for percentage rollouts? — Without a stable hash, a user gets variant A and B on consecutive requests, which breaks sessions and makes metrics meaningless.
  • How do you measure a flag? — Emit the variant as a low-cardinality metric dimension and as a trace tag, so error rate and latency can be sliced by variant.
  • What is the difference between a flag and configuration? — Intent and lifetime: a flag is temporary and expected to be removed; configuration is permanent. Storing them together guarantees flags are never removed.

Wrong answer: "if (config["NewThing"] == "true") everywhere." No targeting, no audit, no consistency, and no way to find every flag when it is time to delete one.

A config change took down the fleet. Design the system so that cannot happen. principal

Treat configuration exactly like code: versioned, reviewed, tested, and rolled out progressively — the fact that it is "just a value" is the reason it bypasses every safety mechanism you built for deploys. Concretely: schema-validate at author time, validate at startup with ValidateOnStart so a bad value fails one pod instead of serving errors, and make the rollout staged — one pod, then one zone, then the fleet — with an automatic halt on a health signal. Then design for the case where it still gets through: last-known-good caching so a pod that cannot fetch or parse configuration keeps running with the previous values rather than crash-looping, a hard-coded safe default for every value that gates traffic, and a rollback path that does not depend on the same control plane. The organisational half is the audit trail: every change attributable, diffable and revertible in one action, because in the middle of an incident "who changed what" is the question that costs the most minutes. And measure it — configuration-change events should appear on the same timeline as deploys in your dashboards, or nobody will correlate them.

Example 
// Fail fast on this pod, keep the fleet alive; the orchestrator stops the rollout.
try { host.Services.GetRequiredService<IOptions<CriticalOptions>>().Value; }
catch (OptionsValidationException ex)
{
    logger.LogCritical(ex, "invalid configuration: {Failures}", string.Join("; ", ex.Failures));
    return 78;   // EX_CONFIG: crashloop this pod, do not proceed with the rollout
}

Follow-ups

  • Crash or degrade on bad config? — Crash at startup (the rollout stops); degrade at reload (keep the last good values and alert), because a running fleet crashing on a hot reload is the worst of both.
  • How do you test a config change? — Load the real artefact in a test that binds and validates every options type; it catches typos that no unit test would.
  • What about dynamic values that must be instant? — Kill switches; give them their own minimal path with a hard-coded fallback, and never route them through the same store as ordinary config.

Wrong answer: "We will add a review step for config changes." Reviews catch intent, not typos, and they do not help at 3 a.m. when someone is changing a value to stop an incident.

06 Memory, GC & allocation

The runtime question that separates people who have run .NET in production from people who have written it. Interviewers ask because memory problems are the most common .NET incident after starvation, and because the vocabulary — generations, LOH, server vs workstation, DATAS — is a fast proxy for depth. Mid: generations and what a leak looks like. Senior: read a dotnet-gcdump, explain GC modes and container limits, know Span/pooling. Principal: choose GC configuration for a workload with numbers, and know when the answer is architecture rather than tuning.

docs: Fundamentals of garbage collection · GC config settings

Explain the generational GC and why it exists. screener

The heap is split into generations on the empirical observation that most objects die young. New allocations go to gen 0, which is small and collected very often and very cheaply — a gen 0 collection only traces the objects that survived, so if nearly everything is garbage the cost is near zero. Survivors are promoted to gen 1 (a buffer generation) and then gen 2, which holds long-lived data and is collected rarely because tracing it is expensive. Objects of 85,000 bytes or more go straight to the Large Object Heap, which is collected with gen 2 and, by default, is not compacted, so it fragments; .NET 5 added the Pinned Object Heap for pinned buffers to keep them out of the way. The mechanism that makes this correct is the write barrier plus card table: when an old object starts referencing a young one, the runtime records it so a gen 0 collection does not have to scan gen 2. .NET 10 improved the Arm64 write-barrier implementation specifically, reporting GC pause improvements between roughly 8% and 20% with the new defaults.

Example 
dotnet-counters monitor -p 1 --counters System.Runtime[gc-heap-size,gen-0-gc-count,gen-1-gc-count,gen-2-gc-count,loh-size,time-in-gc,alloc-rate]
# healthy: many gen0, few gen1, rare gen2, time-in-gc < ~5%

Follow-ups

  • Why is the LOH threshold 85,000 bytes? — An empirical cutoff from the original tuning; above it, copying costs more than the fragmentation, so the LOH is swept, not compacted, by default.
  • Can you compact the LOH? — Yes: GCSettings.LargeObjectHeapCompactionMode = CompactOnce before an induced collection. It is expensive and a maintenance-window tool.
  • What is a card table? — A bitmap marking regions of old generations that were written to, so young collections scan only those regions.

Wrong answer: "Gen 2 is for large objects." Size decides LOH vs SOH; age decides generation. They are independent axes and confusing them makes every follow-up wrong.

Workstation vs server GC, and what did DATAS change? senior

Workstation GC uses one heap and prioritises short pauses; server GC allocates one heap and one dedicated GC thread per core, which raises throughput dramatically for a multi-core server but also raises the memory footprint, because each heap has its own budget. ASP.NET Core enables server GC by default. DATAS — Dynamic Adaptation To Application Sizes — became the default for server GC in .NET 9: instead of committing heaps proportional to core count, the GC starts small and adapts the number of heaps and the heap size to the application's actual live data and throughput, which typically cuts memory use substantially for small and idle services and makes container sizing far more predictable. The trade-off you should name unprompted: DATAS adds GC work for workloads with a stable, large working set and bursty allocation, so a service with a big cache can see more frequent collections; measure under production-representative load, and if it hurts, System.GC.DynamicAdaptationMode = 0 turns it off.

Example 
<PropertyGroup>
  <ServerGarbageCollection>true</ServerGarbageCollection>
  <ConcurrentGarbageCollection>true</ConcurrentGarbageCollection>
</PropertyGroup>
{ "configProperties": {
    "System.GC.Server": true,
    "System.GC.DynamicAdaptationMode": 1,        // 1 = DATAS on (default in .NET 9+)
    "System.GC.HeapHardLimitPercent": 75         // stay under the container limit
} }

Follow-ups

  • When is workstation GC right on a server? — Many small processes per host (dense multi-tenant sidecars), or a single-core container where server GC's per-core heaps buy nothing.
  • What is background GC? — Concurrent gen 2 collection on a background thread so most of the gen 2 trace happens without a full pause; on by default.
  • How do you verify which mode is running? — GCSettings.IsServerGC, or the gc-heap-count counter (server GC > 1 heap).

Wrong answer: "Server GC is always better for a server." It is a throughput/memory trade; in a 256 MB container with two cores it can be strictly worse, which is the problem DATAS exists to solve.

Your container gets OOM-killed at 512 MB but the .NET heap shows 200 MB. Explain. senior

The managed heap is only part of the process's RSS. The rest is: the GC's committed-but-unused memory (it does not return everything to the OS immediately), native allocations from libraries (OpenSSL, ICU globalization data, a native database driver), thread stacks at 1 MB each — a starved app with 300 pool threads is 300 MB of stacks — memory-mapped assemblies and the JIT's code heap, and any ArrayPool/buffer pools you configured. The cgroup limit counts all of it. The runtime is container-aware and reads the cgroup limit to set a heap hard limit (75% of the limit by default), so the fix is usually to give it explicit budgets: System.GC.HeapHardLimitPercent, DOTNET_GCHeapHardLimit, and a memory request/limit that leaves headroom for native memory rather than being sized off the managed heap. Confirm rather than guess: compare the gc-heap-size counter, Environment.WorkingSet, and the cgroup's memory.current — the gap between the first and the last is exactly what you are looking for.

Example 
cat /sys/fs/cgroup/memory.max /sys/fs/cgroup/memory.current
dotnet-counters monitor -p 1 --counters System.Runtime[gc-heap-size,gc-committed,working-set,threadpool-thread-count]
dotnet-gcdump collect -p 1     # managed graph only: if it is small, the problem is native

Follow-ups

  • What is InvariantGlobalization worth? — Dropping ICU saves tens of MB of native memory and the ICU data files; the cost is culture-sensitive comparison and formatting, so audit for it first.
  • Does GC.Collect() help? — Almost never in production; it can force decommit with GCSettings.LatencyMode games, but if you need it, the real problem is elsewhere.
  • Why does memory not drop after load? — The GC keeps committed segments for reuse; DATAS makes this far less pronounced, and GCConserveMemory pushes it further.

Wrong answer: "There must be a managed memory leak." A leak shows as a growing gen 2 in the gcdump; a flat managed heap with a growing RSS points at native memory, stacks or committed-not-returned pages.

How do you find a managed memory leak in a running production service? senior

Take two dotnet-gcdump snapshots several minutes apart under steady load and diff them: the type whose instance count grows monotonically is your leak, and the retention path in the diff tells you who is holding it. The classic roots in ASP.NET Core are a static or singleton collection that only ever gets added to, event handlers never unsubscribed (the publisher outlives the subscriber), IDisposable transients resolved from the root provider, an unbounded IMemoryCache with no size limit or expiration, and captured HttpContext/DbContext in a long-lived closure. A gcdump is cheap (it triggers a GC and walks the graph, no full dump), safe to take in production and small enough to copy out; a full dotnet-dump plus dumpheap -stat / gcroot is the next step when you need field-level detail. The discipline that gets marks: state the hypothesis from the counters first (gen-2-gc-count and gc-heap-size both climbing), then confirm with the dump — not the reverse.

Example 
dotnet-gcdump collect -p 1 -o t0.gcdump
sleep 600
dotnet-gcdump collect -p 1 -o t1.gcdump   # open both in Visual Studio / PerfView and diff

# or from a full dump:
dotnet-dump analyze core.1234
> dumpheap -stat
> gcroot -all 00007f3c1a2b3c40

Follow-ups

  • What is the most common leak in a web app? — An unbounded cache. IMemoryCache without SizeLimit or expiry grows until the container dies.
  • How do you leak with events? — A short-lived subscriber attached to a singleton's event is rooted by it forever; use weak events or unsubscribe in Dispose.
  • Can a gcdump be taken from a distroless image? — Via dotnet-monitor as a sidecar or an ephemeral debug container sharing the process namespace.

Wrong answer: "Restart it nightly and add an alert." That is a mitigation, not a diagnosis, and it hides the growth rate until the day traffic doubles.

Where does Span<T> actually pay off in a web app, and where is it cargo cult? senior

Span<T>/Memory<T> pay off where you are slicing existing buffers on a hot path: parsing headers and tokens, splitting strings without allocating substrings, formatting into a stack buffer with TryFormat, and reading from a PipeReader where the data already lives in pooled memory. That is why Kestrel, System.Text.Json and the header parsers are written in terms of them. In ordinary application code — a controller that loads an entity and maps it to a DTO — the allocation cost is dwarfed by the database call, and rewriting it in spans buys nothing while making the code harder to read and harder to make async (a Span is a ref struct: it cannot cross an await, cannot be a field of a class, cannot be captured by a lambda). The mature answer is to name the boundary: use spans inside a measured hot loop, and pooling (ArrayPool<byte>.Shared, RecyclableMemoryStream) for large short-lived buffers to keep them off the LOH; do neither speculatively.

Example 
// Worth it: parse a bearer token with no allocation.
static bool TryGetToken(ReadOnlySpan<char> header, out ReadOnlySpan<char> token)
{
    token = default;
    if (!header.StartsWith("Bearer ", StringComparison.OrdinalIgnoreCase)) return false;
    token = header["Bearer ".Length..].Trim();
    return !token.IsEmpty;
}

// Worth it: a large buffer that would otherwise hit the LOH every request.
var buf = ArrayPool<byte>.Shared.Rent(128 * 1024);
try { /* ... */ } finally { ArrayPool<byte>.Shared.Return(buf); }

Follow-ups

  • Why can't a Span cross an await? — It is a ref struct that may point at the stack; the async state machine would have to store it on the heap.
  • What is the risk of ArrayPool? — Returning a buffer you still hold, or not clearing sensitive data; both produce cross-request data bleed, which is a security bug.
  • What did .NET 10 add here? — More automatic stack allocation: the JIT now stack-allocates small fixed-size arrays of value and reference types, and escape analysis covers local struct fields and delegates, so some allocations disappear without code changes.

Wrong answer: "Rewrite everything with Span for performance." You will spend weeks optimising the 2% of time not spent waiting on I/O, and introduce buffer-lifetime bugs that no test catches.

What is the difference between a memory leak and memory pressure, and how do the symptoms differ? mid

A leak is unbounded retention: live data grows over time, gen 2 grows, collections get more frequent and more expensive, and the process eventually dies — the signature is a sawtooth that trends upward and never returns to baseline after load drops. Pressure is high allocation rate with normal retention: objects die young, so the heap size is stable but gen 0 collections are constant, % time in GC is high, and latency shows up as jitter rather than growth. They need opposite fixes — the leak needs a retention path, the pressure needs fewer or smaller allocations (pooling, avoiding LINQ in hot loops, streaming instead of buffering, ArrayPool). The distinguishing measurement is trivial and worth stating: watch gc-heap-size after load stops. Back to baseline means pressure; a new, higher plateau means a leak.

Example 
// Pressure, not a leak: allocates a new 1 MB buffer per request, dies immediately,
// but every one goes to the LOH and forces gen 2 work.
var buffer = new byte[1024 * 1024];

// Fixed:
using var stream = _streamManager.GetStream("upload");   // RecyclableMemoryStream, pooled

Follow-ups

  • Which counter tells you fastest? — alloc-rate plus time-in-gc for pressure; gen-2-gc-count and heap size trend for a leak.
  • Does allocation pressure cause pauses? — Yes, mostly short gen 0 pauses, but at high rates they add up and show as p99 jitter.
  • Is string.Concat in a loop a leak? — No, it is textbook pressure; the strings die immediately, they just cost the GC constant work.

Wrong answer: "High GC time means we are leaking." High GC time with a flat heap is the opposite diagnosis, and chasing a nonexistent leak wastes the incident.

What is IDisposable for if there is a GC, and what does the framework do with it? mid

The GC manages memory; IDisposable manages everything else — sockets, file handles, database connections, semaphores, unmanaged buffers — because the GC gives no guarantee about when it runs, and a finalizer is worse than useless as a primary mechanism (it promotes the object to the next generation, delays reclamation by at least one more collection, and runs on a single finalizer thread that can back up). In ASP.NET Core the container disposes what it created at scope end, using/await using covers the rest, and IAsyncDisposable exists because closing a network resource often requires I/O that should not block a thread. The senior nuance: implement a finalizer only when you directly own unmanaged memory, use SafeHandle instead wherever possible, and never let Dispose throw — a throwing Dispose inside a finally replaces the original exception and destroys the diagnosis.

Example 
public sealed class LeaseHolder : IAsyncDisposable
{
    private readonly IDistributedLock _lock;
    public async ValueTask DisposeAsync()
    {
        try { await _lock.ReleaseAsync(); }
        catch (Exception ex) { _log.LogWarning(ex, "lock release failed"); }  // never throw from Dispose
    }
}

Follow-ups

  • What happens if you forget to dispose an HttpResponseMessage? — The connection returns to the pool only when the content is read/disposed; leaks manifest as pool exhaustion, not memory growth.
  • Why is a finalizer costly? — Finalizable objects survive at least one extra GC and are queued to the finalizer thread; a slow finalizer stalls all of them.
  • What does the analyzer CA2000 catch? — Disposables that go out of scope undisposed; worth enabling as an error in library code.

Wrong answer: "Call GC.Collect() in Dispose to clean up." It forces a full collection, hurts throughput badly, and does nothing about the handle you failed to close.

A GC pause of 400 ms is showing in your p99. What are the options, in order? principal

First establish it really is GC: correlate time-in-gc and the pause durations from an EventPipe GC trace against the latency histogram; a 400 ms pause is almost always a blocking gen 2, so find why gen 2 is being collected — a large live set, LOH fragmentation forcing compaction, or induced collections from someone's GC.Collect(). Then work down the cost ladder. Cheapest: reduce the live set and the promotion rate, because gen 2 cost is proportional to surviving data — cap caches with size limits and expiry, stop buffering whole responses, pool large buffers off the LOH. Next: configuration — confirm background GC is on, evaluate DATAS on or off for this workload, consider GCConserveMemory or a heap hard limit, and on Arm64 take the .NET 10 write-barrier improvements for free. Then architecture: move the giant cache out of process (Redis) so its objects are not your gen 2 at all, or split a monolithic process into ones with smaller working sets. Only after that consider exotic options such as GCSettings.LatencyMode = SustainedLowLatency around a critical window, or, for a genuinely allocation-free service, Native AOT with a tightly bounded heap. State the trade-off explicitly: every option trades memory, throughput or complexity for pause time, and the right answer depends on which of those you have to spare.

Example 
# Attribute the pauses precisely
dotnet-trace collect -p 1 --providers Microsoft-Windows-DotNETRuntime:0x1:4 --duration 00:01:00
# PerfView: GCStats -> pause durations, gen, reason (AllocLarge, Induced, OutOfSpace)

Follow-ups

  • Why does a bigger cache make pauses worse? — Gen 2 cost scales with surviving objects; a cache is by definition surviving objects, and a million-entry dictionary is a million references to trace.
  • Does moving the cache to Redis always win? — No: you trade a GC pause for a network hop on every read. It wins when the cache is large and the hit path can tolerate ~1 ms.
  • Is Native AOT a GC fix? — Not directly — it still has a GC — but the smaller heap, no JIT and lower startup working set often shrink pauses as a side effect.

Wrong answer: "Switch to workstation GC to reduce pauses." Workstation GC has smaller heaps but no dedicated GC threads; on a multi-core server under load the gen 2 pause typically gets worse, not better.

What runtime knobs would you set for a memory-constrained container, and which would you refuse to set? principal

Set: an explicit heap budget (System.GC.HeapHardLimitPercent around 70–80% of the cgroup limit so native memory has headroom), DATAS left on (default since .NET 9) because that is precisely the scenario it was built for, System.GC.Concurrent on, InvariantGlobalization if you have audited culture usage, TieredCompilation and ReadyToRun for startup, and a thread-pool minimum that matches the CPU limit rather than the node's core count — a container limited to one CPU on a 64-core node still sees 64 in older runtimes' heuristics if the limit is not visible. Refuse: GC.Collect() on a timer, SetMinThreads at 500 as a permanent setting, GCHeapCount pinned by hand without a benchmark, and any knob copied from a blog post without a before/after measurement on your workload. The framing that lands at principal level: every one of these is a hypothesis, so they get rolled out like any other change — one canary, a fixed observation window, and a documented result — because GC settings interact and the only thing worse than an untuned service is a service tuned by five people who never wrote down why.

Example 
{
  "configProperties": {
    "System.GC.Server": true,
    "System.GC.Concurrent": true,
    "System.GC.DynamicAdaptationMode": 1,
    "System.GC.HeapHardLimitPercent": 75,
    "System.Globalization.Invariant": true,
    "System.Threading.ThreadPool.MinThreads": 4
  }
}

Follow-ups

  • Does the runtime see the cgroup CPU limit? — Yes, modern .NET reads cgroup v1/v2 CPU and memory limits and sizes heaps and the pool accordingly; verify with Environment.ProcessorCount inside the container.
  • What breaks with InvariantGlobalization? — Culture-aware comparisons, ToUpper on non-ASCII, time-zone/culture formatting; it is safe for many APIs and dangerous for anything user-facing.
  • How do you prove a knob helped? — Same traffic, one changed variable, compare p99 latency, RSS and time-in-gc over an hour — and revert if the result is inside the noise.

Wrong answer: "Set ServerGarbageCollection=false and SetMinThreads(1000) — it worked for us before." Copy-pasted tuning without measurement is exactly the anti-pattern the question is probing for.

07 Authentication & authorization

Two words that candidates conflate and interviewers separate deliberately: authentication establishes who the caller is and produces a ClaimsPrincipal; authorization decides what that principal may do. Almost every question here is really "do you understand the framework's model — schemes, handlers, policies, requirements — or have you only copy-pasted [Authorize]?" Mid: schemes, JWT validation, policies vs roles. Senior: multiple schemes, resource-based authorization, token lifetimes, data protection. Principal: authorization architecture across services, and the failure modes of doing it in the gateway versus the app.

docs: Authentication · Authorization

What is an authentication scheme, and what happens on [Authorize] when the caller has no token? mid

A scheme is a named handler registration — "Bearer", "Cookies", "OpenIdConnect" — implementing IAuthenticationHandler with four operations: authenticate (produce a principal from the request), challenge (tell an unauthenticated caller how to authenticate), forbid (the caller is known but not allowed), and sign-in/sign-out where applicable. UseAuthentication runs the default authenticate scheme and sets HttpContext.User; UseAuthorization then evaluates the endpoint's policies. With no token, authentication succeeds "with no principal", authorization fails, and the middleware issues a challenge on the default challenge scheme: 401 with a WWW-Authenticate header for JWT bearer, a 302 to the login path for cookies. If the caller is authenticated but the policy fails, you get a forbid instead: 403, or a redirect to an access-denied page. That distinction — 401 challenge versus 403 forbid — is the single most-tested detail in this area, and .NET 10 sharpened it: cookie authentication now returns 401/403 instead of redirecting for endpoints marked as API endpoints (IApiEndpointMetadata, applied automatically to [ApiController], JSON minimal APIs, TypedResults and SignalR).

Example 
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        o.Authority = "https://login.example.com/";     // discovery + JWKS, keys rotate automatically
        o.Audience  = "orders-api";
        o.TokenValidationParameters = new()
        {
            ValidateIssuer = true, ValidateAudience = true,
            ValidateLifetime = true, ClockSkew = TimeSpan.FromSeconds(30)   // default is 5 minutes
        };
    })
    .AddCookie("Cookies");

Follow-ups

  • Why is the default ClockSkew five minutes a problem? — A revoked or expired token stays acceptable for up to five extra minutes; tighten it when your clocks are synchronised.
  • Can one endpoint accept two schemes? — Yes: [Authorize(AuthenticationSchemes = "Bearer,Cookies")] or a policy with AddAuthenticationSchemes.
  • What sets HttpContext.User before the auth middleware runs? — Nothing; earlier middleware sees an unauthenticated principal, which is why logging enrichment with the user id has to sit after UseAuthentication.

Wrong answer: "No token means 403." 403 means "I know who you are and you still may not"; returning it for missing credentials breaks every client that would otherwise refresh a token.

Roles, claims or policies? mid

Roles are just claims of type ClaimTypes.Role with a legacy API attached ([Authorize(Roles = "Admin")], User.IsInRole), and they scale badly: permissions get encoded as role names, tokens grow, and "who can do X" becomes ungreppable. Policies are the modern model — a named policy is a set of requirements evaluated by handlers, so authorization logic lives in one place, is unit-testable, and can combine claims, roles, resource state and external data. The practical convention that reads as senior: put fine-grained permissions in the token (or fetch them once per request), define policies in terms of permissions, and keep roles as a coarse grouping in the identity provider rather than in your endpoint attributes. That also solves the token-bloat problem: 200 permissions do not belong in a JWT, a role plus a cached permission lookup does.

Example 
builder.Services.AddAuthorizationBuilder()
    .AddPolicy("orders:write", p => p.RequireAuthenticatedUser()
                                     .RequireClaim("permission", "orders.write"))
    .AddPolicy("same-tenant", p => p.AddRequirements(new SameTenantRequirement()))
    .SetFallbackPolicy(new AuthorizationPolicyBuilder()   // deny by default, everywhere
        .RequireAuthenticatedUser().Build());

app.MapPost("/orders", CreateOrder).RequireAuthorization("orders:write");

Follow-ups

  • Default policy vs fallback policy? — The default applies to endpoints with [Authorize] and no named policy; the fallback applies to endpoints with no authorization metadata at all — that is how you get deny-by-default.
  • How do you test a policy? — Resolve IAuthorizationService and evaluate it against a constructed ClaimsPrincipal; no HTTP needed.
  • Multiple handlers for one requirement? — All registered handlers run; the requirement succeeds if any handler calls Succeed and no handler calls Fail — an OR, which surprises people.

Wrong answer: "Roles are for users, claims are for machines." They are the same mechanism; the distinction that matters is coarse grouping versus fine-grained permission, and where each is evaluated.

How do you authorize "the user may edit this document" — data the token cannot know? senior

That is resource-based authorization: you cannot decide it in the middleware because the resource has to be loaded first. The framework's answer is to inject IAuthorizationService and call AuthorizeAsync(User, resource, policyOrRequirement) inside the handler after loading the entity, with an AuthorizationHandler<TRequirement, TResource> containing the rule. Two details separate a good answer. First, the response shape: return 404 rather than 403 when the existence of the resource is itself sensitive, otherwise you have built an enumeration oracle. Second, do not spread the rule across the codebase — if ownership is checked in three handlers, the fourth will forget; prefer a query-level filter (a repository that only ever returns rows the caller may see, EF global query filters for tenancy) so the default is safe and the explicit check is the exception.

Example 
public sealed class DocumentOwnerHandler : AuthorizationHandler<OperationAuthorizationRequirement, Document>
{
    protected override Task HandleRequirementAsync(AuthorizationHandlerContext ctx,
        OperationAuthorizationRequirement req, Document doc)
    {
        if (req.Name == "edit" && doc.OwnerId == ctx.User.FindFirstValue(ClaimTypes.NameIdentifier))
            ctx.Succeed(req);
        return Task.CompletedTask;
    }
}

app.MapPut("/docs/{id:guid}", async (Guid id, Doc body, IDocs docs, IAuthorizationService auth,
                                     ClaimsPrincipal user, CancellationToken ct) =>
{
    var doc = await docs.FindAsync(id, ct);
    if (doc is null) return Results.NotFound();
    var r = await auth.AuthorizeAsync(user, doc, Operations.Edit);
    return r.Succeeded ? Results.Ok(await docs.UpdateAsync(doc, body, ct)) : Results.NotFound();
});

Follow-ups

  • Why 404 instead of 403 here? — 403 confirms the id exists; for private resources that is an information leak. Pick one convention and document it.
  • How do you avoid the N+1 authorization check? — Push the predicate into the query (tenant filter, owner filter) rather than loading then checking per item.
  • Where do EF global query filters help and hurt? — They make tenancy safe by default; they hurt when you legitimately need cross-tenant admin queries and someone reaches for IgnoreQueryFilters() without review.

Wrong answer: "Put the document id in a claim." Claims are issued before the request; resource state cannot be known at token-issue time, and a token that grows per resource is unbounded.

Cookies or JWTs for a browser app? Where do you store the token? senior

For a first-party browser app, cookies: HttpOnly, Secure, SameSite=Lax (or Strict), signed and encrypted by the data-protection stack, with antiforgery tokens for state-changing requests. They cannot be read by JavaScript, so an XSS bug cannot exfiltrate the credential, and revocation is possible because the server holds the session. JWTs in localStorage are the pattern the industry moved away from: any XSS reads the token, they cannot be revoked before expiry, and refresh-token handling in the browser is where most implementations get subtly wrong. The current recommended shape for SPAs is the backend-for-frontend pattern — the BFF holds the tokens server-side, the browser gets only a cookie, and the BFF attaches the bearer token to downstream calls; ASP.NET Core supports this directly and .NET 8's Identity API endpoints plus AddBearerToken exist for the API-to-API case. Bearer tokens remain right for machine-to-machine and mobile, where there is no cookie jar and no CSRF surface.

Example 
builder.Services.AddAuthentication(CookieAuthenticationDefaults.AuthenticationScheme)
    .AddCookie(o =>
    {
        o.Cookie.HttpOnly = true;
        o.Cookie.SecurePolicy = CookieSecurePolicy.Always;
        o.Cookie.SameSite = SameSiteMode.Lax;
        o.SlidingExpiration = true;
        o.ExpireTimeSpan = TimeSpan.FromHours(8);
    });
builder.Services.AddAntiforgery(o => o.HeaderName = "X-CSRF-TOKEN");
app.UseAntiforgery();

Follow-ups

  • Why does SameSite matter? — It is the primary CSRF defence in modern browsers; antiforgery tokens are the belt to that pair of braces, and both are needed for older clients and cross-site flows.
  • How do you revoke a JWT? — You cannot, directly: keep lifetimes short (minutes), use refresh tokens with rotation and reuse detection, and maintain a revocation list only for high-value cases.
  • What breaks cookies across replicas? — Data-protection keys: without a shared, persisted key ring every pod encrypts with its own keys and users are logged out on every restart or rebalance.

Wrong answer: "Store the JWT in localStorage, it is stateless and scales." Stateless is a property of the token, not of where you store it; localStorage trades a revocable, XSS-resistant credential for one that is neither.

Explain the OIDC authorization code flow with PKCE, and what ASP.NET Core does for you. senior

The app redirects the browser to the identity provider's authorize endpoint with response_type=code, a state value, a nonce, and a PKCE code_challenge derived from a random verifier. The user authenticates there; the IdP redirects back to your callback with the code; the app then POSTs the code plus the original code_verifier to the token endpoint over a back channel and receives an ID token, an access token and optionally a refresh token. PKCE exists so that an intercepted code cannot be redeemed by anyone who lacks the verifier — originally for public clients, now recommended for all. The ID token is validated (signature via JWKS, issuer, audience, nonce, expiry) and turned into a ClaimsPrincipal, which is usually then persisted in a cookie so subsequent requests need no round trip. ASP.NET Core's AddOpenIdConnect handler does all of it — discovery document, JWKS caching and rotation, PKCE by default, state/nonce correlation cookies, token persistence with SaveTokens, and events (OnTokenValidated, OnRedirectToIdentityProvider) for the parts you need to customise.

Example 
builder.Services.AddAuthentication(o =>
{
    o.DefaultScheme = CookieAuthenticationDefaults.AuthenticationScheme;
    o.DefaultChallengeScheme = OpenIdConnectDefaults.AuthenticationScheme;
})
.AddCookie()
.AddOpenIdConnect(o =>
{
    o.Authority = "https://login.example.com/";
    o.ClientId = "web"; o.ClientSecret = cfg["Oidc:Secret"];
    o.ResponseType = "code";                       // PKCE is enabled by default
    o.SaveTokens = true;
    o.Scope.Add("orders.read"); o.Scope.Add("offline_access");
    o.GetClaimsFromUserInfoEndpoint = true;
    o.MapInboundClaims = false;                    // keep short JWT claim names (sub, not nameidentifier)
});

Follow-ups

  • Why is the implicit flow deprecated? — Tokens travel in the URL fragment (history, logs, referrers) and there is no client authentication; code+PKCE replaced it in OAuth 2.1.
  • ID token vs access token? — The ID token is about the user and is for your app; the access token is for the API and your app should treat it as opaque.
  • What is MapInboundClaims = false for? — It stops the legacy WS-Federation claim-type mapping that renames sub to a long XML URI and confuses everyone downstream.

Wrong answer: "The client validates the access token." Your API validates it; the client should not parse it at all, and apps that do break the moment the IdP changes its format.

What is the data protection stack and when does it bite you? senior

ASP.NET Core Data Protection is the built-in service for symmetric encryption of short-lived payloads with automatic key management: auth cookies, antiforgery tokens, TempData, password-reset tokens, and anything you protect yourself via IDataProtectionProvider. It maintains a key ring with rolling 90-day keys, so old payloads still decrypt after a rotation. It bites in exactly one scenario, and it is a scenario every multi-replica deployment hits: by default the key ring is stored per machine (or in the container's ephemeral filesystem) and is not shared, so pod A cannot decrypt pod B's cookie and users are randomly signed out, antiforgery validation fails intermittently, and the symptom looks like a load-balancer problem. The fix is to persist the ring to shared storage (blob, Redis, a database, a mounted volume) and protect it at rest with a key vault or certificate, and to set SetApplicationName to the same value across every instance and across blue/green slots.

Example 
builder.Services.AddDataProtection()
    .SetApplicationName("orders-web")                       // must match across all instances
    .PersistKeysToAzureBlobStorage(blobUri, credential)
    .ProtectKeysWithAzureKeyVault(keyUri, credential)
    .SetDefaultKeyLifetime(TimeSpan.FromDays(90));

// Purpose strings isolate payloads: a token protected for one purpose cannot be unprotected for another.
var protector = provider.CreateProtector("Orders.EmailConfirm.v1");

Follow-ups

  • What is a purpose string? — A domain separator; different purposes derive different keys from the same master key, so payloads cannot be swapped between features.
  • Is it a general-purpose crypto library? — No. It is for short-lived, self-owned payloads; it is explicitly not for storing data you must decrypt years later.
  • What breaks on a container restart without shared keys? — Every existing auth cookie and antiforgery token becomes undecryptable; users see logouts and 400s on form posts.

Wrong answer: "Just turn off cookie encryption / use a fixed machine key." A fixed key with no rotation is the ASP.NET Framework machineKey anti-pattern, and disabling protection makes the cookie forgeable.

How do you propagate identity across services — and should you? senior

Three models, and the interview is about naming their failure modes. Token passthrough forwards the caller's access token downstream: simple, preserves the end-user identity for audit and authorization, but every downstream service becomes a valid audience for that token and a compromised service can replay it anywhere. On-behalf-of exchange (OAuth token exchange) swaps the incoming token for a narrowly scoped one per hop: correct, auditable, and costs a round trip to the IdP per exchange unless cached. Service identity plus propagated user context sends the service's own client-credentials token and carries the user id in a signed header or trace baggage: fast and decoupled, but only safe inside a trust boundary where the network is authenticated (mTLS/mesh), because otherwise anyone can claim to be any user. For most systems the pragmatic answer is service identity inside the mesh with user context propagated, plus on-behalf-of at the boundaries where a downstream must enforce user-level authorization itself. Whatever you choose, HttpClient header propagation must be deliberate: forwarding Authorization blindly to a third-party host is a credential leak.

Example 
builder.Services.AddHeaderPropagation(o =>
{
    o.Headers.Add("x-correlation-id");
    o.Headers.Add("x-tenant-id");          // deliberately NOT Authorization
});
builder.Services.AddHttpClient<InventoryClient>(c => c.BaseAddress = new(cfg["Inventory:Url"]!))
    .AddHeaderPropagation()
    .AddHttpMessageHandler<ServiceTokenHandler>();   // client-credentials token, cached until expiry
app.UseHeaderPropagation();

Follow-ups

  • How do you cache a client-credentials token safely? — Per audience and scope, refreshed at ~75% of lifetime, with a single-flight lock so a burst does not stampede the IdP.
  • What audits well? — Both identities in the log: acting service and effective user. Auditing only the service makes forensics impossible.
  • Where does a service mesh fit? — mTLS gives you authenticated service identity for free, which is what makes propagated user context safe.

Wrong answer: "Forward the Authorization header everywhere, it is simplest." It gives every service — including a compromised one — a token valid at every other service; blast radius becomes the whole system.

Passkeys landed in ASP.NET Core Identity in .NET 10. What changes, and would you adopt them? senior

.NET 10 added Web Authentication API (WebAuthn/FIDO2) support to ASP.NET Core Identity, with passkey registration and login built into the Blazor Web App template UI — so the framework now ships the server side of the ceremony (challenge generation, attestation and assertion verification, credential storage) instead of requiring a third-party library like Fido2.NET. What changes practically is that the password stops being the primary factor: a passkey is a device-bound or synced key pair, phishing-resistant because the assertion is bound to the origin, and it removes credential-stuffing and password-reuse risk entirely. Adoption judgment: yes as an additional factor and an opt-in primary for new users, but plan the recovery path first — account recovery becomes the weakest link, and a passkey-only account with an email-based reset is only as strong as the mailbox. Keep a second passkey or a strong fallback registered, decide your position on synced (cloud-backed) versus device-bound credentials, and keep the password path alive for the tail of users on old devices while you measure adoption.

Example 
// .NET 10 Identity: passkey support is part of the Identity UI/templates.
builder.Services.AddIdentityCore<AppUser>()
    .AddEntityFrameworkStores<AppDbContext>()
    .AddApiEndpoints();
// Registration and assertion endpoints are provided by the Identity endpoints/UI;
// the credential (public key, sign count, transports) is stored per user.

Follow-ups

  • Why is WebAuthn phishing-resistant? — The assertion is bound to the relying-party origin by the browser, so a lookalike domain cannot obtain a usable signature.
  • What is the migration path? — Offer enrolment after login, measure, then make it the default for new accounts; never force it before recovery is solved.
  • What did teams use before? — Fido2.NET or an IdP-hosted implementation (Entra ID, Auth0); the framework support removes the need to hand-roll ceremony validation.

Wrong answer: "Passkeys are just a fancier password stored in the browser." The private key never leaves the authenticator and never reaches your server, which is the entire security property.

Where should authorization live in a system with a gateway, a mesh and 40 services? principal

Split it by what each layer can actually know. The gateway does coarse, cheap enforcement it can do without domain knowledge: authentication (validate the token, reject garbage before it costs you anything), rate limiting, and route-level scope checks. The service does fine-grained authorization, because only it knows the resource, the tenant and the business rule — and it must not trust the gateway to have done it, or a misrouted internal call bypasses everything. The mesh gives you authenticated service identity (mTLS) so services can trust the caller without trusting the payload. The part candidates miss is the policy lifecycle: with 40 services you need one vocabulary of permissions, one place to change a rule, and a way to answer "who can do X" — which pushes you toward externalised policy (OPA/Cedar-style, or a shared policy package evaluated locally with a cached decision) rather than 40 hand-written handler implementations that drift. Whatever the mechanism, keep the decision enforcement in the service and make the decision logic shared and testable, log every deny with the reason, and treat deny-by-default (SetFallbackPolicy) as non-negotiable so a new endpoint is closed until someone opens it.

Example 
// One vocabulary, evaluated locally, decisions cached; the service still enforces.
public sealed class PermissionHandler(IPolicyEngine engine, IMemoryCache cache)
    : AuthorizationHandler<PermissionRequirement>
{
    protected override async Task HandleRequirementAsync(AuthorizationHandlerContext ctx, PermissionRequirement req)
    {
        var key = (ctx.User.FindFirstValue("sub"), req.Permission);
        var allowed = await cache.GetOrCreateAsync(key, e =>
        {
            e.AbsoluteExpirationRelativeToNow = TimeSpan.FromSeconds(30);
            return engine.EvaluateAsync(ctx.User, req.Permission);
        });
        if (allowed) ctx.Succeed(req);
    }
}

Follow-ups

  • What is the risk of caching decisions? — Revocation latency. Bound it (seconds), and provide an explicit invalidation path for high-risk permissions.
  • Centralised policy service or local evaluation? — Local evaluation of a distributed policy bundle: a central decision service is a new single point of failure on every request.
  • How do you prove it works? — Authorization tests as first-class citizens: a matrix of principal × endpoint asserted in CI, plus a periodic scan for endpoints with no policy.

Wrong answer: "The gateway handles authorization so services can trust the request." Any internal caller, misconfiguration or SSRF then has full access; defence in depth means the service checks too.

08 HttpClient, resilience & outbound calls

Every service calls other services, and the two canonical .NET mistakes here — new HttpClient() per request and no timeout — are so common that interviewers use them as a filter. The modern answer is IHttpClientFactory plus Microsoft.Extensions.Http.Resilience, and the senior part is knowing what each policy does to a struggling dependency. Mid: factory, typed clients, socket exhaustion. Senior: handler lifetime, DNS, timeouts, retries, circuit breakers, idempotency. Principal: the resilience strategy for a whole estate, and when retrying makes an outage worse.

docs: IHttpClientFactory · HTTP resilience

Why not new HttpClient() per request — and why is a static one also wrong? screener

A new client per request creates a new SocketsHttpHandler and therefore a new connection pool; because a closed TCP socket sits in TIME_WAIT for a couple of minutes, a busy service exhausts ephemeral ports and starts failing with SocketException — the symptom is sudden connection failures under load with a healthy remote. The naive fix, one static HttpClient forever, solves that and introduces a subtler bug: the handler caches DNS resolution for the life of the connection pool, so when the remote service fails over to a new IP your client keeps dialling the old one until something forces a reconnect. IHttpClientFactory resolves both: it pools handlers and rotates them on HandlerLifetime (default 2 minutes), so DNS is picked up again while connections are still reused. If you genuinely need a long-lived static client, set PooledConnectionLifetime on the handler instead, which achieves the same rotation at the connection level.

Example 
builder.Services.AddHttpClient<InventoryClient>(c =>
{
    c.BaseAddress = new Uri(cfg["Inventory:Url"]!);
    c.Timeout = TimeSpan.FromSeconds(10);          // whole-request ceiling
})
.SetHandlerLifetime(TimeSpan.FromMinutes(2))
.ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
{
    PooledConnectionLifetime  = TimeSpan.FromMinutes(2),
    PooledConnectionIdleTimeout = TimeSpan.FromSeconds(30),
    MaxConnectionsPerServer = 64,
    ConnectTimeout = TimeSpan.FromSeconds(2)
});

Follow-ups

  • What does HandlerLifetime not do? — It does not kill in-flight requests; the expired handler is kept alive until its outstanding requests finish, then disposed.
  • Is disposing an HttpClient from the factory harmful? — No; the client is a thin wrapper and the factory owns the handler.
  • How do you see the pool's behaviour? — The System.Net.Http event counters: requests started/failed, connections established, and request queue duration.

Wrong answer: "Use one static HttpClient — the docs say so." That was the 2016 advice; without PooledConnectionLifetime it produces the stale-DNS failure that only shows up during a failover, which is the worst possible time.

Named, typed or basic clients — and where do delegating handlers fit? mid

AddHttpClient() with no name gives you IHttpClientFactory.CreateClient() for ad-hoc use; a named client (AddHttpClient("github", …)) attaches configuration to a string key; a typed client (AddHttpClient<GitHubClient>(…)) registers your own class as transient with a configured HttpClient injected, which is the preferred shape because the configuration and the usage live together and the class is a normal injectable dependency. Delegating handlers are the middleware of the outbound pipeline: they wrap the primary handler in registration order (first registered is outermost), so authentication token attachment, logging, retry policies and header propagation are all composed there. The lifetime trap worth naming: a typed client is transient but the handler chain is pooled, so a delegating handler must not capture scoped state — inject IHttpContextAccessor or a scope factory instead of the scoped service itself.

Example 
public sealed class BearerTokenHandler(ITokenCache tokens) : DelegatingHandler
{
    protected override async Task<HttpResponseMessage> SendAsync(HttpRequestMessage req, CancellationToken ct)
    {
        req.Headers.Authorization = new("Bearer", await tokens.GetAsync("inventory", ct));
        return await base.SendAsync(req, ct);
    }
}

builder.Services.AddTransient<BearerTokenHandler>();
builder.Services.AddHttpClient<InventoryClient>()
    .AddHttpMessageHandler<BearerTokenHandler>()      // outermost
    .AddStandardResilienceHandler();                  // retry/CB/timeout, innermost of the two

Follow-ups

  • In what order do handlers run? — Outermost is the first added; the resilience handler should generally sit close to the primary handler so retries re-run the inner work but not token acquisition.
  • How do you configure defaults for every client? — services.ConfigureHttpClientDefaults(b => b.AddStandardResilienceHandler()) (.NET 8+), so a new client is resilient by default.
  • Can a handler see the response body? — Yes, but reading it consumes the stream; buffer deliberately or you break streaming responses.

Wrong answer: "Typed clients are singletons, so cache state in them." They are transient by default; the handler chain is what is pooled, and assuming otherwise produces per-request state that silently resets.

Design the resilience pipeline for a call to a flaky dependency. senior

The standard resilience handler (Polly v8 under Microsoft.Extensions.Http.Resilience) composes five strategies in a deliberate order: an overall request timeout, a rate/bulkhead limiter, total retries, a circuit breaker, and a per-attempt timeout innermost. That order matters — the per-attempt timeout must be inside the retry so a hung attempt is abandoned and retried, and the total timeout must be outside everything so retries cannot exceed your latency budget. Retries need jittered exponential backoff (a fixed delay synchronises every client into a thundering herd) and must be restricted to idempotent operations or paired with an idempotency key. The circuit breaker exists to stop feeding a dependency that is already failing: after a failure ratio over a sampling window it opens, fails fast for a break duration, then half-opens to probe. And every one of these needs to be visible: emit attempts, breaker state changes and rejections as metrics, because a silently retrying client looks healthy right up until it triples the load on a struggling service.

Example 
builder.Services.AddHttpClient<PricingClient>()
  .AddResilienceHandler("pricing", b =>
  {
      b.AddTimeout(TimeSpan.FromSeconds(5));                       // total
      b.AddRetry(new HttpRetryStrategyOptions
      {
          MaxRetryAttempts = 3,
          BackoffType = DelayBackoffType.Exponential,
          UseJitter = true,
          Delay = TimeSpan.FromMilliseconds(200)
      });
      b.AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions
      {
          FailureRatio = 0.5, MinimumThroughput = 20,
          SamplingDuration = TimeSpan.FromSeconds(30),
          BreakDuration = TimeSpan.FromSeconds(15)
      });
      b.AddTimeout(TimeSpan.FromSeconds(1.5));                     // per attempt
  });

Follow-ups

  • Why jitter? — Without it, every client retries at the same instant after an outage and the dependency is knocked over by the recovery attempt.
  • What should never be retried? — Non-idempotent writes without an idempotency key, and 4xx responses other than 408/429 — retrying a 400 just wastes budget.
  • Circuit breaker per what? — Per endpoint or per host; one global breaker means a single bad route trips calls to healthy ones.

Wrong answer: "Retry three times on any exception." That retries validation failures, retries writes, and turns a partial outage into a self-inflicted DDoS.

How do you make a retried POST safe? senior

With an idempotency key supplied by the client and enforced by the server: the caller generates a key per logical operation (not per attempt), sends it in a header, and the server stores the key with the result of the first successful execution so a repeat returns the same response instead of doing the work twice. Storage has to be transactional with the effect — writing the key and the order in one transaction — otherwise a crash between them recreates the double-charge you were preventing. Give keys a TTL matching your retry window (24 hours is common), handle the in-flight case explicitly (a second request arriving while the first is still running should get 409 or wait, not execute), and remember that HttpClient retries are not the only source of duplicates: users double-click, gateways retry, and queues deliver at least once. The alternative shape, worth naming, is to make the operation naturally idempotent — PUT to a client-generated id — which removes the need for a key at all.

Example 
app.MapPost("/payments", async (PaymentRequest req, [FromHeader(Name = "Idempotency-Key")] string key,
                                AppDbContext db, CancellationToken ct) =>
{
    if (await db.Idempotency.FindAsync([key], ct) is { } prior)
        return Results.Json(prior.ResponseBody, statusCode: prior.StatusCode);

    await using var tx = await db.Database.BeginTransactionAsync(ct);
    var payment = await ChargeAsync(req, ct);
    db.Idempotency.Add(new(key, StatusCodes.Status201Created, payment));   // same transaction
    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
    return Results.Created($"/payments/{payment.Id}", payment);
});

Follow-ups

  • Who generates the key? — The client, once per logical operation; if the server generates it, a retry gets a new key and the protection is gone.
  • What about concurrent duplicates? — A unique constraint on the key plus catching the violation is the simplest correct implementation.
  • Does this replace exactly-once delivery? — It is how you achieve effectively-once: at-least-once delivery plus idempotent handling.

Wrong answer: "We only retry on timeouts, and a timeout means it did not happen." A timeout is the one case where you have no idea whether it happened; that is precisely when idempotency matters.

How do timeouts compose across a call chain, and what is a latency budget? senior

Timeouts must shrink as you go deeper, or the outer caller gives up while inner work continues — burning capacity on results nobody will read. A latency budget makes this explicit: the client-facing SLO (say 1 second p99) is divided among the hops, each service passes its remaining budget downstream (a deadline header, or gRPC's built-in deadline propagation), and each hop's timeout is its share minus what has already elapsed. The pathology to name is the inverted chain: an outer timeout of 2 seconds wrapping an inner client with a 30-second default, so the outer request fails fast while the inner call keeps a connection and a database query alive; multiply by request rate and the dependency saturates with abandoned work. HttpClient.Timeout is a whole-request ceiling (it does not distinguish connect, first byte and body), so use ConnectTimeout on the handler and a per-attempt resilience timeout for finer control, and always pass HttpContext.RequestAborted so a disconnected client cancels the chain.

Example 
// .NET 8+ request timeouts middleware: an inbound budget the handler can observe.
builder.Services.AddRequestTimeouts(o =>
    o.AddPolicy("fast", new RequestTimeoutPolicy { Timeout = TimeSpan.FromMilliseconds(800),
                                                  TimeoutStatusCode = StatusCodes.Status504GatewayTimeout }));
app.UseRequestTimeouts();
app.MapGet("/quote", Quote).WithRequestTimeout("fast");

Follow-ups

  • How do you propagate a deadline over HTTP? — A convention header carrying remaining milliseconds, read by middleware into a linked CancellationTokenSource; gRPC does this natively.
  • What is the default HttpClient timeout? — 100 seconds, which in a web service is effectively "no timeout"; overriding it is not optional.
  • Where do you put the retry budget? — Inside the total timeout: three retries at 1.5 s each cannot fit in a 2 s budget, and doing that arithmetic out loud is the point of the question.

Wrong answer: "Set a generous timeout everywhere so we do not fail unnecessarily." Generous timeouts convert a fast failure into held resources, which is how one slow dependency takes down an unrelated service.

What is HTTP/2 and HTTP/3 doing for outbound calls, and when do they hurt? senior

HTTP/2 multiplexes many concurrent requests over a single TCP connection, so you stop paying per-request connection setup and stop being limited by MaxConnectionsPerServer — excellent for chatty service-to-service traffic and required for gRPC. Its weakness is head-of-line blocking at the TCP layer: one lost packet stalls every stream on that connection, and a single connection can also pin all your traffic to one backend instance behind an L4 load balancer, defeating load spreading. HTTP/3 (QUIC over UDP) removes the TCP head-of-line problem and survives network changes, and .NET supports it on both Kestrel and HttpClient; the caveats are UDP being blocked or deprioritised on some corporate networks and less mature middlebox support. In .NET you opt in per request or per client with DefaultRequestVersion plus VersionPolicy, and you set EnableMultipleHttp2Connections = true when you want the pool to open more than one HTTP/2 connection rather than queueing behind the stream limit.

Example 
builder.Services.AddHttpClient<GrpcLikeClient>(c =>
{
    c.DefaultRequestVersion = HttpVersion.Version20;
    c.DefaultVersionPolicy  = HttpVersionPolicy.RequestVersionOrLower;  // graceful downgrade
})
.ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
{
    EnableMultipleHttp2Connections = true      // avoid queueing behind MAX_CONCURRENT_STREAMS
});

Follow-ups

  • Why does one connection hurt load balancing? — An L4 balancer routes connections, not requests; long-lived HTTP/2 connections stick to one backend until they are recycled.
  • What does RequestVersionExact do? — Fails rather than downgrading; useful to prove a path really is HTTP/3, dangerous as a default.
  • What changed recently? — .NET 11 previews add Zstandard compression support in ASP.NET Core and further HTTP/3 work; on .NET 10 you already get HTTP/3 on Kestrel and HttpClient where the platform supports QUIC.

Wrong answer: "HTTP/2 is always faster." For a single large download it is not, and for a fleet behind an L4 balancer it can concentrate traffic on one instance.

Every service in the estate retries. How do you keep that from causing a retry storm? principal

Retries compose multiplicatively: three hops with three attempts each is up to 27 requests for one user action, so the first thing to establish is a rule that only one layer retries — typically the one closest to the failure, with everything above it failing fast. Then bound retries as a budget rather than a count: a retry budget (say, retries may not exceed 10% of successful requests over a window) caps the amplification no matter how many clients are misbehaving, and it is what the mature libraries and meshes implement. Add circuit breakers so a dependency that is already down is not fed at all, jitter so recovery is staggered, and load shedding at the server so it can reject cheaply — a server that cannot say no fast is a server that dies slowly. Then make it visible: retries and breaker state as metrics with a client dimension, so during an incident you can see which caller is amplifying. The organisational half at principal level is that this belongs in the shared platform package or the mesh, not in 40 teams' judgment, because retry policy is a property of the system, not of any one service.

Example 
// One place, one policy, applied to every client in the estate.
services.ConfigureHttpClientDefaults(b => b.AddStandardResilienceHandler(o =>
{
    o.Retry.MaxRetryAttempts = 2;                  // only the edge-most caller retries
    o.Retry.UseJitter = true;
    o.CircuitBreaker.FailureRatio = 0.3;
    o.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(3);
}));

Follow-ups

  • How do you signal "do not retry" downstream? — A response header or an error code the client library understands; 429 with Retry-After is the standard, and clients must honour it.
  • What does load shedding look like in ASP.NET Core? — The rate limiter with a concurrency limiter and a small queue, plus a cheap 503 path that skips auth and serialization.
  • How do you test this? — Fault injection in a load test: make a dependency slow, not down, because slow is what actually causes the storm.

Wrong answer: "Increase timeouts and retries so users do not see errors." That maximises amplification and holds resources; the user sees a slow error instead of a fast one, and the dependency never recovers.

How do you handle unhandled exceptions properly? mid

UseExceptionHandler as the outermost middleware, plus one or more IExceptionHandler implementations (.NET 8+) registered with AddExceptionHandler: each gets a chance to handle the exception in registration order and returns true when it did, falling through to the default ProblemDetails response otherwise. That replaces the older pattern of a hand-written try/catch middleware and gives you typed, testable handlers per exception family — domain validation to 400, not-found to 404, concurrency to 409, everything else to a 500 with no detail. The developer exception page stays for Development only, because it renders the stack trace, the query string and the loaded assemblies. Two .NET 10 behaviours to know: exceptions handled by an IExceptionHandler are no longer logged by default (control it with ExceptionHandlerOptions.SuppressDiagnosticsCallback), and if the response has already started, the handler cannot do anything but abort.

Example 
public sealed class DomainExceptionHandler(IProblemDetailsService problems) : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(HttpContext ctx, Exception ex, CancellationToken ct)
    {
        if (ex is not DomainException d) return false;
        ctx.Response.StatusCode = StatusCodes.Status422UnprocessableEntity;
        return await problems.TryWriteAsync(new()
        {
            HttpContext = ctx,
            ProblemDetails = new() { Title = "Domain rule violated", Detail = d.Message,
                                     Type = $"https://errors.example.com/{d.Code}" }
        });
    }
}

What is ProblemDetails and why standardise on it? mid

ProblemDetails is the IETF standard error body (RFC 7807, updated by RFC 9457) served as application/problem+json: type (a URI identifying the error class), title, status, detail, instance, plus arbitrary extension members. Standardising matters because clients then write one error handler instead of one per endpoint, and because type gives you a stable, documentable identifier that survives message rewording — the field a client should branch on, unlike a human-readable message. ASP.NET Core produces it automatically for [ApiController] actions and, once you call AddProblemDetails(), for status-code responses and unhandled exceptions in minimal APIs too. The extension you almost always want is a correlation/trace id, so a user can quote one string and support can find the request.

Wrong answer: "We return { success: false, message: '...' }, it is simpler." It is simpler for the first endpoint and worse for every client, and it throws away the status-code semantics HTTP already gives you.

How does validation work in minimal APIs in .NET 10? senior

Until .NET 9 minimal APIs had no built-in validation: you validated by hand, with an endpoint filter, or with FluentValidation. .NET 10 added it — builder.Services.AddValidation() turns on a source-generated validator (so it is AOT- and trimming-friendly and does not use reflection at runtime) that validates parameters annotated with data annotations, including nested objects and collections, and returns a ValidationProblemDetails 400 through IProblemDetailsService. Root model types need the [ValidatableType] attribute for the generator to emit a validator, types from other assemblies need an AddValidation call in that assembly, [SkipValidation] opts a member out, and DisableValidation() opts a single endpoint out. The APIs moved into Microsoft.Extensions.Validation so the same machinery works outside HTTP. It is worth naming the alternative: FluentValidation remains popular for complex, conditional, cross-field rules and for keeping validation out of the DTO, and mixing both is normal — annotations for shape, FluentValidation or the domain for meaning.

  • Where does validation belong: DTO or domain? — Shape and format at the edge, invariants in the domain. A rule that must always hold cannot live in a DTO attribute.
  • What did controllers already have? — [ApiController] validated ModelState and returned 400 automatically; minimal APIs are only now catching up.

Client sends {"quantity": "5"} for an int. What happens, and how do you control it? mid

When would you write a custom model binder or a custom TryParse? senior

When a parameter's wire format is not a plain value the framework already understands: a comma-separated filter expression, a base64 cursor for pagination, a domain identifier with a prefix (ord_7fa3…), a date range in one query parameter, or a value that must come from several sources at once. In minimal APIs the lightweight hooks are a static TryParse on the type (single string value) or BindAsync (full control over the HttpContext); in MVC it is IModelBinder plus an IModelBinderProvider. The reason to prefer this over parsing inside the handler is that it moves the failure to the binding layer, where it becomes a consistent 400 with a field name rather than an ad-hoc exception, and it makes the type appear correctly in OpenAPI. The counter-argument a senior should raise: custom binders are invisible magic — a reviewer reading the handler cannot see where the value came from — so keep them few, name them after the domain type, and unit-test them directly.

What is the difference between 400, 409, 422 and 500 — and when do you use each? senior

400 is a malformed request: the server could not parse or bind it — bad JSON, wrong type, missing required field. 422 is a well-formed request that violates a semantic rule: the JSON parsed, the types are right, but the business says no (insufficient funds, sku not orderable). 409 is a state conflict: the request was valid when written but the resource has moved on — an optimistic-concurrency mismatch, a duplicate creation, a version clash. 500 is your fault, always: an unhandled exception, a dependency you failed to handle, a bug. The reason interviewers like this question is that it is really about client behaviour: a client should not retry 400 or 422 (retrying will fail identically), should retry 409 after re-reading state, and may retry 500 with backoff. Two adjacent codes worth naming: 404 when the resource does not exist or when existence itself is sensitive, and 429 with Retry-After for rate limiting.

Example

{
    await db.SaveChangesAsync(ct);
    return Results.NoContent();
}
catch (DbUpdateConcurrencyException)
{
    return Results.Problem(statusCode: StatusCodes.Status409Conflict,
        title: "The record changed since you read it", type: "https://errors.example.com/concurrency");
}

Follow-ups

  • Is 422 controversial? — Slightly: some teams use 400 for everything and distinguish by type. Either is defensible; inconsistency is not.
  • What does a 500 look like to the client? — A ProblemDetails with a trace id and nothing else; the details belong in your logs.
  • Do 4xx count against your error budget? — Client errors usually do not; but a spike in 400s often means you shipped a breaking change, so alert on the ratio anyway.

Wrong answer: "Return 200 with an error object so the client always gets a body." It breaks caching, monitoring, retry logic and every HTTP tool ever written.

Design the error contract for a platform used by 30 internal teams and external partners. principal

Start from what consumers must be able to do programmatically: distinguish retryable from terminal, map an error to a support action, and localise a message. Distinguish internal from external deliberately: partners get sanitised details and no internal identifiers, internal callers may get more. Finally close the loop on operations — every error response carries the trace id, every log line carries it too, and support tooling can go from a customer-quoted id to the trace in one hop; that is what makes the contract worth the effort rather than a document nobody reads.

10 Caching & request-path performance

Caching is where framework knowledge meets distributed-systems judgment, so it appears in both the coding round and the design round. The framework question is which of five caching abstractions to use; the interesting question is always invalidation, stampede and staleness. Mid: IMemoryCache vs IDistributedCache, response vs output caching. Senior: HybridCache, stampede protection, cache keys and tenancy, ETags. Principal: cache topology and the failure modes of a cache that becomes load-bearing.

Name the caching options in ASP.NET Core and when each applies. mid

Five, and they solve different problems. IMemoryCache: in-process, fastest, per-replica, lost on restart — good for small hot data and computed values. IDistributedCache: out-of-process (Redis, SQL Server, or the in-memory implementation for tests), shared across replicas, serialised, ~1 ms — good for session-scale data and anything that must be consistent across pods. HybridCache (.NET 9): the combination — an L1 in-process cache in front of an L2 distributed cache, with stampede protection and tag-based invalidation built in, which is what most people were hand-rolling badly. Response caching: HTTP-level, honours Cache-Control, mostly relevant for enabling downstream/proxy caching. Output caching (.NET 7): server-side caching of the whole response independent of client headers, with named policies, tag-based eviction and a pluggable store — the right choice for expensive anonymous GETs. Choosing well is mostly about the invalidation story: if you cannot describe how an entry becomes wrong and how you evict it, you have picked the wrong layer.

Example 
builder.Services.AddOutputCache(o =>
{
    o.AddBasePolicy(b => b.Expire(TimeSpan.FromSeconds(10)));
    o.AddPolicy("catalog", b => b.Expire(TimeSpan.FromMinutes(5))
                                 .SetVaryByQuery("page", "size").Tag("catalog"));
});
app.UseOutputCache();
app.MapGet("/catalog", GetCatalog).CacheOutput("catalog");

// invalidate on write
await outputCacheStore.EvictByTagAsync("catalog", ct);

Follow-ups

  • Response caching vs output caching? — Response caching obeys the client's Cache-Control (and so is easily bypassed); output caching is server-controlled and caches even for authenticated-looking requests if you tell it to.
  • Does output caching work for authenticated requests? — By default it does not cache when there is an Authorization header or cookies; overriding that requires varying by user, which usually defeats the point.
  • What is the distributed output cache story? — IOutputCacheStore is pluggable (Redis implementations exist), which is what makes tag eviction work across replicas.

Wrong answer: "They are all basically the same, use IMemoryCache." Per-replica caching with no shared invalidation is how you get users seeing different data depending on which pod answered.

What is a cache stampede and how does HybridCache prevent it? senior

A stampede (dogpile) is what happens when a popular key expires: every concurrent request misses, and all of them run the expensive factory at once, hammering the database exactly when the cache stopped protecting it. The classic hand-rolled fix is a per-key SemaphoreSlim or Lazy<Task<T>> so only one caller computes and the rest await the same task — easy to get subtly wrong (leaking semaphores, caching a faulted task forever). HybridCache (GA with .NET 9, shipped as Microsoft.Extensions.Caching.Hybrid) builds this in: GetOrCreateAsync deduplicates concurrent callers for the same key in-process, coordinates L1 and L2, serialises with a pluggable serializer, and supports tag-based invalidation. Complementary mitigations worth naming: jitter the expiry so a million keys do not expire in the same second, and use a soft/hard TTL (serve slightly stale while one caller refreshes in the background) when staleness is cheaper than a latency spike.

Example 
builder.Services.AddHybridCache(o => o.DefaultEntryOptions = new()
{
    Expiration      = TimeSpan.FromMinutes(5),      // L2
    LocalCacheExpiration = TimeSpan.FromSeconds(30) // L1
});

public sealed class Catalog(HybridCache cache, ICatalogDb db)
{
    public ValueTask<Product> GetAsync(string sku, CancellationToken ct) =>
        cache.GetOrCreateAsync($"product:{sku}", sku,
            (s, t) => db.LoadAsync(s, t),
            tags: ["catalog", $"sku:{sku}"], cancellationToken: ct);
}
await cache.RemoveByTagAsync("catalog", ct);

Follow-ups

  • Does deduplication work across replicas? — No: it is per process, so ten pods can still produce ten factory calls. That is usually acceptable; if it is not, you need a distributed lock.
  • What happens if the factory throws? — The failure is not cached and the waiters see the exception; guard the factory yourself if you want negative caching.
  • Why did teams hand-roll this? — Because before .NET 9 there was nothing between IMemoryCache and IDistributedCache; that code is exactly what you should now delete.

Wrong answer: "Set a longer TTL so it expires less often." The stampede is just rarer and bigger, and the data is staler in between.

How do you design a cache key, and what goes wrong? senior

A key must include every input that changes the value — and in a multi-tenant system that starts with the tenant. The failure mode is not subtle: omit the tenant and you serve tenant A's data to tenant B, which is a data breach discovered by a customer. So: namespace by domain (catalog:), include a schema/serializer version so a deployment that changes the DTO does not deserialize old entries into the wrong shape, include the tenant and any authorization-relevant dimension, and normalise case and ordering so ?b=1&a=2 and ?a=2&b=1 do not become two entries. Watch cardinality: a key that includes a user id turns a shared cache into a per-user cache with a near-zero hit rate and a large memory bill. And for HTTP-level caching the same discipline is Vary — cache a response that varies by Accept-Language without Vary: Accept-Language and the CDN will happily serve French to everyone.

Example 
static string Key(string tenant, string sku) => $"v3:catalog:{tenant}:{sku}";
// v3      – bump when the cached shape changes, so old entries are ignored, not misread
// tenant  – the isolation dimension; never optional
// sku     – the identity

Follow-ups

  • How do you invalidate across replicas? — Tags plus a shared store, or a pub/sub message on write that evicts the local L1 in every pod.
  • What is the risk of a version prefix? — A deployment invalidates everything at once — a cold-cache stampede at exactly the moment you are rolling out. Warm or stagger it.
  • Absolute or sliding expiration? — Absolute bounds staleness; sliding keeps hot items alive but can keep a stale item alive forever. Most designs want absolute plus a size limit.

Wrong answer: "The key is just the entity id." That is the tenancy leak, and it is one of the few interview answers that is genuinely disqualifying.

The cache is down. What happens to your service? senior

The honest answer depends on whether the cache is an optimisation or a dependency, and most teams discover which one it is during the outage. If it is an optimisation, a cache failure should degrade to the origin: catch the exception, emit a metric, serve from the database — but only if the database can take the full load, which for a 95% hit rate means 20× traffic, so you also need a concurrency limiter in front of it and probably load shedding. If it is a dependency (rate-limit counters, session state, distributed locks), the service should fail fast and loudly rather than silently behaving as if every check passed — a rate limiter that fails open under a cache outage is an availability incident waiting to become a cost incident. Practical hardening: short connect and operation timeouts on the Redis client (a hung cache call is worse than a miss), a circuit breaker so you stop trying, an in-process L1 that keeps serving hot keys (HybridCache gives you this for free), and a game-day where you actually turn the cache off in staging and watch what breaks.

Example 
public async ValueTask<Product?> GetAsync(string sku, CancellationToken ct)
{
    try { return await _cache.GetOrCreateAsync(Key(sku), sku, Load, cancellationToken: ct); }
    catch (Exception ex)
    {
        _cacheFailures.Add(1);                       // metric first
        _log.LogWarning(ex, "cache unavailable, falling back to origin");
        return await _limiter.RunAsync(() => Load(sku, ct));   // bounded fallback
    }
}

Follow-ups

  • Fail open or fail closed? — Fail open for read caches, fail closed for anything security- or quota-relevant. Decide per use, and write it down.
  • How do you recover from a cold cache? — Staggered warm-up, request coalescing, and admission control; a cold start under full traffic is a stampede by definition.
  • What is the right Redis timeout? — Tens of milliseconds. If the cache is slower than the database, it is not a cache.

Wrong answer: "Redis is highly available so it will not go down." Failover, network partitions and noisy neighbours all look like "down" for tens of seconds, and that is enough.

ETags and conditional requests — what do they buy and how do you implement them? senior

An ETag is a version identifier for a representation. On a GET, returning ETag lets the client send If-None-Match next time and receive a 304 with no body — saving bandwidth and serialization, though not the work of determining the version. On a PUT/PATCH it is the HTTP-native form of optimistic concurrency: the client sends If-Match, and the server returns 412 if the resource changed underneath, which is how you avoid lost updates without inventing your own version field in the payload. Implementation matters: derive the tag from something that already changes with the data — a row version / xmin, an updated-at timestamp plus id, or a hash of the serialized body (cheapest to write, most expensive to compute since you must serialize anyway) — and use a weak tag (W/"…") when byte-for-byte equality is not guaranteed across servers. The design payoff is that this pushes concurrency control to the protocol, so every client and proxy understands it.

Example 
app.MapGet("/docs/{id}", async (Guid id, HttpContext ctx, IDocs docs, CancellationToken ct) =>
{
    var doc = await docs.FindAsync(id, ct);
    if (doc is null) return Results.NotFound();

    var etag = new EntityTagHeaderValue($"\"{Convert.ToBase64String(doc.RowVersion)}\"");
    if (ctx.Request.Headers.IfNoneMatch.Any(v => v == etag.ToString()))
        return Results.StatusCode(StatusCodes.Status304NotModified);

    ctx.Response.Headers.ETag = etag.ToString();
    return Results.Ok(doc);
});

Follow-ups

  • Strong vs weak ETag? — Strong means byte-identical (required for range requests); weak means semantically equivalent, which is what most APIs actually have.
  • Does a 304 save server work? — Only the body: you still authenticate, route and compute the version. Saving the query needs the version in a cheap lookup.
  • How does this relate to DbUpdateConcurrencyException? — Same idea, different layer: the ETag carries the row version to the client and back, and the database enforces it.

Wrong answer: "ETags are only for static files." They are the standard mechanism for API concurrency control, and using them is what stops two clients silently overwriting each other.

Response compression: turn it on or leave it to the proxy? mid

Prefer the edge — a CDN, ingress or reverse proxy compresses more efficiently, caches the compressed artefact, and keeps the CPU cost off your application pods. Enable ASP.NET Core's ResponseCompression middleware when there is no such layer, or when the payload never reaches the proxy in a compressible form. If you do enable it in-process: it must be registered before whatever produces the body, HTTPS compression is off by default because of the BREACH/CRIME class of attacks (enabling it is only safe when responses do not mix secrets with attacker-controlled input), and Brotli generally beats gzip on text at similar CPU. .NET 11 previews add Zstandard support to ASP.NET Core, which is worth knowing about but not yet a production answer on .NET 10. Whatever you choose, compress text and skip already-compressed types (images, video, most binary formats) — compressing a JPEG spends CPU to make the file marginally larger.

Example 
builder.Services.AddResponseCompression(o =>
{
    o.EnableForHttps = false;                       // deliberate: BREACH
    o.Providers.Add<BrotliCompressionProvider>();
    o.Providers.Add<GzipCompressionProvider>();
    o.MimeTypes = ResponseCompressionDefaults.MimeTypes.Concat(["application/problem+json"]);
});
app.UseResponseCompression();                        // before anything that writes a body

Follow-ups

  • Why is BREACH a real concern? — Compression leaks information about the plaintext through response size when secrets and attacker-controlled data share a response; anti-CSRF tokens were the classic target.
  • Does compression help streamed responses? — Yes, but it buffers to a block size, adding latency to the first byte; measure for SSE.
  • What about request decompression? — .NET 7 added UseRequestDecompression; treat the decompressed size as untrusted and cap it (zip bomb).

Wrong answer: "Compress everything at maximum level for the smallest payload." Maximum Brotli is dramatically more CPU for a few percent; the default level is the right trade for dynamic responses.

Where does the time actually go in a typical ASP.NET Core request, and what do you optimise first? senior

For an ordinary CRUD endpoint the profile is dominated by I/O: the database round trip (often several, thanks to a hidden N+1), then outbound HTTP calls, then serialization, with the framework's own overhead — routing, model binding, filters, DI resolution — usually in the tens of microseconds. That ordering dictates the optimisation order: fix the query count and the query plan first, then the number of network hops (batch, parallelise, cache), then payload size, and only then micro-optimise the managed code. The way to earn the answer is to name how you would know: a trace with spans for each dependency, http.server.request.duration split by route, and the database's own statement statistics. Two framework-level items do reliably show up in real profiles and are worth naming: allocations from buffering large responses (stream instead), and reflection-based serialization on hot paths (use the System.Text.Json source generator).

Example 
// The classic: 1 + N queries hidden behind lazy loading or a loop.
var orders = await db.Orders.Where(o => o.CustomerId == id).ToListAsync(ct);
foreach (var o in orders) o.Lines = await db.Lines.Where(l => l.OrderId == o.Id).ToListAsync(ct);

// One query, projected to exactly what the DTO needs:
var dto = await db.Orders.AsNoTracking()
    .Where(o => o.CustomerId == id)
    .Select(o => new OrderDto(o.Id, o.Total, o.Lines.Select(l => new LineDto(l.Sku, l.Qty)).ToList()))
    .ToListAsync(ct);

Follow-ups

  • How do you catch N+1 automatically? — Count database commands per request as a metric and alert on the p99; EF Core also logs a warning for evaluated-client queries and lazy loading.
  • Is AsNoTracking always right for reads? — For read-only projections yes; it skips change-tracker setup and cuts allocations noticeably on large result sets.
  • What framework overhead is actually measurable? — Reflection-based JSON on large payloads, response buffering, and per-request scoped graphs that construct dozens of objects.

Wrong answer: "Middleware and DI are the bottleneck, so we removed layers." Those are microseconds against milliseconds of I/O; the optimisation removes structure and buys nothing.

Your read-heavy API must serve 50k rps with 99.9% availability. Where does caching sit? principal

Layer it, and be explicit about what each layer protects and how each one goes wrong. CDN/edge for anything anonymous and cacheable, keyed carefully with Vary, because the cheapest request is the one that never reaches you. In-process L1 for the hottest keys with a short TTL, because it survives a Redis outage and costs nothing per hit. Distributed L2 for shared state and to keep the origin miss rate low across replicas. Origin protection last: a concurrency limiter and request coalescing so a cold cache cannot take the database down. Then design the invalidation path deliberately — tags plus pub/sub eviction, and a version prefix as the big red button — and accept a stated staleness bound rather than pretending it is zero; "catalog data may be up to 30 seconds stale" is an engineering decision you can defend, "eventually consistent, we hope" is not. Finally, work the availability arithmetic out loud: 99.9% is 43 minutes a month, so a cache-cold restart storm or a single-region Redis failover can consume the whole budget — which is the argument for L1, for graceful degradation, and for load shedding that returns a fast 503 rather than dragging every request to a timeout.

Example 
client → CDN (public GETs, 60s, Vary: Accept-Encoding)
       → ingress
       → app  L1 HybridCache in-process (10–30s, survives Redis outage)
              L2 Redis cluster (5m, tag-invalidated, pub/sub eviction of L1)
       → origin DB behind a concurrency limiter (bounded misses, shed on saturation)

Follow-ups

  • What is your miss budget? — At 50k rps and a 95% hit rate the origin sees 2,500 rps; size and test the database for that, plus a cold-start multiple.
  • How do you deploy without a stampede? — Rolling restarts with a warm-up phase behind readiness, and L1 populated before the pod is marked ready.
  • How do you know the cache is healthy? — Hit ratio per layer, origin miss rate, eviction rate and p99 of the cache call itself — all four, because a high hit ratio with a slow cache is still an outage.

Wrong answer: "Put Redis in front of everything and set a long TTL." It creates a single point of failure with unbounded staleness, and the first failover becomes a full outage because nothing can serve without it.

What makes logging "structured", and why does it matter? mid

Structured logging keeps the message template and its parameters separate, so the sink stores fields rather than a rendered string: logger.LogInformation("Order {OrderId} shipped to {Region}", id, region) produces OrderId and Region as queryable properties plus a stable template you can group by. That is what makes "show me every failure for order X across four services" a query rather than a regex hunt, and it is why string interpolation into the message is the one thing you must not do — it destroys both the fields and the template. Layer on scopes (BeginScope) to attach request-wide context to every line, and use the LoggerMessage source generator on hot paths, which precomputes the template and avoids boxing and allocation when the level is disabled. Note the ordering rule people get wrong: parameters bind to placeholders positionally, not by name, so swapping two arguments silently mislabels your fields.

Example 
public static partial class Log
{
    [LoggerMessage(EventId = 1001, Level = LogLevel.Warning,
        Message = "Payment {PaymentId} declined for tenant {TenantId}: {Reason}")]
    public static partial void PaymentDeclined(ILogger logger, string paymentId, string tenantId, string reason);
}

using (logger.BeginScope(new Dictionary<string, object> { ["TenantId"] = tenant }))
{
    Log.PaymentDeclined(logger, id, tenant, reason);
}

Follow-ups

  • Why does LogInformation($"...") hurt? — The string is built even when the level is disabled, the fields are lost, and every message becomes a unique template so grouping breaks.
  • What is EventId for? — A stable numeric identity for an event, independent of wording; useful for alerting rules that must survive a message reword.
  • Where do scopes end up? — Only in sinks that support them; enable IncludeScopes explicitly for the console and OpenTelemetry exporters.

Wrong answer: "We log everything as JSON strings we build ourselves." You have reimplemented the formatter, lost the template, and made levels and scopes useless.

Which log level for what, and how do you keep the volume sane? mid

The convention that survives contact with production: Trace/Debug for development detail, off in production; Information for business-significant events (an order placed, a job completed), not for every function entry; Warning for something recoverable that a human might care about in aggregate; Error for a failed operation that a user noticed; Critical for the process or a dependency being unusable. Volume control is configuration, not code: per-category minimum levels in appsettings, which reload at runtime so you can raise verbosity during an incident without a deploy. Add sampling for high-volume categories, and remember the framework's own categories — Microsoft.AspNetCore.Hosting.Diagnostics logs two lines per request, which at 50k rps is your entire logging bill. The senior instinct to voice: logs are the expensive signal; prefer metrics for anything you would otherwise count by grepping logs.

Example 
{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning",
      "Microsoft.EntityFrameworkCore.Database.Command": "Warning",
      "System.Net.Http.HttpClient": "Warning"
    }
  }
}

Follow-ups

  • How do you raise a level at runtime? — Change the configuration source; ILoggerFactory subscribes to the change token, so it applies without a restart.
  • What is IsEnabled good for? — Guarding expensive argument computation; the source generator does this for you.
  • Do you log request bodies? — Only behind a flag, redacted, and never by default — it is the fastest route to storing PII and secrets in your log platform.

Wrong answer: "Log everything at Information so we have it if we need it." That is the bill nobody budgeted for, and it buries the ten lines that mattered.

How does distributed tracing work in .NET, and what is Activity? senior

System.Diagnostics.Activity is .NET's native span: it carries a W3C traceparent (trace id, span id, flags), tags, events and links, and Activity.Current flows through async continuations via AsyncLocal. ASP.NET Core starts an Activity per request from the incoming traceparent header (or creates a new trace), and HttpClient injects the current context into outbound requests automatically — so context propagation across services is on by default, without OpenTelemetry. OpenTelemetry then exports those activities: AddOpenTelemetry().WithTracing(...) with the ASP.NET Core and HttpClient instrumentation subscribes to the existing ActivitySources and ships them via OTLP. For your own spans, create an ActivitySource as a static field and start activities around meaningful work — a database call, a queue publish, a business step — and add tags rather than log lines, since a tag is queryable and a log line inside a span usually is not.

Example 
private static readonly ActivitySource Source = new("Orders.Api", "1.0.0");

using var activity = Source.StartActivity("reserve-inventory", ActivityKind.Client);
activity?.SetTag("sku", sku);
activity?.SetTag("tenant.id", tenantId);
try { await inventory.ReserveAsync(sku, ct); }
catch (Exception ex) { activity?.SetStatus(ActivityStatusCode.Error, ex.Message); throw; }

Follow-ups

  • What is baggage? — Key/value context propagated across services alongside the trace id; useful for tenant id, dangerous for anything sensitive because it travels to every hop including third parties.
  • How do you sample? — Head sampling (decide at the root, cheap, may miss rare errors) or tail sampling in a collector (keep all traces that contain an error or exceed a latency threshold). Most teams want tail sampling and get head sampling.
  • Does a span survive a queue? — Only if you propagate the context in the message headers and link it on the consumer side; that is manual work every messaging integration must do.

Wrong answer: "You need a vendor agent to get traces." The primitives are in the BCL and the propagation is automatic; the vendor supplies storage and a UI.

What metrics would you emit from an ASP.NET Core service, and what is the cardinality trap? senior

Start with what the framework already gives you — since .NET 8 there are standardised OpenTelemetry-conventions metrics: http.server.request.duration (histogram, tagged by route, method, status), http.server.active_requests, kestrel.active_connections, plus System.Runtime counters for GC, thread pool and exceptions, and .NET 10 added authentication and authorization metrics (challenge, forbid, sign-in counts) and memory-pool metrics. Add your own domain metrics via Meter/Counter<T>/Histogram<T> for things that matter to the business: orders placed, payments declined by reason, queue depth. The trap is cardinality: every distinct combination of tag values is a separate time series, so a tag carrying a user id, an order id, a raw URL path or an unbounded error message multiplies your series count into the millions and either bankrupts or breaks the metrics backend. Route templates are safe, raw paths are not; error codes are safe, exception messages are not.

Example 
public sealed class OrderMetrics
{
    private readonly Counter<long> _placed;
    private readonly Histogram<double> _value;
    public OrderMetrics(IMeterFactory f)
    {
        var m = f.Create("Orders.Api");
        _placed = m.CreateCounter<long>("orders.placed", unit: "{order}");
        _value  = m.CreateHistogram<double>("orders.value", unit: "EUR");
    }
    public void Placed(string region, string channel)      // low cardinality only
        => _placed.Add(1, new("region", region), new("channel", channel));
}

Follow-ups

  • Why IMeterFactory rather than new Meter? — It ties the meter's lifetime to DI, which makes metrics testable and avoids duplicate meters in WebApplicationFactory tests.
  • Counter, histogram or gauge? — Counter for monotonic events, histogram for distributions you will percentile, observable gauge for a value you sample (queue depth, pool size).
  • How do you find a high-cardinality tag before production does? — Assert on series count in a load test, or scrape the meter locally and count distinct tag sets.

Wrong answer: "Tag metrics with the user id so we can debug individual users." That is what traces and logs are for; in metrics it is the classic way to take down the observability platform.

Design health checks that are actually useful. senior

Separate the questions the orchestrator is asking. Liveness answers "is this process wedged, should you kill it" and must depend on nothing external — a dependency blip must never restart your pods, because a restart storm turns a partial outage into a total one. Readiness answers "should traffic go here" and may check the dependencies you cannot serve without, with a short timeout and a cached result so probes do not become load. A third, startup, exists for slow-booting apps so liveness does not fire during warm-up. Beyond probes, health checks are useful as a human-facing dependency dashboard (/health/detail, authenticated) and as a degradation signal: a service that can serve reads without its cache should report degraded, not unhealthy, because "unhealthy" removes it from rotation entirely. Tag checks and expose them through separate endpoints with a predicate, publish results to your metrics backend with IHealthCheckPublisher, and keep every check bounded by a timeout so a hung dependency cannot hang the probe.

Example 
builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])
    .AddNpgSql(cs, name: "db", tags: ["ready"], timeout: TimeSpan.FromSeconds(2))
    .AddRedis(redisCs, name: "cache", failureStatus: HealthStatus.Degraded, tags: ["ready"]);

app.MapHealthChecks("/health/live",  new() { Predicate = c => c.Tags.Contains("live") });
app.MapHealthChecks("/health/ready", new()
{
    Predicate = c => c.Tags.Contains("ready"),
    ResultStatusCodes = { [HealthStatus.Degraded] = StatusCodes.Status200OK }   // degraded still serves
}).ShortCircuit();

Follow-ups

  • Why must liveness not check the database? — A database outage would restart every pod simultaneously, discarding warm caches and connection pools exactly when recovery needs them.
  • How do you stop probes from costing? — Cache the result for a few seconds, short-circuit the endpoint out of the middleware pipeline, and keep the checks cheap (a ping, not a query).
  • What does degraded mean operationally? — Serve, but alert; it is the state that lets you page a human without taking the service out of rotation.

Wrong answer: "One /health endpoint that checks everything, used for both probes." That is the configuration that turns a five-minute database hiccup into a full restart storm.

A user reports a slow request from an hour ago. Walk me through finding it. senior

Ask for the correlation or trace id first — if your error responses and your UI surface one, this is a single lookup, and if they do not, that is the first thing to fix after the incident. With the trace id, open the trace: the waterfall shows which span dominated, whether it was one slow dependency or many small ones, and whether time was spent in a gap between spans (which usually means queueing, GC or thread-pool delay rather than work). Without an id, narrow by dimensions you do have: the route's latency histogram for that window, filtered by tenant or region, then use exemplars — the trace ids attached to histogram buckets — to jump from "the p99 bucket" straight into a matching trace. Then correlate with the infrastructure timeline: deploys, config changes, GC pause counters, thread-pool queue length, dependency error rates. The answer that impresses is the one that ends with a system improvement, not just a diagnosis: if the lookup took twenty minutes, the gap is that trace ids are not surfaced to users or not sampled on errors.

Example 
// Make every response carry the id, so support never has to guess.
app.Use(async (ctx, next) =>
{
    ctx.Response.OnStarting(() =>
    {
        ctx.Response.Headers["trace-id"] = Activity.Current?.TraceId.ToString() ?? ctx.TraceIdentifier;
        return Task.CompletedTask;
    });
    await next();
});

Follow-ups

  • What if the trace was sampled out? — Tail sampling that always keeps errors and slow requests fixes this; head sampling at 1% guarantees the interesting ones are missing.
  • How do logs and traces join? — Every log line carries the trace and span id when the OpenTelemetry logging provider is enabled; that join is the whole point of the setup.
  • What if it was a client-side problem? — Compare server-side duration with any RUM/client timing; a fast server span with a slow user experience points at the network, TLS or the browser.

Wrong answer: "Grep the logs for the user's email." Slow, privacy-hostile, and it fails the moment the request did not log anything unusual — which is exactly the case you are investigating.

Why did .NET standardise on OpenTelemetry, and what does that change for you? senior

Because the instrumentation APIs in the BCL — ILogger, Activity/ActivitySource, Meter — are now the OpenTelemetry data model in all but name, so libraries can instrument themselves once and every backend can consume it. Practically that means you add instrumentation packages plus an OTLP exporter and you are done: no vendor SDK compiled into your code, no rewrite when you change observability vendors, and third-party libraries (EF Core, the Azure SDKs, MassTransit, StackExchange.Redis) emit spans you did not have to write. It also means the semantic conventions matter: attribute names like http.request.method and db.system are standardised, so dashboards and alerts are portable. What changes for you day to day is mostly negative work — you delete vendor-specific instrumentation, you stop maintaining a bespoke correlation-id middleware because traceparent does it, and you push vendor choice out to the collector, which is also where you do sampling, redaction and routing without redeploying the app.

Example 
builder.Services.AddOpenTelemetry()
    .ConfigureResource(r => r.AddService("orders-api", serviceVersion: version))
    .WithTracing(t => t.AddAspNetCoreInstrumentation()
                       .AddHttpClientInstrumentation()
                       .AddEntityFrameworkCoreInstrumentation()
                       .AddSource("Orders.Api")
                       .AddOtlpExporter())
    .WithMetrics(m => m.AddAspNetCoreInstrumentation()
                       .AddHttpClientInstrumentation()
                       .AddRuntimeInstrumentation()
                       .AddMeter("Orders.Api")
                       .AddOtlpExporter());
builder.Logging.AddOpenTelemetry(o => { o.IncludeScopes = true; o.IncludeFormattedMessage = true; });

Follow-ups

  • Why run a collector rather than exporting directly? — Batching, retry, redaction, tail sampling and vendor routing, all changeable without touching the app.
  • What is .NET Aspire's role here? — Its service defaults wire exactly this configuration plus health checks and resilience, and its dashboard consumes OTLP locally — useful even if you do not deploy with Aspire.
  • Does it cost performance? — Spans are cheap when nobody listens (ActivitySource checks for listeners first) and measurable when everything is sampled at 100%; sample deliberately.

Wrong answer: "OpenTelemetry is just another vendor SDK." It is a specification plus a wire protocol; the point is that it is the one your BCL types already speak.

You are on call for 40 services. What must be instrumented before you accept the rota? principal

Non-negotiables, in the order they get used during an incident. One: the RED metrics per service and per route — rate, errors, duration as a histogram — with consistent names, because the first question is always "what changed and where". Two: distributed tracing with tail sampling that always keeps errors and slow requests, plus trace ids on responses and in logs, so you can go from a symptom to a specific request. Three: a deploy and config-change feed on the same timeline as the metrics, because most incidents are caused by a change and correlating them by eyeball costs the first ten minutes. Four: dependency health as a first-class signal — saturation of pools, breaker state, queue depth — since these lead the user-visible failure by minutes and are what you alert on. Five: runbooks attached to alerts, and alerts defined on symptoms (SLO burn rate) not causes, so you are not paged for a CPU spike nobody feels. The principal-level framing is that this is a platform deliverable: no team should be instrumenting these by hand, and a service that does not emit them should fail its production-readiness review rather than being fixed after its first outage.

Example 
Per service, non-negotiable:
  http.server.request.duration    histogram, tags: route, method, status
  dependency.calls / errors       per dependency, breaker state, pool saturation
  traces                          tail-sampled: all errors, all > p99, 1% baseline
  logs                            structured, trace-correlated, PII-redacted at the collector
  events                          deploys + config changes on the same timeline
  alerts                          SLO burn rate (fast + slow burn), runbook link per alert

Follow-ups

  • How do you enforce it? — A shared bootstrap package plus a production-readiness gate that checks the signals exist, not a checklist someone ticks.
  • What do you delete? — Alerts nobody acted on in six months, and dashboards nobody opened during the last three incidents; unused telemetry is cost plus noise.
  • What is the first thing you add after an incident? — Whatever you wished you had had: usually one metric or one tag, added while the pain is fresh.

Wrong answer: "We have dashboards and we log a lot." Volume is not observability; if you cannot answer "which dependency, for which tenant, since when" in one query, you are debugging by intuition.

What is Kestrel, and do you still need a reverse proxy? mid

Kestrel is the cross-platform, in-process HTTP server built on System.IO.Pipelines and sockets, and it is the default in every ASP.NET Core template. Since .NET 2.1 it is explicitly supported as an internet-facing edge server, so a reverse proxy is no longer required for safety — but it is still usual, for reasons that have nothing to do with Kestrel's HTTP parsing: TLS termination and certificate management, load balancing across replicas, request buffering to absorb slow clients, static content, WAF rules, header rewriting, and canary routing. In Kubernetes the ingress controller plays that role; on Windows, IIS with the ASP.NET Core Module hosts it in-process (best throughput) or out-of-process (Kestrel behind IIS as a proxy). The essential consequence of running behind anything is UseForwardedHeaders: without it your app sees the proxy's IP and scheme, so HTTPS redirection loops, rate limiting keys on one address, and logs record the load balancer as the client.

Example 
builder.Services.Configure<ForwardedHeadersOptions>(o =>
{
    o.ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto;
    o.KnownNetworks.Clear(); o.KnownProxies.Clear();      // only if the proxy network is trusted
    o.ForwardLimit = 1;
});
app.UseForwardedHeaders();     // FIRST, before anything that reads scheme or client IP

Follow-ups

  • Why is clearing KnownProxies risky? — It makes the app trust X-Forwarded-For from anyone who can reach it; only do it when nothing but the ingress can, and prefer configuring the actual proxy network.
  • In-process vs out-of-process on IIS? — In-process runs Kestrel inside the IIS worker with no loopback hop and is substantially faster; out-of-process is a proxy to a separate dotnet process.
  • What is YARP? — Microsoft's reverse proxy library for building a proxy in .NET; useful for BFFs, gradual strangler migrations and per-tenant routing.

Wrong answer: "Kestrel is not safe to expose, you must put IIS or nginx in front." That has not been true since 2018; the modern reasons for a proxy are operational, not safety.

Which Kestrel limits matter, and what attack or bug does each prevent? senior

MaxConcurrentConnections and MaxConcurrentUpgradedConnections bound resource use per instance. MaxRequestBodySize (default 30 MB, and separately enforced by the ASP.NET Core Module on IIS) stops an unbounded upload from becoming an OOM. MinRequestBodyDataRate and MinResponseDataRate are the slowloris defence: a client that trickles bytes to hold a connection open is disconnected once it falls under the rate. KeepAliveTimeout and RequestHeadersTimeout bound idle and half-open connections. For HTTP/2 there are stream-level equivalents — MaxStreamsPerConnection, header table size, and InitialConnectionWindowSize/InitialStreamWindowSize which control flow-control buffering and directly trade memory for throughput. Worth knowing as a current detail: .NET 11 previews report 20–40% better Kestrel throughput specifically for handling malformed requests, which is the traffic you get from scanners. The point of the question is that defaults are a starting position, not a security posture — an endpoint accepting large uploads needs its own limit raised locally, not the global one.

Example 
builder.WebHost.ConfigureKestrel(k =>
{
    k.Limits.MaxConcurrentConnections = 10_000;
    k.Limits.MaxRequestBodySize = 10 * 1024 * 1024;                 // 10 MB globally
    k.Limits.MinRequestBodyDataRate = new(bytesPerSecond: 240, gracePeriod: TimeSpan.FromSeconds(5));
    k.Limits.KeepAliveTimeout = TimeSpan.FromSeconds(60);
    k.Limits.Http2.MaxStreamsPerConnection = 100;
});

app.MapPost("/upload", Upload).WithMetadata(new RequestSizeLimitAttribute(200 * 1024 * 1024));

Follow-ups

  • How do you allow a big upload on one endpoint? — [RequestSizeLimit] / DisableRequestSizeLimit, or set IHttpMaxRequestBodySizeFeature.MaxRequestBodySize before reading the body.
  • What does the ASP.NET Core Module add on IIS? — Its own maxAllowedContentLength, which will reject the request before Kestrel ever sees it — a classic "I raised the limit and nothing changed".
  • Where do you enforce TLS versions? — ConfigureHttpsDefaults with SslProtocols, or at the proxy; be explicit rather than relying on OS defaults across environments.

Wrong answer: "Set MaxRequestBodySize to null so uploads never fail." That is an unbounded memory or disk write driven by an anonymous client.

Framework-dependent or self-contained? What about Native AOT? mid

Framework-dependent deployment ships only your code and relies on a shared runtime installed on the host or present in the base image: smallest artefact, and security patches to the runtime arrive by updating the image or host without rebuilding your app. Self-contained bundles the runtime with the app: it runs anywhere, pins the exact runtime version, and makes you responsible for shipping runtime CVE fixes — which is the trade people underestimate. Native AOT compiles ahead of time to a single native binary: no JIT, tiny startup (milliseconds), lower memory, no runtime dependency at all, at the cost of no reflection-heavy libraries, no dynamic assembly loading, larger build times and platform-specific artefacts. In containers the calculus is usually: framework-dependent on the official aspnet image for most services, self-contained plus trimming when image size matters, Native AOT for serverless, CLI tools and sidecars where cold start dominates. .NET 11 previews make the NativeAOT CLI path and MSBuild server defaults, which lowers the friction further.

Example 
<PropertyGroup>
  <PublishAot>true</PublishAot>
  <InvariantGlobalization>true</InvariantGlobalization>
  <StripSymbols>true</StripSymbols>
</PropertyGroup>
dotnet publish -c Release -r linux-x64 --self-contained   # or /p:PublishAot=true

Follow-ups

  • Who patches the runtime in a self-contained app? — You do, by rebuilding and redeploying; that is an operational commitment, not a build flag.
  • Does Native AOT support ASP.NET Core? — Minimal APIs and gRPC yes (with the request-delegate and JSON source generators); MVC, Razor Pages and Blazor Server are not supported.
  • What breaks under trimming? — Anything resolving types by name at runtime; the analyzer warnings are real, and suppressing them is how you get a TypeLoadException in production only.

Wrong answer: "Self-contained is always safer because nothing external can change." It also means nothing external can fix a runtime CVE for you.

Write a production Dockerfile for an ASP.NET Core service. What matters? mid

Multi-stage: an SDK stage that restores and publishes, and a runtime stage on mcr.microsoft.com/dotnet/aspnet that copies only the published output. Restore before copying the whole source so the layer cache survives code changes. Run as a non-root user — the official images since .NET 8 ship an app user and default to port 8080 rather than 80 precisely so they can run unprivileged. Prefer -alpine or -noble-chiseled images for a much smaller attack surface (chiseled has no shell and no package manager, which is a real security win and a real debugging inconvenience — plan for ephemeral debug containers). Set ASPNETCORE_URLS or rely on the image default, keep configuration in the environment rather than baked into the image, and do not put secrets in build args, which persist in the image history. Worth mentioning: dotnet publish /t:PublishContainer builds an OCI image with no Dockerfile at all, which many teams now prefer.

Example 
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY ["src/Api/Api.csproj", "src/Api/"]
RUN dotnet restore "src/Api/Api.csproj"
COPY . .
RUN dotnet publish "src/Api/Api.csproj" -c Release -o /app/publish --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:10.0-noble-chiseled AS final
WORKDIR /app
COPY --from=build /app/publish .
USER $APP_UID
EXPOSE 8080
ENTRYPOINT ["dotnet", "Api.dll"]

Follow-ups

  • Why did the default port change to 8080? — Binding below 1024 needs privileges; 8080 lets the container run as a non-root user out of the box.
  • How do you debug a chiseled image? — kubectl debug with an ephemeral container, or a -extra variant with the diagnostics tools for non-production.
  • What sets the runtime version? — The base image tag plus TargetFramework; a mismatch produces a startup error naming the required framework version.

Wrong answer: "Single-stage build from the SDK image." You ship the compiler, the NuGet cache and your source in the production image — several hundred megabytes of attack surface.

What happens to in-flight requests and connections during a rolling deploy? senior

Old pods receive SIGTERM and start draining while new pods start; the risks are on both ends. On shutdown, the endpoint-removal race means traffic can arrive after the listener closes — the preStop sleep and readiness-first draining discussed under hosting. Keep-alive and HTTP/2 connections make it worse: a long-lived connection pinned to an old pod keeps sending requests until it is closed, so the proxy must be told to drain (most ingresses do this) and your KeepAliveTimeout should be shorter than the grace period. On startup, a new pod that is marked ready before it is warm serves the first requests with a cold JIT, an empty cache and an unopened connection pool — visible as a latency spike at every deploy, which is why readiness should include a warm-up and why ReadyToRun matters more than its raw numbers suggest. WebSocket and SignalR connections deserve their own answer: they cannot be drained silently, so the client must reconnect, which means your app needs a backplane and reconnection logic, not just a longer grace period.

Example 
terminationGracePeriodSeconds: 60          # > ShutdownTimeout (45s) > longest request
lifecycle:
  preStop:
    exec: { command: ["/bin/sleep", "10"] }  # let endpoint removal propagate first
readinessProbe:
  httpGet: { path: /health/ready, port: 8080 }
  periodSeconds: 5
  failureThreshold: 2

Follow-ups

  • How do you prove drains work? — Deploy under load in staging and assert zero 5xx and zero connection resets; if you have never tested it, assume it does not.
  • Blue/green or rolling? — Rolling is cheaper and slower to roll back; blue/green gives instant rollback and doubles capacity cost. Canary is the middle, and needs per-version metrics to be worth anything.
  • What about database migrations? — Expand/contract: deploy a schema both versions can use, migrate, then remove — otherwise rollback is impossible.

Wrong answer: "Kubernetes handles it, that is what rolling updates are for." It handles pod lifecycle; connection draining, warm-up and schema compatibility are yours.

How do you configure the app per environment without rebuilding the artefact? mid

ASPNETCORE_ENVIRONMENT (or DOTNET_ENVIRONMENT) selects appsettings.{Environment}.json and drives IWebHostEnvironment.IsDevelopment(), and everything else comes from environment variables and the platform's secret store — so the same image promotes from staging to production unchanged, which is the property you actually want. Two rules make it hold. First, no environment-specific code branches beyond the developer-experience ones (the developer exception page, Swagger UI); a feature that only works in production is a feature that is never tested. Second, no configuration baked into the image at build time, because that turns a config change into a rebuild and breaks the "the artefact I tested is the artefact I ship" guarantee. The environment name is not a security boundary either — an app that decides whether to enable authentication based on the environment string will eventually run in production with the wrong variable set.

Example 
env:
  - name: ASPNETCORE_ENVIRONMENT
    value: Production
  - name: ConnectionStrings__Default
    valueFrom: { secretKeyRef: { name: orders-db, key: connection-string } }
  - name: Logging__LogLevel__Microsoft.AspNetCore
    value: Warning

Follow-ups

  • Custom environment names? — Fully supported (Staging, QA, Load); IsDevelopment() is just a string comparison against "Development".
  • How do you keep dev and prod honest? — Run the production configuration path in CI (bind and validate every options type) and keep environment-only branches to a hard-coded, reviewed list.
  • Where does launchSettings.json apply? — Local development only; it is never read in a container or in production.

Wrong answer: "Build a separate image per environment with the config baked in." Then you never ship the artefact you tested, and a config typo needs a full build and deploy to fix.

Fifty services, and cold start now matters. What is your deployment strategy? principal

First establish whether cold start actually matters, and where: for a service kept warm behind a load balancer it is a deploy-time latency blip; for autoscaling under bursty load or a scale-to-zero workload it is user-visible on every scale-out, and that is a different problem worth real money. Then attack it in cost order. Free: ReadyToRun (composite where it helps), tiered compilation with the defaults, trimming the assembly graph, and moving warm-up work out of StartAsync so the process becomes live fast and ready when warm. Cheap: right-size the container so the CPU limit does not throttle JIT during startup — a 250 millicore limit makes every cold start three times worse and is the most common self-inflicted cause. Expensive: Native AOT for the services whose profile fits (minimal APIs, no reflection-heavy dependencies), which turns hundreds of milliseconds into tens but costs library compatibility and build complexity, so pilot it on two or three services and measure before mandating anything. Alongside that, keep capacity ahead of demand — pre-scaling on a schedule and a small warm pool are often cheaper than an AOT migration across fifty codebases. And measure the thing you care about: time to first successful request under production CPU limits, not Stopwatch in Program.cs.

Example 
<!-- Directory.Build.props: one change, fifty services -->
<PropertyGroup>
  <PublishReadyToRun>true</PublishReadyToRun>
  <TieredCompilationQuickJitForLoops>true</TieredCompilationQuickJitForLoops>
  <InvariantGlobalization>true</InvariantGlobalization>
</PropertyGroup>

Follow-ups

  • Why does the CPU limit matter so much? — Startup is JIT-bound and bursty; a tight CFS quota throttles exactly the phase that needs CPU, so raising the limit (not the request) often halves cold start for free.
  • Would you mandate AOT? — No. Pilot, publish the numbers and the compatibility findings, then let teams opt in where the profile fits; a mandate produces workarounds.
  • What about Aspire? — It standardises local orchestration and service defaults, which reduces variance between fifty services — useful for consistency more than for cold start itself.

Wrong answer: "Rewrite everything with Native AOT." Most of the fifty will hit a reflection-based dependency, and you will have spent a quarter to fix a problem that a CPU-limit change and ReadyToRun would have mostly solved.

Explain tiered compilation and OSR. senior

The JIT compiles each method twice under tiered compilation: tier 0 is produced quickly with minimal optimisation so startup is fast, and a method that is called often enough (a call-count threshold, with background compilation) is recompiled at tier 1 with full optimisation. The obvious hole is a method that is entered once and then loops for a long time — a batch loop or a server loop — which under naive tiering would run at tier 0 forever. On-Stack Replacement, on by default since .NET 7, fixes exactly that: the runtime can transition a running method from tier 0 to optimised code mid-execution, patching the stack frame at a loop back-edge. The practical consequences are that benchmarks must warm up or they measure tier 0, and that TieredCompilation=false is almost always the wrong lever — it trades a much slower startup for a marginal steady-state gain that ReadyToRun plus tiering usually already gives you.

Example 
<PropertyGroup>
  <TieredCompilation>true</TieredCompilation>               <!-- default -->
  <TieredPGO>true</TieredPGO>                                <!-- default since .NET 8 -->
  <TieredCompilationQuickJitForLoops>true</TieredCompilationQuickJitForLoops>
</PropertyGroup>

Follow-ups

  • How do you see which tier a method is at? — dotnet-trace with the JIT provider, or the Microsoft-Windows-DotNETRuntime method-load events showing the optimisation tier.
  • Does ReadyToRun replace tier 0? — Effectively: R2R code serves as the starting tier, so startup skips JIT for those methods and hot ones are still rejitted at tier 1.
  • When would you disable tiering? — Benchmarks and latency-critical short-lived processes where you would rather pay startup once; measure, do not assume.

Wrong answer: "Tier 1 kicks in after 30 calls, so warm-up is a myth." The thresholds and the background compilation mean measured steady-state performance can take thousands of iterations to appear — which is exactly why unwarmed benchmarks mislead.

What is dynamic PGO and what does it actually do to your code? senior

Dynamic profile-guided optimisation, on by default since .NET 8, instruments tier-0 code to collect real profile data — which branches are taken, which concrete types show up at a virtual call site, how often a loop runs — and feeds that into the tier-1 compilation. The most valuable transformation it enables is guarded devirtualization: at an interface call site where 95% of the calls are one implementation, the JIT emits a type check plus a direct (and inlinable) call for that type, with a fallback for the rest. That collapses the abstraction penalty of interfaces and delegates, which is why "use an interface" stopped being a measurable performance decision for most code. .NET 10 continued down this path: array interface methods can now be devirtualized and inlined, array enumeration is de-abstracted, inlining considers profile data when deciding size budgets, and escape analysis was extended so more short-lived objects are stack-allocated. The practical implication for an interview: the JIT is now good enough that hand-devirtualizing (sealing everything, avoiding LINQ reflexively) is usually not where your wins are.

Example 
// Before PGO: a virtual call the JIT could not inline.
foreach (var item in (IEnumerable<int>)array) sum += item;

// With PGO + .NET 10 array-interface devirtualization, this compiles close to:
// if (enumerator is SZGenericArrayEnumerator<int>) { inlined fast path }
// else { virtual call }

Follow-ups

  • What is the cost? — Instrumented tier-0 code is slower, so startup is marginally worse; the trade was judged worth it and made default in .NET 8.
  • Static PGO too? — Yes: ReadyToRun images can carry profile data (the framework's own do), which gives better cold code before dynamic profiles exist.
  • Does sealed still help? — Occasionally, and it is free — but it is no longer the lever it was; measure before restructuring code for it.

Wrong answer: "PGO means I should run a profiler and feed it a profile at build time." That is static PGO; the default in modern .NET is dynamic and requires nothing from you.

What is ReadyToRun and when is it worth it? mid

ReadyToRun precompiles IL to native code at publish time and stores it alongside the IL in the assembly, so at startup the runtime can execute directly instead of JIT-compiling everything. The IL is still there, so tiering can rejit hot methods with full optimisation and PGO — you get fast startup without giving up steady-state performance, which is the key difference from Native AOT. Costs: the artefact roughly doubles in size for the precompiled assemblies, the code is version-bound (a runtime update invalidates it and falls back to JIT), and R2R code is slightly less optimised than tier-1 JIT because it must be conservative about what it can assume. Composite R2R compiles the app and framework together into one image for better cross-assembly inlining, at the cost of a much larger artefact and a hard version pin. It is worth it for anything where startup is visible — autoscaling services, CLI tools, serverless — and roughly free otherwise apart from image size.

Example 
dotnet publish -c Release -r linux-x64 --self-contained \
  /p:PublishReadyToRun=true /p:PublishReadyToRunComposite=true

Follow-ups

  • Does R2R need self-contained? — Cross-platform R2R requires a RID; composite effectively requires self-contained.
  • How much does it help? — Typically a large fraction of managed startup time on a cold process; measure yours, since it depends on how much code runs before first request.
  • Why is it "version bubble" limited? — Precompiled code embeds assumptions about the framework's layout, so it is only valid within the bubble it was compiled against.

Wrong answer: "ReadyToRun is the same as Native AOT." R2R keeps the runtime, the JIT and reflection; AOT removes them, with a very different compatibility contract.

What does Native AOT give up, and how do you tell whether an app can use it? senior

Native AOT compiles the whole application ahead of time into a self-contained native executable: no JIT, no runtime code generation, and the linker removes anything it cannot prove is used. What you give up follows directly: Reflection.Emit and dynamic code (so expression-tree compilation, most dynamic proxies and many mocking or ORM strategies fail), Assembly.LoadFrom-style plugin loading, and any reflection over types the trimmer could not see — which surfaces as a runtime MissingMetadata/TypeLoadException rather than a build error unless the library is annotated. In ASP.NET Core, minimal APIs and gRPC support AOT (with the request-delegate generator and JSON source generation); MVC, Razor Pages and Blazor Server do not. The way to tell is not to reason about it but to publish with AOT and read the trim/AOT analyzer warnings: they are accurate, and every suppressed warning is a future production-only failure. Then test on the real artefact — an AOT build is a different binary, so your integration tests must run against it.

Example 
var builder = WebApplication.CreateSlimBuilder(args);          // AOT-friendly host
builder.Services.ConfigureHttpJsonOptions(o =>
    o.SerializerOptions.TypeInfoResolverChain.Insert(0, AppJsonContext.Default));

[JsonSerializable(typeof(Order))]
[JsonSerializable(typeof(List<Order>))]
internal partial class AppJsonContext : JsonSerializerContext { }

Follow-ups

  • What are the wins in numbers? — Startup in the low tens of milliseconds, working set often less than half, no runtime to install; build time and artefact-per-platform are the costs.
  • What is CreateSlimBuilder? — A host builder without the heavier defaults (no IIS integration, fewer configuration sources, no file watching), which is what the AOT template uses.
  • Can you use EF Core? — Increasingly, with compiled models and precompiled queries, but check the current support matrix rather than assuming; it has historically been the blocker.

Wrong answer: "AOT is just a compiler flag, everything still works." The trimming contract is the whole difficulty; the flag is the easy part.

Why does trimming break libraries, and what does an annotation like [DynamicallyAccessedMembers] do? senior

The trimmer performs static reachability analysis over IL: anything it cannot see being used is removed. Reflection defeats that analysis — Type.GetType(name), Activator.CreateInstance, serializers that discover properties at runtime — because the type name is a string the analyzer cannot follow, so the type is trimmed and the reflection fails at runtime with a confusing error. The annotations exist to restore the missing edges: [DynamicallyAccessedMembers] on a parameter or field tells the trimmer "whatever type flows here needs its public constructors/properties preserved", [RequiresUnreferencedCode] marks an API as fundamentally untrimmable so callers get a warning, and [UnconditionalSuppressMessage] is the escape hatch you must justify. That is why the ecosystem moved to source generators for serialization, DI registration, logging, options validation and regex: a generator produces statically visible code, so the trimmer keeps it and there is nothing to annotate.

Example 
public static object Create(
    [DynamicallyAccessedMembers(DynamicallyAccessedMemberTypes.PublicConstructors)] Type t)
    => Activator.CreateInstance(t)!;      // trimmer now preserves constructors of anything passed in

[RequiresUnreferencedCode("Uses reflection over the model; use the source-generated overload.")]
public static string Serialize(object value) => JsonSerializer.Serialize(value);

Follow-ups

  • How do you find these before shipping? — Publish with <IsTrimmable>/<PublishTrimmed> and treat trim analyzer warnings as errors in CI.
  • What is a trim feature switch? — A build-time constant (for example EventSourceSupport) that lets the trimmer remove whole subsystems; useful for shrinking size further.
  • Does trimming help startup? — Somewhat (less to load and JIT), but its primary benefit is artefact size; ReadyToRun and AOT are the startup levers.

Wrong answer: "Just suppress the warnings, it works fine in testing." It works until the code path that reflects on the trimmed type runs — usually an error handler or an admin endpoint, in production.

Why did .NET move so much to source generators? senior

Because generated code is statically visible, so it works with trimming and AOT, and because it moves work from every startup or every call to build time once. The pattern shows up everywhere now: System.Text.Json's JsonSerializerContext replaces reflective metadata discovery, [LoggerMessage] precomputes the log template and avoids boxing, [GeneratedRegex] emits a compiled matcher without RegexOptions.Compiled's runtime emit, [OptionsValidator] generates validation code, minimal APIs have a request-delegate generator, [LibraryImport] replaces DllImport's runtime marshalling stubs, and .NET 10 added a source-generated validator for minimal APIs and a generator that pulls XML doc comments into OpenAPI. The trade-offs worth naming: build time grows, debugging steps into generated files, and the generated code is part of your compilation so an analyzer bug is your problem. The framing that reads well: reflection is a runtime tax you pay forever; a generator pays it once, at build.

Example 
[GeneratedRegex(@"^\d{3}-\d{4}$", RegexOptions.CultureInvariant)]
private static partial Regex PhonePattern();     // compiled at build time, trim-safe

[LoggerMessage(Level = LogLevel.Information, Message = "Order {OrderId} accepted")]
static partial void OrderAccepted(ILogger logger, string orderId);

Follow-ups

  • How do you inspect the generated code? — <EmitCompilerGeneratedFiles>true</EmitCompilerGeneratedFiles> writes it to disk; useful when a generator does something surprising.
  • Do generators slow the IDE? — They can; incremental generators exist precisely to keep the editor responsive, and a badly written one is noticeable immediately.
  • Do you still need reflection? — Yes for genuinely dynamic scenarios (plugins, scripting); the point is that the common cases no longer need it.

Wrong answer: "Source generators are just a way to avoid writing boilerplate." That is the smallest benefit; trimming compatibility and removing runtime reflection are why the framework adopted them.

You must halve p99 latency on a service you did not write. How do you approach it? principal

Refuse to optimise before you can attribute. Establish a reproducible load test that produces the production latency profile, then decompose p99 into its parts with traces and counters: time in your code, time waiting on dependencies, time queueing (thread pool, connection pool, semaphores), and time in GC pauses. p99 is usually not "the code is slow" — it is a tail cause: a lock, a cold cache, a retry, a GC pause, a connection-pool wait, or a single slow shard. So the first pass is to find which of those it is, and the fix follows mechanically: remove the lock or make it per-key, warm or coalesce the cache, cap or remove the retry, tune the GC or the allocation rate, size the pool. Only after those do micro-optimisations (serialization, allocations, LINQ in hot loops) matter, and by then you can measure them honestly. Two things to say out loud because they mark seniority: define the target in terms the business cares about (an SLO with a burn-rate alert, not a benchmark number), and change one thing at a time with a canary, because in a system this size two simultaneous changes make the result uninterpretable.

Example 
p99 decomposition (one week, one service):
  38%  waiting on the connection pool (Max Pool Size 100, 140 concurrent requests)  → raise + limit inbound
  24%  a single lock in a cache refresh path                                        → per-key coalescing
  19%  gen 2 pauses from a 3 GB in-process cache                                    → move hot set to Redis L2
  11%  retries against a degraded dependency                                        → breaker + budget
   8%  everything else (serialization, mapping)                                     → left alone

Follow-ups

  • How do you know the load test is representative? — Replay production traffic shapes (mix, key distribution, payload sizes); a uniform synthetic load hides exactly the hot-key effects that cause tails.
  • What if the fix is architectural? — Say so with the number attached: "the p99 is dominated by a synchronous call chain three services deep; no local optimisation fixes it".
  • How do you keep it from regressing? — A latency budget in CI on the critical path plus an SLO alert; without one, the next feature spends the gain.

Wrong answer: "Profile it and optimise the hottest method." CPU profiles show throughput cost, not tail latency; the p99 cause is usually waiting, which barely appears in a CPU profile.

14 System.Text.Json & serialization

Every API serialises, so binding and serialization bugs are universal, and the Newtonsoft-to-System.Text.Json migration is still live in enough codebases that interviewers use it as a "have you done this recently" probe. Mid: defaults, naming policies, why STJ is stricter. Senior: source generation, polymorphism, custom converters, performance. Principal: contract evolution and versioning across producers and consumers.

docs: System.Text.Json overview · Migrate from Newtonsoft.Json

What are the important differences between System.Text.Json and Newtonsoft.Json? mid

STJ is strict and UTF-8-first by design; Newtonsoft is permissive. The differences that break migrations: STJ will not read a number from a JSON string without AllowReadingFromString, will not accept comments or trailing commas without opting in, is case-sensitive by default (though ASP.NET Core configures case-insensitivity), does not support ReferenceLoopHandling the same way (you get ReferenceHandler.Preserve or a cycle exception), historically ignored non-public members and fields (fields need IncludeFields), and requires explicit configuration for polymorphism rather than the TypeNameHandling free-for-all — which was a security hole in Newtonsoft and is deliberately not replicated. In exchange you get roughly a two-to-three-times throughput improvement on typical payloads, far fewer allocations, source generation for AOT, and no dependency. Newtonsoft is still the right answer when you need its dynamic features (JObject manipulation, custom contract resolvers, JsonPath) and ASP.NET Core still ships AddNewtonsoftJson() for exactly that.

Example 
var options = new JsonSerializerOptions(JsonSerializerDefaults.Web)   // camelCase + case-insensitive
{
    NumberHandling = JsonNumberHandling.AllowReadingFromString,
    ReadCommentHandling = JsonCommentHandling.Skip,
    AllowTrailingCommas = true,
    DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull
};

Follow-ups

  • What is JsonSerializerDefaults.Web? — The preset ASP.NET Core uses: camelCase naming, case-insensitive reads, numbers-as-strings allowed for reads.
  • How do you handle cycles? — ReferenceHandler.Preserve (emits $id/$ref, which clients must understand) or fix the model — usually a DTO without the back-reference.
  • Is DateTime handling different? — STJ is strict ISO 8601 by default; Newtonsoft was looser, and this is a very common migration break.

Wrong answer: "They are interchangeable, just swap the package." The strictness differences change runtime behaviour for real payloads, and the failures appear as 400s for a subset of clients.

What does the JSON source generator do, and when is it required? senior

Instead of discovering a type's shape by reflection at runtime and caching the metadata, the generator emits that metadata — and optionally straight-line serialization code — at build time, in a JsonSerializerContext you point the serializer at. Benefits: faster startup (no reflection warm-up on first serialization), lower steady-state allocations, and, crucially, compatibility with trimming and Native AOT, where reflection over trimmed types simply fails. It is required for Native AOT and strongly recommended when publishing trimmed. The two modes matter: metadata-based generation supports everything the reflective serializer does, while serialization-optimised (fast-path) generation produces the fastest writer but falls back for features it cannot express (custom converters, reference handling, some options). Register it via TypeInfoResolverChain so the framework's own types keep working alongside yours.

Example 
[JsonSourceGenerationOptions(PropertyNamingPolicy = JsonKnownNamingPolicy.CamelCase,
                             GenerationMode = JsonSourceGenerationMode.Default)]
[JsonSerializable(typeof(OrderDto))]
[JsonSerializable(typeof(IReadOnlyList<OrderDto>))]
[JsonSerializable(typeof(ProblemDetails))]
internal partial class ApiJsonContext : JsonSerializerContext { }

builder.Services.ConfigureHttpJsonOptions(o =>
    o.SerializerOptions.TypeInfoResolverChain.Insert(0, ApiJsonContext.Default));

Follow-ups

  • What if a type is missing from the context? — With a reflection fallback in the chain it still works; without one (AOT) you get a runtime exception naming the type — which is why you list every root type.
  • Does it help a non-AOT web API? — Modestly on throughput, more on startup; the main reason to adopt it there is future-proofing for trimming.
  • Can you mix generated and reflective? — Yes, via the resolver chain, and that is the normal migration path.

Wrong answer: "The source generator is just a performance optimisation." It is a correctness requirement under AOT and trimming; performance is the side benefit.

How do you serialise a polymorphic hierarchy safely? senior

With [JsonDerivedType] (.NET 7+), which declares an explicit closed set of allowed subtypes and a type discriminator written into the payload ($type by default, renameable via JsonPolymorphicAttribute.TypeDiscriminatorPropertyName). The point of the design is that the set is closed and declared in code, so deserialization can never be persuaded to instantiate an arbitrary type. That is the direct answer to Newtonsoft's TypeNameHandling.Auto/All, which embedded assembly-qualified type names in the JSON and, when applied to untrusted input, was a remote-code-execution vector — a genuinely famous class of .NET vulnerability. Practical notes: discriminator values are part of your wire contract, so use stable short strings rather than type names; put the discriminator first in the payload for streaming readers; and if the hierarchy is open-ended, deserialise to a envelope with a known kind field and dispatch yourself rather than trying to make polymorphism open.

Example 
[JsonPolymorphic(TypeDiscriminatorPropertyName = "kind")]
[JsonDerivedType(typeof(CardPayment), "card")]
[JsonDerivedType(typeof(SepaPayment), "sepa")]
public abstract record Payment(decimal Amount);
public sealed record CardPayment(decimal Amount, string Last4) : Payment(Amount);
public sealed record SepaPayment(decimal Amount, string Iban)  : Payment(Amount);

Follow-ups

  • What happens with an unknown discriminator? — It throws; catch it and return a 400 with a clear message, or add an explicit fallback type if forward compatibility matters.
  • Why not just a kind property and a switch? — Perfectly valid, and sometimes clearer; the attribute version keeps OpenAPI and the serializer in agreement.
  • What did TypeNameHandling do wrong? — It let the payload choose the type to instantiate, so a crafted document could construct dangerous types — a deserialization RCE.

Wrong answer: "Enable TypeNameHandling.All like we did with Newtonsoft." On untrusted input that is a known remote-code-execution pattern, and STJ deliberately has no equivalent.

Write a custom JsonConverter. When is it the right tool? senior

When the wire format and the CLR type genuinely differ and you cannot change either: a value object that should serialise as a bare string, a legacy API sending dates as epoch milliseconds, an enum that must round-trip as a specific set of strings, or a union type. A converter overrides Read and Write for one type and is registered on the options or with [JsonConverter] on the type. The mechanical details that separate a working converter from a correct one: Read must leave the reader positioned on the last token of the value it consumed, must handle JsonTokenType.Null, and must not assume the property order; Write should honour the naming policy and encoder from the options rather than hard-coding. And know when not to: if you are writing a converter to reshape your own DTO, change the DTO — a converter is invisible to readers of the model and to most OpenAPI schema generation, so it should be a last resort, and when you do use it, add a schema transformer so the documented type matches reality.

Example 
public sealed class TenantIdConverter : JsonConverter<TenantId>
{
    public override TenantId Read(ref Utf8JsonReader r, Type t, JsonSerializerOptions o)
        => r.TokenType == JsonTokenType.Null ? default
         : TenantId.TryParse(r.GetString(), out var id) ? id
         : throw new JsonException("invalid tenant id");

    public override void Write(Utf8JsonWriter w, TenantId value, JsonSerializerOptions o)
        => w.WriteStringValue(value.ToString());
}

Follow-ups

  • How do you convert a dictionary key? — Override WriteAsPropertyName/ReadAsPropertyName; forgetting them is why a custom key type serialises as an object.
  • Do converters work with the source generator? — Yes for metadata mode; the fast path falls back to the converter, which costs some of the speed benefit.
  • How do you test one? — Round-trip properties: serialise, deserialise, assert equality, plus explicit tests for null and malformed input.

Wrong answer: "Use a converter to add computed fields to the output." That hides business logic in the serialization layer; project to a DTO instead.

How do you serialise large payloads without blowing up memory? senior

Stream, do not buffer. On the write side, return IAsyncEnumerable<T> or use JsonSerializer.SerializeAsync(stream, …) directly into the response body so elements are written as they are produced; avoid JsonSerializer.Serialize to a string, which materialises the whole payload — and if it exceeds 85 KB, on the Large Object Heap, once per request. On the read side, JsonSerializer.DeserializeAsyncEnumerable processes a large array element by element, and Utf8JsonReader over a PipeReader gives you full control for very large or unusual documents. Two constraints to state: the framework enforces a maximum depth (64 by default) as a stack-overflow defence, and you should cap the request body size for any endpoint that accepts a large document, because "stream it" without a limit just means the attacker chooses how much memory you use. Also worth naming: .NET 10 switched MVC and minimal APIs to PipeReader-based JSON deserialization, so custom converters must now handle Utf8JsonReader.HasValueSequence — a real breaking change for hand-written converters.

Example 
app.MapPost("/import", async (HttpRequest req, IImporter importer, CancellationToken ct) =>
{
    var items = JsonSerializer.DeserializeAsyncEnumerable<ImportRow>(req.Body, JsonOpts, ct);
    var count = 0;
    await foreach (var row in items) { await importer.HandleAsync(row, ct); count++; }
    return Results.Ok(new { imported = count });
}).WithMetadata(new RequestSizeLimitAttribute(500 * 1024 * 1024));

Follow-ups

  • Why is 85 KB the magic number? — The Large Object Heap threshold; a serialized string above it is allocated on a heap that is collected with gen 2 and not compacted by default.
  • What about MemoryStream? — Use RecyclableMemoryStream if you must buffer; it pools chunks and keeps them off the LOH.
  • Does streaming break error handling? — Yes, the same trade as any streamed response: after the first flush you cannot change the status code.

Wrong answer: "Serialise to a string and write it — the GC will handle it." At scale that is a per-request LOH allocation, which is one of the most reliable ways to cause gen 2 pressure.

How do you evolve a JSON contract without breaking consumers? principal

Adopt an explicit compatibility rule and enforce it mechanically. The rule that works: adding an optional field is safe; removing a field, renaming one, narrowing a type, changing an enum's serialised values or tightening a validation are all breaking. Consumers must ignore unknown fields (so do not enable UnmappedMemberHandling.Disallow on a public API) and must not depend on property order or on the absence of a field. Enforce it with generated-schema diffing in CI — the OpenAPI document produced at build time, compared against the previous release with a breaking-change detector — plus consumer-driven contract tests for your top consumers, because a schema diff cannot catch semantic changes like "status now means something different". For the deprecation path, ship the new field alongside the old one, emit a metric when the old one is still read or written so you can see actual usage rather than guess, and remove it only when that metric is zero for a defined period. Then say the uncomfortable part out loud: with external consumers you can rarely remove anything, so design the first version as if the fields are permanent, and prefer adding a new resource or version over mutating an existing shape.

Example 
public sealed record OrderDto
{
    public required Guid Id { get; init; }

    [Obsolete("Use TotalAmount; removal after 2027-01-01")]
    [JsonPropertyName("total")]
    public decimal LegacyTotal => TotalAmount.Value;      // still emitted, usage metered

    public required Money TotalAmount { get; init; }
}

Follow-ups

  • How do you measure who still uses a field? — Count reads on the server for inputs; for outputs you cannot, so you need client telemetry or a deprecation window plus an announcement.
  • Are enums safe to extend? — Only if consumers tolerate unknown values; document a fallback (unknown) from day one, or you cannot ever add a case.
  • What about nullability changes? — Making a field nullable is breaking for consumers that assumed it was present; treat it as a version bump.

Wrong answer: "We tell consumers to update when we change the contract." With external consumers you do not control deployment, and "we announced it" is not a rollback plan.

What is WebApplicationFactory and what does it actually run? mid

It boots your real application — the real Program.cs, the real DI container, the real middleware pipeline and endpoints — on an in-memory TestServer rather than a socket, and hands you an HttpClient wired to it. So the test exercises routing, model binding, filters, authentication and serialization exactly as production does, without a port or a process. You override what you must through WithWebHostBuilder/ConfigureTestServices, which runs after the app's own registrations, so Replace and RemoveAll work there. Two mechanical details: with top-level statements the generated Program class is internal, so you need public partial class Program; at the bottom of Program.cs or an InternalsVisibleTo; and TestServer is not a real network stack, so anything depending on real sockets, TLS, HTTP/2 framing or Kestrel limits needs a real server (UseKestrel with a dynamic port) instead.

Example 
public sealed class ApiFactory : WebApplicationFactory<Program>
{
    protected override void ConfigureWebHost(IWebHostBuilder builder)
    {
        builder.UseEnvironment("Testing");

        {

  • How do you authenticate in tests? — A test authentication scheme that issues a fixed principal, or a signed token from a test key; never disable authorization, or you stop testing it.
  • Is it slow? — Startup dominates; share the factory across a test class or collection rather than constructing one per test.
  • What does it not cover? — Anything below the pipeline: TLS, Kestrel limits, proxy behaviour, real network failures.

Wrong answer: "It mocks the whole app so the tests are fast." It runs the app; the value is precisely that almost nothing is mocked.

In-memory database, SQLite, or a real database in a container? senior

The EF Core in-memory provider is not a database: no relational constraints, no transactions, different query translation, no SQL. It will happily pass a test for code that fails against SQL Server, which makes it actively dangerous for anything touching queries or constraints — it is only reasonable for testing code that merely uses DbContext as a collection. SQLite in-memory is a real relational engine and catches constraint and transaction issues, but its SQL dialect and type affinity differ enough that provider-specific queries, JSON columns and computed columns diverge. A real database in a container (Testcontainers, or a shared ephemeral instance) tests what you actually run, catches migration problems, and is now cheap enough that it is the default recommendation for repository and integration tests. The judgment answer is a pyramid: unit-test domain logic with no database at all, use a containerised real database for the data-access and integration layer, and keep the count of those tests small enough that they stay fast — parallelised with a schema or database per test class, and seeded by migrations so the schema under test is the schema you ship.

Example 
public sealed class DbFixture : IAsyncLifetime
{
    private readonly PostgreSqlContainer _db = new PostgreSqlBuilder()
        .WithImage("postgres:17-alpine").Build();

    public string ConnectionString => _db.GetConnectionString();
    public async Task InitializeAsync()
    {
        await _db.StartAsync();
        await using var ctx = new AppDbContext(Options());
        await ctx.Database.MigrateAsync();          // the real migrations, on the real engine
    }
    public Task DisposeAsync() => _db.DisposeAsync().AsTask();
}

Follow-ups

  • How do you isolate tests sharing one container? — A database or schema per test class, or a transaction rolled back per test; the former parallelises better.
  • Does this slow CI unacceptably? — Container start is a few seconds, amortised over a whole class; the alternative is bugs that only appear in staging.
  • What about cloud-only dependencies? — Emulators where they exist (Azurite, the Cosmos emulator), contract tests plus a thin adapter where they do not.

Wrong answer: "Use the in-memory provider, it is what the docs show for testing." Microsoft's own guidance now warns against it for exactly this reason.

Where do you put test doubles, and what do you refuse to mock? senior

Mock at the boundary you own: an interface that represents an external system (a payment gateway, a mail sender, a clock) is a legitimate seam because it is a contract you defined and can verify separately. Do not mock types you do not own — HttpClient, DbContext, cloud SDK clients — because your mock encodes your belief about their behaviour, and that belief is exactly what tests should be checking; use a fake HTTP handler or a real containerised dependency instead. Do not mock the thing under test's own collaborators so thoroughly that the test asserts the implementation: a test that verifies "called SaveChangesAsync once" breaks on every refactor and passes when the behaviour is wrong. Two doubles worth having in every codebase: a controllable clock (TimeProvider, in the BCL since .NET 8, so you no longer need a hand-rolled IClock) and a fake message bus, because time and asynchrony are where flaky tests come from.

Example 
// TimeProvider makes time a dependency instead of an ambient global.
public sealed class TokenService(TimeProvider clock)
{
    public bool IsExpired(Token t) => t.ExpiresAt <= clock.GetUtcNow();
}

var clock = new FakeTimeProvider(new DateTimeOffset(2026, 9, 8, 12, 0, 0, TimeSpan.Zero));
clock.Advance(TimeSpan.FromHours(2));
Assert.True(new TokenService(clock).IsExpired(token));

Follow-ups

  • How do you fake HttpClient? — A DelegatingHandler that returns canned responses, injected via the factory; it tests your real serialization and headers.
  • What is TimeProvider? — The BCL abstraction over time (GetUtcNow, timers, Task.Delay) with FakeTimeProvider for tests; it removes an entire category of sleep-based flakiness.
  • When are strict mocks worth it? — Rarely; they couple tests to call sequences and turn refactoring into test maintenance.

Wrong answer: "Mock everything so tests are fast and isolated." You end up testing your mocks, and the integration bugs — which is where the failures actually are — remain invisible.

A test passes locally and fails in CI one time in twenty. How do you handle it? senior

Treat it as a defect in the test or in the code, never as noise to be retried away — a suite people do not trust is a suite people stop reading. The usual causes in ASP.NET Core tests are shared mutable state between tests running in parallel (a static, a shared database row, a singleton in a shared factory), real time (sleeps, timeouts sized for a fast laptop, anything asserting on wall-clock ordering), unordered asynchrony (asserting on a background worker having finished), and port or container contention. The fix follows the cause: isolate state per test (a database per class, a fresh factory when the container is mutated), replace sleeps with TimeProvider and deterministic waits on an actual signal, and make assertions on observable outcomes rather than timing. Quarantine is acceptable as a short-term measure with an owner and a deadline; a retry annotation with no ticket is how a suite rots. And instrument it: track flake rate per test in CI so you can argue from data instead of from the last person's annoyance.

Example 
// Flaky: depends on the worker having run within 500 ms.
await Task.Delay(500);
Assert.Single(await repo.GetOutboxAsync());

// Deterministic: wait for the actual signal, with a bounded timeout.
await outbox.Published.WaitAsync(TimeSpan.FromSeconds(5), ct);
Assert.Single(await repo.GetOutboxAsync());

Follow-ups

  • Is auto-retry ever acceptable? — For genuinely external flakiness (a registry pull) at the job level, not at the test level, and always with a recorded count.
  • How do you find shared state? — Run the suite in a random order and with parallelism forced; order-dependent tests fail immediately.
  • What if the flake is in production code? — Then it is a race in production too, and the test just found it — the best possible outcome.

Wrong answer: "Add a retry and move on." You have hidden a race that will reappear in production, and taught the team that red is negotiable.

What is your test strategy for 40 services — and what do you deliberately not test? principal

Push testing down and outward: fast unit tests for domain logic (the majority, milliseconds, no I/O), a solid layer of in-process integration tests per service using WebApplicationFactory plus a containerised database, contract tests at every service boundary so a producer cannot break a consumer without a red build, and a deliberately small number of end-to-end journeys covering the two or three flows the business genuinely cannot lose. Cross-service integration tests are where organisations burn the most time for the least signal — they are slow, flaky, expensive to own and usually fail for environmental reasons — so replace most of them with contracts. What I explicitly do not test: framework behaviour (that routing routes, that DI injects), third-party libraries, getters and mappers with no logic, and any UI detail that changes weekly. What I add instead, because it catches more real defects per hour than another test layer: production smoke tests after every deploy, synthetic monitoring of the critical journeys, and progressive delivery so the first real signal comes from 1% of traffic rather than from a staging environment nobody trusts.

Example 
per service:   unit (ms, thousands)  →  integration (WebApplicationFactory + Testcontainers, dozens)
across:        consumer-driven contracts (every boundary, in CI on both sides)
whole system:  2–3 end-to-end journeys, run on release candidates only
production:    post-deploy smoke + synthetics + canary with automatic rollback on SLO burn

Follow-ups

  • Why contracts instead of integration environments? — Contracts fail on the producer's PR with a precise message; an integration environment fails hours later for reasons nobody can attribute.
  • What is the budget? — A PR pipeline that finishes in under ten minutes; anything slower gets bypassed, and a bypassed gate is not a gate.
  • How do you handle the tests nobody owns? — Ownership is assigned with the service; unowned suites get deleted rather than left red, because a permanently red suite is worse than none.

Wrong answer: "Aim for 90% code coverage across all services." Coverage measures execution, not verification; the number drives tests for trivial code and says nothing about the integration seams where the outages come from.

16 SignalR, gRPC & streaming

Rarely the focus of a loop unless the role involves real-time or internal RPC, but it comes up as a design-round tangent ("how would you push updates to 100k clients?") and as a way to check breadth. Mid: what SignalR and gRPC are for. Senior: transports, backplanes, scaling stateful connections, gRPC's HTTP/2 requirements. Nothing here is usually make-or-break, but a wrong answer about scaling websockets is memorable in the bad way.

docs: SignalR · gRPC on .NET

How does SignalR pick a transport, and what does that mean operationally? mid

SignalR negotiates down a list: WebSockets first, then Server-Sent Events, then long polling, based on what the client and every intermediary support. WebSockets is the only one that is genuinely bidirectional and cheap; SSE is server-to-client only; long polling works everywhere and costs a request per message plus reconnection churn. Operationally, the transport dictates everything else: WebSockets need your proxy, ingress and any WAF to support the upgrade and to allow long-lived connections with generous idle timeouts, and they hold a connection (and memory) per client, so connection count — not request rate — becomes your capacity metric. The negotiation step also means the first request is an HTTP call to /hub/negotiate, which must be routed to the same backend as the subsequent connection unless you use sticky sessions or skip negotiation entirely.

Example 
builder.Services.AddSignalR(o =>
{
    o.KeepAliveInterval  = TimeSpan.FromSeconds(15);
    o.ClientTimeoutInterval = TimeSpan.FromSeconds(30);   // must exceed 2x keep-alive
    o.MaximumReceiveMessageSize = 32 * 1024;
}).AddMessagePackProtocol();

app.MapHub<NotificationHub>("/hubs/notifications").RequireAuthorization();

Follow-ups

  • Why does long polling break things? — Every message is a request: your request-rate metrics, rate limiters and logs are swamped, and latency is a round trip.
  • What is the hub lifetime? — The hub instance is transient per invocation; do not store state in it, and scoped services resolve per hub method call.
  • How do you authenticate? — Standard schemes; for WebSockets the browser cannot set headers, so the token goes in the query string and must be read by the JWT handler's OnMessageReceived.

Wrong answer: "SignalR always uses WebSockets." It negotiates, and the fallback is exactly what bites you when a corporate proxy strips the upgrade.

How do you scale SignalR beyond one server? senior

Connections are stateful and pinned to one server, so a message published on server A must reach the clients connected to server B — that is what a backplane does. The options are the Redis backplane (every server subscribes and forwards, simple, but the backplane becomes a fan-out bottleneck at high message rates), Azure SignalR Service (offloads the connections themselves, so your app holds none and scales by message throughput), or a design that avoids the problem: shard clients by topic so all subscribers to a resource land on one server, or push through a message broker where each server filters. You also need sticky sessions if negotiation and the connection can land on different instances (or disable negotiation and use WebSockets only). And plan for reconnection, because deployments and scaling events disconnect everyone: automatic reconnect on the client, idempotent message handling, and a way to resync missed state — clients that reconnect into a stale view are the real-world failure, not the disconnection itself.

Example 
builder.Services.AddSignalR()
    .AddStackExchangeRedis(cfg["Redis:Connection"]!, o =>
        o.Configuration.ChannelPrefix = RedisChannel.Literal("notifications"));

// or offload connections entirely:
builder.Services.AddSignalR().AddAzureSignalR(cfg["AzureSignalR:ConnectionString"]);

Follow-ups

  • What is the backplane's scaling limit? — Every message goes to every server; with N servers and M messages the fan-out is N×M, so it is fine for moderate rates and poor for chat-scale broadcast.
  • How do groups work? — Group membership is per server plus the backplane; joining a group is a local operation replicated by message routing, not a durable subscription.
  • What happens on deploy? — Every connection drops; clients must reconnect and resync, which is why a "load the current state on reconnect" path is mandatory.

Wrong answer: "Just add more servers behind the load balancer." Without a backplane, a client connected to server B never sees a message published on server A — the bug appears only in multi-instance environments.

When is gRPC the right choice, and what are the constraints on .NET? senior

gRPC fits internal service-to-service communication where you want a schema-first contract, code generation for both sides, compact binary framing and streaming in both directions — typically a high-volume internal API, or one with genuine streaming semantics. The constraints matter: it requires HTTP/2 end to end, so every proxy, ingress and load balancer in the path must support it (and gRPC-Web exists precisely because browsers cannot speak raw gRPC); ASP.NET Core's gRPC server does not run on HTTP.sys or IIS in all configurations; and TLS is effectively required for HTTP/2 without prior knowledge. The other consideration is organisational: protobuf's field-number-based evolution gives you excellent additive compatibility for free, but you now maintain .proto files as a first-class artefact with its own review and publishing process. For public or partner APIs, JSON over HTTP remains the pragmatic answer, and .NET's gRPC JSON transcoding can expose the same service both ways when you need both.

Example 
builder.Services.AddGrpc(o => o.EnableDetailedErrors = env.IsDevelopment())
    .AddJsonTranscoding();               // same service, REST/JSON facade

app.MapGrpcService<OrdersService>();

builder.Services.AddGrpcClient<Orders.OrdersClient>(o => o.Address = new(cfg["Orders:Url"]!))
    .AddStandardResilienceHandler();

Follow-ups

  • How does load balancing work? — HTTP/2 multiplexing means an L4 balancer pins all calls to one backend; you need an L7 proxy, client-side load balancing (SocketsHttpHandler + a resolver) or a mesh.
  • Deadlines? — Built in and propagated automatically, which is genuinely better than the ad-hoc header conventions HTTP APIs use.
  • Error model? — Status codes plus rich error details; map them to your ProblemDetails at the boundary rather than leaking gRPC statuses to HTTP clients.

Wrong answer: "gRPC is faster so we should use it for the public API." Browsers cannot call it directly, partners will not adopt it, and the wins are largely irrelevant next to network latency on an external API.

Server-sent events, WebSockets or polling for a live dashboard? mid

For a dashboard — server-to-client only, moderate update rate, browser client — SSE is usually the best fit: it is plain HTTP, works through every proxy, reconnects automatically with Last-Event-ID, and has no framing complexity. WebSockets win when you need client-to-server messages on the same connection, very high message rates, or binary payloads. Polling wins when updates are rare and staleness of a few seconds is acceptable, because it needs no long-lived connections and no special infrastructure — never dismiss it, it is often the right engineering answer. .NET 10 made SSE first-class in minimal APIs with TypedResults.ServerSentEvents over an IAsyncEnumerable<SseItem<T>>, so you no longer hand-write the wire format. Whatever you pick, remember the connection is a resource: cap concurrent connections, send heartbeats so dead peers are detected, and make sure a client reconnecting after a deploy can resync rather than assuming it missed nothing.

Example 
app.MapGet("/dashboard/stream", (IMetricsFeed feed, CancellationToken ct) =>
    TypedResults.ServerSentEvents(Stream(feed, ct), eventType: "tick"));

static async IAsyncEnumerable<SseItem<Tick>> Stream(IMetricsFeed feed,
    [EnumeratorCancellation] CancellationToken ct)
{
    await foreach (var t in feed.ReadAsync(ct))
        yield return new SseItem<Tick>(t) { EventId = t.Sequence.ToString() };
}

Follow-ups

  • What is the browser's SSE connection limit? — Six per host over HTTP/1.1; HTTP/2 multiplexing removes the practical limit, which is a real argument for enabling it.
  • How do heartbeats work? — A comment line every N seconds keeps intermediaries from closing an idle connection and lets the client detect death.
  • Does SSE work through a corporate proxy? — Usually, since it is a normal HTTP response — but a buffering proxy will hold the stream, so X-Accel-Buffering: no and friends matter.

Wrong answer: "Always use WebSockets, they are the modern option." For unidirectional updates you have taken on connection management, proxy compatibility and a backplane requirement for no benefit.

A hub method takes 3 seconds. What is wrong and how do you fix it? senior

Hub invocations for a single connection are processed in order, so a slow method blocks that client's subsequent messages and holds resources on the server; with many clients doing the same you are also consuming the thread pool and the connection's buffers, and back-pressure eventually shows up as dropped or delayed messages across the whole hub. The fix is to make the hub a thin dispatcher: validate, enqueue the work (channel, queue, background service), acknowledge immediately, and push the result back to the caller or their group when it completes — which is also what makes the operation survive a disconnection, because the client can reconnect and receive the result rather than losing it. If the work genuinely must be synchronous, it belongs behind a normal HTTP endpoint with a timeout, not on a persistent connection. And configure the guardrails: MaximumParallelInvocationsPerClient, ClientTimeoutInterval, and stream results with IAsyncEnumerable when the response is naturally incremental.

Example 
public sealed class ReportHub(Channel<ReportJob> jobs) : Hub
{
    public async Task<string> RequestReport(ReportRequest req)
    {
        var id = Guid.NewGuid().ToString("n");
        await jobs.Writer.WriteAsync(new(id, req, Context.ConnectionId));
        return id;                                  // returns in microseconds
    }
}
// worker: await hubContext.Clients.Client(connectionId).SendAsync("ReportReady", id, url);

Follow-ups

  • How do you send to a client from outside a hub? — Inject IHubContext<THub>; it is the supported way for background services to push.
  • What if the client reconnects with a new connection id? — Address by user (Clients.User(userId)) or group rather than connection id, and make results retrievable by id.
  • Streaming from a hub? — Return IAsyncEnumerable<T> or ChannelReader<T>; the client consumes it incrementally with cancellation.

Wrong answer: "Increase the client timeout so it does not disconnect." That hides the symptom and keeps the connection blocked; the problem is doing long work on a message-ordered channel.

Treat it as a ceiling-raiser, not a gap to close first.

How does .NET load assemblies, and how would you build a plugin system? principal

Assemblies are resolved through AssemblyLoadContext: the default context resolves from the application's deps file and probing paths, and you can create additional contexts with their own resolution logic. A plugin system uses one AssemblyLoadContext per plugin, constructed with isCollectible: true and an AssemblyDependencyResolver built from the plugin's own .deps.json, so each plugin gets its dependencies without version-clashing with the host or with other plugins. The shared contract assembly must be loaded once, by the host, and deliberately not loaded into the plugin context — otherwise the same type name in two contexts produces the confusing "cannot cast Foo to Foo" error, which is the single most common symptom. Unloading is cooperative and hard: the context is collectible, but it only unloads once every reference — including threads, delegates, cached reflection objects, and ILogger instances held by the host — has been released, so a plugin that leaks one delegate never unloads. In a service, restarting the process is usually the honest answer, and dynamic unload is worth it only when the requirement is genuinely non-negotiable.

Example 
sealed class PluginContext(string pluginPath) : AssemblyLoadContext(isCollectible: true)
{
    private readonly AssemblyDependencyResolver _resolver = new(pluginPath);

    protected override Assembly? Load(AssemblyName name)
    {
        // Contract assemblies fall through to the default context on purpose.
        if (name.Name is "Plugins.Abstractions") return null;
        var path = _resolver.ResolveAssemblyToPath(name);
        return path is null ? null : LoadFromAssemblyPath(path);
    }
}

Follow-ups

  • Why does "cannot cast Foo to Foo" happen? — Type identity includes the load context; the same IL loaded twice produces two distinct types.
  • How do you verify unloading? — A weak reference to the context plus GC.Collect in a loop; if it stays alive, something still references it.
  • What breaks under Native AOT? — All of it: there is no runtime assembly loading, so plugins must be compiled in or run out of process.

Wrong answer: "Load the plugin with Assembly.LoadFrom into the default context." Version conflicts with the host are then unavoidable and nothing can ever be unloaded.

What is EventPipe, and how do the dotnet-* tools work? senior

EventPipe is the runtime's cross-platform tracing pipeline: the runtime and the framework write events through EventSource providers (GC, JIT, thread pool, ASP.NET Core, HttpClient, your own), and EventPipe streams them out over a diagnostic IPC channel — a Unix domain socket or a named pipe — that every .NET process exposes. That is what the dotnet- tools attach to: dotnet-counters subscribes to counter events, dotnet-trace collects an event stream into a nettrace file, dotnet-dump captures and analyses a process dump, dotnet-gcdump triggers a GC and walks the object graph, dotnet-stack prints managed stacks. Because it is in-process and always available, you can attach to a running container without a restart, an agent or a code change — which is the operationally important property. dotnet-monitor packages the same capability as a sidecar with an HTTP API and rules ("collect a dump when CPU exceeds X"), which is how you make this usable in a fleet where nobody can shell into a pod.

Example 
dotnet-counters monitor -p 1 --counters System.Runtime,Microsoft.AspNetCore.Hosting
dotnet-trace collect -p 1 --providers Microsoft-DotNETCore-SampleProfiler --duration 00:00:30
dotnet-stack report -p 1              # managed stacks of every thread, no dump needed
dotnet-gcdump collect -p 1

Follow-ups

  • How do you enable this in a locked-down container? — The diagnostic socket exists by default (DOTNET_EnableDiagnostics); ship dotnet-monitor as a sidecar or use an ephemeral debug container sharing the process namespace.
  • ETW vs EventPipe? — ETW is Windows-only and needs admin; EventPipe is cross-platform, in-process and is the modern path.
  • Can you write your own provider? — Yes, an EventSource subclass; but prefer Meter and ActivitySource unless you need raw event streams.

Wrong answer: "You need to attach a debugger or install a profiler agent." Both are far more intrusive than the built-in pipeline, and neither is realistic in production.

A production process is hung. What do you collect, in what order? senior

Collect before you mitigate, because a restart destroys the evidence and the next occurrence may be weeks away. In order: dotnet-stack report (or dotnet-dump collect if you want the full picture) for managed stacks — a deadlock or starvation is visible immediately as many threads parked in the same frame; dotnet-counters for a snapshot of thread-pool queue length, thread count, GC and lock contention; and a dotnet-gcdump if memory is implicated. Then analyse the dump: clrthreads for the thread list, parallelstacks to group them, syncblk for monitor ownership (which thread holds the lock everyone is waiting on), dumpasync for the async state machines that a plain stack walk cannot show — that last one is essential in modern .NET, because most hangs are awaits, not blocked threads, and they are invisible in clrstack. Only then restart, and file the artefacts with the incident so the analysis can continue afterwards.

Example 
dotnet-dump collect -p 1 -o /tmp/hang.dmp
dotnet-dump analyze /tmp/hang.dmp
> clrthreads          # how many, what state
> parallelstacks      # grouped stacks: the hot wait shows up as a wide branch
> syncblk             # who owns the contended monitor
> dumpasync           # pending async state machines - where the awaits are stuck

Follow-ups

  • What does a starvation dump look like? — Many pool threads in the same blocking frame (Monitor.Wait, Task.Result) and a large queue length.
  • What about a deadlock across async awaits? — dumpasync shows continuations waiting on each other; no OS-level deadlock is reported, which is why teams miss it.
  • How do you get a dump on crash automatically? — DOTNET_DbgEnableMiniDump and friends, or dotnet-monitor rules; configure it before you need it.

Wrong answer: "Restart it and add more logging." You have destroyed the only evidence and committed to waiting for a recurrence you cannot predict.

How does P/Invoke work, and what is [LibraryImport]? principal

P/Invoke calls native code by declaring an extern method with [DllImport]; the runtime resolves the library, generates a marshalling stub that converts managed arguments to the native ABI, transitions out of cooperative GC mode for the duration of the call, and transitions back. The costs and hazards are in that description: the transition is not free (tens of nanoseconds, more with marshalling), a native call that blocks holds a thread the GC may need to suspend, and any pointer you pass must be pinned or the GC may move it underneath the callee. [LibraryImport] (.NET 7+) is the source-generated replacement: the marshalling code is emitted at compile time as ordinary C#, so it is inspectable, trim- and AOT-compatible, and avoids the runtime IL stub generation that AOT cannot do. Practical rules: use SafeHandle rather than raw IntPtr so handle lifetime is tied to the GC and to finalization; be explicit about string marshalling and calling conventions; use SuppressGCTransition only for genuinely tiny, non-blocking calls; and keep the interop surface behind one wrapper class so the unsafe part of the codebase is small and reviewable.

Example 
internal static partial class Native
{
    [LibraryImport("libcrypto", StringMarshalling = StringMarshalling.Utf8)]
    [UnmanagedCallConv(CallConvs = [typeof(System.Runtime.CompilerServices.CallConvCdecl)])]
    internal static partial int Digest(string algorithm, ReadOnlySpan<byte> input, Span<byte> output);
}

Follow-ups

  • Why does the GC care about a native call? — Threads in native code are in preemptive mode; the GC cannot move objects they reference, hence pinning and fixed.
  • What is SafeHandle for? — Deterministic, leak-resistant handle ownership with a critical finalizer, avoiding handle-recycling races that raw IntPtr allows.
  • When is interop the wrong answer? — When a managed implementation exists; the maintenance and crash surface of native code is rarely worth a small speedup.

Wrong answer: "DllImport and LibraryImport are the same, one is just newer syntax." One generates marshalling IL at runtime and the other at build time — which is exactly why only the second works under Native AOT.

What actually happens between dotnet run and your first request being served? principal

The host resolves the runtime (hostfxr reads runtimeconfig.json and deps.json, picks a framework version by roll-forward policy, loads hostpolicy and then coreclr), the CLR initialises — GC heaps sized by mode and by any container limits, the thread pool, the type system — and your Main is JIT-compiled and invoked. Then the managed startup you control: the configuration providers are read in order, logging is set up, service descriptors are registered, Build() compiles the container, StartAsync runs the hosted services in registration order, Kestrel binds its endpoints and begins accepting, and ApplicationStarted fires. The first request then pays whatever is still cold: JIT for the pipeline and your handler, first-use initialisation in the serializer and the routing table, the first database connection and its handshake, and TLS session setup. Knowing this sequence is what lets you attribute a slow start correctly — "before Main" is a host/runtime problem you fix with ReadyToRun and CPU limits, "inside StartAsync" is your own eager work, and "after listening" is warm-up you should be doing behind a readiness gate rather than in front of users.

Example 
# Split host startup from managed startup
DOTNET_gcServer=1 dotnet-trace collect --providers \
  Microsoft-Windows-DotNETRuntime:0x1F000080018:5,Microsoft-Extensions-Logging \
  -- dotnet ./Api.dll
# PerfView: JIT time, assembly loads, and the gap before the first request event

Follow-ups

  • What is roll-forward? — The policy (latestPatch by default) deciding which installed runtime satisfies the app's requested version; a mismatch is the classic "framework not found" startup error.
  • Where does deps.json matter? — It lists dependencies and their locations; a missing or stale one produces assembly-resolution failures that look like packaging bugs, because they are.
  • Why does the first request cost more? — JIT plus first-use initialisation plus connection and TLS handshakes; a warm-up request behind readiness moves all three off the user's path.

Wrong answer: "It just starts the process and listens." The question is deliberately about the layers you can only optimise if you know they exist.

Explain Blazor's render modes. mid

Since .NET 8 there is one Blazor Web App model with per-component render modes. Static server rendering produces HTML on the server with no interactivity — fast, cheap, SEO-friendly, and now the default for pages that do not need events. Interactive Server (the old Blazor Server) keeps a stateful circuit over SignalR: the DOM diff is computed on the server and sent to the browser, so every interaction is a round trip. Interactive WebAssembly downloads the .NET runtime and your assemblies and runs entirely in the browser: no per-user server state, but a large first load and no direct database access. Interactive Auto starts on the server for the first visit and switches to WebAssembly once the runtime has been cached, which is a genuinely clever compromise. Enhanced navigation and streaming rendering sit alongside these, letting a static page update in place and stream slow content in. The reason interviewers ask: choosing a mode is choosing where state lives and what a network outage does to your app.

Example 
builder.Services.AddRazorComponents()
    .AddInteractiveServerComponents()
    .AddInteractiveWebAssemblyComponents();

app.MapRazorComponents<App>()
   .AddInteractiveServerRenderMode()
   .AddInteractiveWebAssemblyRenderMode();

Follow-ups

  • What does @rendermode InteractiveAuto require? — Both server and WebAssembly components registered, and code shared in a client project so the same component runs in both places.
  • What is streaming rendering? — The server sends initial HTML immediately and streams updates as async work completes, without interactivity.
  • Can render modes be mixed on a page? — Yes, per component; that granularity is the point of the .NET 8 unification.

Wrong answer: "Blazor Server and Blazor WebAssembly are two different frameworks you pick between." Since .NET 8 they are render modes within one app model, and choosing per component is the normal design.

What are the operational consequences of Blazor Server? senior

Every user holds a circuit: a stateful, server-side object graph plus a live SignalR connection. That makes latency a UX property — every click is a round trip, so a 200 ms RTT makes the app feel broken — and makes memory per user your scaling metric rather than requests per second. Deployments disconnect everyone, so you need reconnection UI (the ReconnectModal component .NET 10 shipped) and state that survives a reconnect; .NET 10 added circuit state persistence and declarative [PersistentState] for exactly this, and .NET 11 previews add automatic circuit pausing when the browser tab is hidden, which directly targets the idle-memory cost. You also need sticky sessions or a backplane, a bounded circuit retention time, and a careful stance on scoped services, because "scoped" means the whole circuit — potentially hours — which is why IDbContextFactory rather than an injected DbContext is the standard guidance. The upside is real: no API surface to build, no client-side auth token handling, and secrets stay on the server.

Example 
builder.Services.AddRazorComponents().AddInteractiveServerComponents()
    .AddCircuitOptions(o =>
    {
        o.DetailedErrors = env.IsDevelopment();
        o.DisconnectedCircuitRetentionPeriod = TimeSpan.FromMinutes(3);
        o.DisconnectedCircuitMaxRetained = 100;
    });
builder.Services.AddDbContextFactory<AppDbContext>(o => o.UseNpgsql(cs)); // not AddDbContext

Follow-ups

  • How many users per server? — Governed by memory per circuit and message rate; measure with a realistic component tree, and expect thousands rather than tens of thousands per instance.
  • What happens on a network blip? — The circuit reconnects if it is still retained; past the retention period the user loses state unless you persisted it.
  • Is it suitable for the public internet? — For latency-tolerant internal tools, yes; for a global consumer app, the round-trip-per-click model is a hard constraint.

Wrong answer: "It scales like any other ASP.NET Core app." It scales on concurrent stateful connections and memory, which is a completely different capacity model from stateless requests.

Blazor WebAssembly: what are the real costs? senior

Payload and startup first: the browser downloads the .NET runtime plus your assemblies, which even after IL trimming and Brotli compression is a multi-megabyte first load — mitigated by caching, fingerprinted assets and preloading (.NET 10 added automatic preloading of framework assets and moved boot configuration into dotnet.js), but never as small as a comparable JavaScript bundle. Then execution: the default is IL interpretation with AOT compilation available for hot paths, which trades a much larger download for near-native speed — so you AOT-compile selectively, not wholesale. Then the architecture: the app runs in the browser, so it needs a real API, real CORS and real client-side auth token handling, and nothing in it is secret. Debugging and diagnostics are weaker than on the server, though .NET 10 improved WebAssembly profiling and enabled hot reload by default in Debug. The honest framing is that Blazor WebAssembly is compelling when the team's expertise is C# and the app is line-of-business; it is not a payload or ecosystem win against a modern JavaScript framework.

Example 
<PropertyGroup>
  <RunAOTCompilation>true</RunAOTCompilation>    <!-- much bigger download, much faster CPU work -->
  <PublishTrimmed>true</PublishTrimmed>
  <InvariantGlobalization>true</InvariantGlobalization>
</PropertyGroup>

Follow-ups

  • Where should the auth token live? — Same answer as any SPA: prefer a BFF with cookies over tokens in browser storage.
  • Can it work offline? — Yes, as a PWA with a service worker; that is one of its genuine advantages over Blazor Server.
  • How do you call JavaScript? — IJSRuntime, and .NET 10 added constructor invocation and property get/set to the interop surface.

Wrong answer: "It is as fast as JavaScript because it is WebAssembly." Interpreted IL is not; AOT closes the gap on CPU-bound code at a large download cost, and DOM interop remains a bridge.

Would you choose Blazor for a new product, and how would you argue it? principal

Decide on team and product constraints, not on framework preference, and say the constraints out loud. Blazor is a strong choice when the team is C#-deep and hiring for C#, when the app is internal or line-of-business with a tolerant latency profile, when sharing validation and models between client and server has real value, and when you would otherwise carry the cost of a second language ecosystem for a small front end. It is a weak choice for a public consumer app where first-load size and SEO are commercial concerns, where you need the JavaScript ecosystem's component libraries and design systems, or where hiring front-end specialists matters more than reusing back-end ones. The honest risks to name unprompted: a smaller talent pool and component ecosystem, Blazor Server's latency and memory model, WebAssembly's payload, and the fact that you are betting on one vendor's roadmap for the UI layer. And the way to de-risk it: build the API first and treat the UI as a client of it, so the front-end decision stays reversible — which is the argument that actually wins the room, because it costs nothing and removes the irreversibility that makes people nervous.

  team is C#-deep                public consumer app, first-load size is commercial
  internal / LOB, latency ok     you need the JS component ecosystem
  shared validation + models     hiring front-end specialists
  small front end, one language  SEO and edge rendering are central
Either way: API first, UI as a client — keeps the decision reversible.

Follow-ups

  • How would you pilot it? — One real internal app end to end, with the real auth and the real deployment; a prototype proves nothing about circuits or payloads.
  • What would make you reverse? — Sustained hiring difficulty, or a latency or payload budget the render modes cannot meet. Write the criteria down before starting.
  • Can you mix? — Yes: Blazor for internal tooling and a JS framework for the public product is a common and defensible split.

Wrong answer: "Blazor, because then we do not need JavaScript." You still need it for interop, and a technology choice justified by avoidance rather than by fit does not survive its first hard requirement.

19 Judgment calls

Open-ended questions with no single right answer, asked from senior upward to see how you reason rather than what you recall. There is no "wrong answer" block here because the failure mode is different: a weak answer picks a side immediately, a strong one names the forces, states a default, and says what evidence would change it. Each block below says what a top-of-ladder answer demonstrates and which trade-offs it names unprompted.

Should a new service be minimal APIs or controllers — and should you migrate the existing 300 controllers? senior

What a strong answer demonstrates: that you separate the greenfield decision from the migration decision, and that you price the migration honestly. New service: minimal APIs with route groups, because they are the AOT-supported default, the per-request overhead is lower and group-level configuration makes cross-cutting concerns visible — unless you need MVC's model binding conventions, filters, formatters or Razor views, in which case controllers are not a legacy choice. Migration: almost never as a project. The two coexist in one app, so you migrate opportunistically when a controller is being substantially changed anyway, and you stop if the measured benefit does not materialise.

Trade-offs to name unprompted: a rewrite converts working, tested code into new untested code and the defect rate reflects that; consistency has real value for a team reading unfamiliar code, so a half-migrated codebase has its own cost; [ApiController] behaviours (automatic 400s, binding inference) have to be re-established explicitly in minimal APIs, and .NET 10's AddValidation() only just closed the validation half of that gap; and the performance difference is invisible next to a database call, so "faster" is not the argument — testability, AOT and explicit configuration are.

Monolith or microservices for a 12-person team building a new product? senior

What a strong answer demonstrates: that you know the constraint is organisational, not technical. Twelve people cannot staff independent on-call rotations for fifteen services, so the default is a modular monolith: one deployable, strong module boundaries enforced by architecture tests, separate schemas or at least separate table ownership per module, and in-process messaging where you would later put a queue. That keeps the option to extract a service when a real forcing function appears — a differing scaling profile, a compliance boundary, a team that genuinely needs independent deployment.

Trade-offs to name unprompted: distributed systems tax you with network failure, partial failure, eventual consistency, distributed tracing and a deployment pipeline per service — all of which cost engineering time you do not have at twelve people; a monolith's risk is boundary erosion, which you mitigate with enforced module boundaries rather than hope; extraction is much easier from a well-modularised monolith than from a poorly-bounded one, so the modularity work is not wasted either way; and the honest counter-argument — if a piece of the system has a genuinely different scaling or availability profile from day one, extract that one piece and only that one.

A dependency is down. Fail fast or degrade? senior

What a strong answer demonstrates: that the choice is per feature and driven by what a wrong answer costs. Degrade when serving stale or partial data is better than nothing: a recommendations panel, a product rating, an enrichment. Fail fast when a wrong answer is worse than no answer: pricing, entitlements, balances, permissions. The mechanism follows — cached fallbacks, feature-level circuit breakers and a documented degraded mode for the first; fast 503 with Retry-After and load shedding for the second.

Trade-offs to name unprompted: silent degradation hides outages from your own monitoring, so degraded mode must emit an explicit signal and ideally be visible to the user; stale data has a correctness bound that someone must own and state ("prices may be up to 60 seconds old"); failing open on anything security- or quota-related converts an availability incident into a security or cost incident; and the fallback path is code that almost never runs, so it must be exercised deliberately — a game day, or a scheduled fault injection — or it will be broken on the day it matters.

Repository pattern over EF Core: worth it? senior

What a strong answer demonstrates: that you can argue both sides and then commit. Against: DbSet is already a repository and DbContext already a unit of work, so a thin generic IRepository<T> adds indirection with no abstraction — it usually leaks IQueryable, which means it abstracts nothing, and it makes efficient queries harder by hiding Include, projection and split queries. For: a task-oriented repository (IOrderRepository.GetOpenForCustomerAsync) is not a generic wrapper, it is a domain-language boundary; it keeps query knowledge in one place, makes the data-access surface testable and greppable, and stops EF concerns spreading into handlers.

Trade-offs to name unprompted: "we might swap the ORM" is almost never a real requirement and is the weakest argument for the pattern; the strongest is query centralisation and domain vocabulary; testability is largely a non-argument now that a containerised database is cheap, so do not lean on it; and the cost of getting it wrong is real — a repository that returns IQueryable gives you the indirection without the boundary, which is the worst of both.

When do you upgrade to .NET 11, given .NET 10 is LTS? senior

What a strong answer demonstrates: that you have a policy rather than a preference, and that you know today's dates: .NET 10 is LTS with support to November 2028, .NET 11 is an STS release due 10 November 2026 with roughly 18 months of support, and .NET 8 and .NET 9 both reach end of support on 10 November 2026 — so the urgent migration this quarter is anything still on 8 or 9, not the question of 11. A defensible policy: production services track LTS by default; adopt the STS release only where a specific feature justifies committing to an 18-month upgrade cadence; and keep every service on a supported version as a hard rule, because an unsupported runtime is an unpatched runtime.

Trade-offs to name unprompted: LTS gives you a slower upgrade treadmill at the cost of waiting for features; STS gives you features at the cost of an upgrade every year and a half, which across fifty services is real recurring work; staying current is cheaper in aggregate than a big-bang jump every three years, so the fleet should be able to move continuously (automated dependency updates, one shared bootstrap package, CI running the next preview); and the actual risk in this cycle is scheduling — 8 and 9 go out of support the same day 11 ships, so the migration plan needs to be in flight now, not in November.

Native AOT across the fleet: yes or no? principal

What a strong answer demonstrates: that you scope it to where the benefit is measurable. AOT buys startup in the low tens of milliseconds, roughly half the working set and no runtime dependency — which is decisive for serverless, scale-to-zero, sidecars and CLI tools, and close to irrelevant for a long-running service that is warm 99.9% of the time. So: pilot on two or three services whose profile fits, publish the numbers and the compatibility findings, and let teams opt in. Not a mandate.

Trade-offs to name unprompted: the compatibility contract is the real cost — no Reflection.Emit, no dynamic loading, MVC and Blazor Server unsupported, and every reflective library must be checked; trim warnings are the truth and suppressing them defers failures to production; build times and per-platform artefacts complicate CI; debugging and profiling differ enough that the on-call runbook needs updating; and the cheaper alternatives — ReadyToRun, a correctly sized CPU limit, moving warm-up behind readiness — often capture most of the startup win for a fraction of the effort, which is the comparison you should make before spending a quarter.

Should the platform team own the HTTP pipeline for every service? principal

What a strong answer demonstrates: that you distinguish standardising the shape from owning the values, and that you think about incentives. Own the shape: auth, error contract, telemetry, resilience defaults, health checks, all in a versioned package with a single entry point and a rollout mechanism. Do not own per-service values: timeouts, cache TTLs, rate limits, business middleware. And make the package escapable in the middle — teams must be able to insert their own middleware without forking, or they will fork.

Trade-offs to name unprompted: centralisation buys you the ability to ship a security fix once instead of forty times, and costs you the ability to move fast on any service whose needs differ; a shared package becomes a bottleneck if its release cadence is slower than its consumers need, so it must ship weekly and be adoptable independently; enforcement has to be automatic (analyzers, startup self-checks, readiness gates) because review does not scale; and the failure mode to watch for is the platform team becoming an approval queue, at which point teams route around it and the standard silently dies.

Async everywhere, or is sync sometimes right? senior

What a strong answer demonstrates: that you know what async buys and what it costs. In a web server, async I/O is not about speed — an individual request is usually slightly slower — it is about not holding a thread while waiting, which is what lets a handful of threads serve thousands of concurrent requests. So any request-path I/O must be async. Sync is right for CPU-bound work (an async wrapper around computation just adds a state machine), for genuinely fast local operations, and inside a console tool or a startup path where concurrency does not matter.

Trade-offs to name unprompted: async has a real cost in state machines, allocations and stack traces that are harder to read, and it is viral through the call chain; mixing the two is where the danger is — sync-over-async is the top cause of thread-pool starvation, and there is no safe way to block on an async call in a request path; ValueTask exists to reclaim the allocation on synchronous-completion paths but adds sharp usage rules; and the .NET 11 runtime-async work is aimed exactly at this overhead, which is worth knowing but not yet a production answer on .NET 10.

Multi-tenant: shared database, schema per tenant, or database per tenant? principal

What a strong answer demonstrates: that you tie the decision to isolation requirements, tenant count and operational cost rather than to elegance. Shared schema with a tenant column scales to many tenants cheaply and makes migrations trivial, at the cost of the isolation being enforced by your code — every query, every cache key, every log — which is a security property maintained by discipline. Database per tenant gives real isolation, per-tenant backup, restore and residency, and noisy-neighbour containment, at the cost of migration fan-out, connection-pool pressure and a much heavier operational story. Schema per tenant sits in between and usually inherits the worst of both at scale.

Trade-offs to name unprompted: with a shared schema the defence must be structural — EF global query filters, a tenant in every cache key, a middleware that fails closed when the tenant is unresolved — because one forgotten WHERE is a breach; with database per tenant, migrations become an orchestration problem and connection pooling gets hard past a few hundred tenants; a hybrid is common and defensible (shared for the long tail, dedicated for enterprise customers who pay for it), but it doubles the code paths, so decide deliberately; and whatever you choose, the tenant boundary should be provable by a test that queries as tenant A and asserts it cannot see tenant B.

You inherit a .NET Framework 4.8 monolith. What is your migration plan? principal

What a strong answer demonstrates: that you sequence by risk and keep the business running. Assess first with the .NET Upgrade Assistant and the API portability analysers to find the blockers that decide feasibility — WCF hosting, WebForms, System.Web dependencies, third-party libraries with no .NET-compatible version, and anything using AppDomains or remoting. Then pick a strategy: lift-and-shift the whole app if the blockers are few (often surprisingly viable, and it delivers the runtime performance and support benefits immediately), or strangler-fig it behind a reverse proxy (YARP) if they are not, extracting routes one at a time into a new ASP.NET Core app while both run side by side.

Trade-offs to name unprompted: a big-bang rewrite is the option that sounds fastest and reliably is not — it freezes feature work, and the new system inherits none of the old one's accumulated bug fixes; the strangler approach costs you a period of running two stacks with duplicated cross-cutting concerns and a shared session/auth story that is genuinely fiddly (data protection keys, cookie compatibility); the strongest argument to management is not modernity but support and hiring — .NET Framework 4.8 is supported as a Windows component but gets no new features, and the runtime performance difference alone often pays for the work in infrastructure; and the sequencing rule that keeps it honest is to migrate the highest-change, lowest-risk components first, so the team gets fast feedback and the plan can be abandoned cheaply if the estimates were wrong.

Exercise 1 — Design a file-upload and processing API: up to 5 GB files, virus scanning, thumbnailing, resumable, 10k uploads/day. senior

Clarifying questions to ask first: Who uploads — browsers, mobile, server-to-server? Must the client see the processed result synchronously, or is "we will notify you" acceptable? What is the retention and residency requirement? Is the 5 GB a hard ceiling or a p99? What happens to a file that fails scanning — quarantine, delete, notify? Is deduplication required? What is the acceptable end-to-end latency for the thumbnail?

Solution outline. Do not stream 5 GB through your API at all: issue a pre-signed URL (S3/Azure Blob) so the client uploads directly to storage, which removes the bandwidth, memory and timeout problem from your service entirely and gives you resumable, chunked upload for free from the storage SDK. Your API's job becomes three small endpoints: request an upload (validate the caller, generate the pre-signed URL and a pending record), confirm completion (or better, react to the storage event), and query status. Processing is an event-driven chain: storage event → queue → scanner worker → on clean, a thumbnail worker → status update and a webhook or SignalR notification to the client. Every step is idempotent and keyed by the blob's identity, because the queue is at-least-once. Store state in a small table (pending / uploaded / scanning / clean / infected / processed / failed) so status is a cheap read and retries are safe. Back-pressure comes from the queue and a bounded worker concurrency; the scanner is likely the slow, expensive step, so it gets its own scaling policy and a concurrency limiter. For the API itself: a strict request size limit on the metadata endpoints, no multipart parsing of large bodies, and MinRequestBodyDataRate left on.

Trade-offs you are expected to name unprompted: pre-signed URLs mean the client talks to storage directly, so you cannot inspect the bytes in flight — validation is post-hoc, and the file exists in a bucket before it is known to be safe (hence a quarantine container and no public read until scanned); event-driven processing makes the result eventually consistent, so the API must expose status and the UI must handle "not ready"; at-least-once delivery means every worker must be idempotent, which is a design constraint not an implementation detail; virus scanning is the throughput bottleneck and the cost centre, so decide whether you scan everything or only what leaves the tenant boundary; and 10k/day is a low rate — the design is driven by file size and failure handling, not by throughput, which is worth saying out loud so the interviewer knows you are not over-engineering.

Exercise 2 — Design the API and runtime shape for a multi-tenant SaaS: 2,000 tenants, strict data isolation, per-tenant rate limits, one deployment. principal

Clarifying questions to ask first: What does "strict isolation" mean contractually — logical separation, separate databases, or separate encryption keys per tenant? Are there residency requirements per tenant? What is the tenant size distribution (2,000 tenants where three are 90% of the traffic is a different problem)? Do tenants get custom domains? Is there any cross-tenant functionality (admin, analytics, marketplace)? What is the per-tenant SLA, and does anyone pay for a better one?

Solution outline. Resolve the tenant once, in early middleware, from the host name, the token claim or the path — and fail closed with a 400 if it cannot be resolved, so nothing downstream ever runs without a tenant. Put the resolved tenant into a scoped ITenantContext, and make isolation structural rather than remembered: EF Core global query filters on every tenant-owned entity, a tenant segment in every cache key, a tenant tag on logs and traces (low cardinality is fine at 2,000), and an integration test that queries as tenant A and asserts tenant B's data is invisible. Data: shared schema with a tenant column for the long tail, with the option to move a large or regulated tenant to its own database behind the same interface — the connection string comes from the tenant record, so the code path is identical. Rate limiting: partition the limiter by tenant with per-tier limits from configuration, and remember the per-replica problem — either divide the budget by replica count or enforce centrally. Noisy neighbours: a concurrency limiter per tenant on expensive endpoints, and separate worker queues so one tenant's bulk import cannot starve everyone's interactive traffic. Operationally, every metric and log carries the tenant, so "is it everyone or one tenant" is answerable in one query.

Trade-offs you are expected to name unprompted: shared-schema isolation is enforced by your code, so it needs structural defences and a test that proves it — this is the point where you should say plainly that one missing filter is a breach, not a bug; per-tenant databases give real isolation and cost you migration fan-out and connection-pool pressure, which is why the hybrid exists; per-tenant rate limits in-process multiply by replica count, so either accept the approximation or add a shared store and pay the latency; tenant as a metric dimension is fine at 2,000 and catastrophic at 200,000, so state the cardinality bound; and a single deployment for all tenants means a bad release affects everyone, which is the argument for canarying by tenant cohort rather than by percentage of requests.

Exercise 3 — Design an idempotent, observable webhook delivery system: 500k events/day, third-party endpoints, at-least-once with ordering per subscription. principal

Clarifying questions to ask first: Is ordering required per subscription, per resource, or not at all? What is the acceptable delivery latency, and the maximum acceptable delay before giving up? Do subscribers verify signatures, and do we need key rotation? Are subscriber endpoints trusted (SSRF risk)? What must be replayable, and for how long? Is there a fan-out ratio (one event to many subscribers)?

Solution outline. Producers write the event and the delivery intent in the same transaction as the business change — a transactional outbox — so an event is never lost and never emitted for a rolled-back change. A relay moves outbox rows onto a queue partitioned by subscription (or by resource id when ordering is per resource), which is what gives you ordering: a partition is consumed by exactly one worker at a time, so retries block that partition rather than reordering it. Delivery is an HttpClient with a strict per-attempt timeout, a signature header (HMAC over the body plus a timestamp, with a key id so keys can rotate), an event id the subscriber can deduplicate on, and a resilience pipeline: jittered exponential backoff over hours, a per-subscription circuit breaker so one dead endpoint stops consuming workers, and a dead-letter store after the retry budget with an operator-visible replay. Guard against the subscriber being hostile or careless: validate and pin the destination (no internal addresses — SSRF), cap response size and time, and never follow redirects. Observability is the deliverable, not an afterthought: per-subscription success rate, latency, retry count, queue depth and breaker state; a delivery log queryable by event id; and a self-service page where a subscriber can see their own failures, because otherwise your support team becomes the debugger for someone else's endpoint.

Trade-offs you are expected to name unprompted: ordering and throughput are in tension — strict per-subscription ordering means one slow subscriber's partition backs up, so decide whether ordering is really required or whether an event sequence number that lets subscribers reorder is enough; at-least-once plus subscriber-side deduplication is the achievable contract, and promising exactly-once to a third party is a promise you cannot keep; long retry windows mean a subscriber that was down for hours gets a burst on recovery, which needs a delivery rate limit per subscription or you become the attacker; the outbox adds write amplification and a relay to operate, which is the price of not losing events; and 500k/day is about six per second on average but will be bursty, so size for the burst and say what the burst multiple is assumed to be.
