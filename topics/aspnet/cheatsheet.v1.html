01Host, startup & configuration

One Program.cs, one WebApplication. Startup.cs has not existed in a template since .NET 6 and is not supported by minimal hosting.

var builder = WebApplication.CreateBuilder(args);   // config + logging + DI, host defaults
builder.Services.AddOpenApi();                       // services go here
builder.Services.AddProblemDetails();

var app = builder.Build();                           // no service registration after this line
if (app.Environment.IsDevelopment()) app.MapOpenApi();
app.UseExceptionHandler();
app.UseHttpsRedirection();
app.UseAuthentication();  app.UseAuthorization();     // order matters, see 04
app.MapGet("/healthz", () => Results.Ok());
app.Run();

02Dependency injection & options

Three lifetimes, one container, and one rule that causes most production DI bugs: never resolve a scoped service from a singleton.

builder.Services.AddSingleton<IClock, SystemClock>();          // one per app
builder.Services.AddScoped<IOrderRepo, SqlOrderRepo>();        // one per request
builder.Services.AddTransient<IPriceCalc, PriceCalc>();        // one per resolve
builder.Services.AddKeyedSingleton<ICache, Redis>("l2");       // .NET 8+
builder.Services.TryAddEnumerable(ServiceDescriptor
    .Singleton<IValidator, EmailValidator>());                 // idempotent multi-registration

// options: bind + validate, and fail at startup rather than at first request
builder.Services.AddOptions<SmtpOptions>()
    .BindConfiguration("Smtp")
    .ValidateDataAnnotations()
    .Validate(o => o.Port > 0, "Port must be set")
    .ValidateOnStart();
Inject a keyed service
public Svc([FromKeyedServices("l2")] ICache cache)
Singleton-safe access to a scoped service
using var scope = sp.CreateScope(); var repo = scope.ServiceProvider.GetRequiredService<IOrderRepo>();
Catch lifetime mistakes early
ValidateScopes / ValidateOnBuild on by default in Development only — turn both on everywhere in CI
Read options
IOptions<T> (singleton snapshot) · IOptionsSnapshot<T> (per request, scoped) · IOptionsMonitor<T> (live + OnChange, singleton-safe)
Post-bind adjustment
services.PostConfigure<T>(o => o.Timeout ??= TimeSpan.FromSeconds(5))
Named options
services.Configure<T>("primary", cfg.GetSection("Primary")) → IOptionsMonitor<T>.Get("primary")
AOT-safe options validation
[OptionsValidator] partial class MyValidator : IValidateOptions<T> source generator, no reflection
Decorate / replace a registration
services.Replace(ServiceDescriptor.Scoped<IX, Fake>()) the integration-test seam via WithWebHostBuilder
Open generics
services.AddScoped(typeof(IRepo<>), typeof(EfRepo<>))
Async disposal
implement IAsyncDisposable; the container awaits it for scoped/transient
Third-party container
builder.Host.UseServiceProviderFactory(new AutofacServiceProviderFactory())
Captive dependency. A singleton that takes DbContext (scoped) in its constructor still starts; it fails at runtime with Cannot consume scoped service … from singleton, or worse, silently pins one DbContext for the process lifetime. ValidateScopes makes it a startup failure.

03Routing & minimal APIs

Minimal APIs are the default for HTTP services (since .NET 6, AOT-capable since 8); controllers remain the right call for heavy filter/model-binder investment and existing MVC estates.

var orders = app.MapGroup("/orders")
                .RequireAuthorization("orders:read")
                .WithTags("Orders")
                .AddEndpointFilter<AuditFilter>();

orders.MapGet("/{id:guid}", async Task<Results<Ok<Order>, NotFound>>
        (Guid id, IOrderRepo repo, CancellationToken ct) =>
    await repo.Find(id, ct) is { } o ? TypedResults.Ok(o) : TypedResults.NotFound());

orders.MapPost("/", (CreateOrder cmd, IOrderRepo repo) => TypedResults.Created($"/orders/{cmd.Id}"))
      .WithName("CreateOrder");

// .NET 10: Server-Sent Events as a first-class result
app.MapGet("/ticks", (CancellationToken ct) =>
    TypedResults.ServerSentEvents(Ticks(ct), eventType: "tick"));

04Middleware pipeline & error handling

The pipeline is ordered, and the order is the bug. Terminal middleware short-circuits; everything registered after it never runs.

app.UseExceptionHandler();          // 1 outermost: catches everything below
app.UseHsts();                      // 2 (production only)
app.UseHttpsRedirection();          // 3
app.UseStaticFiles();               // 4 before auth: static files are public
app.UseRouting();                   // 5 endpoint is selected here
app.UseCors();                      // 6 after routing, before auth
app.UseRateLimiter();               // 7
app.UseAuthentication();            // 8 who
app.UseAuthorization();             // 9 may they  (must be after UseRouting)
app.UseOutputCache();               // 10
app.MapControllers();               // 11 endpoint executes
Inline middleware
app.Use(async (ctx, next) => { …; await next(ctx); })
Terminal middleware
app.Run(async ctx => …) never calls next; nothing after it executes
Branch on a path
app.Map("/admin", b => …) · app.MapWhen(ctx => …, b => …) · UseWhen (re-joins the main pipeline)
Class middleware, singleton-scoped
ctor(RequestDelegate next) + InvokeAsync(HttpContext, IScopedDep) scoped deps go on InvokeAsync, never the ctor
Factory-activated middleware
IMiddleware + AddScoped<MyMiddleware>() + app.UseMiddleware<MyMiddleware>()
RFC 9457 problem details everywhere
builder.Services.AddProblemDetails(); app.UseExceptionHandler(); app.UseStatusCodePages();
Typed exception handler 8
class MyHandler : IExceptionHandler { ValueTask<bool> TryHandleAsync(…) } + AddExceptionHandler<MyHandler>()
new 10 Silence the log for exceptions you handled
ExceptionHandlerOptions.SuppressDiagnosticsCallback .NET 10 also stops logging exceptions an IExceptionHandler handled
Dev-only stack traces
if (env.IsDevelopment()) app.UseDeveloperExceptionPage(); on by default in Development
Behind a proxy / ingress
app.UseForwardedHeaders(new(){ ForwardedHeaders = XForwardedFor | XForwardedProto }) first in the pipeline, and set KnownProxies/KnownNetworks or it is ignored
Request/response size limits
[RequestSizeLimit(n)] · KestrelServerLimits.MaxRequestBodySize (30 MB default) · IHttpMaxRequestBodySizeFeature
Read the body twice
ctx.Request.EnableBuffering() before anything reads it
Cancellation
ctx.RequestAborted → pass the CancellationToken all the way to the DB call
CORS
AddCors(o => o.AddPolicy("api", p => p.WithOrigins("https://app.example").AllowCredentials())) AllowAnyOrigin() + credentials is rejected at runtime

06Authentication, authorization & security

Schemes authenticate, policies authorize. .NET 10 added WebAuthn passkeys to Identity and stopped cookie auth from 302-ing API calls to a login page.

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o => {
        o.Authority = "https://login.example.com";   // fetches JWKS + metadata
        o.Audience  = "orders-api";
        o.TokenValidationParameters.ValidateIssuerSigningKey = true;
    });

builder.Services.AddAuthorizationBuilder()
    .AddPolicy("orders:read", p => p.RequireClaim("scope", "orders.read"))
    .AddPolicy("adult", p => p.AddRequirements(new MinimumAgeRequirement(18)))
    .SetFallbackPolicy(new AuthorizationPolicyBuilder()   // secure by default
        .RequireAuthenticatedUser().Build());

app.MapGet("/orders", …).RequireAuthorization("orders:read");
app.MapGet("/ping", …).AllowAnonymous();
Custom rule
IAuthorizationRequirement + AuthorizationHandler<TReq> registered as singleton
Resource-based check (does this user own this order?)
await IAuthorizationService.AuthorizeAsync(User, order, "owner")
Fallback vs default policy
Fallback applies where no [Authorize] exists; Default is what a bare [Authorize] means
new 10 Passkeys / WebAuthn in Identity
passkey registration + sign-in built into ASP.NET Core Identity and the Blazor Web App template
new 10 APIs get 401, not a login redirect
cookie handler detects API endpoints via IApiEndpointMetadata ([ApiController], minimal APIs, TypedResults, SignalR)
new 10 Auth metrics

07HttpClient & resilience

new HttpClient() in a loop exhausts sockets; a static HttpClient never sees DNS changes. IHttpClientFactory is the only correct answer, and since .NET 8 the retry/circuit-breaker story is first-party.

builder.Services.AddHttpClient<PricingClient>(c => {
        c.BaseAddress = new Uri("https://pricing.internal/");
        c.Timeout = TimeSpan.FromSeconds(10);
    })
    .AddStandardResilienceHandler()        // Microsoft.Extensions.Http.Resilience (Polly v8)
    .SetHandlerLifetime(TimeSpan.FromMinutes(2));

public class PricingClient(HttpClient http) {
    public Task<Price?> Get(string sku, CancellationToken ct) =>
        http.GetFromJsonAsync<Price>($"prices/{sku}", ct);
}
Standard handler contents
rate limiter → total timeout (30s) → retry (3, exp. backoff + jitter) → circuit breaker → per-attempt timeout (10s)
Tune it
.AddStandardResilienceHandler(o => { o.Retry.MaxRetryAttempts = 5; o.CircuitBreaker.FailureRatio = .2; })
Hedging (fan out to a second call)
.AddStandardHedgingHandler()
Named client
AddHttpClient("github", …) → IHttpClientFactory.CreateClient("github")
JSON helpers
GetFromJsonAsync<T> · PostAsJsonAsync · ReadFromJsonAsync<T> · PostAsJsonAsync(…, AppJson.Default.Order) for AOT
Do not buffer a large response
SendAsync(req, HttpCompletionOption.ResponseHeadersRead, ct)
Test seam
inject a fake HttpMessageHandler; .ConfigurePrimaryHttpMessageHandler(() => fake)
HTTP/2 & HTTP/3 client-side
req.Version = HttpVersion.Version30; req.VersionPolicy = RequestVersionOrLower
Connection pool tuning
SocketsHttpHandler { PooledConnectionLifetime, MaxConnectionsPerServer, EnableMultipleHttp2Connections }
gRPC client
services.AddGrpcClient<Greeter.GreeterClient>(o => o.Address = …).AddStandardResilienceHandler()
Outgoing telemetry
the factory emits http.client.request.duration and W3C traceparent automatically
Cookie handling
off by default in the factory pipeline — enable deliberately, it is shared across the pooled handler
Handler lifetime. Typed clients are transient but the underlying handler is pooled for 2 minutes by default. Nothing in a typed client's constructor may hold per-request state, and PooledConnectionLifetime (not the handler lifetime) is what makes a long-lived SocketsHttpHandler re-resolve DNS.

08Caching, data access & background work

HybridCache (GA since .NET 9) is the default answer for read caching: L1 memory + optional L2 distributed, with stampede protection and tag invalidation you would otherwise hand-roll.

builder.Services.AddHybridCache(o => o.DefaultEntryOptions = new() {
    Expiration = TimeSpan.FromMinutes(10),        // L2
    LocalCacheExpiration = TimeSpan.FromMinutes(1)// L1
});
builder.Services.AddStackExchangeRedisCache(o => o.Configuration = cs);  // becomes L2

var order = await cache.GetOrCreateAsync(
    $"order:{id}",
    (id, repo),
    static (s, ct) => s.repo.FindAsync(s.id, ct),   // static lambda + state = no closure alloc
    tags: ["orders"], cancellationToken: ct);

await cache.RemoveByTagAsync("orders", ct);

10Runtime, GC & performance

Server GC plus DATAS is the .NET 9+ default for ASP.NET Core; most "we need more memory" incidents are actually a knob that was copied from a .NET 6 project.

GC flavours
Workstation (low latency, small heap) vs Server (one heap + thread per core) — Server is the ASP.NET Core default
DATAS 9
Dynamic Adaptation To Application Sizes — on by default with Server GC; scales heap count to real load. Disable: <GarbageCollectionAdaptationMode>0</GarbageCollectionAdaptationMode>
Container memory limit
DOTNET_GCHeapHardLimitPercent · the GC reads cgroup limits automatically — set the container limit, not the GC knob, first
Tiered compilation / PGO
tiered + dynamic PGO on by default since .NET 8; DOTNET_TieredPGO=0 only to isolate a regression
new 10 Stack allocation
small fixed-size arrays of value and reference types, plus escape analysis for local struct fields and non-escaping delegates, now avoid the heap entirely
new 10 Devirtualisation
array interface methods devirtualise + inline — foreach over IEnumerable<int> backed by an array finally optimises like a for loop
new 10 Code layout & Arm64
block reordering solved as an asymmetric-TSP 3-opt; new Arm64 write barrier cuts GC pauses 8–20%
new 10 AVX10.2
System.Runtime.Intrinsics.X86.Avx10v2 present but JIT support off by default — no shipping hardware yet
Allocation-free string work
ReadOnlySpan<char> · string.Create · ArrayPool<byte>.Shared.Rent/Return · SearchValues<char> 8
Zero-copy pipelines
System.IO.Pipelines: PipeReader/PipeWriter — what Kestrel itself and .NET 10 JSON binding use
Async correctness
ValueTask for hot hits · ConfigureAwait(false) in libraries (no-op in ASP.NET Core, which has no SyncContext) · never .Result / .Wait()
Thread-pool starvation symptom
latency climbs while CPU is idle; ThreadPool.ThreadCount creeping up ~1/s. Cause is nearly always sync-over-async
Publish modes
JIT (default) · ReadyToRun (fast start, bigger) · Native AOT (fastest start, smallest RSS, no reflection/EF-provider dynamics)
Native AOT constraints
no runtime codegen, no unbounded reflection, no Assembly.Load; needs source-generated JSON, CreateSlimBuilder, and rules out MVC/Razor/EF migrations
Trim/AOT warnings as errors
<IsAotCompatible>true</IsAotCompatible> on every library you own
Benchmarking
BenchmarkDotNet + [MemoryDiagnoser]; dotnet run -c Release only — never benchmark a Debug build
11 preview Runtime async
async/await state machines moved into the runtime — less allocation and better stacks; still preview-gated
Trade-off to be able to argue. Native AOT buys ~10–30 ms cold start and a much smaller working set, and costs you reflection-based libraries, dynamic plugins, EF Core migrations and a slower inner loop. For a request-serving API kept warm, ReadyToRun + tiered PGO is usually the better default; AOT earns its keep in scale-to-zero, per-request-billed, or high-density workloads.

14Gotchas & pitfalls

  • Middleware order — UseCors after UseRouting and before UseAuthorization; put UseForwardedHeaders first or every scheme/IP downstream is wrong.
  • UseForwardedHeaders ignored — without KnownProxies or KnownNetworks it silently drops the headers for anything that is not loopback. Symptom: Request.Scheme == "http" behind an HTTPS ingress, giving redirect loops.
  • Captive dependency — a scoped service injected into a singleton. Turn on ValidateScopes/ValidateOnBuild in every environment, not just Development.
  • Sync over async — .Result, .Wait(), GetAwaiter().GetResult() starve the thread pool. Symptom: p99 latency climbing while CPU sits at 20%.
  • Fire and forget — _ = DoWorkAsync() in a request loses the exception and dies at shutdown. Use a channel + BackgroundService, or a real queue.
  • CancellationToken not threaded through — a cancelled request keeps burning a DB connection to the end. Accept CancellationToken ct in every handler and pass it down.
  • HttpClient — new HttpClient() per request exhausts ports (TIME_WAIT); a process-wide static one never picks up DNS changes. IHttpClientFactory or PooledConnectionLifetime.
  • DbContext is not thread-safe — no Task.WhenAll over queries on one context. Symptom: A second operation was started on this context instance.
  • EF tracking in read paths — forgetting AsNoTracking() on list endpoints is the most common "EF is slow" cause, right after N+1 from lazy loading.
  • Migrate() at startup — races across replicas and blocks readiness. Use dotnet ef migrations bundle as a deploy step.
  • IMemoryCache stampede — on a cold key every concurrent request rebuilds the value. HybridCache deduplicates; a plain IMemoryCache does not.
  • Unbounded IMemoryCache — no SizeLimit plus no Size on entries equals a slow OOM. Set both, or use HybridCache.
  • In-memory state on more than one replica — sessions, SignalR groups, rate-limit counters and data-protection keys all need a shared store or the behaviour is per-instance.
  • Data protection keys not persisted — a container restart invalidates every antiforgery token, auth cookie and protected payload. Persist and SetApplicationName.
  • CORS AllowAnyOrigin + AllowCredentials — throws at runtime; the browser also rejects it. Enumerate origins.
  • Serving files with UseStaticFiles before auth — correct and intentional; anything under wwwroot is public. Do not put reports there.
  • Two JSON configurations — ConfigureHttpJsonOptions (minimal APIs) and AddJsonOptions (MVC) are separate; setting one leaves the other on defaults.
  • Custom JsonConverter after .NET 10 — request bodies now arrive via PipeReader, so a converter that ignores Utf8JsonReader.HasValueSequence breaks on large payloads.
  • Interpolated log messages — LogInformation($"user {id}") allocates always and produces no structured field. Use the template overload or [LoggerMessage].
  • Exceptions as flow control — a first-chance exception costs microseconds each and floods diagnostics; a 404 is a return value, not a throw.
  • Health check that touches every dependency — as a liveness probe it turns a Redis blip into a rolling restart. Liveness must be dependency-free.
  • Kestrel body-size limit — 30 MB by default; uploads fail with 413 long before your code sees them.
  • InvariantGlobalization=true — smaller container, but culture-aware comparison and formatting silently change. Fine for an API, dangerous for anything user-facing.
  • Native AOT + reflection — anything doing runtime type discovery (some DI scanners, AutoMapper profiles, EF migrations) fails at publish or at first call, not at build.
  • Environment variable separator — Db:Password only works on Windows; use Db__Password everywhere.
  • Registering services after builder.Build() — throws; and IOptionsSnapshot resolved from a singleton throws too. Use IOptionsMonitor.
