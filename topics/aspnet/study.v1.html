ASP.NET Core & .NET runtime

study · .NET 10 (10.0.11 LTS) · released 2025-11-11

.NET 10 is the current LTS, shipped 2025-11-11 and serviced to November 2028; the servicing build as of today is 10.0.11 (2026-08-11), and .NET 11 (STS) is at Preview 7 ahead of a November 2026 release. The clock everyone is actually watching is 2026-11-10, when both .NET 8 and .NET 9 go out of support on the same day — so "we're on 8, it's LTS" is no longer an answer. The framework story in 10 is consolidation rather than reinvention: built-in OpenAPI now emits 3.1 (and YAML), minimal APIs finally have first-class source-generated validation via AddValidation(), Identity ships WebAuthn passkeys, and cookie auth returns 401/403 instead of a login redirect for endpoints marked as APIs. Assumption stated once: this page treats C# 14 as already known and spends its budget on the framework, the host and the runtime.

01Platform, runtimes and the release train

Start here because every other answer in this interview is version-shaped. "The .NET runtime" is not one thing: it is a family of runtimes that all execute the same IL and the same Base Class Library, but make different trade-offs. CoreCLR is the server/desktop runtime — tiered JIT, generational GC, full reflection, hot reload. Mono is the mobile/browser runtime used by .NET MAUI and Blazor WebAssembly (with an AOT-to-WASM mode). NativeAOT is not a runtime you pick at deployment time so much as a compilation model: ILC ahead-of-time compiles your app plus a cut-down runtime (still with a GC, still with the type system) into one native executable with no JIT at all. The mental model that carries you: one BCL, three execution strategies, and your TFM (net10.0) picks the API surface while the RID (linux-x64, win-arm64) picks the machine.

The release train is a calendar, not a surprise. Every November a major ships. Even-numbered releases are LTS (3 years), odd-numbered are STS (originally 18 months). .NET 10 shipped 2025-11-11 as LTS and is supported to November 2028. The recent change worth naming in an interview: Microsoft extended STS from 18 to 24 months, which moved .NET 9's end of support from 2026-05-12 to 2026-11-10 — the same day .NET 8 LTS expires. So on 2026-11-10 two of the three shipped generations die at once, and .NET 11 (STS, November 2026) lands within days of it. If you are advising a team today, the answer is "go to 10, it is the only version with runway."

Patching matters too. Servicing releases go out on Patch Tuesday; today's is 10.0.11 (2026-08-11). Patch level is a runtime concern, not a recompile concern: a framework-dependent app rolls forward automatically to the highest installed patch of the same major/minor (Microsoft.NETCore.App roll-forward policy latestPatch by default). It will not roll forward across a major version unless you say so — which is why a container built FROM mcr.microsoft.com/dotnet/aspnet:8.0 keeps running 8.0 forever until someone edits the Dockerfile.

The one legacy fact you must have straight

.NET Framework 4.8.1 is Windows-only, still supported as a Windows component, and is not going to get new features. Migration off it is the single most common "legacy reality" question. The route is: retarget to net10.0, replace System.Web (HttpContext, HttpModules, WebForms) with ASP.NET Core equivalents, replace web.config/ConfigurationManager with the configuration system (unit 03), replace global.asax with the host (unit 02), and use the .NET Upgrade Assistant plus Microsoft.Windows.Compatibility for the Windows-only APIs. WCF server-side has no in-box successor: you go to gRPC, to CoreWCF, or to plain HTTP. WebForms has none at all.

.NET 10's SDK also made file-based apps a real thing: dotnet run app.cs executes a single C# file with no project, and in .NET 10 those files can be dotnet published — including to NativeAOT. Directives live in the file (#:package Humanizer@2.14.1, #:sdk Microsoft.NET.Sdk.Web). Alongside it, dotnet tool exec and the new dnx script run a tool without installing it — the .NET answer to npx. Small features, but they are exactly the "are you current?" signal an interviewer is fishing for.

Interview trap

"LTS means stable, so we stay on 8." Two things are wrong. First, LTS is a support promise, not a quality one — 10.0.11 has had eleven rounds of fixes that 8.0 also got, and the security patches are simultaneous. Second, as of 2026-11-10 .NET 8 and .NET 9 both stop receiving security fixes, so "we're LTS" buys you two months, not two years. The other half of the trap is claiming .NET Framework 4.8 is "unsupported" — it is not; it ships with Windows and is supported for the life of the OS. It is frozen. Say frozen, not dead: interviewers listen for that precision.

For the publish comparison: framework-dependent output is ~200 KB of your code against a shared 70 MB runtime; NativeAOT is a single ~10–15 MB binary, roughly 3–6× lower RSS, and first response in single-digit milliseconds instead of ~100 ms. If AOT publish fails, the warnings will name reflection-based code — usually a JSON serializer without a source-generated context (unit 08).

Interview Q&A

What is the difference between .NET Standard, a target framework moniker, and a runtime identifier?

.NET Standard was a versioned API contract that let one library run on .NET Framework, Xamarin and .NET Core; it is effectively legacy — you only target netstandard2.0 today when you must be consumable from .NET Framework. A TFM like net10.0 says "these APIs, this BCL"; net10.0-windows adds an OS-specific surface. A RID like linux-musl-arm64 says "this machine", and only matters for self-contained or AOT publishes and for native asset selection. The practical rule I give teams: application projects target the current TFM, shared libraries target the lowest TFM their consumers actually need, and nobody writes netstandard2.0 in a new solution unless a .NET Framework consumer exists.

Framework-dependent or self-contained deployment — how do you decide?

Framework-dependent means the machine or base image supplies Microsoft.NETCore.App, so your artifact is tiny and patching the runtime is someone else's job — you rebase the image and you get 10.0.11. Self-contained bundles the runtime, so you own patching forever, and a runtime CVE means rebuilding and redeploying every app. I default to framework-dependent in containers and on managed platforms, because the patch story is the whole argument. Self-contained wins when you cannot control the target machine (desktop tools, appliances, air-gapped installs) or when you want AOT, which is self-contained by definition. The mistake is choosing self-contained "for isolation" in Kubernetes, where the base image already gives you that.

Your team is on .NET 8 in September 2026. What do you do?

Move to .NET 10 now, and treat 2026-11-10 as a hard deadline rather than a target, because both 8 and 9 lose security servicing that day. Practically: bump the TFM, run the analyzers and let the obsoletion warnings drive the work, re-baseline performance because the GC behaves differently (DATAS with Server GC), and re-test anything that touches JSON, since .NET 10's stricter serializer options and PipeReader-based deserialization change edge cases. Sequence it as one PR per service with the container base image bumped in the same commit so runtime and framework never disagree. If a service genuinely cannot move, the only honest options are a paid extended-support arrangement or accepting documented risk with compensating controls — not silence.

What does "roll-forward" mean and when has it bitten you?

Roll-forward is the host's policy for picking an installed runtime when the exact one your app was built against is absent. The default, latestPatch, means a 10.0.0 app happily runs on 10.0.11 — good, because it is how security patches reach you. It will not cross a minor or major boundary by default, so an app built on 10.0 will refuse to start on a machine that only has 11.0 installed with the classic "framework 'Microsoft.NETCore.App' version '10.0.0' was not found" message. The bite is usually a slim container image that has the ASP.NET runtime but not the desktop or a mismatched minor; the fix is either installing the right runtime or setting rollForward deliberately, never blindly to latestMajor, which silently runs your app on an untested runtime.

When is Blazor WebAssembly the wrong choice, and what do you use instead?

Blazor WebAssembly pays a download and a startup cost — the Mono runtime plus your assemblies — and runs on a single browser thread, so it is wrong for public, SEO-sensitive, first-paint-sensitive pages and for anything CPU-heavy. Blazor Web Apps in .NET 8+ let you mix: static server rendering for the public shell, server interactivity (a SignalR circuit) for latency-tolerant internal screens, WebAssembly only for the components that genuinely need offline or zero-latency interaction. .NET 10 narrowed the gap with fingerprinted, preloaded framework assets and boot config inlined into dotnet.js, and .NET 11 previews add auto-pausing idle circuits, which fixes Server mode's per-user memory cost. The lead-level framing: choose render mode per component, not per application.

What is a servicing release allowed to change?

Patches carry security fixes, functional regressions and, occasionally, targeted performance fixes — never new public APIs and never intentional behaviour breaks. That is why latestPatch roll-forward is safe by default and why the Docker tags 10.0 and 10.0.11 mean different things: the floating tag gets the fixes, the pinned one does not. In practice I pin the digest for reproducibility in the release pipeline but rebuild against the floating tag on a schedule, so we get patched deliberately rather than accidentally. The place people get hurt is pinning 10.0.0 in a Dockerfile and never touching it again.

What actually runs when a .NET app starts?

The apphost (a native shim named after your app) locates hostfxr, which reads runtimeconfig.json, resolves the framework and roll-forward policy, and loads hostpolicy, which reads deps.json to build the assembly probe list and starts CoreCLR. CoreCLR initialises the GC (heap count, Server vs Workstation, DATAS), sets up the default AssemblyLoadContext, and JITs Main at tier 0. NativeAOT removes essentially all of it: there is no hostfxr, no deps.json probing, no JIT — just an executable whose entry point starts the pre-built runtime. Knowing this chain is what lets you debug "it works on my machine but the container exits with code 150."

How do you keep a large solution's dependency versions coherent?

Directory.Build.props for shared MSBuild properties (TFM, nullable, warnings-as-errors, deterministic builds) and Central Package Management via Directory.Packages.props with ManagePackageVersionsCentrally, so a version appears exactly once in the repository. Add NuGetAudit (on by default since .NET 8) to fail builds on known-vulnerable transitive packages, and a lock file if you need reproducible restores. The failure mode without this is diamond dependencies resolving differently per project and a runtime MissingMethodException that only reproduces in one service. It is also the mechanism that makes a framework upgrade a five-line diff instead of a hundred.

Explain what changed for you between .NET Framework's request model and ASP.NET Core's.

In .NET Framework, IIS owned the process, HttpContext.Current was ambient and thread-static, config came from web.config and lived in ConfigurationManager, and the pipeline was HttpModules and HttpHandlers wired in XML. In ASP.NET Core, your process owns itself (Kestrel is in-process), HttpContext is passed explicitly and there is no synchronisation context, config is a layered provider system bound to options objects, and the pipeline is composed in code as middleware. The consequences interviewers probe: ConfigureAwait(false) stopped mattering in app code because there is no SynchronizationContext to capture, static mutable state that used to be per-request is now shared and dangerous, and "restart the app pool" became "restart the process".

How would you introduce .NET 10 to a team that is nervous about upgrading?

Make the risk observable before you make the change. I pick the lowest-traffic service, upgrade it behind the existing canary, and put three dashboards side by side: p99 latency, working set, and GC pause time — the three things .NET 10 actually shifts, because DATAS changes the memory profile noticeably. Then I run the same load test on both versions and let the numbers, not my opinion, argue. In parallel I turn on TreatWarningsAsErrors for the obsoletion diagnostics so the migration surface is enumerated rather than discovered. The organisational half matters more than the technical half: the deadline (2026-11-10) is a fact I can point at, and one successful low-stakes upgrade converts more skeptics than any deck.

02The host, startup and application lifetime

Everything in a modern .NET app hangs off the Generic Host: a container plus a configuration system plus a set of IHostedServices, with a defined start and stop protocol. WebApplicationBuilder (the "minimal hosting model", .NET 6+) is that host with the web bits pre-wired. The mental model that unlocks the whole area: an ASP.NET Core app is a console app whose long-running background service happens to be a web server. Kestrel is registered as GenericWebHostService, an IHostedService like any other — which is exactly why a background worker and a web API can live in the same process, and why the shutdown story is identical for both.

The lifecycle has two halves, and the split is where the bugs live. Build time is everything before builder.Build(): you add configuration sources and register services into an IServiceCollection. After Build(), the collection is frozen — the container is built and app.Services is real. Run time is composing the middleware pipeline on the WebApplication and then app.Run(), which starts every hosted service in registration order and blocks until shutdown is requested. Registration order is start order; stop order is the reverse. That reversal is the answer to "how do I make sure my message consumer drains before the database connection pool disposes."

var builder = WebApplication.CreateBuilder(args);

builder.Configuration.AddJsonFile("appsettings.Local.json", optional: true);
builder.Services.AddOpenApi();                       // built-in since .NET 9

builder.Services.AddDbContextPool<AppDb>(o => o.UseNpgsql(builder.Configuration.GetConnectionString("Db")));

app.MapOpenApi();

Graceful shutdown is the part candidates hand-wave and interviewers care about. On SIGTERM (or Ctrl+C, or IIS recycle) the host triggers IHostApplicationLifetime.ApplicationStopping, stops accepting new connections, and gives in-flight requests HostOptions.ShutdownTimeout — 30 seconds by default — to finish. Hosted services get StopAsync with a token that is already cancelled once that timeout expires. In Kubernetes this interacts with the readiness probe: you want the pod marked unready first so the load balancer stops sending traffic, then SIGTERM, then drain — and terminationGracePeriodSeconds must exceed ShutdownTimeout, or the kubelet SIGKILLs you mid-drain.

// A hosted service that actually shuts down correctly
public sealed class OutboxPublisher(IServiceScopeFactory scopes, ILogger<OutboxPublisher> log)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stopping)
    {
        // await Task.Yield() first if the loop's first phase is synchronous and slow:
        // ExecuteAsync runs inline during StartAsync until its first true await.
        while (!stopping.IsCancellationRequested)
        {
            using var scope = scopes.CreateScope();       // singleton -> scoped bridge
            var db = scope.ServiceProvider.GetRequiredService<AppDb>();
            try { await PublishBatchAsync(db, stopping); }
            catch (OperationCanceledException) when (stopping.IsCancellationRequested) { break; }
            catch (Exception ex) { log.LogError(ex, "outbox batch failed"); }   // never let it escape
            await Task.Delay(TimeSpan.FromSeconds(5), stopping);
        }
    }
}

Interview trap

Two classics. First: injecting a scoped service (a DbContext, anything per-request) into a hosted service or any singleton. It compiles under the default container only if you disable scope validation; otherwise Build() throws — and if you got past it, you now have one DbContext shared across threads for the life of the process. Always take IServiceScopeFactory and create a scope per unit of work. Second: assuming BackgroundService.ExecuteAsync runs on a background thread. It runs inline on the startup path until its first genuine await, so a synchronous 10-second warm-up in there delays the server binding its ports — and your readiness probe. The tell that a candidate has actually run this in production is mentioning await Task.Yield() or Task.Run for the pre-await work.

Try it

1. Register three hosted services that log in StartAsync and StopAsync, run the app, press Ctrl+C, and record the order of both sets of log lines.
2. Break it on purpose: make one service's StopAsync take 40 seconds while ShutdownTimeout is the default 30, and observe what the host does.

Solution sketch

Start order is registration order; stop order is exactly reversed — that is the mechanism you rely on when a consumer must drain before its dependencies go away. In the second experiment the host does not wait: after 30 seconds it logs a warning that hosted services failed to stop within the timeout and continues exiting, so anything after the 30-second mark in StopAsync simply never happens. Fix it by shortening the drain, or by raising HostOptions.ShutdownTimeout and the platform's grace period together — raising only one of the two just moves which layer kills you.

Interview Q&A

Walk me through what WebApplication.CreateBuilder(args) gives you for free.

It builds the configuration stack — appsettings.json, appsettings.{Environment}.json, user secrets in Development, environment variables, then command-line args, in that precedence order — sets the content root and environment from DOTNET_ENVIRONMENT/ASPNETCORE_ENVIRONMENT, wires logging providers (Console, Debug, EventSource, plus EventLog on Windows), enables scope validation and validate-on-build in Development, registers Kestrel with its configuration section bound, and adds routing, host filtering and IIS integration where relevant. Knowing the precedence order is the practically useful bit, because "why is my connection string not the one in appsettings" is nearly always an environment variable winning. The rest matters because CreateSlimBuilder and CreateEmptyBuilder exist precisely to drop parts of it for AOT and size-sensitive apps.

How do you run database migrations at startup, and should you?

Mechanically: after Build(), create a scope from app.Services, resolve the DbContext, call Database.MigrateAsync(), or do the same inside an IHostedService.StartAsync so it happens before traffic. Architecturally I usually argue against it beyond small systems, because with N replicas you get N concurrent migrations racing, a failed migration turns into a crash-loop rather than a clear pipeline failure, and the app then needs DDL permissions it should not hold in production. The pattern I default to is a separate migration job in the deployment pipeline that runs to completion before the new pods roll, with the app asserting on startup that the schema version matches and refusing to serve if it does not. If you must migrate in-process, take a database advisory lock so only one replica runs it.

What is the difference between IHostedService and BackgroundService?

IHostedService is the interface: StartAsync and StopAsync, both called by the host, both expected to return quickly. BackgroundService is an abstract base that implements it for the common "loop forever" case by calling your ExecuteAsync from StartAsync and storing the returned task so StopAsync can cancel and await it. The subtlety worth stating: since .NET 6 an unhandled exception in ExecuteAsync stops the entire host by default (BackgroundServiceExceptionBehavior.StopHost) — before that it was silently swallowed, which produced the classic "our consumer stopped consuming and nobody noticed" incident. I keep the default and catch deliberately inside the loop, so a transient failure retries but a genuine misconfiguration crashes loudly.

How do you make a component participate in graceful shutdown correctly?

Take the CancellationToken the host hands you and thread it into every await; never pass CancellationToken.None to hide a warning. Distinguish two phases: on ApplicationStopping you should stop accepting new work (deregister from the queue, fail the readiness probe), and only then drain. For an HTTP request, HttpContext.RequestAborted fires when the client disconnects and is what you propagate into the database call, so a cancelled request stops burning a connection. The end-to-end version of the answer includes the platform: readiness off, a few seconds of lame-duck so proxies notice, SIGTERM, drain under ShutdownTimeout, with terminationGracePeriodSeconds comfortably larger.

Why would you still use a Startup class in 2026?

Because it is a named, reusable composition unit. Integration tests with WebApplicationFactory want to swap a handful of registrations, and having ConfigureServices as a method you can subclass or call from a test-specific host is genuinely tidier than re-running a 200-line Program.cs. It also gives you a natural seam for multi-tenant or per-SKU composition. What I would not do is convert working minimal-hosting code back to it, or convert working Startup code forward for tidiness — both are churn. The modern middle ground is minimal hosting plus extension methods (builder.AddPersistence(), builder.AddMessaging()) so Program.cs stays a readable table of contents.

How do you fail fast on bad configuration at startup?

Bind options with ValidateDataAnnotations() and ValidateOnStart(), which moves the failure from the first request that touches the option to the moment the host starts — so a bad deploy fails the readiness probe instead of returning 500s. For cross-field rules use Validate(o => ...) or an IValidateOptions<T>. I also turn on ValidateOnBuild and ValidateScopes in every environment, not just Development, because the cost is a few milliseconds at startup and the payoff is catching a captive dependency before it reaches production. The principle: a process that cannot possibly work should never reach the "ready" state.

What happens to in-flight requests during a rolling deployment?

The correct sequence is: the new pod becomes ready, the old pod's readiness probe starts failing, the proxy or service mesh stops routing to it, the platform sends SIGTERM, ASP.NET Core stops accepting new connections while letting existing ones complete within ShutdownTimeout, and then the process exits. Two things break it in practice. Load balancers cache endpoints, so without a lame-duck delay between "unready" and SIGTERM you drop requests that were already in flight to the old pod. And keep-alive connections mean a client can be pinned to a dying instance; Kestrel handles this by sending Connection: close during drain, but long-lived streams — WebSockets, SSE, gRPC streaming — need application-level handling, because a 30-second drain will not save a 30-minute stream.

How do you host a web API and a worker in the same process, and should you?

Mechanically it is trivial: AddHostedService next to your endpoints, since Kestrel is itself a hosted service. The reason to do it is operational simplicity — one deployable, one config, one set of dashboards — and it is right for small systems and for a worker that is genuinely an implementation detail of the API, like an outbox publisher. The reason not to is that the two have different scaling curves and different failure modes: you cannot scale the API for request volume without also multiplying your consumers, and a runaway background job now degrades request latency in the same thread pool. My rule is that they share a process until either one needs independent scaling or independent deployment cadence, and then they split — with the code already structured so splitting is a project-file change, not a rewrite.

What is the request scope, exactly, and when does it end?

ASP.NET Core creates an IServiceScope per request before the pipeline runs and disposes it after the response completes; HttpContext.RequestServices is that scope's provider. Everything registered scoped resolves once per request and is disposed at the end, which is why DbContext change tracking is per-request. The edges are what get asked about: work you fire off with Task.Run inside a request outlives the scope and will hit ObjectDisposedException on the DbContext; SignalR hub method invocations get their own scope per invocation, not per connection; and a middleware that resolves scoped services in its constructor captures the first request's scope forever, which is why middleware constructors take singletons and method parameters take the scoped ones.

How do you structure Program.cs in a large service so it stays reviewable?

Treat it as a table of contents, not an implementation. Each feature area exposes one extension method — builder.AddPersistence(), builder.AddAuthN(), app.MapCatalogEndpoints() — living beside the code it configures, so Program.cs is thirty lines that a reviewer can read top to bottom and see the pipeline order. The pipeline half must stay literal and in one place, because middleware order is semantics and hiding it behind helpers is how UseAuthorization ends up before UseAuthentication. I also insist on ValidateOnStart for every options type registered in those helpers, so the composition is self-checking. When it grows past that, the answer is usually a second process, not a cleverer Program.cs.

03Configuration and the options pattern

Configuration in ASP.NET Core is a layered key–value store, and once you see it as exactly that, every surprising behaviour becomes obvious. Each IConfigurationProvider contributes a flat dictionary of string keys to string values; hierarchy is encoded with : (Logging:LogLevel:Default); providers are queried in reverse registration order so last one wins; and arrays are just keys with numeric segments (Cors:Origins:0). Environment variables use __ instead of : because : is illegal in variable names on Linux — that single fact explains most "my Kubernetes config isn't applying" tickets.

The default stack from CreateBuilder, lowest precedence first: appsettings.json → appsettings.{Environment}.json → user secrets (Development only) → environment variables → command-line arguments. Anything you add later wins over all of them. Note what is not in the list: nothing encrypted, nothing remote. Key Vault, App Configuration, Consul and friends are additional providers you add explicitly, and each brings a question the interview will ask — what happens if it is unreachable at startup, and what happens when a value changes at runtime.

Reading IConfiguration directly in business code is the anti-pattern; the options pattern is the cure. You bind a section to a POCO once, validate it once, and inject a strongly-typed object. The three interfaces are not interchangeable and the distinction is a reliable interview question:

Reload is the other half. The JSON provider watches the file (reloadOnChange: true by default from CreateBuilder) and raises a change token; IOptionsMonitor and IOptionsSnapshot ride that token, IOptions does not. Environment variables and command-line args never reload — the process would have to restart. In containers this is why a mounted ConfigMap can hot-reload but a env: value cannot, and why the honest default for most teams is "config changes mean a rollout", with hot reload reserved for genuinely dynamic knobs like log levels and feature flags. Note also the historical footgun: reloadOnChange uses a file watcher, and on some mounted filesystems it either fires twice or not at all, so validate it in your environment rather than trusting it.

For secrets, the ladder is: dotnet user-secrets in development (stored outside the repo in the user profile, so it cannot be committed), the platform's secret store in production (Key Vault, AWS Secrets Manager, Kubernetes secrets projected as files), and never appsettings.Production.json. Adding Azure.Extensions.AspNetCore.Configuration.Secrets or the AWS equivalent makes them ordinary configuration keys, so PaymentsOptions.ApiKey binds identically in both worlds — which is the actual point of the abstraction.

Interview trap

Injecting IOptionsSnapshot<T> into a singleton. It is scoped, so the container either refuses (scope validation on) or hands the singleton the very first request's scope, and you have a captive dependency that never updates and holds a scope alive forever. The rule is mechanical: singletons and hosted services take IOptionsMonitor<T> and read CurrentValue at point of use; request-scoped code can take IOptionsSnapshot<T>. The second trap in the same family is caching opts.CurrentValue in a field at construction — that silently converts your monitor back into an IOptions, and the reload you demoed in the sprint review will not work in production.

Interview Q&A

Give me the precedence order of the default configuration providers, and why it is that order.

Base appsettings.json, then appsettings.{Environment}.json, then user secrets in Development, then environment variables, then command-line arguments — each overriding the previous. The order encodes "more specific to this execution wins": a file checked into the repo is the least specific thing anyone knows, and a flag typed at launch is the most. It also means the mechanism you use to override in production (environment variables) always beats anything a developer committed, which is the safety property you want. The corollary I mention in reviews: because environment variables win, a stray ConnectionStrings__Db left in a deployment manifest silently overrides everything and is invisible in the repo, so config diffs must include the platform manifests.

IOptions, IOptionsSnapshot, IOptionsMonitor — when do you reach for each?

IOptions<T> for values that genuinely cannot change while the process runs — a database provider choice, a feature that shapes the object graph at startup — because it is a singleton computed once and cheapest to consume. IOptionsSnapshot<T> for request-scoped code that wants a consistent view for the duration of one request, which also gives you per-request named options in multi-tenant scenarios. IOptionsMonitor<T> for singletons and background services that must observe changes, either by reading CurrentValue each time or by subscribing with OnChange. The trap is lifetime mismatch, and the second-order trap is that OnChange can fire twice for one file save because of how file watchers behave, so the callback must be idempotent.

How do you handle secrets across development and production without two code paths?

Keep the shape identical — one options class, one section name — and vary only which provider supplies the values. Development uses dotnet user-secrets, which stores JSON in the user profile keyed by a UserSecretsId in the csproj, so it is physically impossible to commit. Production adds the platform provider (Key Vault, Secrets Manager, or files projected from a Kubernetes secret via AddKeyPerFile), registered only when the relevant configuration is present. Two operational details separate a senior answer: decide explicitly whether a secret-store outage at startup should be fatal (usually yes — better to fail readiness than serve with stale credentials), and plan for rotation, which means the app must re-read the secret rather than capture it in a singleton at construction.

What breaks when configuration keys come from environment variables in a container?

The separator: Logging:LogLevel:Default becomes Logging__LogLevel__Default, because colons are not valid in environment variable names on Linux. Arrays are index-keyed, so Cors__Origins__0 and Cors__Origins__1, and — the part that surprises people — providing an array in an environment variable does not replace the JSON array, it merges key by key, so leftover higher indices from the file survive. Values are always strings, so a boolean must be true/false and a bad value produces a binding exception rather than a default. Finally, prefixed providers (AddEnvironmentVariables("MYAPP_")) strip the prefix, which is worth using in shared hosts to avoid collisions with unrelated variables.

How do you do feature flags properly?

A flag is configuration with an evaluation context, so I model it as such rather than as a boolean in appsettings. Microsoft.FeatureManagement gives you IFeatureManager, filters (percentage, targeting, time window) and [FeatureGate] on endpoints, and it rides the configuration change tokens so a backing store like Azure App Configuration can flip a flag without a deploy. The engineering discipline matters more than the library: every flag gets an owner and a removal date, flags are evaluated once per request and passed down rather than sampled repeatedly (so behaviour cannot change mid-request), and flags that gate schema-affecting behaviour need both code paths tested in CI. Long-lived flags are technical debt with a nice name.

Someone puts IConfiguration into a domain service. What do you say in review?

That it turns a typed dependency into a stringly-typed one and moves failure from startup to runtime. The service now depends on the whole configuration tree, so its unit tests need a configuration builder instead of a plain object; a typo in "Payments:TimeoutSecnods" compiles, returns null, and silently becomes a default; and nothing validates the value. The fix is a bound options class with validation, injected as IOptions/IOptionsMonitor. I do accept IConfiguration in composition code — inside Program.cs or a registration extension — because that is the place whose job is reading configuration.

How would you support per-tenant configuration?

Named options: register with AddOptions<T>("tenant-a"), or implement IConfigureNamedOptions<T> to compute a tenant's options on demand, then resolve through IOptionsSnapshot<T>.Get(tenantId) in request scope so each request sees its own tenant's values. Resolution of the tenant itself belongs in middleware that sets a scoped ITenantContext from host header, path segment or a claim. Two failure modes to design against: the options cache is keyed by name and lives in a singleton, so a tenant added at runtime needs a change token or a cache eviction to appear; and anything that caches per-tenant state (an HttpClient, a connection pool) must be keyed by tenant too, or tenant A's credentials leak into tenant B's calls. Keyed DI services (.NET 8) make that keying explicit rather than a dictionary in a singleton.

Can you change configuration at runtime without a restart, and should you?

You can for file-based and remote providers that publish change tokens: the provider reloads, IOptionsMonitor recomputes, and consumers that read CurrentValue at point of use pick it up. You cannot for environment variables or command-line args. Whether you should depends on blast radius. Log levels, sampling rates and feature flags are ideal — they are reversible and observable. Connection strings, authentication settings and anything that shapes the DI graph are not, because half the object graph captured the old value at construction and you end up with a process in a state no test ever covered. The rule I hold teams to: hot-reloadable configuration is an explicit, documented subset, and everything else means a rollout.

How do you keep configuration honest across a dozen microservices?

Shared options classes in a small internal package, so the shape of "how we configure a database" or "how we configure outbound HTTP" is written once and validated identically everywhere. A single naming convention for sections and environment variables, enforced by a CI check that starts each service with the production-shaped configuration and asserts ValidateOnStart passes. Drift detection matters more than documentation: a job that diffs the effective configuration of each running service against the expected schema catches the ConfigMap someone hand-edited in a hurry. And schema before secrets — the biggest wins come from every service failing loudly when a required key is missing, not from a fancier store.

What does IConfiguration.GetValue<T> do when the key is missing versus present but unparseable?

Missing returns default(T) (or the default you supply) silently — no exception, which is exactly why it is dangerous in business code. Present but unparseable throws InvalidOperationException from the type converter. Binding a whole section with Bind/Get<T> behaves the same way per property, and by default it ignores unknown keys in configuration and leaves unmatched properties at their defaults, so a typo in a key name is invisible. Two switches address that: BinderOptions.ErrorOnUnknownConfiguration = true makes stray keys fail, and ValidateDataAnnotations().ValidateOnStart() makes missing required values fail at boot. In AOT and trimmed apps the source-generated configuration binder replaces the reflection-based one, which also surfaces binding problems at compile time.

04Dependency injection and object lifetimes

The built-in container (Microsoft.Extensions.DependencyInjection) is deliberately small: constructor injection, three lifetimes, no property injection, no interception, no auto-registration. That minimalism is a design decision — it is the abstraction every library in the ecosystem targets, so third-party containers plug in underneath rather than replacing the API. The mental model: IServiceCollection is a list of ServiceDescriptors (service type, implementation, lifetime) that gets compiled into a provider at Build(); from then on it is immutable, and resolution is a cached factory lookup, not reflection per call.

Three lifetimes, and the only two rules you need to derive the rest: Transient — a new instance per resolution. Scoped — one per IServiceScope, which in ASP.NET Core means one per HTTP request (and one per SignalR hub invocation, and one per whatever you create manually). Singleton — one per container, for the process lifetime. Rule one: a service may only depend on services with an equal or longer lifetime; violating it gives you a captive dependency. Rule two: the container disposes what it created, at the end of the owning scope — so a transient IDisposable resolved from the root provider is never disposed until the process exits, which is a real memory leak with a real name.

builder.Services.AddScoped<IUnitOfWork, EfUnitOfWork>();       // per request

Two behaviours catch experienced people out. First, registering the same service type twice is not an error: GetRequiredService<T> returns the last registration, while GetServices<T> returns all of them in registration order. That is how IEnumerable<T> injection works and why TryAddEnumerable exists (plain Add in a library called twice gives you two copies of the same validator). Second, an implementation registered twice under two interfaces gives you two instances unless you forward: AddSingleton<IA, Impl>() plus AddSingleton<IB, Impl>() creates two Impls. Register the concrete type once and forward both interfaces to it with a factory.

Interview trap

"We use IServiceProvider injection so components can resolve what they need." That is service location, and it converts every missing registration from a startup failure into a runtime InvalidOperationException in production, while making the class's real dependencies invisible to both reviewers and tests. The two legitimate uses are factories that must resolve by a runtime key, and bridging from a singleton into a scope via IServiceScopeFactory. The related trap is the "god" constructor with fourteen dependencies: that is not a DI problem, it is a cohesion problem, and adding a facade that takes IServiceProvider hides it rather than fixing it.

Solution sketch

The root provider tracks every disposable it creates so it can dispose them at shutdown, so 100 000 transients means 100 000 live objects — the heap grows and never shrinks. That is the textbook "transient disposable captured by the root scope" leak; resolving from HttpContext.RequestServices instead bounds it to the request. Interview Q&A

Explain a captive dependency and how the framework helps you catch it.

A captive dependency is a longer-lived service holding a reference to a shorter-lived one: a singleton that takes a scoped DbContext captures the first request's instance and then uses it forever, on many threads, with change-tracking state from a request that ended hours ago. The framework catches it because ValidateScopes makes the root provider refuse to resolve scoped services, and ValidateOnBuild walks every registration at Build() and throws for the whole graph — both are on by default in Development from CreateBuilder. I enable both in every environment: a few milliseconds at startup versus a class of bug that only appears under concurrency. The fix is always the same shape — take IServiceScopeFactory and create a scope per unit of work.

When would you replace the built-in container?

Rarely, and only for a capability it deliberately lacks: property injection into types you do not construct, decoration and interception at scale, convention-based registration over many assemblies, or child containers with different registrations per tenant. Autofac and Lamar do those. The cost is real: you now own an adapter that must keep up with framework changes, resolution errors have unfamiliar messages, and startup is measurably slower. Before switching I ask whether Scrutor's Decorate plus keyed services covers 90% of the need — since .NET 8 it usually does. And for NativeAOT the calculus tilts further, because assembly scanning and dynamic proxies are exactly what trimming cannot see.

How do you unit-test something that depends on the current time or a timer?

Inject TimeProvider (.NET 8) rather than calling DateTime.UtcNow, and use its GetUtcNow(), CreateTimer() and the Task.Delay(..., timeProvider)/CancellationTokenSource(..., timeProvider) overloads. In tests, FakeTimeProvider from Microsoft.Extensions.TimeProvider.Testing lets you advance time instantly, so a test for "retry after 30 seconds, three times" runs in microseconds and is deterministic rather than flaky. This is a real upgrade over hand-rolled IClock interfaces, because the framework's own timer-based APIs accept it — your abstraction never could. In review I treat a raw DateTime.Now in domain code the same way I treat a raw new HttpClient().

What are keyed services good for, and where do they go wrong?

They are for one abstraction with several interchangeable implementations selected by data — payment gateways, storage backends, per-tenant clients — replacing hand-written factory dictionaries. Resolution is [FromKeyedServices("x")] for a static key or GetRequiredKeyedService<T>(key) for a dynamic one. Where they go wrong: the dynamic form is service location again, so an unknown key becomes a runtime exception, which means you need validation at the edge that the key is one you registered. They also do not compose with IEnumerable<T> the way people expect — non-keyed resolution does not see keyed registrations at all, and vice versa, so a library that enumerates IEnumerable<IValidator> will silently miss your keyed ones.

How do you register a decorator?

The container has no first-class decoration, so you register the inner type concretely and register the interface to a factory that resolves the inner and wraps it: AddSingleton<IRepo>(sp => new CachingRepo(sp.GetRequiredService<SqlRepo>(), sp.GetRequiredService<HybridCache>())). Scrutor's Decorate<IRepo, CachingRepo>() does the same thing generically by rewriting the existing descriptor. Order matters and is the thing to say out loud: decorators apply outermost-last, so registering caching then logging means logging wraps caching and you will not see cache hits in the log. For cross-cutting concerns that need to apply to every call, I usually prefer an explicit pipeline (endpoint filters, DelegatingHandler) over container decoration, because the ordering is visible in one place.

Singleton or scoped for HttpClient, and why is that the wrong question?

Neither: you inject a typed client and let IHttpClientFactory own the lifetime. A manually constructed long-lived HttpClient caches DNS forever, so a failover never reaches you; a per-request one exhausts sockets because TIME_WAIT holds ports for minutes. The factory splits the two concerns — a short-lived HttpClient wrapping a pooled, rotated HttpMessageHandler (default handler lifetime two minutes) — which fixes both. The modern alternative for a genuinely singleton client is a static SocketsHttpHandler with PooledConnectionLifetime set, which is what the factory does under the hood; that is the answer for a library that must not depend on DI. Details in unit 12.

How do you inject services into middleware, and why is it different?

Convention-based middleware is instantiated once, at pipeline build time, so its constructor can only take singletons — anything scoped injected there is captive for the process lifetime. Scoped dependencies go as extra parameters on InvokeAsync(HttpContext ctx, IMyScoped svc), which the framework resolves from the request scope per call. The alternative is IMiddleware, which is resolved from the container per request, so its constructor can take scoped services — at the cost of registering it explicitly and one resolution per request. I default to convention-based with method injection, and reach for IMiddleware when the middleware itself needs a scoped lifetime or a factory.

What is the performance cost of DI, and when have you had to care?

Almost never at the level people fear: resolution is a compiled factory delegate, so a scoped service is roughly a dictionary lookup plus a constructor call — nanoseconds. The costs that do show up are structural: a deep object graph resolved per request means dozens of allocations per request, which shows in gen0 pressure at high RPS; and a service whose constructor does real work (opening a connection, reading a file) turns into per-request latency. I have had to care exactly twice — once where a scoped validator graph was rebuilt per request and became measurable at ~20k RPS (fixed by making the stateless parts singletons), and once in a NativeAOT app where the reflection fallback dominated startup. The general rule: profile before restructuring, because the DI container is virtually never the bottleneck the middleware chain or the database is.

A colleague wants AddScoped everywhere "to be safe". What is your response?

That "scoped by default" trades one bug class for another. It makes stateless, thread-safe services allocate per request for no benefit, and it quietly forbids them from being used by singletons and hosted services, which is where the friction eventually surfaces as an IServiceScopeFactory sprinkled through the codebase. The honest default is: stateless and thread-safe → singleton; holds per-request state or wraps a per-request resource (DbContext, unit of work, tenant context) → scoped; cheap, short-lived and stateful → transient. What actually keeps you safe is the pair of validations (ValidateScopes, ValidateOnBuild) turned on everywhere, not a blanket lifetime.

How does DI interact with trimming and NativeAOT?

Explicit registrations are fine — the linker sees AddSingleton<IFoo, Foo>() as a normal reference. What breaks is anything reflective: assembly scanning to auto-register by convention, Activator.CreateInstance on a type name from configuration, open-generic registrations resolved via reflection, and libraries that build proxies at runtime. Those produce IL2xxx trim warnings at publish and a MissingMethodException at runtime if you ignore them. The practical approach is to publish with PublishAot in CI from day one so the warnings are enforced, replace scanning with generated or hand-written registration, and prefer source generators (the config binder, the JSON context, the request delegate generator) over the reflection paths. If a dependency fundamentally needs reflection, that dependency decides you are not shipping AOT.

05Kestrel, hosting topology and deployment

Kestrel is a cross-platform, event-driven HTTP server built on System.IO.Pipelines, and since ASP.NET Core 2.1 it has been an edge-capable server, not a "must sit behind IIS" one. Its job is to turn bytes into an HttpContext: it accepts a connection, parses request lines and headers into pooled buffers, hands you a Stream/PipeReader body, and writes the response back without copying more than it must. The design idea that explains most of its behaviour: buffers come from a pool and are returned; headers are parsed lazily; and everything is async so a request waiting on a database occupies zero threads.

Deployment topology is where the interview usually goes. Kestrel can face the internet directly, but a reverse proxy in front (nginx, YARP, Envoy, IIS, Application Gateway, an ingress controller) buys you TLS termination and certificate rotation, request buffering against slow clients, static-file caching, WAF rules and shared ports across apps. On Windows, IIS runs ASP.NET Core in one of two modes: in-process (the default since 2.2 — Kestrel is replaced by IISHttpServer inside the IIS worker process, fastest) and out-of-process (IIS reverse-proxies to a Kestrel on a random localhost port). Knowing which you are in changes how you diagnose things, because in-process means no second hop and no ASPNETCORE_PORT.

Interview trap

UseForwardedHeaders without KnownProxies/KnownNetworks, or placed after the middleware that reads the scheme. Both are security bugs, not style issues: the first lets any client spoof X-Forwarded-For — defeating IP rate limits and poisoning audit logs — and the second means authentication redirects are built with http:// and either break or downgrade. The related trap is RequireHttpsMetadata/HSTS reasoning: with TLS terminated at the proxy, Kestrel genuinely sees plain HTTP, so "we redirect to HTTPS in the app" is either a no-op or a redirect loop unless the forwarded scheme is honoured first. Forwarded-headers middleware goes as early in the pipeline as it can, and it trusts a named set of proxies.

Try it

1. Start an app, then curl -v --http2 https://localhost:5001/ and curl -v --http1.1 ..., and confirm the negotiated protocol in the handshake output; then set Protocols = HttpProtocols.Http2 only, and see what a plain HTTP/1.1 client gets.
2. Break it on purpose: send a request body one byte per second with MinRequestBodyDataRate at its default, and observe when Kestrel gives up.

Expected outcome

Over TLS, HTTP/2 is chosen by ALPN; over plain HTTP the client must do prior-knowledge h2c, which most tools will not, so you fall back to 1.1. Restricting the endpoint to HTTP/2 only makes an HTTP/1.1 client fail at the connection level rather than getting a helpful status code — which is exactly why gRPC endpoints are usually on their own port. The slow-body experiment ends with Kestrel aborting the connection after the five-second grace period once the rate drops below 240 bytes/second; that limit is the built-in Slowloris defence, and turning it off "because a customer has a slow uplink" is a decision to accept a cheap denial-of-service vector.

Interview Q&A

Do you need a reverse proxy in front of Kestrel?

Not for safety — Kestrel has been hardened for edge exposure since 2.1, with header, body-size and data-rate limits on by default. You want one for the things it is better at: terminating TLS and rotating certificates centrally, buffering slow clients so a request occupies your process for milliseconds instead of seconds, serving static assets and caching, WAF and DDoS filtering, and multiplexing many apps onto ports 80/443. In Kubernetes the ingress controller already is that proxy, so adding nginx inside the pod is usually cargo cult. The judgment answer: if you own the edge (an ingress, a CDN, an API gateway) you already have it; if you are on a bare VM facing the internet with one app, Kestrel alone is defensible provided you have set the limits and automated certificate renewal.

What actually happens between the socket accept and your endpoint running?

The transport (sockets, or io_uring/named pipes/QUIC depending on configuration) accepts the connection and hands a duplex Pipe to the HTTP layer. Kestrel parses the request line and headers out of the pipe's buffers — pooled, so no per-request allocation for the common case — builds an HttpContext from pooled objects, and invokes the middleware pipeline's first delegate. Routing matches the endpoint, model binding reads the body from the same pipe, your handler runs, and the response is written back through a PipeWriter that flushes based on backpressure. Understanding the pooling is what makes two rules make sense: never capture HttpContext, Request.Headers or a Span over the body past the end of the request, because those objects are recycled for the next one.

How do you decide between HTTP/2 and HTTP/3 for a service?

HTTP/2 is the default answer for internal service-to-service traffic, because gRPC requires it, multiplexing removes connection churn, and every proxy in the path supports it. HTTP/3 buys you the removal of TCP head-of-line blocking and much faster recovery when the network path changes — genuinely valuable for mobile clients and lossy networks, largely irrelevant inside a data centre where loss is near zero. The costs are real: UDP is blocked or deprioritised on many corporate networks, load balancers and observability tooling lag, and it requires TLS plus msquic on the host. My default is HTTP/1.1 + HTTP/2 on the public edge with HTTP/3 advertised via Alt-Svc where the CDN supports it, and HTTP/2 internally.

Your service's memory climbs after a traffic spike and never comes back. Where do you look?

Three suspects in order. First, Kestrel's memory pool used to keep its high-water mark permanently — .NET 10 added automatic eviction of idle blocks plus a Microsoft.AspNetCore.MemoryPool meter, so on 10 you check the metric and on 8/9 you know it is expected behaviour rather than a leak. Second, the GC: with Server GC the heap grows per core and does not return memory eagerly, which is exactly what DATAS was built to fix, so confirm DATAS is on and compare committed versus used bytes. Third, a genuine leak — static collections, event handler subscriptions, transient disposables held by the root provider, or a cache with no eviction policy. The tool order is dotnet-counters for the shape, then dotnet-gcdump or a full dump for who holds what.

Which Kestrel limits would you set before going to production?

MaxRequestBodySize tightened to what the endpoint actually needs (the 30 MB default is generous, and per-endpoint overrides via [RequestSizeLimit]/IHttpMaxRequestBodySizeFeature are better than one global number), MaxConcurrentConnections and MaxConcurrentUpgradedConnections so an overload sheds rather than swaps, RequestHeadersTimeout and KeepAliveTimeout, and the MinRequestBodyDataRate/MinResponseDataRate pair which I keep at defaults unless a real client needs otherwise. I also turn off AddServerHeader and set MaxRequestLineSize/MaxRequestHeadersTotalSize deliberately if the app takes long URLs or big auth headers, because the default 32 KB header budget is where large JWTs with many claims fail mysteriously. The framing that lands: these are availability controls, and every one of them is the difference between shedding load and falling over.

In-process versus out-of-process IIS hosting — what changes?

In-process (default since 2.2) runs your app inside the IIS worker process with IISHttpServer replacing Kestrel, so there is no localhost hop, throughput is markedly higher, and the process lifetime is IIS's — app pool recycling and idle timeouts apply to you. Out-of-process starts dotnet as a child process with Kestrel on a dynamic port and IIS proxying to it, which costs a hop but isolates you from IIS's process model and lets you use features Kestrel has and IIS does not. The practical differences that bite: in-process you must read ASPNETCORE_ environment variables from web.config's aspNetCore element rather than the machine environment, Windows authentication flows differ, and a stdout log path in web.config is how you diagnose startup failures — the infamous HTTP 500.30/500.31.

How do you handle TLS certificates?

Wherever possible, not in the app: terminate at the ingress, gateway or CDN where rotation is automated and a certificate change does not need a deployment. When Kestrel must do TLS, configure it from the certificate store or a mounted file via the Kestrel:Endpoints configuration section, and use ServerCertificateSelector or UseHttps(o => o.ServerCertificateSelector = ...) so a rotated file is picked up without a restart. In development, dotnet dev-certs https --trust generates and trusts the local certificate, and in .NET 10 that certificate additionally covers *.dev.localhost so multiple apps can each have a real hostname instead of a port. The failure I have seen most is a certificate that expires because renewal was manual — so the answer that matters is "automated renewal with expiry alerting", regardless of where termination happens.

What is YARP and when would you reach for it?

YARP is a reverse proxy as a library — you host it in an ASP.NET Core app and configure routes, clusters, transforms and health checks in configuration or code. It shines when your proxying needs are application-aware: strangler-fig migrations where a path prefix moves from the legacy app to the new one, per-tenant routing based on a claim, request/response transforms you would otherwise write in Lua, or a BFF that also proxies. Where it is the wrong tool: a plain "terminate TLS and round-robin" job that nginx or your cloud load balancer does with no process of yours to operate. The trade-off to name is that YARP is one more .NET process to scale, patch and monitor, and it inherits your runtime's failure modes.

How would you configure this app to run well in Kubernetes?

ASPNETCORE_HTTP_PORTS=8080 on a non-root user, TLS at the ingress, and two distinct probes: liveness that only proves the process is not wedged, readiness that also checks the dependencies you cannot serve without. Requests and limits set from measurement, with the knowledge that .NET reads cgroup limits to size the thread pool and GC heap — so a CPU limit of 500m gives you a very different GC configuration than the node's 32 cores would suggest, and DOTNET_GCHeapHardLimitPercent or DATAS is how you keep the heap inside the memory limit. Graceful shutdown wired end to end: a preStop sleep or readiness flip for lame-duck, then SIGTERM, with terminationGracePeriodSeconds greater than HostOptions.ShutdownTimeout. And structured logs to stdout with the trace id, because in a pod that is your only debugger.

A health check endpoint is returning healthy while the service is broken. How do you fix the design?

Almost always because one endpoint is doing two jobs. Liveness answers "should the orchestrator kill this process?" and must depend on nothing external — if it checks the database, a database blip restarts every pod simultaneously and turns a degradation into an outage. Readiness answers "should traffic come here?" and legitimately checks the dependencies required to serve. So I split them with tags: MapHealthChecks("/healthz/live", new(){ Predicate = _ => false }) and MapHealthChecks("/healthz/ready", new(){ Predicate = c => c.Tags.Contains("ready") }). Then I make the checks meaningful — a query that touches the schema rather than opening a socket — cache their results for a few seconds so probes cannot themselves become load, and add a startup probe for apps with slow warm-up so the liveness probe does not kill them during boot.

06The middleware pipeline and routing

The pipeline is a function composed from functions: each middleware is a Func<RequestDelegate, RequestDelegate>, and Build() folds the list into one nested delegate. Concretely, app.Use(async (ctx, next) => { /* before */ await next(ctx); /* after */ }) gives you the classic onion — code before next runs on the way in, code after runs on the way out, in reverse order. That single picture answers most pipeline questions: exception handling must be outermost to catch anything inner, response-header mutation must happen before the response starts, and anything that short-circuits (does not call next) hides everything below it.

The other half is endpoint routing (since 3.0). Routing is split in two: UseRouting matches the request to an Endpoint and puts it on the context, and UseEndpoints (implicit at the end of the pipeline in minimal hosting) executes it. Everything registered between the two can see which endpoint was selected and its metadata — which is precisely how UseAuthorization knows what policy applies before the handler ever runs. Get that ordering wrong and authorization silently does nothing.

// Order is semantics. This is the canonical order for a typical API.
app.UseForwardedHeaders();      // 1. fix scheme/IP before anything reads them
app.UseExceptionHandler();      // 2. outermost catch (ProblemDetails since .NET 8)
app.UseHsts();                  // 3. production only
app.UseHttpsRedirection();
app.UseStaticFiles();           // legacy; MapStaticAssets() since .NET 9
app.UseRouting();               // 4. endpoint is now known
app.UseCors();                  // 5. after routing, before auth
app.UseRateLimiter();           //    can read endpoint metadata for per-endpoint policies
app.UseAuthentication();        // 6. who are you
app.UseAuthorization();         // 7. may you  -- MUST be after UseRouting
app.UseOutputCache();
app.MapControllers();           // 8. execute

// Branching: Map on path, MapWhen on a predicate, Run as a terminal
app.Map("/admin", admin => { admin.UseMiddleware<AdminAudit>(); admin.Run(Terminal); });
app.MapWhen(c => c.Request.Headers.ContainsKey("X-Legacy"), legacy => legacy.UseMiddleware<Shim>());

// .NET 8+: skip the rest of the pipeline for endpoints that need nothing from it
app.MapGet("/healthz", () => Results.Ok()).ShortCircuit();

Route matching is not first-match-wins; it is most-specific-wins, scored by a precedence algorithm. Literal segments beat parameters, constrained parameters beat unconstrained ones, and a catch-all ({*rest}) is always last. Two templates of identical precedence that both match is an AmbiguousMatchException at request time, not at startup — which is why a route conflict introduced by a merge shows up as 500s on one URL rather than a failed build. Constraints ({id:int}, {slug:regex(...)}, {date:datetime}) participate in matching, so /orders/{id:int} and /orders/{code} can coexist; they are a routing tool, never a validation tool, because a failed constraint yields 404 rather than 400.

Middleware or endpoint filter? This is a genuine design question at lead level. Middleware runs for every request that reaches it, knows nothing about parameters, and works in bytes and headers — right for correlation ids, compression, forwarded headers, global exception handling. An endpoint filter runs only for the endpoints you attach it to, after model binding, so it sees the bound arguments and can short-circuit with a typed result — right for validation, authorization on a resource, idempotency keys. Filters also compose per-group (app.MapGroup("/v1/orders").AddEndpointFilter<IdempotencyFilter>()), which keeps Program.cs honest. The rule of thumb: if it needs the request's meaning, it is a filter; if it needs the request's bytes, it is middleware.

Interview trap

Writing to Response.Headers after await next(). Once the response has started — the first byte flushed, which can happen inside the handler — headers are immutable and you get InvalidOperationException: Headers are read-only, response has already started. The correct mechanism is ctx.Response.OnStarting(() => { ...; return Task.CompletedTask; }), registered on the way in. The companion trap is the exception-handling one: UseExceptionHandler cannot rewrite a response that has already begun streaming, so a failure halfway through a large JSON payload yields a truncated 200, not a 500. That is a strong argument for materialising the result before writing, and for treating "partial success" as a design decision rather than an accident.

Try it

1. Write three app.Use middlewares that log "in-N" before next and "out-N" after, then add an endpoint that throws, and read the log order.
2. Break it on purpose: move app.UseAuthorization() above app.UseRouting() and hit an endpoint with [Authorize].

Solution sketch

You get in-1, in-2, in-3, then out-3, out-2, out-1 — and when the endpoint throws, the "out" lines below the throwing point never run, which is why cleanup belongs in finally or in OnCompleted, not after await next(). For the second experiment, modern ASP.NET Core actually protects you: the framework throws at startup or on the first request complaining that UseAuthorization must appear between UseRouting and UseEndpoints. That guard exists precisely because in earlier versions the same mistake silently allowed every request through — a real vulnerability class, and worth naming as the reason the guard exists.

Interview Q&A

Give me the canonical middleware order and justify three of the positions.

Forwarded headers, exception handler, HSTS/HTTPS redirection, static files, routing, CORS, rate limiting, authentication, authorization, output caching, endpoints. Forwarded headers first because everything downstream that reads scheme or client IP — HTTPS redirection, rate limiting, audit logs — would otherwise read the proxy's values. Exception handling next-to-outermost so it wraps everything that can throw, including authentication. Authorization strictly after routing because it needs the selected endpoint's metadata to know which policy applies; the framework now throws if you get that wrong. CORS before authentication because a preflight OPTIONS carries no credentials and must be answered, not challenged — the classic symptom being a browser that reports a CORS error when the real response was a 401.

What is the difference between Map, MapWhen, UseWhen and endpoint routing?

Map(path) branches the pipeline on a path prefix, strips it into PathBase, and the branch is terminal — control never rejoins the main pipeline. MapWhen(predicate) does the same on an arbitrary predicate. UseWhen(predicate) branches but rejoins, so it is the one you want for "apply this middleware only to /api". None of the three is routing: they run before endpoint selection and know nothing about templates, constraints or metadata. Endpoint routing (MapGet, MapControllers, MapGroup) builds a matcher over templates with precedence rules and attaches metadata that later middleware can read. In new code I use MapGroup plus filters for almost everything, and reserve Map for genuinely separate sub-applications like a mounted legacy handler.

How do route precedence and ambiguity actually work?

Each template is scored segment by segment: literals outrank constrained parameters, which outrank plain parameters, which outrank catch-alls; more segments generally outrank fewer; and the HTTP method acts as a filter, producing 405 rather than 404 when the path matches but the verb does not. If two endpoints tie, you get AmbiguousMatchException — a 500 at request time, not a build error, which is the detail interviewers like. You disambiguate with a constraint, a literal, or an explicit Order on the endpoint metadata, though relying on Order is usually a smell that two features are fighting over a URL. In a large API I enforce a convention (version prefix, resource-first paths) precisely so precedence never has to be reasoned about at review time.

How do you add a correlation id to every request and every log line?

ASP.NET Core already creates an Activity per request with a W3C traceparent, and HttpContext.TraceIdentifier exposes a per-request id, so the first move is to use those rather than invent a header. I add early middleware that accepts an inbound correlation header if it comes from a trusted caller, sets it on the current Activity as a baggage item or tag, pushes it into the logging scope with ILogger.BeginScope, and echoes it on the response via OnStarting. Then IHttpClientFactory's built-in propagation carries traceparent outbound automatically. The two mistakes to avoid: trusting a client-supplied id without validating its shape (log injection), and generating a new id per log call instead of per request, which produces beautifully useless logs.

When is custom middleware the wrong answer?

When the concern needs bound parameters or endpoint semantics — that is an endpoint filter, and writing it as middleware means re-parsing the body and re-implementing routing. When the framework already ships it: rate limiting (.NET 7), output caching (.NET 7), exception handling with IExceptionHandler (.NET 8), request decompression, response compression, W3C logging. And when the middleware would need to buffer the response to inspect it — that quietly disables streaming for every request and is a common cause of memory spikes. My review heuristic: middleware should be small, allocation-free on the happy path, and never await anything slow, because it is on the path of literally every request including health probes.

How do you version an HTTP API?

Mechanically, Asp.Versioning (the community continuation of the Microsoft package) supports URL segment, query string, header and media-type versioning, and integrates with the OpenAPI document so each version gets its own document. I default to URL segment (/v1/orders) because it is visible in logs, cacheable, trivially routable at the proxy and impossible to get wrong in a curl command; header versioning is cleaner in theory and worse in operations. Architecturally the more important answer is that most changes should not need a version at all: additive fields, optional parameters and tolerant readers cover the majority, and a new version is for genuinely breaking semantics. When you do version, commit to a deprecation policy with dates and Sunset headers, and instrument per-version traffic so you can prove the old one is dead before removing it.

Explain ShortCircuit() and when it earns its place.

Added in .NET 8, .ShortCircuit() on an endpoint (or MapShortCircuit(404, "robots.txt", ...)) makes routing execute the endpoint immediately after matching, skipping the rest of the middleware pipeline. It earns its place on very high-frequency endpoints that need nothing from the pipeline: health probes hit every second or two, robots.txt, favicon requests you want to 404 cheaply. The saving is real when your pipeline does authentication, rate limiting and logging work per request. The danger is equally real: short-circuiting skips authentication, authorization, CORS and your logging, so applying it to anything that carries data is a security hole. I treat it as an explicit allow-list of trivial, unauthenticated endpoints.

How do you handle exceptions globally, and what does the response look like?

app.UseExceptionHandler() as the outermost handler, plus AddProblemDetails() so unhandled failures come back as RFC 9457 application/problem+json with a stable shape. For mapping specific exceptions to specific statuses I register IExceptionHandler implementations (.NET 8) — they run in registration order, each returning true if it handled the exception — which is far cleaner than a switch inside one lambda. .NET 10 added ExceptionHandlerOptions.SuppressDiagnosticsCallback and stopped logging an error for exceptions an IExceptionHandler handled, so expected domain failures no longer pollute error dashboards. The rules I hold: never leak stack traces or inner exception messages outside Development, always include the trace id in the problem details so a user's screenshot is actionable, and keep UseDeveloperExceptionPage strictly to Development.

A middleware needs to inspect the response body. What do you tell the author?

That it is a bigger decision than it looks. Inspecting the body means replacing Response.Body with a MemoryStream, which buffers the entire response in memory, disables streaming and chunked transfer, breaks server-sent events and large downloads, and turns a constant-memory endpoint into one that scales with payload size. If the goal is audit logging, log the metadata — status, size, duration, endpoint name — not the payload. If it is genuinely required (a compliance mandate), scope it to specific endpoints with an endpoint filter and a size cap, use RecyclableMemoryStream to avoid LOH allocations, and redact before writing. If the goal is a transform, do it where the data is still objects — a result filter or an output formatter — rather than on the serialized bytes.

Where does CORS actually go wrong in practice?

Almost never in the CORS configuration itself. The three real causes: UseCors placed after UseAuthentication/UseAuthorization, so the preflight OPTIONS — which carries no credentials by design — gets a 401 and the browser reports it as a CORS failure; an exception in the pipeline producing a 500 with no CORS headers, so the browser hides the real error; and AllowAnyOrigin combined with AllowCredentials, which the spec forbids and the framework throws on, pushing people toward SetIsOriginAllowed(_ => true), which is the same hole with the guard rail removed. The correct posture is an explicit origin allow-list from configuration, credentials only where genuinely needed, and remembering that CORS is a browser convention, not a security boundary — it protects users from your API, not your API from attackers.

07Endpoints: minimal APIs and MVC controllers

Both models produce the same thing — an Endpoint with a RequestDelegate and metadata — and both run on the same routing. They differ in how the delegate is built and what runs around it. MVC builds an action invoker with a filter pipeline (authorization → resource → model binding → action → exception → result), value providers, model validation and result formatters, discovered by convention. Minimal APIs compile your lambda's parameters into a binder at startup — or, with the Request Delegate Generator, at build time — and give you a lean endpoint filter chain instead of the filter zoo. Minimal is faster and AOT-compatible; MVC has more built-in machinery (model binding of complex forms, views, conventions, ApplicationParts).

Minimal API parameter binding follows an inference order that is worth memorising because it is where the surprises live: route values by name, then query string, then header/service/body according to attributes. A complex type with no attribute is assumed to be the body (JSON), which is why adding a CancellationToken, HttpContext, ClaimsPrincipal, IFormFile or a registered service just works — they are special-cased — and why an accidental complex parameter on a GET produces a confusing 415. [AsParameters] collapses many query/route parameters into a struct; TryParse/BindAsync statics on your own type make it bindable.

var orders = app.MapGroup("/v1/orders")
    .RequireAuthorization("orders:write")
    .WithTags("Orders")
    .AddEndpointFilter<IdempotencyFilter>();

orders.MapPost("/", async Task<Results<Created<OrderDto>, ValidationProblem, Conflict>> (
        CreateOrder cmd,                 // complex type -> JSON body
        IOrderService svc,               // registered service

    {
        var result = await svc.CreateAsync(cmd, ct);
        return result switch
        {
            { IsConflict: true } => TypedResults.Conflict(),
            _ => TypedResults.Created($"/v1/orders/{result.Id}", result.Dto)
        };
    })
    .WithName("CreateOrder");            // used by LinkGenerator and OpenAPI operationId

    [property: Required, StringLength(64)] string Sku,

The .NET 10 headline for this unit is validation. Until now, minimal APIs had no built-in model validation — you wrote a filter, or pulled in FluentValidation, or (worst) validated inside the handler. builder.Services.AddValidation() now enforces System.ComponentModel.DataAnnotations attributes and IValidatableObject on body, query and header parameters, returns a 400 with a ValidationProblemDetails body through IProblemDetailsService, supports records, and is implemented with a source generator so it costs nothing at runtime and survives trimming. DisableValidation() opts a single endpoint out. FluentValidation is still the better tool for genuinely complex, cross-field, async rules; the built-in one removes the 80% case.

The other .NET 10 addition here is server-sent events: TypedResults.ServerSentEvents(IAsyncEnumerable<SseItem<T>>, eventType) makes a streaming endpoint a one-liner, which matters now that every product wants token-by-token LLM output. SSE over HTTP/2 avoids the six-connection-per-origin limit that made it awkward on 1.1; it is one-way and reconnects automatically, which is why it beats WebSockets for pure server push.

Interview trap

Reading the request body twice. It is a forward-only, non-seekable stream: after model binding has consumed it, a middleware or filter that tries to read it again gets nothing, and the symptom is a mysteriously empty DTO. HttpContext.Request.EnableBuffering() makes it re-readable — but it buffers to memory up to a threshold (30 KB by default) and then to a temp file on disk, so switching it on globally to "make debugging easier" is a memory and I/O regression on every upload endpoint. The related trap: minimal APIs allow exactly one body-bound parameter, so two complex parameters is a startup error, and a complex parameter on a MapGet means the framework wants a body on a GET — bind it with [AsParameters] or [FromQuery] instead.

The filter's EndpointFilterInvocationContext.Arguments contains the already-bound, already-deserialized parameters in declaration order — that is the whole reason a filter beats middleware for validation and idempotency. The validation response is a 400 with application/problem+json, a errors dictionary keyed by property name, and both violations reported, because the generated validator collects rather than short-circuits. Interview Q&A

Minimal APIs or controllers for a new service — how do you choose?

For a JSON API I start with minimal APIs plus route groups, because the per-request machinery is thinner, the contract is visible in the signature, and it is the only model that supports NativeAOT. I go to controllers when I need server-rendered views, complex multipart form binding, or when the team already has a large investment in MVC conventions and filters that would be a pointless rewrite. The false dichotomy worth naming: they coexist in one app, share routing and DI, and a group of minimal endpoints with a shared filter chain is structurally the same thing as a controller with attributes — so this is a style and performance decision, not an architecture one. What I do insist on is consistency within a bounded area, because mixed idioms are where the ordering bugs come from.

How does minimal API parameter binding decide where a parameter comes from?

Explicit attributes win ([FromRoute], [FromQuery], [FromHeader], [FromBody], [FromForm], [FromServices], [FromKeyedServices], [AsParameters]). Otherwise: special types (HttpContext, HttpRequest, CancellationToken, ClaimsPrincipal, IFormFile, Stream, PipeReader) bind to themselves; a type registered in DI binds from services; a type with a static BindAsync uses it; a type with a static TryParse binds from route then query by name; simple types bind from route then query; and anything left that is a complex type binds from the JSON body — of which there may be only one. The rule that saves you: if a parameter is surprising you, it is almost always because the framework decided "complex type, therefore body".

What does [ApiController] actually change?

It turns on a set of conventions: automatic 400 responses from ModelState before the action runs, inference of binding sources (complex types from body, simple ones from route/query, so you stop writing [FromBody]), a requirement for attribute routing, ProblemDetails for error status codes, and multipart/form-data inference for IFormFile. The automatic 400 is the one to discuss: it is convenient but it means your action never sees invalid input, so a custom error shape needs ApiBehaviorOptions.InvalidModelStateResponseFactory rather than code in the action. You can disable individual behaviours through the same options object, which is what teams with a bespoke error envelope do. Minimal APIs got the equivalent conveniences much later — AddValidation() in .NET 10 is the last big gap closing.

Where do you validate, and why not in the handler?

Structural validation — required, ranges, formats, string lengths — belongs at the edge, declaratively, so it is enforced uniformly, documented in OpenAPI, and produces a consistent RFC 9457 response. Since .NET 10 that is AddValidation() with DataAnnotations for minimal APIs and ModelState for controllers. Business invariants — "this customer's credit limit allows this order" — belong in the domain, because they need data the edge does not have and they are not the same thing as a malformed request; those come back as 409 or 422 with a domain-specific problem type. Validating in the handler mixes the two, duplicates the rules per endpoint, and silently drifts from the published schema. FluentValidation stays worth its dependency when rules are cross-field, conditional or async.

Endpoint filter or action filter — what is the actual difference?

An endpoint filter is a single ValueTask<object?> InvokeAsync(EndpointFilterInvocationContext, EndpointFilterDelegate) that wraps the handler and sees the bound arguments; you compose them on an endpoint or a whole MapGroup, and they run in registration order, innermost last. MVC has five distinct filter kinds with different positions in the invoker — authorization, resource, action, exception, result — which gives finer control (a resource filter runs before model binding, so it can short-circuit an expensive bind) at the cost of a model you have to remember. Endpoint filters work for both models in .NET 8+ via AddEndpointFilter on controller endpoints too. If I need to intercept before binding, MVC's resource filter is still the only clean hook; for everything else the endpoint filter is simpler and faster.

How do you handle file uploads safely?

Bind IFormFile/IFormFileCollection for small files, and for large ones read the multipart stream directly with MultipartReader so you never buffer the whole payload — the framework's form binding buffers to disk beyond a threshold, which is fine for a 2 MB avatar and disastrous for a 2 GB video. Cap the size at the endpoint ([RequestSizeLimit] or the Kestrel feature) rather than globally, validate the content type by sniffing magic bytes rather than trusting ContentType or the extension, generate your own storage name instead of using the client's filename, and store outside the web root. Antiforgery applies to browser-posted forms and .NET 8+ requires it explicitly for minimal API form binding. The threat model to say out loud: unbounded uploads are a denial-of-service vector, and client-supplied filenames are a path-traversal vector.

How do you stream a large response without exhausting memory?

Return IAsyncEnumerable<T> and let the JSON formatter write items as they arrive, or write to Response.BodyWriter directly for full control; for files, Results.File/PhysicalFile uses sendfile-style paths and supports range requests. The things that silently break streaming are worth listing because they are the actual interview answer: response buffering middleware, response compression in some configurations, and any code that materialises the collection with ToListAsync() before returning. For push-style streams .NET 10's TypedResults.ServerSentEvents is now the idiomatic choice. And whatever you do, thread HttpContext.RequestAborted through, or a client that disconnects halfway through a million-row export leaves the query running to completion.

What is the Request Delegate Generator and why does it exist?

RDG is a source generator that, at build time, emits the strongly-typed binding and invocation code for each minimal API endpoint instead of building it with reflection and expression trees at startup. It exists for NativeAOT — Reflection.Emit does not exist there — and it is enabled automatically when you publish AOT or set <EnableRequestDelegateGenerator>true</EnableRequestDelegateGenerator>. The side benefits are faster startup and binding errors reported as compiler diagnostics rather than at first request. The constraint it imposes is that endpoint signatures must be statically analysable: handlers defined inline or as named static methods, not dynamically constructed delegates, which is one of the reasons AOT-targeted APIs read differently from reflective ones.

How do you keep 200 endpoints organised without a 2000-line Program.cs?

Route groups plus one registration method per feature: a static class per bounded area exposing MapCatalogEndpoints(this IEndpointRouteBuilder), called from Program.cs, with the group carrying the shared prefix, tags, authorization policy and filters. That gives you the same encapsulation a controller does, but the cross-cutting configuration is explicit at the group rather than implied by attributes scattered across the class. I additionally require every endpoint to have a WithName (so link generation and OpenAPI operation ids are stable) and typed results (so the contract is checked by the compiler). If the folder structure follows the feature rather than the technical layer, this scales considerably better than controllers do, because a feature is one folder rather than four.

Server-sent events, WebSockets, SignalR or long polling?

SSE for one-way server-to-client streams over plain HTTP — notifications, progress, LLM token streams; it is text-only, reconnects automatically with Last-Event-ID, passes through most proxies, and since .NET 10 is a one-liner with TypedResults.ServerSentEvents. WebSockets when you genuinely need bidirectional, low-latency, possibly binary frames — collaborative editing, games, trading. SignalR when you want an abstraction that negotiates the best available transport, handles reconnection and groups, and gives you a scale-out backplane; the price is a stateful connection per client and a protocol your non-.NET clients must speak. Long polling only as a fallback for hostile networks. The lead-level point: every one of these is stateful, so the real design question is what happens when a server instance dies mid-stream, and the answer must be at the application level (resumable cursors), not the transport's.

08JSON, OpenAPI and the API contract

System.Text.Json replaced Newtonsoft as the default in ASP.NET Core 3.0 for one reason: it works on Utf8JsonReader over spans, so it never converts UTF-8 bytes into UTF-16 strings just to throw them away. Every one of those strictnesses is a migration bug for someone, which is why "we had to keep Newtonsoft for one endpoint" is a normal, defensible answer.

Interview Q&A

When is it still right to use Newtonsoft.Json?

When you depend on behaviour System.Text.Json deliberately does not have and the cost of changing the contract exceeds the benefit: JsonPath-style querying with JObject, custom IContractResolver-based conventions across a huge legacy surface, [JsonExtensionData]-heavy dynamic shapes, or third-party SDKs that hand you JToken. It is fully supported via AddNewtonsoftJson(), and mixing is possible per-controller. What you give up is AOT and trimming, roughly half the throughput, and the security posture — TypeNameHandling exists there and does not here. My default is STJ everywhere and Newtonsoft quarantined to the specific boundary that needs it, never as the app-wide default "because migration is risky".

How do you make an API contract evolvable?

Tolerant readers on both sides: unknown fields are ignored (STJ's default), new fields are optional with sensible defaults, and nothing is ever repurposed — a field's meaning is immutable even if its name is ugly. Serialize enums as strings, not integers, so inserting a member does not shift the wire values. Never make a previously optional field required, and never tighten a validation rule without a version. Publish the OpenAPI document from CI and diff it against the previous release as a build gate, so a breaking change is a red build rather than a support ticket. And distinguish "additive" from "breaking" explicitly in the PR template, because most of this fails socially rather than technically.

What does the source-generated JSON context buy you, and what does it cost?

It emits the metadata and, optionally, fast serialization logic at compile time, so there is no reflection at runtime: startup is faster, steady-state serialization is faster (particularly in SerializationOptimized mode), and the code survives trimming and NativeAOT, where reflection-based STJ simply throws. The cost is discipline — every serializable type must be listed with [JsonSerializable], including closed generics like List<OrderDto>, and anything genuinely dynamic (object, JsonNode trees you re-serialize) does not fit the model. Mixing is possible via TypeInfoResolverChain, with the generated resolver first and the reflection one as a fallback, which is the pragmatic migration path for a large codebase.

How do you document and publish an API in .NET 10 without Swashbuckle?

AddOpenApi() and MapOpenApi() generate the document in-process — 3.1 by default, JSON or YAML — driven by endpoint metadata, so TypedResults, [ProducesResponseType] and WithName are what make the document good. XML doc comments flow in through a source generator once GenerateDocumentationFile is on, provided handlers are methods rather than lambdas. Document transformers (AddDocumentTransformer) and the new per-endpoint operation transformers cover security schemes, servers and bespoke tweaks. For a UI you now bring your own — Scalar, Swagger UI as a static asset, or Redoc — because the framework deliberately stopped shipping one. Generating the document at build time with the Microsoft.Extensions.ApiDescription.Server package is what lets you diff it in CI.

How do you handle dates, times and time zones on the wire?

DateTimeOffset or DateTime with Kind.Utc serialized as ISO 8601 with an explicit offset — never a local DateTime, which serializes without enough information and is reinterpreted differently on the other side. For dates without times use DateOnly/TimeOnly (natively supported by STJ since .NET 7), which removes the entire class of "midnight in which zone?" bugs. Store UTC, convert at the presentation edge using the IANA zone id, and remember that .NET 6+ accepts IANA ids on Windows too, so Europe/Budapest works everywhere. The subtle one worth mentioning: a future appointment cannot be stored as a UTC instant if the zone's rules might change — store local time plus zone id for those, which is why "always store UTC" is good advice with a real exception.

Your OpenAPI document says every response is "Success". How do you fix it?

The document is generated from metadata, so the fix is to produce metadata. In minimal APIs, return TypedResults — ideally the union form Results<Ok<T>, NotFound, ValidationProblem> — which the framework reads directly, and add Produces/ProducesProblem only for what the type cannot express. In MVC, put [ProducesResponseType(typeof(T), StatusCodes.Status200OK, Description = "...")] on every action; the Description parameter is new in .NET 10 and is exactly what turns "Success" into a sentence. Then turn on XML documentation so summaries and parameter docs flow in, and gate it: a CI check that fails when an endpoint lacks a name, a summary or a documented error response. The root cause is almost never the tooling.

Why is duplicate-property rejection a security feature?

Because different parsers resolve duplicates differently — some take the first occurrence, some the last, some concatenate. When a request passes through a gateway, a WAF and then your app, and they disagree, an attacker can craft a payload where the security layer reads {"role":"user"} and the application reads {"role":"admin"}. That is the same family as HTTP request smuggling, applied to JSON. .NET 10 lets you set AllowDuplicateProperties = false (and includes it in JsonSerializerOptions.Strict), so the payload is rejected instead of silently resolved. It is a small switch with a disproportionate payoff, and the reasoning behind it is exactly the kind of thing a principal-level interview is probing for.

How do you deal with very large JSON payloads?

Do not materialise them. On the way in, stream with JsonSerializer.DeserializeAsyncEnumerable<T> over the body so you process record by record with bounded memory, and set an explicit body-size limit so an attacker cannot choose your memory profile. On the way out, return IAsyncEnumerable<T> and let the formatter write incrementally. Watch the Large Object Heap: any single buffer over 85 000 bytes lands there and is not compacted by default, so a 200 KB string per request at high RPS produces LOH fragmentation that looks like a leak. And question the requirement — a 500 MB JSON response is usually a missing pagination or export-to-object-storage design, and saying so is worth more than any serializer tuning.

How do you version a JSON contract without versioning the URL?

Additively, and with a discriminator when you cannot. Add fields rather than change them; keep the old field populated alongside the new one for a deprecation window; use [JsonPropertyName] so the wire name and the C# name can diverge when you rename internally. For genuinely different shapes, a polymorphic payload with an explicit $kind discriminator lets a single endpoint serve both, with the client choosing via Accept or a request field. Media-type versioning (application/vnd.acme.order.v2+json) is the purist's answer and works well when you control the clients. Whatever the mechanism, the governance is the same: measure usage per shape, publish sunset dates in Sunset/Deprecation headers, and never remove anything you cannot prove is unused.

What is JSON Patch's place, and what changed in .NET 10?

JSON Patch (RFC 6902) expresses a partial update as a list of operations, which beats PUT-the-whole-resource when documents are large or concurrent edits are common; Microsoft.AspNetCore.JsonPatch historically required Newtonsoft, and .NET 10 added a System.Text.Json-based implementation plus automatic OpenAPI metadata — the application/json-patch+json media type and schema now appear in the generated document without hand-written transformers. The caution I give teams: patch documents can express operations your domain has no invariant for (removing a required field, replacing an id), so a patch endpoint needs the same validation as a full update, applied after the patch is materialised onto a DTO — never onto the entity. For most CRUD APIs a well-designed PATCH with a partial DTO and explicit "field present" semantics is simpler and easier to document.

09Async, the thread pool and the request lifecycle

This is the unit that separates people who use async from people who understand it. The point of async in a server is not speed — an async request is marginally slower than a synchronous one — it is thread economy. A synchronous request blocks a thread pool thread for the entire duration of a database call; an async one returns the thread to the pool at the first await and resumes on some thread when the I/O completes. With a 50 ms database call and 1000 concurrent requests, sync needs 1000 threads (~1 GB of stack, plus context-switching); async needs a handful. That is the whole argument, and it is the answer to "why not just raise the thread pool minimum".

Mechanically: the compiler rewrites an async method into a state machine struct; awaiting an incomplete task boxes it onto the heap and registers a continuation; the completion is queued to the thread pool (there is no SynchronizationContext in ASP.NET Core, unlike WinForms or old ASP.NET). This is why ConfigureAwait(false) is a no-op in ASP.NET Core application code — there is nothing to capture — while still mattering in shared libraries that might run under a UI or legacy ASP.NET context. Say that distinction precisely; a lot of candidates get half of it.

// Thread-pool starvation: the shape that causes it, and the shape that fixes it.
public async Task<IResult> Bad(IOrderService svc)
{
    var order = svc.GetAsync(id).Result;                 // blocks a pool thread until I/O completes
    Thread.Sleep(100);                                    // and burns another 100ms of it
    return Results.Ok(order);
}

public async Task<IResult> Good(IOrderService svc, CancellationToken ct)
{
    var order = await svc.GetAsync(id, ct);               // thread returns to the pool here
    return Results.Ok(order);
}

Thread-pool starvation is the incident you will be asked to diagnose. Symptom: latency climbs across all endpoints including trivial ones, CPU is low, and the queue length grows. Cause: something blocks pool threads — .Result, .Wait(), GetAwaiter().GetResult(), Task.Run(() => syncIO()), a lock held across I/O, or a sync-over-async third-party SDK. The pool injects new threads only slowly (roughly one or two per second beyond the minimum, by design, since thrashing threads is worse), so a burst of blocking produces minutes of degradation. Diagnosis: dotnet-counters monitor System.Runtime and watch ThreadPool Thread Count climbing with ThreadPool Queue Length; confirm with a dump and dotnet-dump analyze's clrthreads/syncblk. The fix is to remove the blocking, not to raise ThreadPool.SetMinThreads — that is a bridge while you fix it.

async void. It is fire-and-forget with no task to observe, so an exception inside it does not propagate — it is raised on the thread pool and, by default, crashes the process. Interview Q&A

Does async make my API faster?

No — a single request is slightly slower, because you pay for a state machine, a heap allocation when the await actually suspends, and a continuation dispatch. What it buys is scalability: the thread that would have blocked on I/O goes back to the pool, so throughput under concurrency is bounded by your downstream dependencies rather than by thread count. That means async is close to pointless for a purely CPU-bound handler with no I/O — there is nothing to release — and enormously valuable for anything touching a database, a queue or another service. The way I frame it in reviews: async is about how many requests you can have in flight, not how fast one goes.

Walk me through diagnosing thread-pool starvation in production.

Confirm the signature first: latency up across all endpoints including static ones, CPU low, no obvious downstream slowdown. Then dotnet-counters monitor --process-id N System.Runtime and look for ThreadPool Thread Count rising steadily while ThreadPool Queue Length stays high — that pair is close to conclusive. Capture a dump with dotnet-dump collect and look at what the threads are doing; a wall of threads parked in Monitor.Wait, Task.Result or a sync socket read names the culprit. The fix is at the call site — remove the sync-over-async, or move genuinely blocking third-party work onto a dedicated thread rather than the pool. Raising SetMinThreads is a mitigation to buy time during an incident, and I would say so explicitly rather than present it as a fix.

When should a method return ValueTask instead of Task?

When it is on a hot path and usually completes synchronously — a cache lookup that hits 95% of the time, a PipeReader.ReadAsync, a buffered stream read — because ValueTask avoids allocating a Task for the synchronous case, and with IValueTaskSource pooling it can avoid allocation even when it does suspend. The cost is a much stricter contract: await it exactly once, never await it twice, never store it in a field or a collection, never call .Result on an incomplete one. For public library APIs consumed by people who will not read that contract, Task is the safer default. My rule: ValueTask when a benchmark shows the allocation matters, Task otherwise.

How do you do fire-and-forget work correctly?

You do not fire and forget; you hand off to something that owns the work. In-process, that is a bounded Channel<T> written from the request and drained by a BackgroundService that creates its own DI scope per item — bounded, so backpressure is a slow write rather than an OOM. Across processes, it is a queue or an outbox row committed in the same transaction as the business change, which is the only version that survives a crash. What breaks with naked Task.Run: the request scope disposes underneath you, exceptions are unobserved, shutdown does not wait, and there is no retry or visibility. If the work genuinely must not be lost, it needs durability, and "we'll do it in the background" is a persistence design question wearing a threading costume.

What is CancellationToken actually for in a web request?

HttpContext.RequestAborted fires when the client disconnects, so threading it through means a cancelled request stops occupying a database connection, stops a long query, and stops burning downstream quota — a real capacity saving when clients time out and retry. Minimal APIs and controllers inject it as a parameter automatically. Two nuances: the token also fires during shutdown, so code must distinguish "client gave up" (log at debug, no alarm) from a genuine failure, which is why catch (OperationCanceledException) when (ct.IsCancellationRequested) is the idiomatic filter; and cancellation is cooperative, so a call that ignores the token cancels nothing. For writes, cancelling mid-transaction leaves you needing idempotency, which is why I do not blindly pass RequestAborted into a command that has already been accepted.

Why is ConfigureAwait(false) everywhere in some codebases and absent in others?

Because it only matters when there is a SynchronizationContext to capture. WinForms, WPF and classic ASP.NET had one, so resuming on the captured context could deadlock if a caller blocked on the task — that is where the "always ConfigureAwait(false) in libraries" rule comes from. ASP.NET Core has no SynchronizationContext, so in application code it does nothing and only adds noise. The correct nuance: shared libraries that might be consumed by a UI or legacy ASP.NET app should still use it (or set <ConfigureAwait> via the analyzer/MSBuild property), application code in ASP.NET Core need not. .NET 8 added ConfigureAwait(ConfigureAwaitOptions.SuppressThrowing) and friends, which is a genuinely different feature and worth knowing exists.

How do you protect shared state in an async method?

lock cannot be held across an await — the compiler forbids it, and for good reason, since the continuation may run on a different thread and Monitor is thread-affine. So async mutual exclusion is SemaphoreSlim(1,1) with WaitAsync and a finally { Release(); }, or, better, a design that does not need it: immutable state, ConcurrentDictionary, Interlocked, or a single consumer draining a channel. .NET 9 added System.Threading.Lock, which is a faster, clearer replacement for lock (object) in the synchronous case, and does not change the async story. The design point I make: a semaphore around I/O serialises your throughput to one operation at a time, so it is usually the wrong tool — cache the task rather than locking around the work.

How do you bound concurrency when fanning out to a downstream service?

Parallel.ForEachAsync with MaxDegreeOfParallelism for a simple bounded fan-out, or a SemaphoreSlim gate combined with Task.WhenAll when the shape is irregular. The number should come from the downstream service's stated capacity, not from your core count, and it should be configurable because it is the knob you will turn during an incident. Layer a rate limiter or a concurrency-limiting resilience pipeline (Microsoft.Extensions.Http.Resilience) on the client itself so the bound applies across all callers rather than per call site. And design for partial failure: with Task.WhenAll, one failure surfaces first and the rest are hidden, so if you need per-item outcomes, collect results explicitly rather than relying on the aggregate.

What is the difference between concurrency and parallelism here, and why does it matter for capacity planning?

Concurrency is how many requests are in flight; parallelism is how many are executing on CPUs at this instant. An async I/O-bound service can have thousands concurrent on a four-core box because almost all of them are parked on a socket. That means your capacity limit is not CPU — it is the downstream connection pool, the database's max connections, or memory for in-flight buffers, and those are the numbers to size. It also means the classic "add more replicas" reflex can make things worse by multiplying pressure on a shared database. Concretely, I plan capacity by measuring where the queue actually forms (Little's Law on the slow dependency) rather than by watching CPU, and I put an explicit concurrency limiter in front of the scarce resource so overload sheds predictably.

What is runtime async in .NET 11 and why should I care?

Today the C# compiler rewrites every async method into a state machine class, which costs an allocation per suspension and turns stack traces into a maze of MoveNext frames. Runtime async pushes that responsibility into the runtime itself, so the JIT generates suspension points directly; the payoff is lower overhead and stack traces that read like the code you wrote. As of .NET 11 Preview 7 (2026-08-11) it no longer needs EnablePreviewFeatures for net11.0 projects, and the JIT now emits dedicated runtime-async variants of synchronous task-returning methods with tail-merged suspension points to shrink code size. You care because it is free performance on upgrade and because debugging async production issues gets meaningfully easier — but it is not something you write differently for, and it is still preview until November 2026.

10Memory, spans and the garbage collector

The .NET GC is generational, mark-and-sweep with compaction, and tracing — it finds what is reachable, not what is dead. Objects are born in gen0, which is small (roughly the size of a CPU cache) and collected extremely often and extremely cheaply; survivors are promoted to gen1, then gen2. The generational hypothesis is the whole design: most objects die young, so collecting only the young space is almost free. Anything 85 000 bytes or larger goes straight to the Large Object Heap, which is collected only with gen2 and is not compacted by default — so LOH fragmentation shows up as "we have plenty of free memory but allocation fails".

Two flavours, and the interview always asks. Workstation GC uses one heap and prioritises latency for a client app. Server GC creates a heap and a dedicated GC thread per core, so collections run in parallel and throughput is far higher — it is the default for ASP.NET Core, and it is why a .NET service on a 32-core node can appear to use enormous amounts of memory while doing nothing wrong. Both have a background/concurrent mode for gen2 so long collections do not stop the world entirely.

DATAS (Dynamic Adaptation To Application Sizes) is the modern answer to Server GC's appetite. Opt-in in .NET 8, on by default with Server GC since .NET 9, and further tuned in .NET 10, it starts with a single heap and grows heap count based on measured throughput and survival, targeting a heap roughly proportional to the live data set rather than to the core count, at a budgeted ~2% throughput cost. The practical consequence on upgrading: memory graphs drop, sometimes dramatically, and a service that was sized by its old RSS suddenly looks over-provisioned. If you measured a regression on a very allocation-heavy service, System.GC.DynamicAdaptationMode = 0 turns it off — but measure first, because the usual finding is that it helped.

Span<T> and Memory<T> are the language-level half of this. A Span<T> is a ref struct — stack-only, cannot be a field of a class, cannot cross an await or a yield — which is exactly what makes it safe to point at stack memory, unmanaged memory or a slice of an array with no copying. Memory<T> is the heap-friendly sibling you use when you need to hold it across an await, converting to a span at the point of use. In practice you meet them everywhere in modern .NET: Utf8JsonReader, PipeReader, string parsing, and Encoding.UTF8.GetBytes(span, span).

.NET 10's runtime work is mostly about not allocating in the first place. Escape analysis now understands objects referenced by local struct fields and by delegates, so a Func whose closure never escapes the method can be stack-allocated. The JIT now stack-allocates small fixed-size arrays of value types and of reference types. Array interface methods devirtualize, so foreach over an IEnumerable<int> that is really an int[] can inline and, in some cases, stack-allocate the enumerator. Add the Arm64 write-barrier rework — dynamic write-barrier selection, previously x64-only, giving 8% to over 20% better GC pause times — and an ASP.NET Core service on Graviton or Ampere gets a free win on upgrade.

The correct pattern is IDisposable/IAsyncDisposable with using, and a finalizer only as a safety net around genuinely unmanaged handles — preferably SafeHandle instead.

1. Run a load test twice, once with System.GC.DynamicAdaptationMode=1 and once with 0, on a 8+ core machine, and compare peak working set and p99 latency.
2. Allocate a byte[100_000] per request, run it hot, and watch which generation grows; then switch to ArrayPool<byte>.Shared.

Expected outcome

With DATAS on you should see markedly lower peak working set — often a large fraction of the old value — with p99 within a couple of percent; that trade is why it became the default with Server GC in .NET 9. The 100 KB array is over the 85 000-byte threshold, so it goes straight to the LOH and is only reclaimed by gen2 collections: you will see gen2 count climb and pause times spike, with fragmentation growing because the LOH is not compacted by default. ArrayPool removes both effects entirely — the same buffer is reused, gen2 stays flat, and pauses return to baseline. That is the cleanest demonstration of why "just allocate, the GC is fast" stops being true above 85 KB.

Interview Q&A

Explain generations and why they make collection cheap.

Objects start in gen0. A gen0 collection only traces roots into the gen0 segment, uses the card table to find gen1/gen2 objects that point into it, and typically finishes in well under a millisecond because almost everything there is already dead. Survivors are promoted, and the same logic applies at gen1; gen2 is the expensive one because it traces the whole heap. The design bet is the generational hypothesis — most objects die young — which is overwhelmingly true for request-scoped web workloads. The engineering consequence is the one to state: what hurts is not allocation, it is promotion, so a per-request cache that keeps objects alive for two seconds is far worse than one that allocates twice as much and drops it immediately.

Server GC or Workstation GC for a container with a 1-core limit?

Server GC's advantage is per-core parallel heaps, so on a 1-core container it costs you the extra bookkeeping and gives back nothing — Workstation is usually the better choice there, and the runtime already restricts heap count to the cgroup CPU limit rather than the node's core count (which is a common misconception worth correcting). The broader point is that GC configuration must be derived from the container's limits, not the host: DOTNET_GCHeapHardLimitPercent or the automatic 75%-of-limit default keeps the heap inside the memory limit so you get a GC instead of an OOMKill. With DATAS on since .NET 9 the heap-count question largely answers itself dynamically, which is a good reason to upgrade rather than hand-tune. And whatever you choose, measure — this is the area where folklore outlives the runtime that inspired it.

How do you find a managed memory leak?

Establish that it is one: heap size and gen2 count rising monotonically under steady load, not just RSS, which can be pool high-water marks or fragmentation. Then take two dotnet-gcdump snapshots minutes apart under load and diff them — the type whose instance count grew is your suspect, and the retention path tells you who is holding it. The usual culprits are static collections, event handlers never unsubscribed, IDisposable transients resolved from the root provider, unbounded MemoryCache or dictionaries used as caches, and Tasks captured in long-lived state. If the managed heap is flat but RSS grows, it is native: unclosed sockets or file handles, a native library, or LOH fragmentation — different tools (dotnet-counters for handle counts, a native profiler) and a different conversation.

When is Span<T> the right tool, and when is it premature?

Right when you are slicing or parsing on a hot path and the alternative allocates: substring-heavy header or CSV parsing, encoding conversions, binary protocol framing, anything called per request per item. Premature when the code runs once per request, is dominated by I/O, or is business logic where clarity matters more than nanoseconds — a ref struct cannot be captured in a lambda, stored in a field, or used across an await, so span-ifying ordinary code makes it rigid for no measurable gain. My rule is that spans follow benchmarks, not intuitions, and that the biggest wins usually come from removing an allocation entirely rather than making it cheaper.

What is the Large Object Heap and how do you stay off it?

Any allocation of 85 000 bytes or more (arrays of doubles from 1000 elements, due to alignment) is allocated on the LOH, which is collected only during gen2 and, by default, swept but not compacted — so repeated large allocations of varying sizes fragment it, and you end up unable to satisfy a large request despite free space. You stay off it by pooling (ArrayPool, RecyclableMemoryStream), by streaming instead of buffering whole payloads, and by chunking large buffers into 64 KB pieces. If you genuinely must, GCSettings.LargeObjectHeapCompactionMode = CompactOnce before an induced collection compacts it, at the cost of a long pause — an incident tool, not a design.

What did .NET 10 change about allocations, concretely?

Escape analysis got two extensions: objects referenced by local struct fields no longer count as escaping if the struct itself does not escape, and delegates whose Func object cannot outlive the method are stack-allocated (the closure object itself still heap-allocates, with that planned for a later release). Stack allocation now covers small fixed-size arrays of both value types and reference types. The JIT can devirtualize and inline array interface methods, so iterating an array through IEnumerable<T> stops being an abstraction tax, and inlining improved in several ways — methods with try/finally can now be inlined, and profile data loosens size limits for hot callees. Separately, the new block-layout algorithm models code placement as an asymmetric travelling-salesman problem solved with a 3-opt heuristic, improving hot-path density. Net effect: less garbage and better code layout for free on upgrade.

How do you size memory limits for a .NET service in Kubernetes?

Start from measurement under representative load, not from a guess. Set the memory limit, then let the runtime derive its heap budget from the cgroup — the default is 75% of the limit — leaving headroom for native memory: thread stacks, socket buffers, the JIT's code heap, and any native dependency. Set requests close to the steady-state working set and the limit high enough that a transient spike causes a GC rather than an OOMKill, because a killed pod mid-request is far worse than a 50 ms pause. With DATAS on, expect the working set to track live data rather than sit at a plateau, which makes requests easier to set honestly. And alert on OOMKill events and on GC pause time, not on memory percentage, which is meaningless for a runtime that deliberately keeps memory it might reuse.

IDisposable, finalizers, SafeHandle — how do they relate?

IDisposable is deterministic cleanup you invoke, normally through using; it is the only mechanism with predictable timing. A finalizer is the GC's last resort: the object is placed on the finalization queue, survives at least one extra collection, and is finalized on a single dedicated thread whose blockage stalls all finalization. SafeHandle is the right way to own an unmanaged handle — it has a critical finalizer, participates in reliability guarantees and prevents handle-recycling races — which is why modern code almost never writes a finalizer directly. IAsyncDisposable exists because releasing a resource can require I/O (flushing a stream, closing a connection gracefully), and await using is the correct syntax. In review, a class with a finalizer and no unmanaged resource is always a bug.

Your p99 latency has a periodic sawtooth. How do you tell if it is the GC?

Correlate. dotnet-counters monitor System.Runtime gives you time-in-gc, gen2 count and pause duration; if the sawtooth peaks line up with gen2 collections, that is your answer. dotnet-trace with the GC keyword gives per-collection detail — which generation, blocking or background, how long, and how much was promoted. If GC is the cause, the fix is upstream: reduce promotion (do not cache short-lived objects), reduce LOH traffic (pool buffers), and confirm background gen2 is enabled. If GC is not the cause, the same trace usually reveals the real one — thread-pool queueing, a connection-pool wait, or a downstream dependency's own sawtooth. The discipline worth demonstrating is refusing to blame the GC without the counter that proves it.

What is the cost model you carry in your head for allocations?

Allocation itself is a pointer bump — a few nanoseconds — so the cost is never the new, it is the collection and the promotion it eventually causes. Short-lived gen0 garbage is close to free; anything that survives into gen1 or gen2 costs real pause time, and anything over 85 KB is a gen2-only, non-compacted problem. So my mental ranking is: avoid LOH allocations, avoid promotion, and only then worry about gen0 churn — and the last one only when a benchmark or an alloc-rate counter says so. The corollary for reviews is that "this allocates" is not by itself a finding; "this allocates a 200 KB buffer per request and survives to gen2" is.

11JIT, tiered compilation, PGO, Native AOT and trimming

The JIT does not compile a method once. Tiered compilation (default since .NET 3.0) compiles first at tier 0 — fast to produce, poorly optimised — and promotes methods to tier 1 after 30 calls, recompiling with full optimisation. That gives you fast startup and eventual peak throughput. On-stack replacement (default since .NET 7) fixed the hole in that story: a method with a long-running loop used to be stuck in tier 0 forever because it never returned, so the runtime now swaps the optimised code in while the frame is still live.

Dynamic PGO (on by default since .NET 8) is the piece that makes the JIT genuinely smarter than an ahead-of-time compiler can be. Tier-0 code is instrumented: it records which concrete types show up at each virtual call site and which branches are taken. When the method is promoted, the JIT uses that profile to guarded-devirtualize the hot type (an inline type check plus a direct, inlinable call, with a fallback), to lay out hot blocks together, and to guide inlining. This is why a .NET service benchmarked in its first second looks nothing like the same service at steady state, and why "warm the app before rotating it into the load balancer" is real advice rather than superstition.

Trimming is the prerequisite for AOT and useful on its own. The IL linker walks from your entry point and removes unreferenced code; anything reached only by reflection is invisible to it and disappears. That is what the IL2xxx warnings are telling you, and the correct response is to fix them (source generators, [DynamicallyAccessedMembers] annotations, explicit registration) rather than to suppress them — a suppressed warning becomes a MissingMethodException in production. Interview trap

Reaching for NativeAOT to "make the API faster". It makes startup faster and memory smaller; steady-state throughput is usually slightly lower than a warmed-up JIT, because there is no dynamic PGO to devirtualize your hot interface calls. So AOT is the right call for serverless, CLI tools, sidecars, short-lived jobs and dense multi-tenant hosting — and the wrong call for a long-running service where the JIT has hours to optimise. The second trap is publishing AOT late: trim and AOT warnings must be errors in CI from the first commit, because retrofitting AOT onto a mature service means discovering that three dependencies use Reflection.Emit and one of them is your ORM.

Solution sketch

Interview Q&A

Explain tiered compilation and OSR to someone who has only used AOT-compiled languages.

The JIT trades compile time for code quality twice. On first call a method is compiled at tier 0 — quick, minimally optimised, and instrumented to collect a profile. After it has been called about thirty times it is queued for tier 1, where the JIT applies full optimisation informed by that profile. The gap this left was a method entered once with a long loop inside: it never returns, so it never gets promoted, and you would run an entire batch job at tier-0 quality. On-stack replacement, default since .NET 7, fixes that by compiling an optimised version and transferring execution into it mid-frame, mapping the live locals across. The operational takeaway is that a .NET process has a warm-up curve, so benchmarks and canary comparisons must account for it.

What is dynamic PGO doing that a static compiler cannot?

Using facts only observable at runtime. It records the concrete types arriving at each virtual or interface call site and the actual branch frequencies, then uses that at tier 1 to guarded-devirtualize — emit a type check plus a direct, inlinable call to the dominant implementation with a fallback for everything else — and to lay out hot blocks contiguously. A static compiler must be conservative because it cannot know that 99% of your IRepository calls are the SQL one. That is why an ahead-of-time-compiled .NET binary is usually a little slower at steady state, and why abstraction in .NET is much cheaper than the IL suggests. It has been on by default since .NET 8, so it is the baseline, not an opt-in.

When would you actually ship NativeAOT?

When startup or density dominates: serverless functions billed per invocation with cold starts, CLI tools, sidecars and agents deployed to thousands of nodes, short-lived jobs, or a multi-tenant host running hundreds of small services where per-process memory is the constraint. It also has a security-adjacent benefit — no JIT means no runtime code generation surface, and a smaller attack surface overall. I would not ship it for a long-running request-serving API where the JIT has hours to profile, nor for anything using MVC, Blazor Server, or a dependency that needs Reflection.Emit. And I would only start a service on AOT, never migrate one to it late, because the constraint has to shape the dependency choices from the beginning.

How do you make a library trim-friendly?

Set <IsTrimmable>true</IsTrimmable> so consumers get warnings from your assembly, then eliminate them properly: replace reflection with source generators, annotate the reflection you must keep with [DynamicallyAccessedMembers] so the linker preserves the right members, mark genuinely unsafe APIs with [RequiresUnreferencedCode] so callers are warned rather than silently broken, and provide a non-reflective alternative alongside. Add a trimmed and an AOT-published smoke test to CI, because warnings alone do not prove the app runs. ILLink.Substitutions.xml and feature switches let you compile out whole code paths for trimmed consumers. The honest test of success is that a consumer can publish AOT with warnings-as-errors and no suppressions.

ReadyToRun versus NativeAOT — where does R2R fit?

R2R precompiles IL to native code but keeps the full runtime and the JIT, so startup improves markedly while everything still works — reflection, Emit, MVC, profilers, hot reload. It is the low-risk startup optimisation: a build flag, no code changes, no dependency audit. The costs are a larger artifact and the fact that R2R code is compiled conservatively, so hot methods still get re-JITted at tier 1 to reach peak speed. Composite R2R (compiling the framework and app together) improves it further at the cost of a much larger, version-locked bundle. My sequencing advice: reach for R2R first when cold start hurts, and only consider AOT when R2R is not enough and you are willing to accept its constraints.

How would you profile a CPU regression in production?

Start with counters to characterise it — dotnet-counters monitor System.Runtime for CPU, GC time, thread pool queue, exception rate — because "CPU is up" has several very different causes. Then capture a sampled trace with dotnet-trace collect --profile cpu-sampling for 30 seconds, and open it in PerfView or Visual Studio; the hot stacks usually name the culprit directly. If the suspect is a specific method, DOTNET_JitDisasm or a BenchmarkDotNet [DisassemblyDiagnoser] run locally shows the generated code, and comparing it across runtime versions catches the rare JIT regression. Two process points matter as much as the tools: capture from a canary rather than the whole fleet, and always compare against a baseline trace from a known-good build, because absolute numbers mean very little on their own.

Does exception handling cost anything?

Throwing does — building the exception, capturing the stack trace and unwinding is on the order of microseconds, thousands of times more than a return — while a try block that does not throw is essentially free, and since .NET 9's rewritten (managed) exception handling implementation, throwing itself got substantially faster. So exceptions for exceptional cases are fine; exceptions for control flow at request rate are a measurable, and visible, problem — the exception-count counter is one of the first things I look at when a service is inexplicably CPU-heavy. The classic offenders are validation implemented by throwing, int.Parse in a loop over user input, and a library that throws on cache misses. Notably, .NET 10 also made methods containing try/finally inlinable, which removes a small long-standing penalty for well-structured cleanup code.

What is single-file publish and how does it relate to trimming and AOT?

Single-file bundles your assemblies (and optionally the native runtime) into one executable that extracts or memory-maps at startup; it is packaging, not compilation, so by itself it changes nothing about performance. Trimming removes unreferenced IL and reduces size; AOT compiles everything to native and removes the JIT. They compose: AOT implies both trimming and a single file, while single-file alone works with or without trimming. The practical distinction to state is what breaks: single-file breaks code that assumes Assembly.Location is a real path on disk (a surprisingly common assumption in configuration and plugin loading), trimming breaks reflection, and AOT breaks dynamic code generation. Three different failure modes, often blamed on the wrong one.

A team wants to disable tiered compilation "for consistent performance". What do you say?

That they are optimising the first thirty calls at the expense of every call after. Disabling tiering (TieredCompilation=false) makes everything compile at full optimisation immediately, which lengthens startup considerably and — importantly — turns off dynamic PGO, so steady-state throughput usually gets worse, not more consistent. The legitimate variant of their concern is warm-up: a pod that starts serving before it is warm shows a latency spike, and the right fixes are ReadyToRun, a warm-up request loop before the readiness probe passes, or TieredPGO left on with a longer ramp-in at the load balancer. If someone genuinely needs deterministic first-call latency — a trading hot path — that is an AOT or a pre-JIT conversation, not a tiering switch.

What did you learn from the .NET 10 codegen notes that changes how you write code?

Mostly that it reinforces existing good habits rather than creating new ones. Small local arrays and short-lived lambdas are now much more likely to be stack-allocated, so the defensive contortions people used to write — hoisting a static lambda to avoid a closure, replacing a three-element array with three locals — matter less than they did. Iterating an array through IEnumerable<T> is no longer an automatic abstraction tax now that array interface methods devirtualize. And because inlining now sees through a devirtualization it just performed, keeping methods small and sealing classes you do not intend to extend pays off more than before. The meta-lesson I take into reviews: prefer clear code and re-measure on each major, because last year's micro-optimisation is this year's pessimisation.

12Resilience, caching and outbound HTTP

Every distributed system fails at the edges, and in .NET those edges are HttpClient calls. The canonical trap is the pair of opposite mistakes: a new HttpClient() per request exhausts sockets (each disposed client leaves a connection in TIME_WAIT for up to four minutes, so a few hundred RPS runs a machine out of ephemeral ports), while a single static HttpClient held forever caches DNS at the connection level and keeps talking to an IP that failed over an hour ago. IHttpClientFactory solves both by separating the cheap, disposable HttpClient from the expensive, pooled HttpMessageHandler, and rotating handlers on a lifetime (two minutes by default) so DNS gets re-resolved. The modern alternative for non-DI code is a static SocketsHttpHandler with PooledConnectionLifetime set — which is exactly what the factory does underneath.

builder.Services.AddHttpClient<PaymentsClient>(c =>
    {
        c.BaseAddress = new Uri(cfg["Payments:BaseUrl"]!);
        c.Timeout = TimeSpan.FromSeconds(10);          // outer bound; the pipeline has its own
    })
    .AddStandardResilienceHandler(o =>                  // Microsoft.Extensions.Http.Resilience (Polly v8)
    {
        o.Retry.MaxRetryAttempts = 3;
        o.Retry.BackoffType = DelayBackoffType.Exponential;
        o.Retry.UseJitter = true;                       // without jitter, retries synchronise into a stampede
        o.AttemptTimeout.Timeout = TimeSpan.FromSeconds(3);
        o.CircuitBreaker.FailureRatio = 0.5;
        o.CircuitBreaker.SamplingDuration = TimeSpan.FromSeconds(30);
    })
    .ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
    {
        PooledConnectionLifetime = TimeSpan.FromMinutes(2),
        EnableMultipleHttp2Connections = true
    });

The standard resilience handler stacks five strategies in a deliberate order: rate limiter → total timeout → retry → circuit breaker → per-attempt timeout. The ordering is the lesson. A retry inside the total timeout means three attempts cannot exceed your overall budget; a circuit breaker inside the retry means a broken dependency fails fast rather than being retried into the ground. Jitter is not optional: without it, every instance retries at the same moment after a shared failure and you have built a self-inflicted DDoS. And retries are only safe on idempotent operations — GET, PUT, DELETE, and POST only when you send an idempotency key the server honours.

Caching in ASP.NET Core is four distinct things, and mixing them up is a reliable interview tell. IMemoryCache is in-process and per-instance. IDistributedCache is out-of-process (Redis, SQL Server) and shared. Output caching (.NET 7) caches the server's response under your control, with tag-based invalidation. Response caching is the older HTTP-header-driven one that mostly delegates to clients and proxies and disables itself the moment an Authorization header appears — which is why teams think it "doesn't work". HybridCache (.NET 9, Microsoft.Extensions.Caching.Hybrid) is the one to name: it layers L1 in-memory over L2 distributed, and — the actual point — it does stampede protection, so a thousand concurrent misses for the same key produce one backend call rather than a thousand.

builder.Services.AddHybridCache(o => o.DefaultEntryOptions = new()
{
    Expiration = TimeSpan.FromMinutes(5),          // L2
    LocalCacheExpiration = TimeSpan.FromSeconds(30) // L1: shorter, bounds staleness across instances
});

// One backend call even under a thundering herd; tags give you group invalidation.
var product = await cache.GetOrCreateAsync(
    $"product:{id}",
    (id, ct) => store.GetProductAsync(id, ct),
    tags: ["products", $"tenant:{tenantId}"],
    cancellationToken: ct);

Rate limiting has been in the box since .NET 7: AddRateLimiter with fixed-window, sliding-window, token-bucket and concurrency limiters, applied globally or per endpoint via RequireRateLimiting("policy"), partitioned by whatever key you choose (API key, tenant, client IP once forwarded headers are trusted). Two design points that separate a senior answer: the limiter is per instance, so with N replicas your effective limit is N times what you configured unless you partition at the gateway or use a distributed store; and a rejected request should return 429 with a Retry-After header, because a limiter that clients cannot cooperate with just converts load into retries.

Interview trap

Retry without a budget, without jitter, or on a non-idempotent operation. Three attempts at each of three layers — client, gateway, service — is 27 requests to a struggling dependency, which is how a partial degradation becomes an outage; that is the "retry storm" or "metastable failure" pattern, and naming it scores points. Equally common: a circuit breaker configured per HttpClient instance while the factory hands out a new client per injection, so the breaker state is never shared and never opens — check that the strategy lives on the handler, not on a transient object. And on caching: a cache with no maximum size and no eviction policy is not a cache, it is a leak with better branding.

Try it

1. Point a typed client at a service you can stop, add the standard resilience handler, and watch the logs as you kill and restore it — note when the circuit opens, how long it stays open, and what a half-open probe looks like.
2. Hammer one HybridCache key with 500 concurrent requests on a cold cache and count the calls that actually reach the backing store.

Expected outcome

You will see retries with growing, jittered delays, then the breaker opening once the failure ratio crosses the threshold within the sampling window — after which calls fail immediately with BrokenCircuitException instead of waiting for a timeout, which is the entire point: fast failure protects your threads as much as the dependency. After the break duration a single half-open probe decides whether to close. In the cache experiment the backing store should be hit exactly once; without stampede protection (plain IMemoryCache plus GetOrCreate) you would see hundreds, which is the classic cold-start-after-deploy incident.

Interview Q&A

Explain socket exhaustion and both of its cures.

Each HttpClient you construct and dispose leaves its TCP connections in TIME_WAIT for up to four minutes; with a limited ephemeral port range, a few hundred requests per second exhausts the ports and new connections fail with SocketException — while the process looks healthy. The naive fix, one static client forever, trades it for stale DNS: the connection pool never re-resolves, so a failover or a scaling event never reaches you. The correct answers are IHttpClientFactory, which pools handlers and rotates them (default two-minute lifetime) so DNS refreshes, or a static SocketsHttpHandler with PooledConnectionLifetime set, which is the same mechanism without DI. Typed clients are my default because they also give a natural place to hang the resilience pipeline and the base address.

Design a retry policy for a payment call.

First establish idempotency, because without it retrying a payment is a duplicate charge: the client generates an idempotency key per logical operation, sends it as a header, and the provider returns the original result on a repeat. Then a small number of attempts — two or three — with exponential backoff and jitter, an overall timeout budget that the retries must fit inside, and retry only on transport failures, 408, 429 (honouring Retry-After) and 5xx; never on 4xx, which will fail identically forever. Wrap it in a circuit breaker so a sustained outage fails fast instead of queueing. And decide the user-facing behaviour explicitly: for payments I would rather return "we are processing this" and reconcile asynchronously than hold an HTTP request open through three retries.

Which cache would you use for a product catalogue read by ten instances?

HybridCache, because it gives me both layers with one API: a short-lived L1 in memory for per-instance speed, an L2 in Redis so a cold instance does not hammer the database, stampede protection so a popular key produces one backend call under a thundering herd, and tag-based invalidation so a category update can evict a group. The knob that matters is LocalCacheExpiration — it bounds how stale one instance can be relative to the others, and it is the thing to tune when someone reports "I updated the price and it still shows the old one on refresh". Before HybridCache this was a hand-written L1/L2 with a SemaphoreSlim for stampede control and a pub/sub channel for invalidation, and everyone's version had a subtle bug — which is a good reason to use the framework's.

How do you invalidate a distributed cache correctly?

Prefer designs that do not need invalidation: short TTLs where staleness is acceptable, and versioned keys (product:42:v7) where it is not, so a write publishes a new key and the old one expires on its own — no coordination, no race. When you must invalidate, use tags (RemoveByTagAsync) so one business event evicts a coherent group, and accept that L1 caches on other instances are eventually consistent unless you add a backplane message. The failure modes to design against are the write-then-invalidate race (a concurrent read repopulates the old value between the two steps — mitigated by invalidating after commit and by short L1 TTLs) and cache penetration on missing keys, where a negative cache entry prevents repeated misses from becoming a database scan.

Where should rate limiting live?

At the outermost layer that can see the identity you want to limit. A gateway or CDN handles volumetric abuse before it costs you a process, and it is the only place a global limit is genuinely global. In-process limiting via AddRateLimiter is for protecting a specific resource — an expensive report endpoint, a downstream with a quota — partitioned by tenant or API key, and it is per instance, so the effective limit multiplies by replica count unless you account for that. I use both: coarse at the edge, fine-grained in the app where the business meaning lives. And I always return 429 with Retry-After and emit a metric per partition, because an invisible limiter is indistinguishable from an outage to the client.

What is a bulkhead and have you needed one?

A bulkhead caps the concurrency any single dependency may consume, so one slow downstream cannot absorb every thread, connection or memory buffer and take the whole service with it — the ship metaphor is exact. In .NET that is a concurrency limiter in the resilience pipeline, or a dedicated connection pool per dependency. It matters most when one process talks to several dependencies with different reliability: without a bulkhead, the flaky reporting service's slowness consumes the pool that the checkout path needs. The signature it prevents is "everything is slow but only one dependency is broken". The cost is that you must size each compartment, and sizing them from guesses gives you artificial ceilings — so I derive them from measured concurrency at p99, with headroom, and expose them as configuration.

How do timeouts compose across layers?

They must form a decreasing budget from the outside in: if the client waits 10 seconds, the gateway should give up before that, the service before the gateway, and the database call before the service — otherwise the outer layer abandons the request while inner layers keep working, burning capacity for a response nobody will read. In .NET that means an HttpClient.Timeout as the outer bound, an attempt timeout inside the retry so a single slow attempt does not eat the whole budget, a CommandTimeout on the database, and CancellationTokens threaded everywhere so cancellation actually propagates. The anti-pattern is the infinite or default timeout somewhere in the middle, which converts a slow dependency into an unbounded queue of stuck requests — the most common root cause I have seen behind "the service just stops responding."

How do you make a POST endpoint idempotent?

Require an Idempotency-Key header, and store the key with the outcome in the same transaction as the business change — a table with a unique constraint on the key is the simplest correct implementation. On a repeat, return the stored response rather than re-executing. The details that separate a working implementation from a broken one: the key must be scoped to the caller so two tenants cannot collide, there must be a state for "in progress" so a concurrent duplicate waits or gets a 409 rather than double-executing, and there must be an expiry so the table does not grow forever. In ASP.NET Core this lives naturally in an endpoint filter applied to a route group. It is also the precondition for safe retries anywhere upstream, which is why I treat it as a platform concern rather than a per-endpoint one.

What does the standard resilience handler give you that hand-rolled Polly does not?

A vetted default ordering — rate limiter, total request timeout, retry, circuit breaker, attempt timeout — with sensible values, telemetry wired into the standard meters and ActivitySource, and configuration binding so the values are operable rather than compiled in. Hand-rolled pipelines usually get the ordering subtly wrong (retry outside the total timeout, breaker outside the retry) and almost never emit metrics, so nobody notices when the breaker is permanently open. Polly v8's resilience pipelines underneath are the same engine, so you can still customise or replace individual strategies. I reach for a bespoke pipeline only for genuinely unusual requirements — hedged requests, per-tenant policies — and even then I start from the standard one and modify it.

A downstream dependency is degrading. Walk me through the incident.

First, confirm the blast radius: is our latency up because of them, or are we amplifying it? The two things I check immediately are whether our circuit breaker is opening (if not, why not — wrong thresholds, or a per-instance breaker that never sees enough traffic) and whether our retries are multiplying their load, because turning retries off is often the fastest way to help both sides. Then shed: enable the fallback or degraded mode for that feature so the rest of the product keeps working, and if there is no fallback, that is the top action item afterwards. Communicate with the owning team with numbers — request rate, error ratio, our retry multiplier — rather than "your service is broken". Afterwards, the review questions are why the breaker did not protect us, whether the timeout budget was decreasing, and whether the feature could have degraded gracefully instead of failing.

13Observability and diagnostics

Modern .NET observability is not a vendor SDK bolted on; it is three built-in primitives that OpenTelemetry merely exports. ILogger for events, System.Diagnostics.Metrics.Meter for aggregates, and System.Diagnostics.Activity for distributed traces — the last one is an OpenTelemetry span, with W3C traceparent propagation on by default. The mental model: your code emits to BCL types; OpenTelemetry subscribes and ships. Swapping backends is a package change, not a code change, and that is the reason to use the primitives rather than a vendor client.

Logging discipline first, because it is where most cost and most noise come from. Use the source-generated logging pattern ([LoggerMessage]): it produces a strongly-typed method with no boxing, no string formatting when the level is disabled, and a stable EventId. Interpolated strings inside LogInformation($"...") are the anti-pattern — they format eagerly even when the level is off, they allocate, and they destroy structure so the message becomes unqueryable. And structure is the point: log fields, not sentences, so "show me all failures for tenant X in the last hour" is a query rather than a regex.

The three signals answer different questions and you need all three. Metrics tell you something is wrong and how widely — cheap, aggregated, alertable, but with no per-request detail and a hard constraint on tag cardinality. Traces tell you where the time went for a specific request across services — expensive, so sampled, which means the interesting request may not be in there unless you use tail-based sampling or always sample errors. Logs tell you what happened in detail — expensive to store and easy to drown in. The mature setup alerts on metrics, pivots to traces via exemplars, and reads logs filtered by trace id, which is why every log line must carry the trace id.

Interview trap

Unbounded metric cardinality. Every distinct combination of tag values creates a separate time series, so adding user_id, order_id or a raw URL path as a dimension turns one metric into millions — it will blow up your backend's bill and often the agent's memory before that. Tags must be low-cardinality and bounded: tenant (if you have dozens, not millions), status code, endpoint route template (never the resolved path). The related trap is logging personal data or secrets: LogInformation("Request {@Request}", req) with destructuring will happily serialize an authorization header or a card number into your log store, which is a compliance incident, not a bug. Redaction belongs at the logging boundary — Microsoft.Extensions.Compliance.Redaction exists for exactly this.

Solution sketch

Interview Q&A

Logs, metrics, traces — what does each answer, and how do you connect them?

Metrics answer "is something wrong, and how much of the fleet?" — cheap, pre-aggregated, alertable, cardinality-constrained. Traces answer "where did the time go for this request across these six services?" — rich but sampled, so you need error-biased or tail sampling to keep the interesting ones. Logs answer "what exactly happened here?" — detailed, expensive, and only useful if structured. You connect them with the trace id: every log line carries it (ASP.NET Core does this automatically once you enable the OTel logging provider or add Activity.Current to the scope), and metrics carry exemplars pointing at sample traces. The operational shape I aim for is: alert fires on a metric, one click to an exemplar trace, one click to that request's logs — no grep, no guessing.

How do you decide what to alert on?

On symptoms the user feels, expressed as SLOs — request success ratio and latency percentiles per endpoint class — not on causes like CPU or memory, which produce pages that nobody can act on. Then a small number of cause-level alerts for conditions that are always wrong regardless of symptoms: a circuit breaker open for more than a few minutes, a consumer's queue lag growing monotonically, a certificate expiring in seven days, OOMKill events. Error-budget burn rate alerting (fast and slow windows) gives you urgency without flapping. And every alert must name an action; if the runbook says "look at the dashboard", it is a dashboard, not an alert. I would rather have six alerts people trust than sixty they route to a muted channel.

What is Activity and how does context propagate?

Activity is the BCL's span type: it has a trace id, a span id, a parent, tags, events and links, and it flows on ExecutionContext so it survives awaits without you passing anything. ASP.NET Core starts one per request from the inbound traceparent header (W3C format, the default since .NET 5), and HttpClient injects the current one outbound. ActivitySource is how your code creates child spans, and it only allocates when someone is listening, so instrumentation is close to free when disabled. The things that break propagation are worth naming: crossing a queue (you must carry traceparent in the message headers and use links, since the consumer is not a child in wall-clock terms), and any place where ExecutionContext is deliberately suppressed. Baggage propagates key/value context alongside, and should be used sparingly because it travels on every hop.

Your service is slow and you have five minutes. What do you run?

dotnet-counters monitor -p PID System.Runtime Microsoft.AspNetCore.Hosting first, because it distinguishes the main hypotheses in seconds: high CPU with low GC points at the code, high time-in-gc points at allocation, a growing thread-pool queue with low CPU points at blocking, and a rising exception rate points at control-flow-by-exception. If it is the code, dotnet-trace collect --profile cpu-sampling for thirty seconds and read the hot stacks. If it is a hang, dotnet-dump collect and look at what the threads are parked on. In parallel I check the trace waterfall for a representative slow request, because half the time the answer is a downstream dependency and nothing in my process is wrong at all. These tools install as global tools and work in a container if you can exec into it — worth having in the image or as an ephemeral debug container.

How do you keep logging costs under control without losing the ability to debug?

Default to Information for your own code and Warning for framework namespaces, configured per-category so you can raise one area without raising everything. Make the level runtime-adjustable through configuration reload, so an incident can turn on Debug for a single namespace for ten minutes rather than requiring a deploy. Sample high-volume, low-value events rather than dropping them entirely. Push detail into traces and metrics, which are cheaper per unit of insight than log lines. And audit the top talkers periodically — in every codebase I have worked on, two or three log statements account for most of the volume, and they are almost always inside a loop or on a health-check path. Structured logging is what makes all of this possible, because you can aggregate by EventId instead of eyeballing text.

What are the .NET 10 authentication metrics good for?

They turn a security question into a dashboard. aspnetcore.auth.authenticate.duration shows when your identity provider or token validation is the latency source, which is otherwise invisible because it happens before your handler. aspnetcore.auth.challenges and aspnetcore.authz.requests show the ratio of anonymous to authorised traffic and how often authorization actually denies — a sudden change in either is usually a client bug or an attack. The Identity family (check_password_attempts, verify_token_attempts, sign_ins, two-factor counters) gives you credential-stuffing and account-takeover signals with no custom instrumentation. Previously every team hand-rolled this, badly. I would alert on failed-to-successful password check ratio and on a spike in challenges, and keep the rest for dashboards.

How do you debug a problem that only happens in production?

Escalate the observation without escalating the risk. First, raise log level for the specific category on one instance via configuration reload. Second, add a targeted metric or span attribute and ship it — a cheap change that turns a guess into data. Third, capture artefacts from one pod: dotnet-counters live, then a trace or a gcdump, ideally from an instance taken out of rotation so the capture cost harms nobody. dotnet-monitor as a sidecar automates that: trigger a dump when p99 exceeds a threshold, then upload it. Only after that would I consider a debugger. Two guard rails I insist on: never capture a full-process dump on a live serving instance without accounting for the pause and for the fact that the dump contains secrets and personal data, and always write down the hypothesis before capturing, so the artefact is chosen to falsify something rather than to browse.

What is dotnet-monitor and where does it fit?

It is a sidecar or systemd service that exposes the diagnostics IPC pipe over HTTP: you can pull counters, traces, dumps and logs from a running process on demand, or configure rules that trigger a capture automatically when a condition holds (p99 over a threshold, GC over a percentage, an exception type appearing). It fits exactly where interactive debugging is impossible — Kubernetes, where you cannot attach, and the pod may be gone by the time you look. The trade-offs to name: it must be secured (authenticated, not exposed publicly) because it can dump your process memory, and dumps contain secrets, so egress and retention need a policy. In practice I run it in staging always and in production behind an explicit toggle plus network policy.

How do you instrument a background worker so it is as observable as a web request?

Give each unit of work its own Activity from your own ActivitySource, with the trace context taken from the message headers as a link rather than a parent, since the producer's request finished long ago. Emit a duration histogram and a success/failure counter tagged by message type and outcome, plus a queue-lag gauge, because lag is the metric that actually predicts user pain. Create a DI scope per message so logging scopes, options snapshots and the DbContext behave like they do in a request. And log start and end with the message id and attempt number, so a poison message is traceable across retries. The failure I have seen most is a worker with excellent logs and no metrics: you can explain any single failure and cannot tell whether the system is keeping up.

How would you roll out observability to a fleet that has almost none?

Standardise before instrumenting. One shared package that configures OpenTelemetry, resource attributes (service name, version, environment), the standard ASP.NET Core and HttpClient instrumentation, the logging provider with trace-id enrichment, and the exporter — so a service adopts observability with one line and cannot get the conventions wrong. Then pick the top three services by traffic, land it, and build the alert-to-trace-to-log path end to end so people see the payoff before being asked to do work. Custom metrics come last and per-domain, once the plumbing is trusted. The organisational trick is to make the shared package the path of least resistance rather than a mandate; the failure mode is a beautiful platform nobody adopts because it takes a day per service to wire up.

14Security: authentication, authorization and data protection

ASP.NET Core separates the two words carefully, and so should you in the interview. Authentication establishes a ClaimsPrincipal — a set of identities, each a bag of claims — via a scheme (cookies, JWT bearer, OIDC, negotiate). Authorization decides whether that principal may do this thing, via policies evaluated against endpoint metadata. UseAuthentication populates HttpContext.User; UseAuthorization enforces. The three verbs to know precisely: challenge (you are not authenticated — 401 or a redirect to login), forbid (you are authenticated but not permitted — 403), and sign in/out (issue or clear the authentication ticket).

Policies over roles. Roles are a claim type with special syntax; policies are the extensible mechanism — RequireClaim, RequireAssertion, or a custom IAuthorizationRequirement with one or more handlers. The rule that scales: authorize on permissions ("orders:write") granted to roles, not on role names scattered through [Authorize(Roles="Admin")] attributes, because the day someone invents a second kind of admin you would otherwise touch two hundred files. For anything that depends on the specific object being acted on — "may this user edit this document" — you need resource-based authorization, an explicit IAuthorizationService.AuthorizeAsync(user, resource, policy) call after loading the resource, because an attribute cannot see data that has not been fetched yet.

What is new in .NET 10. ASP.NET Core Identity ships passkeys — WebAuthn/FIDO2 credentials — in the box, with the Blazor Web App template offering passkey management out of the box; this is phishing-resistant authentication without a third-party library, and it is the single most quotable security change of the release. Second: cookie authentication now returns 401/403 instead of redirecting to the login page when the endpoint is marked as an API (via the new IApiEndpointMetadata, applied automatically to [ApiController], JSON-returning minimal APIs and TypedResults) — which kills the perennial bug where a fetch call receives a 200 with an HTML login page. Third, the auth/authz/Identity metrics from unit 13 make authentication observable.

Data Protection is the subsystem nobody thinks about until it breaks. It encrypts and signs cookies, antiforgery tokens and anything you pass through IDataProtector, using a rotating key ring. By default the keys live on the local filesystem, unencrypted-at-rest outside Windows — so in a multi-instance deployment, instance A cannot decrypt instance B's cookie and users get randomly signed out, and a container restart invalidates every session. The fix is a shared, persisted key ring (PersistKeysToAzureBlobStorage, Redis, a database) protected at rest (ProtectKeysWithAzureKeyVault, or DPAPI/certificate on Windows) and an explicit SetApplicationName so apps that should share a ring do and apps that should not, do not.

Interview trap

Three that recur. First, authorization on the client: hiding a button is UX, not security — every endpoint must check independently, which is what FallbackPolicy plus explicit [AllowAnonymous] gives you (deny by default, opt out visibly). Second, the default 5-minute ClockSkew on token validation: a "revoked" 5-minute token is actually valid for ten, which matters when your incident response plan says "revoke the token". Third, losing the Data Protection key ring — the symptom is users logged out on every deploy or bouncing between instances, and the root cause is ephemeral container storage. A fourth honourable mention: [Authorize] on a controller with an action that has [AllowAnonymous] does what you expect, but [Authorize] on a base class with a derived override does not always — which is why a fallback policy is more reliable than attribute discipline.

Try it

1. Run two instances of a cookie-authenticated app behind a round-robin proxy with default Data Protection settings, log in, and refresh repeatedly.

Expected outcome

You will be signed out roughly every other request: each instance generated its own key ring, so a cookie encrypted by A fails to decrypt on B, and the framework treats an undecryptable ticket as no ticket at all. Persisting the ring to shared storage with a common SetApplicationName fixes it immediately — and doing this experiment once makes the failure instantly recognisable in production. The fallback-policy experiment is a free security audit: every endpoint that suddenly 401s and should not is one you must consciously mark [AllowAnonymous], and in my experience the exercise always turns up at least one endpoint that was unintentionally public.

Interview Q&A

Cookies or JWTs for a browser-based SPA?

For a first-party SPA I default to the BFF pattern: the browser holds an HttpOnly, Secure, SameSite=Lax cookie against a backend that owns the tokens and proxies to APIs. That keeps tokens out of JavaScript entirely, which removes the whole XSS-steals-your-token class, and gives you server-side revocation because the session is real state. Bearer tokens in the browser mean choosing between localStorage (readable by any injected script) and memory (lost on refresh), plus a refresh-token dance with its own rotation and replay-detection requirements. JWTs remain the right answer for machine-to-machine calls, for mobile and for third-party API access. The cost of the BFF is CSRF exposure, handled by antiforgery tokens and SameSite, and a stateful component you must scale.

How do you revoke a JWT?

Strictly, you cannot — a signed, self-contained token is valid until it expires, which is the trade you made for statelessness. So the practical answers are: keep access tokens short (5–15 minutes) so the revocation window is bounded; keep refresh tokens long but stateful and revocable, with rotation and reuse detection so a stolen refresh token is caught; and maintain a denylist for the emergency case, keyed by jti or by user with a "tokens issued before" timestamp, checked in a distributed cache. Remember the default ClockSkew of five minutes extends every window unless you tighten it. And a token with a two-hour lifetime is a two-hour incident, which is why "how long are your access tokens?" is a question I ask in design reviews.

Design an authorization model for a multi-tenant SaaS.

Three layers. Tenant isolation first, and it must not be an authorization check — it is a data-access invariant: the tenant id comes from the validated token, is put into a scoped context by middleware, and is enforced by a query filter or row-level security so no query can accidentally omit it. Then permissions: fine-grained strings (orders:write, invoices:read) granted through roles that tenants can define themselves, evaluated by policies rather than role-name attributes. Then resource-based checks for object-level rules, done with IAuthorizationService after loading the entity. The failure I have seen most is tenant id taken from a header or a route parameter and merely checked — one missing check away from cross-tenant data exposure. Belt and braces: integration tests that attempt cross-tenant access for every endpoint, generated from the route table.

What do you check in a security-focused code review of an ASP.NET Core service?

Deny-by-default authorization (a FallbackPolicy, with every [AllowAnonymous] justified), no secrets in configuration files or logs, HTTPS enforced with HSTS in production, forwarded headers restricted to known proxies, CORS with an explicit origin list, request size and rate limits, and parameterised data access — EF Core does this by default, but FromSqlRaw with interpolation does not. Then output: DTOs rather than entities, no stack traces or inner exception text outside Development, and problem details that do not leak internals. Then dependencies: NuGetAudit enabled and failing the build on known vulnerabilities. Finally the specific traps of this stack — Data Protection key ring persisted, ClockSkew tightened, antiforgery on cookie-authenticated form posts, and no TypeNameHandling anywhere near Newtonsoft.

Explain Data Protection and how it fails.

It is a key-management and cryptography subsystem: a rotating ring of keys (90-day default lifetime) used to encrypt and sign cookies, antiforgery tokens and anything you protect with IDataProtector, with purposes providing isolation so a cookie protector cannot decrypt a token protector's payload. It fails when the ring is not shared or not persisted: on Linux containers the default location is inside the container, so every replica has its own ring and every restart discards it — users get logged out on deploy and bounce between instances behind a load balancer. The fix is persistence to shared storage plus encryption at rest plus an explicit SetApplicationName, since the application name is part of the isolation. The second failure is the opposite: two unrelated apps sharing a ring and a name, so one can forge the other's cookies.

What are passkeys and would you adopt them?

Passkeys are WebAuthn/FIDO2 credentials: a key pair generated by the authenticator (phone, laptop, security key), with the private key never leaving the device and the signature bound to the origin — which makes them phishing-resistant in a way no OTP or push notification is, because a lookalike domain cannot produce a valid assertion. .NET 10 ships support in ASP.NET Core Identity with template-level management UI, so you no longer need a third-party library for the ceremony. I would adopt them as a strong second factor first and as a passwordless primary later, because the hard part is not the cryptography, it is recovery: device loss, account bootstrapping, and support processes that do not reintroduce a phishable channel. Roll it out to internal and high-privilege users first, where the recovery process can be human.

When is antiforgery needed and when is it noise?

It is needed whenever the browser attaches credentials automatically — cookies, Windows auth — because that is exactly what lets a third-party site trigger an authenticated request on the user's behalf. It is noise for a pure bearer-token API, because the browser does not attach an Authorization header to a cross-site request. SameSite=Lax (the modern default) blocks the classic cross-site form POST and covers much of the risk, but it is not sufficient alone — it does not protect against same-site subdomain attacks and browsers vary. In .NET 8+ minimal APIs, form binding requires antiforgery explicitly via AddAntiforgery and the validation middleware, which is a deliberate secure-by-default change. My rule: cookie-authenticated state-changing request implies antiforgery, no exceptions.

How do you handle service-to-service authentication inside a cluster?

Prefer workload identity issued by the platform — a managed identity, a projected service-account token, or SPIFFE/mTLS from the mesh — over long-lived shared secrets, because those rotate automatically and are scoped to the workload rather than copied into a config store. If you must use a token, it is the client-credentials flow against your identity provider with a cached token and proactive refresh, and the receiving service validates issuer, audience and scope like any other JWT. mTLS via a service mesh gives you mutual identity at the transport with no application code, at the cost of operating the mesh. Whatever you choose, authorization still belongs in the application: transport identity says who is calling, not what they may do, and conflating the two is how a compromised low-privilege service reaches everything.

An endpoint returns 401 to a fetch call that should be authenticated. How do you debug it?

Work outside-in. Is the credential arriving — check the raw request at the proxy, since CORS preflight, a stripped Authorization header, or a cookie blocked by SameSite on a cross-site call are all common. Is authentication running before authorization, and is the right scheme the default for that endpoint? Then token validity: issuer, audience, signing key rotation (a cached JWKS that missed a rotation gives exactly this), and lifetime including clock skew — enabling IdentityModelEventSource.ShowPII in a non-production environment turns the generic failure into a specific one. In .NET 10 there is a new wrinkle worth knowing: cookie auth now returns 401 for API-marked endpoints instead of a 302 to the login page, so a client that was silently receiving an HTML login page with status 200 will start seeing an honest 401 after upgrade — which looks like a regression and is actually the bug becoming visible.

How would you approach a security review for a service you did not write?

Start from the data, not the code: what is the most sensitive thing here, who may see it, and what would an attacker want? Then map the entry points — the route table is a complete inventory — and check each against the authorization model, looking specifically for the ones that are anonymous, that take an identifier from the client, or that return more than the caller needs. Then trust boundaries: where does user input reach a query, a file path, a deserializer, an outbound URL (SSRF), or a shell? Then the platform items — TLS, secrets, dependency vulnerabilities, logging of sensitive data, Data Protection. Finish with the things that only show up in operations: what is logged on failure, what an attacker can learn from error messages and timing, and whether there is any detection at all. I write findings with a severity and a concrete fix, and I separate "this is exploitable now" from "this is fragile", because conflating them is how security reviews get ignored.

15The big Q&A

Everything an interviewer reaches for that is not one of the fourteen building blocks: the ecosystem decisions around the framework, the data layer that sits under every service, the tooling, the migration reality, and the scenario questions where they are testing judgment rather than recall.

Architecture & ecosystem decisions

When is ASP.NET Core the wrong choice?

When the deployment target cannot carry a runtime or a 10 MB native binary — deeply embedded devices, where Rust or C is the answer. When the team's centre of gravity is elsewhere and the service is small: a five-endpoint sidecar in a Python shop should be Python. When you need a mature, opinionated ecosystem .NET does not have — heavy data science and ML training pipelines still belong in Python, and .NET's role there is serving the model, not training it. And when startup latency dominates in a way even NativeAOT cannot fix, though that bar is now genuinely low. What is not a good reason: "Java/Go is faster", which has not been true in a general sense for years, or licensing, since the whole platform is MIT-licensed and cross-platform.

Modular monolith or microservices for a new .NET product?

Modular monolith first, almost always: one deployable, in-process calls, one transaction boundary, one set of dashboards — and modules with enforced boundaries (separate projects, internal types, architecture tests that fail a cross-module reference) so that extracting a service later is a project-file change rather than an archaeology project. Microservices buy independent deployment and scaling, and they cost you distributed transactions, network failure modes, and an operational burden that a small team cannot carry. The honest heuristic is organisational: you split when two teams' release cadences genuinely conflict, or when one component's scaling profile is wildly different. .NET makes both work; what decides it is how many people are shipping, not how the diagram looks.

gRPC, REST or messaging for internal communication?

REST/JSON for anything crossing an organisational boundary or consumed by browsers — universal tooling, cacheable, debuggable with curl. gRPC for internal service-to-service where you control both ends: contract-first with protobuf, code generation in both directions, HTTP/2 multiplexing, streaming, and roughly an order of magnitude less payload than JSON. Messaging when the interaction is genuinely asynchronous — the caller does not need the answer now, and you want the buffer and retry semantics a broker gives you. The most common mistake is using synchronous calls to model an asynchronous business process, which chains availability: five services at 99.9% in series is 99.5%. Note also that gRPC-Web exists for browsers but adds a proxy hop, and that Grpc.AspNetCore is AOT-compatible, which matters for dense deployments.

What is Aspire and does it change how you build .NET services?

Aspire is an opinionated stack for composing distributed applications: an app host that describes your services and their dependencies (databases, caches, brokers) in C#, service discovery and connection wiring generated from that model, a dashboard with logs, traces and metrics out of the box, and deployment manifests. Two things are worth knowing as of 2026: it dropped the ".NET" prefix at version 13 and is now a polyglot platform with first-class Python and JavaScript resources, and its versioning has been decoupled from the .NET release train — Aspire 13.1 was the release paired with .NET 10. It changes local development substantially (no more docker-compose drift, telemetry from minute one) and changes production less than the marketing suggests, since you still deploy to Kubernetes or a cloud service. I would adopt it for the inner loop and evaluate its deployment story separately.

How do you decide what belongs in the framework versus a shared internal library?

Anything that encodes an organisational convention — telemetry setup, authentication configuration, resilience defaults, problem-details shape — belongs in a shared package, because the value is uniformity and the cost of drift is real. Anything that encodes business logic does not, because a shared package becomes a distributed monolith the moment two teams need different behaviour and one of them wins. My test is whether an upgrade of the package would ever need coordinating with a team's release: if yes, it is too coupled. I also insist shared packages be thin wrappers over the framework rather than abstractions away from it, so someone reading the code can still find the Microsoft documentation that explains it.

Data access

EF Core or Dapper?

EF Core for the write side and for anything with a rich object model — change tracking, migrations, LINQ, and the unit of work are genuine productivity wins, and its compiled queries and AsNoTracking close most of the performance gap. Dapper (or raw ADO.NET) for read models and reporting queries where you want exactly one SQL statement, no materialisation surprises and no translation guessing. They coexist happily in one service sharing a connection and a transaction, and I would rather have both used deliberately than one used dogmatically. The senior framing: the choice is about who owns the SQL. If the query is complex enough that you would review the SQL in a PR, write the SQL.

How do you find and fix an N+1 query?

Find it in traces: EF Core's instrumentation emits a span per command, so an N+1 is visually unmistakable as a picket fence of identical queries inside one request; failing that, the Microsoft.EntityFrameworkCore.Database.Command logger at Information level shows the same shape. Fix it with Include/ThenInclude for a real join, or a projection with Select that fetches exactly the columns you need — and prefer the projection, because Include on a one-to-many produces a cartesian explosion that EF mitigates with split queries (AsSplitQuery) at the cost of multiple round trips. Prevent it structurally: lazy loading off (it is opt-in, keep it that way), AsNoTracking for reads, and a CI check that fails a test when a single request exceeds a query budget. The version that catches people out is an N+1 caused by serialization touching a navigation property — another reason DTOs, not entities.

How do you handle transactions across a database and a message broker?

You do not — two-phase commit across heterogeneous systems is not available and would not be desirable. The pattern is the transactional outbox: write the business change and an outbox row in the same database transaction, and have a separate publisher read the outbox and publish, marking rows as sent. That gives at-least-once delivery, which means consumers must be idempotent — deduplicate on a message id, or make the operation naturally idempotent. The inverse, the inbox pattern, records processed message ids on the consumer side. The trade-offs to name: added latency (the publisher polls or tails the log), ordering guarantees that are weaker than people assume, and the operational need to monitor outbox lag as a first-class metric. Anything else — publishing before commit, or after, without a record — loses messages in exactly the failure you built the system to survive.

What are EF Core's biggest footguns at scale?

Change tracking on large read sets, fixed by AsNoTracking or projections. Cartesian explosion from multiple Includes on collections, fixed by split queries or projections. Client-side evaluation: since EF Core 3.0 it throws instead of silently pulling the table into memory, which is a big improvement, but a method it cannot translate still fails at runtime rather than compile time. DbContext is not thread-safe, so any parallel use inside one scope corrupts it — a common consequence of Task.WhenAll over queries on one context. Migrations applied automatically from N replicas. And query plan churn from parameter-sensitive queries. EF Core 10 added named query filters (several per entity, selectively disabled), which finally makes multi-tenant plus soft-delete filters composable rather than a single tangled expression.

Performance & debugging

How do you approach a "the API is slow" report with no further detail?

Quantify before theorising: which endpoint, which percentile, since when, and for whom — because "slow" is usually p99 for one tenant on one endpoint, not the average. Then split the timeline: the request duration histogram tells you if it is us; the trace waterfall tells you which span owns the time; if the time is unaccounted for between spans, it is queueing (thread pool, connection pool) rather than work. From there the runtime counters distinguish GC from CPU from blocking. I try hard to avoid the two classic failures — optimising the thing I happen to understand, and optimising the mean when the complaint is the tail. And I write down the hypothesis and the measurement that would falsify it before touching code, because performance work without that discipline is expensive guessing.

What are the highest-leverage performance wins in a typical ASP.NET Core service?

In the order I actually find them: a missing index or an N+1 in the data layer, which usually dwarfs everything else; a synchronous call blocking pool threads; no caching where the same expensive answer is computed repeatedly; serializing far more data than the client needs; and a chatty call pattern to a downstream that should have been one batched request. Framework-level tuning — minimal APIs over MVC, source-generated JSON, response compression — is real but typically single-digit percentages against the multiples the list above delivers. I would rather spend a day on a query plan than a week on allocation micro-optimisation, and I say so explicitly when someone proposes rewriting a service "for performance" before profiling it.

How do you benchmark .NET code credibly?

BenchmarkDotNet, because it handles the things hand-rolled stopwatch loops get wrong: warm-up until tiered compilation and PGO have settled, multiple iterations with statistical analysis, isolation of the process, and diagnosers for allocations and disassembly. Benchmark the right thing — a micro-benchmark of a method that is 2% of the request tells you nothing — and always benchmark against a baseline in the same run so machine noise cancels. For whole-service numbers, a load test (k6, NBomber, bombardier) against a deployed instance with realistic data volumes and a warm-up period, measuring percentiles, not averages. And publish the environment with the result: .NET version, GC mode, core count and container limits change the answer enough that a number without them is not reproducible.

A pod restarts every few hours with OOMKilled. Walk me through it.

First, distinguish a leak from a limit that is simply too low: does the managed heap grow monotonically (gcdump diff), or is it stable while RSS exceeds the limit? If the managed heap is flat, the memory is native — buffers, sockets, a native dependency, or the runtime's heap limit not being derived from the cgroup — and the fix is a limit-aware configuration (DOTNET_GCHeapHardLimitPercent) or finding the native consumer. If it is a leak, the gcdump diff names the type and the retention path. Two .NET-specific twists: with Server GC and no DATAS, per-core heaps can legitimately exceed a small memory limit on a big node, and Kestrel's memory pool used to hold its high-water mark forever, which is fixed by .NET 10's automatic eviction. Interim mitigation is raising the limit; the fix is one of the above, and I would say which is which.

Testing & tooling

How do you test an ASP.NET Core service?

A thin layer of unit tests over the logic that has interesting branches, and a thick layer of integration tests through WebApplicationFactory, which boots the real pipeline in-memory — real routing, real middleware, real DI, real serialization — so it catches the things that actually break: ordering, binding, authorization, and contract shape. Back it with Testcontainers so the database is the real engine rather than an in-memory provider that has different semantics (the EF in-memory provider is not a relational database and will let queries pass that SQL Server rejects). Contract tests where services integrate, and a smoke test against a deployed environment. What I avoid is heavy mocking of the framework: a test that asserts a mock was called proves nothing about whether the endpoint returns 400 for bad input.

What does WebApplicationFactory give you, and what does it not?

It builds your real host in-process with a test server that bypasses the network, so requests go through the entire pipeline with full fidelity and sub-millisecond latency; WithWebHostBuilder/ConfigureTestServices lets you replace specific registrations — a fake payment gateway, a test clock — after your Program.cs has run. What it does not give you: real Kestrel behaviour (no TLS, no HTTP/2 negotiation, no connection limits, no forwarded headers from a proxy), real network failure modes, or anything about your deployment. So it will not catch a misconfigured reverse proxy, a Data Protection key-ring problem or a container that cannot resolve DNS. That is what a smoke test against a deployed environment is for, and knowing which layer catches which bug is the actually useful part of the answer.

How do you keep a large test suite fast?

Share expensive setup: one WebApplicationFactory and one database container per collection rather than per test, with per-test isolation achieved by transactions rolled back or by a schema reset that is cheaper than a container start. Run in parallel, which forces you to remove shared mutable state — a good pressure. Keep the pyramid honest: if 80% of your suite is integration tests, the fix is usually that the domain logic is not testable in isolation. And measure the suite itself; in every slow suite I have profiled, a handful of tests account for most of the time, usually because of a Thread.Sleep waiting for something asynchronous — replace those with FakeTimeProvider or a polling assertion with a timeout.

What does the .NET 10 SDK change about your build and CI?

dotnet test now supports Microsoft.Testing.Platform, which runs tests in-process without the VSTest host — faster, better console output, and AOT-compatible test hosts. CLI argument order was standardised and --cli-schema exposes the command structure as JSON, which is handy for tooling. dotnet tool exec and the dnx script run a tool without installing it, so CI does not need a tool manifest for a one-shot formatter or scanner. Container publishing (/t:PublishContainer) now covers console apps and lets you pick the image format explicitly. And file-based apps (dotnet run app.cs) can be published, including to NativeAOT, which makes single-file build scripts a genuine option instead of a toy. None of it is transformative individually; together it removes a lot of pipeline yak-shaving.

Legacy & migration reality

How would you migrate a large .NET Framework monolith?

Strangler fig, with a proxy in front — YARP is ideal because it is .NET and route-aware. Stand up a new ASP.NET Core app beside the old one, move one bounded capability at a time, and route that path prefix to the new app while everything else still goes to the legacy one; the users never see a big-bang cutover and every step is independently revertible. Before that, do the mechanical work in place: retarget projects to SDK-style, replace packages.config, remove System.Web dependencies from business logic, and get the code compiling against netstandard2.0 where possible so it can be shared during the transition. Use the .NET Upgrade Assistant for the repetitive parts. The two things that decide success are shared session/authentication state during the overlap (a Data Protection ring both sides understand, or an OIDC provider both use) and a definition of done that includes deleting the old code — otherwise you run two systems forever.

What legacy ASP.NET Core patterns will I still see, and should I change them?

Startup.cs with ConfigureServices/Configure (fine, still supported); IHostingEnvironment and IApplicationLifetime, the pre-3.0 names now obsolete in favour of IWebHostEnvironment/IHostApplicationLifetime; UseStaticFiles where MapStaticAssets (.NET 9) now gives build-time compression and fingerprinting; Swashbuckle where the built-in OpenAPI generator now suffices; IMemoryCache plus a hand-rolled distributed layer where HybridCache exists; System.Net.Http clients constructed by hand; and Newtonsoft as the app-wide serializer. My rule is that none of these justify a dedicated migration project — change them when you are already in the file, prioritise the ones with a security or reliability dimension (hand-built HttpClient, Newtonsoft's TypeNameHandling), and never let a "modernisation" PR touch fifty files it does not otherwise need to.

Something you own depends on a package that has not been updated in three years. What now?

Assess before acting: is it actually broken, or merely quiet? A small, stable, dependency-free library that still works on .NET 10 is not a problem. It becomes one when it blocks a framework upgrade, when it fails a vulnerability scan, or when it prevents trimming/AOT. Then the options, in ascending cost: pin and monitor, fork and patch (viable for small MIT-licensed libraries and often the pragmatic answer), replace with a maintained alternative, or absorb the ~200 lines you actually use into your own codebase. What I would not do is silently suppress the audit warning. I would also write down the decision and the trigger that would revisit it, because "we'll deal with it later" without a trigger means "never".

Judgment & scenarios

What do you flag in a code review of an ASP.NET Core PR?

In rough priority: security (authorization present and deny-by-default, no secrets, no raw SQL interpolation, entities not serialized), correctness under concurrency (captive dependencies, DbContext shared across tasks, missing cancellation tokens, sync-over-async), and resource ownership (undisposed resources, unbounded caches or channels, HttpClient constructed by hand). Then observability: does a failure here produce something an on-call engineer can act on? Then contract: is this a breaking API change, is it documented in OpenAPI, does it have tests at the right level? Style and structure last, and mostly as non-blocking comments. I try to distinguish "this is wrong" from "I would have done it differently" explicitly, because conflating them is the fastest way to make reviews adversarial.

How would you guide a team that wants to rewrite a working service in a new architecture?

Ask what problem the rewrite solves, in measurable terms — deploy frequency, incident rate, onboarding time, a specific latency target. If nobody can name one, the answer is no, and that conversation is more valuable than the rewrite. If there is a real problem, look for the smallest change that addresses it: usually the pain is concentrated in one module, and extracting or rewriting that gets 80% of the benefit at 10% of the risk. If a full rewrite is genuinely warranted, insist on strangler-fig sequencing with production traffic on the new path early, a hard rule that both systems are never both being feature-developed, and an explicit deletion date for the old one. And I would say plainly that rewrites overwhelmingly overrun, because the tacit knowledge in the old code is invisible until it is missing.

You are on call. p99 latency has tripled after a deploy 20 minutes ago. What do you do?

Roll back first, diagnose second — a deploy correlation that tight is enough evidence, and 20 minutes of degradation is not the time to be curious. Then confirm the rollback worked, and only then investigate with the artefacts I have: the diff, the trace waterfall from the bad window, and the runtime counters if I captured them (which is an argument for automatic capture via dotnet-monitor triggers). Common causes in this stack, in the order I would check: a query without an index on a newly added column, a change that made a call synchronous, a serialization change that ballooned payloads, a new dependency call in a hot path, and a configuration change that altered GC or thread-pool behaviour. The follow-up that matters is why the canary did not catch it — if there is no canary, that is the incident's real finding.

How do you introduce a significant change — say NativeAOT, or an upgrade to .NET 10 — to a skeptical team?

Make it small, measurable and reversible. Pick one low-stakes service, do the work myself so the cost is not a tax on someone else's sprint, and produce a before/after with the numbers the team actually cares about — cold start, memory, p99, and how many hours the migration took. Then present the trade-offs honestly, including what got worse, because a proposal with no downsides reads as a sales pitch and gets discounted. Give people an exit: a documented rollback and a decision point after a defined trial. And separate the deadline-driven from the optional: ".NET 8 and 9 lose security support on 2026-11-10" is not a preference, while "we could adopt AOT for the sidecars" is, and treating them the same way burns credibility on the one that matters.

What is your framework for choosing between two reasonable technical options?

Write down what would have to be true for each to be the right answer, then look for the cheapest evidence that discriminates between them — usually a timeboxed spike against the actual constraint rather than a document. Weigh reversibility heavily: a decision that is cheap to undo deserves far less analysis than one that shapes the data model or the deployment topology, and treating them identically is how teams spend three weeks choosing a logging library. Consider the team's actual capacity to operate the thing at 3 a.m., not just to build it. Then decide, record the decision and its assumptions in an ADR, and name the signal that would make us revisit. The failure mode I guard against most is deciding by seniority or enthusiasm rather than by the constraint that actually binds.

16Night-before cheat sheet

Ten sentences you can say out loud, confidently, and that each open a door to a deeper conversation.

  1. .NET 10 is the current LTS — shipped 2025-11-11, serviced to November 2028, currently at 10.0.11 — and .NET 8 and .NET 9 both lose support on 2026-11-10, so "we're on LTS" is no longer a plan.
  2. An ASP.NET Core app is a generic host whose web server is just another IHostedService: build-time registers services, run-time composes middleware, hosted services start in registration order and stop in reverse, with a 30-second default shutdown timeout.
  3. Configuration is a layered key–value store where the last provider wins — command line beats environment variables beats environment JSON beats base JSON — and the options pattern with ValidateOnStart turns a bad config into a failed boot instead of a 500 at 3 a.m.
  4. Three DI lifetimes with one rule: never depend on something shorter-lived than yourself; ValidateScopes and ValidateOnBuild catch the violation at startup, and keyed services plus TimeProvider (both .NET 8) removed most of the reasons to hand-roll factories.
  5. Middleware order is semantics: forwarded headers, exception handler, HTTPS, routing, CORS, rate limiting, authentication, authorization, endpoints — and authorization must sit after routing because it reads the selected endpoint's metadata.
  6. Minimal APIs bind by inference (complex type means body, and there can be only one), and .NET 10 finally gave them source-generated validation via AddValidation(), alongside built-in OpenAPI 3.1 with YAML output and XML doc comments flowing into the document.
  7. Async in a server is about thread economy, not speed: sync-over-async blocks pool threads, the pool injects new ones only a couple per second, and the result is fleet-wide latency with low CPU — the signature of thread-pool starvation.
  8. The GC is generational with a non-compacted Large Object Heap above 85 000 bytes; Server GC is the ASP.NET Core default and DATAS — on by default with Server GC since .NET 9 — is why memory graphs drop when you upgrade.
  9. Tiered compilation plus dynamic PGO (default since .NET 8) means the JIT devirtualizes and inlines based on observed types, so a warmed-up JIT usually out-throughputs NativeAOT — AOT is for startup, density and short-lived processes, not peak speed.
  10. The .NET 10 headline features I would name unprompted: WebAuthn passkeys in Identity, cookie auth returning 401/403 instead of a login redirect for API endpoints, Kestrel memory-pool eviction with a meter, auth/authz/Identity metrics, escape analysis extended to struct fields and delegates, and Arm64 write barriers cutting GC pauses by 8–20%.
