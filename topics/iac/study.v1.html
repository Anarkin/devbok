IaC (Terraform & Bicep)

study · Terraform 1.16.1 · Bicep v0.47.16 · released 2026-09-02 / 2026-09-08

This guide treats "IaC" as the underlying discipline — declarative, versioned, idempotent infrastructure change — and grounds it in the two tools the topic names: Terraform (multi-cloud, HCL2, now BSL-licensed under IBM/HashiCorp with OpenTofu as the Linux Foundation's open-source fork) and Bicep (Azure-native, a transpiler that compiles to ARM JSON and has no state of its own). Terraform is at 1.16.1 (2 Sep 2026) — its most interview-relevant recent addition is a resource lifecycle block that can now say destroy = false, alongside provider-preserved private plan state and import blocks that finally work for resources nested in modules; Bicep is at v0.47.16 (8 Sep 2026), which just shipped an extends config-inheritance chain for bicepconfig.json and an experimental bicep docs generate command, on top of GA'd @retryOn retries and extensible parameter files. Both ecosystems have converged on the same three "modern" practices: typed, versioned modules pulled from a registry instead of copy-pasted; a plan or what-if review gate in front of every apply; and policy-as-code enforcement running in the pipeline instead of in a reviewer's head. At lead/principal altitude, treat the syntax below as things you verify at speed — the real ground this guide covers is architecture: who owns state, how a change is reviewed and rolled back, and how you walk a team off a decade of console clicks or hand-maintained ARM JSON.

01 · Foundations: Declarative IaC, Idempotency & Drift

Infrastructure as Code starts from a specific claim: infrastructure should be described the way you describe a target state, not the way you describe a sequence of steps to reach it. A shell script that runs az group create then az storage account create is automation, but it is imperative — it encodes a path. A Terraform or Bicep file that declares "there is a resource group named X containing a storage account named Y" is declarative — it encodes a destination, and a separate engine (Terraform's core, or the Azure Resource Manager for Bicep) is responsible for diffing that destination against whatever exists right now and computing the path itself. This is the single idea every other unit in this guide builds on: once a tool owns the diff-and-plan step, you get properties an imperative script structurally cannot give you — the same file can be applied to an empty subscription or a partially-built one and converge both to the same place, and the tool can show you the path before committing to it.

That convergence property has a name, idempotency: applying the same configuration N times has the same effect as applying it once. The cleanest mental model is a thermostat, not a light switch. A light switch (imperative) either was already flipped or fails loudly; a thermostat (declarative) is told "72°F" and runs whatever combination of heating and cooling closes the gap between the current temperature and that setpoint — run it a hundred times and it settles, it doesn't overheat the room. Terraform's plan/apply loop and Bicep/ARM's incremental deployment mode are both thermostats: on the first run they create everything from nothing; on the second run, with nothing changed, they compute an empty diff and do nothing. This is also why "day 1" (initial provisioning) and "day 2" (ongoing changes: a new subnet, a bumped SKU, a removed resource) are the same operation in IaC — you edit the declaration and reapply — where in a purely imperative world day 2 usually means writing a different script than day 1 ever ran.

The idea a declarative engine actually has to solve is drift: the gap between what your configuration says should exist and what is actually running, caused by anything that changed infrastructure outside the tool's own apply — a teammate's console click, an autoscaler resizing a node pool, another pipeline, or a manual break-glass fix during an incident. Terraform detects drift by refreshing state from the real provider APIs before every plan (or on `terraform plan -refresh-only`) and shows you the delta; Bicep/ARM, having no state file of its own, only sees drift indirectly — a normal incremental deployment won't touch a property it doesn't mention, so an out-of-band change to something the template never set can silently persist forever until someone happens to declare it. That difference — one tool actively tracks "what I made," the other only ever compares "what I'm about to send" against live resources — is the seed of unit 02, and it is worth previewing here because it changes what drift even means in each tool.

The same intent, two engines

Look at the same destination declared both ways. Neither snippet is a script — neither says "create," both just assert a fact about the world the engine is responsible for making true:

resource "azurerm_resource_group" "app" {
  name     = "rg-billing-prod"
  location = "westeurope"
  tags = { costcenter = "billing", managed_by = "terraform" }
}
resource appRg 'Microsoft.Resources/resourceGroups@2025-04-01' = {
  name: 'rg-billing-prod'
  location: 'westeurope'
  tags: { costcenter: 'billing', managed_by: 'bicep' }
}

Run either a second time with nothing edited and the tool reports zero changes — Terraform prints "No changes. Your infrastructure matches the configuration," ARM's what-if reports an empty diff. Edit the tags value and rerun: both compute a minimal, targeted update rather than a destroy-and-recreate, because neither field forces replacement. That "which fields force replacement" question — Terraform calls it ForceNew in provider schema, ARM calls entire resource types immutable-on-certain-properties — is itself a common interview probe, covered concretely in units 03 and 04.

Interview trap

"Idempotent" does not mean "side-effect-free" or "safe to rerun blindly," and candidates who equate the two get caught by the first follow-up. A Terraform null_resource with a local-exec provisioner and no triggers map runs its script on every apply that touches that resource's dependency graph — the resource block is idempotent (Terraform doesn't recreate it), but the side effect inside the provisioner is not. Likewise, a Bicep deployment in Complete mode (as opposed to the default Incremental) will delete any resource in the target scope that isn't in the template — rerunning the "same" deployment against a scope where someone added an unrelated resource by hand is destructive, not idempotent in the way people assume. The honest answer is: the engine's reconciliation is idempotent, but idempotency is a property you have to actively preserve inside anything with a side effect (provisioners, deployment scripts, external data sources).

Interview Q&A

What problem does Infrastructure as Code actually solve that a well-organized set of admin runbooks doesn't?

Runbooks describe steps a human (or script) executes once; they don't give you a machine-checkable diff between "what should exist" and "what exists," so there's no cheap way to know if reality has drifted or to safely re-run a runbook against a partially-built or already-built environment. IaC's declarative model makes the target state itself the artifact under version control, so the diff, the review, and the audit trail are all byproducts of the same file — a runbook gives you repeatability at best, IaC gives you repeatability plus a verifiable, diffable source of truth.

Explain idempotency to someone who's never heard the term, using a non-technical analogy.

A thermostat set to 72°F doesn't care whether the room starts at 60°F or already at 72°F — it runs whatever heating or cooling closes the current gap, and once there's no gap, it does nothing. Set it to 72°F a hundred times in a row and nothing bad happens, because the instruction is "reach this state," not "run these steps." A declarative IaC apply is the same: it computes the gap between declared and actual, acts only on the gap, and converges to a stable no-op once they match.

Is a Terraform apply always idempotent? Give a case where it isn't, in practice.

The core resource lifecycle is idempotent, but anything that shells out is only as idempotent as what it shells out to. A null_resource paired with a local-exec provisioner re-runs its command whenever the resource is touched (unless pinned with triggers), and if that command isn't itself idempotent — appending a line to a file, calling a non-idempotent API — repeated applies produce different real-world outcomes even though Terraform reports the resource as unchanged. The lesson for a lead: idempotency is a contract you have to preserve at every boundary where Terraform hands control to something outside its own state model.

How does drift detection differ between Terraform and Bicep at a mechanical level?

Terraform keeps a state file recording every attribute of every resource it created, and a plan first refreshes that state against live provider APIs, surfacing any attribute that changed out-of-band as drift — even on a field the config doesn't reference, if the provider's schema tracks it. Bicep has no state file; ARM's incremental deployment mode only ever compares the template's declared properties against the live resource's current values for those same properties, so a change to a property the template never mentions is invisible — Bicep can tell you "does the template still produce this state," not "has anything about this resource changed since I last touched it." This gap is exactly why unit 02 exists.

What's the difference between "day 1" and "day 2" operations, and why does IaC collapse the distinction?

Day 1 is initial provisioning — building something from nothing; day 2 is every subsequent change — resizing, patching, adding a resource, retiring one. Imperative automation usually needs separate tooling for each, because a "create" script doesn't know how to safely "update." A declarative engine treats both as the same operation: edit the desired state and reapply, and the diff-and-plan step figures out whether that means create, update-in-place, or destroy-and-recreate for each affected resource — day 2 is not a different feature, it's the same feature run again against a changed file.

Why does Terraform show you a plan before applying, and what would be lost without that step?

The plan is the diff, computed and rendered as data before any provider API call executes — it lets a human (or an automated policy check) veto an unintended destroy-and-recreate, a security-group rule that's about to open 0.0.0.0/0, or a resource silently renamed into a different one, before it's real. Without it you'd be applying blind: the engine would still be declarative and idempotent, but "idempotent and unreviewed" is how a one-line variable typo becomes a production outage, because the first time anyone sees the actual effect is after it already happened.

A teammate says "IaC just means we use Terraform." What's wrong with that framing, at your level?

It collapses a discipline into a single vendor's tool. IaC is the practice of representing infrastructure as versioned, declarative, reviewable text with a diff-and-apply engine in front of it; Terraform, Bicep, Pulumi, and CloudFormation are four implementations of that same idea with different execution models (unit 12 is the decision framework). Conflating the discipline with one tool is how teams end up unable to answer "why Terraform and not Bicep here" — they never separated the requirement from the product.

What's the practical difference between configuration management (Ansible, Chef) and infrastructure provisioning (Terraform, Bicep)?

Provisioning tools are mostly concerned with the existence and shape of resources — a VM, its network, its disks; configuration management tools are concerned with the state inside a running machine — installed packages, files, running services. Both are declarative-leaning and both fight drift, but they operate at different layers, and mature stacks use both together: Terraform/Bicep stands up the VM and hands its IP to Ansible, which then converges the OS-level state. Treating them as competitors rather than complementary layers is a common junior-to-mid confusion.

Why is "push" vs "pull" a meaningful distinction when comparing IaC tools, and where do Terraform and Bicep each sit?

A push model has a central actor (your laptop, a CI runner) computing the plan and issuing API calls outward to the target; a pull model has an agent inside the target periodically fetching and applying its own desired state (Chef, Puppet, Kubernetes controllers). Terraform and Bicep/ARM are both push-only for the resources they manage — there's no agent sitting inside a VNet reconciling itself — though Kubernetes-native IaC (a Terraform provider managing CRDs that a pull-based operator then reconciles) can layer a pull model underneath a push-model apply, which is a nuance worth having ready if the conversation goes there.

What changed recently that's worth naming to show you're current on this topic?

Terraform 1.16 (Aug 2026) added a lifecycle { destroy = false } block, letting a resource be declared un-destroyable by Terraform without the older, blunter prevent_destroy escape hatch conflating "don't destroy" with "error if you try" — a direct response to years of teams accidentally destroying stateful resources during a refactor. On the Bicep side, v0.47 added configuration inheritance (extends in bicepconfig.json), letting a monorepo define linter and module-alias defaults once and have every subdirectory's config layer on top of it instead of duplicating the whole file — small, but exactly the kind of "what's newly available" detail that separates someone reading stale blog posts from someone who checked this week.

How would you explain to a skeptical engineer why "just write a script" isn't good enough at scale, without sounding dogmatic?

Ask them what their script does if it's run against an environment that's half-built because the last run failed at step 7 — most imperative scripts either error out ungracefully or silently re-run steps 1-6 with side effects (a second resource group, a duplicated role assignment). A declarative tool's diff-based apply handles that case for free, because "half-built" is just another starting state it diffs against the target from; that's the concrete, falsifiable claim to lead with, rather than "declarative is better" as an assertion.

02 · State: Terraform's State File vs Bicep's Stateless Model

Terraform's defining architectural choice is that it keeps its own record of what it manages: the state file (by default terraform.tfstate, JSON), a map from every resource address in your configuration to the real-world attributes Terraform observed the last time it touched or refreshed that resource — including values the provider generated, like a VM's assigned private IP or a generated resource ID, that never appear in your HCL at all. Every plan is a three-way diff: configuration (desired), state (last known), and a live refresh of the real provider (actual). That third leg is why Terraform can tell you not just "the config changed" but "the config changed and/or the real world drifted since we last looked" — it is the only one of the two tools in this guide with a persistent memory of its own actions.

Bicep has no equivalent file, by design, because it isn't really a provisioning engine — it's a transpiler. A .bicep file compiles to ARM JSON, and that JSON is submitted to the Azure Resource Manager's own deployment API; ARM does the diffing, and the "record of the past" it consults is simply the live resource graph of the target scope, plus a deployment history it keeps for its own audit purposes (visible as one entry per az deployment group list) but that Bicep never reads back to compute a plan. This is the single fact from which every other Terraform-vs-Bicep operational difference in this guide flows: Terraform's correctness is bounded by "is state accurate," Bicep's correctness is bounded by "is the live resource graph what I assume it is" — different failure modes, different recovery procedures, different things that keep a lead up at night.

The state file being a first-class artifact is also why Terraform has an entire vocabulary of state-surgery commands that Bicep simply has no analogue for: terraform state list, state mv (rename or move a resource's address without touching real infrastructure), state rm (stop managing something without destroying it), import (start managing something that already exists), and the declarative moved block (the modern, code-reviewable replacement for running state mv by hand — HashiCorp's own migration guidance has pushed moved blocks as the default since Terraform 1.1, precisely because a shell command run once by one engineer isn't in version control and a moved block is). Bicep's "I want to adopt an existing resource" story is comparatively humble: because there's no state to reconcile, you just write a resource block whose name and type match something that already exists, and the next incremental deployment treats it as an update rather than a create — no import step needed, but also no explicit record that an adoption happened.

Where the state file actually lives, and why that's the scary part

A local terraform.tfstate file works for a solo experiment and fails immediately with more than one person: two applies racing against the same local file corrupt it or silently overwrite each other's changes. Production Terraform always uses a remote backend — HCP Terraform (formerly Terraform Cloud), an S3 bucket with DynamoDB locking, an Azure Storage Account container, or a Consul/GCS backend — which gives you two things a local file can't: state locking (a second apply blocks or errors while one is in flight, instead of racing it) and a durable, shared source of truth independent of any one laptop. Losing that state file, or letting it drift so far from reality that a refresh can't reconcile it, is the single most common Terraform-specific incident: infrastructure keeps running, but Terraform's own map of it is gone, and every subsequent plan proposes recreating things that already exist. The remediation path is terraform import (one resource at a time, or the newer import block for a batch, declared in code and reviewable) or, if you're rebuilding a mapping wholesale, terraform state push from a hand-reconstructed state — both are recovery surgery, not routine operations.

terraform {

    storage_account_name = "sttfstateprod01"

  }
}

Gotcha

"Bicep has no state, so Bicep can't have a state-related outage" is the trap. Bicep trades state-file risk for scope risk: because ARM's Complete deployment mode treats "anything in this resource group not mentioned in the template" as "should be deleted," a Bicep pipeline that deploys in Complete mode against a resource group that also holds manually-created or differently-pipelined resources will delete them with no warning beyond a what-if diff someone has to actually read. Terraform's analogous risk is state corruption; Bicep's is scope contamination. Both are "the tool did exactly what it was told, and what it was told turned out to be wrong" — the lesson for a lead is that statelessness removes one failure class and does not remove risk in general.

Interview Q&A

What is the Terraform state file, concretely, and what does it store that your configuration files don't?

It's a JSON document mapping every resource address in your config to the real attributes Terraform observed for it — most importantly, provider-generated values that never appear in HCL, like a generated resource ID, an assigned IP, or a computed ARN. Your configuration is desired state; the state file is Terraform's memory of what it actually created and what that turned out to look like, which is what lets a plan diff three things — desired, remembered, and live — instead of just two.

Why does Bicep not need a state file the way Terraform does?

Bicep isn't an independent provisioning engine; it's a transpiler that compiles down to ARM JSON, and it's ARM — the Azure control plane itself — that computes the diff, using the live resource graph of the deployment scope as its only reference point. There's nothing for Bicep to "remember" between runs because the thing that would normally hold that memory (the cloud provider's own record of your resources) already exists and is authoritative; Terraform needs a state file precisely because it manages resources across providers that have no shared, queryable "what does Terraform own here" concept.

Your team's Terraform state file for a production workspace is lost. Walk through your recovery approach.

First, don't run apply — a plan against empty state will propose recreating everything, and if anyone applies it blind, you get duplicate or colliding resources. Recreate the mapping with terraform import (or a batch of declarative import blocks) resource by resource, or, if you have a recent state backup — which is why remote backends with versioning, like an S3 bucket with versioning enabled or HCP Terraform's own state history, are non-negotiable for production — restore that instead of re-deriving it by hand. Afterward, run a plan and confirm it's empty before letting anyone near apply again, and treat the incident as a forcing function to check that state backups/versioning are actually enabled everywhere else.

What's the difference between terraform state rm and terraform destroy?

state rm removes a resource from Terraform's management without touching the real infrastructure at all — the resource keeps running, Terraform just forgets about it, useful when a resource is being handed to another team, another Terraform root, or a different tool. destroy (or removing the resource block and applying) actually deletes the real infrastructure. Confusing them is a classic incident: someone means "stop tracking this" and runs the command that deletes it, or vice versa.

What is a moved block and why did it replace terraform state mv as the recommended pattern?

A moved block declares, in HCL, that a resource previously known by one address is now known by another — a rename, a move into a module, a change of resource type during a provider migration — and Terraform applies that mapping automatically on the next plan without proposing a destroy/recreate. It replaced ad hoc state mv commands as the default guidance because a shell command run once on someone's laptop is invisible to code review and to anyone who didn't run it themselves, while a moved block ships in the same pull request as the refactor it describes and applies identically for every teammate and every environment.

Explain ARM's Complete deployment mode and why it's dangerous in a way Incremental mode isn't.

Incremental mode (the default) only ever adds or updates resources the template mentions and never touches anything else in scope; Complete mode additionally deletes any resource in the target scope that the template does not mention, effectively treating the template as an exhaustive declaration of everything that should exist there. It's dangerous because that "exhaustive" claim is easy to get subtly wrong — a resource group that has anything else in it, created by another pipeline, another team, or a manual fix, gets silently swept away on the next Complete deployment unless someone reads the what-if diff first.

How does Terraform detect drift, and what's a scenario where it would miss it entirely?

Before computing a plan, Terraform refreshes state by re-reading every managed resource's current attributes from the provider API and comparing them against what state last recorded — any mismatch surfaces as drift in the plan output. It misses drift on anything outside its state entirely: resources it never created and was never told to import are invisible to it, no matter how they change, because refresh only ever re-reads resources already in state.

What's the modern, code-reviewable way to bring an existing cloud resource under Terraform management, and what did it replace?

A declarative import block (stable since Terraform 1.5) that names the target resource address and the real-world ID to import, checked into version control and visible in a plan before it's applied — it replaced the imperative terraform import

CLI command, which performed the import immediately with no plan step and no PR record of what happened or why. The block form also composes: you can generate several in one file for a bulk adoption and review them together.

Can two engineers safely run terraform apply against the same workspace at the same time? What makes that safe or unsafe?

Only if the backend supports locking and it's enabled — HCP Terraform and the common remote backends (S3+DynamoDB, azurerm with blob leasing) acquire a lock for the duration of a plan/apply and make a second run wait or fail rather than race. A local state file has no such protection: two concurrent applies against the same terraform.tfstate can corrupt it or silently drop one run's changes, which is the concrete reason "local state in a team setting" is a code-review flag, not a style preference.

Why doesn't Bicep have a "state surgery" toolkit analogous to terraform state mv/rm/import?

Because there's no persisted mapping to perform surgery on. Renaming a Bicep resource's symbolic name in the template never changes the deployed Azure resource's actual name (the symbolic name is purely a template-local identifier), so there's no recreate to avoid and nothing to declare a "move" for. Adopting an existing resource is just referencing it by its real name and type — optionally as `existing = true` if you only want to read its properties without managing them — and there's no equivalent to "stop managing but don't delete," because Bicep was never the one doing the remembering.

A junior engineer proposes storing terraform.tfstate directly in the git repo "so it's versioned like everything else." What do you tell them?

State often contains sensitive values in plaintext — database passwords, connection strings, any provider-generated secret an attribute exposes — so committing it leaks secrets into history permanently, and git's merge model can't safely reconcile two people's concurrent state changes the way a locking remote backend can. Versioning the state file isn't the goal; a remote backend with locking and its own versioned history (S3 bucket versioning, HCP Terraform's state history UI) gives you the audit trail without either problem, and is the standard answer any interviewer is listening for.

03 · Terraform Language & the Resource Graph

HCL2 (HashiCorp Configuration Language) is Terraform's syntax, but the part that actually matters architecturally is invisible in the syntax: every resource, data, module, and output block is a node in a directed acyclic graph, and every reference from one block to another — subnet_id = azurerm_subnet.app.id — is an edge. Terraform never executes top-to-bottom; it walks that graph, and by default it parallelizes every node whose dependencies are already satisfied (10 concurrent operations, tunable with -parallelism). This is why block order in a `.tf` file is cosmetic — you can define a resource before or after something that depends on it, in the same file or a different one in the same directory, and it makes no difference — and it's why a config with no dependencies at all provisions faster than the same resource count declared with an explicit chain of dependencies (each layer of the chain is a synchronization point the graph has to wait through before starting the next).

The graph is built from two kinds of edges: implicit ones, created automatically whenever one resource's argument references another resource's attribute (the common, preferred case — Terraform infers the dependency from the reference and you never write it down), and explicit ones via depends_on, needed only when a real ordering constraint exists that no attribute reference captures — most often when a resource's side effects (an IAM role's eventual-consistency propagation, a policy attachment) aren't visible as a value the dependent resource could reference. Reaching for depends_on when an implicit reference would do is a code-smell interviewers watch for: it usually means someone doesn't trust the graph rather than that the graph is actually wrong, and it silently over-serializes applies that could otherwise run in parallel.

Two language features exist specifically to answer "how many of this, and which shape" without hand-duplicating blocks. count creates N nearly-identical instances of a resource, indexed 0..N-1 — simple, but famously fragile: removing the third of five items shifts every subsequent index, and Terraform reads that as "destroy index 2, then also recreate 3 and 4 with the shifted values," because count's identity is purely positional. for_each (over a map or a set of strings) fixes exactly that: each instance's identity is the map key or set member, not its position, so removing one item destroys only that one instance and leaves every other key's resource untouched. The modern default is for_each for anything keyed by a meaningful identifier (an environment name, a subnet name) and count only for genuinely anonymous repetition (three identical NAT gateways with no distinguishing property) — a distinction that shows up constantly in code review of other people's modules.

Interview Q&A

Does Terraform execute resource blocks in the order they appear in the file?

No. Terraform builds a dependency graph from every implicit reference and explicit depends_on, then walks that graph, applying independent nodes concurrently (up to the parallelism limit, default 10) and only serializing where a real dependency exists. File order is purely for human readability; you can define a resource anywhere relative to things that reference it.

When should you reach for depends_on instead of relying on an implicit reference?

Only when a genuine ordering requirement exists that isn't visible through any attribute reference — typically eventual-consistency propagation (an IAM role or policy attachment that needs time to take effect before something that uses it) or a provider whose side effects aren't exposed as a value. If you can express the dependency by referencing an actual attribute, do that instead — it documents itself, and reaching for depends_on first is a sign of not trusting or understanding the graph.

Explain why count is fragile when the middle of a list changes, using a concrete example.

With count, an instance's identity is purely its numeric index. Given three subnets built from a list and count = length(var.subnets), removing the second list element shifts what used to be the third element into index 1 — Terraform sees "index 1's attributes changed" (destroy/recreate if any changed attribute forces replacement) and "index 2 no longer exists" (destroy), even though conceptually only one subnet was removed and the other two shouldn't have been touched at all.

What's the practical rule of thumb for choosing count vs for_each?

Use for_each over a map or set whenever each instance has a natural, stable key — an environment name, a subnet name, a list of role assignments — because identity then tracks the key, not position, and insertions/removals only affect the specific item that changed. Reserve count for genuinely anonymous, interchangeable repetition where no instance is more meaningfully "subnet A" than "subnet B" — a fixed number of identical availability-zone-spanning resources, for instance.

How does Terraform decide how many operations to run in parallel, and when would you tune that?

It walks the graph and starts any node whose dependencies are already satisfied, up to the -parallelism flag's limit (default 10) at any given time. You'd lower it when a provider or downstream API rate-limits concurrent requests — a cloud API returning 429s under a large apply is the usual symptom — and there's rarely a reason to raise it beyond the default unless you've confirmed the bottleneck isn't the provider API itself.

What does terraform graph do, and when have you actually needed it?

It renders the dependency graph in DOT format (typically piped into Graphviz for a visual), which is genuinely useful when a plan's ordering is surprising and you need to see exactly which reference or depends_on created an edge you didn't expect — usually while debugging why two resources you thought were independent are serializing, or confirming a refactor didn't introduce an unintended dependency.

Can a resource in a for_each loop reference another instance from the same loop?

Not directly within the same for_each expression — the map or set being iterated is evaluated once, before any instances exist, so it can't reference sibling instances of itself. Cross-instance relationships (subnet A's route table referencing subnet B) are expressed by keying both from the same upstream map/variable and referencing across the two resources' respective for_each keys, not within one.

What happens if you switch an existing resource from count to for_each?

Terraform treats it as a completely different set of resource addresses — aws_instance.this[0] and aws_instance.this["app"] are unrelated addresses even if they'd end up representing the same real resource — so a naive switch proposes destroying every count-indexed instance and creating new for_each-keyed ones. The safe migration path is a set of moved blocks mapping each old index to its new key, so Terraform recognizes them as the same underlying resources rather than destroy/recreate.

Why does Terraform sometimes destroy and recreate a resource for a change that looks minor, like renaming a tag?

Because some attributes are marked ForceNew in the provider's resource schema — the underlying cloud API has no in-place update operation for that field, so the only way to change it is delete-and-recreate. This is provider-schema-specific, not a Terraform core behavior, and the plan output always tells you explicitly ("must be replaced") before you apply, which is exactly the review step that catches an unintentional outage before it happens.

What's the difference between a resource block and a data block, structurally?

A resource block is something Terraform creates, updates, and destroys — it appears in state as something under management. A data block only reads information about something that already exists (a lookup, not a creation) and is refreshed on every plan but never appears as something Terraform would destroy. They participate in the same dependency graph identically — a resource can reference a data source's attributes exactly like it references another resource's.

A reviewer sees a module with fifteen depends_on entries and flags it. Why might that be a legitimate concern?

Fifteen explicit dependency declarations is a strong signal that the graph isn't actually being trusted to infer ordering from real attribute references, which usually means either the module has legitimately unusual cross-cutting side-effect ordering (rare) or someone added depends_on defensively every time a plan didn't do what they expected, without diagnosing why — the latter tends to compound into an over-serialized, slow-to-apply module that's also harder to reason about, since the reason for each dependency isn't self-documented the way an attribute reference would be.

04 · Bicep Language & the ARM Compilation Model

Bicep is best understood not as "ARM, but nicer syntax" but as a genuine compiler with its own front-end: you write .bicep, the Bicep CLI (or the transparent build step inside az deployment group create --template-file main.bicep) lowers it to ARM JSON, and that JSON — verbose, positional, historically hand-written — is the only thing Azure Resource Manager itself has ever understood. You can always inspect the output with bicep build main.bicep, and doing so at least once is genuinely clarifying: it's the fastest way to see that a Bicep module block compiles to a nested ARM deployment, that a Bicep if compiles to a condition property, and that string interpolation compiles to ARM's concat() function calls — the abstractions are real, but they bottom out in exactly the JSON you'd have written by hand a few years ago.

Because ARM itself has no notion of "variables," "loops," or "modules" — a raw ARM template is a flat-ish JSON document with a resources array, a parameters object, and template functions evaluated at deployment time — every one of Bicep's ergonomic features is sugar the compiler resolves before ARM ever sees it. A Bicep for loop over an array becomes ARM's copy loop construct; a Bicep module becomes a nested Microsoft.Resources/deployments resource whose properties.template is the child template inlined (or, for a registry-published module, a templateLink reference); decorators like @secure() or @allowed([...]) become metadata ARM's parameter validation reads before deployment starts. None of this changes what actually gets sent to Azure's control plane — which is the point: Bicep improves the authoring experience with zero change to what ARM executes, so anything you could do in raw ARM JSON you can still do, and anything odd about ARM's actual behavior (deployment scopes, the two deployment modes from unit 02, resource provider registration) still applies unchanged underneath Bicep.

The other language-level idea worth internalizing is Bicep's scope system: a deployment targets exactly one of four levels — resource group, subscription, management group, or tenant — declared with `targetScope` at the top of the file (defaulting to resource group), and a resource block deploys into that scope unless it explicitly targets a different one via the `scope:` property (used, for instance, to create a resource group itself from a subscription-scoped deployment, or to assign an RBAC role at a management group from a file whose other resources live in a resource group). Getting scope wrong is a compile-time or early-deployment-time error, not a silent misfire — Bicep's linter and ARM's own validation both catch a resource type that can't legally exist at the declared `targetScope` before any real API call happens, which is a meaningfully safer failure mode than Terraform's provider-level scoping, where a wrong subscription ID in a provider block only surfaces once a resource actually tries to apply against it.

"Bicep and Terraform's azurerm provider both talk to Azure, so they should behave identically for the same resource" is the trap, and it's wrong in a way that bites in practice: Bicep resource types and API versions map directly onto ARM's own resource provider schema (Microsoft.Storage/storageAccounts@2024-01-01, exactly as ARM defines it), while Terraform's azurerm provider is a separately-maintained abstraction layer with its own resource and attribute names, its own opinions about defaults, and its own release cadence relative to ARM's — a brand-new ARM API version or resource type is usually usable from raw ARM JSON or Bicep on day one, but only usable from Terraform once the provider maintainers add support, which has historically lagged by weeks to months for less common resource types. Interview Q&A

What is Bicep, precisely — is it a new deployment engine or something else?

It's a domain-specific language and compiler, not a new engine: Bicep source transpiles to ARM JSON, and Azure Resource Manager — the same control plane that has always processed ARM templates — is what actually executes the deployment. Nothing about how Azure provisions resources changes; Bicep only changes what you author, which is why bicep build can always show you the exact ARM JSON your file compiles to.

How does a Bicep module differ from a Terraform module at the compiled-output level?

A Bicep module compiles to a nested ARM deployment resource (Microsoft.Resources/deployments) — visible as its own entry in the deployment history, with its own scope and its own inputs/outputs wired through ARM's nested-template mechanism. A Terraform module has no equivalent runtime artifact at all; it's purely a source-code organizing construct that Terraform inlines into one flat graph before planning — there's no "nested deployment" concept in Terraform's execution model, only in Bicep's, because Bicep inherited it from ARM.

What are Bicep's four deployment scopes, and what determines which one a file targets?

Resource group, subscription, management group, and tenant, declared via the top-level targetScope statement (defaulting to resource group if omitted). Individual resources within the file normally deploy into that declared scope, but any resource can override it with its own scope: property — the common case being a subscription-scoped file that creates a resource group and then deploys a module into that just-created group via scope: newRg.

Why might a brand-new Azure resource type be usable in Bicep before it's usable in Terraform?

Bicep resource declarations map directly onto ARM's resource provider schema and API versions — as soon as a resource type ships an ARM API, you can reference it in Bicep by type and version string. Terraform's azurerm provider is a separate abstraction with its own maintainers who have to write and ship support for each new resource type or property, which introduces a lag — sometimes days, sometimes months for niche resources — between ARM shipping something and Terraform being able to manage it (the AzAPI provider exists specifically to bridge that gap by exposing raw ARM resource types to Terraform without waiting on azurerm).

What does the @secure() decorator do, and what does it not do?

It marks a string or object parameter as sensitive, which stops its value from being logged or displayed in deployment history/outputs and signals tooling (including the Bicep linter) to flag if it's used somewhere unsafe, like being written into a plain output. It does not encrypt the value in transit or at rest beyond what ARM's own transport already does, and it does not replace a proper secret store — the modern pattern is a `.bicepparam` file pulling the actual value from Key Vault via a `getSecret()` reference at deployment time, with `@secure()` protecting how it's displayed once resolved.

Explain what happens, step by step, when you run az deployment group create with a .bicep template file.

The Azure CLI detects the `.bicep` extension and transparently invokes the Bicep compiler to transpile it to ARM JSON in memory (no separate build step needed by the caller); that JSON, along with any parameters, is submitted to ARM's deployment API for the target resource group; ARM validates the template, computes the diff against the live scope (Incremental or Complete mode), and executes the resulting create/update/delete operations, recording the whole thing as one deployment history entry.

How do Bicep loops handle a shrinking array, compared to Terraform's count?

Bicep's for loops compile to ARM's copy construct, which — like Terraform's count — is fundamentally positional: removing the middle element of an array being looped over shifts every later index's identity, and ARM will propose updating/recreating shifted instances rather than only removing the one that's gone, for exactly the same structural reason count has that problem. Bicep's mitigation is the same as Terraform's for `for_each`: loop over an object/map keyed by a stable identifier instead of a plain array wherever identity matters.

What's the AzAPI provider, and why does it exist alongside azurerm in the Terraform ecosystem?

AzAPI is a thin Terraform provider that exposes raw ARM resource types and API versions directly — effectively giving Terraform the same "day one" access to new Azure features that Bicep gets natively — at the cost of losing azurerm's higher-level ergonomics (typed schema, sane defaults, cross-resource validation). Teams use it as an escape hatch for the specific resource or property azurerm hasn't caught up on yet, sometimes alongside azurerm in the same configuration, then migrate to azurerm once support lands.

Can you mix Bicep and raw ARM JSON in the same deployment?

Yes — a Bicep file can reference a raw ARM JSON template as a module via `module foo 'template.json' = {...}`, useful for incrementally migrating a large legacy ARM estate without rewriting everything at once, or for consuming a third-party template that hasn't been ported to Bicep. The reverse (raw ARM JSON referencing a `.bicep` file directly) isn't supported; you'd compile the Bicep to JSON first.

What's a decorator in Bicep, and name two beyond @secure()?

A decorator is metadata attached to a parameter, output, or resource that Bicep's compiler and linter use for validation or documentation without affecting the compiled JSON's runtime behavior beyond what it encodes into parameter metadata. `@allowed([...])` constrains a parameter to an explicit value set, rejected at deployment time if violated; `@minLength()`/`@maxLength()` constrain string or array size the same way — all three exist so invalid input is caught before a single API call, rather than failing deep into a partially-applied deployment.

Why is a compile-time scope error in Bicep considered "safer" than Terraform's equivalent misconfiguration?

Bicep's linter and ARM's pre-flight validation reject an illegal resource-type/scope combination before any resource is touched — the failure is static and immediate. Terraform's nearest equivalent mistake — a resource block pointed at the wrong provider alias, subscription, or region — typically isn't caught until the provider actually attempts an API call during apply, meaning some resources in the same apply may have already been created successfully before the misconfigured one fails, leaving a partially-applied, harder-to-reason-about state to clean up.

05 · Modules, Registries & Reuse

A module in either tool is the same basic idea — a parameterized, reusable bundle of resources with a defined input/output contract — but the ecosystems around that idea have matured very differently, and knowing the difference is a fast way to demonstrate real hands-on experience rather than textbook familiarity. Terraform's public registry (registry.terraform.io) has existed since 2017 and is enormous: tens of thousands of community and vendor modules, each versioned with semver, each pinnable with a `source`/`version` pair, with well-established modules (`terraform-aws-modules/vpc`, `Azure/naming`) treated as de facto standard library. Bicep's registry story is newer and Microsoft-curated rather than community-sprawling: the **Bicep public registry** hosts Microsoft-published modules, and the flagship initiative is **Azure Verified Modules (AVM)** — a cross-language standard (the same module concept published for both Bicep and Terraform's azurerm provider) that Microsoft and its partners maintain to a defined quality bar (tested, documented, following the Well-Architected Framework) rather than "whatever the community happened to publish."

The practical implication for a lead making a build-vs-reuse call: Terraform's registry breadth means you'll almost always find something for a given resource, but quality and maintenance vary wildly — vetting a community module (checked recently? pinned dependencies? sane defaults? no drive-by contributors introducing breaking changes?) is real, ongoing due diligence. AVM's narrower but curated catalog trades breadth for a guarantee: an AVM module for `Microsoft.Storage/storageAccounts` will exist in near-identical form for both Bicep and Terraform, follow the same naming and tagging conventions, and be maintained under a public governance process — which is precisely why AVM is Microsoft's answer to "how do we stop every team writing its own storage-account module with slightly different defaults."

Versioning discipline matters more for modules than almost anywhere else in an IaC codebase, because a module is a dependency exactly like a package from npm or NuGet: pin it. Terraform's `source = "Azure/naming/azurerm"` with an unconstrained or overly loose `version = ">= 1.0"` will silently pick up a new major version's breaking changes on the next `terraform init -upgrade`; the disciplined pattern is an exact or narrowly-bounded pin (`version = "~> 1.2.0"`) plus a deliberate, reviewed bump. Bicep module references work the same way against the registry (`br/public:avm/res/storage/storage-account:0.14.3`) or a private registry (an Azure Container Registry hosting your org's modules, referenced the same `br:` way) — the discipline is identical even though the mechanics differ slightly.

Interview Q&A

What is Azure Verified Modules, and what problem was it created to solve?

AVM is Microsoft's curated, cross-language module catalog — the same resource module published in near-identical form for both Bicep and Terraform's azurerm provider, built to a defined quality bar covering testing, documentation, and Well-Architected Framework alignment. It exists because unmanaged module sprawl — every team writing its own storage-account or vnet module with slightly different defaults, naming, and tagging — is a real, recurring cost at organizations with many teams; AVM gives a single reviewed default to converge on regardless of which IaC tool a given team uses.

Why is pinning a module version non-negotiable, and what's the failure mode if you don't?

An unpinned or loosely-bounded module reference can pull a new version — potentially with breaking changes, renamed inputs, or changed defaults — on any teammate's next init, with no code change and no PR to review; the failure shows up as a confusing plan error at best, or a silent behavior change at worst. Pinning to an exact or narrowly-bounded version and bumping deliberately in a reviewed PR treats the module as the dependency it actually is, exactly like a library version in a lockfile.

How does a Terraform module differ from a Bicep module in what actually happens at deploy time?

Terraform inlines a module's resources into one flat dependency graph before planning — there's no runtime trace that a "module" was ever involved, just resources with a module-prefixed address. A Bicep module compiles to a nested ARM deployment resource, which shows up as its own entry in Azure's deployment history with its own scope, inputs, and outputs — a structural difference that comes directly from Bicep being a transpiler over ARM's own nested-template mechanism rather than an independent planning engine.

What would make you write a custom module instead of reusing a public/AVM one?

When the public module's abstraction doesn't fit — it exposes the wrong set of configurable knobs for your compliance or architecture requirements, its defaults conflict with an organizational standard you can't easily override, or the resource combination you need genuinely doesn't map to any existing module's scope. The judgment call is weighing maintenance cost (you now own upgrades, security patches, and bug fixes yourself) against control — for a common, well-covered resource like a storage account, that trade almost always favors reuse; for a bespoke internal platform pattern, it often favors a custom module.

How do you host a private module registry for an organization, in each tool?

Terraform: HCP Terraform's built-in private registry, or simply any Git repository, HTTP endpoint, or S3/GCS bucket referenced directly as a module source — no dedicated registry server is strictly required. Bicep: any OCI-compliant registry, in practice almost always Azure Container Registry, referenced with the `br:/:` syntax, with `br/public:` reserved for Microsoft's own public registry.

What's a module's "output" for, and how does a caller consume it?

An output exposes a value computed inside the module — typically an ID, name, or connection string of something the module created — to whatever called it, without exposing the module's internal resource structure directly. A Terraform caller reads `module.name.output_name`; a Bicep caller reads `moduleName.outputs.outputName` — in both cases this is how you wire a network module's subnet ID into a compute module without either module needing to know the other's internals.

Is a module's internal resource structure part of its contract, or just its inputs and outputs?

Only inputs and outputs are the contract; internal resource structure is an implementation detail a well-behaved module can refactor freely (splitting one resource into two, renaming an internal resource address) without it being a breaking change to consumers, as long as the same inputs still produce the same outputs and the same real-world result. Callers who reach past the module boundary — referencing a module's internal resource address directly, which Terraform technically allows but strongly discourages — break that contract and should be flagged in review.

What review process would you put in place for bumping a shared module's version across many consuming repositories?

Read the module's changelog/release notes for breaking changes first; bump in one low-risk consumer (a dev or sandbox environment) and run a plan to confirm no unexpected diff; only then roll the bump out to the rest, ideally automated via a dependency-update tool (Renovate/Dependabot support Terraform module version pins) that opens a PR per repository so each bump gets its own diff and review rather than a blind, org-wide simultaneous change.

Why does Terraform's module ecosystem have more breadth but Bicep/AVM more consistency?

Terraform's registry has existed since 2017, is open to any publisher, and multi-cloud by nature — breadth was the point from day one, at the cost of no enforced quality bar across the catalog. AVM launched later, is scoped to Azure only, and is governed by Microsoft with an explicit testing/documentation/Well-Architected standard every module must meet — narrower scope traded deliberately for a consistency guarantee the open Terraform registry never tried to provide.

A team wants to standardize resource naming across dozens of Terraform and Bicep repositories. What would you point them at?

The `Azure/naming` module on the Terraform side, and AVM's naming conventions/utility modules on the Bicep side — both encode Microsoft's Cloud Adoption Framework naming standard (resource-type abbreviation, environment, region, instance) as a reusable function rather than leaving every team to reinvent a naming scheme, which is exactly the kind of low-risk, high-consistency win a lead should push for before letting fifteen teams debate naming conventions in a meeting.

What's the risk of consuming a community Terraform module with very few GitHub stars or a stale last-commit date?

Low adoption and staleness both correlate with unpatched provider-version incompatibilities, unaddressed security issues, and a higher chance you'll need to fork or vendor it yourself once you hit its first real limitation — the due-diligence questions worth asking before adopting are: when was it last updated, does it pin its own provider version constraints sanely, and is there any test suite (`terraform test` / Terratest) giving confidence it actually works as documented, not just that it compiles.

06 · Terraform Workflow: Providers, Workspaces & Stacks

A **provider** is Terraform's plugin boundary: a separately-versioned binary implementing the Terraform Plugin Protocol that translates HCL resource blocks into calls against one specific API surface — `azurerm` for Azure's Resource Manager API, `aws` for AWS, `azuread` for Entra ID, `kubernetes` for a cluster's API server. Every provider ships and versions independently of Terraform core itself, which is why a `required_providers` block pins both the provider source address and its version constraint, and why "Terraform 1.16 supports X" and "the azurerm provider supports X" are frequently two entirely different questions with two entirely different answers — core added the `lifecycle.destroy` block in 1.16; azurerm shipping a new resource type is a provider release, decoupled from core's release train.

Multiple, isolated instances of the same configuration are handled by two mechanisms that are easy to conflate but solve different problems. **CLI workspaces** (`terraform workspace new staging`) give one configuration multiple named state files sharing the same backend — cheap, built-in, but with no isolation of variables or credentials beyond whatever `terraform.workspace` conditionals you write yourself, which is why HashiCorp's own guidance has, for years, steered production multi-environment setups toward separate root modules or separate HCP Terraform workspaces (a different concept sharing an unfortunately identical name — a full first-class entity with its own variables, run history, and permissions) rather than CLI workspaces for anything beyond quick personal experimentation.

The newest layer, and the most interview-relevant recent addition to name, is **HCP Terraform Stacks**, which reached general availability in 2025 after a long beta. A Stack is not a bigger workspace — it's a different unit of composition entirely: you author a `.tfcomponent.hcl` file describing a graph of **components** (each wrapping a normal Terraform module) and their relationships, then define **Deployments** (an environment-like instance of the whole stack — dev, staging, prod) which can be grouped into **Deployment Groups** for coordinated, ordered rollout across many deployments at once. The problem Stacks solves is one CLI workspaces and even separate root modules handle badly: modeling *dependencies between environments or between layers of infrastructure* (network stack must roll out before the app stack that references it, and both must be replicated identically across five regions) as a first-class, reviewable graph, instead of as a pile of separately-triggered CI pipeline stages held together by convention and hope.

Interview trap

"Terraform workspaces" is a genuinely overloaded term, and interviewers know it: CLI workspaces (`terraform workspace new`) and HCP Terraform workspaces are almost entirely unrelated concepts that happen to share a name, and conflating them in an answer is an immediate signal of surface-level familiarity. Try it

Interview Q&A

What is a Terraform provider, mechanically, and why is it versioned separately from Terraform core?

A provider is a separate plugin binary implementing the Terraform Plugin Protocol, translating HCL resource/data blocks into calls against one API surface — Azure, AWS, Kubernetes, and so on. It's versioned independently because a provider's release cadence tracks its underlying API's changes (a new Azure resource type, a deprecated AWS parameter), which has nothing to do with when Terraform core ships a language or graph-engine feature — coupling the two would force every provider to release in lockstep with core for no reason.

What's the difference between a CLI workspace and an HCP Terraform workspace?

A CLI workspace (`terraform workspace new`) is a lightweight mechanism for giving one configuration multiple named state files under the same backend, with no other isolation — variables, credentials, and the config itself are shared unless you branch on `terraform.workspace` yourself. An HCP Terraform workspace is a full first-class entity in HashiCorp's managed platform with its own variables, run history, permissions, and VCS trigger — a completely different, unrelated concept that unfortunately shares the word "workspace."

Why does HashiCorp discourage CLI workspaces for production multi-environment setups?

Because the isolation is too shallow for production stakes: a single typo or missing `terraform.workspace` conditional can apply a prod-shaped resource in what was meant to be dev, since both share the same variable definitions and provider credentials by default. Separate root modules (or HCP Terraform workspaces) give each environment its own explicit configuration and credentials, making cross-environment mistakes a visible, reviewable diff rather than a runtime conditional that's easy to get wrong.

What problem do HCP Terraform Stacks solve that separate root modules per environment don't?

Separate root modules isolate environments from each other but give you no native way to express dependencies *between* them — network must roll out before app, and both must replicate identically across five regions — beyond whatever ordering your CI pipeline happens to encode. Stacks make that graph a first-class, versioned artifact (components and their relationships in `.tfcomponent.hcl`), with Deployments and Deployment Groups letting you roll a change through many coupled environments in a defined, reviewable order rather than via ad hoc pipeline sequencing.

What's a "component" in the Stacks model, and how does it relate to a normal Terraform module?

A component wraps an existing Terraform module and gives it identity within a Stack's dependency graph — its inputs can reference another component's outputs the same way a module call can reference another module's outputs, but a Stack additionally understands the resulting graph across an arbitrary number of Deployments, not just within one root module's single apply.

How would you decide between CLI workspaces, separate root modules, and Stacks for a new project?

CLI workspaces only for genuinely disposable, single-person experimentation. Separate root modules (or HCP Terraform workspaces) for the common case — a handful of environments with no meaningful cross-environment ordering dependency. Stacks when you have many environments/regions that must roll out in a coordinated, dependency-aware order, or when the "network before app, replicated across five regions" pattern is a recurring operational pain point rather than a one-off.

What does a version constraint like "~> 4.20" mean, and how is it different from ">= 4.20"?

~> 4.20 is a pessimistic constraint allowing any version from 4.20 up to (but not including) 5.0 — patch and minor upgrades only, protecting against an unexpected major-version breaking change. >= 4.20 allows any version 4.20 or higher with no ceiling at all, including a future major version that may contain breaking changes — a much looser and generally riskier constraint for production use.

What breaks if two engineers apply from different machines against the same local state file at the same time?

A local backend provides no locking, so both applies can read the same starting state, compute independent plans, and write back independently — whichever finishes last silently overwrites the other's recorded changes, potentially leaving real infrastructure that one apply created completely untracked in the final state. This is the concrete, mechanical reason a remote backend with locking (S3+DynamoDB, azurerm with blob leasing, HCP Terraform) is considered mandatory for any team setting, not just a nice-to-have.

What is the Terraform Plugin Protocol, and why does it matter that it's a defined protocol rather than an internal implementation detail?

It's the gRPC-based contract between Terraform core and any provider binary, defining how core requests a plan, an apply, a data read, and so on, from a provider — a stable, versioned protocol rather than an internal detail, because it's what lets third parties write and ship providers (thousands of them, most not maintained by HashiCorp) without needing access to Terraform core's source, and what let HashiCorp evolve core and providers on independent release cycles in the first place.

A team has one giant root module deploying everything for every environment via long lists of count-based conditionals. What would you recommend?

Split into separate root modules (or HCP Terraform workspaces) per environment, each consuming shared, versioned modules for the actual resources — this trades one giant, conditional-laden file for several small, explicit ones, each independently plannable and reviewable, and removes the risk of a conditional bug in one environment's branch silently affecting another's. If the environments have real rollout-ordering dependencies on each other, that's the specific signal to additionally evaluate Stacks rather than just splitting the files.

Why can't you mix provider versions within a single Terraform run, and what's the operational implication?

A given root module's provider requirements are resolved once at `init` time into a single locked version per provider (recorded in `.terraform.lock.hcl`), used for every resource of that provider type in that run — Terraform doesn't support two different azurerm versions coexisting within one apply. The implication is that upgrading a provider is an all-or-nothing event for everything that root module manages, which is exactly why a staged rollout (bump in a low-risk environment's root module first, confirm a clean plan, then propagate) matters more than it would for a per-resource-granular tool.

07 · Bicep Deployments: Scopes, What-If & Deployment Stacks

Where Terraform's review gate is `terraform plan` computed against its own state, Bicep's is `what-if` (`az deployment group what-if` or the equivalent PowerShell cmdlet), which asks ARM to simulate a deployment and report the predicted create/modify/delete/no-change classification for every resource — without persisted state to consult, ARM computes this by resolving the template and diffing it against the live scope at the moment the request is made. What-if output is colour-coded and grouped by change type, and — critically for review discipline — a `Complete`-mode what-if run will explicitly list every resource it plans to delete because it's absent from the template, which is precisely the check that catches the "scope contamination" failure mode from unit 02 before it becomes real. Making `what-if` a mandatory, human-read pipeline gate before any `Complete`-mode apply is the single highest-leverage Bicep-specific safety practice, the direct analogue of never letting `terraform apply` run against an unreviewed plan.

The most significant recent addition to Bicep's operational model is **Deployment Stacks** (`Microsoft.Resources/deploymentStacks`, GA since 2024 and now the recommended replacement for raw `Complete`-mode deployments): a Deployment Stack is a persistent Azure resource that groups everything a template deployed and remembers that grouping across subsequent deployments — much closer to Terraform's state-tracking model than anything ARM has offered before. Update a stack with a new template revision, and unlike a bare `Complete` deployment, you get an explicit `actionOnUnmanage` setting controlling what happens to resources that fall out of the new template: `detachAll` (stop managing them, leave them running — Terraform's `state rm` equivalent), `deleteResources` (delete them but keep the stack's other management scope, roughly `terraform destroy` on a subset), or `deleteAll` (delete both the resources and the stack). That's a direct, deliberate answer to the exact scope-contamination gotcha from unit 02 — Deployment Stacks give Bicep something it never had: an explicit choice about what "removed from the template" should mean, instead of `Complete` mode's single, silent, always-delete behavior.

Stacks add a second safety layer with no real Terraform analogue: **deny settings** (`denySettings`), which can lock a stack's managed resources against out-of-band modification or deletion by anyone other than the deployment identity itself — `denyWriteAndDelete` blocks both, `denyDelete` blocks only deletion, and up to five excluded principals can be carved out for legitimate break-glass access. This is ARM enforcing "don't touch what I manage" at the authorization layer, something Terraform has no built-in equivalent for at all (Terraform's closest analogue is a strict RBAC/Sentinel policy preventing anyone but the CI identity from having write access to the resources in the first place — a process control, not a resource-level lock).

Interview Q&A

What does az deployment what-if actually compute, given that Bicep has no state file to diff against?

ARM resolves the template (post-Bicep-compilation) and compares each declared resource's properties against the corresponding live resource's current properties in the target scope right now — a live comparison, not a comparison against any persisted memory of past deployments. In `Complete` mode it additionally lists every live resource in scope that the template doesn't mention, flagged for deletion, which is the mechanism that catches scope contamination before an apply.

What is a Deployment Stack, and what gap in ARM's deployment model was it built to close?

A Deployment Stack is a persistent Azure resource (`Microsoft.Resources/deploymentStacks`) that remembers, across updates, exactly which resources a given template deployment manages — closing the gap that made raw `Complete`-mode deployments risky: silent, unconditional deletion of anything not in the current template. A stack replaces that silent default with an explicit `actionOnUnmanage` choice (detach, delete resources, or delete everything) every time resources fall out of the template.

Explain the three actionOnUnmanage options and when you'd choose each.

detachAll stops tracking removed resources but leaves them running — safest default, use when you're not certain removal from the template means the resource should actually be destroyed. deleteResources deletes the removed resources but keeps the stack itself for future updates — use once you're confident "removed from template" really does mean "should not exist." deleteAll tears down both the resources and the stack — use when retiring the whole deployment entirely, the Bicep-side equivalent of `terraform destroy`.

What do deny settings on a Deployment Stack protect against, and what's the closest Terraform analogue?

Deny settings block out-of-band write or delete operations against a stack's managed resources at the ARM authorization layer itself, with up to five excluded principals for legitimate exceptions — enforced by the platform regardless of who has portal or CLI access. Terraform has no resource-level equivalent; the closest analogue is process-level — strict RBAC limiting write access to the CI identity alone, or a Sentinel/OPA policy — which prevents accidental changes through governance, not through an unbypassable platform lock.

Why should a Complete-mode deployment always be preceded by a what-if run in a pipeline, not just optionally?

Because `Complete` mode's failure mode is silent, irreversible deletion of anything outside the template's scope, and what-if is the only mechanism that surfaces that list before it happens — skipping it means the first time anyone learns what's about to be deleted is after the deployment already ran. Making it a mandatory, human- or policy-gated pipeline step is the direct Bicep analogue of never allowing `terraform apply` without a preceding, reviewed `plan`.

Can a what-if diff go stale between when you read it and when you actually deploy?

Yes — what-if computes a live comparison at request time with no lock or transactional guarantee tying it to the subsequent deployment, so any change to the scope in between (another pipeline, a manual fix) can make the executed deployment's actual effect differ from what you approved. The mitigation is procedural: keep the window between diff and apply short, and re-run the diff if there's reason to suspect the scope changed — the same caveat applies to Terraform's plan/apply gap.

What built-in RBAC roles exist specifically for managing Deployment Stacks, and why does that matter?

Azure Deployment Stack Contributor and Azure Deployment Stack Owner are purpose-built roles scoping exactly what's needed to create and manage stacks without granting broader Contributor/Owner rights across the resource group — letting a CI pipeline's service principal hold only stack-management permissions rather than blanket write access to everything in scope, a meaningfully tighter blast radius than a typical Contributor-scoped Terraform service principal.

How would you migrate a set of long-running Complete-mode ARM/Bicep deployments to Deployment Stacks?

Create a stack referencing the existing template and target scope with `--action-on-unmanage detachAll` as the safe first choice, confirming the stack correctly identifies and adopts the already-deployed resources without proposing any deletions; only after verifying that baseline would you consider tightening to `deleteResources` for future updates, and layering deny settings on once the team trusts the stack's tracked-resource list is accurate.

What happens to a Deployment Stack's tracked resources if the stack resource itself is deleted with deleteAll vs detachAll semantics available at deletion time?

Deletion of the stack itself takes an explicit unmanage-action parameter just like an update does — choosing the delete-everything path removes both the stack and every resource it tracked, while choosing detach leaves the resources running and simply removes ARM's record of the grouping, exactly mirroring the update-time semantics rather than introducing a separate deletion-specific behavior.

Why doesn't Terraform need something like what-if the way Bicep does?

Terraform already has an equivalent review mechanism — `terraform plan` — computed from its own state-plus-refresh model rather than a live-only comparison; what-if exists specifically because Bicep/ARM has no persisted state to compute a plan from, so it had to invent a mechanism that derives the same kind of pre-apply diff purely from a live scope comparison. The two serve an identical purpose in the workflow; they differ only in what data source they diff against.

What's the operational argument for preferring Deployment Stacks over plain Incremental-mode deployments even when you never intend to use Complete mode's deletion behavior?

A stack still gives you a persistent, queryable record of exactly which resources a given deployment manages — useful for audit, for onboarding someone unfamiliar with the estate, and for eventually being able to safely retire a whole deployment via `deleteAll` — none of which plain Incremental-mode deployments track at all, since ARM's deployment history records what happened but not an ongoing, updatable notion of current ownership.

08 · Multi-Environment Patterns at Scale

Every IaC codebase eventually has to answer the same question: how do dev, staging, and prod share code without either duplicating every resource block three times or entangling all three so tightly that a staging-only experiment risks prod. The dominant Terraform answer since roughly 2020 has consolidated around **separate root modules per environment, each thin, each calling shared versioned modules** — a `live/dev/main.tf`, `live/staging/main.tf`, `live/prod/main.tf` pattern (the shape popularized by Gruntwork's Terragrunt, though the pattern itself doesn't require Terragrunt) where each environment's file is mostly a short list of module calls with environment-specific input values, and all the actual resource logic lives once in the shared modules from unit 05. The legacy pattern this replaced — one giant root module with `count = var.env == "prod" ? 1 : 0` conditionals sprinkled everywhere — still shows up in real codebases and is worth recognizing on sight, because it's exactly the anti-pattern unit 06 already named: environments sharing so much surface area that a conditional bug in one silently affects another.

Bicep's answer to the same problem is more explicit about parameter separation because the language has a purpose-built construct for it: **`.bicepparam` files**, one per environment, each `using` the same shared `.bicep` template and supplying only the values that differ. This became the modern default once `.bicepparam` reached GA (Bicep 0.18+), replacing the older pattern of maintaining parallel `azuredeploy.parameters.dev.json` / `.staging.json` / `.prod.json` ARM parameter files — the same idea, but `.bicepparam` files are strongly typed against the template's declared parameters (a wrong type or an unknown parameter name is a compile error, not a silent runtime mismatch) and, since a more recent Bicep release, can pull values dynamically at deployment time via `getSecret()` against Key Vault rather than embedding secrets in the file at all.

Both ecosystems converge on the same underlying principle even though the mechanics differ: **the thing that changes between environments should be small, explicit, and reviewable in a diff, while the thing that stays constant (the actual resource topology and logic) should live in exactly one place.** A pull request that changes staging's instance count from 2 to 4 should be a one-line diff in a parameter file or a tfvars file, not a multi-hundred-line diff across duplicated resource blocks — and code review that has to squint at a large diff to find the one meaningful change buried in triplicated boilerplate is itself a signal the environment-separation pattern has decayed.

Interview Q&A

What's the modern pattern for managing multiple environments in Terraform, and what did it replace?

Separate, thin root modules per environment (or separate HCP Terraform workspaces), each calling the same shared, versioned modules with environment-specific input values — replacing the legacy pattern of one large root module riddled with `count`/conditional logic branching on an environment variable, which entangles environments and makes a bug in one conditional risk affecting another.

What is a .bicepparam file, and what did it replace?

A strongly-typed parameter file that `using`s a specific Bicep template and supplies environment-specific values, checked at compile time against the template's declared parameter types. It replaced parallel ARM JSON parameter files (`parameters.dev.json`, `parameters.prod.json`, etc.), which had no compile-time type checking and no `getSecret()`-style dynamic secret resolution.

Why is "separate tfvars per environment" not sufficient on its own to call a codebase well-structured for multi-environment use?

Because it only addresses differing values, not differing topology — if the resource blocks themselves still contain environment-conditional logic, the environments remain entangled at the level that actually matters for blast-radius and review-clarity, even though the surface-level tfvars files look clean and separated.

How does .bicepparam's getSecret() function change how secrets flow into a deployment, compared to the older pattern?

It resolves a Key Vault secret reference at deployment time, so the actual secret value never has to be embedded in the parameter file, checked into source control, or passed as a plaintext CLI argument — the older pattern (a plaintext value in a JSON parameters file, or a value piped in from a CI secret variable with no strong typing) risked the value ending up in logs, history, or a file someone forgot was sensitive.

What's Terragrunt, and is it required to follow the "thin root modules per environment" pattern?

Terragrunt is a popular wrapper around Terraform that adds DRY conveniences for exactly this pattern — generating backend/provider boilerplate, running commands across a whole environment tree, managing dependencies between root modules — but the underlying pattern (thin per-environment roots calling shared modules) is a Terraform convention, not a Terragrunt feature; you can implement it with plain Terraform and no additional tooling, Terragrunt just removes some of the repetition in doing so.

How would you review a pull request that changes a value for just one environment, in each tool?

For Terraform, the diff should be confined to that environment's `.tfvars` or root module input values, plus a `plan` output showing only the expected resources in that environment affected — anything touching the shared module's own files should prompt asking whether the change is meant to affect every environment. For Bicep, the diff should be confined to that environment's `.bicepparam` file, with the same expectation that the shared `.bicep` template is untouched unless the change is genuinely meant to be universal.

What's a concrete symptom that an organization's environment-separation pattern has decayed?

A pull request meant to bump one environment's instance count or SKU shows a large, multi-file diff instead of a one- or two-line change — usually because resource logic is duplicated per environment rather than centralized in a shared module/template, so the same conceptual change has to be hand-applied in several places, each a chance for the environments to drift out of sync with each other.

Can a shared Terraform module have different behavior per environment without introducing environment-conditional logic inside it?

Yes — by exposing the differing behavior as an explicit input variable (an instance count, a SKU, a feature-flag boolean) that each environment's root module supplies its own value for, rather than the module itself branching on a hardcoded notion of "environment." The module stays environment-agnostic; the difference lives entirely in what each caller passes in, which is the same principle that keeps a well-designed function free of special-cased branches for each of its callers.

What's the risk of copy-pasting an entire root module for a new environment instead of parameterizing an existing shared module?

Every future fix or feature has to be manually re-applied to every copy, and copies drift apart over time as some get updated and others don't — the exact problem shared, versioned modules exist to prevent. It's a reasonable stopgap under real time pressure, but should be treated as technical debt to consolidate, not a long-term pattern.

How do you handle a configuration value that's the same across all environments except one deliberate, permanent exception (e.g. one region uses a different SKU due to availability)?

Keep the default in the shared module (a sane default value for the input variable/parameter) and override it explicitly only in that one environment's root module or parameter file — the exception is then visible exactly where it applies and nowhere else, rather than encoded as a conditional inside the shared module that every other environment has to silently pass through unaffected.

Would you recommend HCP Terraform workspaces or separate root modules for a startup with three environments and one small platform team?

Either works at that scale; the deciding factor is usually whether the team already wants HCP Terraform's run history, policy enforcement, and remote execution (in which case workspaces per environment fit naturally and get those features for free) or is running Terraform via a simpler self-managed CI pipeline (in which case separate root modules with a shared remote backend are simpler to reason about and require no additional platform dependency) — there's no universally correct answer, only a fit to the team's existing tooling.

09 · Testing, Linting & Policy as Code

Testing IaC has matured well beyond "run `plan` and eyeball the diff," and the modern stack has three distinct, complementary layers, each catching a different class of mistake. **Static linting** runs against source with no cloud call at all — Terraform's built-in `terraform validate` catches syntax and internal-reference errors, while `tflint` adds provider-aware rules (a deprecated argument, an invalid instance type string) and custom rule plugins; Bicep ships a linter built into the compiler itself, configurable via `bicepconfig.json`, catching things like unused parameters, use of an `adminPassword`-shaped parameter without `@secure()`, or a hardcoded location string where a parameter was clearly intended. **Policy-as-code** sits between plan and apply, evaluating the *proposed change* against organizational rules before anything is applied — Sentinel (HashiCorp's own, HCP Terraform-integrated) and Open Policy Agent/Rego (`conftest` against a `terraform show -json` plan, or `checkov`/`tfsec` scanning source directly) are the Terraform-side tools; Azure Policy, evaluated by ARM itself during a Bicep deployment, plus PSRule and the older ARM-TTK (ARM Template Test Toolkit) are the Bicep-side equivalents. **Integration/behavioral testing** — Terraform's own `terraform test` (`.tftest.hcl` files, stable since 1.6) or the older Terratest (Go-based, spins up real infrastructure and asserts against it) — actually applies a configuration (often against a throwaway account or ephemeral scope) and checks the result behaves as intended, the most expensive layer and the one most teams under-invest in.

`terraform test` deserves specific attention because it changed what "testing Terraform" means for a huge share of teams: before 1.6 stabilized it, genuinely testing a module meant either Terratest (a real dependency on Go, real cloud spend, real cleanup risk if a test crashes mid-run) or nothing at all — most modules simply weren't tested beyond "someone applied it once and it worked." A `.tftest.hcl` file defines `run` blocks, each applying (or, since 1.7, optionally only planning) the configuration with specific variable overrides and asserting conditions against the result, natively in HCL, with no additional language or dependency — dramatically lowering the bar for a module to ship with real tests, and correspondingly raising the expectation that a serious internal module registry actually has them.

Policy-as-code's core value is moving a rule out of a human reviewer's head and into an automatically-enforced, versioned check — "never allow a security group open to 0.0.0.0/0," "every storage account must have `min_tls_version` set to at least TLS1.2," "prod resources must carry a `costcenter` tag" — evaluated identically on every single plan, in seconds, with no reviewer fatigue and no "I meant to check that but the PR was big." The trade-off is real, though: a policy engine can only check what someone thought to encode, it adds a layer of tooling and false-positive risk to maintain, and an overly strict policy set that blocks legitimate, unusual-but-correct changes trains engineers to route around it rather than through it — which is itself worth naming when discussing where policy-as-code fits versus where human review still matters.

Interview Q&A

What are the three layers of IaC testing, and what does each one actually catch that the others don't?

Static linting (`terraform validate`/tflint, Bicep's built-in linter) catches syntax and known-bad patterns with no cloud call at all. Policy-as-code (Sentinel, OPA/Rego, Azure Policy) evaluates a proposed plan or deployment against organizational rules before it's applied, catching rule violations a human reviewer might miss or wave through under time pressure. Behavioral testing (`terraform test`, Terratest, Pester) actually provisions (or plans) and asserts the real, deployed result behaves as intended — the only layer that catches "this compiles and passes every rule but doesn't actually work."

What changed about Terraform testing when terraform test stabilized in 1.6?

It gave every module a native, dependency-free way to define real test cases (`.tftest.hcl` `run` blocks with variable overrides and assertions) without needing Terratest's Go toolchain and real cloud spend — before that, most modules had no automated tests at all beyond "it applied successfully once." It significantly lowered the bar for a module to ship with tests, and raised the reasonable expectation that a serious internal registry has them.

Explain what a policy-as-code tool like Sentinel or OPA actually evaluates, and when in the workflow it runs.

It evaluates the proposed plan — typically Terraform's `terraform show -json` plan output, or the equivalent structured representation for Bicep/ARM — against a set of rules encoded in a policy language (Sentinel or Rego), running after `plan` and before `apply` is allowed to proceed. A failing policy blocks the apply outright (or, in soft-mandatory mode, requires an explicit override), moving the rule enforcement out of a human reviewer's judgment and into an automated, consistent gate.

What's the limitation of a security scanner like tfsec or checkov that's important to name honestly?

These tools check for known, encodable misconfiguration patterns against a fixed or community rule set — they can't catch an architecturally wrong choice, a business-logic security gap, or any risk that hasn't already been expressed as a rule. Passing every check is a floor, not a ceiling; it doesn't substitute for genuine architectural or threat-model-aware security review.

What's Azure Policy's relationship to a Bicep deployment, mechanically?

Azure Policy is evaluated by ARM itself, independent of Bicep — a policy assignment can deny a deployment outright (a resource that violates an enforced policy simply fails to create), audit it (logged but allowed), or even append/modify properties automatically (a `DeployIfNotExists` or `Modify` effect). It's not a Bicep-specific tool at all; it applies identically whether the template originated from Bicep, raw ARM JSON, the portal, or Terraform's AzAPI provider, because it's enforced at the control-plane layer every deployment path funnels through.

What's the difference between "hard-mandatory" and "soft-mandatory" policy enforcement, and why would you choose one over the other?

Hard-mandatory policies block an apply with no override path at all — appropriate for genuinely non-negotiable rules (no public storage containers, ever). Soft-mandatory policies fail by default but allow an explicit, logged override by an authorized person — appropriate for rules that are almost always right but have legitimate, rare exceptions (a tagging convention that a specific migration temporarily can't satisfy). Choosing hard-mandatory for something that turns out to have a legitimate exception just trains people to find workarounds outside the policy system entirely.

How would you introduce policy-as-code to a team that has none today, without immediately blocking their existing pipeline?

Start in audit/report-only mode — running the checks and surfacing violations without blocking anything — for a few weeks to build a real picture of what would actually be caught and how much existing infrastructure would need remediation, then graduate the most confidently correct, lowest-false-positive rules to soft-mandatory, and only the ones with a genuinely zero-exception track record to hard-mandatory. Flipping straight to hard-mandatory on day one against an unaudited existing estate is a fast way to halt every pipeline and burn the team's trust in the tool.

What is ARM-TTK, and is it still relevant given Bicep's built-in linter?

ARM-TTK (ARM Template Test Toolkit) is an older PowerShell-based test suite for validating raw ARM JSON templates against Microsoft's best-practice conventions, predating Bicep. It's still relevant for any raw ARM JSON in an estate (including JSON emitted from Bicep, in principle) but Bicep's own built-in linter covers most of the same ground natively for `.bicep` source and is the primary tool for anything authored in Bicep directly — ARM-TTK persists mainly for legacy JSON templates that haven't been migrated.

Should terraform test replace Terratest entirely? What would make you still reach for Terratest?

Not entirely — `terraform test` covers the common case well and needs no extra dependency, but Terratest's general-purpose Go code can assert against things outside Terraform's own model entirely: making an actual HTTP request to a deployed endpoint, inspecting cloud-provider-specific behavior `terraform test`'s assertion syntax can't express, or orchestrating multi-step scenarios spanning multiple applies. Reach for Terratest when the test genuinely needs to act like an external client of the infrastructure, not just assert on the plan/apply result itself.

A code review shows a Terraform plan with a resource being destroyed and recreated that the author didn't expect. What tooling would have caught this earlier?

A well-configured policy check (or even just disciplined manual review of `plan` output for "must be replaced" markers) run in CI on every PR before merge would surface it, but the earliest possible catch is simply `terraform plan` output being read carefully in the first place — no static linter flags a legitimate but unintended `ForceNew` attribute change, since it's not a syntax or policy violation, just a consequence of the provider's schema, which is exactly why plan review remains irreplaceable even with every other layer in place.

What's PSRule, and where does it sit relative to the Bicep linter and Azure Policy?

PSRule for Azure is a PowerShell-based rules engine that evaluates exported Azure resource configuration or ARM/Bicep templates against a large, community/Microsoft-maintained set of best-practice and Well-Architected-aligned rules — broader in scope than Bicep's built-in linter (which mostly catches language-level issues) and complementary to Azure Policy (which enforces at deployment/runtime rather than as a pre-merge CI check) — many teams run all three, each catching a different slice of "is this actually good infrastructure."

10 · CI/CD, GitOps & Pipeline Security

A mature IaC pipeline separates two operations that a beginner setup often conflates: **plan** (compute the diff, safe to run on every PR, requires only read-level credentials) and **apply** (execute the diff, requires write-level credentials, should never run against an unreviewed diff). The standard shape — for both Terraform and Bicep/what-if — is: on pull request, run plan/what-if and post the output as a PR comment for human review; on merge to the trunk branch, run apply/deploy automatically (or with a manual approval gate for production) using the diff that was actually reviewed, not a freshly recomputed one that might have drifted since review — GitHub's `terraform-plan` action ecosystem and HCP Terraform's own VCS-driven runs both implement exactly this shape, as does Azure DevOps's Bicep deployment tasks paired with `what-if` as a required PR check.

Credential handling is where pipeline security most commonly goes wrong, and the fix the industry has converged on is **OIDC federation**, replacing long-lived static credentials (a service principal client secret, an AWS access key stored as a CI secret) with short-lived tokens issued per pipeline run via a trust relationship between the CI platform and the cloud provider's identity system — GitHub Actions' `id-token: write` permission paired with an Azure federated credential, or AWS's `sts:AssumeRoleWithWebIdentity`, are the concrete mechanisms. The security win is structural, not just convenient: a leaked long-lived secret is valid until someone notices and rotates it (sometimes months); an OIDC token is scoped to one workflow run and expires in minutes, so a leaked one is nearly worthless outside its narrow window. Static secrets in CI variables are the legacy pattern still extremely common in real codebases — recognizing "we have a Terraform service principal secret sitting in a CI secret store" as a migration target, not a stable end state, is the kind of judgment a lead is expected to bring.

**GitOps** — the practice of git as the single source of truth, with a controller reconciling live state to match what's in the repo, rather than a human or a linear pipeline pushing changes — overlaps with but isn't identical to "IaC in CI/CD." A Terraform or Bicep pipeline triggered by a merge is push-based CI/CD applying declarative config; true GitOps (Flux, Argo CD, or Atlantis's PR-comment-driven apply workflow for Terraform specifically) adds a continuously-reconciling controller and, often, drift auto-correction — if someone manually changes a resource GitOps manages, the controller notices on its next reconcile loop and reverts it back to match git, without anyone re-running a pipeline. Atlantis is the most commonly cited Terraform-specific tool in this space: it listens for PR comments (`atlantis plan`, `atlantis apply`) and runs Terraform against a shared, locked working directory per PR, giving you PR-driven review without needing a full separate GitOps controller.

Interview Q&A

Why should plan and apply run with different credential scopes in a CI pipeline?

Plan only needs to read the current state of resources to compute a diff, while apply needs write access to actually change them — giving plan (which runs on every PR, including from less-trusted contexts like a fork) only read credentials means a compromised or malicious PR can never mutate real infrastructure just by triggering a plan job, confining write capability to the narrower, more controlled apply path that runs only on merge.

What is OIDC federation, and what specific security property does it improve over a static service principal secret?

It replaces a long-lived stored secret with a short-lived token issued per pipeline run through a trust relationship between the CI platform's identity provider and the cloud's identity system, verified via signed claims (repo, branch, workflow) rather than a shared secret. The improvement is blast radius and lifetime: a leaked static secret remains valid until someone notices and rotates it; a leaked OIDC token is scoped to one run and expires within minutes, and there's no secret sitting in a CI store to leak in the first place.

What's the risk of applying a freshly re-computed plan at deploy time instead of the exact plan reviewed on the pull request?

The infrastructure change that actually executes may differ from what a human approved, if the live scope changed in the window between the PR review and the merge-triggered apply — a narrow but real gap. Saving the plan as an artifact from the PR-time run and applying that exact file (with Terraform's built-in staleness check rejecting it if state has since diverged) closes that gap; re-planning at apply time reopens it.

What's the difference between GitOps and "just running Terraform in CI/CD"?

Running Terraform in a merge-triggered pipeline is push-based: a pipeline event triggers one apply, and nothing re-checks reality again until the next triggered run. True GitOps adds a continuously-reconciling controller (Flux, Argo CD, or Atlantis's PR-driven model) that keeps comparing live state to what's declared in git on an ongoing basis, and can auto-correct drift without any new pipeline trigger — the distinction matters because "we deploy from git" alone doesn't guarantee anything about what happens between deployments if something drifts.

What is Atlantis, and what specific problem does it solve for Terraform teams?

Atlantis is a self-hosted tool that listens for PR comments (`atlantis plan`, `atlantis apply`) and runs the corresponding Terraform command against a locked, per-PR working directory, posting output back as a PR comment — it solves the problem of running plan/apply through a reviewable, comment-driven workflow with built-in locking (so two PRs touching the same state can't race) without requiring a full hosted platform like HCP Terraform or a bespoke pipeline script maintaining the same guarantees by hand.

Why is posting a plan's output as a PR comment considered a baseline practice, not a nice-to-have?

Without it, a reviewer approving the PR is reviewing HCL/Bicep source diffs and has to mentally simulate what that translates to in terms of real resource changes — for anything beyond a trivial change, that mental simulation is unreliable. Posting the actual computed diff turns review into "does this concrete, tool-computed set of creates/updates/destroys match what I expect," which is a categorically more reliable review than source-diff-only review.

How would you structure environment promotion (dev to staging to prod) for infrastructure changes in a pipeline?

The same reviewed change (same commit, same module version) should progress through each environment's own plan/apply pipeline sequentially, typically gated by a manual approval before the prod stage, rather than each environment running its own independently-triggered pipeline off the same branch with no ordering guarantee — the goal is that what gets promoted to prod is provably the exact thing that was already validated in staging, not a coincidentally similar redeploy.

What's a "manual approval gate" in a deployment pipeline, and where does it typically sit?

A pipeline step that pauses execution until a designated human or group explicitly approves continuation — typically placed immediately before the production apply stage, after plan/what-if output has been generated and is available for review, giving a human the last chance to catch something automated checks missed before it becomes real in the highest-stakes environment.

Why is state locking specifically important in a CI/CD context, beyond the two-engineers-on-laptops scenario from unit 02?

Concurrent pipeline runs are common in CI/CD — two PRs merging close together, a scheduled drift-detection plan overlapping with a manual trigger — and without locking, two automated applies racing against the same state produce the same corruption risk as two humans racing manually, just triggered by pipeline timing instead of coincidence. Locking (via the remote backend) serializes these automatically, turning a race condition into a queued wait.

A team wants to let developers self-service apply infrastructure changes to a shared dev environment without a human reviewer in the loop every time. What guardrails would you put in place?

Automated policy-as-code checks (unit 09) as a hard gate in place of human review for well-understood, low-risk rule categories; a scoped-down credential (dev-only, narrower permissions than prod's) so a mistake there can't reach other environments; and a required, tool-computed plan/what-if output attached to the change even without human sign-off, so there's still a record of exactly what was applied, for after-the-fact review or rollback if something does go wrong.

11 · Migration, Refactoring & State Surgery

Migrating an existing, unmanaged estate into IaC — or refactoring an already-managed one — is where the theory from units 02 and 03 turns into a specific, repeatable procedure, and it's a scenario interviewers at the lead/principal level probe directly because it's exactly the kind of work a senior engineer is expected to own safely. The Terraform-side toolkit is: `import` blocks (declarative, code-reviewable, and — as of Terraform 1.16 — usable for resources nested inside modules, closing a long-standing gap where importing into a module required either a workaround or the older imperative `terraform import ` CLI form) to bring existing resources under management without recreating them; `moved` blocks to declare renames or restructures (a resource moved into a module, a `count`-to-`for_each` conversion) without a destroy/recreate; and, for genuinely bulk adoption, generating `import` blocks programmatically from a cloud inventory scan rather than hand-writing hundreds of them.

The single most consequential refactor a Terraform codebase goes through is splitting one large root module (or "monolith" state) into several smaller ones — done for blast-radius reasons (a mistake in one team's resources shouldn't be able to touch another's), for apply-speed reasons (a huge graph takes longer to plan and refresh), or for ownership reasons (team boundaries should map to state boundaries). The safe procedure is: introduce the new root module's backend configuration, use `terraform state mv -state-out=` (or the modern equivalent, generating `moved` blocks plus a `terraform init -migrate-state` style flow where supported) to relocate the specific resources' state entries without touching real infrastructure, verify both the old and new root modules produce empty plans immediately afterward, and only then remove the moved resources' blocks from the old module's source. Skipping the "verify empty plan on both sides" step is the single most common way this refactor goes wrong — a resource left half-migrated (present in neither state, or present in both) either gets proposed for a destructive recreate or, worse, gets managed by two independent applies simultaneously.

Bicep's migration story is comparatively lower-ceremony precisely because there's no state to split or reconcile: splitting one large template into several modules is purely a refactor of the source — extract the relevant resource blocks into a `.bicep` module file, replace them with a `module` call in the parent, and redeploy; because ARM matches resources by name and type rather than by any persisted address, the nested-deployment restructuring doesn't itself trigger any resource recreation, as long as the underlying resource names and types are unchanged. The place Bicep migration effort actually concentrates is legacy **ARM JSON to Bicep decompilation**: `bicep decompile main.json` (or `az bicep decompile`) produces a starting-point `.bicep` file from existing JSON, explicitly documented as a best-effort conversion that needs manual cleanup — decompiled output is typically syntactically valid but stylistically far from idiomatic (verbose expressions where a native Bicep construct would be cleaner, missing decorators, ARM functions left un-translated where the compiler had no confident 1:1 mapping) — treating decompiled output as a first draft, never a finished migration, is the correct expectation to set.

Expect leftover raw ARM function calls where a native Bicep construct would be idiomatic, missing decorators, and generally un-idiomatic style that needs a manual cleanup pass before the result should be treated as the team's new source of truth.

What's the risk of using the older imperative terraform import CLI command instead of a declarative import block?

The imperative command executes immediately with no plan step and no artifact checked into version control — there's no PR reviewing what was imported, why, or when, and no record for a teammate who wasn't there when it happened. The declarative `import` block is checked in alongside the resource configuration it targets, reviewed like any other code change, and visible in `plan` output before it's applied — the same "process visibility" argument that favors `moved` blocks over ad hoc `state mv` from unit 02.

How would you migrate a Terraform count-based resource collection to for_each without destroying and recreating every instance?

Write a set of `moved` blocks explicitly mapping each old numeric index (`azurerm_subnet.this[0]`) to its new for_each key (`azurerm_subnet.this["app"]`), then change the resource block itself from `count` to `for_each` over the equivalent map — Terraform reads the `moved` blocks to understand these are the same underlying resources under new addresses and updates state accordingly rather than proposing a destroy/recreate for each one.

What's the first thing you'd check before starting a bulk import of an unmanaged cloud estate into Terraform?

Whether you can generate the `import` blocks (and ideally the matching resource configuration skeletons, which newer Terraform tooling and third-party generators like `terraformer` can help with) from an automated inventory scan rather than hand-writing them one at a time — at any real scale, hand-writing import blocks for hundreds of resources is both slow and error-prone, and getting even one resource's ID or type wrong risks importing the wrong thing or duplicating management of it.

A migration leaves a resource present in both the old and new Terraform state simultaneously. What's the danger, and how would you detect it?

Both root modules now believe they manage the same real resource, so two independent applies (possibly by different teams, possibly at the same time) can conflict — one applying a change the other's next refresh interprets as drift, or worse, one destroying something the other still expects to exist. Detecting it requires explicitly checking both states for the resource's address (`terraform state list` on each) rather than assuming a single successful `state mv` fully removed it from the source side — which is exactly the discipline the "verify empty plan on both sides" step is meant to enforce.

Why is "the migration applied without an error" insufficient evidence that a state-splitting refactor succeeded?

A clean apply only confirms Terraform successfully executed whatever it currently believes needs doing given the current (possibly inconsistent) state — it says nothing about whether the resource is correctly and exclusively tracked in exactly one place going forward. The only reliable confirmation is an explicit post-migration check: both the source and destination configurations independently produce an empty plan, proving neither side believes there's outstanding work or an inconsistency to reconcile.

How would you plan a phased migration of a legacy hand-maintained ARM JSON estate to Bicep for a risk-averse organization?

Start by decompiling and manually cleaning up the least critical, most self-contained templates first, validating each with `what-if` against the already-deployed resources to confirm zero unexpected diff before treating the Bicep version as authoritative; only once the process and tooling are proven on low-risk templates would you move to progressively more critical ones, keeping the ability to fall back to the original JSON at each stage until confidence is established.

12 · Choosing & Evolving Your IaC Stack

Every real "Terraform vs Bicep" decision is downstream of a question neither tool answers for you: are you single-cloud or multi-cloud, and how much do you value a stateless-by-construction model versus a mature, huge ecosystem. Bicep's case is strongest when you're Azure-only and expect to stay that way — no state to lose or corrupt, first-day access to new ARM resource types and API versions, tight native integration with Azure Policy/RBAC/Deployment Stacks, and one less piece of infrastructure (a state backend) to secure and operate. Terraform's case is strongest the moment more than one provider is genuinely in play — one language, one workflow, one state model spanning Azure, AWS, GitHub, Kubernetes, Datadog, and hundreds of other providers, plus a far larger module ecosystem and a longer track record of large-scale, multi-team usage patterns (Stacks, policy engines, private registries) to borrow from. "We might go multi-cloud someday" is not, on its own, sufficient justification for Terraform's added operational overhead (state management, backend security, locking) if the honest current answer is "we are Azure-only and have no concrete plan to change that" — but a genuine, near-term multi-cloud requirement is a decisive point in Terraform's favor that Bicep structurally cannot answer, since it doesn't exist outside Azure.

The industry context around this decision shifted meaningfully in the last few years and is worth naming with precision, because it changes the risk calculus of picking Terraform today. HashiCorp relicensed Terraform from the open-source MPL to the Business Source License (BSL) in August 2023, restricting competing commercial offerings built directly on Terraform's code; IBM's acquisition of HashiCorp closed in 2024, folding Terraform into IBM's portfolio. In direct response, a coalition of companies (including several major cloud and tooling vendors) forked the last MPL-licensed Terraform codebase and founded **OpenTofu** under the Linux Foundation, explicitly to guarantee a permanently open-source, community-governed path forward. OpenTofu has since diverged with real, Terraform-lacking features of its own — dynamic `prevent_destroy` expressions (Terraform's version is static), native support for importing resources by cloud-provider identity rather than only by ID, and, as of the 1.12.0 release (May 2026), ephemeral values and conditional resource enabling — meaning "Terraform" is no longer automatically the single, obvious choice it was before 2023; a lead evaluating this space today has to explicitly decide between HashiCorp's BSL-licensed Terraform (still the larger ecosystem, still HCP Terraform's SaaS features) and OpenTofu (permissively licensed, Linux-Foundation-governed, HCL-compatible, and now growing its own feature set independently) rather than assuming the pre-2023 default is still uncontested.

None of this is a reason to avoid IaC tooling decisions entirely — it's a reason to make them explicitly and revisit them on a cadence, the same way you'd revisit any vendor or licensing dependency. A practical decision framework for a lead: (1) name the actual cloud-provider surface you need today and credibly within the next 1-2 years, not a hypothetical; (2) weigh the BSL/OpenTofu licensing question against your organization's actual risk tolerance for vendor licensing changes, not a generic "open source is safer" instinct; (3) evaluate the module/registry ecosystem maturity for your specific resource needs, since that's where day-to-day productivity is actually won or lost; and (4) never treat the choice as permanent — HCL is close enough between Terraform and OpenTofu that switching between them later is a comparatively low-cost migration, while switching between Terraform/OpenTofu and Bicep is a genuine rewrite, which should weigh into how much ceremony the initial decision deserves.

Interview Q&A

What's the single strongest technical argument for choosing Bicep over Terraform in an Azure-only organization?

No state to lose, corrupt, or secure — Bicep's correctness model is bounded entirely by "is the live ARM resource graph what I assume," removing an entire failure class (state drift/loss/corruption) that a Terraform team has to actively manage via backend security, locking, and versioned backups. Paired with day-one access to new ARM resource types and API versions with no provider-release lag, it's a genuinely strong default for a team with no near-term multi-cloud need.

What's the single strongest technical argument for Terraform over Bicep, and when does it stop applying?

One language, one workflow, and one state model spanning every cloud and SaaS provider you actually use, rather than a different tool per provider — decisive the moment more than one provider is genuinely in play. It stops applying, or at least stops being decisive, for an organization that is credibly and durably single-cloud, where Bicep's statelessness and native integration are a stronger fit and Terraform's multi-provider consistency buys nothing you actually need.

Explain the Terraform licensing situation since 2023 and why it matters for a technology choice made today.

HashiCorp relicensed Terraform from the open-source MPL to the Business Source License in August 2023, restricting certain commercial uses, and was subsequently acquired by IBM (closing 2024); in response, a coalition of vendors forked the last MPL-licensed Terraform codebase into OpenTofu, now governed by the Linux Foundation under the permissive MPL 2.0. It matters today because "adopt Terraform" is no longer a single decision — an organization has to explicitly choose between HashiCorp's product (BSL, larger ecosystem, HCP Terraform SaaS) and OpenTofu (permissive license, community governance, increasingly its own distinct feature set), rather than assume there's one obvious default the way there was before 2023.

Name a feature OpenTofu has that Terraform (as of 1.16) does not, and explain it.

Dynamic `prevent_destroy` — OpenTofu allows the `prevent_destroy` lifecycle argument to be computed from an expression (e.g. tied to an environment variable or a conditional), while Terraform's equivalent must be a static, hardcoded `true`/`false`. It matters practically because a static-only version forces awkward workarounds (separate resource blocks, or conditionally including modules) to express "protect this resource only in prod," where OpenTofu can express it directly as one conditional expression.

Is switching from Terraform to OpenTofu, or vice versa, a low-cost or high-cost migration? Why?

Generally low-cost for typical configurations, because OpenTofu deliberately maintained HCL syntax and provider compatibility as a fork — most existing `.tf` files and provider blocks work unmodified under either CLI. The cost rises only to the extent a codebase already depends on tool-exclusive features (an OpenTofu-only construct, or a HashiCorp HCP Terraform platform feature with no OpenTofu equivalent), which is why understanding what's actually tool-specific versus core-HCL matters before treating either direction as risk-free.

Why is switching from Terraform/OpenTofu to Bicep (or vice versa) categorically different in cost from switching between Terraform and OpenTofu?

Terraform and OpenTofu share the same underlying language and provider model, so most configurations port with minimal change; Terraform/OpenTofu and Bicep are different languages with different execution models entirely (stateful graph engine vs. stateless ARM transpiler) — there's no mechanical translation path beyond ARM JSON as a shared lower-level format, so a real switch between them is closer to a rewrite than a migration, which should weigh into how much ceremony and long-term commitment the initial choice deserves.

How would you evaluate whether an organization's "we might go multi-cloud eventually" justifies choosing Terraform now over Bicep?

Distinguish a credible, funded near-term plan (an actual second cloud contract, a concrete workload already scoped for it) from a hypothetical hedge with no committed timeline — the former is a legitimate, decisive factor for Terraform; the latter is usually better served by choosing the best-fit tool for the cloud you actually have today (often Bicep, if Azure-only) and accepting that a genuine future multi-cloud need would justify a deliberate, later migration rather than paying Terraform's operational overhead speculatively in the meantime.

What operational overhead does Terraform carry that Bicep structurally does not, regardless of which Terraform distribution you use?

A state backend that must be provisioned, secured, and backed up; locking configuration to prevent concurrent-apply corruption; and an entire category of "state surgery" operational knowledge (import, moved blocks, splitting state) that a team has to build up — none of which has a Bicep equivalent, since ARM itself is the only source of truth Bicep ever needs.

Can Terraform and Bicep coexist in the same organization, and what's a legitimate reason to run both?

Yes, and it's common in practice: a platform team managing multi-cloud shared infrastructure (networking, identity, observability tooling) in Terraform, while individual Azure-only application teams use Bicep for their own resource-group-scoped deployments — a legitimate split as long as the boundary between what each tool owns is explicit and non-overlapping, avoiding the scope-contamination risk from unit 02 where two tools might both believe they manage the same resource.

What would make you recommend re-evaluating an existing Terraform-vs-Bicep decision that was made two years ago?

A material change in any of the four decision axes named earlier: the cloud-provider surface actually changed (a genuine multi-cloud commitment materialized, or a multi-cloud org consolidated to one provider), a licensing event shifted risk tolerance (as the BSL relicensing did in 2023), the module ecosystem for a now-critical resource type matured or stagnated on one side, or the operational cost of maintaining state (or, symmetrically, of Bicep's more limited tooling for some cross-cutting concern) turned out higher than originally estimated — a decision made once under one set of facts deserves revisiting when those facts genuinely change, not on a fixed calendar for its own sake.

Architecture & ecosystem decisions

How would you design a platform that lets application teams self-serve infrastructure without each team needing deep Terraform or Bicep expertise?

Build a thin catalog of pre-approved, versioned modules (AVM-style or an internal equivalent) exposing only the inputs teams actually need to vary, wrap them behind a simple interface (a template repository, an internal developer portal, or a CI pipeline that just needs a filled-in values file), and let the platform team own the underlying module correctness, security defaults, and upgrades centrally — the goal is that an application team's "infrastructure expertise" requirement shrinks to "fill in these five values," while the actual IaC skill concentrates in a smaller platform group.

What's the architectural cost of using Terraform's AzAPI provider heavily instead of azurerm?

You gain day-one access to new ARM resource types and properties, closing the provider-lag gap from unit 04, but lose azurerm's higher-level ergonomics — typed schema validation, sane cross-resource defaults, and community familiarity — meaning more of the correctness burden shifts onto your own configuration and review process rather than the provider's abstraction. It's a reasonable, deliberate trade for specific gaps, not a wholesale replacement for azurerm.

How do you decide the right granularity for a Terraform module — one resource, one logical component, or one whole environment?

Aim for one logical, independently-reusable component (a "network," an "app service with its supporting resources") — fine enough that it composes cleanly across different call sites and can be versioned and tested in isolation, coarse enough that consumers aren't forced to wire together a dozen tiny modules just to get one meaningful piece of infrastructure. A module wrapping a single resource is usually too thin to justify the abstraction; a module encompassing a whole environment is usually too coarse to reuse.

What's your view on using Pulumi or CDK for Terraform/CDKTF as an alternative to native HCL or Bicep?

They trade declarative-DSL clarity for general-purpose-language power — type-checked at compile time in your language of choice, real loops/conditionals/abstractions instead of HCL's more limited expression language — at the cost of a steeper mental model (imperative-looking code that still produces a declarative plan can confuse newcomers) and a smaller ecosystem than Terraform's own. Worth it when a team's engineering culture is already strongly one language and wants infrastructure code reviewed with the same tooling as application code; a genuine trade-off, not a strictly better option.

How would you structure IaC ownership boundaries between a platform team and product teams?

Platform owns shared, cross-cutting infrastructure (networking, identity, shared observability, the module/registry catalog itself) in its own state/scope; product teams own their own application-level resources in separate states/resource groups, consuming platform-provided modules and outputs (a VNet ID, a shared Key Vault reference) as inputs rather than reaching into platform's state or scope directly — the boundary should mirror who's actually on call for what, since blast radius should match ownership.

Security

What secrets-handling mistakes do you look for in a Terraform or Bicep code review?

A plaintext secret in a variable default, a `.tfvars` file, or a `.bicepparam` file checked into source control; a sensitive value flowing into a plain (non-`sensitive`/non-`@secure()`) output where it would be logged or displayed; and any secret sourced from an environment variable or CI variable rather than a proper secret store (Key Vault, HCP Terraform's variable sets) with rotation and access-audit built in.

How do you prevent a Terraform state file from leaking secrets if someone gets read access to the backend storage?

Restrict backend storage access as tightly as you would any secrets store (dedicated storage account/bucket, least-privilege IAM, encryption at rest, access logging), because state genuinely does contain plaintext sensitive values for many resource types regardless of `sensitive = true` markings in your config (that flag only affects CLI/UI display, not what's actually written to the file) — treating the state backend itself as a Tier-0 secret store, not just "a place files live," is the correct mental model.

What's the principle of least privilege applied to a CI pipeline's deployment identity?

Scope the identity's permissions to exactly the resource types and scopes the pipeline needs to manage — a Contributor role at a specific resource group rather than Owner at the subscription, a custom role limited to the specific resource providers in use — so that a compromised pipeline or a misconfigured plan can only affect the narrow blast radius the identity was actually granted, not everything the organization runs in that cloud account.

How would you audit an existing IaC codebase for security issues before trusting it in production?

Run the static/policy layers from unit 09 (tfsec/checkov or PSRule/ARM-TTK) against the current source to catch known misconfiguration classes quickly; separately review credential handling end-to-end (where secrets originate, how they flow, what's logged); and check the CI pipeline's own permission scoping and whether OIDC federation or static long-lived secrets are in use — the combination of automated scanning plus a manual credential-flow review catches most of what matters without requiring a full from-scratch security assessment.

What's the security argument for Deployment Stacks' deny settings that a pure RBAC policy can't fully replicate?

RBAC controls who can call which API against which scope, but doesn't distinguish "this specific resource is under active stack management" from any other resource that identity happens to have access to — deny settings enforce protection at the level of "this specific set of managed resources," independent of how broadly an otherwise-legitimate identity's RBAC grants might be scoped, closing a gap a purely role-based model leaves open.

Performance & debugging

A terraform plan that used to take 30 seconds now takes 8 minutes. How do you investigate?

Check whether the resource count in the graph grew substantially (a `for_each` over a now-much-larger data source, an accidental combinatorial expansion), whether a data source or provider is making slow external calls being refreshed on every plan, and whether parallelism is being throttled by a rate-limited provider API forcing near-serial execution — `TF_LOG=debug` timing output and comparing plan time with `-refresh=false` (isolating the graph-build/plan cost from the refresh cost) are the two fastest diagnostic levers.

How would you debug a Bicep deployment that fails with a cryptic ARM error deep into a nested module?

Use `--debug` on the CLI for the raw request/response payloads, check the deployment operations list (`az deployment operation group list`) which often surfaces the specific nested deployment and resource that actually failed with a clearer message than the top-level error, and, if the error is genuinely opaque, compile to JSON (`bicep build`) and inspect the exact resource properties being sent — nested deployment errors often bubble up a generic "deployment failed" at the top level while the real, specific ARM error is one or two levels down in the operations list.

What's a common cause of a Terraform apply hanging indefinitely, and how do you safely intervene?

Most often a provider waiting on a cloud API operation that's itself stuck or slow (a resource stuck in a provisioning state, a quota/throttling wait with no clear timeout), or — less often — a stale state lock left behind by a previous run that crashed without releasing it. For the latter, `terraform force-unlock ` is the escape hatch, but only after confirming no other apply is genuinely still in flight, since force-unlocking a lock that's actually held by a live run reopens the exact race condition locking exists to prevent.

How do you reduce the blast radius and plan time of a very large, slow-to-plan Terraform configuration without a full state split?

`-target` for a scoped, temporary plan/apply against a specific resource or module during iterative debugging (never as a permanent workflow, since it can leave the rest of the graph's intended changes unapplied and out of sync); and reviewing whether unnecessary data sources are being refreshed on every plan when their values rarely change, potentially replaceable with a variable populated less frequently — both buy time without committing to the more invasive state-splitting refactor from unit 11.

What's the performance implication of choosing for_each over count at very large scale (thousands of instances)?

Functionally neither is inherently faster to plan or apply for the same instance count — both produce the same number of graph nodes — but `for_each`'s stable, key-based identity avoids the cascading destroy/recreate churn that a `count`-based collection suffers on any mid-list removal, which at thousands of instances turns what should be a small, targeted change into a plan proposing to touch a large fraction of the collection, a real and avoidable performance and safety cost at scale.

Tooling

What's the role of a linter like tflint beyond what terraform validate already catches?

terraform validate only checks internal syntactic and reference consistency — it has no opinion on whether an instance type string is real, whether an argument is deprecated, or whether a naming convention is followed. tflint adds provider-aware rules (catching a typo'd instance type or SKU name before a plan even runs against a real API) and supports custom/pluggable rule sets for organization-specific conventions, catching a broader and more opinionated class of issues earlier and more cheaply than a plan would.

What does terraform fmt do, and why does enforcing it in CI matter more than it might seem?

It canonicalizes HCL formatting (indentation, alignment, spacing) with no semantic effect — enforcing it as a required CI check (`terraform fmt -check`) removes an entire category of noisy, non-substantive diffs from code review, letting reviewers focus entirely on what actually changed rather than re-litigating whitespace on every PR, which compounds meaningfully across a team over time.

How does the Bicep VS Code extension change day-to-day authoring compared to hand-writing ARM JSON?

It provides real-time compile errors, IntelliSense against the actual ARM resource schema (autocompleting valid properties and catching typos as you type), inline linter warnings, and a live "decompile preview" of the emitted JSON — collapsing what used to be a slow write-JSON/deploy/read-error-message loop into immediate, in-editor feedback, which is a large part of why Bicep adoption displaced hand-written ARM JSON so quickly once the tooling matured.

What's the value of terraform providers lock / the .terraform.lock.hcl file?

It pins the exact resolved version (and cryptographic hash) of every provider used, checked into version control, so every teammate and every CI run gets byte-identical provider binaries rather than each independently resolving "latest matching my constraint" at `init` time — without it, two different machines satisfying the same loose version constraint could silently end up on different provider patch versions with subtly different behavior.

Would you recommend a monorepo or many small repos for an organization's Terraform/Bicep codebase, and why?

Depends on how ownership and blast radius are meant to align: a monorepo makes shared-module changes and cross-cutting refactors easier to land atomically and gives everyone visibility into everything, but risks encouraging state/scope entanglement across teams if not paired with strict per-directory state/backend boundaries; many small repos naturally enforce isolation per team but make a shared-module version bump a multi-repo, multi-PR exercise. Neither is universally correct — the state/scope boundaries from unit 08 matter far more than the repo boundary itself.

Legacy & migration reality

You inherit a codebase full of azurerm provider version 2.x resource blocks with deprecated arguments still in use. How do you approach the upgrade?

Read the provider's upgrade guide for each major version boundary crossed (azurerm publishes explicit migration guides per major release), bump one major version at a time rather than jumping straight to latest, run `plan` after each step and expect (and read carefully) any deprecation warnings before they become hard errors in a later version, and treat each major bump as its own reviewed PR rather than bundling several versions' worth of changes into one unreviewable diff.

What do you do with a large estate of hand-maintained ARM JSON templates that nobody wants to touch?

Prioritize by change frequency and risk, not by size — a rarely-touched, stable template is low-value to migrate regardless of how large it is, while a frequently-modified template is where Bicep's better authoring ergonomics pay off immediately; decompile the high-value candidates first, review and clean up the output as a first draft (never trust it as final, per unit 11), and validate each migrated template with `what-if` against its already-deployed resources before treating the Bicep version as authoritative.

How do you handle a Terraform resource type your team used to manage, that the provider has since deprecated in favor of a new resource type?

Check whether the provider offers a documented migration path (sometimes a `moved` block-compatible rename, sometimes a genuine replacement requiring import/destroy-recreate), test the migration in a non-production environment first, and communicate the timeline clearly if the old resource type is on a deprecation clock — silently leaving deprecated resource types in place until the provider version that removes support entirely forces an unplanned, urgent migration is the failure mode to avoid.

What's your approach to a team still manually clicking through the Azure portal for "just this one exception" resource, alongside an otherwise fully Bicep/Terraform-managed estate?

Treat it as scope contamination risk waiting to happen (unit 02) rather than a harmless one-off — either bring it under management explicitly (import for Terraform, simply reference it in the template for Bicep) or, if there's a genuine reason it must stay unmanaged, exclude its resource group/scope from any `Complete`-mode or stack-managed deployment so it can never be accidentally swept up by a future apply.

How would you convince a team still writing raw ARM JSON by hand that migrating to Bicep is worth the effort?

Lead with concrete, immediate authoring-experience wins they'll feel on the very next change — real-time IntelliSense and compile errors instead of a slow deploy-and-read-the-error loop, roughly 70-80% less verbose syntax for the same resource declarations — rather than an abstract architectural argument; then point out that `bicep decompile` gives them a working first draft of their existing templates for free, lowering the perceived migration cost from "rewrite everything" to "clean up an automated first pass."

Judgment & scenario questions

A teammate wants to skip the plan-review step "just this once" to hotfix a production incident faster. How do you handle it?

Resist skipping the automated diff entirely — even under incident pressure, a plan/what-if run takes seconds and is exactly the check most likely to catch a fat-fingered change from making the incident worse — but do compress the human-review step if the situation genuinely warrants it (a second engineer glancing at the diff in a shared incident channel rather than a full asynchronous PR review), rather than eliminating verification altogether. The tool-computed diff is cheap insurance; the human sign-off latency is the part that's reasonable to shorten under real time pressure.

You're doing a code review and see a PR removing prevent_destroy from a production database resource with no explanation. What do you do?

Block the PR until the author explains why — removing that guard on a stateful, hard-to-recreate resource is exactly the kind of change that should never merge on the strength of "it compiles and the plan looks fine," since the plan itself won't show the risk of a *future* accidental destroy the guard was protecting against. Ask specifically whether the intent is a genuine, deliberate one-time destroy (in which case removing the guard, applying, and reinstating it afterward, or using `-target` with an explicit human-reviewed destroy, is more defensible) or an accidental removal during an unrelated refactor.

How would you introduce policy-as-code to a skeptical team that sees it as unnecessary process overhead?

Start in audit-only mode against their existing infrastructure and show them the actual findings — concrete, specific issues in their own estate tend to be far more persuasive than an abstract pitch — then propose graduating only the highest-confidence, lowest-false-positive rules to a blocking gate, explicitly inviting their input on which rules feel genuinely valuable versus which feel like noise, so the rollout is collaborative rather than imposed.

A junior engineer asks why you can't just use ChatGPT/an LLM to generate the Terraform for a new environment instead of writing it by hand. How do you respond?

Generated HCL/Bicep is a reasonable starting draft the same way `bicep decompile` output is — worth using to accelerate a first pass — but it still needs the same review discipline as any other source of code: a plan/what-if review before applying, policy checks, and a human confirming it actually matches the intended architecture, since a generated resource block that "looks right" can still carry a wrong default, a missing security setting, or a subtly incorrect dependency the generator had no way to know about. The tooling changes who writes the first draft, not whether the review gates in this guide still apply.

How do you decide when a growing Terraform monolith actually needs to be split, versus when that's premature?

Watch for concrete symptoms rather than splitting on a size threshold alone: plan times becoming a real friction point, two teams regularly stepping on each other's changes in the same state, or a change in one area regularly requiring unrelated review sign-off from another team's owners — any of those is a genuine signal; a large-but-stable, single-team-owned configuration with none of those symptoms isn't automatically a problem just because it's big, and splitting it preemptively trades a real, immediate migration cost for a hypothetical future benefit.

What would you flag in a code review of someone's first Terraform module, beyond whether it works?

Whether inputs and outputs form a clean, minimal contract (not leaking internal resource addresses or overexposing every possible knob); whether it has any pinned version constraints on its own required providers; whether sensible defaults exist for optional variables so common cases need minimal configuration; and whether it includes at least a basic `terraform test` covering its core behavior — "it applies successfully" is necessary but is the lowest bar, not the standard to review against.

Ten sentences to have loaded and speakable, not memorized verbatim — say each one out loud once before the interview.

  • Terraform is stateful — a persistent state file is its single source of truth, and losing, corrupting, or racing on it is the tool's characteristic failure mode; Bicep is stateless, compiling to ARM JSON and comparing directly against the live resource graph on every deployment, so it has no state to lose but inherits ARM's own risks instead, chiefly `Complete` mode's scope-wide deletion of anything unlisted.
  • Deployment Stacks (GA 2024) gave Bicep an explicit, reviewable answer to Complete mode's silent-deletion problem — `actionOnUnmanage` (detachAll / deleteResources / deleteAll) plus deny settings that block delete or write-and-delete on managed resources even for otherwise-authorized identities.
  • `count` indexes by position, so removing a middle element shifts every subsequent index and forces a cascading destroy/recreate; `for_each` keys by a stable identifier, so removing one element only ever affects that one — always prefer `for_each` for any collection that might shrink or reorder.
  • Terraform relicensed from open-source MPL to the Business Source License in August 2023, HashiCorp was acquired by IBM in 2024, and the Linux Foundation's OpenTofu fork (MPL 2.0, HCL-compatible, now diverging with features like dynamic `prevent_destroy` and, as of 1.12 in May 2026, ephemeral values) means "just use Terraform" is no longer a single unambiguous choice.
  • `import` blocks (declarative, code-reviewable, and — since Terraform 1.16 — usable inside modules) and `moved` blocks (renames/restructures without destroy-recreate) are the safe adoption and refactor primitives; Bicep needs neither, since ARM matches existing resources by name and type with no state to reconcile.
  • Splitting a Terraform root module safely means `state mv` followed by verifying an empty plan on *both* the old and new module before deleting anything from the old module's source — skipping that verification is the most common way this refactor silently breaks.
  • Three testing layers, and each catches something the others don't: static lint (`terraform validate`/tflint, Bicep's built-in linter) catches syntax with no cloud call; policy-as-code (Sentinel, OPA/Rego, Azure Policy, PSRule) gates a proposed plan against organizational rules before apply; `terraform test` (`.tftest.hcl`, stable since 1.6) or Pester+what-if actually asserts the deployed result behaves right.
  • OIDC federation (GitHub Actions `id-token: write` + an Azure federated credential, or AWS `AssumeRoleWithWebIdentity`) issues short-lived, per-run tokens instead of a long-lived stored secret — the modern default, with static service-principal secrets now the legacy pattern to flag and migrate away from.
  • A defensible pipeline applies the exact plan a human reviewed on the PR (`terraform apply tfplan`, which Terraform itself refuses if state has since drifted) rather than silently re-planning at apply time and executing a diff nobody actually looked at.
  • Azure Verified Modules give Bicep the same curated, versioned-module discipline Terraform's public registry pioneered — for either ecosystem, an unpinned `latest`/unconstrained module reference in production is the same category of mistake as a floating library dependency with no lockfile.
