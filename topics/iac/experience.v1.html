01The plan that took forty minutes

Senior Performance problem diagnosed

EXAMPLE — replace with your own

A shared "platform" root module had grown for two years: every team's networking, every shared Key Vault, every private DNS zone lived in one state file. terraform plan had crept from under a minute to almost forty, and CI timeouts started failing builds that hadn't touched infrastructure at all. The easy villain — "too many resources" — turned out to be only half the story.

I pulled a debug trace (TF_LOG=trace terraform plan 2>trace.log) and grepped for request timing. Two things stood out: first, the AzureRM provider was refreshing every resource serially inside a handful of resource groups because a couple of for_each maps were keyed by an unstable expression, so Terraform couldn't prove independence and fell back to conservative ordering; second, three data sources queried the same Key Vault list on every single plan, unconditionally, even when nothing downstream had changed.

variable "provider_parallelism" {
  description = "Bump provider-level concurrency for read-heavy plans"
  type        = number
  default     = 10
}

provider "azurerm" {
  features {}
}

# terraform plan -parallelism=30 -refresh=false   # diagnostic run, not routine use

Raising -parallelism alone bought a little, but the real fix was structural: I keyed the offending for_each on stable resource names instead of a computed map, split the noisiest data-source lookups behind a -target-friendly module boundary, and added a `terraform_data` scratch resource to cache the Key Vault listing between plans where it was safe to do so. Refresh-only plans (terraform plan -refresh-only) also let us confirm nothing had actually drifted before spending the full forty minutes proving it.

BeforeAfter
Plan time (cold)~38 min~6 min
Provider round-trips per plan~4,100~900
CI timeout failures / week5-80

What I'd do differently: I'd have profiled with TF_LOG=trace on day one of the slowdown instead of two months in — I spent too long assuming it was "just resource count" before the data showed otherwise, and the fix was cheaper than the investigation.

What the interviewer is really probing: whether you reach for measurement before opinion, and whether you understand *why* Terraform serializes some operations (unstable `for_each` keys, provider-level throttling, unnecessary data sources) rather than just reaching for `-parallelism` as a blunt instrument.

(d) Follow-up drill chain

Why does an unstable `for_each` key hurt performance, specifically?

Terraform builds its dependency graph from resource addresses. If a key is only knowable after apply (derived from a computed value), Terraform can't prove two instances are independent ahead of time and falls back to more conservative, less parallel evaluation — and worse, a key that changes value between runs looks like a delete+create of a differently-addressed resource, not an update.

What's the difference between `-refresh=false` and `-refresh-only`?

-refresh=false skips reconciling state with real infrastructure before computing the plan — faster, but the plan can be wrong if drift exists. -refresh-only is the opposite intent: it *only* refreshes and shows you drift, producing a plan you can apply to update state without touching real resources.

How does provider-level parallelism interact with `-parallelism`?

-parallelism caps how many resource operations Terraform core will run concurrently across the whole graph (default 10); it doesn't override a provider's own internal rate limiting or an API's throttling, so raising it can just shift the bottleneck to 429s.

When would splitting state actually have been the right call here, and why wasn't it, yet?

It becomes right when the *blast radius* of a bad apply, not just plan speed, is the pain — see story 07. Here the fix was cheaper and preserved a single source of truth for genuinely coupled resources.

What would you check first if `plan` was fast locally but slow only in CI?

Network latency to the provider's API from the CI runner's region, a cold provider-plugin cache forcing a re-download, and whether CI disables the local plan cache that a developer's machine keeps warm.

Terraform 1.16 added `terraform console -scope=<module>`. How would that have helped here?

It lets you evaluate expressions scoped to one module without walking the whole configuration's context, useful for checking exactly which `for_each` keys a submodule was producing without re-running a full plan.

02One state or many: splitting the platform

Principal Hard architectural trade-off

EXAMPLE — replace with your own

Three platform teams shared one Terraform state for networking, identity and shared data services. Every team's change queued behind every other team's lock. I was asked to decide, and defend to a room of staff engineers, how many states the platform should have and where the seams should sit.

I framed it as a trade-off between blast radius and referential integrity, not "big state bad." A single state gives you compile-time-like guarantees across resources — a subnet rename is one atomic plan. Splitting state trades that guarantee for independent deploy cadence and smaller blast radius, at the cost of needing explicit contracts (remote state data sources, or better, defined outputs consumed by ID/ARN, not implicit cross-references) between the pieces.

# seam: networking state publishes stable contracts, nothing else
output "hub_vnet_id" {
  value       = azurerm_virtual_network.hub.id
  description = "Contract for spoke states. Treat as a public API: breaking changes need a deprecation window."
}

# consumer, in a different state
data "terraform_remote_state" "networking" {
  backend = "azurerm"
  config = {
    resource_group_name  = "tfstate-rg"
    storage_account_name = "tfstateplatform"
    container_name        = "tfstate"
    key                   = "networking.tfstate"
  }
}

We split along team-ownership and change-frequency lines, not resource-type lines: networking (changes rarely, everyone depends on it), identity (changes rarely, high blast radius if wrong), and one state per product team for everything else (changes constantly). We explicitly rejected splitting by resource type (all VNets in one state, all VMs in another) because that scatters ownership without reducing coupling.

Split axisProCon
By team ownershipMatches who's paged, who approvesCross-team contracts still needed
By resource typeLooks tidyScatters ownership, doesn't reduce coupling
By environmentIsolates prod from dev mistakesConfig drift between environment states
Single monolith stateAtomic cross-resource changesLock contention, large blast radius

What I'd do differently: I'd have written the "contract" convention (only stable outputs cross a seam, versioned like an API) down as an ADR before the split, not after — two teams still reached into each other's remote state for internal-looking values in the first month.

What the interviewer is really probing: can you reason about state topology as an architectural decision with real trade-offs, rather than reciting "small states are better" — and did you actually own the decision, including its downside, in front of peers who disagreed?

(d) Follow-up drill chain

What's the actual mechanism of state lock contention — what blocks what?

A backend that supports locking (S3 with `use_lockfile`, Azure Storage with a blob lease, Terraform Cloud natively) takes an exclusive lock for the duration of a plan or apply. Any other `plan`/`apply` against the same state waits or fails fast with a "state is locked" error — it's a mutex, not a queue, so there's no fairness guarantee.

What's a "contract" output in your seam design, concretely, and how do you version it?

An output another state's `data "terraform_remote_state"` block or a documented ID/ARN is allowed to depend on. Versioning in practice means: never remove or repurpose an output without a deprecation period, and prefer adding a new output over changing an existing one's meaning.

Why not just use one giant state with `-target` for smaller changes?

-target is documented as a break-glass tool, not a workflow — it can leave the rest of the graph in a plan-vs-reality mismatch, and repeated use masks a design problem rather than fixing it.

How would HCP Terraform Stacks change this trade-off?

Stacks let you define components with explicit input/output contracts between them inside one conceptual unit, deployed across multiple targets — narrowing the gap between "one state" and "many states with manual contracts" by making the contract a first-class, checked construct instead of a convention enforced by discipline.

What would make you merge two states back together?

If the "contract" between them turns out to need near-constant renegotiation — i.e., the resources are actually tightly coupled and the split just added remote-state indirection without reducing real coordination cost.

How do you stop a junior engineer from casually adding a new cross-seam dependency?

Convention plus review: a CODEOWNERS-style rule on files that declare outputs, paired with a written seam contract doc so a reviewer has something concrete to check a new `data "terraform_remote_state"` reference against.

03The complete-mode deploy that deleted the DNS zone

Staff Production incident / outage

EXAMPLE — replace with your own

A quarterly cleanup pass to a landing-zone Bicep template removed a private DNS zone resource block that "looked orphaned" — it had been provisioned by a different, older template nobody had migrated. The pipeline deployed with az deployment group create --mode Complete, which had been set years earlier to keep the resource group free of manual console additions. Complete mode did exactly what it's documented to do: it deleted every resource in the group not present in the new template, including the DNS zone, mid-business-hours.

The blast radius was every internal service resolving names through that zone. Rollback wasn't a revert-and-redeploy: the zone and its records were gone, and Complete mode's deletion doesn't come back with `git revert`. We rebuilt the zone and records from an infra-as-code copy that, fortunately, lived in a sibling module, and re-ran an Incremental deployment to avoid a second wave of surprise deletions while we stabilized.

// what the template should have declared from the start
resource dnsZone 'Microsoft.Network/privateDnsZones@2024-06-01' = {
  name: 'internal.corp.example'
  location: 'global'
  // ...
}
// deployment command, after the incident:
// az deployment group create --mode Incremental --template-file main.bicep

Longer term, we migrated the whole resource group to an Azure Deployment Stack with a documented deny-delete-outside-stack action-on-unmanage setting, so unmanaged resources are flagged rather than silently deleted, and the "what gets removed" decision is explicit and reviewable per deployment rather than an ambient mode nobody remembers is set.

Mode / mechanismUnmanaged resourcesRecommended today
IncrementalLeft untouchedYes — default
CompleteDeletedNo — being phased out for Deployment Stacks
Deployment Stack (deny action-on-unmanage)Deletion blocked, flaggedYes, for lifecycle-managed groups

What I'd do differently: run az deployment group what-if was already policy for our team — it wasn't run for this change because it was miscategorized as a "docs-only cleanup." I'd add a pipeline gate that requires a what-if diff artifact on every deployment touching a Complete-mode group, full stop, with no category-based exemption a human can misjudge.

What the interviewer is really probing: do you understand ARM deployment modes precisely (not "Complete is dangerous" as folklore but *why*, and what replaces it), and can you describe an irreversible-infrastructure incident with the calm, exact language of someone who has actually run one.

(c) Recall prompts

Have you shipped a change that deleted something you didn't mean to?

(d) Follow-up drill chain

What exactly does ARM Complete mode compare against to decide what to delete?

It compares the full desired-state template against everything currently in the target resource group (Complete mode is scoped to resource groups only, not subscriptions), and deletes anything present in the group but absent from the template — regardless of who or what created it.

Why is Complete mode "being deprecated," and what specifically replaces it?

Deployment Stacks give the same "keep the group's contents in sync with the template" intent but as an explicit, first-class resource (Microsoft.Resources/deploymentStacks) with a configurable action-on-unmanage (delete, detach, or deny) instead of an implicit deploy-time mode flag that's easy to forget is set.

Does Incremental mode ever delete anything?

Not resources — Incremental never removes a resource absent from the template. But it does fully reapply every property the template specifies, so a property *omitted* from the template on a redeploy can revert to its ARM default rather than the value someone set out-of-band; that's a related but distinct trap from Complete's resource deletion.

Would this have happened with Terraform instead of Bicep?

Terraform's default posture is closer to "only touch what's in state," and removing a resource block plus running `apply` produces a plan explicitly listing the destroy, which is easier to catch in review than a deploy-mode side effect baked into the CLI invocation — though a careless `terraform state rm` followed by import drift could cause a similar class of surprise.

What's the actual what-if output format, and what would it have shown here?

az deployment group what-if prints a color-coded diff of Create/Modify/Delete/Ignore/NoChange per resource; for this incident it would have shown the DNS zone under Delete before anything ran, which is precisely the signal the gate was meant to catch.

How do resource locks interact with Complete-mode deletes?

A `CanNotDelete` resource lock on the DNS zone would have blocked the deletion outright and failed the deployment loudly instead of silently succeeding — a cheap mitigation for exactly this class of resource, and one we added afterward for every zone.

04Upgrading AzureRM across a hundred modules

Staff Migration / version upgrade

EXAMPLE — replace with your own

The AzureRM provider had been pinned two major versions behind across roughly a hundred internal modules, because the last attempt to bump it had produced a wall of unreviewable plan diffs and been abandoned. I owned getting the whole estate current without a repeat.

Rather than bump every module in one pull request, I read the provider's own upgrade guide first and built a small compatibility matrix: which modules used resources whose schema had actually changed, versus modules that would see a version bump with zero plan diff. I upgraded the zero-diff modules first, in bulk, to prove the pipeline and build confidence, then went module-by-module through the ones with real changes, using `moved` blocks wherever the provider had renamed a resource type or restructured a nested block, so state tracked the rename instead of planning a destroy-and-recreate.

terraform {
  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 4.0"
    }
  }
}

moved {
  from = azurerm_application_gateway.old_shape
  to   = azurerm_application_gateway.this
}

Every module got its own PR with a full `plan` attached as evidence, reviewed by that module's owning team rather than centrally rubber-stamped — the previous attempt's mistake was one giant PR nobody could meaningfully review. We tracked progress on a shared board so partial completion was visible rather than an all-or-nothing cutover looming at a deadline.

ApproachReview burden per changeRollback granularity
One big-bang PR (previous attempt)UnreviewableAll or nothing — abandoned
Module-by-module, owner-reviewedSmall, focused diffPer module

What I'd do differently: I'd have automated the compatibility matrix from the provider's changelog rather than building it by hand reading `plan` output module by module — it was accurate but took a week I could have saved with a script diffing resource schemas.

What the interviewer is really probing: can you run a large, low-glamour migration without breaking things or burning out the team doing it, and do you actually understand the mechanics (`moved` blocks, version constraints, phased rollout) rather than just "we upgraded it."

(d) Follow-up drill chain

What exactly does a `moved` block do to the state file?

It tells Terraform that a resource address in state should be treated as renamed to a new address before computing the plan, so instead of seeing "old address gone, new address absent from state" (a destroy+create), Terraform records the rename and produces an in-place update plan, if any diff remains at all.

What's the actual risk of pinning `version = "~> 4.0"` versus an exact version?

~>4.0 allows any 4.x, so a provider patch or minor release can change behavior under you between applies without a deliberate bump — safer than an unconstrained provider, but for anything touching production you want CI to pin the lock file (.terraform.lock.hcl) and bump it deliberately, not float silently.

How do you find out which resources actually changed schema between major versions?

The provider's own upgrade guide is the primary source; failing that, running `plan` after only bumping the version constraint (before touching any `.tf` code) shows you exactly what the provider itself thinks changed, since a schema-only rename with no config change should plan clean or show only the rename.

What would you do if `plan` showed a destroy-and-recreate you didn't expect after a version bump?

Stop, don't apply. Check the changelog for a renamed attribute or resource, add a `moved` block or an `ignore_changes` lifecycle rule if it's a benign default-value shift, and only apply once the plan reflects an intentional change.

Why review module-by-module rather than centrally, and what's the cost of that?

The owning team best knows what "no diff" or "expected diff" looks like for their resources; the cost is coordination overhead and a longer overall timeline than one reviewer rubber-stamping everything, which is exactly the trade the earlier failed attempt got wrong in the other direction.

How does this differ for a Bicep/ARM API-version upgrade instead of a Terraform provider upgrade?

Bicep resources are versioned per resource type via the @<api-version> suffix rather than one provider version for everything, so upgrades are naturally more granular but also easier to leave inconsistent — some resources on a 2024 API, others still on 2019, with no single lock file forcing a decision.

05The argument over Terraform vs. Bicep

Senior Technical disagreement

EXAMPLE — replace with your own

A platform re-architecture kicked off a genuine, unresolved disagreement: half the team wanted to consolidate everything on Bicep since we were Azure-only and it removes an entire class of provider-lag problems (new Azure resource types land in ARM/Bicep before AzureRM catches up); the other half wanted to stay on Terraform for its multi-cloud muscle memory, mature testing story, and the state/plan model everyone already knew.

I didn't try to win the argument by asserting a preference — I wrote a short comparison grounded in what we actually needed: our workloads were and would stay Azure-only for the foreseeable future, we had zero cross-cloud modules, but we did rely heavily on Terraform's `terraform test` framework and a library of Sentinel-style policy checks that had no Bicep equivalent at the time.

DimensionTerraformBicep
Cloud scopeMulti-cloudAzure-only, no provider lag
StateExplicit state file, remote backendNo user-managed state (ARM tracks deployment history); Deployment Stacks add explicit lifecycle scope
Testingterraform test, matureWhat-if + ARM-TTK/PSRule, thinner test story
Type systemHCL + provider schemasNative user-defined types, discriminated unions

We landed on staying with Terraform for the core platform, and piloting Bicep only for a couple of teams shipping brand-new Azure resource types where provider lag was a real, recent pain (see story 09 for how that pilot's module story played out). I wrote the decision up as a short doc with the trade-off table so the next person asking "why not Bicep everywhere" had an answer that wasn't tribal.

What I'd do differently: I'd have looped in the two most vocal Bicep advocates to co-author the comparison doc instead of writing it solo and presenting it — the decision landed the same way, but buy-in came slower than it needed to because it read as "my conclusion" rather than "our analysis."

What the interviewer is really probing: can you resolve a genuine technical disagreement with evidence rather than authority or personal preference, and do you actually know the real trade-offs between these two tools rather than a marketing-brochure version of either.

(d) Follow-up drill chain

What's "provider lag" concretely, and why doesn't Bicep have it?

A new Azure resource type or property ships in the ARM API first; a Terraform provider needs a maintainer (HashiCorp or community) to add schema support for it, which can lag weeks to months. Bicep compiles to ARM templates directly against the same API, so a new API version is usable the moment Bicep's type definitions are regenerated, typically far faster.

Does Bicep genuinely have "no state," and is that actually true?

There's no user-managed state file to store, back up, or lock — ARM tracks deployment history server-side. But Azure Deployment Stacks introduce an explicit, queryable resource (Microsoft.Resources/deploymentStacks) that tracks a managed-resource set for lifecycle purposes, which is conceptually closer to state than plain incremental deployments ever were.

If the team had cross-cloud needs six months later, how would you revisit this?

Re-open the same doc with the new requirement added to the needs table rather than starting a fresh argument — the whole point of writing it down was to make the next decision an update, not a re-litigation.

What's a case where you'd recommend Bicep even for a shop with some multi-cloud presence?

When the multi-cloud footprint is small and isolated (one legacy AWS account, say) and the Azure portion is large and fast-moving — running Bicep for Azure and a thin, separate Terraform config for the AWS sliver can beat forcing one tool to be mediocre at both.

How mature is `terraform test` really, and what does it not cover?

08The database password sitting in plaintext state

Senior Security issue found / fixed

EXAMPLE — replace with your own

A routine state-file audit (part of a broader secrets-hygiene sweep) turned up a generated database admin password sitting in cleartext inside a Terraform state file, stored in a backend without encryption-at-rest enforced. The password had been passed as a plain resource argument, which Terraform faithfully records in state exactly as any other attribute value.

The immediate fix was rotating the credential and enabling encryption-at-rest on the state backend (SSE on the S3 bucket, or the storage account's platform-managed key at minimum). The durable fix was re-architecting how the password reached the resource at all, using write-only arguments, introduced in Terraform 1.11, which are never persisted to state or plan files in the first place.

ephemeral "random_password" "db_admin" {
  length  = 24
  special = true
}

resource "azurerm_postgresql_flexible_server" "this" {
  # ...
  administrator_password_wo         = ephemeral.random_password.db_admin.result
  administrator_password_wo_version = 1
}

Pairing an ephemeral value with a _wo write-only argument means the secret exists only in provider memory for the duration of the operation — it's generated, sent to the API, and discarded, never written to state or the plan file. The `_wo_version` counter is the mechanism for intentionally rotating the value: bumping it signals "apply this write-only value again," since Terraform can't diff a value it never stores.

What's the actual mechanism that makes a write-only argument never touch state?

EXAMPLE — replace with your own

A deployment pipeline crashed mid-apply — the runner was killed by an infrastructure-level autoscale-down event, not a Terraform failure — leaving the state file locked with no process left alive to release it. It was 02:14, a genuinely unrelated production incident needed an emergency infrastructure change through that same state, and the lock was blocking it.

(d) Follow-up drill chain

What does `force-unlock` actually do, mechanically?

It removes the lock record from the backend (the DynamoDB item, the blob lease, the lock file) directly, without checking whether the original holder is actually still running — Terraform trusts you that you've verified it's safe, which is precisely why the verification is the operator's job, not the tool's.

What's the actual concurrent-write corruption scenario this check prevents?

If two applies run against the same state simultaneously, both can read the same starting state, compute independent plans, and write back independently — the second write can silently clobber the first's changes in the state file, leaving state that no longer accurately reflects either apply's real infrastructure changes, a much harder problem to detect and fix than a blocked apply.

Does every backend support the same locking and force-unlock behavior?

No — locking support and its exact mechanism (DynamoDB table for S3, blob lease for Azure Storage, native locking for Terraform Cloud/HCP Terraform, S3's own `use_lockfile` since 1.11 as an alternative to DynamoDB) differ per backend, and the local backend's locking is filesystem-based and doesn't help at all across machines — know which backend you're actually running before reasoning about lock safety.

Why run `plan` again before resuming the interrupted apply, rather than just re-running `apply` directly?

The killed runner might have completed some resource operations before being terminated — `plan` shows you the actual current gap between state and desired config, so you resume from an accurate picture rather than assuming either "nothing happened" or "everything from before still needs to happen."

What would you have done if you couldn't confirm the lock holder was dead?

Wait, or escalate to find someone who can confirm it, rather than force-unlocking on a guess — an emergency change blocked a few extra minutes is a far smaller cost than concurrent-write corruption during an already-live incident.

How would you prevent this exact failure mode systemically, beyond the one runner-shutdown fix mentioned?

A lock TTL/staleness alert that pages someone automatically when a lock has been held far longer than any real apply should take, so a stuck lock surfaces proactively during business hours rather than being discovered reactively at 2am by whoever happens to need it next.

19Turning apply from a Friday ritual into a pipeline

Staff CI / test / reliability improvement

EXAMPLE — replace with your own

Terraform applies happened every Friday afternoon, run manually from someone's laptop against whatever the local checkout happened to contain, with no consistent record of who ran what or what plan they actually approved. It worked, in the sense that nothing had caught fire yet, but it depended entirely on the specific senior engineer who'd always done it being available, careful, and not on vacation.

I moved this into a proper pipeline in stages rather than a single cutover: first, plan-on-PR with the plan output posted as a PR comment (visibility, no behavior change yet); then, apply-on-merge-to-main gated by a required manual approval step referencing that exact plan artifact (so the approver reviews the plan that will actually run, not a fresh one that could differ); then, `terraform test` runs as a required check before merge for the modules that had test coverage, catching a class of bug before it ever reached a real plan.

jobs:
  plan:
    steps:
      - run: terraform plan -out=tfplan
      - run: terraform show -no-color tfplan > plan.txt
      - uses: actions/upload-artifact@v4
        with: { name: tfplan, path: tfplan }
  apply:
    needs: plan
    environment: production   # required reviewers configured here
    steps:
      - uses: actions/download-artifact@v4
        with: { name: tfplan }
      - run: terraform apply tfplan   # applies the exact reviewed plan, not a fresh one

The single most load-bearing detail was applying the saved plan file (terraform apply tfplan) rather than re-running plan implicitly inside apply — without that, a reviewer's approval is for a plan that might not be the one that actually executes if anything changed between review and apply.

(d) Follow-up drill chain

Why does `terraform apply tfplan` differ from running `terraform apply` with no saved plan?

With no saved plan, `apply` computes a fresh plan immediately before applying it — if anything in the real infrastructure or the configuration changed between when a human reviewed a plan and when apply actually ran, the executed plan could differ from the reviewed one. Applying a saved plan file guarantees the exact reviewed diff is what executes, or the apply fails if the saved plan is no longer valid against current state.

What can make a saved plan file become invalid before it's applied?

Any change to the real infrastructure or the state file after the plan was computed — someone else's apply, out-of-band drift, or even just enough time passing that a refresh would show different data — Terraform detects this and refuses to apply a stale plan rather than applying it against a no-longer-accurate baseline.

What does `terraform test` actually exercise that `plan` review doesn't?

.tftest.hcl files can run real `plan` and `apply` cycles against a module with assertions on the results, using mocked or overridden provider values to avoid touching real infrastructure for pure logic tests — it catches module-logic bugs (wrong conditional, bad default) before a real plan against production ever runs, which plan review alone can't do since plan review only sees the specific change being proposed, not the module's behavior space.

How do you decide what needs a required human approval versus what can auto-apply?

Blast radius and reversibility — a purely additive, well-tested change to a non-critical module is a reasonable auto-apply candidate; anything touching identity, networking, or data stores, or anything with a forces-replacement diff, should keep a human in the loop regardless of how mature the pipeline is.

What would you do if a required approver wasn't available and an urgent change needed to ship?

A documented break-glass path with a named backup approver or an explicit incident-commander override, logged and reviewed after the fact — not an informal "just merge it," which reintroduces exactly the single-point-of-dependency problem this whole pipeline was built to remove.

How does this pipeline design change for a Bicep-based deployment instead of Terraform?

The same staged shape applies — what-if-on-PR for visibility, then a gated deployment job — but the "apply the exact reviewed artifact" guarantee is harder to get natively, since ARM deployments don't have a first-class saved-plan-file equivalent; the mitigation is minimizing the time between the reviewed what-if and the actual deployment, and treating any drift in between as a reason to re-run what-if before proceeding.

22Night-before cheat sheet

read once then sleep

Ten sentences to read the evening before. They're about delivery, not content — the content is above, and cramming it tonight won't help.

  1. Open with one sentence of situation, then stop. "We ran about sixty Terraform-managed Azure environments, and a complete-mode Bicep deployment on one of them deleted a live DNS zone." Context, tool, symptom — then let them steer.
  2. Reach the result inside 90 seconds. If the story is long, give the result early and offer the detail: "we restored the zone from a paired read replica in nine minutes; the interesting part is the process change after — want that?"
  3. Quantify with the number that matters, not the one you remember best. Minutes of downtime, dollars a month, count of affected modules, plan runtime before and after — not "a lot faster." If you don't have the exact figure, say "roughly" and give a believable range.
  4. Separate "I" from "we" honestly, every time. "The team split the monolithic state into four; I designed the boundary and wrote the `state mv` migration." Blurring this is the single most common thing that sinks an otherwise strong candidate, and it's probed for directly.
  5. Own the failure before you're asked. "The complete-mode deploy running against a drifted resource group was our process gap" beats being walked into it. Every story above ends with a "what I'd do differently" for exactly this reason — deliver it unprompted.
  6. Tie every decision to a real trade-off you can name. State isolation for cross-stack convenience, standing access for speed, a saved-plan artifact for a slightly slower pipeline. A decision with no stated downside reads as one you haven't actually run in production.
  7. Have a scale or blast-radius answer ready for every story. "This state-splitting approach holds to roughly a few hundred resources per state; past that the next constraint is plan time, not correctness." It converts a war story into design thinking and pre-empts the obvious follow-up.
  8. Be precise about versions and dates when you claim currency. Terraform 1.16.0 shipped `terraform_data`, in-module `import` blocks, and Actions `on_failure` handling in August 2026; Bicep 0.47.16 is the current stable release as of September 2026. One dated, checkable fact signals currency far more than "I keep up with the ecosystem."
  9. When you don't know, say so and then reason from what you do know. "I haven't run Deployment Stacks at that scale — here's how I'd validate it, and here's what I'd expect to break first." A calibrated answer lands better than an invented one, and an invented one is unrecoverable under a follow-up.
  10. End each story with what it changed about how you work. The lint rule you now enforce, the metric you now track from day one, the review step that didn't exist before. That's the actual thing being assessed — and it hands the interviewer a natural place to go next.
