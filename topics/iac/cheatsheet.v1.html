IaC (Terraform & Bicep)

cheatsheet · Terraform 1.16.1 · Bicep 0.47.16 · released 2026-09-08

The HCL and Bicep syntax, CLI commands, state/backend and deployment mechanics, module patterns, and a modern-vs-legacy table and timeline for both languages, side by side. “Terraform” is read as HashiCorp/IBM Terraform (BSL-1.1–licensed since 1.5.6) with OpenTofu — its MPL-2.0 fork — noted only where the two now diverge, and “Bicep” as Microsoft’s ARM-native DSL and its az/bicep CLIs; Pulumi, CloudFormation, Ansible and Crossplane are out of scope. Verified 2026-09-08 against Terraform 1.16.1 (2026-09-02), OpenTofu 1.12.6 (2026-08-19) and Bicep 0.47.16 (2026-09-08).

Terraform 1.16.1 OpenTofu 1.12.6 Bicep 0.47.16 HCL2 ARM JSON compile target BSL 1.1 since 1.5.6 verified 2026-09-08

01IaC workflow & mental model

docs: Terraform intro

Both tools compile a declarative description into calls against a cloud control plane (ARM for Bicep; whatever the provider wraps for Terraform), then reconcile desired vs observed state. The loop is always: write → preview the diff → apply → the diff should now be empty.

write config  -->  plan (diff desired vs. real)  -->  human/CI reviews diff  -->  apply  -->  diff is empty
                         ^                                                                      |
                         '---------------------------- next change --------------------------- '
Desired vs. actual state
Terraform keeps its own record of the actual state (the state file); Bicep/ARM keeps none by default — each deployment is compared live against the resources under its scope, unless you opt into a deployment stack, which then tracks ownership the way Terraform state does.
Idempotency
re-running apply/deployment create with no config changes must be a no-op. If it isn’t, either the provider has a bug (a property that reads back different from how it’s written) or something is being managed outside the tool — the #1 cause of “drift” tickets.
Drift
the real resource diverges from the last-applied config (a console click, an autoscaler, a policy remediation). Terraform: terraform plan -refresh-only. Bicep: re-run what-if, or let a deployment stack’s denySettings block the out-of-band change in the first place.
Blast radius
scope every apply as narrowly as the tool allows: Terraform -target (an escape hatch, not a workflow — it can leave a plan that doesn’t match reality) or separate root modules/workspaces per environment; Bicep resource-group- or subscription-scoped deployments plus what-if before anything wider.
Change preview
terraform plan / az deployment group what-if — read every line before approving in CI; a “replace” on something stateful (a database, a storage account) is the one diff that deserves a stop-and-think.

Lead framing: pick Terraform when you need one tool across clouds, a mature module ecosystem, and explicit state you control; pick Bicep when you’re Azure-only and want same-day support for new ARM resource types with no state file to manage or lose. Plenty of shops run both — Bicep for platform/landing-zone plumbing, Terraform for the multi-cloud application layer — and the interview-safe answer is state management and drift handling, not syntax preference.

02Terraform language essentials

docs: Terraform language

HCL2 (stable since Terraform 0.12, 2019). Six top-level block types cover almost everything you write.

terraform {
  required_version = ">= 1.9"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}

variable "env" {
  type        = string
  description = "Deployment environment"
  validation {
    condition     = contains(["dev", "test", "prod"], var.env)
    error_message = "env must be dev, test or prod."
  }
}

locals {
  name_prefix = "orders-${var.env}"
  common_tags = { owner = "platform", env = var.env }
}

resource "aws_s3_bucket" "orders" {
  bucket = "${local.name_prefix}-${data.aws_caller_identity.current.account_id}"
  tags   = local.common_tags

  lifecycle {
    prevent_destroy = true
    ignore_changes  = [tags["last_synced"]]
  }
}

data "aws_caller_identity" "current" {}

output "bucket_arn" {
  value     = aws_s3_bucket.orders.arn
  sensitive = false
}
Meta-arguments
count (index-keyed list), for_each (map/set-keyed, the modern default — safer under reordering), depends_on (only for dependencies the graph can’t see, e.g. IAM eventual consistency), provider (pick an aliased provider instance).
lifecycle block
create_before_destroy, prevent_destroy, ignore_changes, and (since 1.16, 2026-08) destroy = false to keep a resource on terraform destroy instead of only on removal from config.
Custom conditions
precondition / postcondition blocks 1.2, 2022 inside resource, data, output or check blocks assert invariants at plan/apply time with a custom error message — the language-native replacement for a comment saying “don’t change this without also…”.
check blocks
1.5, 2023 post-apply health assertions (e.g. an HTTP data source returning 200) that report a warning, never fail the apply — monitoring-as-code, not a gate.
Dynamic blocks
dynamic "ingress" { for_each = var.rules content { ... } } generates repeated nested blocks from a collection — the only way to loop over a nested block (top-level resources use for_each directly).
Deprecation markers
deprecated = "use var.x instead" on variable/output blocks 1.15, 2026-04 emits a warning wherever the deprecated symbol is referenced.
Type conversion
convert(value, type) 1.15 for explicit, precise inline conversions instead of relying on implicit coercion.
Functions used daily
try(), coalesce(), merge(), jsonencode()/jsondecode(), templatefile(), for expressions ([for x in list : x.id]), splat (aws_instance.this[*].id), optional() inside object type constraints for module variable defaults.

Legacy still seen: count for anything keyed by name (renumbers everything on reorder — use for_each); a bare null_resource with triggers for “run this when X changes” — the modern replacement is the terraform_data resource 1.4, 2023, and its store block 1.16, 2026-08 can now hold ephemeral/sensitive values across plan and apply.

03State, backends & locking

docs: Terraform state

The state file (terraform.tfstate, JSON) is the single most important artifact in a Terraform setup: it maps config to real resource IDs, stores output values, and may contain secrets in plain text.

terraform {
  backend "s3" {
    bucket       = "acme-tfstate-prod"
    key          = "orders/terraform.tfstate"
    region       = "eu-west-1"
    use_lockfile = true          # native S3 locking, GA in 1.11 (2025-02)
    encrypt      = true
  }
}
Remote backends
HCP Terraform/Terraform Enterprise (state + locking + runs + policy as a service), s3, azurerm, gcs, pg. Local state (the default) is fine solo, never for a team — no locking, no shared source of truth.
Locking, modern
S3 backend use_lockfile = true GA 1.11, 2025-02 uses S3’s own conditional writes — no DynamoDB table to provision or pay for. azurerm locks natively via blob leases; both need no extra setup.
Locking, legacy still seen
S3 + a separate DynamoDB table (dynamodb_table) for locking. Still works — both mechanisms can run side by side during migration — but the DynamoDB arguments are deprecated; new setups should use use_lockfile only.
Workspaces
terraform workspace new prod — one state file per workspace, same config. Fine for small variance (dev/test/prod of one small stack); for real environment separation prefer separate root modules/backends — workspaces make it easy to forget which one you’re in and apply to the wrong environment.
Moving resources without destroying
moved { from = aws_instance.old, to = aws_instance.new } 1.1, 2021 records a rename/refactor in config so Terraform updates state instead of destroy+recreate. removed { from = aws_instance.old, lifecycle { destroy = false } } 1.7, 2024 drops a resource from state without touching the real infrastructure — the modern replacement for terraform state rm.
Importing existing infra
import { to = aws_instance.web, id = "i-0123" } config block 1.5, 2023, or by resource identity instead of ID 1.12, 2025-05; works inside modules since 1.16, 2026-08. Legacy: the imperative terraform import CLI command — still works, but writes no reviewable plan.
Ephemeral & write-only values
ephemeral resources/values 1.10, 2024-11 and write-only resource attributes 1.11, 2025-02 let a short-lived secret (a freshly minted DB password, a vault lease) flow through config without ever being written to state or the plan file — the answer to “why is this secret sitting in plaintext in my state”.
Inspecting & fixing state
terraform state list, state show <addr> (-json since 1.16), state mv, state pull > backup.tfstate before anything destructive. terraform force-unlock <lock-id> when a run died mid-apply and left the lock held — confirm no other apply is actually running first.

State always contains sensitive values in full, sensitive = true only redacts CLI/UI output. Encrypt the backend at rest, restrict who can state pull, and never commit a .tfstate file to git — it’s the classic finding in a security review.

04Terraform CLI & testing

docs: Terraform CLI commands 
terraform init -upgrade                       # download providers/modules, refresh the lock file
terraform validate                            # config is syntactically + internally consistent, no API calls
terraform fmt -recursive                      # canonical formatting, run in CI as a gate
terraform plan -out=tfplan                    # compute a diff, save it so apply can't drift from what was reviewed
terraform apply tfplan                        # apply exactly the reviewed plan (never re-plan implicitly in CI)
terraform apply -target=aws_s3_bucket.orders  # narrow blast radius; escape hatch, not a workflow
terraform destroy -target=aws_instance.scratch
terraform plan -refresh-only                  # see drift without proposing changes
terraform graph -type=plan -format=mermaid | ...   # 1.16: Mermaid output, paste straight into a doc
terraform console                             # REPL for evaluating expressions against real state
terraform providers lock -platform=linux_amd64 -platform=darwin_arm64   # cross-platform lock file for CI
The lock file
.terraform.lock.hcl mandatory since 0.14, 2020 pins exact provider versions/hashes — commit it, like a package-lock file. -upgrade is the only thing that should change it outside of adding a new provider.
Plan then apply the saved plan
the modern, CI-safe pattern is always plan -out=file then apply file: what gets reviewed is exactly what gets applied. Running bare terraform apply (which plans and applies in one step, prompting for confirmation) is fine interactively, legacy practice for pipelines.
terraform test
native test framework stable 1.6, 2023-10: *.tftest.hcl files with run blocks, assertions, and mock_provider/override_resource to test without touching real infrastructure. Superseded the community Terratest (Go) pattern for anything that doesn’t need real infra in the loop.
Provider-defined functions
1.8, 2024-04 — providers can ship functions (e.g. provider::aws::arn_parse()), not just resources/data sources; check a provider’s docs before writing an equivalent by hand with regex().
Actions
top-level action blocks 1.14, 2025-11 let a provider define imperative side effects (aws_lambda_invoke, a cache purge) triggered by a resource’s lifecycle or by terraform apply -invoke=<action>; 1.16 added before_destroy/after_destroy events and on_failure = halt|taint|continue. The modern, typed replacement for a local-exec provisioner hack.
Provisioners
local-exec/remote-exec are explicitly a last resort in the docs — Terraform can’t know what they did, so it can’t plan or track it. Prefer cloud-init/user-data, provider-native config, or actions.
Machine-readable output
-json on plan, state show and workspace list (all current through 1.16) — parse this, not the human-formatted text, when scripting CI checks (e.g. failing on any planned delete of a tagged-critical resource).

OpenTofu (see unit 11) is CLI- and state-compatible: the same *.tf config and the same terraform.tfstate shape works with either terraform or tofu as the binary — the fork is a licensing and governance story, not a syntax one.

05Modules & registry

docs: Terraform modules 
module "network" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.0"                 # always pin; unpinned = a silent breaking change some Tuesday

  name            = "vpc-${var.env}"
  cidr            = "10.20.0.0/16"
  azs             = ["eu-west-1a", "eu-west-1b", "eu-west-1c"]
  private_subnets = ["10.20.1.0/24", "10.20.2.0/24", "10.20.3.0/24"]
}

module "buckets" {
  source   = "./modules/bucket"
  for_each = toset(["raw", "curated"])     # for_each on a module, GA since 0.13 (2020)

  name = "${each.key}-${var.env}"
}

output "vpc_id" { value = module.network.vpc_id }
Module source addresses
registry (namespace/name/provider), Git (git::https://..., ?ref=v1.2.0), local (./modules/x), an HTTP archive, an S3/GCS bucket. Variables/locals are usable inside source/version 1.15, 2026-04, so a module path can vary by environment without duplicating the block.
Pin versions, always
a bare Git source with no ref, or a registry module with no version constraint, tracks HEAD/latest — a maintainer’s breaking change becomes your incident. Constrain with ~> (pessimistic, allows patch/minor per its precision) the same way you pin providers.
Structure convention
main.tf, variables.tf, outputs.tf, versions.tf per module; a root module composing child modules, never deeply nested (two or three levels is the practical ceiling before the graph gets hard to reason about).
Registry
public: registry.terraform.io. Verified/partner badges signal maintenance; a module with no recent commits and no pinned provider ceiling is a risk to adopt as-is — fork or vendor it instead of trusting it long-term.
Testing a module
*.tftest.hcl (unit 04) is now the default; put fixture .tf and test files under tests/ in the module repo so CI can run terraform test with no extra wiring.
Composing, not inheriting
Terraform modules have no inheritance — only composition (module calls module) and variable passing. If you want “override a few defaults from a shared base”, that’s a variables-with-defaults design, not a language feature.

06Bicep language essentials

docs: Bicep language

Bicep compiles 1:1 to ARM JSON — a domain-specific language over ARM, not a general IaC runtime. There is no Bicep state file: every deployment diffs live against the target scope (or, with a deployment stack, against what that stack owns).

targetScope = 'resourceGroup'

@description('Deployment environment')
@allowed(['dev', 'test', 'prod'])
param env string
param location string = resourceGroup().location

@secure()
param sqlAdminPassword string

type skuName = 'B1' | 'P1v4' | 'P2v4'          // user-defined type, stable since 0.21 (2023-09)

var namePrefix = 'orders-${env}'
var plans = {
  dev:  'B1'
  prod: 'P1v4'
}

resource plan 'Microsoft.Web/serverfarms@2024-11-01' = {
  name: 'plan-${namePrefix}'
  location: location
  sku: { name: plans[env] }
  properties: { reserved: true }               // reserved: true == Linux
}

resource sites 'Microsoft.Web/sites@2024-11-01' = [for i in range(0, 2): {
  name: '${namePrefix}-${i}'
  location: location
  identity: { type: 'SystemAssigned' }
  properties: { serverFarmId: plan.id }
}]

output principalIds array = [for s in sites: s.identity.principalId]
Scopes
targetScope: resourceGroup (default), subscription, managementGroup, tenant. A module can deploy to a different scope than its caller with an explicit scope: property.
Decorators
@description, @allowed, @secure(), @minLength/@maxLength, @minValue/@maxValue, @discriminator for tagged unions, @retryOn([...], count) to retry a flaky resource operation, @batchSize to control loop parallelism.
Loops
[for item in list: {...}] on a resource, module, property or output; [for (item, index) in list: {...}] when the index is needed; [for item in list: item if cond] filters. This is the only looping construct — there is no while.
Conditions
resource x '...' = if (cond) { ... } — deploys nothing (not an empty resource) when false. Combine with a loop: [for i in range(...): if (cond) {...}].
User-defined types & functions
types (type env = 'dev' | 'prod', object shapes, discriminated unions) stable 0.21, 2023-09; user-defined functions (func double(x int) int => x * 2) landed alongside — both are how you stop repeating a shape or a computation across files.
Null-safety
.?property safe dereference and ?? coalesce are the modern way to read a possibly-absent nested property (e.g. from existingResource().?sku.name ?? 'Standard', useful when re-deploying without clobbering a value set outside Bicep) — string-building your way around a null used to be the only option.
Functions used daily
resourceGroup(), subscription(), uniqueString(), guid(), reference()/existingResource(), listKeys() (control-plane secrets — avoid where a managed identity can do the same job instead).

Legacy still seen: hand-written ARM JSON templates and nested/linked templates for composition. Bicep is the only language Microsoft actively develops ARM authoring in; treat raw JSON in a repo as either bicep decompile bait or something a tool generated (e.g. a marketplace offer) that you shouldn’t hand-edit.

07Bicep params, modules & registry

docs: Bicep parameter files 
// main.bicepparam — typed, not JSON
using 'main.bicep'

param env = 'prod'
param sqlAdminPassword = getSecret('sub-id', 'rg-kv', 'kv-orders', 'sql-admin')

extends 'base.bicepparam'          // config-inheritance for param files, since 0.46 (2026-07)
module kv 'br/public:avm/res/key-vault/vault:0.11.0' = {
  name: 'kv-deploy'
  params: {
    name: 'kv-${env}-${uniqueString(resourceGroup().id)}'
    location: location
    enableRbacAuthorization: true
  }
}

module network 'modules/network.bicep' = {
  name: 'network-deploy'
  scope: subscription()            // module can target a different scope than its caller
  params: { addressPrefix: '10.20.0.0/16' }
}
.bicepparam vs. JSON params
.bicepparam (typed, IntelliSense, getSecret() pulls a value from Key Vault at deploy time without it ever landing in the file) is the modern format; ARM parameter JSON files are the legacy format still generated by older pipelines and templates.
Azure Verified Modules (AVM)
Microsoft-curated, tested modules in the public Bicep registry: br/public:avm/res/<service>/<resource>:<version> for a single resource, avm/ptn/* for multi-resource patterns. Prefer these over hand-rolled modules for anything common (Key Vault, storage, networking) — they track breaking ARM changes for you.
Private registries
az bicep publish --file m.bicep --target br:myacr.azurecr.io/bicep/m:1.0.0 publishes to an ACR-backed registry; reference with br:myacr.azurecr.io/bicep/m:1.0.0 or an alias configured in bicepconfig.json.
Local modules
a relative path (modules/network.bicep) with no registry involved — the common case inside one repo; the compiler inlines it into a nested ARM deployment.
Config inheritance
bicepconfig.json extends 0.46, 2026-07 lets a team config inherit an org-wide base and override only what differs (e.g. tighten one linter rule while keeping the rest); .bicepparam files gained the same extends to layer a base parameter file, with inherited params now optional to override.
Documenting a module
[Experimental] bicep docs generate 0.47.16, 2026-09-08 renders a module’s params/outputs to Markdown from a Scriban template — run it in CI so a module’s README can’t drift from its actual parameters.

08Bicep CLI, deployment & extensibility

docs: deploy Bicep files 
bicep build main.bicep                        # -> main.json, mostly for inspection/CI artifacts
bicep lint main.bicep                          # rules from bicepconfig.json
bicep format main.bicep --outdir .
bicep decompile legacy.json                    # one-way door: JSON -> Bicep, always review the output

az deployment group what-if -g rg -f main.bicep -p main.bicepparam       # the command you run before every apply
az deployment group create  -g rg -f main.bicep -p main.bicepparam -n rel-$(date +%s)
az deployment group create  -g rg -f main.bicep --mode Complete          # deletes anything in the RG not in the template

# deployment stacks: the modern owner-and-cleanup story
az stack group create -g rg -n app-stack -f main.bicep \
  --action-on-unmanage deleteResources --deny-settings-mode denyDelete
az stack group show   -g rg -n app-stack
az stack group delete -g rg -n app-stack --action-on-unmanage deleteAll
Incremental vs. Complete
default mode is Incremental — a resource removed from the template is left alone, same trap as Terraform without a moved/removed block. --mode Complete deletes anything in scope not declared in the template; either way, what-if first.
Deployment stacks
GA Nov 2024 — the stack owns the resources it deploys, can delete ones that leave the template on the next apply, and its denySettings can block out-of-band changes/deletes on managed resources. This is the direct answer to “Bicep has no state file, so who cleans up?” and the modern replacement for the retired Azure Blueprints service.
Extensibility (extension)
the provider keyword was renamed to extension breaking change, 0.29, 2024-07 as Bicep grew non-ARM targets: extension microsoftGraph lets a template manage Entra ID apps/groups (Microsoft Graph extension, public preview since 0.28, 2024-06) alongside ARM resources in the same file. Any provider keyword in a `.bicep` file or `bicepconfig.json` is now dead syntax.
Local deploy
[Experimental] bicep local-deploy/local extension host lets an extension run resource operations locally instead of through ARM — the mechanism behind non-ARM extensions; still experimental, opt in via bicepconfig.json experimentalFeaturesEnabled.
Linting
rules live in bicepconfig.json under analyzers.core.rules; useful ones to turn on: no-hardcoded-env-urls, no-unused-params, no-unused-types 0.46, secure-params-in-parameters-file (catches a secret literal checked into a .bicepparam), and the newer description-enforcement rules 0.47 (off by default — opt in for a shared-module repo).
Snapshot & diffing
bicep snapshot gives a normalised, diffable view of what a file will produce — useful in a PR to see the actual ARM-shape delta instead of the Bicep source delta.
azd (app-centric wrapper)
azd init/azd up/azd provision --preview wrap Bicep (or Terraform) with an app manifest (azure.yaml) and CI wiring (OIDC federated pipeline creds, no secrets). Reach for it on greenfield app+infra repos; plain az deployment/az stack for platform and landing-zone code you want full control over.

09Gotchas, one line each

docs: Terraform state locking
  • State contains secrets in plaintext, always — sensitive = true only hides CLI/UI output, it does not encrypt the state file.
  • count on a heterogeneous list renumbers everything on reorder/insert; a “no-op” plan turns into a destroy-and-recreate cascade. Use for_each.
  • terraform_data/null_resource triggers that never change silently stop re-running the paired provisioner — check the triggers map actually reflects what should invalidate it.
  • Stale lock after a killed apply leaves every teammate blocked; verify nothing is actually running before force-unlock.
  • Unpinned module/provider versions mean “works on my machine” today, a break-fix tomorrow when init -upgrade pulls a new major.
  • -target becomes a habit and the full-config plan silently diverges from what’s actually been applied — it’s an escape hatch, not a workflow.
  • Provisioners can’t be planned: Terraform has no idea what a local-exec script did, so it can’t detect drift it caused.
  • Refresh changes state without a plan review if run bare (terraform refresh is deprecated) — use plan -refresh-only and actually read it before apply.
  • Bicep Incremental mode never deletes a resource removed from the template — it just orphans it, invisibly, unless you’re on a deployment stack or explicit Complete mode.
  • API version pinning bites both tools: a property genuinely does not exist on an older ARM API version, no matter how correctly you spell it in Bicep or in azapi/azurerm.
  • what-if summaries can lie on complex nested changes — rerun with --result-format FullResourcePayload when the one-line summary looks too good to be true.
  • Role/permission propagation lag (Azure RBAC, IAM) makes “grant then use in the same apply” flaky in both tools; retry, add an explicit wait, or split the run.
  • Secrets in a .bicepparam literal are as bad as in JSON — use getSecret() or a Key Vault reference, and turn on secure-params-in-parameters-file.
  • bicep decompile is a starting point, not a finish line — it produces valid but often unidiomatic Bicep; always review and refactor before trusting it.
  • Deployment history growth: Azure keeps a per-resource-group deployment history; very high-frequency pipelines can hit the retention ceiling — deployment stacks and newer tooling auto-prune, hand-rolled loops may not.
  • Terraform and OpenTofu diverge quietly over time — a provider or module that only tests against one may use a construct (an OpenTofu-only function, a Terraform-only action) the other can’t parse.

11Version timeline

docs: Terraform releases

Latest first. Terraform is HashiCorp/IBM (BSL-1.1 since 1.5.6); OpenTofu is the Linux Foundation's MPL-2.0 fork from that same 1.5.6 base, CLI/state-compatible.

  • 2026-09-08 — Bicep 0.47.16: experimental bicep docs generate; .bicepparam extends merge-semantics fixes.
  • 2026-09-02 — Terraform 1.16.1: bug-fix release on 1.16.
