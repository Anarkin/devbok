01Core IaC concepts & state fundamentals

Before any tool-specific syntax, every interviewer wants to know you understand what problem IaC actually solves and what it costs to solve it that way. Screener depth is defining idempotency and declarative-vs-imperative correctly; senior depth is explaining precisely why a state file exists and what breaks without one; principal depth is reasoning about blast radius and coupling as first-class design constraints, the same way you would for a service architecture. This sub-area is asked constantly because a wrong answer here usually means every deeper answer in the bank is memorized rather than understood.

What does it mean for infrastructure-as-code to be declarative, and why do Terraform and Bicep both choose that over an imperative script? screener

Answer. A declarative tool describes the desired end state — “there should be a storage account named X with these properties” — and leaves the tool to work out the sequence of API calls that gets you there; an imperative script describes the steps — “call create-storage-account, then call set-property” — and you own getting that sequence right every time, including on a re-run against something that already exists. Declarative wins for infrastructure specifically because infrastructure is long-lived and repeatedly re-applied: the same file is run today to create something and next month to change one property, and the tool's job is to diff desired against actual and emit only the necessary calls. That diffing step is exactly what a plan or what-if operation shows you before anything happens, which an imperative script has no equivalent of unless you build it yourself.

Example

resource "azurerm_storage_account" "data" {
  name                     = "stdataprodweu001"
  resource_group_name      = azurerm_resource_group.app.name
  location                 = "westeurope"
  account_tier             = "Standard"
  account_replication_type = "ZRS"
}

Run this twice with no change and Terraform's plan says “no changes”; change account_replication_type to GRS and the plan shows exactly one in-place update — you never write the update call yourself.

Follow-ups

  • Is Bicep declarative in the same way? — Yes; it compiles to an ARM JSON template that Azure Resource Manager itself diffs against the resource group's current state, so the declarative engine there is ARM, not the Bicep CLI.
  • Can declarative tools do anything imperative? — Yes, deliberately narrow escape hatches — Terraform's provisioner blocks, Bicep's deployment scripts — and both ecosystems treat them as a last resort because they reintroduce the exact ordering and idempotency problems declarative tools exist to avoid.
  • What's the cost of declarative? — You give up fine-grained control over the exact API call sequence, which occasionally matters for slow, order-sensitive operations (e.g. certain network resource replacements), and you inherit the provider's or ARM's understanding of dependencies rather than your own.

Wrong answer: “Declarative means you don't need to know the order things get created in.” Order still matters and still has to be correct — dependency graphs and depends_on/implicit references exist precisely because of it. What you're freed from is writing the ordering logic yourself and re-deriving it for updates and deletes.

Define idempotency in the IaC sense, and give an example of a resource or operation that quietly breaks it. screener

Answer. An idempotent operation produces the same end state no matter how many times you apply it — applying a config that is already satisfied is a no-op, not an error and not a duplicate. Terraform and Bicep get this largely for free from their declarative diff-then-converge model, but it is a property of the combination of your config and the provider, not a guarantee the tool gives you unconditionally. The classic break is a resource whose creation has a side effect the tool can't see and therefore can't diff against — a null_resource/local-exec provisioner that appends a line to a file, a Bicep deployment script that calls an external API, or a resource attribute generated freshly by the provider on every read (a timestamp, a random suffix) that shows as permanent drift even though nothing you control changed.

Example

resource "null_resource" "seed" {
  provisioner "local-exec" {
    command = "curl -X POST https://api.internal/seed-once"
  }
}

Terraform considers this resource unchanged forever once created, so the provisioner only fires on creation or on an explicit terraform taint/-replace — but if that endpoint is not itself idempotent (it appends rather than upserts), a taint plus re-apply will double-seed. The non-idempotency isn't in Terraform, it's in what you told it to shell out to.

Follow-ups

  • How do you find non-idempotent resources before production? — Run plan (or what-if) twice in a row with no intended change and treat any non-empty second diff as a bug, ideally as an automated CI check.
  • Are all provider bugs idempotency bugs? — Many are — a provider that doesn't fully read back a resource's state will show phantom diffs every run; this is the most common real-world cause of “drift that isn't really drift.”
  • Does count/for_each affect idempotency? — Indirectly: a count driven by something non-deterministic (a data source result that changes order) can make Terraform think it must destroy and recreate items that didn't logically change — a keying problem, not an idempotency problem, but it presents the same way.

Wrong answer: “Idempotent just means re-running apply is safe.” True but incomplete — the interviewer is listening for you to name a concrete way that safety gets violated in practice (a provisioner, a provider bug, a non-deterministic attribute), because “it's safe” with no caveat is the sentence that precedes a production incident.

Why does Terraform need a state file at all — why can't it just query the cloud provider every time to know what exists? mid

Answer. Three separate reasons, and a strong answer names more than one. First, mapping: cloud APIs identify resources by an ID the provider assigns, but your config identifies them by a resource address (azurerm_storage_account.data) — the state file is the only record of which ID a given config block currently owns, and without it Terraform cannot tell “this block already has a resource” from “this block needs to create one.” Second, performance: re-describing every resource by querying live APIs for a large estate is slow and rate-limited, whereas most of a plan can be computed from the cached state plus a targeted refresh. Third — and the one candidates miss — the state file is the only place values not visible in the API response can live at all, such as attributes Terraform itself generated (a random password) or values marked sensitive that a provider's read call would not return in full. Bicep sidesteps most of this because ARM already keeps its own record of what a template deployed, which is why Bicep famously has “no state file” — the state lives server-side in Azure instead of client-side in a file you manage.

Example

terraform state list
# azurerm_resource_group.app
# azurerm_storage_account.data
terraform state show azurerm_storage_account.data
# id = "/subscriptions/.../storageAccounts/stdataprodweu001"

Delete that line from state (terraform state rm) without deleting the real resource, and the very next plan proposes creating a duplicate — proof the mapping, not the cloud, is what Terraform actually trusts.

Follow-ups

  • So Bicep really has no equivalent problem? — It has the same problem one layer up: a Deployment Stack (see unit 12) keeps exactly this kind of record so it can know what to delete when something is removed from the template, which is Azure re-inventing a state file for the one operation ARM couldn't otherwise support.
  • What does -refresh-only actually refresh? — It re-reads every resource's current attributes from the provider and updates state to match, without touching real infrastructure — it's how you detect drift without risking a corrective apply.
  • Can two different state files describe the same real resource? — Yes, and it's a real incident pattern — two Terraform roots both importing the same VNet, each convinced it owns changes to it, fighting on every apply.

Wrong answer: “State is just a cache so Terraform doesn't have to hit the API as often.” That's true but it's the least important of the three reasons, and answering only with it suggests you've never had to recover a broken state file, where the mapping problem is the one that actually hurts.

What is configuration drift, and how do you detect and reconcile it in practice? mid

Answer. Drift is any gap between what your IaC declares and what actually exists in the cloud — caused by a manual portal change, an emergency CLI fix during an incident, another automation touching the same resource, or a provider default changing underneath you. Detection is a scheduled, read-only plan (or terraform plan -refresh-only, or a scheduled Bicep what-if) run against every environment, with any non-empty diff alerted rather than silently ignored; the number of drift incidents caught this way is a genuinely useful platform-health metric. Reconciliation has two directions and picking the wrong one is the actual skill: if the manual change was correct and should stick, you update the config to match reality (or terraform import/generate-config the change) so the code becomes the new source of truth; if the manual change was a mistake or a stopgap, you let the next apply revert it — but only after confirming nobody depends on the drifted state, because a silent revert of an intentional emergency fix is its own incident.

Example

terraform plan -refresh-only -out=refresh.plan
terraform show -json refresh.plan | jq '.resource_changes[] | select(.change.actions != ["no-op"])'

Wiring that into a scheduled pipeline that posts to a channel on any non-empty result turns drift from a surprise during your next real change into a Tuesday-morning ticket.

Follow-ups

  • Does drift detection alone fix anything? — No — -refresh-only updates state to reality but changes no infrastructure; you still choose and run the reconciling action deliberately.
  • How do you stop drift recurring from the same source? — Find and close the door: revoke the portal write access that caused it, or add an Azure Policy/Sentinel rule that denies the specific manual change going forward.
  • What's the Bicep equivalent workflow? — az deployment group what-if against the same template and parameters on a schedule; Deployment Stacks add an explicit “detach vs delete” decision for resources that fell out of the template.

Wrong answer: “Just re-run apply regularly so drift gets fixed automatically.” Blindly applying without reviewing the diff first is how a deliberate emergency fix — a scaled-up SKU, an opened firewall rule to unblock an incident — gets silently reverted in the middle of the night with nobody watching.

Compare the reconciliation model in Terraform/Bicep (run-once diff-and-apply) with a Kubernetes controller (continuous reconciliation loop). What does each buy you? senior

Answer. Terraform and a plain Bicep deployment compute the diff once, at the moment you choose to run them, and then stop — nothing keeps watching afterward, so drift accumulates silently until the next run. A Kubernetes controller (or GitOps tools like Flux/Argo CD layered on top of either IaC tool) reconciles continuously

Example

Run-once:      git push -> CI plan -> human approves -> CI apply -> stops watching
Continuous:     git push -> controller reconcile loop -> converges within its poll interval,
                forever, including reverting a manual kubectl edit within seconds

Follow-ups

  • Why doesn't Terraform just run continuously? — Because most of what it manages (a VNet, a database, an IAM role) is far more dangerous to reconcile unattended than a pod replica count — an unattended destroy-and-recreate on a stateful resource is a different risk class than restarting a container.
  • What does Atlantis / HCP Terraform's VCS-driven runs add? — They automate the run-once loop around a PR (auto-plan on open, apply on merge) without making it continuous — still a human-gated, event-triggered model, not a control loop.
  • Is there a Terraform-native continuous option? — HCP Terraform can be configured to run on a schedule and alert on drift, but it still does not self-heal without a human or a policy triggering the apply — it stays reconciliation-once by design.

Wrong answer: Treating “continuous is strictly better” as the conclusion. Continuous reconciliation applied to the wrong resource class — say, auto-reverting a manually-scaled production database back to a stale config value during an incident — is a worse outcome than drift sitting quietly until a human looks at it.

Walk through what actually happens, mechanically, when you run terraform plan. mid

Answer. Four stages. First, Terraform reads the configuration and builds a dependency graph from every resource, module, data source and their references. Second — unless -refresh=false is set — it refreshes: for every resource already in state it calls the provider's read API to reconcile state with live reality (this is the step that surfaces drift). Third, it walks the graph and, for each node, computes a diff between the refreshed prior state and the desired configuration, producing a proposed action per resource: create, update in place, destroy, or destroy-and-recreate. Fourth, it renders that as a human-readable plan and — if you passed -out — serializes it to a binary plan file that a subsequent apply can execute exactly, guaranteeing what you approved is what runs, with no re-diffing in between.

Example

  # azurerm_storage_account.data will be updated in place
  ~ resource "azurerm_storage_account" "data" {
      ~ account_replication_type = "LRS" -> "ZRS"
        id                       = "/subscriptions/.../stdataprodweu001"
    }

The ~ means in-place; a resource line prefixed -/+ instead means destroy-and-recreate, which is the single symbol most worth training yourself to spot before approving anything.

Follow-ups

  • Why does a saved plan file matter operationally? — Without it, apply re-plans from scratch and can execute a different diff than the one a human reviewed, if anything changed in between — the classic gap that plan -out=tf.plan then apply tf.plan closes.
  • What does -target do to this process, and why is it discouraged as a habit? — It restricts the graph walk to a subresource, which is useful for surgical recovery but produces a plan blind to the rest of the graph's dependencies — repeated use is a sign the module boundaries are wrong.
  • Where does Bicep's what-if differ? — ARM computes the same kind of diff server-side against the resource group's tracked state, but has no separate persisted plan file to apply later — what-if and the subsequent create are two independent server-side computations, so the small window between them is real (see unit 12).

Wrong answer: “plan just shows you a text diff of the .tf files.” It's a diff against live, refreshed infrastructure state, not a source diff — which is exactly why a plan can show unexpected changes even when nobody touched the .tf files, because something in the real world moved.

Give a concrete example of an apply that is idempotent on paper but produces a different real-world result the second time it runs. senior

Answer. Any resource whose creation depends on a data source that resolves to “the current something” rather than a pinned value. The most common real one: a data source that looks up “the latest” VM image, AMI, or container tag at plan time. Nothing in the Terraform config changed between two applies a month apart, but the data source resolves to a different image ID, so the plan proposes recreating (or updating) the resource purely because time passed — the config is stable, but the world it queries is not, and Terraform faithfully reports that as a change because from its point of view, the desired state genuinely changed.

Example

data "azurerm_shared_image_version" "latest" {
  name                = "latest"
  image_name          = "app-image"
  gallery_name        = "gallery"
  resource_group_name = "images-rg"
}

resource "azurerm_linux_virtual_machine" "app" {
  source_image_id = data.azurerm_shared_image_version.latest.id
  # ...
}

Two engineers running terraform apply on the same commit, an hour apart, after a new image version is published, get two different plans — one a no-op, one a VM replacement — despite identical code. That's not a bug; it's a floating reference doing exactly what it says.

Follow-ups

  • How do you fix it? — Pin the version explicitly in a variable, bump it through a reviewed PR, and treat the image version like any other dependency version — the “latest” lookup is fine for discovery, not for what feeds a resource argument.
  • Is this a Terraform problem or a provider problem? — Neither — it's a modeling choice in your config; the same footgun exists in Bicep with any listKeys()/reference() call against a resource whose underlying value rotates, or a parameter defaulted to a “latest” marketplace image.
  • What's the safe pattern for “always the newest” when you genuinely want that? — Make the resolution and the deploy the same pipeline run (resolve once, pass the concrete value down, log it), so at least the outcome is traceable to a specific resolved value in the run's logs rather than resolved silently inside apply.

Wrong answer: “That can't happen if your code hasn't changed — Terraform is deterministic.” Terraform's diff algorithm is deterministic; the inputs to it are not, the moment a data source reaches outside your repository for a value that can change on its own schedule.

Where's the line between an IaC/orchestration tool (Terraform, Bicep) and a configuration-management tool (Ansible, Chef, Puppet)? Where do teams get this wrong? mid

Answer. IaC/orchestration tools provision and wire together cloud resources — the VM, the network, the managed database, the identities and role assignments between them — as whole units addressed by a provider API; configuration-management tools reach inside a running host to install packages, template files, and manage service state, usually by SSH or an agent. The line has moved as clouds shipped more managed services: much of what config management used to do (install a web server, configure it) is now “provision a PaaS resource with the runtime baked in” instead — an App Service, a Container App — which is why Ansible/Chef/Puppet usage has genuinely shrunk in cloud-native shops, not because they got worse but because there are fewer bare VMs left to configure. Teams get it wrong in both directions: encoding host-internal configuration as sprawling Terraform local-exec/remote-exec provisioners (fighting the tool, fragile, no idempotency guarantee) or, conversely, hand-provisioning infrastructure and only managing what's inside it, which reintroduces drift at the layer IaC exists to close.

Example

# Anti-pattern: reaching inside the host from Terraform
resource "azurerm_linux_virtual_machine" "app" {
  # ...
  provisioner "remote-exec" {
    inline = ["sudo apt-get install -y nginx", "sudo systemctl enable nginx"]
  }
}
# Better: bake it into the image (Packer) or use a managed runtime,
# and let Terraform own only the VM/App Service resource itself.

Follow-ups

  • When is a provisioner still legitimate? — A narrow, one-shot bootstrap action with no config-management alternative already in place — e.g. registering a freshly created VM with an external service that has no Terraform provider — used sparingly and treated as a code smell to revisit.
  • Where does immutable-image building (Packer) fit? — Upstream of provisioning: bake the OS/runtime configuration into an image once, then Terraform/Bicep just launches instances of it — pushing configuration management to build time instead of run time.
  • Does Kubernetes change this line again? — Yes — inside a cluster, the container image plus a manifest replaces config management entirely for the workload; Terraform/Bicep's job shrinks to the cluster and its surrounding cloud resources, not what runs on it.

Wrong answer: “Terraform and Ansible do the same job, pick whichever you know.” They solve adjacent but distinct problems, and a design that uses one tool for both jobs — instead of the one it's suited to — is the actual signal an interviewer is checking for, not brand preference.

What is “blast radius” in an IaC context, and why does a single monolithic state file or template make it worse? senior

Answer. Blast radius is how much can go wrong from one mistake — one bad plan approved in a hurry, one lock stuck mid-apply, one bug in a shared module. A single state file (or a single ARM deployment) covering an entire estate means every apply's failure mode includes everything in it: a lock held by a stuck apply blocks every other change to any resource in that state, a single malformed reference can produce a plan that proposes destroying unrelated resources it happens to share a graph with, and a state file corruption or accidental terraform state rm can put dozens of resources' bookkeeping at risk in one action. The IaC-specific reason this is worse than the equivalent mistake in application code is that many of the operations in question (deleting a resource, rotating a key that other systems depend on) are not easily reversible by redeploying — there's no “roll back the pod” equivalent once a database has actually been dropped.

Example

One state file, 400 resources, three teams:
  - team A's apply on a VNet subnet triggers a plan touching the shared Application Gateway
    because both live in the same state and share an implicit dependency
  - the apply fails halfway through and holds the lock for 40 minutes
  - teams B and C cannot deploy anything, including an unrelated hotfix, until it clears

Follow-ups

  • What's the standard mitigation? — Split state along ownership and blast-radius boundaries (unit 04/05): one state per team/lifecycle domain, composed via remote state data sources or a platform-provided vending layer, so a lock or a bad apply in one domain cannot block another.
  • Isn't splitting state itself risky? — Yes, differently: too many tiny states multiplies the coordination burden and the number of places a cross-cutting change (e.g. a new required tag) has to be rolled out to; the goal is boundaries that match real ownership, not maximum fragmentation.
  • How does Bicep's model change this trade-off? — A single ARM deployment is already scoped to a resource group (or a chosen scope), and Deployment Stacks add explicit boundaries and deny-settings per stack — but a subscription-wide template with everything in one deployment has exactly the same monolith problem.

Wrong answer: “Blast radius is just about how many resources are in the state file.” Count is a proxy, not the thing itself — a state file with 500 independent, unrelated resources is far safer than one with five resources tightly coupled through implicit dependencies and shared teams.

A junior engineer asks: “if the tool is declarative and idempotent, why do we still need code review and a plan step at all?” How do you answer that? mid

Answer. Idempotency guarantees that running the same config repeatedly converges to the same state — it says nothing about whether that state is the one you actually want. A plan step exists because the diff between “what's live” and “what the new config declares” can contain a destructive action nobody intended: a renamed argument the provider treats as forcing replacement, a typo that widens a firewall rule, a module upgrade that silently changes a default. Code review catches intent errors before they're even planned; the plan step catches the gap between intent and the provider's actual mechanics, which is a different failure class entirely and one that only shows up at plan time because it depends on live state the reviewer of the diff-in-a-PR can't see. Neither substitutes for the other, and both exist because “the tool won't let you do something wrong” is never actually true — it will faithfully execute whatever you declare, including a mistake.

Example

  # innocuous-looking PR: renaming a variable for clarity
- resource "azurerm_subnet" "app" {
-   address_prefixes = [var.app_cidr]
+ resource "azurerm_subnet" "application" {
+   address_prefixes = [var.app_subnet_cidr]
  }
  # plan reveals the real consequence:
  # -/+ azurerm_subnet.app will be destroyed and azurerm_subnet.application created
  #     (renaming the resource label, not just the variable, changed its address)

Follow-ups

  • Isn't this exactly what moved blocks are for? — Yes — this specific example is the textbook case for a moved block, and pointing that out mid-answer is a strong signal you've actually hit this in practice.
  • Does a plan step catch everything? — No — it catches mechanical consequences of a diff, not whether the desired state is a good idea (a plan will happily show you “this will open port 22 to 0.0.0.0/0” without flagging it as dangerous; that's what policy-as-code and review are for).
  • How do you make plan review actually effective rather than rubber-stamped? — Make the plan output part of the PR (posted as a comment by CI), require any destroy/replace action to be called out explicitly, and treat an unexpected destroy in a plan as a hard stop, not a note.

Wrong answer: “Idempotent tools can't make destructive mistakes because they only converge to the desired state.” The desired state itself can be destructive, and the tool will converge to it just as faithfully as to a correct one — idempotency is about repeatability, not safety.

Walk through the core Terraform workflow commands and what each one is responsible for. screener

Answer. terraform init downloads providers and modules and configures the backend — it's the only command that touches .terraform/ and the lock file, and must be re-run whenever a required provider, module source, or backend config changes. terraform validate checks the configuration is internally consistent (types, required arguments, references that resolve) without talking to any provider API. terraform plan refreshes state, computes the diff against desired configuration, and shows proposed actions, optionally saved to a file with -out. terraform apply executes a plan — either a freshly computed one, or a saved plan file passed as an argument, which is the safer pattern because it guarantees what's applied is exactly what was reviewed. terraform destroy is apply of a plan whose desired state is empty, tearing down everything the state file tracks.

Example

terraform init -upgrade
terraform validate
terraform plan -out=tf.plan
terraform apply tf.plan

Follow-ups

  • When do you need -upgrade on init? — When you've widened a version constraint and want the lock file to consider newer provider/module versions, not just the ones it already pinned.
  • Does validate catch a bad credential or a nonexistent resource ID? — No — it's purely static; anything requiring an API call is only caught at plan or apply.
  • What's the CI-safe way to run this? — Non-interactive: init -input=false, plan -input=false -out=tf.plan, then a human or a policy gate approves before apply tf.plan runs, never re-planning at apply time.

Wrong answer: “apply without an argument does the same thing as applying a saved plan.” It re-plans from scratch first — if anything in the environment changed since you last looked, you can approve one diff interactively and have a subtly different one actually execute.

What's the difference between terraform taint (deprecated) and terraform apply -replace, and why did HashiCorp make the change? mid

Answer. Both mark a resource for destroy-and-recreate on the next apply, but taint mutated the state file immediately and outside of any plan — a side effect with no preview, no approval step, and a real risk if run against the wrong resource address or a stale state. -replace=

(introduced 0.15.2, now the only supported spelling since 0.15.10 deprecated taint) instead becomes part of the plan itself: you see the replacement as a proposed action, like any other change, before anything happens. This fits Terraform's broader direction of removing every state mutation that used to happen as an immediate side-effect command in favor of routing it through plan-and-apply, which is the same motivation behind moving state manipulation into terraform state subcommands with clearer semantics.

Example

# legacy, deprecated
terraform taint azurerm_linux_virtual_machine.app
# current
terraform apply -replace="azurerm_linux_virtual_machine.app"

Follow-ups

  • Can you force replacement from inside the config itself? — Yes, a replace_triggered_by argument in a resource's lifecycle block ties replacement to a change in another resource or value, without any CLI flag.
  • What about the opposite — preventing a replacement Terraform wants to do? — lifecycle { ignore_changes = [...] } for a specific attribute, or create_before_destroy = true if the goal is avoiding downtime during an unavoidable replacement rather than avoiding it altogether.
  • Is -replace destructive on its own? — No — like any plan flag it only takes effect once you approve and run the resulting apply; you can still cancel after seeing the plan.

Wrong answer: “taint and -replace are just old and new names for the same flag with no real behavior difference.” The behavior difference — immediate state mutation with no plan preview versus a reviewable plan action — is exactly the point being tested; naming it as cosmetic misses why the change happened.

When and why would you use -target, and why do senior engineers treat frequent use of it as a smell? senior

Answer. -target=

restricts a plan/apply to one resource (and anything it depends on), skipping the rest of the graph. It's the right tool for surgical recovery: an apply failed halfway through and you need to retry just the resource that errored, or you're breaking a circular-looking dependency deliberately in stages. It's the wrong habit for routine work because a targeted plan is graph-blind to everything outside the target — it can miss a required update to something the target depends on, and repeated cleanly-scoped applies to the whole graph are what actually validate that your configuration is internally consistent. If a team reaches for -target every week, that's usually a sign the module or state boundaries don't match how the team actually wants to deploy — the fix is smaller, better-scoped states or modules, not -target as a permanent workflow.

Example

terraform apply -target="azurerm_key_vault.app" -target="azurerm_key_vault_secret.db_password"

Follow-ups

  • Does -target update state for anything else? — No — resources outside the target set (even if their config changed) are left exactly as they were in state, which can leave the plan and the real applied diff subtly out of sync until a full apply catches up.
  • Is there a modern replacement for some -target use cases? — Partially — the -exclude flag (1.9+) inverts the selection, and for genuinely independent lifecycles the real fix is splitting state (unit 04), not a better flag.
  • What does Terraform warn you about after a targeted apply? — It explicitly prints a warning that the plan was partial and recommends running a full plan afterward — worth reading in CI logs, not just dismissing.

Wrong answer: “-target is dangerous and should never be used.” It's a legitimate, sometimes essential recovery tool — the actual signal being tested is whether you can distinguish emergency surgical use from routine reliance on it.

What's the difference between terraform refresh (removed as a standalone command), plan -refresh-only, and the automatic refresh inside every plan? senior

Answer. Every plan and apply implicitly refreshes state against the provider before computing its diff, unless you pass -refresh=false — this is just step one of the normal workflow, not a separate operation. The standalone terraform refresh command did the same read-and-update-state step in isolation but applied the result to state immediately, with no plan to review and no chance to say no — which made it easy to accidentally accept a drifted value into state without ever looking at it. terraform plan -refresh-only (1.1+) is the replacement: it does the identical refresh, shows you the resulting diff against prior state as an actual plan, and only updates state if you then explicitly apply that plan — same information, but gated behind a review step like everything else.

Example

terraform plan -refresh-only -out=refresh.plan
# review: is this drift something to accept into state, or a bug to fix and revert?
terraform apply refresh.plan

Follow-ups

  • Does -refresh-only ever change real infrastructure? — No, never — it only ever updates the state file's record of reality; the actual resources are read, not written.
  • Why remove the standalone command rather than just deprecate it? — Consistency with the rest of the CLI's direction: every state-affecting operation should go through the plan/apply review gate, and a command that mutated state silently was the odd one out.
  • What if refresh reveals a resource was deleted outside Terraform? — The refreshed plan shows it going from tracked to absent; applying that plan removes it from state (not from the world, since it's already gone), and the next regular plan will then propose recreating it if it's still declared in config.

Wrong answer: “refresh was removed because it's no longer needed — plan does it automatically now.” Refresh-the-behavior is still there and still essential; what was removed is the ungated, no-review way of triggering it on its own.

Explain the dependency lock file (.terraform.lock.hcl): what it pins, what it doesn't, and what happens if it's missing in CI. mid

Answer. The lock file records the exact provider versions and their checksums (for every platform Terraform was told to support) that init selected to satisfy your required_providers constraints — it exists so that two different machines running init against the same config get byte-identical provider binaries, not just versions that happen to satisfy the same constraint range. It pins providers only, not modules (module version pinning lives in the module source/version arguments themselves) and not the Terraform CLI's own version (that's `required_version`, enforced separately). If it's missing or not checked in, every fresh init re-resolves provider versions against the constraints in your config and the provider registry's current state — which means a provider that shipped a new version between two CI runs can silently change what gets installed, defeating the entire point of a lock file.

Example

provider "registry.terraform.io/hashicorp/azurerm" {
  version     = "4.9.0"
  constraints = "~> 4.0"
  hashes = [
    "h1:xxxxx...",
  ]
}

Follow-ups

  • Should the lock file be committed? — Yes, always — it's the entire mechanism, exactly like a language package manager's lock file, and CI should run init without -upgrade so it respects what's committed rather than silently drifting.
  • How do you deliberately update a pinned provider? — terraform init -upgrade, review the resulting lock file diff in the PR like any other dependency bump, then commit it.
  • What if your CI runs on a different OS than developers' laptops? — terraform providers lock -platform=linux_amd64 -platform=darwin_arm64 ... pre-populates hashes for every platform you need, so init never needs network access to the registry to verify a checksum for a platform nobody's run init fresh on yet.

Wrong answer: “The lock file pins the Terraform version so everyone uses the same CLI.” That's the separate `required_version` setting in the `terraform` block — the lock file is exclusively about provider (and provider-only) versions and hashes.

What does the state lock actually protect against, and what happens when a lock gets stuck? senior

Answer. Every plan (that writes a refresh) and every apply acquires a lock on the state (implemented differently per backend — a native lock API on Azure Blob Storage via a lease, a DynamoDB row historically for S3 before native S3 locking, a Postgres row for the `pg` backend) to prevent two concurrent runs from reading, diffing, and writing the same state file at once, which would otherwise corrupt it or silently drop one run's changes. A lock gets stuck when a process holding it dies abnormally — a killed CI job, a laptop that went to sleep mid-apply, a crashed runner — leaving the lock held with nothing left to release it. Recovery is terraform force-unlock , which is deliberately manual and requires the lock ID Terraform prints in its error, precisely so nobody scripts around it without first confirming no other process is actually still running against that state.

Example

Error: Error acquiring the state lock

Lock Info:
  ID:        7f3a1c2e-...
  Path:      env:/prod/terraform.tfstate
  Operation: OpUpdateApply
  Who:       ci-runner-42
  Created:   2026-09-08 03:14:02 UTC

terraform force-unlock 7f3a1c2e-...

Follow-ups

  • What's the actual risk of force-unlocking too eagerly? — If the original process is in fact still running and mid-write, force-unlocking and starting a second apply can genuinely corrupt state — always confirm the run is dead first (check the CI job status, not just the elapsed time).
  • Does every backend support locking? — No — a local backend locks with a filesystem lock (useless across machines), and some remote backends historically required extra configuration (S3 + DynamoDB) before native S3 locking arrived; always confirm the specific backend's locking story.
  • How does HCP Terraform/Terraform Cloud handle this? — Runs are serialized per workspace by the platform itself, so the equivalent of a stuck lock shows up as a run stuck "applying" that an admin has to explicitly cancel or discard.

Wrong answer: “Just force-unlock it whenever you get a lock error so you can keep working.” That's the exact reflex that turns a stuck lock into actual state corruption when the other process wasn't really dead.

What's new in the Terraform 1.16/1.17 CLI workflow, and what's still experimental versus stable as of September 2026? senior

Answer. Terraform 1.16 (latest stable 1.16.1, released 2026-09-02) is the current GA line; the 1.17 alpha series is trialling a `-minimal-refresh` planning mode intended to reduce the cost and blast radius of the automatic refresh step for very large states by refreshing only what a plan's diff actually needs, plus continued work on deferred actions for resources whose `count`/`for_each` can't be fully known until apply time (useful when the collection driving a resource depends on a value only resolved during apply, like an ephemeral resource's output). There's also an experimental `terraform query` command for discovering unmanaged resources against a provider (with a `-policies` flag to filter by policy) — aimed at bringing existing, un-imported infrastructure under management faster than hand-writing `import` blocks one at a time. None of the 1.17-line features should be presented as stable or relied on in production configuration yet — they require explicit experiment opt-in and are exactly the kind of thing worth naming to show currency, while being clear about what "experimental" means operationally: no compatibility promise, can change or disappear before GA.

Example

terraform query -policies=my-org/discovery azurerm_resource_group.discovered

Follow-ups

  • Why does a "minimal refresh" mode matter at scale? — For a state with thousands of resources, refreshing everything on every plan is a real latency and API-rate-limit cost; narrowing refresh to what the diff needs is a direct operational win for large estates.
  • How does this relate to `terraform test`'s cleanup handling? — 1.17 also work-in-progress includes a test-cleanup command and a `skip_cleanup` attribute for `terraform test`, aimed at letting you inspect infrastructure left behind by a failed test run before it's torn down.
  • Should you enable experiments in a shared team config? — Only behind an explicit, well-communicated opt-in and never in a production root module — experiments are for evaluating direction, not for building on.

Wrong answer: “Terraform 1.17 is out and adds deferred actions for dynamic `count`.” As of 2026-09-08, 1.17 is still in alpha and that capability is experimental, not shipped in a GA release — stating it as generally available misrepresents exactly the kind of version precision this topic rewards.

How do you safely recover from an apply that failed partway through? senior

Answer. First, don't panic-retry blindly: read the error to understand which resources actually completed (they're now in state, correctly) versus which failed (state may or may not reflect them depending on whether the provider's create call returned an ID before failing). Run a plain plan next — Terraform will show you, based on current state versus config, exactly what it still thinks needs to happen, which is usually a much smaller diff than the original. If the plan looks sane, apply it. If a specific resource is stuck in a bad state the provider can't reconcile (a partially-created resource that exists but is missing required sub-resources), it's often faster to -target just that resource for a retry, or in the worst case manually delete the broken resource out-of-band and `terraform apply -replace` it. The one thing to actively avoid is `terraform state rm` as a first reflex — it decouples Terraform's bookkeeping from a resource that likely still exists, and the very next plan proposing to create a duplicate is a worse mess than the one you started with.

Example

terraform apply
# ...fails partway: "Error: creating Subnet: context deadline exceeded"
terraform plan            # see the real remaining diff
terraform apply -target="azurerm_subnet.app"   # retry just the stuck piece
terraform plan            # confirm empty diff before moving on

Follow-ups

  • What if the same resource fails the same way every retry? — Stop retrying and read the actual provider error — a hung apply retried identically five times is usually a real quota, permission, or naming-conflict problem, not a transient one.
  • Does a saved plan file help here? — Yes for the original apply (see it was reviewed correctly), but the recovery step itself needs a fresh plan since the world changed mid-failure — never re-apply a stale saved plan after a partial failure.
  • How do you prevent this class of failure generally? — Timeouts tuned per resource (`timeouts` block) for genuinely slow resources, and smaller, more frequent applies so a failure's blast radius and recovery diff are both small.

Wrong answer: “Run `terraform state rm` on the failed resource and re-apply so it creates cleanly.” That's the move that turns one failed apply into an orphaned real resource plus a duplicate — reconciling state with reality, not detaching from it, is almost always the right first instinct.

What's the difference between terraform console, terraform show, and terraform output, and when would you reach for each? screener

Answer. terraform console is an interactive REPL for evaluating expressions against the current state and config — useful for checking what a `for` expression or a function call actually produces before committing it to a resource block. terraform show renders state (or a saved plan file, human-readable or as `-json`) — the tool for inspecting exactly what's tracked or exactly what a plan will do, including piping the JSON into `jq` for automated checks. terraform output reads just the declared `output` blocks' values from state, the mechanism for passing values between root modules (one root's output feeding another's `data "terraform_remote_state"` or a variable) or for scripting against a specific known value without parsing the whole state.

Example

terraform console <<< 'cidrsubnet("10.0.0.0/16", 8, 3)'
terraform show -json tf.plan | jq '.resource_changes[].change.actions'
terraform output -json vnet_id

Follow-ups

  • Can console modify state? — No — it's strictly read/evaluate, which is exactly why it's safe to poke at in production against real state.
  • Why prefer `-json` output in automation? — Human-readable output format is not a stable contract across versions; `-json` schemas are documented and versioned, which is what CI tooling should parse.
  • Are output values ever sensitive? — Yes, and marking an output `sensitive = true` redacts it from CLI output and plan diffs, though it's still stored in plaintext in state unless state encryption is configured (unit 04).

Wrong answer: “`terraform show` and `terraform output` do the same thing, just different formatting.” `show` exposes the entire resource-level state or plan; `output` exposes only what you deliberately declared as an output — very different surface areas and very different sensitivity implications.

When do you use count versus for_each to create multiple instances of a resource, and why does the choice matter for future changes? screener

Answer. Both create multiple instances of a resource block, but they key those instances differently, and the key is what determines how safely you can change the collection later. count keys instances by their numeric index (0, 1, 2…), so removing an early element shifts every later index down by one — Terraform sees that as destroying and recreating every shifted instance, not just the one you removed. for_each keys instances by a map key or set element's own value, so removing one element only affects that one instance; everything else is untouched because its key never changed. The rule of thumb: use count only for genuinely homogeneous, ordinal collections (N identical replicas where index truly doesn't matter, or a simple 0/1 toggle for optional resources); use for_each whenever instances are meaningfully distinct or the collection can shrink/grow/reorder over its lifetime.

Example

# fragile: removing "west" from the middle recreates "central" and "east"
variable "regions" { default = ["west", "central", "east"] }
resource "azurerm_resource_group" "rg" {
  count    = length(var.regions)
  name     = "rg-${var.regions[count.index]}"
  location = var.regions[count.index]
}

# stable: removing "west" only destroys the "west" instance
resource "azurerm_resource_group" "rg" {
  for_each = toset(var.regions)
  name     = "rg-${each.value}"
  location = each.value
}

Follow-ups

  • What's the trade-off of for_each over a set versus a map? — A set's elements must be unique strings and become the key directly; a map lets you carry per-instance attributes (region + SKU + tier) alongside the key, which is usually the more maintainable shape once instances aren't identical.
  • What happens if a `for_each` key's value itself needs to change? — Terraform treats it as destroy-old-key-create-new-key, same as any rename — this is exactly the case a `moved` block can smooth over if the underlying resource is actually the same one logically.
  • Can you switch an existing resource from `count` to `for_each` without downtime? — Not for free — the resource addresses change shape (`rg[0]` to `rg["west"]`), so without a `moved` block or `terraform state mv`, Terraform will plan a destroy-and-recreate of every instance even though nothing about the real resources changed.

Wrong answer: “`count` is for a fixed number of things and `for_each` is for a variable number.” The real distinguishing factor is index-based versus value-based identity, not variability of length — a fixed-length list of three meaningfully-different regions is exactly where `count`'s index keying causes real damage.

Explain optional object type attributes with defaults — what problem did they solve, and how do you declare one? mid

Answer. Before Terraform 1.3, an object() type constraint required every attribute to be present in every value passed to it — if a module accepted a complex object variable and callers wanted to omit an attribute to fall back to a sensible default, the module author had to accept a looser type (or `any`) and write manual null-coalescing logic for every optional field. optional(type, default) inside an object() constraint lets the type system itself say “this attribute may be omitted, and if it is, use this default” — validation and defaulting collapse into the variable declaration instead of being reimplemented in the module body.

Example

variable "subnet_config" {
  type = object({
    name             = string
    address_prefixes = list(string)
    delegation       = optional(string, null)
    nsg_id           = optional(string)
  })
}

Callers can now pass just { name = "app", address_prefixes = ["10.0.1.0/24"] } and get delegation = null, nsg_id = null for free, with the type checker enforcing everything else exactly as before.

Follow-ups

  • What if you omit the default in `optional(type)`? — It defaults to `null`, so `optional(string)` and `optional(string, null)` are equivalent — spelling out the default is purely for readability or when a non-null default is genuinely wanted.
  • Does this work with nested objects? — Yes, and it's where it earns its keep most — a deeply nested config object where only leaf attributes three levels down are optional used to be nearly unworkable before 1.3.
  • How does this interact with `for_each` over a map of these objects? — Cleanly — each map value is independently defaulted, which is the common real pattern: a map of subnet configs, most fields shared, a few varying per entry.

Wrong answer: “Just use `type = any` and it'll accept whatever you pass, optional fields included.” It will, but you lose all validation and the module's contract becomes undocumented and untyped — `any` is a downgrade of exactly the guarantee `optional()` was introduced to preserve.

What are moved blocks, when do you need one, and what's the alternative you're replacing? senior

Answer. A moved block (1.1+) tells Terraform that a resource address changed — renamed a label, moved into or out of a module, switched from `count` to `for_each` — without the underlying real resource changing at all, so the next plan should treat it as a rename in state, not a destroy-and-recreate. Before moved blocks, the only way to express this was the imperative `terraform state mv` command, run by hand (or scripted) against the state file directly — it works, but it's an out-of-band operation nobody reviews in the PR that caused the rename, and every consumer of that module has to remember to run it themselves at the right moment. A `moved` block lives in the configuration itself, travels with the code, and Terraform applies it automatically for anyone who pulls the change — turning a manual, easy-to-forget migration step into a declarative, self-documenting one.

Example

moved {
  from = azurerm_resource_group.rg
  to   = azurerm_resource_group.app_rg
}

Follow-ups

  • Do you ever remove a `moved` block? — Once every consumer has applied it, yes, but they're cheap to leave indefinitely — HashiCorp's own recommendation is to keep them since a late-adopting consumer applying an old version of the module still benefits.
  • Can `moved` cross module boundaries? — Yes — from a resource at root into a resource inside a child module (or vice versa), which is the single most common real use during a "let's modularize this" refactor.
  • What happens if you forget the `moved` block? — The plan shows a destroy-and-recreate for what is, semantically, the exact same resource — the visible symptom that should make you reach for `moved` rather than approve the plan.

Wrong answer: “`moved` blocks and `terraform state mv` do the same thing, so it doesn't matter which you use.” They reach the same end state, but only `moved` blocks are declarative, code-reviewed, and automatically applied for every consumer — `state mv` is a manual side-channel operation with none of those properties.

What are removed blocks, and how do they differ from just deleting a resource block from your config? senior

Answer. Deleting a resource block outright and re-running apply tells Terraform to destroy that resource — the default, and usually correct, behavior. A removed block (1.7+) says the opposite: stop managing this resource, but do not destroy it — remove it from state only, leaving the real infrastructure untouched. This matters whenever ownership is transferring rather than ending: a resource moving to a different Terraform root/state, being handed off to a different team's module, or being deliberately taken out of IaC management (e.g. onboarding it into a different tool). Without `removed`, the only way to achieve "stop tracking, don't destroy" was `terraform state rm`, run out-of-band exactly like the pre-`moved` rename problem — `removed` blocks bring that same declarative, in-PR treatment to detachment.

Example

removed {
  from = azurerm_storage_account.legacy

  lifecycle {
    destroy = false
  }
}

Follow-ups

  • What if you want the resource actually destroyed and just don't want the block cluttering config anymore? — Set `destroy = true` (or omit the `removed` block entirely and just delete the resource, which is the default destroy behavior) — `removed` with `destroy = false` is specifically for the detach-don't-destroy case.
  • Can `removed` target something inside a module you're also deleting? — Yes, and it's the common real pairing: removing a whole module call while adding `removed` blocks for each resource it contained, so the transition away from managing them is explicit rather than an accidental mass-destroy.
  • Does `removed` require the resource to still exist in the real world? — No — it only affects state bookkeeping; whether the resource is later destroyed by someone else, migrated, or left alone is entirely outside Terraform's concern once removed.

Wrong answer: “Just delete the resource block — Terraform will figure out you didn't mean to destroy it.” It won't; deletion means destroy by default, full stop — `removed` with `destroy = false` is the only declarative way to say "stop tracking, don't touch."

What are precondition and postcondition blocks, and how do they differ from a plain validation block on a variable? senior

Answer. A variable's own `validation` block can only check the variable's raw input value, at the moment it's passed in, before anything is resolved against real infrastructure. `precondition` (inside a resource, data source, or output's `lifecycle`/`check` context, 1.2+) asserts something must be true before an operation proceeds — commonly checking a relationship between multiple values, or a data source's result, that a single variable's own validation can't see. `postcondition` asserts something must be true after a resource is created or a data source is read — catching cases where the inputs looked fine but the provider produced a result that violates an assumption your downstream configuration depends on. Together they let you encode “the reason this configuration is safe” as executable assertions that fail the plan/apply loudly, rather than silently producing a resource that technically applied but doesn't satisfy an implicit invariant.

Example

data "azurerm_key_vault" "shared" {
  name                = var.key_vault_name
  resource_group_name = var.key_vault_rg

  lifecycle {
    postcondition {
      condition     = self.sku_name == "premium"
      error_message = "Shared Key Vault must be Premium SKU for HSM-backed keys."
    }
  }
}

Follow-ups

  • Where do these live syntactically? — Inside a `lifecycle` block on a resource/data source (checking `self`), or inside a `check` block for standalone assertions not tied to one resource's lifecycle.
  • What's a `check` block, and how does it relate? — A top-level block (1.5+) for assertions that don't map to any specific resource — e.g. "the app's health endpoint returns 200" via a `data` source — that run on every plan and report failures without blocking the apply, useful for continuous validation rather than a hard gate.
  • Do these run during `plan` or only `apply`? — Conditions referencing only known values can evaluate at plan time; ones referencing values only known after creation (most `postcondition`s) necessarily evaluate during apply.

Wrong answer: “They're just a fancier syntax for variable validation.” Variable validation only ever sees the raw input before any provider interaction; `precondition`/`postcondition` can reference resolved data source results and resource attributes that don't exist until much later in the lifecycle — a fundamentally different, later evaluation point.

What's a dynamic block, and what's the risk of overusing them? mid

Answer. A dynamic block generates a variable number of nested configuration blocks (not top-level resources — nested blocks like a security rule inside an NSG, or a lifecycle rule inside a storage account) from a list or map, when the number of nested blocks isn't fixed at write time. It exists because HCL nested blocks aren't inherently iterable the way arguments are — you can't naturally write a `for_each`-style loop over sub-blocks without this construct. The risk of overuse is readability: a resource whose actual shape is buried behind two or three levels of `dynamic` and `for_each` becomes hard for a reviewer to mentally render into what will actually get created, especially compared to just writing out three or four concrete blocks explicitly when the count is genuinely small and static.

Example

resource "azurerm_network_security_group" "app" {
  name = "nsg-app"

  dynamic "security_rule" {
    for_each = var.rules
    content {
      name                   = security_rule.value.name
      priority               = security_rule.value.priority
      direction              = security_rule.value.direction
      access                 = security_rule.value.access
      protocol               = security_rule.value.protocol
      destination_port_range = security_rule.value.port
    }
  }
}

Follow-ups

  • When would you avoid a dynamic block even with a variable number of items? — When the number is small (2-4) and known at the call site rather than driven by a general-purpose list variable — explicit blocks are often more readable and just as maintainable at that scale.
  • Can `dynamic` blocks be nested inside each other? — Yes, but two levels deep is usually the practical readability ceiling before extracting the inner structure into its own module argument is the better call.
  • What happens with an empty list passed to `for_each` in a dynamic block? — Zero nested blocks are generated — a clean way to make an entire nested configuration section conditional without a separate boolean flag.

Wrong answer: “Use `dynamic` blocks wherever possible since they're more DRY.” DRY-ness that costs a reviewer the ability to see what a resource will actually contain is a net loss — the right amount of dynamic-block use tracks genuine variability, not a stylistic preference for loops.

What are provider-defined functions, and how do they differ from Terraform's built-in functions? senior

Answer. Terraform's built-in functions (`cidrsubnet`, `jsonencode`, `try`, etc.) are baked into the Terraform binary itself and are the same regardless of which providers you use. Provider-defined functions (1.8+) let a provider ship its own functions, invoked with a `provider::` namespace prefix, giving provider authors a way to expose logic that genuinely needs to live close to their domain — validating or transforming a value in a way that mirrors exactly what the provider's API expects, without every user reimplementing that logic themselves or a module ecosystem inventing five slightly different community versions of the same helper. They're pure functions like any other — no side effects, no API calls at plan time beyond what the function itself computes — the distinction is purely about where the logic is authored and maintained.

Example

output "normalized_region" {
  value = provider::azurerm::normalise_location(var.region_input)
}

Follow-ups

  • Why not just add it as a built-in function? — Built-ins have to be maintained forever in Terraform core regardless of relevance; a provider-defined function's lifecycle matches the provider's own release cadence and domain, which scales far better across hundreds of providers.
  • Do you need special configuration to use them? — Just the provider itself declared in `required_providers` at a version that ships the function — no separate opt-in, since functions ship as part of the normal provider plugin.
  • Can modules expose their own custom functions the same way? — No — provider-defined functions are a provider-plugin feature; a module can only compose built-in and provider functions, it can't define new ones of its own (that's a frequently requested feature, still not shipped as of September 2026).

Wrong answer: “Provider-defined functions let you write custom Terraform functions in HCL inside your own module.” That capability doesn't exist — these functions are authored in the provider's own plugin code (Go, typically) and shipped as part of the provider binary, not something you define in your `.tf` files.

Explain the difference between for expressions and for_each meta-arguments — they look similar but solve different problems. mid

Answer. A `for` expression is a general-purpose value transformation — it takes a collection and produces a new list, map, or set by applying an expression to each element, exactly like a list/dict comprehension in Python. It's used anywhere you need a derived value: transforming a variable before passing it somewhere, building a lookup map, filtering a list. `for_each` is a meta-argument specifically on resources, modules, and data sources that tells Terraform to create multiple instances of that block, one per element of the given map or set — it's about resource cardinality, not general value transformation, and it can only appear in that specific position.

Example

# for expression: transforms a value
locals {
  subnet_names = [for s in var.subnets : upper(s.name)]
  subnet_by_id = { for s in var.subnets : s.id => s.name }
}

# for_each: drives resource cardinality
resource "azurerm_subnet" "app" {
  for_each = { for s in var.subnets : s.name => s }
  name     = each.value.name
  # ...
}

The two compose constantly — a `for` expression is very often exactly what builds the map you then hand to `for_each`.

Follow-ups

  • Can a `for` expression filter elements out? — Yes, with an `if` clause: `[for s in var.subnets : s.name if s.enabled]` — the filtered result is a genuinely shorter collection, not nulls in place of skipped elements.
  • Does `for_each` accept a list directly? — Only after converting it to a set (`toset(list)`) or transforming it into a map — a bare list isn't accepted because `for_each` needs each element to have a stable, comparable key, which a plain list index doesn't guarantee the way `count`'s index does either (see the earlier `count` vs `for_each` question).
  • What's a splat expression and how does it relate? — `var.subnets[*].name` is shorthand for the common case of a `for` expression that just extracts one attribute from every element — same underlying idea, terser syntax for the simple case.

Wrong answer: “`for` and `for_each` are just two syntaxes for the same loop.” One produces a value; the other drives how many copies of infrastructure get created — conflating them is the kind of mistake that shows up as "why can't I use a `for` expression to create multiple resources" confusion in real code review.

What does terraform_data do, and what problem did it solve that null_resource didn't? mid

Answer. Both are placeholder resources with no real infrastructure backing them, used to hang provisioners off of, or to force a dependency/trigger relationship that doesn't naturally attach to a real resource. null_resource (from the separate `null` provider) predates and still works, but as an external provider it can't participate in certain core-language features the same way a built-in construct can. `terraform_data` (1.4+) is built into Terraform core itself, requires no separate provider declaration or version pinning, and — the concrete improvement — supports the `input`/`output` attributes cleanly for passing a value through unchanged while still tracking it for replacement triggers, which is a more ergonomic version of the trigger patterns people hand-rolled with `null_resource`'s `triggers` map.

Example

resource "terraform_data" "rerun_on_script_change" {
  input = filesha256("${path.module}/scripts/bootstrap.sh")

  provisioner "local-exec" {
    command = "echo triggered"
  }
}

Follow-ups

  • Should existing `null_resource` usage be migrated? — Not urgently — `null_resource` isn't deprecated, but new code should default to `terraform_data` since it removes an unnecessary provider dependency for something this fundamental.
  • Does `terraform_data` remove the need for provisioners generally? — No — it's a home for triggers and provisioners, not a replacement for the broader "avoid provisioners where possible" guidance from unit 01.
  • Can `terraform_data` be used just to force a dependency between two otherwise-unrelated resources? — Yes — referencing its `output` from a resource that has no natural attribute-level dependency on another is a clean way to make an implicit ordering requirement explicit.

Wrong answer: “`terraform_data` replaced `null_resource`, which is now deprecated.” `null_resource` still works and isn't formally deprecated — the accurate statement is that `terraform_data` is the newer, in-core, generally preferred option for new code.

What's the difference between sensitive = true on a variable/output and actual secret management — what does marking something sensitive not protect against? senior

Answer. `sensitive = true` is a display-redaction flag: it stops the value from being printed in CLI plan/apply output and in the human-readable plan rendering, which is genuinely useful for keeping secrets out of terminal scrollback and CI logs. What it does not do is encrypt or remove the value from the state file — a sensitive-marked value is stored in plaintext in state exactly like any other attribute (unless state encryption, unit 04, is separately configured), and anyone with read access to the state file (or the backend storing it) can retrieve it trivially. It also doesn't stop the value from being sensitive-but-visible if it flows into another value that isn't itself marked sensitive — Terraform propagates the flag through direct references but a computed value combining sensitive and non-sensitive inputs needs its own `sensitive = true` or it can leak.

Example

variable "db_password" {
  type      = string
  sensitive = true
}
resource "azurerm_postgresql_flexible_server" "db" {
  administrator_password = var.db_password  # never printed in plan output
}

But: terraform state show azurerm_postgresql_flexible_server.db or a raw cat terraform.tfstate against an unencrypted local/remote state shows the plaintext password without any redaction at all.

Follow-ups

  • What actually protects secrets in state then? — State encryption (1.10+, unit 04), tight access control on the state backend itself, and — best of all — never putting a long-lived secret into Terraform-managed state in the first place (generate it in Key Vault/Secrets Manager and reference it, don't create-and-store it via Terraform).
  • Do ephemeral resources help here? — Yes directly — an ephemeral resource's value is never persisted to state at all (unit covered under ephemeral resources, see units 04/10), which is a stronger guarantee than `sensitive` for genuinely transient credentials.
  • Does marking a variable sensitive affect provider API calls? — No — the provider receives the real value regardless; sensitivity is purely a Terraform-CLI-and-state display concern, not a transport-level protection.

Wrong answer: “Marking a value `sensitive` keeps it out of the state file, so it's safe there.” It is stored in state in plaintext by default — this is one of the most consequential misconceptions in the whole topic and a favorite senior-level trap question for exactly that reason.

Explain try() and coalesce() — when is each the right tool, and what's the failure mode of overusing try()? mid

Answer. try() evaluates a sequence of expressions and returns the first one that doesn't produce an error, swallowing errors from earlier ones — it's for handling expressions that might fail to evaluate at all (a lookup into a map that might not have the key, an attribute reference on an object that might be null). coalesce() returns the first argument that is not null (and not empty string) among a fixed list — it's for picking the first meaningful value among several possibly-null candidates, and it still errors normally if any argument itself throws an evaluation error. The overuse failure mode with `try()` specifically is masking real bugs: wrapping a broad expression in `try(..., null)` to avoid a crash can silently swallow a typo or a genuinely broken reference, turning a loud plan-time error into a quiet null propagating deep into your configuration.

Example

locals {
  # try: might not evaluate at all if the key is absent
  tier = try(var.config.tier, "standard")

  # coalesce: definitely evaluates, picks first non-null
  region = coalesce(var.explicit_region, var.default_region, "westeurope")
}

Follow-ups

  • What does `try()` do if every argument errors? — It re-raises the last error rather than silently returning null — it's not a universal error-suppressor, just a "first success wins" chain.
  • Is there a more precise alternative to a broad `try()`? — Often yes — `lookup(map, key, default)` for the specific "map might not have this key" case is more explicit about exactly what failure it's tolerating than a generic `try()`.
  • Does `coalesce()` treat an empty string as "present"? — No — `coalesce()` specifically skips both `null` and empty string values, which is a deliberate and sometimes surprising design choice worth knowing if a variable's "unset" sentinel is `""`.

Wrong answer: “Wrap anything that might be null in `try()` to be safe.” Blanket `try()` use turns configuration bugs into silent nulls instead of loud plan-time failures — precise, narrow use (a specific optional lookup) is the actual skill being tested, not defensive wrapping everywhere.

State is where Terraform interviews get serious: backends, locking, splitting state, import, and the newer state-encryption story. Mid-level candidates need the mechanics; senior/principal candidates are expected to reason about state topology as an architectural decision — how many state files, who owns each, how they compose — because getting this wrong is the single most common source of real operational pain in large Terraform estates.

What is a Terraform backend, and why should you never use the default local backend for anything beyond a personal experiment? screener

Answer. A backend determines where the state file is stored and how operations against it are locked and, for some backends, executed. The default `local` backend writes `terraform.tfstate` to disk next to your config — fine for a five-minute experiment, unsafe for anything real because it has no locking that works across machines, no built-in encryption at rest, no versioning/recovery if the file is corrupted or accidentally deleted, and by definition lives only on one person's machine or one CI runner's ephemeral disk, so nobody else's Terraform run can see the true current state. A remote backend (Azure Blob Storage, S3, HCP Terraform's own state storage, etc.) solves all of that: shared visibility, native locking, versioning/soft-delete for recovery, and encryption at rest as a platform feature rather than something you'd have to build yourself.

Example

terraform {
  backend "azurerm" {
    resource_group_name  = "rg-tfstate"
    storage_account_name = "sttfstateprod"
    container_name        = "tfstate"
    key                    = "prod/network.tfstate"
  }
}

Follow-ups

  • What happens if you change backend configuration on an existing project? — `terraform init` detects the change and offers to migrate existing state to the new backend — always review that migration carefully in a shared environment, ideally with a backup of the old state first.
  • Does the backend choice affect where `apply` actually executes? — For most backends, no — they only store state; execution still happens wherever you run the CLI. HCP Terraform's remote execution mode is the exception: it can run the plan/apply itself on its own infrastructure.
  • Can you use `local` backend in CI as long as you upload the state file afterward? — Technically, but you've just rebuilt a worse, unlocked, unversioned remote backend by hand — there's no good reason to when native remote backends exist.

Wrong answer: “Local backend is fine as long as only one person ever runs `apply`.” Even a solo user loses recoverability (no versioning if the laptop's disk fails or the file is fat-fingered) and loses the audit trail a remote backend with versioning gives for free — "only one person" doesn't remove the risk, it just narrows who's exposed to it.

How do you decide the boundaries for splitting one large state file into several? senior

Answer. Split along three axes, in order of importance: lifecycle (things that change together and are deployed together stay together; things with independent release cadences — a shared VNet versus an app team's compute — split apart), blast radius/ownership (a mistake in one state should not be able to lock out or endanger resources owned by a different team), and change frequency (a rarely-touched foundational layer — networking, IAM — benefits from being isolated from a frequently-redeployed application layer, both so frequent applies don't repeatedly refresh and re-diff stable resources, and so a bug in the fast-moving layer can't touch the slow-moving one). The failure mode in both directions is real: one state for an entire org couples every team's blast radius together (unit 01); splitting too finely multiplies the number of `terraform_remote_state` wiring points and the operational burden of coordinating a change that has to land across a dozen tiny states in the right order.

Example

network/        (state: platform team, changes rarely)   -> VNet, subnets, DNS zones
platform/       (state: platform team, changes rarely)    -> AKS cluster, shared Key Vault
app-team-a/     (state: team A, changes often)            -> app A's compute, its own DB
app-team-b/     (state: team B, changes often)             -> app B's compute, its own DB

Follow-ups

  • How do split states reference each other's resources? — `terraform_remote_state` data sources (read-only, tight coupling to the other state's exact output names) or, increasingly, a purpose-built platform API/service catalog that decouples the consuming team from the producing team's internal Terraform structure entirely.
  • Is one state per environment (dev/stage/prod) enough splitting on its own? — It's necessary but not sufficient — it protects environments from each other but does nothing for blast radius or lock contention within a single environment shared by multiple teams.
  • What's a concrete signal you've split wrong? — Frequent `-target` use (unit 02) to work around lock contention or graph-blast-radius within one state is the clearest tell that its boundary doesn't match how the team actually wants to deploy.

Wrong answer: “Split state by resource type — one state for all networking, one for all compute, one for all databases.” That groups by technology, not by lifecycle or ownership, and typically produces exactly the coupling problem splitting was meant to avoid: an app team's routine deploy now depends on locking the one global "compute" state that every other app team is also fighting over.

Walk through recovering from a corrupted or lost state file for a small set of resources, when you have no recent backup. principal

Answer. First, stop anyone from running `apply` against the affected config — a plan against empty/corrupted state proposes creating everything from scratch, and an accidental apply at this point is how you get real duplicate resources. Then rebuild the mapping between config and reality using `terraform import` (or, faster for many resources at once, `import` blocks with `-generate-config-out` to both import and scaffold the matching HCL, 1.5+) for each resource, working from the cloud provider's own inventory (Azure Resource Graph query, `az resource list`, whatever surfaces everything in the affected scope) cross-referenced against what the config expects to exist. After every resource is re-imported, run a full `plan` and scrutinize it hard — a clean, empty plan means the imported state now genuinely matches config; any non-empty diff means either the import missed an attribute or the live resource has actually drifted from what config declares, and that has to be resolved deliberately, not by blindly applying.

Example

import {
  to = azurerm_storage_account.data
  id = "/subscriptions/.../storageAccounts/stdataprodweu001"
}
terraform plan -generate-config-out=generated.tf
# review generated.tf, reconcile with existing module structure, then
terraform apply   # applies the import(s); real infra untouched, state rebuilt
terraform plan     # must come back clean before trusting the recovery

Follow-ups

  • What if you can't identify every resource that was in the lost state? — Query the cloud provider by the tags/naming convention your IaC enforces — this is exactly why consistent tagging matters operationally, not just for cost reporting.
  • Does this fully restore sensitive/computed attributes state used to hold? — No — anything the provider's read API doesn't return (a password Terraform generated and never re-reads) is genuinely gone; recovery for those means rotating them, not recovering the old value.
  • How do you prevent a repeat? — Enable state file versioning/soft-delete at the backend (blob versioning on Azure Storage, S3 versioning) so "lost state" becomes "restore the previous blob version," a five-minute fix instead of a multi-hour reimport exercise.

Wrong answer: “Just delete everything and re-apply from a clean state — Terraform will recreate it identically.” Recreating stateful resources (databases, storage accounts with data in them, anything with a globally unique name already claimed) is a data-loss incident, not a recovery — import, never recreate, is the safe default whenever the real resources still exist.

Terraform 1.10 introduced state encryption. What problem does it solve that a backend's own at-rest encryption doesn't? senior

Answer. Backend-level at-rest encryption (Azure Storage Service Encryption, S3's SSE) protects the state file while it sits on disk in the backend's storage, but the state is decrypted the moment Terraform reads it — into a local plan file, into CLI output if something goes wrong, into logs if a CI system captures stdout carelessly. State encryption (1.10+, `terraform { encryption { ... } }` block with a key provider and a method) encrypts the state content itself, independent of the backend, so even a plaintext-capable backend, a local state file accidentally committed to git, or a plan file passed between CI stages stays encrypted at the Terraform-level, not just at the storage layer. It's a defense-in-depth control specifically for the fact that state routinely contains secrets (see the `sensitive` misconception two units back) and multiple copies of it exist in more places than just the backend — local caches, plan files, CI artifact storage.

Example

terraform {
  encryption {
    key_provider "pbkdf2" "default" {
      passphrase = var.state_encryption_passphrase
    }
    method "aes_gcm" "default" {
      keys = key_provider.pbkdf2.default
    }
    state {
      method = method.aes_gcm.default
    }
    plan {
      method = method.aes_gcm.default
    }
  }
}

Follow-ups

  • Can you encrypt plan files separately from state? — Yes — the `plan { }` block configures encryption for saved plan files independently, which matters because a plan file passed between CI stages is exactly the kind of copy backend encryption never touched.
  • What happens if you lose the encryption key? — The state becomes unrecoverable — this raises the stakes on key management to the same level as the state's own durability, and needs its own backup/rotation story.
  • Is this the same thing as a KMS-backed backend? — No — a KMS-integrated backend still only protects state at rest in that backend; Terraform-level encryption travels with the state/plan content itself regardless of where it's copied.

Wrong answer: “If your backend already encrypts at rest, state encryption is redundant.” Backend at-rest encryption and Terraform's own state encryption protect different exposure windows — plaintext-in-transit-between-stages and plaintext-in-a-mis-stored-copy are exactly what backend-only encryption misses.

What does terraform state mv actually do, and when is it the right tool versus a moved block? mid

Answer. terraform state mv renames a resource's address in state directly, immediately, with no plan to review first — the same category of ungated operation as the old `taint` command. It's still the right tool for a genuinely one-off, interactive fix — untangling a state mistake right now, in a context where writing a `moved` block into the permanent configuration doesn't make sense because there's no ongoing config change to attach it to. A `moved` block is the right tool whenever the rename is a consequence of an actual configuration change (a refactor, a module boundary shift) that other consumers of the same module will also need to apply — it travels with the code and applies automatically for everyone, whereas `state mv` has to be re-run by hand against every affected state.

Example

# one-off fix, no corresponding config change to attach a moved block to
terraform state mv 'azurerm_subnet.app["10.0.1.0/24"]' 'azurerm_subnet.app["web"]'

Follow-ups

  • Can `state mv` move a resource between two different state files? — Yes, with `-state-out`, which is exactly the low-level operation behind manually splitting one large state into several (unit 04's splitting question) before better tooling automates it.
  • Does `state mv` require a real infrastructure change? — No — like `moved`, it's purely a bookkeeping operation; the real resource is completely untouched.
  • What's the risk of `state mv` in CI? — It's imperative and unreviewable in the normal PR flow, so scripting it into automation without a human confirming the exact before/after addresses is a good way to silently detach or duplicate the wrong resource.

Wrong answer: “`state mv` is deprecated in favor of `moved` blocks.” It isn't deprecated — the two serve different situations (ad hoc fix versus a repeatable, code-reviewed migration), and a senior engineer is expected to know when each applies rather than treating one as strictly obsolete.

What's the difference between terraform state list/show and reading the raw JSON state file directly — when would you ever need the latter? mid

Answer. `state list` and `state show` are the supported, stable interface to state — they work regardless of the state file's internal schema version and are what any script or human should use day to day. The raw JSON has an internal format that is explicitly not a stable public contract (it's versioned and can change between Terraform releases), so parsing it directly is fragile and unsupported. The legitimate reason to look at raw state JSON is deep forensic debugging — understanding exactly what's stored for a resource whose behavior doesn't match what `state show`'s formatted output suggests, or diagnosing a corruption issue where the state file itself might be malformed and the normal read path is failing.

Example

terraform state list
terraform state show azurerm_storage_account.data
terraform show -json terraform.tfstate | jq '.values.root_module.resources[]'

The `show -json` route is the supported way to get machine-readable state — still going through Terraform's own serializer, not hand-parsing the raw file.

Follow-ups

  • Is it ever safe to hand-edit the raw state file? — Essentially never in production — `terraform state` subcommands (`mv`, `rm`, `push`) exist precisely so you never need to; hand-editing risks producing a file that doesn't even parse.
  • What's `terraform state pull` / `push` for? — Pulling the current remote state to local for inspection, and pushing a modified copy back — an escape hatch for exactly the forensic case above, used carefully and typically only after backing up the existing remote state first.
  • Does the state JSON schema version matter for tooling? — Yes — `show -json`'s top-level `format_version` and `terraform_version` fields tell you what schema you're parsing, which matters if you maintain tooling across multiple Terraform versions.

Wrong answer: “State is just JSON, so it's fine to write a script that edits it directly for routine tasks.” The schema isn't a stable contract and a slightly malformed hand-edit can corrupt state in a way `terraform state` subcommands are specifically designed to prevent — routine tasks should never touch the raw file.

Explain ephemeral resources and write-only arguments. What real problem do they solve, and why did it take until Terraform 1.10 to solve it? principal

Answer. Before 1.10, any value Terraform used — even briefly, even just to pass a credential through to another resource — got written to state as a normal attribute, because state is Terraform's only mechanism for remembering values between plan and apply and across runs. That's a real security problem for something like a short-lived database password or a Vault-issued token: it has no legitimate reason to be remembered at all, yet it ended up persisted in plaintext-by-default state regardless. Ephemeral resources (a new resource mode, alongside managed and data resources) produce values that are used during a single operation and explicitly never written to state — the resource itself isn't tracked, so there's nothing to persist. Write-only arguments are the matching half on the receiving side: an argument marked write-only accepts an ephemeral value, passes it to the provider, and is then itself excluded from state, so a managed resource can consume a genuinely transient secret without that secret ever landing in the state file at all. It took this long because it required rethinking a fairly deep assumption in Terraform's core resource model — that every managed resource's arguments are, by definition, persisted for later diffing — and the later 1.11+ line added a renewal lifecycle so an ephemeral value tied to a lease (like a Vault dynamic credential) can be automatically refreshed mid-operation before it expires.

Example

ephemeral "azurerm_key_vault_secret" "db_password" {
  name         = "db-password"
  key_vault_id = azurerm_key_vault.app.id
}

resource "azurerm_postgresql_flexible_server" "db" {
  administrator_password_wo         = ephemeral.azurerm_key_vault_secret.db_password.value
  administrator_password_wo_version = 1
}

Follow-ups

  • Why the extra `_wo_version` argument? — Because a write-only value is never stored, Terraform has no way to diff "did the secret change" the normal way — the version number is what you bump to signal a change and trigger a new write, replacing value-diffing with an explicit version bump.
  • Do all providers support write-only arguments yet? — No — providers have to explicitly implement support per-argument, so as of September 2026 coverage is still growing; check the specific resource's documentation before assuming an argument accepts a write-only value.
  • Does this replace external secret managers? — No — it complements them; the ephemeral resource is very often exactly a read from Key Vault/Vault/Secrets Manager, with the improvement being that the value transiting through Terraform never gets persisted on the way through.

Wrong answer: “Ephemeral resources mean Terraform doesn't create real infrastructure for them.” That's true of data sources too and isn't the distinguishing feature — the defining property of ephemeral resources is specifically that their value is never persisted to state, not that they're read-only or side-effect-free.

What's the risk of two different Terraform configurations (or two people) targeting the same backend state key, and how do you prevent it structurally rather than by convention alone? senior

Answer. If two separate root modules point their backend config at the same storage account/container/key (or the same DynamoDB-backed S3 key, etc.), they are, as far as Terraform is concerned, the exact same state — each believes it owns and fully describes that state's resources, and each will happily plan changes (including destroys) for anything the other one created that isn't in its own config. This is a naming-collision problem, not a locking problem — locking only protects against two concurrent operations on the same state; it does nothing to stop two different configs from sequentially fighting over the same state's contents, each "correcting" what the other put there. Preventing it structurally (rather than just naming carefully and hoping) means enforcing state key uniqueness through the platform: a wrapper/module that generates the backend key deterministically from a required, validated identifier (team + environment + purpose), or a policy check in CI that fails a plan if the resolved backend key isn't unique against a registry of known keys.

Example

# two unrelated projects, same key by accident:
# project-a/main.tf
backend "azurerm" { key = "app/prod.tfstate" }
# project-b/main.tf  (different team, didn't know)
backend "azurerm" { key = "app/prod.tfstate" }
# first apply from either "wins" for anything the other doesn't declare

Follow-ups

  • Does HCP Terraform's workspace model solve this automatically? — Largely yes — each workspace has one clearly named, centrally visible state, which makes an accidental collision far less likely than hand-typed backend blocks scattered across repos.
  • What's the blast radius if this happens undetected for a while? — Both configs can end up destroying resources the other created, because each one's plan treats "declared in my config, not in state" and "in state, not in my config" symmetrically — first apply from either side can delete real, in-use infrastructure.
  • How would you detect this had already happened, retroactively? — Compare each state's resource list against what its owning config actually declares — resources present in state but absent from any resource block in that root are the tell.

Wrong answer: “As long as they don't run `apply` at the exact same time, locking prevents this.” Locking only serializes concurrent operations against one state — it does nothing about two different configurations that take turns believing they own the same state's contents.

How does terraform_remote_state create coupling between teams, and what's the alternative when that coupling becomes a problem? senior

Answer. A `data "terraform_remote_state"` block reads another state's outputs directly — which means the consuming config is now coupled not just to the values it needs, but to the exact backend location and access permissions of the producing state, and (more subtly) to that producing team's internal decision about which outputs to expose and under what names. Renaming an output, splitting the producing state, or changing its backend location are all breaking changes for every downstream consumer, and the producing team often has no visibility into who's consuming what, since remote-state reads don't register anywhere centrally. At scale, the alternative most platforms converge on is decoupling through an explicit, versioned interface: a thin module or a small internal API/service catalog that returns the handful of values downstream teams actually need, backed by whatever the producing team's Terraform structure happens to be internally — so the producing team can refactor freely as long as that interface's contract holds.

Example

# tightly coupled: consumer knows the producer's exact backend + output names
data "terraform_remote_state" "network" {
  backend = "azurerm"
  config = {
    resource_group_name  = "rg-tfstate"
    storage_account_name = "sttfstateprod"
    container_name        = "tfstate"
    key                    = "platform/network.tfstate"
  }
}
resource "azurerm_subnet" "app" {
  virtual_network_name = data.terraform_remote_state.network.outputs.vnet_name
}

Follow-ups

  • Is `terraform_remote_state` wrong to use at all? — No — for a small number of teams with high trust and low churn it's a perfectly reasonable, low-ceremony choice; the decoupling investment pays off specifically as team count and change frequency grow.
  • What's a lighter-weight alternative than a full service catalog? — A published, versioned "network outputs" module that wraps the remote-state read and is the only sanctioned way to consume it — at least centralizing the coupling to one place instead of every consumer wiring it independently.
  • Does this problem exist in Bicep too? — Yes, in the equivalent shape — cross-referencing another deployment's outputs (via `reference()` to a deployment resource, or a stored parameter file) couples you to that deployment's exact scope and output names just the same.

Wrong answer: “Remote state coupling isn't a real problem since outputs are just values.” The coupling is structural, not about the values themselves — it's the producing team's freedom to refactor their own internals that gets constrained, which is exactly the kind of hidden cost that shows up months later as "we can't touch that state without breaking three other teams."

What is state bloat, what causes it at scale, and how do you address it? senior

Answer. As a state file accumulates resources over a project's lifetime, every `plan`/`apply` has to refresh, diff, and serialize the entire thing, so operation latency and API-rate-limit pressure both grow roughly with resource count — a state with a few thousand resources can turn a routine plan into a multi-minute operation and materially increase the chance of hitting provider throttling mid-refresh. The causes are usually a state that was never split along the lifecycle/ownership boundaries from earlier in this unit, plus genuinely large fan-out resources (`for_each` over hundreds of near-identical items that could arguably be a smaller number of provider-native "bulk" resources instead). The fix is the same splitting discipline discussed earlier, applied retroactively — moving cohesive chunks into their own state via `state mv -state-out` or `moved` blocks across module boundaries — plus, where the provider supports it, preferring a provider resource that natively represents a collection (fewer, larger API objects) over `for_each`-exploding into many small ones when the domain genuinely allows it.

Example

Before: one state, 3,000 resources, plan takes 6 minutes, frequent 429s from the provider API
After:  split by team/lifecycle into 40 states of ~75 resources each, plans take 10-20 seconds

Follow-ups

  • Does `-parallelism` help with large-state slowness? — It helps apply throughput (default 10 concurrent operations) but doesn't reduce refresh cost, which is largely sequential per-resource API calls against the provider.
  • Is there a size where a single state is simply too big regardless of splitting discipline? — In practice teams start feeling real pain well before state hits even a thousand resources if the resources are chatty to refresh — the right threshold is empirical (watch plan latency trend), not a fixed number.
  • Does HCP Terraform's remote execution change this calculus? — It moves where the operation runs, not the fundamental cost of refreshing a large state — splitting is still the actual fix.

Wrong answer: “Use `-refresh=false` on every plan to avoid the slowness.” That trades slow-but-correct for fast-but-blind to drift — you stop seeing real changes made outside Terraform, which is a worse trade than the latency it avoids for anything beyond a one-off diagnostic run.

05Terraform modules & code organization

Module design is where Terraform interviews test software-engineering judgment rather than syntax: composition versus inheritance-like reuse, versioning strategy, and how much a module should hide versus expose. This is asked often at senior/principal level because a platform team's entire leverage over an organization is expressed through its module design — bad module boundaries multiply the cost of every future change across every consumer.

Docs: modules · module provider handling

What makes a Terraform module well-designed, versus one that's just "code split into a subfolder"? senior

Answer. A well-designed module has a narrow, deliberate interface — variables that express intent ("environment", "instance_size") rather than passing through every underlying provider argument 1:1, and outputs that expose exactly what consumers need and nothing about the module's internal resource structure. It picks one clear level of abstraction and stays there: a module either wraps a single resource with sane defaults and validation, or composes several resources into a cohesive unit ("a standard web app: App Service + Application Insights + a Key Vault reference"), but doesn't do a bit of both in a way that leaves consumers unsure what they're actually getting. Just splitting code into a subfolder without rethinking the interface usually produces a "pass-through" module — every argument exposed as a variable, no defaults, no validation — which is strictly worse than no module at all, since it adds indirection without adding value.

Example

# pass-through anti-pattern: adds indirection, no value
module "storage" {
  source                    = "./modules/storage"
  account_tier               = var.account_tier
  account_replication_type   = var.account_replication_type
  # ...every argument, 1:1, with no defaults or validation
}

# well-designed: encodes an actual decision
module "storage" {
  source      = "./modules/standard-storage"
  environment = "prod"     # module internally decides tier/replication/retention from this
  name_suffix = "data"
}

Follow-ups

  • How small should a module be? — Small enough to have one clear reason to change, matching the "lifecycle" boundary from state design (unit 04) — a module and the state it tends to be used in should usually track the same ownership lines.
  • Should every resource be wrapped in a module? — No — wrapping a single simple resource in a module purely for the sake of having a module adds a layer of indirection a reviewer has to open to understand, for no abstraction benefit.
  • What's a good test of whether a module's interface is right? — Can a new consumer use it correctly by reading only its variables and README, with zero need to open the module's internals? If not, the interface is leaking implementation detail.

Wrong answer: “A good module exposes every underlying argument as a variable so it's maximally flexible.” Maximum flexibility at the interface level is minimum abstraction — it pushes every decision back onto the consumer and forfeits the entire point of building a shared module in the first place.

How should you version modules, and what's the difference between pinning a Git ref versus a registry version constraint? senior

Answer. A module sourced from a Git repository is pinned with `?ref=` in the source URL — Terraform clones exactly that ref, and there's no constraint-range syntax; you name one specific point, full stop. A module sourced from a registry (public Terraform Registry, a private one, or HCP Terraform's module registry) uses a `version` argument with the same constraint-operator syntax as provider versions (`~> 1.2`, `>= 1.0, < 2.0`), letting Terraform resolve to the latest version satisfying the constraint at `init` time — which means, unlike a Git ref, a registry-sourced module's actual resolved version can silently move forward between two `init` runs unless the lock file (for providers only, not modules — modules aren't captured in `.terraform.lock.hcl`) or a strict pin controls it. The practical consequence: registry version constraints need the same discipline as any dependency range (pin tightly in production, bump deliberately via PR) precisely because there's no lock-file safety net catching an unreviewed module version bump the way there is for providers.

Example

# Git ref: exact, immutable pin
module "network" {
  source = "git::https://github.com/org/tf-modules.git//network?ref=v2.4.1"
}

# Registry: version-range resolved at init
module "storage" {
  source  = "app.terraform.io/org/standard-storage/azurerm"
  version = "~> 3.0"
}

Follow-ups

  • Why aren't module versions captured in the lock file? — A deliberate scope decision — the lock file's job is provider binary integrity (checksums matter for a downloaded binary); module source is just HCL text, and Terraform treats re-resolving it on each `init` as acceptable given the version constraint you wrote.
  • What's the safest module version constraint for a production root? — An exact pin (`version = "3.4.2"`, no operator) or a tight `~>` patch-level range, reviewed and bumped deliberately — the same posture as pinning a container base image tag rather than floating `latest`.
  • Does semantic versioning discipline matter for internal modules the same way it does for public ones? — Yes, arguably more — an internal module often has fewer, more tightly coupled consumers who feel a breaking change immediately, so a clear major-version bump for breaking interface changes is what lets consumers upgrade on their own schedule.

Wrong answer: “Pinning a Git ref and a registry version constraint are basically equivalent ways to lock a module version.” A Git ref is a single immutable point; a registry `version` constraint is a range Terraform re-resolves — treating them as equivalent misses that the registry path needs active discipline to behave like the Git ref does by default.

What's the "provider inside a module" problem, and what changed in how Terraform handles provider configuration passed into child modules? principal

Answer. Historically, a child module could declare its own `provider` blocks (configuring, say, a second `azurerm` alias for a cross-subscription resource) which made the module implicitly responsible for its own provider setup — convenient in isolation but a real problem for reusability, since a consumer had no clean way to say "use my already-configured provider instead" without the module explicitly supporting provider pass-through via `configuration_aliases`. Modern guidance (and Terraform's own direction, reinforced through 1.x releases) is that child modules should generally not configure providers themselves at all — provider configuration belongs at the root, and modules should only declare `required_providers` with `configuration_aliases` for the specific aliased providers they need passed in explicitly, keeping the actual provider setup (credentials, subscription, aliasing) entirely under the root's control where a real deployment's environment-specific decisions belong.

Example

# child module: declares it needs an aliased provider, configures nothing itself
terraform {
  required_providers {
    azurerm = {
      source                = "hashicorp/azurerm"
      configuration_aliases = [azurerm.secondary]
    }
  }
}

# root: owns and passes in the actual provider configuration
provider "azurerm" { alias = "secondary" subscription_id = var.secondary_sub_id }
module "cross_sub" {
  source = "./modules/cross-sub"
  providers = { azurerm.secondary = azurerm.secondary }
}

Follow-ups

  • Why does provider-in-module hurt reusability specifically? — Because credentials/subscription/region are deployment-environment decisions, not module-logic decisions — baking them into a module ties one module to one environment's provider setup, defeating reuse across environments.
  • Can a module still work with zero explicit provider passing? — Yes, for the common case of a single default (non-aliased) provider configuration, which is implicitly inherited from the root — explicit passing is only required for aliased/multiple provider configurations.
  • What's the actual failure mode when this is done wrong? — A module with its own hardcoded provider block "works" until a second consumer needs a different subscription/region, at which point the module has to be forked or hastily retrofitted with aliasing it was never designed for.

Wrong answer: “Modules should always configure their own providers so they're self-contained and don't depend on the root.” That self-containment is illusory — it just moves an environment-specific decision into code meant to be reused across environments, which is precisely backwards.

How do you test a Terraform module, and what does terraform test (1.6+) actually check versus what it can't? senior

Answer. `terraform test` runs `.tftest.hcl` files that each define one or more `run` blocks — a set of variables, a command (`plan` or `apply`), and assertions against the resulting plan or applied state. It's genuinely useful for catching regressions in a module's logic: did a refactor change how many resources get created for a given input, does a specific output resolve to the expected value, does a `precondition`/validation correctly reject bad input. What it fundamentally can't check, even with `command = apply` against a real provider, is whether the resulting infrastructure actually behaves correctly at the application layer — a storage account created with the right SKU is not the same as confirming an application can actually write to it under load; that's the job of separate integration/smoke tests run after a real deployment, not something `terraform test`'s scope covers.

Example

run "creates_zrs_by_default" {
  command = plan
  variables { environment = "prod" }
  assert {
    condition     = azurerm_storage_account.data.account_replication_type == "ZRS"
    error_message = "Prod storage must default to ZRS replication."
  }
}

Follow-ups

  • What's the difference between a `plan`-mode and `apply`-mode test run? — `plan` tests logic without touching real infrastructure (fast, safe, the default for most module unit tests); `apply` tests actually create real resources temporarily, catching provider-level issues plan-mode logic checks can't, at real cost and real time.
  • How do mocked providers fit in (1.7+)? — `mock_provider` blocks let you test module logic without any real credentials or API calls at all — pure logic testing, fastest and most isolated, at the cost of not validating anything about actual provider behavior.
  • Does `terraform test` replace policy-as-code checks? — No — `terraform test` validates a module's own logic against its own author's expectations; policy-as-code (unit 09) validates any plan, from any module, against organization-wide rules — different scope and different audience.

Wrong answer: “`terraform test` with `command = apply` is a full integration test of the infrastructure it creates.” It confirms the resources were created as declared, not that they function correctly for their actual purpose — a real integration or smoke test against the deployed system is still a separate, necessary step.

Compose two design patterns for a "landing zone" style set of Terraform modules: layered composition versus a single mega-module. What breaks at scale with the mega-module approach? principal

Answer. Layered composition splits a landing zone into independent, narrowly-scoped modules (network, identity, logging, policy) each with its own state and lifecycle, wired together through explicit interfaces (outputs, a thin composition root, or a platform service layer) — new consumers opt into exactly the layers they need, and each layer can evolve, be tested, and be versioned independently. A mega-module tries to provision an entire landing zone — network, identity, policy, logging, and often the first workload too — from one module call with dozens of input variables. It looks appealing early (one `module` block, one `apply`, done) but breaks down at scale for the same reasons a monolithic state does (unit 01/04): every consumer's blast radius includes the whole thing, a single bug in the policy logic can block an otherwise-unrelated network change, and the module's own maintainers can't evolve one layer without re-validating and re-versioning the entire bundle for every downstream consumer at once. This is exactly the shape Azure Verified Modules (AVM) settled on for Azure landing zones — a library of composable, independently-versioned modules per resource/pattern rather than one all-in-one landing-zone module, replacing the older, more monolithic hand-rolled `ALZ-Bicep`/Terraform landing zone accelerators.

Example

Mega-module:
  module "landing_zone" { source = "..."; network_cidr = "..."; enable_policy = true; log_retention = 90; ... }
  -> one state, one blast radius, one release cadence for everything

Layered composition:
  module "network"  { source = "avm-res-network/virtual-network" ... }   # own state, own cadence
  module "policy"    { source = "avm-ptn-alz/policy" ... }                 # own state, own cadence
  module "logging"   { source = "avm-res-loganalytics/workspace" ... }    # own state, own cadence

Follow-ups

  • Doesn't layered composition just move the coupling problem into wiring between layers? — Yes, partly — the trade-off is real, and the mitigation is the same "explicit versioned interface" discipline discussed for `terraform_remote_state` coupling (unit 04), applied at the module-composition level rather than the state level.
  • Is there a middle ground? — Yes — "pattern modules" (AVM calls these `avm-ptn-*`) that compose a handful of resource modules into a common pattern (a hub network with standard peering, say) without going all the way to a single all-encompassing landing-zone module.
  • Does Terraform's own module composition model make layering easy? — Reasonably, via `module` blocks referencing outputs of sibling modules within the same root, or across roots via remote state/registry outputs for the fully-decoupled version.

Wrong answer: “A mega-module is fine as long as it's well-documented.” Documentation doesn't fix the structural coupling of shared blast radius and shared release cadence — the problem is architectural, not a knowledge gap that better docs close.

What are Azure Verified Modules (AVM), and why should you default to them over hand-rolled modules for Azure resources in 2026? mid

Answer. AVM is Microsoft's first-party catalog of Terraform and Bicep modules for Azure resources and common patterns, announced at Ignite 2023 and now the default recommended starting point for Azure infrastructure in both languages — resource-level modules (`avm-res-*`, one Azure resource type each, following consistent conventions for naming, tagging, diagnostics, RBAC) and pattern modules (`avm-ptn-*`, composing several resource modules into a common architecture). The case for defaulting to them: they're maintained by Microsoft and the community together, tested against real Azure API behavior continuously, and encode a consistent set of well-architected defaults (diagnostic settings wired up, private endpoints supported, sensible naming) that a hand-rolled module has to reinvent and then maintain forever. They've effectively superseded the older, more ad hoc `Azure/terraform-azurerm-*` community modules and the original hand-maintained `ALZ-Bicep` landing zone repository, which is now archived in favor of AVM-based landing zone patterns.

Example

module "storage_account" {
  source  = "Azure/avm-res-storage-storageaccount/azurerm"
  version = "~> 0.2"

  name                = "stdataprodweu001"
  resource_group_name = azurerm_resource_group.app.name
  location             = "westeurope"
}

Follow-ups

  • When would you not use an AVM module? — When it doesn't yet cover a resource type you need, or when its opinionated defaults genuinely conflict with a constraint specific to your environment that isn't exposed as a variable — AVM modules aim to be flexible but aren't universal.
  • Does AVM exist for non-Azure clouds? — No — it's Azure-specific; AWS and GCP have their own separate first-party or community module ecosystems with different conventions.
  • Are AVM modules a good fit for both Bicep and Terraform? — Yes, deliberately — AVM publishes matching modules in both languages with equivalent interfaces where possible, which is part of the pitch for organizations running both.

Wrong answer: “AVM is just Microsoft's branding for the old `Azure/terraform-azurerm-*` community modules.” They're a distinct, first-party effort with different governance, testing, and versioning conventions — treating them as a rename undersells exactly the maturity improvement AVM represents.

What's the difference between a root module and a child module, and why does that distinction matter for where backend configuration and provider configuration are allowed to live? screener

Answer. The root module is the configuration in the directory you run Terraform commands from — it's the one and only place `backend` configuration is allowed, since state is a property of an entire Terraform run, not of an individual reusable component. A child module is anything referenced via a `module` block, called from the root (directly, or transitively through other modules) — it can declare `required_providers` and receive provider configuration passed in, but per the guidance from a few questions back, well-designed child modules shouldn't configure providers themselves, and none of them can declare their own backend at all; every module call in a single `terraform apply` shares exactly one state, determined solely by the root.

Example

# root module (this directory): the only place backend goes
terraform {
  backend "azurerm" { ... }
}
module "network" {
  source = "./modules/network"   # child module: no backend block allowed here
}

Follow-ups

  • Can a child module itself call further nested modules? — Yes, to any depth — the root/child distinction is really "the one entry point" versus "everything it pulls in," regardless of how many levels deep that goes.
  • Do outputs work differently at root versus in a child module? — A root module's outputs are what `terraform output` surfaces to the CLI/consumers; a child module's outputs are only visible to its immediate parent unless explicitly re-exposed up the chain.
  • What happens if you try to put a `backend` block in a child module? — Terraform errors immediately at `init` — it's a hard restriction, not just a convention.

Wrong answer: “Each module in a multi-module project can have its own state via its own backend block.” Only the root determines backend/state for an entire run; achieving genuinely separate state per module means separate root modules (separate directories, separate `terraform` invocations) wired together via remote state, not nested module calls within one run.

Design review: a colleague's module has 40 input variables, most with no default, and a single monolithic `main.tf`. What specifically would you push back on in review, and why? senior

Answer. Forty required variables with no defaults is the pass-through anti-pattern from earlier in this unit taken to an extreme — it signals the module hasn't made any decisions on the consumer's behalf, which is the entire value proposition of a module versus inlined resource blocks. Concretely, I'd push back on: (1) grouping related variables into a smaller number of typed objects with `optional()` attributes and sensible defaults, so a typical caller passes 3-5 things instead of 40; (2) splitting the monolithic file along resource-type or lifecycle lines (`network.tf`, `compute.tf`, `variables.tf`, `outputs.tf`) purely for reviewability — Terraform doesn't care about file boundaries within a module, but humans reviewing a diff do; (3) asking what decisions the module is actually meant to encode — if the answer is "none, it just wraps the provider resource 1:1," the right fix might be deleting the module and using the resource directly, rather than polishing an interface that shouldn't exist.

Example

# before: 40 flat required variables
variable "account_tier" {} variable "account_replication_type" {} # ... x40

# after: grouped, defaulted, decision-encoding
variable "environment" {
  type = string
  validation { condition = contains(["dev","stage","prod"], var.environment) error_message = "..." }
}
variable "overrides" {
  type = object({
    replication_type = optional(string)
  })
  default = {}
}

Follow-ups

  • Is splitting files purely stylistic, or does Terraform treat them differently? — Purely stylistic — Terraform loads every `.tf` file in a module directory as one merged configuration regardless of filename; the split is entirely for human readability.
  • What if the consumer genuinely needs to control all 40 things independently? — Rare in practice — usually most of those 40 correlate (an environment implies a tier, a replication type, a retention policy together), and a module's job is to encode that correlation, not preserve unlimited independent control.
  • How would you introduce this refactor without breaking existing callers? — A new major version with the new grouped interface, `moved`/deprecation guidance for the old flat variables during a transition window, and a clear migration note — not a silent breaking change to the existing version.

Wrong answer: “It's fine, more variables just means more flexibility for consumers.” That's the same false trade-off as the earlier "expose every argument" module design question — flexibility at the interface is exactly what a module is supposed to trade away in exchange for encoded, sensible decisions.

06Bicep fundamentals & language

Bicep questions test whether you understand it as a thin, opinionated DSL over ARM rather than a Terraform clone — scopes, the `existing` keyword, user-defined types/functions, `.bicepparam`, and how Bicep's no-state model actually works day to day. Screener depth is core syntax; senior/principal depth is scoping rules, module composition, and knowing precisely where Bicep's abstractions stop and raw ARM JSON shows through.

Docs: Bicep overview · Bicep file structure

What is Bicep, precisely — is it a new deployment engine, or something else? screener

Answer. Bicep is a domain-specific language that compiles (transpiles) to ARM JSON templates — it introduces no new deployment engine, no new API, and no new runtime behavior; every Bicep file's actual execution is handled entirely by Azure Resource Manager exactly as it would be for a hand-written ARM template. This is the single most important fact to get right about Bicep: anything ARM can do, Bicep can do, because Bicep is ARM underneath a friendlier syntax (no more sprawling JSON, first-class modules and parameters, expressions instead of nested `[concat(...)]` functions); anything ARM can't do, no amount of clever Bicep can either, since the compiled output is the only thing Azure ever actually sees.

Example

resource storage 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: 'stdataprodweu001'
  location: 'westeurope'
  sku: { name: 'Standard_ZRS' }
  kind: 'StorageV2'
}
az bicep build --file main.bicep   # produces main.json - the actual ARM template

Follow-ups

  • Can you go the other direction — ARM JSON to Bicep? — Yes, `bicep decompile`, useful for migrating existing hand-written or exported ARM templates, though the output usually needs cleanup since decompilation isn't always idiomatic.
  • Does this mean Bicep has feature parity with ARM on day one of any new Azure API version? — Very close to it — because Bicep just emits the resource's JSON shape as declared, a brand-new API version's properties are usable in Bicep as soon as you reference that `apiVersion`, with no Bicep-specific update required.
  • Is there any Bicep behavior that isn't just "ARM JSON with nicer syntax"? — A few things live purely at the tooling layer — `what-if`'s formatting, the linter, VS Code IntelliSense — but the deployed behavior is always ARM's.

Wrong answer: “Bicep is Microsoft's answer to Terraform — a full IaC engine that manages Azure resources directly.” It has no engine of its own at all; it's purely a compiler targeting the ARM JSON format that Azure Resource Manager has always consumed.

Why does Bicep have no state file, and how does ARM know what to update or delete without one? mid

Answer. ARM already keeps a server-side record, per resource group (and other scopes), of what resources exist and — for resources deployed via a tracked ARM deployment — which deployment created or last touched them; that record lives in Azure itself, not in a file a client has to manage. A normal (non-stack) ARM/Bicep deployment diffs your template's declared resources against the resource group's actual current resources at deployment time, computing creates and updates the same way Terraform's plan does — but it has traditionally had no concept of "this resource used to be in the template and now it's gone, delete it," because ARM deployments are additive/incremental by default and simply don't track removal across separate deployment operations the way a persisted state file would. That gap is exactly what Deployment Stacks (unit 12) were introduced to close, by adding an explicit, ARM-managed record of "everything this stack currently owns" so removal can be detected and acted on.

Example

az deployment group create --resource-group rg-app --template-file main.bicep
# ARM computes create/update actions against the resource group's current resources
# server-side - no local state file to manage, back up, or lock

Follow-ups

  • Does this mean removing a resource block from a Bicep file deletes it in Azure? — Not with a plain incremental deployment — the resource is simply left alone, still existing in Azure, disconnected from the template; only Complete mode or a Deployment Stack can turn removal-from-template into an actual delete.
  • Is there a Bicep/ARM equivalent of state corruption? — Much rarer, precisely because there's no separate file to corrupt — the closest analogue is a Deployment Stack's own tracked resource list becoming inconsistent with reality, which is a narrower, better-contained failure mode.
  • Does "no state file" mean no locking concerns either? — Mostly yes for a single resource group — but concurrent deployments to the same scope can still race at the ARM API level, and ARM itself serializes conflicting operations on the same resource.

Wrong answer: “Bicep has no state because it doesn't need to track what it created — it just applies the template every time.” ARM absolutely tracks what exists and what a deployment touched; the nuance being tested is that this tracking lives server-side in Azure, and historically didn't include a robust "detect and remove what was taken out of the template" capability until Deployment Stacks.

Explain Bicep's four deployment scopes and how you choose the right one for a given resource. mid

Answer. Resource group scope is the default and covers the vast majority of resources — VMs, storage, networking, most PaaS services. Subscription scope is for things that live above any single resource group: creating resource groups themselves, subscription-level policy assignments, subscription-level RBAC. Management group scope is for governance applied across multiple subscriptions — policy definitions and assignments, RBAC, intended to be inherited down to every subscription underneath. Tenant scope is the rare top-level case — a handful of tenant-wide policy or RBAC scenarios that apply across the entire Azure AD tenant. You choose based on where the resource type itself is defined to live (the resource provider's documentation states its valid scope) and where the governance/blast-radius boundary you actually want sits — provisioning a policy at management-group scope when you only need it on one subscription needlessly widens its blast radius.

Example

targetScope = 'subscription'

resource rg 'Microsoft.Resources/resourceGroups@2023-07-01' = {
  name: 'rg-app-prod'
  location: 'westeurope'
}

module app 'app.bicep' = {
  name: 'app-deployment'
  scope: rg
  params: { /* ... */ }
}

Follow-ups

  • What's `targetScope` for and what happens if you omit it? — It declares the file's own deployment scope; omitted, it defaults to `resourceGroup` — and every resource in the file must be deployable at whatever scope is declared, or Bicep errors at compile time.
  • Can one Bicep file deploy resources at multiple scopes? — Yes, via modules — a subscription-scoped root file creates the resource group, then a module deployed with `scope: rg` (as above) targets resource-group scope for everything inside it.
  • Does scope choice affect RBAC needed to deploy? — Directly — a subscription-scope deployment needs subscription-level permissions (e.g. to create resource groups), which is often a genuinely different, more privileged identity than the one used for routine resource-group-scope app deployments.

Wrong answer: “Just deploy everything at management group scope so it's always available everywhere.” That maximizes blast radius and required privilege for no benefit — the correct scope is the narrowest one the resource type and the governance intent both require.

What does the existing keyword do, and why is it essential for referencing resources Bicep didn't create? mid

Answer. `resource foo 'Type@version' existing = { name: '...' }` declares a symbolic reference to a resource that already exists — Bicep/ARM will never create, update, or delete it, but the reference lets you read its properties (and, critically, use functions like `listKeys()` against it) with full IntelliSense and type-checking, the same way you'd reference a resource this template does manage. It's essential because plenty of real deployments need to read from or grant access on a resource owned by a different template, a different team, or created out-of-band — without `existing`, the only options are hardcoding a resource ID string (no validation, no IntelliSense, easy to get wrong) or over-broadly redeclaring the resource as if you owned it, which risks Bicep/ARM attempting to manage properties you don't actually control.

Example

resource kv 'Microsoft.KeyVault/vaults@2023-07-01' existing = {
  name: 'kv-shared-platform'
}

resource app 'Microsoft.Web/sites@2023-12-01' = {
  name: 'app-web'
  // ...
  properties: {
    siteConfig: {
      appSettings: [
        { name: 'DB_CONN', value: kv.getSecret('db-connection-string') }
      ]
    }
  }
}

Follow-ups

  • Does an `existing` resource need to be in the same resource group? — No — combined with `scope:`, you can reference an existing resource in a different resource group or even subscription, as long as your deployment identity has read access to it.
  • Can you deploy role assignments against an `existing` resource? — Yes, and it's one of the most common real uses — granting an app's managed identity a role on a Key Vault or storage account the app doesn't own, scoped to that `existing` reference.
  • What happens if you accidentally omit `existing`? — Bicep treats it as a resource this deployment owns and will attempt to create or reconcile it against the properties you specified — a real risk of unintentionally modifying a shared resource's configuration.

Wrong answer: “`existing` is just a way to look up a resource's ID for use elsewhere in the template.” It's a fully typed, IntelliSense-backed reference supporting the resource's runtime functions (`.getSecret()`, `.listKeys()`, etc.), not merely an ID lookup — that distinction matters for what you can actually do with the reference.

What are user-defined types and user-defined functions in Bicep, and what did teams do before they existed? senior

Answer. User-defined types (GA in Bicep 0.24, August 2023) let you declare a named, reusable type — an object shape, a union of literal strings, an array of a custom type — with the `type` keyword, so a parameter or variable can be typed precisely instead of falling back to a loosely-typed `object` or a long inline union repeated in every file that needs it. User-defined functions (GA in 0.26, November 2023) let you declare a reusable pure function with the `func` keyword, taking typed parameters and returning a typed value, computed entirely at compile/deploy time. Before both existed, the common workarounds were: for types, an untyped `object` parameter with only a description comment enforcing the intended shape (no compiler help at all if a caller got it wrong); for functions, either copy-pasting the same expression everywhere it was needed, or extracting it into a tiny separate module purely to reuse one calculated value, which is a heavier unit of reuse than a function warranted.

Example

type environmentName = 'dev' | 'stage' | 'prod'

type subnetConfig = {
  name: string
  addressPrefix: string
  delegation: string?
}

func buildResourceName(prefix string, env environmentName, suffix string) string =>
  '${prefix}-${env}-${suffix}'

param environment environmentName
var storageName = buildResourceName('st', environment, 'data')

Follow-ups

  • Can user-defined functions call Azure APIs or reference resources? — No — they're pure, compile-time functions over their own parameters only; they can't reference `resource` symbols or do anything with side effects, which keeps them safely composable.
  • Can a user-defined type be exported and shared across files? — Yes, via `@export()` combined with a `.bicep` file used as a "types" module that other files import from — the closest Bicep equivalent to a shared types library.
  • Does the nullable type syntax (`string?`) relate to this? — Yes, shipped alongside/around the same period — optional properties on a user-defined object type use the same `?` marker as nullable parameters, giving a consistent "this may be absent" story across the type system.

Wrong answer: “Bicep always had strong custom types — that's the main difference from ARM JSON.” Early Bicep (pre-0.24/0.26) was more strongly typed than raw ARM JSON for its built-in types, but user-defined types/functions specifically are a later, deliberate addition — dating them wrong misrepresents which Bicep version a codebase actually needs.

What is .bicepparam, what did it replace, and what does the newer extends keyword (2026) add to it? senior

Answer. `.bicepparam` (GA in Bicep 0.18, early 2023) is a typed parameters file format — `using 'main.bicep'` at the top ties it to a specific template, giving full IntelliSense and compile-time validation of parameter values against the template's actual parameter types. It replaced the older ARM parameters JSON file format (`azuredeploy.parameters.json`), which had no compile-time validation at all — a typo'd parameter name or a wrong type was only caught at deployment time, by ARM, not by any local tooling. The `extends` keyword is one of the most recent Bicep additions relevant here: it lets one `.bicepparam` file inherit from another, so a base parameters file (shared defaults across all environments) can be extended by environment-specific files that only override what differs — before `extends`, teams either duplicated an entire parameters file per environment or fell back to a separate templating/scripting layer to generate parameter files, both of which `extends` now removes the need for.

Example

// base.bicepparam
using 'main.bicep'
param sku = 'Standard'
param location = 'westeurope'

// prod.bicepparam
extends 'base.bicepparam'
param sku = 'Premium'   // override just this one

Follow-ups

  • Can a `.bicepparam` file still reference an ARM JSON template directly? — Yes, `using` can point at a compiled `.json` template too, not just a `.bicep` source file, which matters for teams migrating incrementally.
  • Does `.bicepparam` support expressions, or only literal values? — It supports a useful subset of Bicep expressions and functions (not full resource references), which is more than plain JSON parameter files ever could, while intentionally staying simpler than a full template.
  • Is the old JSON parameters format deprecated? — Not formally removed, but `.bicepparam` is the unambiguous modern default for any new Bicep work as of 2026 — presenting the JSON format as current best practice would be the legacy-unaware answer.

Wrong answer: “`.bicepparam` files are just Bicep syntax for the same JSON parameters format, no functional difference.” The functional difference — compile-time type validation against the template, plus now `extends`-based inheritance — is exactly the improvement that makes `.bicepparam` worth adopting over the legacy format.

How do decorators like @secure(), @allowed(), and @description() work, and what's the actual enforcement mechanism behind @secure()? mid

Answer. Decorators annotate a parameter, output, or resource with metadata that Bicep compiles into the ARM template's own metadata/constraint format — they aren't a Bicep-only convenience, they become real ARM template properties that ARM itself enforces at deployment time. `@secure()` marks a string or object parameter as a secure value: ARM refuses to log or display its value in deployment history/activity logs and the portal, and — the specific mechanic worth knowing — a secure parameter cannot be given a default value in the template at all, precisely so a secret can't accidentally ship baked into source-controlled code. `@allowed([...])` constrains a parameter to a fixed set of values, validated by ARM before any resource operation begins, catching an invalid value at the very start of deployment rather than partway through resource creation. `@description()` is purely documentation, surfaced in generated docs and portal UI, with zero enforcement.

Example

@secure()
@description('Administrator password for the flexible server.')
param adminPassword string

@allowed(['dev', 'stage', 'prod'])
param environment string

Follow-ups

  • Can `@secure()` parameters still be logged accidentally? — Not by ARM's own deployment history, but a resource or script that itself logs the value it received (a deployment script's stdout, an app's own logging) can still leak it — `@secure()` protects the ARM layer, not everything downstream.
  • Does `@allowed()` work on outputs too? — No — it's a parameter-only decorator, since outputs are computed results, not user-supplied inputs to validate.
  • What decorator generates Bicep module documentation, and how new is that? — An experimental Bicep feature for generating module documentation from decorators/descriptions has been in preview through 2025-2026 — worth naming as a very recent, still-experimental capability rather than a stable feature.

Wrong answer: “`@secure()` encrypts the parameter's value.” It doesn't encrypt anything — it suppresses logging/display in ARM's deployment history and disallows a default value; the value still flows to the resource provider and, once applied, lives wherever that resource provider stores it (e.g. in cleartext unless the resource itself encrypts it).

How does Bicep handle loops, and what's the equivalent of Terraform's count/for_each distinction? mid

Answer. Bicep's `for` expression, applied directly on a `resource` or `module` declaration, iterates over an array (or `range()` for a numeric sequence) to produce multiple instances — syntactically it's one construct, not two separate meta-arguments the way Terraform splits `count` and `for_each`. The identity/keying concern is the same underlying issue, though: iterating over an array by index (`for i in range(0, 3)`) behaves like Terraform's `count` — removing a middle element shifts every later instance's identity — while iterating with an explicit loop variable bound to a genuinely unique property of each item, combined with a resource `name` derived from that property rather than the index, behaves more like `for_each`'s stable keying. Bicep doesn't enforce this distinction at the language level the way Terraform's two separate constructs do; it's on the author to iterate in a way that keeps resource names (which is what ARM actually uses for identity) stable across additions/removals.

Example

// index-based: fragile, same risk as Terraform's count over a shrinking list
resource rgs1 'Microsoft.Resources/resourceGroups@2023-07-01' = [for i in range(0, length(regions)): {
  name: 'rg-${regions[i]}'
}]

// value-based naming: stable, same intent as Terraform's for_each
resource rgs2 'Microsoft.Resources/resourceGroups@2023-07-01' = [for region in regions: {
  name: 'rg-${region}'
}]

Follow-ups

  • Can you loop over an object/map, not just an array? — Yes, `for key in items(myObject)` iterates key-value pairs, giving you both the key and value inside the loop body.
  • Does Bicep support loop filtering the way Terraform's `for` expression does with `if`? — Yes, `[for item in list: if (condition) { ... }]` filters which items actually produce a resource instance.
  • What's the practical consequence of getting this wrong in Bicep specifically? — Because there's no separate state file, the "wrong" outcome shows up directly as an unnecessary resource replacement in the `what-if` diff — the same symptom, surfaced through a different mechanism than Terraform's plan.

Wrong answer: “Bicep loops don't have the identity/keying problem Terraform's `count` has, since it's just one `for` construct.” The underlying risk is about how the resource's `name` (ARM's real identity) is derived, not which loop syntax is used — an index-derived name in Bicep has exactly the same fragility as `count`'s index-based keying in Terraform.

Explain Bicep modules — how do they differ conceptually from Terraform modules, given Bicep has no state? mid

Answer. A Bicep module is a reference to another `.bicep` file (or a registry-published module), deployed as a nested ARM deployment — conceptually similar to a Terraform module call in that it's a reusable unit with its own parameters and outputs, but mechanically different because each module deployment becomes its own ARM deployment resource, nested inside the parent's deployment, rather than sharing one flat state graph the way Terraform's module tree shares one state file. This has real consequences: each nested deployment gets its own entry in deployment history (useful for auditing exactly what a module call did), and — because there's no shared state — a module's resources are tracked by ARM at whatever scope the module targets, independently of the parent deployment's own tracking, which is part of why Deployment Stacks (unit 12) had to be designed to account for nested module deployments explicitly when computing what a stack currently owns.

Example

module network 'modules/network.bicep' = {
  name: 'networkDeployment'
  params: {
    vnetAddressPrefix: '10.0.0.0/16'
  }
}

resource app 'Microsoft.Web/sites@2023-12-01' = {
  name: 'app-web'
  properties: {
    virtualNetworkSubnetId: network.outputs.appSubnetId
  }
}

Follow-ups

  • Can Bicep modules be published and versioned like Terraform registry modules? — Yes, via a Bicep Registry (an OCI-compliant container registry, e.g. Azure Container Registry) with semantic version tags — the closest equivalent to Terraform's registry versioning story.
  • Does nesting modules deeply have a real cost, the way deep Terraform module nesting does? — Somewhat — each nested module is its own deployment operation with its own overhead and its own entry in deployment history, so very deep nesting adds real deployment time and a more cluttered history to navigate, not just a stylistic concern.
  • Do template specs solve a similar problem? — Related but different — a template spec packages and versions an entire template (not a reusable component meant for composition) as a first-class Azure resource, more analogous to publishing a whole deployable artifact than to a Terraform-style reusable module.

Wrong answer: “Bicep modules work exactly like Terraform modules, just without a state file to worry about.” The nested-deployment model is a meaningfully different mechanism, not merely "the same thing minus a state file" — the per-module deployment tracking and scoping rules it introduces have no direct Terraform analogue.

What's the Bicep linter, and what does bicepconfig.json let you control? screener

Answer. The Bicep linter runs at compile/build time (and live in VS Code via the Bicep extension) and flags common mistakes and anti-patterns — unused parameters/variables, hardcoded values that should be parameters, insecure defaults, outdated API versions — as warnings or errors depending on configured severity. `bicepconfig.json`, placed at the root of a Bicep project, configures which linter rules are active and at what severity, sets the analyzer's target Azure API version behavior, and can configure module alias shortcuts (naming a registry so `br/public:...` references are shorter) — it's the project-level Bicep tooling configuration file, roughly analogous in role to an ESLint config for a JS project.

Example

{
  "analyzers": {
    "core": {
      "rules": {
        "no-hardcoded-env-urls": { "level": "error" },
        "secure-parameter-default": { "level": "error" }
      }
    }
  }
}

Follow-ups

  • Does the linter block deployment, or only warn? — Configurable per rule — a rule set to `error` fails the build (and CI, if the build is a gate), while `warning`/`info` surface without blocking; teams typically escalate security-relevant rules to `error`.
  • Can you suppress a specific linter finding inline? — Yes, `#disable-next-line rule-name` for a deliberate, justified exception, which is more auditable in review than silencing the rule project-wide.
  • Is there an equivalent check for outdated API versions specifically? — Yes, the linter can flag resources using an old `apiVersion` compared to what's currently available, nudging toward staying current without forcing an immediate bump.

Wrong answer: “The linter only affects the VS Code editing experience, not actual builds or deployments.” `bicep build`/`az deployment ... create` runs the same linter, and a rule configured as `error` genuinely fails the build — it's a real CI gate, not just an editor convenience.

07Choosing the tool: Bicep vs ARM vs Terraform

Interviewers ask this to see if you reason about tool choice from actual constraints (multi-cloud need, existing team skill, time-to-first-resource-availability for new API features) rather than tribal preference. It comes up often precisely because most organizations of any size actually run more than one of these, and the principal-level answer is about how they coexist, not which one "wins."

Docs: Bicep vs Terraform (Microsoft's own comparison)

Give a clear decision framework: when do you reach for Terraform over Bicep, and vice versa? senior

Answer. Reach for Terraform when you're multi-cloud (even "mostly Azure with a bit of Datadog/Cloudflare/GitHub" counts — Terraform's provider ecosystem covers thousands of non-Azure services Bicep has no concept of), when you want one workflow and one state model across everything you provision, or when your organization already has deep Terraform tooling investment (policy-as-code, module registry, CI patterns) that a second tool would duplicate. Reach for Bicep when you're Azure-only (or Azure-overwhelmingly-dominant) and want zero lag between a new Azure resource/API feature shipping and being able to use it — Bicep, being ARM underneath, never waits on a third-party provider release the way Terraform's `azurerm` provider sometimes does — and when you want to avoid state file management entirely. In practice, principal-level judgment is knowing these aren't mutually exclusive: many organizations run Terraform for cross-cutting/multi-cloud concerns and Bicep for Azure-specific teams that want the fastest path to new Azure capabilities, with a clear boundary (see the state/deployment coexistence question below) preventing them from fighting over the same resources.

Example

Multi-cloud platform team, owns network/identity across Azure+AWS+GitHub  -> Terraform
Azure-only app team, wants day-one access to new Azure preview features    -> Bicep
Org running both: platform layer in Terraform, app teams choose per-need  -> coexistence, clear boundaries

Follow-ups

  • Is "Terraform's Azure provider lags behind new APIs" still true in 2026? — Less than it used to be — `azurerm` has matured and the lag for mainstream resources is usually days to a few weeks, but it's still a real, non-zero gap compared to Bicep's zero-lag-by-construction advantage for brand-new or preview API surface.
  • Does team skill matter as much as technical fit? — Often more, practically — a team fluent in HCL that's forced onto Bicep (or vice versa) for a marginal technical reason will be slower and make more mistakes than staying with what they know well, unless the technical gap is substantial.
  • What about cost/licensing as a factor? — Real since HashiCorp's 2023 relicensing — Terraform's BUSL terms matter for certain commercial redistribution scenarios (rare for internal infra use, but not zero), whereas Bicep's tooling is fully open and free; OpenTofu (unit 13) is the answer for teams who want the Terraform ecosystem without the BUSL question.

Wrong answer: “Just pick whichever the team already knows and don't overthink it.” Team familiarity is a real and legitimate input, but treating it as the only input misses cases where a genuine multi-cloud requirement or a hard need for day-one API access makes one tool clearly wrong regardless of who's more comfortable with it.

Where does plain ARM JSON still fit in 2026, if Bicep compiles down to it anyway? mid

Answer. Almost nowhere for new, hand-authored work — there is no real reason to write new templates directly in ARM JSON when Bicep produces the identical deployed result with far better authoring ergonomics. Where it still legitimately shows up: templates exported directly from the Azure portal ("export template" on an existing resource, still JSON, sometimes decompiled to Bicep for further editing but often just used as a one-off reference); very old codebases that predate Bicep's GA (2020) and haven't been migrated; and the compiled output layer itself, which is JSON by necessity since that's ARM's native input format regardless of what authored it. Recommending ARM JSON for new work in an interview answer is the clearest possible signal of being out of date, since Bicep has been Microsoft's explicitly recommended default for Azure IaC authoring for several years now.

Example

az bicep decompile --file exported-template.json   # portal export -> editable Bicep

Follow-ups

  • Does the Azure Portal still generate ARM JSON when you export a resource's template? — Yes, that export path remains JSON, though the portal also offers viewing/exporting as Bicep directly in many blades now.
  • Is there a reason a platform team would still author in raw JSON deliberately? — Essentially none for hand-written new work — the rare case is generating JSON programmatically from some other tool that doesn't have Bicep support, treating the JSON purely as a compilation target rather than a hand-edited artifact.
  • Do template specs require Bicep, or do they accept JSON too? — They accept either — a template spec just packages whatever ARM JSON results, whether it was authored directly or compiled from Bicep.

Wrong answer: “ARM JSON is still commonly used for new templates because it's more explicit and predictable than Bicep.” This inverts current practice — Bicep is unambiguously the modern default, and JSON's remaining role is legacy maintenance and the compiled-output layer, not a competing authoring choice for new work.

Explain the BUSL relicensing of Terraform and the OpenTofu fork — what actually changed, and does it affect a typical enterprise's internal use? senior

Answer. In August 2023, HashiCorp relicensed Terraform (and its other core products) from the fully open MPL 2.0 to the Business Source License (BUSL) — the practical restriction targets competitors building a commercial product that directly competes with HashiCorp's own offerings (e.g. a rival hosted Terraform-as-a-service), and the terms around exactly what counted as "competing" were seen as ambiguous enough to worry a wider set of companies than the narrow set actually targeted. In response, a group of companies with a stake in an open Terraform ecosystem (Gruntwork, Spacelift, Harness, env0, Scalr, and others) forked the last MPL-licensed Terraform codebase and created OpenTofu, which became a Linux Foundation project — giving the ecosystem a fully open-source, community-governed alternative with no BUSL ambiguity at all. For a typical enterprise's purely internal use — writing and running your own Terraform configs against your own infrastructure, never redistributing or reselling the tool itself — the BUSL change has essentially no practical effect; it matters mainly for vendors building competing commercial infrastructure-automation products on top of Terraform's codebase.

Example

2023-08: HashiCorp relicenses Terraform, Vault, etc. to BUSL 1.1
2023-09: OpenTofu (fork of last MPL Terraform) announced under Linux Foundation
2026-09: OpenTofu 1.12.0 current stable; ~3,900+ providers, ~23,600+ modules in its registry

Follow-ups

  • Is OpenTofu a drop-in replacement for Terraform? — Very close, for most day-to-day use — same HCL, largely compatible state format and provider ecosystem, though the two projects have begun diverging slightly in newer features (each adding things the other hasn't yet), so "identical forever" isn't guaranteed.
  • Why would a company choose OpenTofu specifically over sticking with Terraform under BUSL? — Legal certainty for anyone whose use case brushes against BUSL's "competing offering" language, a preference for Linux Foundation governance over a single vendor's control, or simply wanting to avoid any future licensing changes from a for-profit steward.
  • Does state/provider compatibility mean you can switch between them freely today? — Largely yes for now, at the state-file and provider-plugin level, which is part of why the fork was viable at all — but treating this as a permanent guarantee ignores that the two are independently evolving projects.

Wrong answer: “BUSL means you now have to pay HashiCorp to use Terraform.” Ordinary use — internal infrastructure automation, even at large commercial companies — remains free under BUSL; the license restricts specifically building and offering a competing product on top of the source, not general usage.

A team wants to run both Bicep and Terraform against the same Azure subscription. What are the real risks, and how do you structure ownership to avoid them? principal

Answer. The core risk is exactly the same class of problem as two Terraform configs targeting the same state key (unit 04): if both tools are allowed to manage the same resource, each treats the other's changes as unexpected drift and will try to "correct" it on its own next run, producing a fight neither tool can see the other side of, since Bicep has no visibility into Terraform's state and Terraform has no visibility into ARM deployment history beyond what it created itself. The safe structure is a clear, non-overlapping ownership boundary per resource (or, better, per resource group/subscription where feasible) — decide up front which tool owns which resources, enforce it through separate resource groups or tagging conventions with policy that flags unexpected ownership, and never let both tools declare the same resource in their respective configs. Where the two need to interoperate (a Terraform-created VNet that a Bicep-deployed app needs to reference), treat the boundary the same way as any cross-team coupling: Bicep reads the VNet via `existing` using a resource ID passed in as a parameter, never redeclaring or attempting to manage it.

Example

rg-platform-network/   owned by Terraform    -> VNet, subnets, NSGs
rg-app-team-a/         owned by Bicep          -> App Service, its own storage, refs the VNet via existing + passed-in resource ID

Follow-ups

  • Can Azure Policy help enforce this boundary? — Yes — a policy that denies resource creation in the "wrong" tool's resource groups (enforced via tagging or naming convention) turns an easily-violated convention into an actually-enforced guardrail.
  • Does mixing tools multiply the operational/on-call burden? — Yes, meaningfully — two sets of CLI tooling, two sets of CI pipeline patterns, two mental models for anyone doing incident response has to context-switch between; this cost should be weighed against the genuine benefit of letting each team use its best-fit tool.
  • Is there a safe way to have one tool read the other's outputs, similar to Terraform's remote state? — Yes — Terraform can expose outputs consumed as plain values (via a small script, a stored parameter file, or an internal API) that a Bicep `.bicepparam` file's inputs are generated from, keeping the coupling explicit and one-directional.

Wrong answer: “It's fine as long as both teams communicate about who's changing what.” Verbal/process coordination doesn't scale and doesn't survive team turnover — the actual fix is a structural boundary (separate resource groups/policy enforcement) that makes the conflict impossible by construction, not merely discouraged by convention.

How would you justify migrating an existing large ARM JSON or early-Bicep estate to modern Bicep (or to Terraform) to a skeptical engineering leadership team? principal

Answer. Don't lead with "modern is better" — lead with the concrete, measurable costs the current state actually imposes: how long does a routine change take today (if raw JSON, likely much longer due to verbosity and error-proneness), how many incidents in the last year trace back to a template mistake that better tooling (the linter, type checking, `what-if`) would have caught before deployment, and how much onboarding time new engineers spend learning a legacy pattern that has a straightforward modern equivalent. Frame the migration as incremental and low-risk rather than a rewrite: `bicep decompile` for an ARM JSON estate gets a mechanical first pass, then targeted refactors (introducing modules, user-defined types, AVM modules) delivered piece by piece against real files as they're touched anyway, never a stop-the-world rewrite that competes for the same engineering time as feature work. The strongest argument for leadership specifically is usually risk reduction with a number attached — fewer failed deployments, faster recovery, less time debugging opaque JSON — rather than developer experience alone, which resonates less at that level.

Example

Phase 1 (low risk): bicep decompile every JSON template, commit as-is, no behavior change
Phase 2 (opportunistic): as each template is touched for a real change, refactor that one file
                          to modern patterns (types, AVM modules, linter clean)
Phase 3 (deliberate): retire any remaining untouched legacy templates on a set deadline

Follow-ups

  • What if leadership asks "why not just leave it, it works"? — Ask what "works" cost the last time someone had to change it under time pressure — most legacy-IaC pain is invisible until an incident forces a change nobody wants to make carefully.
  • Does the migration choice between Bicep and Terraform change this pitch? — Not fundamentally — the risk-reduction argument is the same either direction; the tool choice itself should follow the decision framework earlier in this unit, made once and separately from the "should we modernize at all" argument.
  • How do you avoid a migration stalling out at "phase 1 forever"? — Tie phase 2/3 progress to a visible metric (percentage of templates still using deprecated API versions, say) reviewed periodically, not an open-ended "as time allows" commitment that competes with every sprint's feature pressure.

Wrong answer: “Propose a full rewrite in one dedicated migration project.” A big-bang rewrite competes directly with feature work for budget and is the version of this pitch most likely to be rejected or to stall halfway — incremental, opportunistic migration is both the safer technical approach and the easier one to actually get funded.

Beyond Terraform, Bicep and OpenTofu, where does Pulumi fit, and when might it be a legitimate alternative for this stack? senior

Answer. Pulumi takes a different approach entirely — infrastructure is described in a general-purpose programming language (TypeScript, Python, Go, C#, etc.) rather than a DSL, with its own state-and-plan engine conceptually similar to Terraform's (it can even use Terraform's own providers via a bridge layer for many resource types). It's a legitimate alternative specifically when a team wants infrastructure logic to use the full expressiveness of a real language — proper loops, real unit testing frameworks, IDE refactoring tools, sharing code/types with the application it provisions for — rather than HCL/Bicep's more constrained, purpose-built expression language. The trade-off is real: general-purpose language power also means general-purpose language footguns (an infrastructure definition that's accidentally Turing-complete and hard to reason about statically), and a smaller ecosystem/hiring pool than Terraform's for most organizations, which is why it's a deliberate niche choice rather than a mainstream default for a topic centered on Terraform and Bicep.

Example

const storage = new azure.storage.StorageAccount("data", {
  resourceGroupName: rg.name,
  sku: { name: "Standard_ZRS" },
  kind: "StorageV2",
});

Follow-ups

  • Does Pulumi have a state file like Terraform? — Yes, conceptually the same role, stored either in Pulumi's own managed service or a self-managed backend (including plain object storage) — the same class of concerns (locking, splitting, blast radius) apply.
  • Would you recommend Pulumi to a team already fluent in Terraform/Bicep with no other driving need? — Generally no — switching tools has real retraining and ecosystem cost, and "we'd rather write TypeScript" alone is rarely enough justification without a concrete pain point HCL/Bicep genuinely can't address.
  • Is Pulumi relevant to an Azure-only shop the way Bicep is? — Less so — its main differentiator (general-purpose language expressiveness) doesn't offset Bicep's zero-lag-on-new-APIs advantage for an Azure-only team the way it might for a genuinely complex multi-cloud, code-heavy platform.

Wrong answer: “Pulumi isn't really used anywhere serious, it's just a curiosity.” It has real production adoption, particularly among teams with strong existing investment in a specific programming language's tooling and testing ecosystem — dismissing it outright misses a legitimate, if niche, part of the current IaC landscape.

08Multi-environment & workspace strategy

Every real IaC estate has to answer "how do dev/stage/prod actually differ in the code, and how do we stop that from becoming copy-paste drift." This sub-area tests whether you know Terraform's built-in workspace mechanism well enough to know its limits, and whether you can design a directory/branching structure that scales past a handful of environments without collapsing into duplication.

Docs: Terraform workspaces · HCP Terraform workspaces

What are Terraform CLI workspaces, and why do many experienced teams deliberately avoid them for dev/stage/prod separation? senior

Answer. A CLI workspace (`terraform workspace new/select`) lets one configuration maintain multiple independent state files, distinguished only by workspace name, within the same backend — switching workspaces switches which state file subsequent commands operate against, with the workspace name available in config via `terraform.workspace`. It looks like a natural fit for dev/stage/prod at first glance, but the practical problems are real: every environment necessarily runs the exact same configuration logic (differences can only be expressed via `terraform.workspace`-conditional lookups, which get unwieldy fast), there's no way to give environments genuinely different access controls at the workspace level (anyone who can run Terraform against the config can switch to any workspace, including prod), and it's easy to forget which workspace is currently selected and apply against the wrong one — a very real, very common incident. Most experienced teams use separate root modules (directories, or in HCP Terraform separate named workspaces backed by separate configuration) per environment instead, accepting the modest duplication in exchange for independent access control, independently reviewable differences, and no "which workspace am I in" footgun.

Example

# CLI workspace footgun: easy to be in the wrong one without noticing
terraform workspace select prod
terraform apply    # ...but you meant to test something in dev
# preferred structure: separate directories, explicit, no ambiguous state
environments/
  dev/    (own backend key, own tfvars, own CI pipeline stage)
  stage/
  prod/

Follow-ups

  • Is there any legitimate use for CLI workspaces? — Yes — genuinely identical, low-stakes, ephemeral instances of the same config (a PR-preview environment spun up and torn down per pull request) where the environments really are meant to be structurally identical and short-lived.
  • How does HCP Terraform's "workspace" concept differ from CLI workspaces despite sharing the name? — An HCP Terraform workspace is a full first-class entity with its own variables, run history, access controls and often its own linked configuration — a much stronger isolation boundary than a CLI workspace's "same config, different state file" model, despite the confusingly shared name.
  • What's the CI-pipeline consequence of the separate-directory approach? — Each environment's pipeline stage explicitly points at its own directory/backend key, so there's no runtime selection step (like `workspace select`) that could target the wrong environment by mistake — the environment is baked into which pipeline stage ran, not chosen at execution time.

Wrong answer: “CLI workspaces are the standard, recommended way to manage dev/stage/prod in Terraform.” HashiCorp's own more recent guidance and most mature teams' practice favor separate configurations for anything where blast-radius separation and independent access control actually matter — CLI workspaces are a narrower-purpose tool than their name suggests.

How do you keep dev/stage/prod configuration DRY without CLI workspaces — what's the actual structure? senior

Answer. The shared logic lives in modules (the resource composition, which resources exist and how they're wired together); the per-environment variation lives entirely in a small `.tfvars` file (or, for Bicep, a `.bicepparam` file, especially now with `extends` for inheritance) per environment plus a thin root that calls the shared module with that environment's variables and its own backend configuration. The key discipline is that the environment-specific root files should be nearly all variable values and almost no logic — if an environment needs genuinely different resources (not just different sizes/SKUs), that's a signal the abstraction in the shared module needs to grow a parameter for it, rather than the environment root growing its own bespoke resource blocks that silently diverge from its siblings over time.

Example

modules/
  app-stack/           # shared logic: what resources, how wired
environments/
  dev/main.tf           # module "app" { source = "../../modules/app-stack" ... }
       dev.tfvars       # instance_size = "small", replica_count = 1
  prod/main.tf          # same module call
       prod.tfvars      # instance_size = "large", replica_count = 3

Follow-ups

  • What's the risk of environment roots drifting apart over time anyway? — Real, and the mitigation is periodic review/linting that the roots stay structurally similar (same module version, same module call shape) — automated diffing of the roots' non-tfvars content is a good CI check.
  • Should module versions differ between dev and prod deliberately? — Sometimes, briefly and intentionally — dev on a newer module version to validate an upgrade before promoting it to prod is a legitimate, controlled use of that divergence, as long as it's tracked and closed out, not left open-ended.
  • How does this map to Bicep's `.bicepparam extends`? — Directly — a `base.bicepparam` holds shared defaults, and `prod.bicepparam extends 'base.bicepparam'` overrides only what prod needs, mirroring the tfvars-per-environment pattern with less duplication than pre-`extends` Bicep required.

Wrong answer: “Just copy the whole config directory per environment and edit what's different.” That's the exact drift risk this structure exists to avoid — any shared-logic bug fix or improvement then has to be manually re-applied to every copy, and eventually they silently diverge in ways nobody remembers deciding.

How does promotion between environments actually work in a mature pipeline — what gets promoted, and what's re-validated at each stage? senior

Answer. What's promoted is the exact module version/commit — dev, stage, and prod all run the same underlying module code at a given point in time, just with different variable values; promotion is the act of pointing stage/prod's root at the commit/tag that dev already validated, not re-writing configuration per environment. What's re-validated at each stage is the plan itself: even though the code is identical, prod's actual current state is different from stage's, so prod gets its own independent `plan` reviewed and approved before its own `apply` — a green dev/stage promotion is evidence the code is probably safe, not a substitute for reviewing what it will actually do against prod's real, current resources. This is the same principle as promoting a container image through environments in application deployment — the artifact doesn't change, only the target and the review gate at each step.

Example

1. PR merges to main -> module version tagged v2.4.0
2. dev pipeline: plan+apply v2.4.0 against dev.tfvars -> automatic, low stakes
3. stage pipeline: plan+apply v2.4.0 against stage.tfvars -> automatic or lightly gated
4. prod pipeline: plan v2.4.0 against prod.tfvars -> human reviews THIS plan -> apply

Follow-ups

  • Should prod ever skip a stage that dev/stage went through? — No — the whole value of the promotion pipeline is that prod only ever receives a version that's already been exercised at least once upstream; skipping a stage under pressure is exactly how untested changes reach prod.
  • What if stage's plan is clean but prod's plan shows something unexpected? — That's the pipeline doing its job — investigate why prod's state differs enough to produce a different diff (real environment-specific drift, a variable difference with an unintended side effect) before approving, never rubber-stamp because "it worked in stage."
  • Does this model apply the same way to Bicep/ARM promotion? — Yes structurally — the same compiled template (or template spec version) gets deployed with different `.bicepparam` files per environment, with `what-if` reviewed independently at each stage exactly like Terraform's plan.

Wrong answer: “Once it's approved and applied in stage, prod can auto-apply without a separate review since it's the same code.” Same code against a different, independently-evolving set of real resources can still produce a genuinely different and risky diff — the review gate exists specifically to catch that, and skipping it defeats the purpose of having a promotion pipeline at all.

How do you structure Terraform for a genuinely large number of near-identical environments — say, 40 customer-specific deployments of the same stack? principal

Answer. At that scale, hand-maintaining 40 separate root-module directories becomes its own maintenance burden, so the usual pattern is a single generic root module parameterized by a per-customer configuration (a YAML/JSON/tfvars file per customer, or entries in a database/registry the pipeline reads from), combined with a pipeline that generates and runs one Terraform (or Terragrunt-style) invocation per customer, each with its own state key derived deterministically from the customer identifier — never one shared state across all 40. The design questions that actually matter here are: how do you roll out a module change safely across 40 independent states (typically a canary subset first, then staged rollout, never all 40 simultaneously) and how do you keep per-customer drift from a one-off support fix from silently diverging each customer's config from the shared template over time — usually solved by treating any manual per-customer override as a tracked, reviewed exception rather than an untracked hand-edit.

Example

customers/
  acme.tfvars      customer_id=acme,  tier=premium, region=westeurope
  contoso.tfvars   customer_id=contoso, tier=standard, region=eastus
  ... (38 more)
pipeline: for each customer.tfvars, terraform apply -var-file=customers/X.tfvars
          with backend key = "customers/${customer_id}.tfstate", staged rollout across a canary group first

Follow-ups

  • Does Terragrunt (or similar wrapper tooling) genuinely help here? — Yes, for exactly this "many near-identical root modules" pattern — it generates backend/provider boilerplate and orchestrates apply order across many independent Terraform runs, though it's an additional tool/dependency to weigh against the problem it solves.
  • How do you avoid a module bug taking down all 40 customers at once during rollout? — Canary a small subset first, gate the rest of the rollout on the canary's health, and never script "apply to all 40" as a single unreviewed batch operation.
  • What's the state-sprawl trade-off here versus the earlier "split state by lifecycle" guidance? — This is the same principle applied at a different granularity — each customer is its own lifecycle/blast-radius unit, so 40 separate states is the correct outcome of that principle, not an exception to it.

Wrong answer: “Use `for_each` over a map of 40 customers inside one module call, all in one state.” That reintroduces the exact monolithic-blast-radius problem from unit 01/04 at the customer level — one bad apply, one stuck lock, or one bug now risks all 40 customers simultaneously instead of one.

What's the risk of using the same Terraform state (or Bicep resource group) for a shared "sandbox" environment used by multiple engineers for ad hoc testing? mid

Answer. A shared sandbox with one state file means every engineer's ad hoc experiment is visible to and can be destructively overwritten by everyone else's — one person's `terraform destroy` of "their" test resource can be an accidental full-state destroy if the state also contains everyone else's in-progress work, and there's no natural boundary telling Terraform which resources belong to which person's experiment. The practical fix is either genuinely per-person ephemeral environments (each engineer's sandbox gets its own state, torn down automatically after a TTL) or, if a shared sandbox is truly wanted for cost/simplicity reasons, strict resource-naming/tagging conventions plus `-target`-scoped operations as the norm rather than full-state applies — with the explicit acknowledgment that this trades safety for convenience and needs a lightweight "announce before you touch shared state" social convention to back it up.

Example

Bad: sandbox/main.tf, one state, everyone applies/destroys against it ad hoc
Better: sandbox//main.tf, own state per person, auto-destroyed nightly by a scheduled pipeline

Follow-ups

  • Does an auto-destroy TTL pipeline need anything special? — Just a scheduled job running `terraform destroy` against each per-person sandbox state past its TTL — the main design point is making sandbox environments cheap enough (in state design terms) that automatic teardown is safe and unsurprising.
  • Is this the same problem as the earlier multi-team blast-radius question? — Same root cause, different context — shared state coupling unrelated parties' blast radius, whether that's production teams or engineers experimenting.
  • What's a lightweight interim fix if per-person states aren't feasible yet? — A shared Slack/chat convention plus strict resource naming (`--*`) so at least a `-target` scoped operation is easy to construct correctly, even though it doesn't remove the underlying risk.

Wrong answer: “Sandbox environments are low-stakes by definition, so state hygiene doesn't matter there.” "Low-stakes" describes the resources, not the coordination problem — losing a colleague's day of test setup to an accidental shared-state destroy is a real, avoidable cost even in a sandbox.

How would you design environment parity checks — automated detection that dev/stage/prod have silently diverged in ways that aren't intentional? senior

Answer. Separate the check into two layers. First, config-level parity: diff the actual Terraform/Bicep source (module version, module call structure, resource types used) between environment roots, ignoring known-intentional variable-value differences — a CI job that fails if stage's root calls a different module version than prod's, or has a resource block prod's root doesn't, catches structural drift before it's ever applied. Second, deployed-state parity: compare the resource inventories and key configuration attributes actually running in each environment (via `terraform show -json` diffed programmatically, or a cloud-native inventory query) to catch drift that happened outside the pipeline entirely — someone applied a hotfix directly to prod that was never backported to the module, or stage was never actually kept current despite the pipeline nominally running there too. Both checks should run on a schedule, not just at deploy time, since divergence accumulates between deploys, not only during them.

Example

# structural parity: are stage and prod running the same module version?
grep -h 'version *=' environments/stage/main.tf environments/prod/main.tf
# deployed parity: diff actual resource inventories
terraform -chdir=environments/stage show -json | jq '.values.root_module.resources[].type' | sort > stage.txt
terraform -chdir=environments/prod  show -json | jq '.values.root_module.resources[].type' | sort > prod.txt
diff stage.txt prod.txt

Follow-ups

  • What's an intentional difference this shouldn't flag as a false positive? — Variable-value differences that are supposed to differ (instance sizes, replica counts) — the check needs to specifically target structural/version parity, not literal attribute-value equality, or it's noisy enough to get ignored.
  • How does this relate to drift detection from unit 01? — Complementary, different axis — drift detection compares one environment's config against its own deployed reality; parity checking compares multiple environments against each other, catching a different class of problem (intentional-looking divergence between environments rather than unplanned divergence within one).
  • What's the actual organizational payoff of catching this early? — Avoiding the classic "it worked in stage" surprise, where prod fails not because the change was wrong but because prod had already silently diverged from stage in some unrelated way nobody had tracked.

Wrong answer: “As long as the same pipeline deploys to every environment, they can't diverge.” The pipeline enforces parity only for changes that go through it — a manual hotfix, a console change, or an environment that stopped receiving deploys for a while all diverge outside the pipeline's view entirely.

09Testing, policy-as-code & CI/CD

This sub-area separates candidates who ship IaC changes through a disciplined pipeline from those who "run apply locally and hope." Expect questions on what's actually testable in IaC (it's not application code, so the testing pyramid looks different), where policy-as-code sits in the pipeline relative to plan/apply, and what a healthy CI/CD gate structure looks like end to end.

Docs: Terraform test · Open Policy Agent

What does "testing" mean for IaC, given there's no business logic to unit-test the way there is in application code? mid

Answer. IaC testing splits into a few distinct layers rather than one pyramid: static/lint checks (does the syntax parse, does it follow style/security conventions — `terraform validate`, `tflint`, the Bicep linter — fast, no cloud calls, run on every commit); plan-level checks (does the diff do what's expected, does it avoid destructive changes to protected resources — increasingly automatable via `terraform test`'s plan-only mode or policy-as-code against the plan JSON); and actual apply-level tests (`terraform test` with real provider blocks, or a full ephemeral-environment apply-then-assert-then-destroy cycle, which genuinely provisions resources and checks their real properties). The last category is the closest thing to a "real" test and also the most expensive — it costs cloud spend and time — so it's used more sparingly, typically for the modules that are reused often enough that a regression would be expensive, not for every leaf configuration.

Example

Fast, every commit:   terraform validate, tflint, bicep lint / bicep build --stdout
Plan-level, every PR:  terraform plan (reviewed diff), policy-as-code against plan JSON
Apply-level, module CI: terraform test with real provider blocks (provisions + destroys)

Follow-ups

  • Should every module have apply-level tests? — Not necessarily — reserve them for modules with real reuse and real blast radius if they regress; a one-off leaf configuration used by a single team is usually adequately covered by lint + plan review.
  • Is `terraform plan` itself a form of test? — Functionally yes — it's the single most valuable "test" in the whole pipeline, since it's the actual diff a human or policy engine reviews before anything real happens.
  • How does this map to Bicep? — Same shape — `bicep lint`/`bicep build` for static checks, `what-if` for the plan-level review, and actual deployment to an ephemeral resource group for the apply-level check.

Wrong answer: “IaC doesn't really need testing beyond checking it applies without errors.” A clean apply proves the syntax was valid and the API calls succeeded — it proves nothing about whether the result is what was intended (wrong SKU, missing NSG rule, a resource left publicly accessible), which is exactly what plan review and policy checks exist to catch.

Walk through how `terraform test` actually works, including its mock-provider capability. senior

Answer. `terraform test` (stable since 1.6, mid-2023) runs `.tftest.hcl` files that define one or more `run` blocks against the module under test, each specifying a command (`plan` or `apply`), variable values, and `assert` blocks checking conditions against the plan or resulting state/outputs. Since 1.7, a `mock_provider` block lets a test fake an entire provider's behavior — returning synthetic resource attributes without ever calling a real cloud API — which makes plan-level assertions (does the module produce the resource count and configuration you expect) fast and free to run on every PR, reserving genuine `apply`-mode runs against real providers for slower, less frequent test suites where you actually need to verify real-world provider behavior, not just your module's own logic.

Example

run "creates_expected_replica_count" {
  command = plan
  variables { replica_count = 3 }
  assert {
    condition     = length(azurerm_linux_web_app.this) == 3
    error_message = "expected 3 web app replicas"
  }
}

mock_provider "azurerm" {}   # no real API calls; synthetic attribute values

Follow-ups

  • What's the trade-off of mock providers versus real ones in tests? — Mocks test your module's own logic (does it wire variables into the right resource shape) fast and free; real providers additionally validate that the actual API accepts what you're sending, which mocks cannot catch.
  • What did the 1.7 `skip_cleanup` / test-cleanup improvements add? — A way to leave apply-mode test resources standing after a failed test run specifically for debugging, instead of tearing them down immediately and losing the evidence of what went wrong.
  • Can `terraform test` replace policy-as-code checks? — No — tests verify your module behaves as its author intended; policy-as-code verifies an actual deployment plan complies with organization-wide rules regardless of which module produced it — different scope, both needed.

Wrong answer: “`terraform test` is just a wrapper around running `terraform apply` and checking the exit code.” It's a structured assertion framework against plan/state/output values, with a native mocking capability specifically so most tests never need to touch a real provider at all — much richer than an apply-and-check-exit-code script.

What is policy-as-code, and where does it fit relative to `plan` and `apply` in a pipeline? senior

Answer. Policy-as-code is expressing organizational rules — no public storage accounts, all resources must carry a cost-center tag, only approved VM SKUs — as machine-checkable code (Open Policy Agent/Rego, HashiCorp Sentinel, Azure Policy, or provider-specific tools) evaluated automatically against a plan before apply, rather than relying on manual review to catch every violation by eye. It sits between `plan` and `apply` as an automated gate: the plan's JSON output (or, for Azure, the `what-if` result) is fed to the policy engine, which either passes, fails hard (blocking apply entirely for a hard-mandatory rule), or produces an advisory warning that a human can override with justification — mirroring the "advisory vs mandatory" distinction many policy frameworks make explicitly. This catches violations mechanically and consistently, at the exact point where they're cheapest to fix (before anything is actually provisioned), rather than depending on every reviewer remembering every rule.

Example

terraform plan -out=plan.tfplan
terraform show -json plan.tfplan > plan.json
opa eval -i plan.json -d policies/ "data.terraform.deny"   # fails pipeline if non-empty
deny[msg] {
  resource := input.resource_changes[_]
  resource.type == "azurerm_storage_account"
  resource.change.after.network_rules[0].default_action == "Allow"
  msg := sprintf("storage account %v must default-deny network access", [resource.address])
}

Follow-ups

  • How does this differ from Azure Policy applied directly to a subscription? — Azure Policy enforces at the ARM API layer regardless of what deployed the resource (Bicep, Terraform, portal, anything) and can be set to deny at admission time; pipeline-level policy-as-code checks the plan before it's even submitted, giving faster, more specific feedback earlier, and the two are commonly used together, not as alternatives.
  • What's a real cost of a hard-mandatory policy gate? — A legitimate edge-case deployment can get blocked with no easy override path, so mandatory rules need a genuinely rare, well-justified scope, with an advisory tier for everything else.
  • Does policy-as-code need to see the full plan, or can it work off just the diff? — Needs the full resulting plan (not just the diff) for most useful rules, since many checks are about the resource's final state, not what specifically changed to get there.

Wrong answer: “Policy-as-code is basically the same thing as `terraform test`.” Tests check a module behaves as its author intended; policy-as-code checks any plan, from any module, against organization-wide rules the module's author may not even be aware of — they operate at different scopes and neither substitutes for the other.

Design a CI/CD pipeline for Terraform changes from PR to production apply. What are the gates, in order? senior

Answer. On PR open: format check (`terraform fmt -check`), `terraform validate`, `tflint`, and a `terraform plan` posted as a PR comment for human review — nothing applies yet. On PR approval and merge: policy-as-code evaluation against the merged plan, then apply to dev automatically (low stakes, fast feedback). Promotion to stage runs the same plan-review-policy sequence against stage's own state, typically automatically gated only by dev's success. Promotion to prod repeats the sequence one more time — plan generated, policy-as-code evaluated, and critically a human approval step before the actual `apply` — since prod is the one stage where an automated green light is deliberately not sufficient on its own. Locking (unit 04) needs to be respected throughout so concurrent PRs against the same state can't race each other's applies.

Example

PR opened  -> fmt, validate, tflint, plan (posted for review)         [no apply]
PR merged  -> policy-as-code check -> apply to dev                    [automatic]
             -> plan+policy vs stage -> apply to stage                [automatic, gated on dev]
             -> plan+policy vs prod -> HUMAN APPROVAL -> apply to prod [manual gate]

Follow-ups

  • Why review the plan at PR time if the actual apply happens later at merge? — The state can have moved between PR review and merge (another change applied in the meantime), so the plan reviewed at PR time is informative but not authoritative — a fresh plan must be regenerated and, ideally, re-reviewed at each subsequent promotion stage against current state.
  • Should the same pipeline definition serve dev, stage, and prod, or separate ones? — Same definition, parameterized by environment (see unit 08) — a separate pipeline per environment risks the pipelines themselves silently diverging, defeating the purpose of a consistent promotion path.
  • What CI-runner-identity concern applies to the apply step specifically? — The credentials/identity the pipeline apply step runs as should be scoped as tightly as the environment it targets (see unit 10) — a single overly-broad CI identity used for every environment reintroduces the blast-radius problem this whole pipeline design exists to contain.

Wrong answer: “Have the pipeline auto-apply to every environment including prod as soon as tests pass, to move fast.” Removing the human approval gate specifically at prod is exactly the tradeoff a mature pipeline design refuses to make — the earlier stages exist to make the prod gate a formality most of the time, not to make the prod gate itself removable.

How would you test a Bicep module's correctness before it's ever deployed to a real subscription? mid

Answer. `bicep build` (or `bicep build --stdout`) compiles to ARM JSON and fails on syntax errors, catching the fastest class of mistake; the Bicep linter (configurable via `bicepconfig.json`) catches style and common-mistake rules (unused parameters, insecure defaults) without deploying anything. Beyond static checks, `az deployment group what-if` against a real (ideally disposable/ephemeral) resource group is the closest equivalent to Terraform's plan review — it shows exactly what would be created/modified/deleted without doing it. For genuine apply-level verification, an actual deployment to a scratch resource group followed by assertions against the deployed resources (via Azure CLI queries or ARM REST calls) and teardown is the Bicep-side equivalent of `terraform test`'s apply mode — there's no first-party unit-test framework built into Bicep itself the way `terraform test` is built into Terraform, so this layer is typically hand-rolled with scripting around the CLI.

Example

bicep build main.bicep --stdout > /dev/null   # syntax check
bicep lint main.bicep                          # style/security lint
az deployment group what-if -g scratch-rg -f main.bicep -p main.bicepparam
az deployment group create -g scratch-rg -f main.bicep -p main.bicepparam   # then assert + delete

Follow-ups

  • Is there a Bicep-native equivalent of mock providers? — Not a first-party one — `what-if` is the closest no-real-deployment check, but it still calls the real ARM API to compute the diff, unlike Terraform's fully offline mock-provider tests.
  • Does AVM (Azure Verified Modules) publish its own tests? — Yes — AVM modules include their own test fixtures and CI validation as part of the module publication standard, which is part of the trust argument for using AVM over a hand-rolled equivalent.
  • How would you keep scratch-resource-group apply tests cheap? — Small, minimal-SKU test resources, aggressive teardown immediately after assertions run, and reusing one scratch resource group across a test suite rather than provisioning a fresh one per test case.

Wrong answer: “Bicep doesn't really need testing since ARM validates the template at deployment time anyway.” ARM's deployment-time validation catches malformed templates, not logic errors (wrong SKU, missing required config, an insecure default) — exactly the class of mistake `what-if` review and scripted apply-level assertions exist to catch before they reach a real environment.

What's the difference between "advisory" and "mandatory" policy violations, and why does that distinction matter for adoption? senior

Answer. A mandatory policy blocks the pipeline outright — no apply proceeds until the violation is fixed, reserved for rules where the cost of a violation reaching production is severe and unambiguous (public exposure of a data store, disabled encryption). An advisory policy surfaces a warning, requires the author (or an approver) to acknowledge or justify it, but doesn't block progress — used for rules that are usually right but have legitimate exceptions (a naming convention, a recommended-but-not-required SKU tier). The distinction matters for adoption because an organization that makes everything mandatory from day one either grinds legitimate work to a halt on edge cases nobody anticipated, or trains engineers to route around the policy engine entirely (a well-known failure mode); starting most new rules as advisory, watching real violation patterns, and promoting only the rules that prove both correct and exception-free to mandatory status builds trust in the system instead of resentment toward it.

Example

Mandatory: deny public network access on a database resource     -> blocks apply, no override
Advisory:  warn if a resource is missing a recommended cost tag   -> logged, requires ack, proceeds

Follow-ups

  • Who decides when an advisory rule graduates to mandatory? — Usually a platform/governance team reviewing violation history — if a rule has near-zero legitimate exceptions in practice over a meaningful period, it's a good mandatory candidate; if exceptions are common, the rule itself may need refining first.
  • Does every organization need both tiers from day one? — Not necessarily day one, but designing the policy engine to support both from the start avoids a painful later migration once the all-mandatory approach starts causing friction.
  • How does this map to Azure Policy's effect types? — Directly — Azure Policy's `Audit`/`AuditIfNotExists` effects are the advisory tier, `Deny` is the mandatory tier, and `DeployIfNotExists` is a third category (auto-remediation) beyond this simple two-tier model.

Wrong answer: “Every policy should be mandatory — otherwise what's the point of having it?” An advisory policy still has real value: visibility, trend data, and a forcing function for justification — treating "not blocking" as "not enforcing" misunderstands why the two-tier model exists at all.

A pipeline run fails midway through `terraform apply` for a change touching 15 resources. What's your incident response, and how do you prevent the pipeline from making it worse? senior

Answer. First, don't auto-retry blindly — a failed apply mid-run (unit 02) usually leaves state accurately reflecting a mix of applied and not-yet-applied resources, and a naive automatic retry without understanding why it failed can compound the problem if the failure was something structural (a quota limit, a conflicting concurrent change) rather than transient. The immediate steps: pull the actual error from pipeline logs, run `terraform plan` against current state to see exactly what's now pending (Terraform's own bookkeeping tells you precisely what succeeded and what didn't — you don't have to guess), and decide whether the fix is a transient-retry (rerun apply, likely the API had a blip), a config fix (the plan itself needs a change to unblock, e.g. a quota-driven SKU adjustment), or a rollback (revert the merge, plan again, apply the revert). Prevention going forward: keep changes reasonably small (a 15-resource simultaneous change is already a wider blast radius than ideal — see unit 04/11 on splitting state and staged rollout) and make sure the pipeline surfaces the specific failed resource clearly rather than a generic failure so the next responder doesn't have to reconstruct it from raw logs.

Example

terraform plan   # shows exactly which of the 15 already applied vs still pending
# then: retry apply, fix-and-replan, or revert-and-replan, based on WHY it failed

Follow-ups

  • Should the pipeline auto-rollback on any apply failure? — Generally no as a blanket policy — an automatic revert-and-reapply on a partially-applied state can itself be destructive if it's not clear what "revert" even means for the already-applied subset; a human decision at this specific juncture is usually safer than a scripted one.
  • How does this connect to the earlier "keep changes small" guidance? — Directly — a 3-resource change failing partway is a much smaller, easier-to-reason-about mess than a 15-resource one, which is one more argument (beyond blast radius) for keeping individual changes narrow.
  • What alerting should exist so this doesn't get discovered hours later? — The pipeline should page/notify on any apply failure immediately, not just on a scheduled drift-detection run — the gap between "apply failed" and "someone noticed" is itself a real risk window.

Wrong answer: “Just re-run the pipeline until it succeeds.” Blind retries without reading why it failed risk retrying a structural failure repeatedly (wasting time) or, worse, applying a change that's no longer correct given what partially succeeded — always plan first to see current reality before deciding the next action.

How do you avoid CI/CD pipeline credentials themselves becoming the biggest security risk in the whole IaC setup? senior

Answer. The pipeline's apply-time credentials are functionally the most powerful credentials in the entire system — whatever the pipeline can provision, so can anyone who compromises it — so they need the same scrutiny as any other privileged credential, generally more than most teams initially give them. Concretely: use short-lived, workload-identity-federated credentials (OIDC-based, e.g. GitHub Actions' or Azure DevOps' native federation to Azure AD/Entra ID) instead of long-lived static secrets stored in pipeline variables, scope the pipeline's identity per environment (a dev-pipeline identity should not have prod permissions, ever — see unit 10), and make sure pipeline configuration changes (which is itself often just more code in the same repo) go through the same review gate as the infrastructure code it deploys, since a malicious or careless pipeline-config change can grant itself broader access silently.

Example

# GitHub Actions + Azure OIDC federation: no static secret stored anywhere
permissions:
  id-token: write
steps:
  - uses: azure/login@v2
    with:
      client-id: ${{ vars.AZURE_CLIENT_ID }}
      tenant-id: ${{ vars.AZURE_TENANT_ID }}
      subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      # no client-secret: short-lived federated token instead

Follow-ups

  • Why is workload identity federation better than a long-lived service principal secret? — No secret to leak, rotate, or accidentally commit — the token is issued per run, short-lived, and cryptographically tied to the specific pipeline run's identity claims, which also makes it auditable which exact run used it.
  • Should the same service principal/identity be used across dev, stage, and prod pipelines? — No — separate identities scoped to each environment's actual permissions, so a compromised dev pipeline identity can't touch prod even if the pipeline definitions are similar.
  • Who should be able to modify the pipeline definition itself? — The same review rigor as production infrastructure changes — pipeline-as-code is still code, and a permissive pipeline-definition change process is a direct path to privilege escalation.

Wrong answer: “Store the cloud credentials as an encrypted pipeline secret and rotate them periodically.” Even encrypted-at-rest, a long-lived static secret is a standing target and a rotation burden; short-lived federated identity removes the long-lived-secret problem entirely rather than just mitigating it.

10Security, secrets & governance

IaC concentrates a huge amount of privilege into whatever runs it, so this sub-area probes whether a candidate treats that privilege with appropriate care: least-privilege identity design, real secret handling (not "put it in a variable and hope"), and organization-wide guardrails that scale beyond any one team remembering to do the right thing.

Docs: Azure RBAC overview · Terraform sensitive values

What identity should Terraform (or a Bicep deployment) actually run as, and how do you scope its permissions? senior

Answer. Never a personal user credential and never a single broad "owner on everything" service principal used everywhere — the identity running IaC should be a dedicated service principal (Azure) or equivalent per environment, scoped via RBAC to exactly the resource groups/subscriptions that environment's configuration is meant to touch, with the permission level (Contributor vs a narrower custom role) matched to what the configuration actually creates rather than granted generously "to avoid friction." Practically this means dev's pipeline identity cannot reach prod's resource groups at all, even if the same person triggers both pipelines, and a compromised or misconfigured dev pipeline run has no path to touch production regardless of what the Terraform/Bicep code says — the RBAC boundary is the actual enforcement, not the code's good behavior.

Example

sp-terraform-dev   -> Contributor scoped to rg-dev-*  only
sp-terraform-prod  -> Contributor scoped to rg-prod-* only
                    (neither can see or touch the other's resource groups)

Follow-ups

  • Why not just use Owner for simplicity and avoid permission-denied surprises during development? — Owner includes access-management rights (granting others access), which is far more than provisioning needs and turns a compromised pipeline identity into a path to broader privilege escalation, not just resource creation.
  • How do you handle a module that legitimately needs cross-resource-group access (e.g. writing DNS records in a shared zone)? — Grant that specific narrow permission (a custom role scoped to just the DNS zone) rather than widening the whole identity's scope — the exception should be as narrow as the actual need.
  • Does this scoping model apply the same way to OpenTofu or Pulumi? — Yes — the principle is tool-agnostic; whatever executes the provisioning needs its own scoped identity per environment, regardless of which IaC tool is running.

Wrong answer: “Give the CI pipeline's service principal Owner on the whole subscription so nothing ever breaks from a permissions issue.” That converts a permissions inconvenience during development into a standing, subscription-wide privilege-escalation risk in production — exactly backwards from where the friction should be tolerated.

Terraform state can contain secrets in plaintext. Walk through why, and how you actually mitigate it. senior

Answer. State records every attribute of every managed resource so Terraform can compute future diffs, and that includes attributes a provider returns as sensitive — a database admin password set via a resource argument, a generated API key — regardless of whether the corresponding variable was marked `sensitive = true` in the configuration (that flag only suppresses console/plan output, it does not encrypt or omit the value from state itself, a very common misconception from unit 03). The real mitigations layer: prefer not putting secrets into Terraform-managed attributes at all where possible (write-only arguments, unit 04, exist specifically to let a value be used during apply without ever being persisted to state); where a secret genuinely must live in state, use state encryption (1.10+) or an encrypted-at-rest backend and tightly scoped access to the state store itself; and treat anyone with read access to state as having read access to every secret it contains, which should shape who gets that access at all.

Example

resource "azurerm_mssql_server" "db" {
  administrator_login_password = var.admin_password   # sensitive = true only hides CLI/plan output
}                                                        # the value is still stored in plaintext in state
# better: write-only argument (1.11+) — never persisted to state at all, see unit 04

Follow-ups

  • Does moving to a remote backend fix this automatically? — Only the "who can read the state file" access-control half — the value is still in the state's plaintext (or encrypted, if 1.10+ state encryption is configured) content; a remote backend just changes where and how access to that content is controlled.
  • What's the actual relationship between write-only arguments and state encryption? — Complementary — write-only arguments avoid persisting a secret at all; state encryption protects whatever's left in state (including secrets that couldn't avoid being persisted, or non-secret-but-still-sensitive attributes) at rest.
  • Should secrets be pulled from a vault at apply time instead of passed as tfvars? — Yes, generally preferred — a data source reading from Key Vault/a secrets manager at plan/apply time avoids the secret ever sitting in a `.tfvars` file, CI variable, or command-line history, narrowing where it's exposed even before state is considered.

Wrong answer: “Marking a variable `sensitive = true` keeps it out of the state file.” It only redacts CLI/plan/apply output — the value is still written to state in full; this is one of the most common and consequential misconceptions about Terraform secret handling.

How should Terraform or Bicep retrieve secrets from a vault (Azure Key Vault, HashiCorp Vault) — what's the safe pattern versus the tempting-but-wrong one? senior

Answer. The safe pattern is a data source (Terraform's `azurerm_key_vault_secret` data source, or Bicep's `Microsoft.KeyVault/vaults/secrets` `existing` reference used inside a `@secure()` parameter default) that reads the secret's current value at plan/apply time and feeds it directly into whatever resource argument needs it, ideally one that's also a write-only argument or otherwise never persisted further than necessary. The tempting-but-wrong pattern is retrieving the secret once, writing it into a `.tfvars`/parameter file or a CI pipeline variable "for convenience," and then having that copy live indefinitely somewhere with weaker access controls and no rotation awareness than the vault itself — every additional place a secret's value is copied to is another place it can leak from, and a vault-backed data source keeps there being exactly one source of truth with its own access logging.

Example

data "azurerm_key_vault_secret" "db_password" {
  name         = "db-admin-password"
  key_vault_id = data.azurerm_key_vault.this.id
}
resource "azurerm_mssql_server" "db" {
  administrator_login_password_wo         = data.azurerm_key_vault_secret.db_password.value
  administrator_login_password_wo_version = 1
}

Follow-ups

  • What access does the pipeline identity need for this to work? — Key Vault "get secret" access scoped to exactly the secrets it needs, via Azure RBAC or Key Vault access policy — not blanket Key Vault Contributor, which would let it manage the vault itself, not just read from it.
  • Does this still leave the secret's value in the plan output? — Terraform marks values sourced from a `sensitive` data source as sensitive in CLI/plan output automatically in most cases, but always verify — an unmarked custom output that echoes the value would still leak it into logs.
  • How does secret rotation interact with this pattern? — Cleanly — since the value is fetched fresh at each plan/apply rather than copied statically, a rotated secret in the vault is picked up on the next run without any pipeline-variable update needed.

Wrong answer: “Fetch the secret from the vault once and store it as a CI/CD pipeline variable so every run doesn't need vault access.” That defeats the entire purpose of centralizing the secret in a vault — you now have a second, less-controlled, rotation-unaware copy of the same secret sitting in pipeline configuration.

How do you enforce tagging, naming, and resource-type standards across many teams' IaC without a full-time enforcement team reviewing every PR? senior

Answer. Push the standard as far left (early) and as automated as possible rather than relying on human review to catch it every time: shared modules that bake required tags/naming into the resource definition itself so an individual team's config can't omit them without deliberately overriding a default, a linter rule (`tflint`, Bicep linter custom rules) that fails CI on a missing/malformed tag, and a policy-as-code check (unit 09) as the final automated backstop before apply. Azure Policy with `DeployIfNotExists` or `Modify` effects adds a fourth layer that catches anything that slipped through all of the above by auto-remediating (adding the missing tag) or denying at the ARM API level regardless of which tool deployed the resource. The combination matters because no single layer is complete — a team can bypass a shared module by not using it, bypass a linter by disabling the rule locally, but Azure Policy at the API layer is very hard to route around since it applies to the actual resource creation call itself.

Example

Layer 1 (module default):   shared module sets required tags unless explicitly overridden
Layer 2 (CI lint):           tflint/bicep-lint rule fails build if required tag missing
Layer 3 (policy-as-code):    plan-time check denies apply if tag absent
Layer 4 (Azure Policy):      DeployIfNotExists auto-adds tag; Deny blocks non-compliant creation at the API

Follow-ups

  • Which layer should be considered the actual source of truth for compliance? — Azure Policy (or the cloud-native equivalent) at the API layer — it's the one layer nothing can bypass by skipping a tool or process step, since it evaluates the real resource-creation call.
  • Isn't four layers excessive for something as simple as a tag? — Each layer catches a different failure mode cheaply and early — the cost of running a linter rule is near zero, and catching a violation at PR time is far cheaper than catching it after the fact via policy remediation.
  • How do you roll out a new mandatory tag requirement without breaking every existing team's pipeline overnight? — Advisory first (unit 09's advisory/mandatory distinction), a grace period with visible warnings, then promote to mandatory once teams have had a real chance to comply.

Wrong answer: “Document the tagging standard in a wiki page and ask teams to follow it.” Undocumented enforcement (i.e., only a wiki page and goodwill) reliably decays as teams turn over and deadlines pressure — every layer above exists precisely because unenforced documentation doesn't scale.

What's the blast radius of a leaked Terraform Cloud/HCP Terraform API token or a leaked Azure service principal secret used by a pipeline, and how do you limit it? senior

Answer. The blast radius is exactly the scope of what that credential can do — an HCP Terraform token tied to a workspace with apply permissions on a production configuration means whoever holds it can trigger applies (or read state, including any secrets in it) against that production environment; an Azure service principal secret with Contributor on a subscription means the same for every resource in that subscription. Limiting it starts upstream of the leak itself: short-lived/federated credentials (unit 09) so there's nothing long-lived to leak in the first place, least-privilege scoping (this unit's first question) so even a successful leak has a bounded scope, and secret-scanning on the repo/pipeline-config itself to catch an accidental commit before it's exploited. If a leak does happen, the response is immediate revocation/rotation of the specific credential, an audit of what that credential was used for during the exposure window (cloud audit logs, HCP Terraform's run history), and treating anything it could have touched as needing a trust review, not just a rotation.

Example

Leaked: sp-terraform-prod secret, scoped to rg-prod-* with Contributor
Response: 1) revoke/rotate the secret immediately
          2) audit Azure AD sign-in + resource activity logs for the exposure window
          3) review every resource in rg-prod-* for unexpected changes
          4) root-cause how it leaked (committed secret? CI log exposure?) and close that gap

Follow-ups

  • Why does workload identity federation reduce this risk category almost entirely? — There's no long-lived secret value to leak at all — the federated token is issued per-run and expires quickly, so even capturing one from a compromised log has a narrow, time-boxed usefulness.
  • What's the specific extra risk of a leaked HCP Terraform token versus a leaked cloud credential? — It can expose state content directly (including any secrets state contains, unit 10's earlier point) even if the underlying cloud credential itself is separately scoped tightly — state read access is its own blast-radius category.
  • Should secret-scanning run on every commit or only periodically? — Every commit/push, as a pre-merge CI gate — catching a committed secret before merge (and ideally before push completes) is far cheaper than finding it days later after it's already been exposed in history.

Wrong answer: “Rotating the leaked credential after the fact is sufficient response.” Rotation stops further use of that specific credential but doesn't address what was already done with it during the exposure window — an audit of actual activity during that window is the step that catches whether real damage already occurred.

How do you design least-privilege access for engineers who need to run `terraform plan`/`apply` locally, without giving everyone standing production credentials? principal

Answer. The general answer is to make production apply access a pipeline-only capability, not something any individual engineer holds as a standing credential at all — engineers get read/plan access (useful for investigation and drafting changes) scoped to non-prod, and any prod change flows through the reviewed pipeline described in unit 09, with the human approval gate substituting for "an engineer with prod credentials decided to run apply." Where a genuine break-glass need exists (an incident requiring an immediate manual change prod's normal pipeline can't move fast enough for), use just-in-time elevated access (Azure PIM-style time-boxed role activation, logged and often requiring a second approver) rather than a standing credential — the access exists only for the window it's actually needed and is automatically revoked afterward, with the activation itself creating an audit trail.

Example

Everyday: engineers have Reader on prod, Contributor on their own dev sandbox
Change:   flows through pipeline (unit 09) with its own scoped, non-personal identity
Incident: PIM-style time-boxed elevation to Contributor on prod, auto-expires, logged, second approver

Follow-ups

  • Doesn't this slow down incident response when every minute counts? — A well-designed break-glass flow (pre-approved role, one-click activation, expiring automatically) is fast in practice — the goal is removing standing risk, not adding bureaucratic friction to the moment it's needed most.
  • What should be logged about a break-glass activation? — Who activated it, when, the stated justification, what was changed during the window, and when it expired/was revoked — enough to fully reconstruct the incident response afterward without relying on memory.
  • Does this model conflict with engineers needing to debug a real prod issue interactively? — Reader access covers most debugging (inspecting current resource state, logs, metrics) without needing write access at all — write access is the specific thing being gated, not all prod visibility.

Wrong answer: “Give senior engineers standing Contributor access to production so they can respond quickly when needed.” Standing broad access for convenience is exactly the pattern least-privilege design tries to eliminate — just-in-time elevation gets the same responsiveness without the permanent exposure of a credential that's powerful nearly all the time it's not being used.

What governance concerns come up specifically when a platform team publishes shared modules (or AVM modules) for other teams to consume — beyond the module's own correctness? senior

Answer. Version-pinning discipline across consumers — if every consuming team pins loosely (`>= 1.0`) rather than to a tested version, a module publisher's breaking change can silently ripple across every consumer simultaneously with no coordinated rollout; the platform team needs to both publish clear semantic-versioned releases and encourage (or enforce via linting) that consumers pin deliberately. Supply-chain trust for the module registry itself — who can publish under the organization's module namespace, whether publishes are reviewed, whether a compromised publishing credential could push a malicious module version that every consumer's next `terraform init` would pull. And deprecation lifecycle — a module the platform team wants to retire or substantially change needs a communicated migration path and a realistic timeline, not an abrupt removal that breaks every consumer's next init with no warning.

Example

module "network" {
  source  = "app.terraform.io/org/network/azurerm"
  version = "~> 2.3.0"   # deliberate pin, not ">= 1.0" — reviewed before bumping
}

Follow-ups

  • How does AVM address the supply-chain trust concern specifically? — Publication under Microsoft/community-governed standards with defined review and testing requirements before a module is accepted as "verified" — reducing (though not eliminating) the "who can push what" trust question relative to an arbitrary internal registry with looser controls.
  • What's a practical way to catch consumers on an unpinned or dangerously wide version constraint? — A periodic automated scan across the organization's repos for module version constraints, flagging anything wider than a minor-version pin for review — the same kind of drift/parity check discussed in unit 08 applied to dependency hygiene.
  • Should breaking changes ever ship as a version bump without a major-version increment? — No — strict adherence to semantic versioning is exactly what lets consumers trust a pin like `~> 2.3.0` to be safe to auto-update within that range; violating semver breaks the entire trust model this whole practice depends on.

Wrong answer: “Once a shared module is published and works, governance is done — it's just a technical artifact like any other.” A widely-consumed shared module is closer to a dependency an entire organization runs on — its versioning discipline, publishing trust model, and deprecation process are ongoing governance responsibilities, not a one-time technical concern.

A junior engineer asks why the team bothers with all this — RBAC scoping, vault-backed secrets, policy-as-code — instead of just being careful. How do you explain the underlying principle? screener

Answer. "Being careful" doesn't scale and doesn't survive the cases that actually cause incidents — a tired engineer at the end of a long day, a new hire who hasn't yet learned every unwritten rule, a one-off urgent fix under pressure. Every mechanism in this unit exists to make the safe behavior the automatic one rather than the remembered one: least-privilege access means a mistake has a bounded blast radius even when it happens; vault-backed secrets mean there's no plaintext copy sitting around for a moment of carelessness to expose; policy-as-code catches a violation mechanically and consistently, every single time, regardless of who's reviewing or how careful they were feeling that day. The underlying principle is designing systems that are safe by default and hard to misuse, rather than systems that are safe only when everyone using them is simultaneously careful, well-rested, and fully informed — which is never true of every person, every time, forever.

Example

"Careful" fails when: someone's tired, new, rushed, or simply wrong about a rule they never learned.
Structural controls (RBAC scope, vault, policy-as-code) don't depend on anyone being careful at all.

Follow-ups

  • Isn't this overhead frustrating for experienced engineers who really would be careful? — Some friction is real and worth minimizing where possible, but the controls aren't there because any one person is untrusted — they're there because the system as a whole includes people who will, eventually and inevitably, not be careful in some specific moment.
  • Does this reasoning apply outside IaC too? — Yes — it's the same argument behind code review, automated testing, and least-privilege access generally in software engineering; IaC just concentrates unusually high blast radius per mistake, which raises the stakes.
  • What's a good way to introduce this mindset without sounding paranoid to a junior engineer? — Frame it as "make good behavior the path of least resistance" rather than "assume everyone will fail" — the goal is removing friction from doing the right thing, not just adding friction to doing the wrong thing.

Wrong answer: “It's mostly about compliance checkboxes and audit requirements, not real risk.” Treating governance controls as a paperwork exercise misses that they're the actual mechanism preventing routine human variability from becoming an incident — audits are a downstream benefit, not the primary reason these controls exist.

11Scale, incident command & operational judgment

At the senior/principal level, interviewers want to see how you behave when IaC itself is the thing on fire — a bad apply mid-flight, a state file that's inconsistent with reality, a change that looked safe in review but wasn't. This sub-area is scenario-heavy: the "right" answer is less about a specific command and more about the sequence of judgment calls that keeps a bad situation from becoming a worse one.

Docs: Terraform apply · ARM deployment history

A production `terraform apply` is 20 resources into a 30-resource change when it hangs — no output, no error, for ten minutes. What do you do? senior

Answer. First, don't kill the process reflexively — a hang usually means Terraform is waiting on a slow cloud API call (a resource genuinely taking a long time to provision, or an API throttling response) rather than being stuck in a bad state, and killing it mid-operation can leave the state lock held and the in-flight resource's state inconsistent with reality. Check what's actually happening first: cloud-provider-side activity logs/portal for the specific resource type being created, whether the provider is emitting any debug logging (`TF_LOG=debug` if this is reproducible), and how long that resource type has legitimately taken to provision before (some resources, like certain database SKUs or CDN endpoints, genuinely take many minutes). If it's confirmed stuck rather than slow — the cloud side shows no in-progress operation at all — only then consider interrupting, and immediately follow up with `terraform plan` (or `force-unlock` if the lock survived the interrupt) to see exactly what state believes happened versus what actually exists before touching anything further.

Example

# while waiting: check the cloud side, not just the CLI
az resource show --ids  --query properties.provisioningState
# only after confirming it's genuinely stuck, and only if needed:
terraform force-unlock 
terraform plan   # see what state now believes vs what's real, before any further action

Follow-ups

  • What's the risk of killing the process too early? — The resource being created might complete on the cloud side moments later, leaving state unaware of a resource that now exists (drift) or, worse, in a half-written state entry that confuses the next plan.
  • Should you have alerting for "apply has been running longer than N minutes"? — Yes — a duration-based alert on pipeline apply steps catches this class of situation proactively rather than someone happening to notice a stuck terminal.
  • Does this reasoning change if it's a Bicep/ARM deployment instead? — Same principle — check ARM's deployment operations/activity log for the specific operation's real status before assuming the CLI/portal is simply unresponsive; ARM deployment history is authoritative about what's actually happening server-side.

Wrong answer: “Kill the terminal and re-run apply — it'll pick up where it left off.” Terraform will indeed resume based on state on a re-run, but killing the process without first checking whether the in-flight operation actually completed on the cloud side risks a state/reality mismatch that a blind re-run won't detect or fix on its own.

Post-incident, you discover the last three `terraform apply` runs in production silently ignored a policy-as-code warning that should have blocked them. How do you investigate and prevent recurrence? principal

Answer. First establish exactly what happened mechanically — was the policy check misconfigured to be advisory when it should have been mandatory (unit 09/10's distinction), did the pipeline have a code path that let apply proceed despite a failed policy check (a bug in the gate itself), or did someone override an advisory warning through a legitimate but unaudited path. Each of those has a different fix: a misclassified policy gets reclassified after establishing it truly warrants mandatory status; a pipeline gate bug gets fixed and, critically, retroactively audited for how many other runs might have slipped through the same hole; an unaudited override path gets closed by requiring a logged justification for any override going forward. Beyond the immediate fix, review whether the three prior applies actually caused any real-world problem (check what specifically the policy would have blocked and whether that condition is still present) — the incident isn't fully closed until you know whether it was a near-miss or an active ongoing issue.

Example

1. Reproduce: does the pipeline gate actually fail correctly today against the same plan?
2. If yes -> gate was bypassed somehow; audit override/approval logs for those 3 runs
3. If no  -> gate itself is broken; fix it, then re-audit every apply since it broke
4. Either way: check current state of what the policy would have blocked — still a problem?

Follow-ups

  • How far back should the audit go once you find a gate was broken? — Back to when the gate was last known-good (a config change, a deploy of the pipeline definition itself) — bound the search by evidence of when the break was introduced, not an arbitrary fixed window.
  • Should this become a blameless postmortem, and why does that matter here specifically? — Yes — the goal is finding the structural gap (why did the gate allow this, why wasn't it caught sooner) rather than who clicked apply, since punishing the person who happened to trigger it discourages exactly the kind of honest reporting that surfaced the issue.
  • What's a good structural fix to prevent "the gate silently didn't run" from recurring? — Make the pipeline fail closed, not open — if the policy-check step itself errors or is skipped for any reason, that should block apply by default, not silently let it through.

Wrong answer: “Since nothing bad actually happened, no further action is needed beyond fixing the immediate bug.” A gate silently failing to enforce is itself the incident, independent of whether this specific instance caused visible damage — the same gap will eventually let through a change that does cause damage unless the structural cause is found and closed.

You're asked to reduce the blast radius of a single monolithic Terraform configuration managing an entire production environment (200+ resources, one state file) without a multi-month rewrite. What's your approach? principal

Answer. Treat it as incremental extraction, not a rewrite: identify natural lifecycle/ownership boundaries within the monolith (networking, a specific application's resources, shared platform services — the same boundaries discussed in unit 04/05) ranked by which is both lowest-risk to extract first and highest-value once separated, then extract one boundary at a time using `state mv` (or `moved` blocks) to relocate resources into a new, separate state without destroying and recreating them. Each extraction is validated with a `plan` showing zero changes (proving the move didn't alter anything Terraform thinks needs to change) before being trusted, and the team keeps working against the shrinking monolith throughout rather than freezing all other work until the extraction finishes. Prioritize extracting whatever boundary is most frequently a source of incidents or blocked concurrent work first, since that's where blast-radius reduction pays off soonest.

Example

# extract "networking" into its own state, one boundary at a time
terraform state mv 'azurerm_virtual_network.main' -state-out=networking.tfstate azurerm_virtual_network.main
# ... repeat for every resource in the boundary ...
terraform plan   # in BOTH the old and new state configs — must show zero unexpected changes

Follow-ups

  • How do you handle resources in the monolith that depend on ones you're extracting? — Replace the direct in-state reference with a `terraform_remote_state` data source (or an explicitly passed variable/output) reading the newly-extracted state, converting an implicit intra-state dependency into an explicit cross-state one (unit 04's coupling-cost trade-off, deliberately accepted here for the blast-radius win).
  • What's the risk if a `state mv` step goes wrong mid-extraction? — Always keep a backup of both state files before any `state mv` operation, and validate immediately with `plan` in both configs — catching a wrong move before the next apply is far cheaper than after.
  • Should this extraction work happen during normal business hours or a maintenance window? — `state mv` alone doesn't touch real infrastructure (it only edits Terraform's bookkeeping), so it's lower-risk than it sounds, but doing it during low-traffic hours with a rollback plan is still the disciplined choice given the size of the monolith involved.

Wrong answer: “Freeze all other infrastructure work until the whole monolith is split apart properly.” A multi-month freeze imposes its own real cost on every other team depending on this infrastructure — incremental extraction alongside continued work is both safer (smaller, individually-validated steps) and more organizationally realistic.

How do you decide when a configuration drift finding (from a scheduled `plan` or drift-detection run) needs an immediate response versus can wait for the next normal change window? senior

Answer. Weigh two axes: how the drift happened, and what it changed. Drift from a legitimate emergency manual fix (someone hand-patched a firewall rule during an active incident) that's already been communicated is usually low-urgency to reconcile — the fix is presumably still correct and just needs to be reflected back into config at the next convenient window. Drift with an unknown cause (nobody knows why a setting changed) or drift affecting something security/compliance-sensitive (a network rule opened, an encryption setting disabled) needs immediate investigation regardless of how small the change looks, since an unexplained change to a sensitive attribute could be a genuine security incident, not just administrative housekeeping. The practical decision rule: unexplained + sensitive = investigate now; explained + low-sensitivity = queue for the next change window, but always queue it (unresolved drift left indefinitely reopens the plan-doesn't-mean-what-it-says-anymore problem discussed in unit 01).

Example

Drift: NSG rule allowing an unexpected inbound port, no one recalls changing it
  -> unexplained + security-sensitive -> investigate NOW, treat as possible incident

Drift: a VM's tag value changed, matches a known emergency fix from last week's on-call notes
  -> explained + low-sensitivity -> reconcile at next normal change window

Follow-ups

  • Who should own triaging drift findings — the on-call rotation, or a dedicated platform team? — Whoever owns the affected resource's lifecycle boundary (unit 04's ownership question) is best positioned to judge "explained or not" quickly — a generic on-call rotation without that context will either under- or over-react.
  • Should reconciling drift mean importing the manual change into config, or reverting it? — Depends on whether the manual change was actually correct — if yes, update config to match reality (`import`/`state mv` as needed) rather than reverting a legitimate fix; if it was a mistake or unauthorized, revert via a normal apply.
  • How often should scheduled drift detection run for a production environment? — Frequently enough that the gap between drift occurring and being caught is short relative to how bad an unnoticed security-sensitive drift could get — daily is a common baseline, with more sensitive environments running it more often.

Wrong answer: “All drift should be reconciled immediately regardless of cause, to keep config and reality in sync.” Treating every drift finding as equally urgent either burns out the team on false urgency or, more likely, trains them to start ignoring drift alerts altogether — the triage judgment is the actual skill being tested here.

A change that passed plan review, policy-as-code, and a human approval still caused a production outage. The plan looked correct. What went wrong, and what do you check? principal

Answer. A correct-looking plan can still cause an outage for reasons the plan diff itself can't show: the change was logically correct but had an operational side effect the plan doesn't represent (a resource replacement that the plan flagged but whose actual downtime during replacement was underestimated — e.g., a "must replace" on a resource believed to support in-place update, or a genuinely in-place update that nonetheless causes a brief service interruption the plan has no way to surface), a dependency outside Terraform's/Bicep's visibility (an application that didn't handle the resource's brief unavailability gracefully), or a timing issue (the change landed during a period of unusually high load that turned a normally-negligible blip into a real outage). The investigation checks, in order: did the plan show a replacement where an update was expected (a provider quirk or a configuration change type that forces replacement unexpectedly), was there a known operational caveat for this resource type that wasn't accounted for (some resource updates are documented as causing brief downtime even though the plan just says "update in-place"), and was the blast radius of this specific resource change larger in practice than its position in the dependency graph suggested.

Example

Plan showed: azurerm_mssql_server.this  ~ update in-place (SKU change)
Reality:     that specific SKU change type triggers a brief connection-dropping restart
             — documented provider behavior the plan's diff format can't express

Follow-ups

  • How do you build institutional knowledge about which "safe-looking" changes actually aren't? — A living runbook/checklist of known operationally-risky change types per resource kind, fed by exactly this kind of postmortem — the plan diff will never encode this, so the team's own accumulated knowledge has to.
  • Should there be a lower-traffic deployment window requirement for certain resource types going forward? — Yes, if this postmortem reveals the resource type has real operational impact on update — codify that as a policy-as-code check or at minimum a documented requirement, not just tribal knowledge held by whoever was on-call that day.
  • Does this argue for canary/staged rollout even for a single-resource production change? — Where feasible, yes — for resource types with known or suspected operational risk on update, a staged rollout (or at minimum a monitored, easily-revertible window) catches this class of surprise before it becomes a full outage.

Wrong answer: “The process worked as designed since the outage wasn't caused by a process failure — nothing to change.” A correct process that still produced an outage means the process has a real gap (missing operational-impact knowledge, no canary step) — "the checklist was followed" isn't the same as "the checklist was sufficient."

How do you run a rollback for an infrastructure change, given that "rollback" doesn't mean the same thing for infrastructure as it does for application code? senior

Answer. Application rollback usually means redeploying a previous artifact/image — cheap, fast, and typically non-destructive. Infrastructure rollback means generating a new plan that reverts the configuration to its previous state and applying that plan — which itself has to go through the same plan-review discipline as any other change, since "revert the config" can itself be destructive (if the change being rolled back created a resource, rolling back means destroying it, potentially with data loss if that resource held state — a database, a storage account). The practical approach: revert the config change (a git revert of the merge), regenerate a plan against current state, and scrutinize that plan just as carefully as a forward change — specifically checking whether the revert plan proposes destroying anything that's accumulated real data or traffic since the original change applied, in which case a straight revert may be the wrong move and a more careful, manually-crafted forward-fix might be safer than an automatic rollback.

Example

git revert    # config now matches pre-change state
terraform plan              # CAREFULLY review: does this propose destroying something
                             # that now holds real data/traffic accumulated since the original apply?

Follow-ups

  • When is a straight config revert the wrong move? — Whenever the change being rolled back created a stateful resource that's since accumulated real data — reverting would destroy that data, so a forward-fix (keep the resource, fix whatever's actually broken about it) is usually safer.
  • Does Bicep/ARM rollback work the same way? — Same principle — redeploying an earlier template version (or template spec version) generates a new deployment whose `what-if` needs the same scrutiny, since ARM has no "undo" concept beyond deploying a different template.
  • How does this connect to the "-replace footgun" idea from earlier units? — Same theme — any operation that looks like a safe undo can itself be destructive; the discipline is always regenerating and reviewing a fresh plan/what-if rather than trusting that "revert" is inherently safe.

Wrong answer: “Rollback just means re-running apply with the previous version of the config, same as redeploying an old app version.” That's true mechanically but glosses over the actual risk — infrastructure rollback can destroy real accumulated data in a way an application redeploy almost never can, which is exactly the review step that must not be skipped.

Design an on-call runbook entry for "unexpected `terraform plan` diff on a routine scheduled drift-check of production." What does the runbook actually need to tell an on-call engineer who's never touched this specific configuration before? senior

Answer. A good runbook entry front-loads exactly the judgment this unit has been building: how to tell explained-safe drift from unexplained-risky drift (link to recent known emergency changes, on-call handoff notes, and the actual diff's specific attributes), who actually owns this specific state/resource boundary so the on-call engineer isn't guessing who to page next, and an explicit "do NOT apply" default until the drift's cause is understood — the runbook's main job for someone unfamiliar with this specific config is preventing a well-intentioned but uninformed reconciliation apply from making things worse. It should also link directly to the specific state's backend location, the pipeline that normally manages it, and recent change history (git log for that config directory), since an unfamiliar on-call engineer's biggest time sink is usually just finding where to look, not judging what they find once they get there.

Example

Runbook: "Unexpected drift, prod, "
1. DO NOT apply. Read-only investigation first.
2. Owner: . Escalate here if unexplained after step 3.
3. Check: recent git log for this dir; recent on-call handoff notes; cloud activity log
   for the specific changed resource in the last 48h.
4. If explained + low-sensitivity: file a ticket to reconcile at next change window.
5. If unexplained OR touches auth/network/encryption: escalate to owner NOW, treat as possible incident.

Follow-ups

  • Why is "do not apply by default" the right starting instruction? — Because reconciling drift via an uninformed apply risks destroying or reverting something that was actually a legitimate emergency fix, or masking evidence of a genuine security incident before it's investigated — the default should be the reversible action (look) not the irreversible one (change).
  • Should the runbook itself live next to the Terraform config, or in a separate wiki? — Ideally versioned alongside the config it describes (a `RUNBOOK.md` in the same repo/directory) so it stays current as the config evolves, rather than drifting out of sync with it the way an external wiki page often does.
  • How do you keep runbooks like this from going stale as the underlying system changes? — Treat runbook updates as a required part of any change that alters ownership, on-call escalation paths, or the resource's operational risk profile — the same discipline that keeps the config itself accurate should extend to its runbook.

Wrong answer: “A generic company-wide 'how to use Terraform' runbook is enough — the specific config's context doesn't need its own entry.” Generic tooling instructions don't tell an unfamiliar on-call engineer who owns this specific boundary, what's normal drift for it, or what's actually sensitive about it — exactly the judgment-critical context a generic runbook can't provide.

12Azure deployment operations: stacks, what-if & scopes

This sub-area is Bicep/ARM-specific operational depth: the mechanics of `what-if`, the four deployment scopes and when each is used, and Deployment Stacks — the newest (GA May 2024) answer to Bicep's historic lack of a Terraform-state-like ownership/cleanup model. Expect it to come up whenever the interviewer wants to check real, current hands-on Azure operational knowledge rather than just conceptual Bicep syntax.

Docs: what-if deployments · Deployment Stacks

Explain `what-if` in depth: what does it actually compute, and where does it diverge from a Terraform plan's guarantees? senior

Answer. `what-if` (via `az deployment group what-if` or the equivalent module/subscription/tenant-scope commands) asks ARM to compute the difference between the template's desired state and the current state of the target scope's resources, returning a categorized diff — Create, Modify, Delete, Ignore, NoChange, Deploy (for nested/unknown-until-deploy cases) — without actually deploying anything. The key divergence from Terraform's plan guarantee is that `what-if` has no persisted state of its own to compare against — it always compares the template against live ARM resource state directly, so it can't tell you about a resource that's meant to be managed by this template but has actually been deleted outside of ARM's knowledge the way Terraform's own state-vs-real-world comparison can surface as drift; it's comparing template-vs-live only, not template-vs-last-known-good-vs-live. It's also known to sometimes report `Deploy` (rather than a firm Create/Modify) for resources whose final result genuinely depends on values only known during the actual deployment (certain nested templates, some resource properties computed server-side) — a category Terraform's plan doesn't have an equivalent for since Terraform's provider model resolves more of this ahead of time.

Example

az deployment group what-if -g rg-prod -f main.bicep -p main.bicepparam
# output categorizes every resource: + Create, ~ Modify, - Delete, = NoChange, ! Deploy (uncertain until deploy)

Follow-ups

  • Why can't `what-if` detect a resource that was deleted outside ARM (e.g., a VM's disk deleted directly via the data plane)? — `what-if` only reasons about resources ARM itself tracks and their properties as ARM currently sees them — anything invisible to ARM's own resource graph (some data-plane-level changes) is invisible to `what-if` too.
  • Should `what-if` output be attached to a PR the same way a Terraform plan is? — Yes, exactly analogous — piping `what-if`'s JSON output into a PR comment or a policy-as-code check gives Bicep the same reviewable-diff discipline unit 09 describes for Terraform.
  • Does `what-if` require any special permissions beyond normal deployment permissions? — It needs read access to evaluate current state plus whatever the template would need to actually deploy (since some Modify/Delete categorization requires evaluating what a real deployment would compute) — not a separate, lesser permission set.

Wrong answer: “`what-if` and `terraform plan` provide the exact same guarantee, just for different tools.” Close in spirit but not identical — `what-if`'s template-vs-live comparison has no persisted-state layer, which changes what kinds of drift/deletion scenarios it can and can't detect compared to Terraform's state-anchored plan.

Walk through Azure's four deployment scopes and give a concrete example of something that must be deployed at each. mid

Answer. Resource group scope is the default and most common — most application resources (VMs, storage, app services, databases) deploy here since a resource group is the natural unit most resources belong to. Subscription scope is for things that don't belong inside any single resource group — creating resource groups themselves, subscription-level RBAC role assignments, subscription-level Azure Policy assignments. Management group scope is for governance applied across multiple subscriptions at once — a policy or RBAC assignment meant to apply org-wide across every subscription under that management group, without repeating the deployment per subscription. Tenant scope is the rarest, reserved for genuinely tenant-wide operations — creating management groups themselves, or tenant-wide policy definitions that need to exist before any management-group-scoped assignment can reference them.

Example

targetScope = 'subscription'

resource rg 'Microsoft.Resources/resourceGroups@2024-11-01' = {
  name: 'rg-app-prod'
  location: 'westeurope'
}
// resource-group creation itself must happen at subscription scope or higher —
// a resource group cannot create its own parent

Follow-ups

  • Can one Bicep file deploy resources at multiple scopes? — Yes, via modules — a subscription-scoped root can deploy a module targeting a specific resource group (using `scope: resourceGroup(...)`) inside the same overall deployment, mixing scopes across a module tree.
  • What's the most common mistake with scope choice? — Trying to create a resource group from inside a resource-group-scoped template — it's a structural impossibility (a resource group can't contain its own parent resource group), and the fix is simply moving that piece to subscription scope.
  • Does Terraform have an equivalent scope concept? — Not really as an explicit language construct — Terraform's `azurerm` provider has resources for each of these levels (subscription, management group), but there's no `targetScope`-style declaration; scope is just whatever the specific resource type's API operates against.

Wrong answer: “Scope is just a deployment command-line flag with no real effect on what you can deploy.” Scope determines what's even addressable in the template — a management-group-level policy assignment simply cannot be expressed in a resource-group-scoped deployment; it's a structural constraint, not a minor flag.

What problem do Deployment Stacks (GA ~May 2024) solve that plain ARM/Bicep deployments never could? senior

Answer. Before Deployment Stacks, ARM/Bicep had no native concept of "this set of resources belongs together as a unit, and removing something from the template should delete the corresponding resource" — a resource removed from a Bicep file simply stopped being managed; it stayed deployed, orphaned, with nothing tracking that it used to be part of this template. That's the single biggest structural disadvantage Bicep had relative to Terraform's state file, which does track exactly this and destroys removed resources on the next apply. Deployment Stacks close that gap: a stack resource wraps a deployment and tracks the full set of resources it manages, so removing a resource from the template and redeploying the stack will actually delete that orphaned resource (configurable via `actionOnUnmanage`), and deleting the stack itself can cascade-delete everything it manages — giving Bicep something functionally much closer to Terraform's state-driven lifecycle tracking, natively, without adopting a whole separate tool.

Example

az stack group create -g rg-prod -n app-stack -f main.bicep -p main.bicepparam \
  --action-on-unmanage deleteResources --deny-settings-mode none
# removing a resource from main.bicep and re-running this will now DELETE that resource,
# something a plain `az deployment group create` would never do

Follow-ups

  • What does `actionOnUnmanage` actually control? — Whether a resource removed from the template gets deleted, detached (left alone but no longer tracked by the stack), or left in place — giving explicit, deliberate control over the exact ambiguity plain deployments never resolved.
  • Does this make Deployment Stacks a full replacement for needing Terraform's state model conceptually? — Much closer than before, yes, for the specific "track and clean up what I manage" problem — though Terraform's ecosystem (multi-cloud providers, mature module registry, `terraform test`) still covers considerably more ground than a stack resource alone.
  • What's `denySettingsMode` for? — An additional protection that can lock resources managed by the stack against deletion/modification by anything other than the stack itself — a governance feature with no direct Terraform equivalent, closer to a resource-level lock tied to stack ownership.

Wrong answer: “Deployment Stacks are just a naming/grouping convenience for organizing related deployments.” They're a genuine lifecycle-tracking mechanism — the ability to actually delete orphaned resources on template changes is new behavior ARM never had before, not merely cosmetic grouping.

How would you migrate an existing set of Bicep deployments (currently plain `az deployment group create` calls) to Deployment Stacks without causing accidental deletions? principal

Answer. The risk is exactly the new capability that makes stacks valuable — the first stack deployment against an existing resource group needs to correctly recognize every currently-deployed resource as "already managed, don't touch it," rather than seeing them as unmanaged and deleting them. The safe path: first deploy the stack with `actionOnUnmanage` set to `detachAll` (or the least destructive option) so the stack starts tracking the current template's resources without deleting anything it doesn't yet know about, verify via `az stack group show` that the tracked resource list matches expectations exactly, and only once confidence is established switch `actionOnUnmanage` to `deleteResources` for future template changes. Treat the very first stack creation against a previously plain-deployed resource group as its own reviewed change — ideally rehearsed first against a cloned/scratch resource group with the same template, not directly against production on the first attempt.

Example

# first migration attempt: safest possible action-on-unmanage
az stack group create -g rg-prod -n app-stack -f main.bicep -p main.bicepparam \
  --action-on-unmanage detachAll
az stack group show -g rg-prod -n app-stack --query resources
# verify the tracked list is exactly what's expected before ever switching to deleteResources

Follow-ups

  • What if the template doesn't perfectly match what's currently deployed (some drift already exists)? — Reconcile that drift first, the same way you would before trusting a Terraform `import`, so the stack's initial managed-resource baseline is accurate rather than inheriting existing confusion.
  • Is rehearsing against a scratch resource group actually representative of the real migration? — Reasonably, if the scratch group is seeded with the same resource types/configuration — it validates the mechanics and the `actionOnUnmanage` behavior even if it can't perfectly replicate every production-specific edge case.
  • Does this migration risk mirror anything from the Terraform side of this topic? — Yes — directly analogous to the caution around `terraform import`/state-generation from unit 04: the dangerous moment is always the first time a tracking mechanism establishes its baseline against already-existing, unmanaged-by-it resources.

Wrong answer: “Just create the stack with default settings — it'll correctly detect what's already there.” Defaulting straight to a destructive `actionOnUnmanage` setting on the very first stack creation against an existing, previously-unmanaged resource group is exactly the scenario most likely to produce an unexpected deletion.

What's the difference between ARM's built-in deployment history and something like a Terraform state file — can you rely on deployment history the same way? mid

Answer. ARM deployment history is a log of past deployment operations (what templates were submitted, when, with what parameters, and their outcome) scoped to a resource group/subscription — genuinely useful for auditing what happened and when, and it's what `what-if` and the portal's "deployment" blade surface. It is not the same as Terraform state's role as the live source of truth Terraform consults on every plan to know what it currently manages and what each resource's last-known attributes were — deployment history doesn't get consulted to compute a diff the way state does (that's what `what-if` does independently, by querying live resources directly), and it doesn't get updated or pruned the way state gets replaced on every apply. Deployment Stacks close part of this gap for tracking currently-managed resources, but deployment history itself remains an append-only audit log, not a live-state model.

Example

az deployment group list -g rg-prod --query "[].{name:name, timestamp:properties.timestamp, state:properties.provisioningState}"
# an audit trail of past operations — not consulted by `what-if` to compute its diff,
# which queries live resource state directly instead

Follow-ups

  • Does deployment history ever get used to answer "what does this resource group currently contain"? — Not reliably — the authoritative answer to "what currently exists" is always the live resource graph itself (`az resource list`), or a Deployment Stack's tracked-resources list if one is in use; deployment history only tells you what was submitted, not necessarily what's still true now.
  • Is there a retention limit on ARM deployment history? — Yes — resource-group-scoped deployment history has a retention limit (historically around 800 deployments per resource group), which is one more reason not to treat it as a durable long-term record the way Terraform state is treated.
  • How does this affect incident investigation compared to Terraform's state-backed history? — Deployment history gives you "what was deployed when," useful for correlating with an incident timeline, but you still need the live resource graph (or a Deployment Stack) to know current managed state — a genuinely different investigative workflow than pulling a Terraform state snapshot.

Wrong answer: “ARM deployment history is functionally Bicep's version of a Terraform state file.” It's an audit log of past operations, not a live, continuously-consulted source of truth about current managed resources — Deployment Stacks, not deployment history, is the closer (if still partial) analog to state's tracking role.

A subscription-scoped Bicep deployment needs to create a resource group and then deploy resources into it in the same operation. How do you structure that, and what's the common mistake? mid

Answer. The root template runs at subscription scope (`targetScope = 'subscription'`), creates the resource group as a resource within that scope, and then invokes a module scoped explicitly to that resource group (`scope: resourceGroup(rg.name)`) to deploy the resources that need to live inside it — the module itself is written as an ordinary resource-group-scoped Bicep file, unaware that its caller happens to be running at a higher scope. The common mistake is trying to declare both the resource group and the resources meant to live inside it directly in the same resource-group-scoped file — which is structurally impossible, since a resource group can't be a peer resource alongside things declared to already be inside it; the fix is always the two-scope, module-boundary pattern.

Example

targetScope = 'subscription'

resource rg 'Microsoft.Resources/resourceGroups@2024-11-01' = {
  name: 'rg-app-prod'
  location: 'westeurope'
}

module appResources 'app-resources.bicep' = {
  name: 'appResourcesDeploy'
  scope: resourceGroup(rg.name)   // module runs at resource-group scope, inside the newly created RG
  params: { /* ... */ }
}

Follow-ups

  • Does the module file itself need any special declaration to be deployable this way? — No — `app-resources.bicep` is written as a completely ordinary resource-group-scoped Bicep file; the `scope:` property on the module call from the subscription-scoped caller is what redirects it, not anything inside the module itself.
  • Can this same pattern create a resource group and immediately assign RBAC roles within it? — Yes, same shape — a subscription-scoped root creates the resource group, then a resource-group-scoped module (or a subscription-scoped role assignment referencing the new resource group's ID) handles the role assignment.
  • How does this map conceptually to Terraform, which has no `targetScope` construct? — Terraform just uses `azurerm_resource_group` and lets subsequent resources reference its name/location as a normal dependency — no scope-switching construct needed, since Terraform's providers don't have Bicep's explicit multi-scope deployment model at all.

Wrong answer: “Declare the resource group and its resources together in one resource-group-scoped file — Bicep will figure out the ordering.” This isn't an ordering problem Bicep can resolve — a resource-group-scoped file has no ability to create its own parent resource group at all; the subscription-scope-plus-module pattern is structurally required, not just a stylistic preference.

13Providers, extensibility & the ecosystem

A smaller, rarely-deeply-probed sub-area, but worth being fluent in: how Terraform providers actually work under the hood, what OpenTofu really is at a technical level (beyond the licensing story from unit 07), and where a team would reach for writing its own provider or module versus consuming an existing one.

Docs: Terraform plugin framework · OpenTofu docs

What is a Terraform provider, mechanically — how does the core binary actually talk to `azurerm` or any other provider? senior

Answer. A provider is a separate compiled binary (written in Go, using HashiCorp's plugin framework) that Terraform Core launches as a subprocess and communicates with over gRPC — Core itself has no built-in knowledge of any specific cloud API at all; it only knows the generic protocol for asking a provider "given this configuration, what would you create/update/destroy, and please now actually do it." This architecture is why providers can be versioned and released independently of Terraform Core itself, why a provider crash doesn't crash Core, and why the ecosystem could grow to thousands of providers (cloud platforms, SaaS APIs, even things like generating random values or reading local files) without HashiCorp needing to write or maintain most of them — providers are largely community- and vendor-maintained, including `azurerm`, which Microsoft contributes to heavily but doesn't solely control.

Example

terraform apply
  -> Core reads config, builds a dependency graph
  -> Core launches the azurerm provider binary as a subprocess
  -> Core <-gRPC-> azurerm provider: "here's the desired config for this resource,
                                      what's the plan/diff, then please apply it"
  -> azurerm provider makes the actual Azure ARM API calls

Follow-ups

  • Why does this explain the dependency lock file's importance from unit 02? — Because the exact provider binary version in use materially affects behavior (bug fixes, new resource support, occasionally breaking changes) — the lock file pins exactly which provider binary gets launched, which is why an unpinned or loosely-pinned provider version is a real reproducibility risk.
  • Can a provider maintain its own local state or caching beyond what Terraform Core tracks? — Generally no — providers are meant to be largely stateless request/response services from Core's perspective; all persistent state lives in Terraform's own state file, not inside the provider process.
  • Does this gRPC-based plugin model apply to provider-defined functions (1.8) too? — Yes — provider-defined functions are just another RPC call type the same plugin protocol supports, alongside the resource CRUD operations, which is why they arrived as a protocol version bump rather than a wholly new mechanism.

Wrong answer: “Providers are just configuration files that tell Terraform which API endpoints to use.” They're full compiled executables implementing real logic (translating HCL-described desired state into actual API calls, handling that API's specific quirks and retry behavior) — much more than declarative endpoint configuration.

Technically, how compatible is OpenTofu with Terraform providers and modules today, and what's actually diverging between the two projects? senior

Answer. Because OpenTofu forked from the last MPL-licensed Terraform codebase, it inherited the same core plugin protocol, so the overwhelming majority of existing Terraform providers (including `azurerm`) work with OpenTofu entirely unmodified — a provider has no idea which core binary launched it, since the gRPC protocol is what it speaks either way. Registries differ though: OpenTofu maintains its own registry (with providers/modules mirrored or independently published) rather than relying on HashiCorp's registry, partly for licensing-independence reasons. Where the two projects have started diverging is in newer language/CLI features each adds independently — OpenTofu has shipped some capabilities (like native state encryption approaches and certain built-in functions) on its own schedule not perfectly synchronized with Terraform's, and vice versa — so "identical forever" is not a safe assumption for brand-new features going forward, even though the core provider protocol compatibility remains very strong.

Example

terraform {
  required_providers {
    azurerm = { source = "hashicorp/azurerm", version = "~> 4.0" }
  }
}
# this block is identical whether the binary running it is `terraform` or `tofu`

Follow-ups

  • Does state written by Terraform open cleanly in OpenTofu, and vice versa? — Largely yes today, given the shared lineage and format — but this is exactly the kind of guarantee that could erode over time as the two projects evolve independently, so it shouldn't be treated as a permanent contract.
  • Why would a module published to HashiCorp's registry need re-publishing for OpenTofu's registry? — Discoverability and licensing-independence more than technical necessity — the module's HCL content works either way, but OpenTofu's own registry exists so its users aren't dependent on HashiCorp's infrastructure/policies for finding modules.
  • What's the practical risk of picking OpenTofu today for a new project? — Mainly the slow, low-probability risk of long-term feature divergence eventually requiring a choice — day-to-day, for the vast majority of configurations, the experience is close to indistinguishable from Terraform.

Wrong answer: “OpenTofu and Terraform are now two completely separate ecosystems with incompatible providers and modules.” The opposite of current reality — the shared plugin protocol and shared lineage mean the overwhelming majority of the ecosystem works across both; divergence is real but limited to specific newer features, not a wholesale incompatibility.

When would a team actually justify writing its own custom Terraform provider, versus using the generic `http`/`external` providers to integrate with an internal API? principal

Answer. The generic providers (`http` for simple request/response calls exposed as a data source, `external` for shelling out to a local script that returns JSON) are the right first move for almost any internal-API integration need — they cost nothing to set up and handle a large share of "I just need Terraform to read or trigger something from our internal system" cases with no maintenance burden of a compiled plugin. A custom provider is justified once the integration needs genuine CRUD lifecycle semantics that the generic providers can't express well — proper create/read/update/delete operations with drift detection against the internal system's own state, complex nested schema validation, or reuse broad enough across many configurations/teams that a first-class typed schema (with real Terraform-native error messages and plan-time validation) pays for the ongoing maintenance cost of a compiled plugin that needs its own release process, versioning, and testing.

Example

Generic http/external provider fits: "call this internal API once to fetch a value" or
                                       "trigger this internal webhook on apply"
Custom provider justified: "manage the full lifecycle of an internal service's tenant
                             records, with drift detection, across 30+ configurations"

Follow-ups

  • What's the ongoing cost of maintaining a custom provider that's easy to underestimate? — Keeping it compatible with new Terraform Core protocol versions, handling the internal API's own breaking changes, and providing the same quality of error messages/documentation users expect from any well-known provider — a real, ongoing software-maintenance commitment, not a one-time build.
  • Does the `external` provider have real limitations that push teams toward a custom provider sooner? — Yes — it has no real drift detection or nuanced update semantics (it typically re-runs the whole script on every apply), which is fine for simple lookups but becomes awkward for genuine stateful lifecycle management.
  • Is there a middle ground between "generic provider" and "full custom provider"? — The Terraform Plugin Framework (the modern SDK) substantially lowers the effort of writing a minimal custom provider compared to older SDK versions, which has shifted some teams' calculus toward building a narrow custom provider sooner than they might have a few years ago.

Wrong answer: “Writing a custom provider is rarely worth it for anything internal — just always use the generic `http`/`external` providers.” That's the right default for simple cases, but dismissing custom providers entirely ignores the real cases (broad reuse, genuine CRUD lifecycle needs) where the generic providers' limitations become a genuine ongoing cost of their own.

How does Bicep's extensibility model compare to Terraform's provider model — can Bicep integrate with non-ARM APIs the way Terraform providers can integrate with non-cloud services? senior

Answer. Historically, no — Bicep compiles to ARM JSON and ARM's deployment engine only knows how to talk to Azure Resource Manager resource providers, so there was no equivalent of Terraform's generic plugin model for arbitrary non-Azure APIs. Bicep has been extending this via "Bicep extensibility" / extension providers (a newer, still-maturing capability) that let Bicep author resources against non-ARM targets — Microsoft Graph being the most mature example (managing Entra ID/Azure AD objects, which live outside ARM's native resource model, directly from Bicep) — but this remains narrower in scope and maturity than Terraform's thousands-strong general-purpose provider ecosystem; it's explicitly aimed at closing specific Microsoft-ecosystem gaps (Graph, and a growing but still limited set of others) rather than becoming a general-purpose arbitrary-API integration mechanism the way Terraform's provider model is by design.

Example

extension microsoftGraphV1

resource group 'Microsoft.Graph/groups@v1.0' = {
  displayName: 'engineering-team'
  mailEnabled: false
  securityEnabled: true
}

Follow-ups

  • Why did Microsoft Graph specifically need its own extensibility path rather than just being another ARM resource type? — Entra ID/Graph objects (users, groups, app registrations) live in a fundamentally different backing system than ARM-managed Azure resources, so representing them natively required Bicep to learn to talk to a second API surface entirely, not just add more ARM resource types.
  • Should a team expect Bicep extensibility to eventually rival Terraform's provider breadth? — Not a safe assumption for the current state of the ecosystem — it's a genuinely useful, growing capability for Microsoft-ecosystem gaps specifically, but Terraform's general-purpose, third-party-driven provider model has a multi-year head start and a fundamentally broader design intent.
  • Does this affect the "Bicep vs Terraform" decision framework from unit 07? — Marginally — it narrows one specific gap (managing Graph objects without reaching for a second tool) but doesn't change the core multi-cloud-vs-Azure-only calculus that framework is built on.

Wrong answer: “Bicep has no extensibility model at all — it can only ever manage ARM resources.” That was true historically but is no longer accurate — Bicep extensibility (Microsoft Graph being the flagship example) is a real, shipping capability, just considerably narrower in scope than Terraform's general-purpose provider ecosystem.

A provider version upgrade (e.g. `azurerm` major version bump) introduces breaking changes to resource schemas already in use across dozens of configurations. How do you plan that upgrade? principal

Answer. Read the provider's upgrade guide first — major provider version bumps (like `azurerm`'s major versions) typically ship a detailed migration guide enumerating exactly which resource arguments were renamed, removed, or changed in required type, and often the provider itself emits deprecation warnings for at least one prior minor version cycle before the breaking major bump, which is the moment to start responding rather than waiting for the bump itself. The upgrade plan mirrors module version rollout: bump one non-critical configuration first, run `plan` (a properly non-breaking upgrade should show zero unexpected changes if the config was already updated to the new schema, or a clear, expected diff if the new provider version genuinely changes real resource behavior, not just schema), fix any config syntax the provider now requires differently, then roll the bump out to remaining configurations in controlled batches rather than a single simultaneous mass-update across dozens of configurations that could all break at once if something was missed in the migration guide.

Example

1. Read azurerm 4.x upgrade guide; note every breaking schema change relevant to configs in use
2. Bump one low-risk config's version constraint; run `terraform plan`; expect zero unplanned changes
3. Fix any required syntax changes; re-verify plan is clean
4. Roll out to remaining configs in batches, canary-first, same discipline as unit 08's rollout pattern

Follow-ups

  • What if `plan` shows an unexpected change after the version bump, not just a syntax fix? — Investigate before applying — some provider version bumps do change actual resource behavior (a default value changed, a previously-implicit setting now needs to be explicit), and an unexpected diff needs to be understood as either a config bug to fix or a genuinely intended new default to accept.
  • Should the dependency lock file be updated as part of this, and how? — Yes — `terraform init -upgrade` refreshes the lock file to the new allowed version, and that updated lock file should be committed and reviewed like any other change, since it's what makes the new version reproducible for everyone else.
  • Does this same discipline apply to a Bicep API-version bump (a resource type's `@yyyy-mm-dd` API version)? — Yes, directly analogous — a newer API version can rename or require different properties, and `what-if` against the updated template plays the same "catch it before applying" role as `terraform plan` does here.

Wrong answer: “Bump the provider version everywhere at once since the upgrade guide says what changed — reading it is enough preparation.” Reading the guide is necessary but not sufficient — an actual `plan` against real, current state for each configuration is what catches config-specific surprises the guide's generic examples can't anticipate, and a simultaneous mass rollout removes the chance to catch a problem before it's everywhere at once.

14Judgment calls

These have no single correct answer — they're here because a lead/principal loop usually spends real time on open-ended judgment rather than more Q&A. Each one is a prompt to think out loud with, not a definition to recite. What follows each is what a strong answer tends to demonstrate, and a common weak answer that sounds reasonable but misses the actual trade-off.

Docs: Bicep vs Terraform (Microsoft's own comparison)

A team wants to adopt a brand-new Terraform 1.17-alpha feature (say, deferred actions) in production before it's stable. How do you respond? principal

There's a real tension here between staying current and staying safe — alpha/experimental features exist precisely so real usage can surface problems before general availability, but "production" and "experimental" are an uncomfortable pairing regardless of how appealing the feature is. The honest answer usually depends on what "production" means for this specific team: a genuinely low-blast-radius internal tool is a very different risk than a customer-facing revenue path.

What a strong answer demonstrates

  • Separates "is the feature useful" from "is now the right time" — the two questions have different owners and different evidence.
  • Proposes a concrete way to get the benefit safely: a scoped trial on the lowest-blast-radius environment available, an explicit rollback plan, and a real timeline for revisiting once the feature stabilizes.
  • Names the actual cost of waiting (a competitor advantage, a real pain point the feature solves) rather than treating "wait for GA" as automatically safe and free.

Weak answer: “Never use anything experimental in production, full stop.” This sounds disciplined but is a rule, not a judgment — it skips actually weighing this specific feature's risk against this specific team's blast radius and need, and would have blocked plenty of now-uncontroversial adoptions (write-only arguments, `moved` blocks) during their own pre-stable window.

Your organization is Azure-only today but leadership is exploring a second cloud "for resilience." Do you start writing new infrastructure in Terraform now, ahead of any actual multi-cloud need? principal

This is a build-for-the-future-versus-optimize-for-today tension. Terraform now, before multi-cloud is real, costs the Bicep-native advantages (day-one API access, no state management) for a need that might never materialize or might materialize on a timeline nobody can predict yet. Waiting risks a much larger, more urgent migration later if the second-cloud decision lands suddenly.

What a strong answer demonstrates

  • Asks how firm and how soon the second-cloud plan actually is, rather than treating "leadership is exploring" as equivalent to "this is happening."
  • Distinguishes between genuinely cloud-agnostic pieces (networking topology, identity patterns) worth designing portably now, and Azure-specific application resources not worth the premature abstraction.
  • Names the real cost of guessing wrong in either direction — over-engineering for a multi-cloud future that never comes versus a rushed migration if it comes sooner than expected.

Weak answer: “Switch everything to Terraform now to be ready.” Treats "exploring" as a decision already made, and pays the ongoing cost of Terraform's Azure-provider lag and state management for a need that may never fully materialize — premature generalization is exactly the trap this framing walks into.

A platform team wants to mandate that every team's IaC go through a central review gate before any apply, including dev environments. An app team pushes back hard, saying it kills their velocity. How do you mediate? principal

This is the standardization-versus-autonomy trade-off that shows up constantly in platform engineering. Central review reduces variance and catches mistakes consistently; it also adds latency and a bottleneck that scales badly as more teams onboard, and applying the same rigor to a disposable dev sandbox as to production conflates two very different risk levels.

What a strong answer demonstrates

  • Separates the policy question (what needs review) from the process question (how fast can review happen) — the app team's complaint might be about speed, not about the principle of review existing at all.
  • Proposes risk-tiered gating (unit 09/10's advisory-vs-mandatory idea) rather than one-size-fits-all — dev environments likely need far lighter gates than prod.
  • Treats the central team's mandate and the app team's velocity complaint as both legitimate inputs to resolve, not a dispute to simply rule on from authority.

Weak answer: “The platform team is the authority here, so their mandate should just apply as stated.” Ignores that a mandate with no calibration to actual risk will get quietly routed around by a frustrated team — sustainable governance needs buy-in and proportionality, not just an org chart's authority.

You inherit a production environment that was built entirely by hand (portal clicks, ad hoc CLI commands) with no IaC at all. Leadership wants it under Terraform or Bicep management "as soon as possible." What do you actually do first? principal

"As soon as possible" and "safely" are in tension here — the fastest path (write config that roughly matches what you see, apply, let Terraform reconcile any difference) risks destructive surprises against resources nobody has a full, accurate inventory of yet. The safe path (import everything carefully, verify no unintended changes at each step) is slower than leadership's stated urgency implies they want.

What a strong answer demonstrates

  • Leads with inventory and risk-tiering before any import/write activity — knowing what exists and which pieces are highest-blast-radius shapes the whole plan.
  • Explicitly reframes "as soon as possible" in terms of what's actually achievable safely, rather than silently accepting an unrealistic timeline and cutting corners to hit it.
  • Proposes bringing the highest-risk, most-frequently-changed resources under management first (where IaC pays off fastest) rather than starting wherever is easiest.

Weak answer: “Write the Terraform config to match what's there and run apply — Terraform will sort out any differences.” Skips the import step entirely and risks Terraform treating unmanaged existing resources as things to create fresh (potential duplicate/conflicting resources) or, worse, to destroy — exactly the dangerous first-encounter risk unit 04's import discipline exists to prevent.

Your team has accumulated real "IaC debt" — a monolithic state file, no tests, inconsistent module patterns — but there's no dedicated time allocated to fix it and feature work keeps landing. How do you actually get traction on this? senior

This is the classic technical-debt-versus-feature-pressure trade-off, made sharper because IaC debt's cost (a bigger incident later, slower onboarding, more painful migrations) is largely invisible until it bites, which makes it perpetually easy to deprioritize against visible, dated feature commitments.

What a strong answer demonstrates

  • Attaches a concrete cost to the debt (time lost per incident, onboarding friction measured, not just "this feels messy") to make the trade-off visible to whoever allocates time.
  • Prefers incremental, opportunistic paydown (unit 07's migration pitch: fix what you touch anyway) over asking for a dedicated block of time that competes directly with feature work and is easy to say no to.
  • Picks the highest-leverage piece of debt to address first (often state-splitting or test coverage for the most-changed module) rather than trying to fix everything at once.

Weak answer: “Escalate to leadership and ask for a dedicated quarter to pay down the debt properly.” A big, undifferentiated ask competing with visible feature commitments is the request most likely to be deferred indefinitely — a credible, incremental plan tends to get further than a large one-time ask without a strong quantified justification.

Two senior engineers on your team disagree sharply: one wants to standardize everything on AVM modules for Azure work, the other argues AVM's abstraction hides too much and prefers hand-rolled modules for full control. How do you resolve this? senior

Both positions have real merit — AVM buys tested, maintained, community-reviewed modules at the cost of some control and a dependency on someone else's release cadence; hand-rolled modules buy full control and transparency at the cost of the team maintaining everything itself, including edge cases AVM's broader user base has already found and fixed.

What a strong answer demonstrates

  • Doesn't force a single organization-wide answer where the right call may genuinely differ by use case — a well-trodden resource type (a storage account) is a strong AVM fit; a highly specific internal pattern may not be.
  • Surfaces the actual disagreement's root — is it really about AVM specifically, or a broader disagreement about how much abstraction the team is comfortable trusting — since that reframing often unlocks the real conversation.
  • Proposes a concrete way to test both approaches against a real case (try AVM for the next new resource type, compare against a hand-rolled equivalent) rather than resolving it by argument alone.

Weak answer: “Pick whichever position the more senior or more persuasive engineer holds.” Resolving a technical trade-off by seniority or rhetorical strength rather than by weighing the actual trade-off risks entrenching whichever engineer argues loudest, not whichever approach is actually better for the team's specific situation.

A stakeholder wants a production infrastructure change deployed today, bypassing the normal plan-review-approval pipeline, citing business urgency. The change isn't a genuine incident — it's a deadline. How do you handle the request? senior

This is the pressure-versus-process tension that tests whether the pipeline's discipline (unit 09/11) actually holds when someone senior wants an exception. The business urgency may well be real and legitimate — the question is whether skipping review is actually necessary to meet it, or just the fastest-looking option under pressure.

What a strong answer demonstrates

  • Separates the urgency of the business outcome from the specific request to skip review — often the same deadline can be met with an expedited-but-still-reviewed path rather than no review at all.
  • Offers a concrete faster alternative (an expedited review with the fewest people needed to approve safely, rather than zero review) instead of a flat no that doesn't solve the stakeholder's actual problem.
  • Is willing to hold the line if the request is genuinely unsafe, and explains why in terms the stakeholder cares about (risk to the very deadline they're trying to protect, not process for its own sake).

Weak answer: “Since it's a business priority from someone senior, just apply it directly and skip the pipeline this once.” Treats organizational pressure as sufficient justification to bypass the exact safeguard this whole topic has been building toward — "this once" is also precisely how gates observed to be silently bypassable (unit 11) become bypassed as a habit.

You're deciding whether to invest engineering time building an internal Terraform module registry and CI templates, versus just letting each team run its own ad hoc setup. How do you decide if the platform investment is worth it? principal

This is a build-versus-let-teams-self-manage trade-off, and the honest answer scales with organization size and the number of teams actually duplicating effort — a platform investment that pays off at 20 teams can be pure overhead at 3.

What a strong answer demonstrates

  • Quantifies the duplication cost currently being paid (how many teams are independently solving the same backend-configuration, CI-pipeline, and module problems) before proposing a platform investment to fix it.
  • Names the platform investment's own ongoing cost honestly — someone has to maintain the registry and templates indefinitely, which is a standing commitment, not a one-time build.
  • Considers a middle ground (a shared starter template teams can copy and diverge from, versus a fully centralized mandatory platform) rather than treating it as a binary choice.

Weak answer: “Building shared platform tooling is always worth it — DRY is a universal good.” Ignores that a platform investment has real, ongoing maintenance cost that can exceed the duplication it saves at small scale — the right call is genuinely conditional on the organization's size and actual duplication, not a universal principle.

How would you evaluate whether a teammate's Terraform module pull request is genuinely good, beyond "does it apply cleanly"? senior

This tests whether a candidate has a real code-review mental model for infrastructure code specifically, not just a generic "looks fine" pass. A module that applies cleanly today can still be a liability — a bad interface, hidden coupling, no tests, or scope creep that will show up as pain the first time someone else has to use or change it.

What a strong answer demonstrates

  • Checks the module's interface design (unit 05) — are the exposed variables genuinely necessary and well-scoped, or is it a 40-variable pass-through anti-pattern.
  • Looks for what the plan would actually do against real usage, not just that the module's own isolated test passes — does the diff match what the PR description claims.
  • Considers blast radius and reversibility — does this module make a future mistake easier or harder to make, and easier or harder to undo.

Weak answer: “If `terraform plan`/`validate` pass and the PR description looks reasonable, approve it.” Mechanical validation catches syntax errors, not design quality — a module can validate and plan cleanly while still being a poorly-designed interface that causes real pain the first time someone else has to extend or reuse it.

A new hire on your team keeps reaching for `-target` and `taint`/`-replace` as their default troubleshooting tools whenever something looks slightly wrong, rather than investigating root cause. How do you coach this without just telling them "don't do that"? senior

This is a mentoring judgment call as much as a technical one — the tools themselves aren't wrong (unit 02 covers legitimate uses for both), but reaching for them reflexively as a first response usually signals treating symptoms rather than causes, a habit that compounds badly as they take on more responsibility.

What a strong answer demonstrates

  • Distinguishes coaching the habit (reflexive tool-reaching before understanding) from banning the tools (which have real, narrow, legitimate uses) — the goal is better judgment, not memorizing a list of forbidden commands.
  • Uses a recent real example from their own work as the teaching moment — asking "what would `plan` have told you before you reached for `-replace`" is more effective than an abstract rule.
  • Recognizes this as a pattern worth naming explicitly and following up on, not a one-time correction, since habits form from repetition and need repeated, gentle redirection to actually change.

Weak answer: “Tell them not to use `-target` or `-replace` at all going forward.” Bans legitimately useful tools instead of addressing the actual problem (reaching for a workaround before understanding root cause), and teaches compliance with a rule rather than the underlying judgment that would make the rule unnecessary.

These are the longer, whiteboard-style prompts a lead/principal loop reaches for once the Q&A is going well. Each has a short prompt, the clarifying questions a strong candidate asks before designing anything, and a collapsed solution outline — read the prompt, actually think it through, then expand the outline to compare.

Exercise 1 — Terraform structure for a growing platform team

Prompt. You're the platform lead for an organization with 15 application teams, all on Azure, currently each running their own ad hoc Terraform setup with wildly inconsistent state backends, module patterns, and CI. You're asked to design the platform-level Terraform structure going forward: state organization, module strategy, environment handling, and how much is centrally mandated versus left to each team. Sketch the design.

Clarifying questions to ask

  • How many of the 15 teams' current setups are actively causing incidents versus just inconsistent-but-working — the migration urgency differs a lot depending on the answer.
  • Is there an existing platform team with ongoing capacity to maintain shared modules/CI templates, or would this be a one-time push with no dedicated follow-up capacity?
  • Do any teams have genuinely different requirements (a regulated workload needing stricter controls) that shouldn't be forced into one universal template?
  • What's the appetite for a migration timeline — days, one quarter, an ongoing background effort?
Solution outline principal

Structure. One shared module registry (internal, or AVM where it fits) for common resource patterns, versioned with strict semver; a standard root-module template (backend config shape, provider version pinning, standard variable names) every team starts from but can extend; per-team, per-environment state (never shared across teams, per unit 04's blast-radius principle), with a consistent state-key naming convention (`//.tfstate`) so the backend layout itself is self-documenting. CI is centrally templated (the pipeline stages from unit 09 — fmt/validate/lint/plan/policy-as-code/apply, environment-gated) but each team's pipeline instance is theirs to trigger and own, not centrally operated.

registry/                     # shared, versioned, semver-strict
  modules/network/
  modules/app-service/
templates/
  root-template/               # starter: backend shape, provider pins, CI hookup
  ci-pipeline-template.yml      # fmt, validate, lint, plan, policy check, env-gated apply

team-a/
  dev/    -> state key: team-a/dev/*.tfstate      -> own SP, own CI trigger
  stage/  -> state key: team-a/stage/*.tfstate
  prod/   -> state key: team-a/prod/*.tfstate      -> human-approval gate before apply
... (14 more teams, same shape)

Trade-offs to name unprompted

  • Mandating the shared registry for common patterns while leaving team-specific resources hand-rolled — full centralization would fight legitimate per-team differences; zero centralization reproduces today's inconsistency.
  • Migration should be incremental (new work adopts the template immediately, existing setups migrate opportunistically or in a scheduled wave ranked by incident history) rather than a simultaneous cutover across 15 teams at once.
  • The platform team's ongoing maintenance burden for the shared registry/templates is a real, standing cost that needs a named owner, not a one-time project that's considered "done" after the initial rollout.
  • A rigid, over-specified template can itself become the next generation's technical debt if it doesn't leave enough room for legitimate per-team variation — versioned, not frozen.

Exercise 2 — Migrating a legacy ARM JSON estate

Prompt. A large Azure estate (roughly 300 resources across 12 resource groups) was built entirely in hand-authored ARM JSON templates over the last six years, deployed manually from a jump box with no CI, no source-control discipline beyond "the last person who touched it," and no consistent naming. Leadership wants it modernized. Design the migration approach, including how you'd decide between Bicep and Terraform for the target state.

Clarifying questions to ask

  • Is there any other cloud in this organization's future, or is this genuinely, durably Azure-only — directly informs the Bicep-vs-Terraform decision from unit 07.
  • How much of the 300 resources' current configuration is actually correct and intentional versus accumulated cruft nobody would choose to keep if starting fresh?
  • Is there budget/appetite for parallel effort (a small dedicated migration workstream) or does this have to happen entirely opportunistically alongside other work?
  • What's the actual pain driving "leadership wants it modernized" — slow change velocity, a recent incident, audit/compliance pressure? The answer shapes what to prioritize first.
Solution outline principal

Approach. Assuming Azure-only durably (confirmed via the clarifying question), Bicep is the reasonable target given zero-lag Azure API access and no new state-management burden to introduce on top of an already under-tooled estate. Phase 1: get everything into source control and behind CI as-is, no rewriting — `bicep decompile` every JSON template mechanically, commit, wire up a CI pipeline that at minimum runs `what-if` on every future change so nothing gets hand-deployed from the jump box again. Phase 2: introduce Deployment Stacks per resource group so orphaned-resource cleanup and ownership tracking exist going forward. Phase 3, opportunistic: as each resource group is touched for a real change, refactor that group's templates into modern patterns (modules, user-defined types, AVM where a resource matches an available AVM pattern), retiring cruft discovered along the way rather than preserving it out of caution.

Phase 1 (weeks):     bicep decompile all 12 RGs -> commit -> CI gate: what-if required, no more jump-box deploys
Phase 2 (weeks):     wrap each RG in a Deployment Stack -> orphan tracking + cleanup enabled
Phase 3 (ongoing):   opportunistic refactor per RG as touched -> modules, UDTs, AVM where it fits
                      retire confirmed-cruft resources found along the way, don't preserve blindly

Trade-offs to name unprompted

  • Choosing Bicep over Terraform here trades away Terraform's broader ecosystem/testing maturity for zero migration of a state-management concept this estate has never had — the right call specifically because the organization is confirmed Azure-only, not a universal default.
  • Phase 1's "no rewriting, just decompile" deliberately defers code-quality wins to get the safety win (CI, `what-if`, source control) fast — modernizing further immediately would slow down the most urgent fix.
  • Deployment Stacks' first-time adoption against already-existing, previously-untracked resources carries real risk (unit 12) and needs its own careful, rehearsed rollout per resource group, not a blanket simultaneous adoption.
  • Phase 3 being purely opportunistic risks stalling indefinitely on rarely-touched resource groups — worth a periodic check-in on progress, not an open-ended "eventually" commitment.

Exercise 3 — CI/CD architecture across Bicep and Terraform coexisting

Prompt. Your organization runs Terraform for a multi-cloud platform layer (networking, identity, shared services) and Bicep for individual Azure application teams, per the coexistence model from unit 07. Design the end-to-end CI/CD architecture spanning both tools — pipeline structure, secrets handling, and how the two tools' changes get sequenced when an app team's Bicep deployment depends on something the platform team's Terraform manages.

Clarifying questions to ask

  • How often does the platform layer (Terraform-managed) actually change relative to app teams' Bicep deployments — informs how tightly coupled the sequencing needs to be.
  • Is there an existing secrets management system (Key Vault, HashiCorp Vault) already in use that both pipelines should integrate with, or is this being designed from scratch?
  • What's the current state of policy-as-code enforcement, if any, and does it need to apply uniformly across both tools' pipelines or can each tool's pipeline own its own checks?
  • Who has authority to approve production changes for each layer — the same approvers for both, or does each team own its own production gate?
Solution outline principal

Approach. Two independent pipeline families, each following the same shape internally (fmt/lint, plan or what-if, policy-as-code, environment-gated apply with human approval at prod — unit 09/12) but owned and operated separately, since the platform and app teams have different change cadences and different approvers. The coupling point — Bicep needing a value only Terraform's state knows, like a VNet resource ID — is resolved by the platform team's pipeline publishing its relevant outputs (via a small script or internal API, never raw state access) to a location app teams' `.bicepparam` generation step reads from at deploy time, making the dependency explicit and one-directional rather than either tool reaching into the other's internals. Both pipelines use workload-identity-federated credentials scoped per environment (unit 09/10), and a shared policy-as-code ruleset (tagging, naming, security baselines) is evaluated against both Terraform's plan JSON and Bicep's `what-if` JSON through a common thin adapter, so organization-wide rules don't have to be maintained twice in two different policy languages.

Terraform pipeline (platform team)          Bicep pipeline (app team)
  plan -> policy check -> approve -> apply    what-if -> policy check -> approve -> apply
       |                                              ^
       +--- publishes outputs (VNet ID, etc) ---------+
            to a small internal outputs store/API
            (never raw state access from the Bicep side)

Shared: workload-identity federation per env; common policy ruleset via a
        plan-JSON/what-if-JSON adapter feeding one Rego/OPA policy set

Trade-offs to name unprompted

  • Keeping the two pipeline families separate (rather than one unified mega-pipeline) costs some coordination overhead but avoids either team's pipeline being blocked by the other's release cadence or ownership model.
  • Publishing outputs through an intermediate store rather than granting Bicep pipelines direct read access to Terraform state avoids the coupling risk from unit 07's cross-tool ownership discussion, at the cost of one more moving part to maintain.
  • A shared policy ruleset via an adapter avoids duplicating governance logic in two policy languages, but the adapter itself becomes a piece of shared infrastructure someone has to own and keep working as both tools' JSON output formats evolve.
  • If the platform layer changes rarely relative to app deployments, the coupling point is low-traffic enough that this design's complexity may be more than needed — a simpler, more manual output-sharing process might be the pragmatic starting point, with automation added once the volume justifies it.

16Night-before cheat sheet

The ten questions most likely to open the conversation, compressed to one sentence each. If you only have five minutes before the loop starts, read this section.

  1. Why does Terraform need a state file at all? — Because HCL is declarative and describes desired end-state, not a sequence of steps, so Terraform needs its own record of what it created and each resource's last-known attributes to compute a diff against reality and know what maps to what.
  2. What's the real difference between `count` and `for_each`? — `count` indexes by position (0, 1, 2…) so removing a middle item shifts and can recreate everything after it; `for_each` indexes by a stable map/set key, so removing one item only affects that item.
  3. Does `sensitive = true` keep a value out of the state file? — No — it only redacts CLI/plan/apply output; the value is still written to state in full unless a write-only argument (1.11+) was used instead.
  4. Bicep or Terraform? — Terraform for multi-cloud or an existing HCL investment; Bicep for Azure-only estates wanting zero-lag access to new Azure APIs and no state file to manage — most real organizations run both, with a clear ownership boundary.
  5. What is OpenTofu and why does it exist? — A Linux Foundation fork of the last MPL-licensed Terraform, created after HashiCorp's August 2023 BUSL relicensing, giving the ecosystem a fully open-source alternative with no licensing ambiguity for internal use.
  6. What are ephemeral resources and write-only arguments? — Stable since Terraform 1.10 (Dec 2024): a way to fetch or mint a short-lived value (a Vault token, a generated password) and feed it into a resource argument that's used during apply but never persisted to the state or plan file at all.
  7. Why do Deployment Stacks matter for Bicep? — Before them, ARM had no way to delete a resource just because it was removed from the template — Deployment Stacks (GA ~May 2024) track a template's managed resources and can clean up what's no longer in it, closing Bicep's biggest structural gap versus Terraform state.
  8. What's the biggest state management mistake candidates describe? — One shared state file across unrelated teams or lifecycles, so an unrelated team's mistake, stuck lock, or blast radius spills onto resources they don't even own — split state along ownership/lifecycle boundaries instead.
  9. What should run before every production `apply`? — A fresh `plan` (or `what-if`) reviewed by a human, evaluated against policy-as-code, with the identity executing the apply scoped to exactly that environment via short-lived, workload-identity-federated credentials.
  10. What actually changed most recently worth naming unprompted? — Terraform 1.16.1 is current stable (2 Sept 2026) with 1.17-alpha trialling deferred actions for dynamic `count`/`for_each`; Bicep CLI is at 0.47.16 (8 Sept 2026) with `.bicepparam extends` for parameter-file inheritance; AVM is now the default module source for Azure landing zones in both ecosystems.

One last currency check before you walk in: Terraform 1.16.1 stable / 1.17 alpha (deferred actions, `-minimal-refresh`, experimental `terraform query`); ephemeral resources and write-only arguments stable since 1.10 with renewal lifecycle support since 1.11; OpenTofu 1.12.0 stable under the Linux Foundation; Bicep CLI 0.47.16 with `.bicepparam extends` and experimental module documentation generation; Deployment Stacks GA since ~May 2024; Azure Verified Modules is the default landing-zone module source, with the old hand-rolled ALZ-Bicep repository archived.
