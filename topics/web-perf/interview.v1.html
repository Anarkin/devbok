Web performance & browser platform

interview · reference stack: Chrome 153 stable / Core Web Vitals spec · released 2026-09-08

Interviews on this topic test three layers: whether you know what the browser is actually doing between a URL and a painted pixel, not just the vocabulary (parse, style, layout, paint, composite); whether you can move Core Web Vitals and explain why a fix works, not just recite thresholds; and, once you are past API recall, whether you can make and defend architecture-level performance trade-offs — a caching layer, a bundling strategy, an incident response to a regression that shipped last Tuesday. Work down the sub-area table in order: the first six sub-areas are asked in nearly every front-end performance interview regardless of level, the rest separates mid from senior from principal. This bank is framework-agnostic by design — no React/Angular rendering internals, which live in their own banks. One currency note up front: as of INP’s most recent guidance (web.dev, updated September 2025) the Core Web Vitals thresholds — LCP ≤2.5s, INP ≤200ms, CLS ≤0.1, all at the 75th percentile — are unchanged since INP replaced FID in March 2024, but the mechanics underneath keep moving: Chrome 133 changed how cross-origin image LCP timing is measured, and the Speculation Rules API (the modern, JSON-based replacement for the long-deprecated <link rel="prerender">) picked up server-side tag filtering in Chrome 136 and target_hint support in Chrome 138 — exactly the kind of detail that separates a candidate who learned Web Vitals once from one who tracks the platform.

01 Rendering path & critical CSS

This is the universal screener: can you narrate, accurately, what the browser does between a URL and a painted pixel, and where a page can get stuck along the way. Principal-level candidates are expected to go further — to reason about the cost of style recalculation at scale, and to defend a critical-CSS strategy against its own build-time complexity.

Docs: web.dev — Critical Rendering Path

Walk through what happens from hitting Enter on a URL to the first pixel on screen.screener

Navigation resolves DNS, opens a TCP (or QUIC) connection and does the TLS handshake, then the server streams HTML. The parser builds the DOM incrementally while the preload scanner looks ahead for CSS, JS and other subresources it can start fetching early. CSS builds the CSSOM in parallel; the two combine into a render tree of only the nodes that will actually paint. Layout ("reflow") computes geometry for that tree, paint records the drawing instructions per layer, and compositing assembles the layers on the GPU into the frame shown on screen.

Example

A server-rendered page with a blocking stylesheet in <head> and no synchronous script: DOM parsing continues the whole time CSS downloads, but render tree construction — and therefore first paint — waits for the CSSOM, so a slow stylesheet delays pixels even though the HTML itself parsed instantly.

Follow-ups

  • Where does the preload scanner fit in? It scans raw HTML ahead of the main parser to kick off fetches for scripts, styles and images before the parser reaches those tags.
  • Why is the render tree smaller than the DOM? It excludes nodes with no visual output — display: none, <head>, <script> — because they never need layout or paint.
  • What's the difference between layout and paint cost? Layout is geometry (position/size) and can cascade to ancestors and siblings; paint is per-layer pixel drawing and is usually cheaper unless the painted area is large.

Wrong answer

"The browser parses the HTML, then parses the CSS, then renders." This misses that HTML parsing and CSS/JS fetching are parallel via the preload scanner, and collapses layout/paint/composite into one undifferentiated "render" step — which fails the moment the interviewer asks what changed when they moved a transform animation off the main thread.

Why is CSS render-blocking by default, and when does that stop being true?screener

The browser can't build a correct render tree without knowing the final styles, so by default it withholds first paint until all discovered stylesheets have loaded — painting unstyled content and then repainting would be worse than a short blank screen (this is why browsers avoid a "flash of unstyled content"). A <link> stops being render-blocking when its media attribute doesn't match the current environment (e.g. media="print" on screen), or when it's loaded via the media="print" onload="this.media='all'" swap trick, or natively via rel="preload" as="style" combined with a deferred rel="stylesheet" swap.

Example

<link rel="stylesheet" href="print.css" media="print">
<!-- fetched at low priority, never blocks rendering on screen -->

Follow-ups

  • Does a non-matching-media link still get fetched? Yes, at a lower priority, in case the media query starts matching (e.g. a window resize crossing a breakpoint).
  • What's the modern, standards-based way to mark a resource explicitly non-blocking? The blocking="render"/absence-of-it distinction and fetchpriority now give explicit control instead of relying on the media-swap hack for most cases.

Wrong answer

"CSS always blocks rendering, full stop." Candidates who say this can't then explain why a print stylesheet or a preloaded, later-swapped stylesheet doesn't tank LCP — a real pattern in production code they'll be asked to review.

What is "critical CSS" and how do you generate it correctly?mid

Critical CSS is the minimal set of rules needed to render the above-the-fold content correctly on first paint, inlined directly in <head> so the browser never blocks on a network round trip for it; the rest of the stylesheet loads asynchronously (preload + swap, or a deferred non-blocking link) and applies once ready. It has to be generated per breakpoint (or a representative set of viewports) because "above the fold" is layout-dependent, and it has to be regenerated whenever the page's markup or styles change, or it silently drifts from the real above-the-fold content and either under- or over-includes rules.

Example

A blog post template: critical CSS covers the header, hero image container and first two paragraphs' typography; everything for comments, footer and related-posts widgets ships in the deferred stylesheet.

Follow-ups

  • How big should inlined critical CSS be? Small enough not to itself become the new bottleneck — commonly kept under ~14 KB so it fits in the first TCP/QUIC congestion-window round trip.
  • What breaks if critical CSS goes stale? A flash of incorrectly-styled content when the real stylesheet swaps in, or missing above-fold styles entirely if a build step didn't rerun.
  • Is critical CSS extraction still worth it with HTTP/2+ multiplexing? Multiplexing removes the connection-limit reason for inlining, but the round-trip latency for the CSS request itself is unchanged, so inlining still wins the first-paint race on high-latency connections.

Wrong answer

"Just inline your whole stylesheet in <head> to avoid the extra request." This trades one problem for a worse one: every page now ships CSS for parts of the page it never uses on that route, bloats HTML (which itself has to be parsed before paint), and can't be cached separately from markup.

Explain the difference between preload, prefetch, preconnect and dns-prefetch.mid

dns-prefetch only resolves DNS early; preconnect does DNS + TCP + TLS, readying a full connection for a resource you're about to request — both are cheap hints for third-party origins. preload fetches a specific resource this page needs at high priority because the browser wouldn't otherwise discover it early enough (a font referenced only from CSS, a hero image behind JS); prefetch fetches a resource for a likely future navigation at low priority, so it doesn't compete with the current page's own critical resources.

Example

<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
<link rel="preload" href="/hero.avif" as="image" fetchpriority="high">
<link rel="prefetch" href="/next-step.js">

Follow-ups

  • What happens if you preload something the page doesn't use within a few seconds? Chrome logs a console warning for an unused preload; it wasted bandwidth and priority budget that a real critical resource needed.
  • Why does preconnect need crossorigin for fonts? Font fetches are always CORS requests, so a connection opened without matching credentials mode is a separate, wasted connection.
  • How many preconnects is too many? Each one holds a connection open at a real cost (memory, and on mobile, radio); more than 2–3 per page usually indicates hints being sprinkled rather than measured.

Wrong answer

"Preload everything important so it loads faster." Preload doesn't create bandwidth, it reorders priority — preloading too much just means everything competes at high priority again, which is the same congestion with extra bookkeeping.

async vs defer vs plain <script> vs type="module" — what does each do to the rendering path?mid

A plain synchronous script blocks HTML parsing while it downloads and executes, and can also block on CSSOM if it might read computed style. defer downloads in parallel without blocking parsing and executes in document order right before DOMContentLoaded — the right default for app logic that touches the DOM. async downloads in parallel and executes as soon as it's ready, out of order relative to other scripts, interrupting parsing at that point — good for independent scripts like analytics that don't touch the DOM. type="module" scripts are deferred by default and execute in dependency order.

Example

<script src="analytics.js" async></script>
<script src="app.js" defer></script>

Follow-ups

  • Why can a synchronous script block on CSS too? If it runs before the stylesheet finishes, and might call getComputedStyle or similar, the engine must first finish CSSOM to answer correctly — so script execution order can force a CSSOM wait even before render-tree construction needs it.
  • What order do multiple defer scripts execute in? Document order, regardless of which finishes downloading first.
  • Does async guarantee a script runs after DOMContentLoaded? No — it can run before, after, or interrupt parsing right when it becomes ready, which is exactly why DOM-touching code shouldn't use it.

Wrong answer

"Just add async to every script to make the page faster." async on a DOM-dependent script produces intermittent bugs — it works when the network is fast and the script happens to finish after parsing, and breaks under exactly the throttled conditions an interviewer will bring up next.

What makes style recalculation ("recalc style") expensive at scale, and how do you keep it cheap?senior

Recalc cost scales with selector matching complexity and the number of elements whose computed style might have changed, not raw stylesheet size alone: descendant and universal selectors force the engine to walk more of the tree to decide what matches, and changing a class high in the DOM (or on :root) can invalidate style for a huge subtree. Modern engines mitigate this well with bloom filters and invalidation sets, but pathological selectors and runtime style mutation (heavy CSS-in-JS churn, JS setting inline styles in a loop) still show up as long "Recalculate Style" entries in a profile.

Example

A design system that reads * { box-sizing: border-box } plus deep descendant selectors like .card .body p span forces broader matching than an equivalent flat, class-scoped selector would.

Follow-ups

  • Does selector specificity affect recalc cost? Not directly — specificity is a cascade tiebreak; matching cost is about how much of the tree the selector has to be tested against.
  • How would you find this in a real profile? The Performance panel's "Recalculate Style" entries, and their frequency/duration correlated with a specific interaction or class toggle.
  • What's the fix once you've found it? Flatten deep selectors, scope class-based styling instead of relying on cascade depth, and batch style/class changes instead of toggling per-element in a loop.

Wrong answer

"Minify the CSS and it'll recalc faster." Minification shrinks download size, not selector-matching work — a candidate who conflates the two hasn't actually looked at a style-recalc profile.

What does content-visibility: auto do, and what's the catch?senior

It tells the browser to skip layout, paint and (mostly) style work for an off-screen element's subtree entirely, only doing that work as the element approaches the viewport — a huge win for long pages (comment threads, big tables) where most content is never on screen at once. The catch is that skipped content has no layout size by default, so without a contain-intrinsic-size estimate the page's scrollbar and layout jump around as sections pop in, which can itself cause visible layout shift.

Example

.comment { content-visibility: auto; contain-intrinsic-size: auto 120px; }

Follow-ups

  • Does this help LCP? Indirectly — by removing rendering work for off-screen content, it frees the main thread to get the actually-visible content painted sooner.
  • Can you use it on the LCP element itself? No — you'd be hiding the thing you're trying to render fast; it's for content the user hasn't scrolled to yet.
  • What's contain-intrinsic-size: auto specifically for? It lets the browser remember the element's last real rendered size and reuse it as the placeholder, which is usually more accurate than a hand-picked constant.

Wrong answer

"It's just display: none for performance." display: none removes the element from layout and accessibility entirely; content-visibility: auto keeps it in the layout flow (reserving its space) and searchable/focusable, which is the whole point — conflating them misses why it doesn't break in-page find or anchor links.

How does CSS-in-JS at runtime change the critical rendering path compared to static CSS?senior

Runtime CSS-in-JS moves style generation into JavaScript execution: the browser can't discover styles via the preload scanner, style rules often aren't ready until the relevant JS has downloaded, parsed and run, and many implementations inject <style> tags or mutate stylesheets during render, which triggers extra recalculation as components mount. That's a strictly worse position on the critical path than a static stylesheet the preload scanner finds in the first bytes of HTML, which is why most CSS-in-JS libraries have moved toward build-time extraction (zero-runtime) to get back to shipping a normal, cacheable, early-discoverable stylesheet.

Example

A component library that generates class names and injects rules on first render will show a visible unstyled flash on a slow device, then a burst of style recalculation as thousands of dynamically-scoped classes get inserted.

Follow-ups

  • Does server-side rendering fix this? Partially — SSR can extract the critical style tags into the initial HTML response, but hydration can still trigger a second wave of style injection for anything not captured server-side.
  • What's the "zero-runtime" alternative? Compile-time extraction (e.g. build-step CSS extraction) that emits a normal static stylesheet, keeping the developer ergonomics without the runtime cost.

Wrong answer

"CSS-in-JS is just a developer-experience choice with no performance cost since it's all CSS in the end." The cost isn't the CSS itself, it's when and how the browser learns about it — late discovery and runtime injection are real, measurable regressions versus a static stylesheet, independent of how the CSS is authored.

You inherit a page that inlines every page's full stylesheet to "avoid the critical CSS problem." How do you evaluate whether to keep that approach?principal

Inlining everything removes one render-blocking request but pays for it on every subsequent navigation: the CSS can't be cached across pages, so it's re-downloaded and re-parsed on every route even though most of it is shared, and HTML payload (which itself must be parsed before paint) grows with every page. Whether that trade is right depends on the app's navigation pattern — a mostly-single-page app with rare full navigations pays the cost once and benefits from it every route thereafter; a content site with many first-visits and few repeat views per session may never get the caching benefit back and should split into a small cached shared stylesheet plus genuinely small per-route critical CSS.

Example

A marketing site where 80% of traffic is a single-page visit from search: inlining is defensible. The same approach on a logged-in dashboard with dozens of routes per session is actively worse than a cached shared stylesheet.

Follow-ups

  • What would you measure to decide? Repeat-navigation rate per session and the cache-hit rate a shared stylesheet would realistically get, from real analytics, not intuition.
  • Is there a middle ground? Inline only the truly critical subset per route and let a separate, long-cached stylesheet carry the rest — the standard critical-CSS pattern, at the cost of a build step.

Wrong answer

"Inlining is always wrong, you should always split critical CSS." Treating it as a universal rule instead of a navigation-pattern trade-off is exactly the kind of context-free answer that reads as memorized rather than reasoned, at a level where the interviewer is listening for judgment.

A teammate wants to delete the critical-CSS build step because "HTTP/2 multiplexing made it obsolete." How do you respond?principal

Multiplexing solved the connection-limit reason critical CSS was invented for in the HTTP/1.1 era — you no longer burn a connection slot per resource — but it did nothing about the physical round-trip latency of fetching the stylesheet at all, and render still blocks until that fetch (and parse) completes. On a low-latency, high-bandwidth connection the difference is a few tens of milliseconds and may genuinely not be worth the build complexity; on real-world mobile networks with 100–300 ms RTT it's still the difference between painting in one round trip or two, which shows up directly in LCP. The right response is to ask for the data — field LCP by connection type — rather than accept or reject the claim on protocol theory alone.

Example

Field data segmented by effective connection type in the CrUX report or RUM: if 4g/3g traffic shows a materially worse LCP than the desktop broadband cohort, that gap is exactly what inlining critical CSS closes.

Follow-ups

  • What would change your mind either way? A before/after A​/​B test on the actual site's traffic mix, not a synthetic lab run on fast Wi-Fi.
  • Is there a lower-maintenance alternative that keeps most of the benefit? rel="preload" as="style" plus fetchpriority="high" on the main stylesheet gets it fetched at the earliest possible moment without a separate critical-CSS build, trading some of the win for much less complexity.

Wrong answer

"HTTP/2 changed the rules so the old advice is dead" — or its mirror image, "always keep critical CSS no matter what." Both skip the actual question, which is a latency-vs-complexity trade-off that depends on the site's traffic and connection mix, not on which protocol version is in use.

02 Core Web Vitals: LCP, INP & CLS

Every level gets asked to define the three metrics; what separates them is whether you can explain the subparts underneath each one, translate a regression into the right fix, and reason about field data (what real users experienced) versus lab data (a single synthetic run) instead of treating Lighthouse as ground truth.

Docs: web.dev — Web Vitals

Define LCP, INP and CLS, and their "good" thresholds.screener

LCP (Largest Contentful Paint) is the render time of the largest image or text block visible in the viewport, capturing perceived load speed; good is ≤2.5s. INP (Interaction to Next Paint) is the longest interaction latency observed over the page's lifetime (with outliers discounted at high interaction counts), capturing responsiveness; good is ≤200ms. CLS (Cumulative Layout Shift) sums the impact of every unexpected layout shift that isn't the direct result of user input, capturing visual stability; good is ≤0.1. All three are scored at the 75th percentile of real-user sessions, not as a single-run average.

Example

A page with a fast hero image (LCP 1.8s), snappy filters (INP 90ms) but a late-loading ad slot that pushes content down (CLS 0.3) passes two of three CWV and fails the "poor" bucket on the third — which is enough to fail the overall CWV assessment.

Follow-ups

  • Why p75, not average? Average hides the tail; a metric that's great for most users and terrible for a meaningful minority still averages out fine, while p75 forces you to fix the experience for the worse-off three-quarters.
  • What replaced INP, and when? INP itself replaced First Input Delay (FID) as the responsiveness metric in March 2024, because FID only measured input delay, not the full interaction-to-paint latency.

Wrong answer

"CWV are lab metrics you get from Lighthouse." Lighthouse reports lab estimates from one simulated run; the metrics that actually gate Google's page-experience signal and that "good/needs improvement/poor" labels apply to are field data from real users, aggregated at p75 — a distinction that trips up candidates who've only ever looked at a CI Lighthouse score.

What are LCP's four subparts, and which one do most regressions live in?mid

Time to First Byte, Resource Load Delay (time from TTFB until the LCP resource's fetch actually starts), Resource Load Time (the fetch itself), and Element Render Delay (time from resource-ready to the element actually painting, often blocked by main-thread work or render-blocking CSS). In most real regressions the culprit is Resource Load Delay — the LCP image or font is discoverable by the browser late, because it's requested from CSS background-image, injected by JS, or simply not preloaded, so the fetch doesn't even start until well after TTFB.

Example

A hero image set via a JS-rendered <img> inside a client component: the browser can't discover it until the JS bundle has downloaded, parsed and run, adding the entire script's load delay onto the image's load delay before its own fetch even begins.

Follow-ups

  • How do you see these subparts in practice? Chrome DevTools' Performance panel breaks a recorded LCP into these four segments directly.
  • How does fetchpriority="high" help which subpart? Resource Load Time, by raising the LCP image above its default priority so it isn't queued behind less important requests.
  • Does preloading fix Render Delay too? No — preload only affects when the fetch starts and finishes; a slow render delay is a main-thread or CSS-blocking problem, not a resource-loading one.

Wrong answer

"LCP is just how long the biggest image takes to download." That's only Resource Load Time — ignoring TTFB, load delay and render delay means missing the subpart that's actually broken, and proposing the wrong fix (e.g. compressing an image that was never the bottleneck).

What counts as an LCP candidate element, and what doesn't?mid

Candidates are <img>, the poster of a <video>, an element with a CSS background-image, and block-level text nodes containing text (not their containers). SVG <image> counts; content painted by <canvas> does not, because the browser can't attribute canvas pixels to a specific loaded resource. Whichever candidate is largest within the viewport at any point up to the point of first user interaction (or timeout) becomes the reported LCP element, and the candidate can change as bigger elements paint in.

Example

A page that first paints a full-width skeleton <div> then swaps in a hero image: the div isn't a candidate (no background-image, no text), so LCP is reported against the image once it paints — which is why the skeleton doesn't "trick" the metric into reporting early.

Follow-ups

  • Can LCP fire more than once? The candidate can be reported multiple times as larger elements appear, but only the last reported value before interaction/timeout counts.
  • Does a video's playing frames count? No, only the poster image — there is currently no LCP signal for in-progress video playback.

Wrong answer

"LCP always refers to whatever image is biggest in pixels on the page." It's largest within the viewport at render time, and text blocks and background-images compete too — a candidate who only thinks "images" will misdiagnose an LCP regression caused by a huge headline text block.

Break down INP into its subparts and name a concrete fix for each.mid

Input delay is the time before an event handler starts, usually because the main thread is busy with an unrelated long task — fixed by breaking up long tasks so the thread can respond to input sooner. Processing duration is the handler's own execution time — fixed by doing less work synchronously: defer non-essential work, memoize, or move heavy computation off-thread. Presentation delay is the time from handler completion to the next frame actually painting — often caused by forced synchronous layout, huge DOM updates, or style recalculation triggered inside the handler.

Example

A search-as-you-type input that recalculates and re-renders a 5,000-row result list on every keystroke: input delay is fine, but processing duration and presentation delay both spike because the handler does synchronous, expensive DOM work before the next frame can paint.

Follow-ups

  • What's a "long task" precisely? Any task on the main thread running ≥50ms, measurable via the PerformanceObserver long-tasks API.
  • How do you yield mid-handler without losing the work? scheduler.yield() (or setTimeout(fn, 0) as a fallback) to break a long synchronous block into chunks the scheduler can interleave with input and paint.

Wrong answer

"INP is basically the new FID, so the fixes are the same." FID only measured input delay; INP also captures processing and presentation delay, so a page can have zero input delay and still fail INP purely on a slow handler or an expensive re-render — a case FID would never have flagged.

What triggers a layout shift for CLS purposes, and what's explicitly excluded?mid

A shift is any visible element whose start position changes between two rendered frames, without a matching, recent user gesture. The impact score multiplies the "impact fraction" (how much of the viewport moved) by the "distance fraction" (how far it moved). Shifts within 500ms of a real input event (tap, click, keypress) are excluded, on the theory that content appearing because the user asked for it isn't a stability bug — which is why a well-behaved accordion or modal doesn't hurt CLS.

Example

An ad that loads late and pushes an article's text down by 200px, three seconds after load with no user interaction, scores a large layout shift; a "Show more" button expanding content directly under the click that triggered it does not.

Follow-ups

  • Does transform-based movement count? No — CSS transforms don't change layout geometry, only the painted position, so an animation done via transform is invisible to CLS even though it visually moves.
  • What's the most common real-world CLS cause? Images and embeds without explicit dimensions, and late-injected banners/ads/cookie notices above existing content.

Wrong answer

"Any movement on the page counts against CLS." User-triggered, expected UI changes (an expanding menu, a tab switch) and transform-driven animation are excluded by design — treating all movement as harmful leads to over-engineering things like disabling legitimate expand/collapse interactions.

Despite the name, is CLS a literal running total of every shift for the whole page lifetime?mid

No — it's the largest "session window" score, not an unbounded sum. Individual shifts are grouped into windows that close after a 1s gap with no new shift, capped at 5s per window, and the page's CLS is the maximum single window's total, not the sum across the whole session. This exists so a page that's open for hours in a background tab doesn't accumulate an unbounded, meaningless score just from the passage of time.

Example

Three unrelated shifts scattered minutes apart, each in their own window, contribute only their own window's score to the max — they don't add together the way a naive "sum every shift ever" model would suggest.

Follow-ups

  • Why windows instead of a simple sum? To avoid unfairly penalizing long-lived pages (a tab left open all day) purely for staying open, while still catching a genuinely janky burst of shifts.
  • Does this change how you'd fix a bad CLS score? Yes — you're hunting for the single worst cluster of shifts, not trying to reduce a global count, so one bad late-loading widget often matters more than many tiny scattered ones.

Wrong answer

"CLS just adds up every shift score for the whole time the page is open." That model predicts long-lived tabs should always have terrible CLS, which isn't how the metric is defined and leads to chasing the wrong shifts when debugging.

Give three concrete, independent techniques to improve LCP on a real page.senior

(1) Make the LCP resource discoverable in the initial HTML and fetch it at high priority — a plain <img fetchpriority="high"> or a rel="preload", never a JS-injected or CSS-background-image-only hero. (2) Cut server response time (TTFB) via caching, edge rendering, or trimming server-side work that runs before the first byte. (3) Remove render-blocking resources ahead of the LCP element — defer non-critical CSS/JS, and don't let a synchronous script sit between the HTML for the LCP element and its paint.

Example

<img src="hero.avif" fetchpriority="high" width="1600" height="900" alt="…">

Follow-ups

  • Does lazy-loading the LCP image ever make sense? No — loading="lazy" on an above-the-fold, likely-LCP image is a well-documented anti-pattern; it delays exactly the resource you most want fetched immediately.
  • What's a fourth lever if those three aren't enough? Serve a smaller/better-compressed format (AVIF/WebP) so Resource Load Time itself shrinks.

Wrong answer

"Just compress the image more." If the bottleneck is Resource Load Delay (late discovery) or TTFB, shaving image bytes barely moves LCP — a candidate should diagnose the subpart before naming a fix, and image compression is the fix for exactly one of the four.

A page's Lighthouse score is 99 but real-user CWV in the field are poor. How do you explain that to a stakeholder?senior

Lighthouse runs one simulated session on a fixed device/network profile and reports lab metrics; field data (CrUX, or your own RUM) aggregates real sessions across the actual distribution of devices, networks and geographies your users have, at p75. The gap almost always means real users are on slower devices/networks than the lab profile, or are hitting a code path Lighthouse's scripted run never exercises — a personalized above-the-fold banner for logged-in users, a slow third-party script that only loads for a subset of traffic, or a CDN edge that's far from a meaningful user segment.

Example

Lighthouse (mid-tier "Moto G" emulation, fixed 4G throttling profile) reports LCP 1.9s; CrUX shows p75 LCP of 4.6s because 30% of real traffic is genuinely low-end Android on congested mobile networks that the emulation profile doesn't represent.

Follow-ups

  • Where would you look first to find the gap? CrUX segmented by device type and connection (effective connection type), or your own RUM breakdowns, to find which cohort is actually failing.
  • Is Lighthouse useless, then? No — it's a fast, reproducible regression check for CI; it's just not a substitute for field data when the two disagree.

Wrong answer

"The field data must be wrong, our Lighthouse score is great." Dismissing field data in favor of a synthetic score gets this exactly backwards — field data is what real users experienced and is what Google's page-experience signal is actually based on.

How do Core Web Vitals get measured for a single-page app that never does a full navigation?senior

Classic CWV are defined against a single hard navigation's lifecycle, so an SPA's later in-app route changes ("soft navigations") historically weren't measured at all by the field tools, which understated real experience for apps where most time is spent post-initial-load. Chrome has been rolling out soft-navigation detection so that INP and CLS can be attributed per soft-navigation segment, giving each virtual "page" its own vitals instead of lumping the entire session under the first hard load.

Example

A dashboard SPA where the initial load is fast (LCP 1.2s) but a client-side route change to a heavy chart view causes a 600ms-INP interaction: under soft-navigation attribution that regression is visible against the chart route, not hidden inside an aggregate for the whole session.

Follow-ups

  • Does this apply to CLS too? Yes — layout shifts are now attributable per soft navigation where supported, rather than only counted against the initial load.
  • What should teams do in the meantime for accurate SPA metrics? Instrument route changes explicitly with the web-vitals JS library, which can reset/attribute metrics per route change independent of browser-native soft-navigation support.

Wrong answer

"SPAs don't have Core Web Vitals since there's no real navigation." CWV are collected for the initial load regardless, and support for attributing them to in-app route changes has been actively developing — declaring the whole topic inapplicable to SPAs is a stale answer.

Why does a font swap sometimes cause a layout shift, and how do you prevent it without blocking text render?senior

When a web font hasn't loaded yet, the browser paints a fallback font (Flash of Unstyled Text) or paints nothing for a timeout window (Flash of Invisible Text), then swaps to the real font once it arrives; if the fallback and the web font have different metrics (x-height, average character width), text reflows and pushes surrounding content, registering as a layout shift. The fix is font-display: optional or swap combined with size-adjust/a matched fallback via the CSS font-metric-override properties (ascent-override, descent-override, size-adjust), so the fallback occupies the same box the real font will.

Example

@font-face {
  font-family: "Brand Fallback";
  src: local("Arial");
  size-adjust: 105%;
  ascent-override: 90%;
}

Follow-ups

  • Why not just font-display: block everywhere? It hides text for up to 3s while the font loads, trading a layout-shift risk for guaranteed invisible text — usually a worse user experience and worse for LCP if the LCP element is text.
  • Does self-hosting versus a font CDN change this? Not the metric-mismatch problem itself, but self-hosting removes an extra DNS/connection round trip, which shortens the window during which the fallback is shown.

Wrong answer

"Preload the font and the shift goes away." Preloading makes the real font arrive sooner but doesn't change whether its metrics differ from the fallback — on a slow connection the swap, and the shift, can still happen well before the preloaded font arrives.

Your team ships a feature that measurably improves lab Lighthouse LCP by 400ms but field p75 LCP doesn't move. How do you investigate?principal

Start from the fact that lab and field disagree, which means either the change doesn't reach the real-traffic mix the way it reached the lab run, or it helped a cohort that wasn't the one holding back p75. Check rollout coverage (was it behind a flag or A/B at less than 100%, diluting the field aggregate), check whether the change targeted a code path most real users don't hit (e.g. logged-out fast path when most traffic is logged-in), and segment field data by device/connection to see if the improvement shows up in a slice rather than the p75 headline.

Example

The fix preloads a hero image that only renders for anonymous visitors; if 70% of field traffic is authenticated and hits a different hero path, the lab run (always anonymous) shows the win while p75 — dominated by the authenticated path — doesn't move at all.

Follow-ups

  • What's the fastest way to rule out a rollout/sampling issue? Confirm the experiment's exposure percentage and check the field metric's sample size for the treatment arm before concluding the fix didn't work.
  • If coverage and cohort are both fine, what next? Re-check whether the lab scenario matches the real p75-dominant path at all — it may be measuring a best case that few real users experience.

Wrong answer

"Field data is noisy, give it another month." Waiting without segmenting is how real regressions hide behind aggregate noise for a quarter; the investigation is tractable in a day with the right breakdowns, and a principal-level answer finds the mismatch, not the patience to outlast it.

How would you design an internal CWV budget and alerting system for a multi-team org, so regressions are caught before they reach users at scale?principal

Two complementary layers: a fast, deterministic lab gate in CI (Lighthouse or a custom Puppeteer run against key pages/flows) that blocks obviously regressive PRs before merge, and a field-data layer (RUM piped into a dashboard, segmented by page template, device tier and connection) with alerting on p75 crossing budget thresholds, because lab gates alone miss real-world third-party and network variance. Budgets should be per-page-template, not site-wide averages, since a single global number hides which template actually regressed; ownership and alert routing should map to the team that owns that template, or the alert becomes noise nobody acts on.

Example

A checkout-flow template gets a stricter INP budget than a marketing blog template, alerts route to the checkout team's channel with the offending deploy/commit attached, and the CI gate blocks a PR that adds 200KB of synchronous JS to the checkout bundle before it ever reaches field data.

Follow-ups

  • How do you avoid alert fatigue? Alert on sustained budget breaches over a rolling window, not single-sample noise, and tie each alert to the most likely recent deploy/commit range.
  • What's the failure mode of a CI-only gate with no field layer? It can't catch regressions caused by third-party scripts, CDN issues, or real device/network distributions the lab profile never represents.

Wrong answer

"Set one global Lighthouse score threshold in CI and call it done." A single site-wide number in CI alone catches nothing about real-user distribution, gives no per-team ownership signal, and is exactly the setup that produces the "great Lighthouse score, poor field CWV" gap this whole unit is about.

03 JS execution, main thread & memory leaks

This sub-area is where responsiveness (INP) problems actually get fixed: the event loop, what counts as a long task, and where memory quietly leaks over a long session. Senior and principal candidates are expected to reason about garbage collection and worker offloading trade-offs, not just recite "debounce your handlers."

Docs: web.dev — Optimize long tasks

Explain the event loop: call stack, task queue, microtask queue, and where rendering fits in.screener

The call stack runs synchronous code to completion. Once it's empty, the microtask queue (promise callbacks, queueMicrotask) fully drains before anything else runs. Only after both are empty does the browser have a chance to render a frame and then pull the next macrotask (a timer callback, an event handler, an I/O callback) off the task queue — and it repeats. Because rendering only gets a chance between tasks, a single long-running synchronous task, or a microtask queue that keeps re-scheduling itself, starves the browser of any opportunity to paint or respond to input.

Example

Promise.resolve().then(function loop() {
  // never resolves further work back to a macrotask;
  // keeps re-queuing microtasks, starving rendering
  return Promise.resolve().then(loop);
});

Follow-ups

  • Where do requestAnimationFrame callbacks run relative to this? Right before the next repaint, after the microtask queue has drained, as part of the browser's rendering steps.
  • Is setTimeout(fn, 0) a macrotask or microtask? Macrotask — which is exactly why it's a valid, if crude, way to yield back to rendering and input.

Wrong answer

"JavaScript is single-threaded so nothing can be async." Conflates single-threaded execution with an inability to be responsive — the whole point of the event loop and the task/microtask split is enabling concurrency-like behavior on one thread, which is precisely what makes long-task avoidance possible.

What is a "long task," and why does it matter more now than it used to?screener

Any task on the main thread that runs for 50ms or longer, measurable via PerformanceObserver with entryTypes: ['longtask']. It matters because the main thread can't respond to input, run other JS, or paint while a task is running — and since INP became a Core Web Vital, a long task sitting between a user's tap and the resulting paint is a direct, measured responsiveness regression, not just a theoretical concern.

Example

const po = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) console.log(entry.duration);
});
po.observe({ type: 'longtask', buffered: true });

Follow-ups

  • Why 50ms specifically? It's roughly the threshold below which input still feels instantaneous even if the task briefly delays a frame; above it, users start perceiving lag.
  • What's the fix, in one sentence? Break the task into smaller chunks and yield control back to the event loop between them.

Wrong answer

"Long tasks only matter for animations." They matter for any input — taps, keystrokes, scroll-linked effects — and are specifically what INP measures; framing this as an animation-only concern misses the metric it's actually tied to.

When would you use requestAnimationFrame, requestIdleCallback, and scheduler.postTask/scheduler.yield respectively?mid

requestAnimationFrame is for anything that must be visually synchronized with the next paint — reading layout, driving a JS-based animation. requestIdleCallback runs work only when the browser is otherwise idle and about to miss nothing, good for genuinely low-priority background work, but it offers no guarantee of running soon and isn't supported everywhere (notably Safari has historically lagged). scheduler.postTask is the modern Prioritized Task Scheduling API: it lets you post work at an explicit priority (user-blocking, user-visible, background) so the browser can interleave it correctly with input and rendering; scheduler.yield() is for breaking a long synchronous function into chunks that yield control back to the scheduler, resuming after other pending, higher-priority work.

Example

async function processRows(rows) {
  for (const row of rows) {
    render(row);
    if (shouldYield()) await scheduler.yield();
  }
}

Follow-ups

  • What did people use before scheduler.yield existed? setTimeout(fn, 0) or requestIdleCallback as manual yield points — functional, but coarser and without priority control.
  • Would you use requestIdleCallback for analytics beaconing? Yes — it's a good fit for work that's fine to delay indefinitely and shouldn't compete with anything user-visible.

Wrong answer

"Just wrap everything in requestIdleCallback to be safe." Idle callbacks can be starved indefinitely on a busy page, so work that actually needs to finish soon (like finishing a user-triggered update) will silently stall if it's misclassified as idle-priority work.

Name the most common real-world causes of JS memory leaks in a long-lived web page.mid

Detached DOM nodes still referenced from JS (removed from the document but kept alive by a variable, closure, or cache), event listeners added but never removed (especially on window/document from a component that unmounts), timers/intervals that keep firing and holding closures after their owning view is gone, ever-growing caches or maps keyed by something unbounded (user IDs, request IDs) with no eviction, and accidental globals from a missing var/let/const or a leaked this in an event handler.

Example

function attachPanel(el) {
  const handler = () => update(el);
  window.addEventListener('resize', handler);
  // el is removed from the DOM later, but `handler`
  // closes over it and window still references handler
}

Follow-ups

  • Why are detached nodes specifically dangerous? Because the whole subtree they root stays alive too — one forgotten reference to a container can retain thousands of descendant nodes.
  • What's the framework-level version of this bug? A component's cleanup/unmount hook that doesn't remove its subscriptions, so every mount of a route leaves another listener behind.

Wrong answer

"JavaScript has garbage collection, so it can't really leak." GC only reclaims objects with no reachable references; every leak pattern above is a live, reachable reference the GC correctly refuses to collect — the leak is a logic bug, not a GC failure.

Walk through how you'd confirm and localize a suspected memory leak using DevTools.mid

The reliable approach is the three-snapshot technique: perform the suspected leaking action once (to warm up caches and let one-time allocations settle), take a heap snapshot, repeat the action, take a second snapshot, repeat again, take a third. Compare snapshots two and three filtered to objects allocated between them — anything still present that should have been freed (and keeps growing each cycle) is the leak, and the retainer tree for those objects shows exactly what's holding the reference.

Example

Opening and closing a modal 3 times, then diagnosing: if snapshot 3 still shows the modal's detached DOM tree retained by a subscription callback registered on open and never unregistered on close, the retainer path points straight at the missing cleanup.

Follow-ups

  • Why do the same action three times instead of once? The first run includes one-time setup allocations that aren't a leak; comparing runs 2→3 isolates only what grows on every repeat.
  • What's the quick first signal before doing a full heap-snapshot diff? The Performance panel's memory timeline, or the Task Manager's per-tab JS heap size, showing a sawtooth-that-never-returns-to-baseline pattern across repeated actions.

Wrong answer

"If memory usage goes up while using the app, that's a leak." Rising memory alone can just be normal allocation for legitimate live data; a leak is specifically memory that should have been freed after an action completes and wasn't — that's what the snapshot diff, not a single reading, actually proves.

Debounce vs throttle — how do they differ, and which fits a scroll-position handler vs a search-input handler?mid

Debounce delays execution until a pause of a given length in the event stream — it fires once, after activity stops. Throttle guarantees execution at most once per fixed interval while events keep firing — it fires periodically during continuous activity, not just at the end. A search-as-you-type field is a debounce case: you want one request after the user pauses typing, not one per keystroke. A scroll-linked visual effect is a throttle case: you want regular updates while scrolling continues, capped to a sane rate, not silence until scrolling stops.

Example

const onScroll = throttle(updateProgressBar, 100);
const onInput = debounce(runSearch, 300);

Follow-ups

  • What's a leading vs trailing debounce? Leading fires on the first event of a burst; trailing (the common default) fires after the burst's final pause — some UIs want both, e.g. immediate feedback plus a final settle.
  • Is requestAnimationFrame throttling ever better than a fixed interval? Yes for visual updates — it naturally caps to the display's actual refresh rate instead of a hand-picked millisecond interval that might not match it.

Wrong answer

"They're basically the same, just use whichever." Swapping one for the other changes user-visible behavior — a debounced scroll handler feels laggy and unresponsive during continuous scrolling, and a throttled search box fires far more requests than intended.

Why do single-page apps tend to accumulate memory over a long session in ways a series of full page loads doesn't?senior

A full navigation tears down the entire JS heap, DOM and all listeners for free — the browser's own process gives you a clean slate every time. An SPA that never reloads has no such reset: every route change is a manual cleanup responsibility, and any component, subscription, cache, or listener that isn't explicitly torn down on route exit survives into the next route and the next, compounding over a session that might run for hours. This is why "it works fine in a quick manual test" and "it degrades badly over an 8-hour shift" are both true of the same bug — the leak is real but linear, and only a long session makes it visible.

Example

A router that mounts a WebSocket subscription per page and only unsubscribes on the framework's unmount hook: if one route's component has a code path that skips cleanup (an early return, a thrown error in the cleanup function), every visit to that route adds one more live subscription that never dies.

Follow-ups

  • What's the practical mitigation if you can't find every leak immediately? A periodic full reload for very long-lived sessions (dashboards, kiosks) as a pragmatic safety net, alongside actually fixing the leaks.
  • How would you catch this class of bug in CI rather than in production after hours of drift? An automated test that repeats a route-navigation cycle N times and asserts heap size returns to baseline (within noise) after forced GC.

Wrong answer

"SPAs just use more memory than regular sites, that's normal." Baseline memory for a richer client-side app can legitimately be higher, but unbounded growth over time is never normal — treating growth as an inherent SPA property rather than a specific, fixable bug is the wrong frame entirely.

What problem do WeakMap, WeakRef and FinalizationRegistry solve, and what's the catch with each?senior

All three let code hold a reference to an object without that reference being enough, by itself, to keep the object alive — solving the classic "cache keyed by a DOM node/object that should die with the node" leak. WeakMap/WeakSet only allow object keys and aren't enumerable, which is exactly the safety rail that makes them work for caching metadata against live objects. WeakRef gives a dereferenceable-but-collectible handle to a single object, and FinalizationRegistry lets you register a cleanup callback for when an object is collected — but that callback's timing is intentionally unspecified and unreliable, so neither should be used for anything correctness-critical, only for optional cleanup/telemetry.

Example

const metadataFor = new WeakMap();
metadataFor.set(domNode, { lastSeen: Date.now() });
// entry disappears on its own once domNode is unreachable

Follow-ups

  • Why can't you iterate a WeakMap? Because entries can vanish between any two lines of code as GC runs, so a stable iteration order can't be guaranteed — the API deliberately doesn't offer one.
  • Would you rely on FinalizationRegistry to release a file handle or network connection? No — use an explicit close()/dispose() call; finalizers are a last-resort safety net, not a resource-management primitive.

Wrong answer

"Use WeakRef everywhere instead of normal references to prevent leaks." Weak references only help for genuinely optional, cache-like associations; replacing normal ownership references with weak ones causes objects to disappear out from under code that still needed them.

Explain generational garbage collection at a level that's actually useful for reasoning about performance, not just naming it.senior

Most objects are short-lived (a function's local variables, a temporary array in a loop), so V8 and similar engines split the heap into a small young generation, collected frequently and cheaply because most of it is already garbage by the time it's scanned, and an old generation for objects that survive multiple young-gen collections, collected less often but at higher cost because it has to trace more live references. The performance-relevant consequence is that objects promoted to old-gen are expensive to reclaim, so code that unintentionally keeps long-lived references to what should be short-lived data (a growing array pushed to every frame, a closure capturing a big object "just in case") forces more into old-gen and makes major collections more frequent and longer — which shows up as GC pauses stealing main-thread time exactly when you're trying to hit an INP budget.

Example

Allocating a new array every animation frame and discarding it is cheap (young-gen churn); accidentally accumulating those arrays into a module-level log that's never cleared promotes them to old-gen and turns a harmless pattern into a leak with real major-GC cost.

Follow-ups

  • How would you see a GC pause in a profile? As "Minor GC" / "Major GC" entries in the Performance panel's main-thread track, correlated with a frame drop or an INP spike.
  • Does this mean you should avoid creating short-lived objects to reduce GC work? Not usually — young-gen collection is designed to be cheap for exactly that pattern; the actual risk is objects that unintentionally survive into old-gen, not allocation volume itself.

Wrong answer

"Garbage collection is automatic so allocation patterns don't matter for performance." Generational GC is specifically tuned around the assumption of mostly-short-lived objects; violating that assumption at scale (accidentally retaining what should be ephemeral) is a direct, measurable performance cost, not a solved problem you can ignore.

When is offloading work to a Web Worker actually worth it for responsiveness, and when is it not?principal

It's worth it when the work is genuinely CPU-heavy and self-contained — parsing/transforming a large payload, image processing, complex client-side computation — because moving it off the main thread frees that thread for input and paint entirely, not just in smaller slices. It's not worth it for work that's already fast, or that needs frequent, fine-grained access to the DOM (workers have no DOM access at all), because message-passing and structured-clone serialization cost real time and complexity for data crossing the boundary, and can itself become the new bottleneck if the payload is large or the messages are frequent. The right test is comparing the main-thread cost saved against the serialization + orchestration cost added, on the actual data sizes involved — not "workers are parallel so they're always better."

Example

Parsing a 5MB CSV client-side is a clean worker win: one message in, one result out, large main-thread time saved. A worker that recomputes a small derived value on every keystroke is a poor fit: the per-message overhead of structured cloning can exceed the computation it's trying to offload.

Follow-ups

  • Does OffscreenCanvas change this trade-off? Yes for canvas-heavy workloads specifically — it lets a worker render directly without round-tripping pixel data through the main thread, removing the usual DOM-access limitation for that one case.
  • What's Transferable for, and why does it matter here? Transferring ownership of an ArrayBuffer (rather than cloning it) avoids the serialization cost entirely for binary data, which is often the difference between a worker being worth it and not.

Wrong answer

"Move all your heavy JS to workers to keep the main thread free." Blindly offloading ignores serialization cost, the DOM-access restriction, and orchestration complexity; a chatty worker exchanging small messages constantly can be worse for responsiveness than the same work chunked and yielded on the main thread.

A production dashboard's tab memory grows steadily over an 8-hour shift and eventually crashes, but you can't reproduce it locally in minutes. How do you approach this?principal

First, make the slow leak fast: script a headless session that repeats the dashboard's real usage pattern (route changes, live-data updates, filter changes) in a tight loop against a realistic backend, and watch heap size across hundreds of cycles instead of hours of wall-clock time — this turns an 8-hour production-only bug into a reproducible, minutes-long local one. In parallel, if it truly can't be reproduced locally (e.g. it depends on real-time data volume or a specific backend behavior), instrument production itself: sample performance.memory-equivalent signals or periodic heap snapshots from a canary session, and correlate the growth curve with specific user actions or data-volume milestones from real telemetry rather than guessing.

Example

A live-updating chart that appends every incoming websocket tick to an in-memory array for a "session history" feature no one asked to be unbounded: fine for the first hour, catastrophic by hour eight, and only visible once the loop-and-measure harness runs long enough or production telemetry shows the array's growth against tick count.

Follow-ups

  • What's your first mitigation while root-causing is in progress? A safe, user-invisible mitigation like a scheduled soft-reload during low-activity windows, so the symptom (the crash) stops hurting users before the cause is fixed.
  • How do you know the accelerated repro is actually the same bug? Compare the retainer tree/growth pattern from the fast repro's heap snapshots against whatever production telemetry (heap size samples, crash reports) you can get — matching shape, not just "also grows," is the bar.

Wrong answer

"Add a page reload button and tell users to refresh periodically." That treats a fixable engineering bug as a permanent user workaround, ships no actual diagnosis, and is the kind of non-answer that reads as avoiding the hard part of the problem rather than solving it.

04 Bundling & code-splitting

Every framework-agnostic performance interview probes whether you understand that JS cost isn't just download bytes, and whether you can split a bundle sensibly instead of either shipping one giant file or over-fragmenting into hundreds of tiny requests. At senior+ this extends to org-scale bundling trade-offs like module federation and legacy/modern differential serving.

Docs: web.dev — Reduce JavaScript payloads with code splitting

What is tree-shaking, and why does it depend on ES modules rather than CommonJS?screener

Tree-shaking is dead-code elimination at the module level: a bundler statically determines which exports are actually imported anywhere and drops the rest. ES module import/export declarations are static — fixed at parse time, not computed at runtime — so a bundler can build an exact reachability graph without executing any code. CommonJS's require/module.exports are just function calls and object mutations that can happen conditionally or dynamically, so a bundler generally can't prove a given export is unused without risking breaking the program, which is why CJS code tree-shakes far worse in practice.

Example

// ESM: statically analyzable, only `formatDate` is kept
import { formatDate } from "date-utils";

// CJS: bundler can't safely prove the rest is unused
const utils = require("date-utils");
utils.formatDate(x);

Follow-ups

  • Does publishing a library as ESM guarantee it tree-shakes well? No — it also needs side-effect-free modules (or an accurate "sideEffects" field in package.json) so the bundler is confident dropping unused exports won't skip an import-time side effect.
  • What's a common way libraries accidentally defeat tree-shaking? A barrel index.js that re-exports everything from one entry point, which can pull in modules with side effects the bundler can't safely exclude.

Wrong answer

"Tree-shaking removes unused code, so it works the same regardless of module format." The mechanism fundamentally requires static analyzability; a codebase or dependency still written in CommonJS gets little to no tree-shaking benefit no matter what bundler is used on top of it.

What is code-splitting, and what's the simplest way to introduce it in a modern app?screener

Code-splitting breaks one large JS bundle into multiple smaller chunks that load on demand, so a user pays for the code a route or feature actually needs rather than the entire application up front. The simplest lever is the dynamic import() expression, which every major bundler recognizes as a split point and turns into a separate chunk fetched only when that code path runs.

Example

button.addEventListener("click", async () => {
  const { openEditor } = await import("./editor.js");
  openEditor();
});

Follow-ups

  • Does code-splitting reduce total bytes shipped? Not necessarily — it changes when bytes are fetched, front-loading only what's needed for the current view and deferring the rest.
  • What's the most common first split point in a real app? Route boundaries — each page/route becomes its own chunk, which is usually the biggest win for the least effort.

Wrong answer

"Code-splitting means putting your JS in multiple files instead of one." Multiple files without on-demand loading (e.g. all of them still tagged in the initial HTML) is just splitting for its own sake — the actual benefit only shows up when a chunk's fetch is deferred until it's needed.

Route-based vs component-based code-splitting — how do you choose, and can you combine them?mid

Route-based splitting (one chunk per page/route) is coarse, easy to reason about, and usually captures most of the win with minimal risk of creating too many tiny requests. Component-based splitting (lazy-loading a specific heavy widget — a rich-text editor, a chart library — behind user interaction, independent of route) targets features that are expensive but not always needed even within a route that loads. Real apps combine both: route splits as the default granularity, with a handful of component-level splits for the specific heavy, conditionally-used pieces that would otherwise bloat every route that happens to include them.

Example

A settings page (its own route chunk) that also lazy-loads a chart library only when the user opens the "usage analytics" tab within that page — most visitors to settings never pay for the chart bundle at all.

Follow-ups

  • What's the risk of over-splitting? Too many small chunks means too many round trips and per-request overhead, which can net negative versus a slightly larger, well-cached shared chunk — especially before HTTP/2 multiplexing, and still measurable after.
  • How do you decide a component is "worth" its own split? Its size relative to the rest of the route, and how often it's actually used by visitors to that route — splitting a component used by 95% of visitors barely helps.

Wrong answer

"Split everything you can into its own chunk to be safe." Maximal splitting produces a request waterfall and duplicated shared dependencies across chunks unless the bundler's chunk-deduplication is tuned carefully — more splits isn't automatically better.

Why does JavaScript weight cost more than its download size alone?mid

Every byte of JS shipped also has to be parsed, compiled and executed on the main thread before it does anything, and that cost scales with device CPU, not network speed — the same bundle that downloads instantly on fast Wi-Fi can still take hundreds of milliseconds to parse and execute on a low-end phone. This is why "reduce bundle size" and "reduce main-thread JS cost" are related but distinct goals, and why a bundle that looks fine in a fast-network/fast-CPU lab test can still blow the INP budget for a large share of real users on cheaper devices.

Example

DevTools' Performance panel shows "Loading," "Scripting" and "Rendering" as separate time buckets for the same page load — a bundle can be small enough to download in 200ms and still cost 400ms of "Scripting" on a mid-tier Android device.

Follow-ups

  • What metric captures this specifically? Total Blocking Time in lab tooling, and INP in the field — both are sensitive to script execution cost independent of download size.
  • Does minification help the execution cost, not just download size? Marginally — smaller identifiers parse slightly faster, but the dominant lever for execution cost is shipping less code and less work per byte, not just shorter names.

Wrong answer

"If the bundle downloads fast, the JS cost is basically solved." This ignores parse/compile/execute time entirely, which is often the larger share of the cost on the low-end devices that dominate a global user base.

How do you structure vendor/common chunk splitting so caching actually helps, instead of invalidating everything on every deploy?mid

Separate rarely-changing third-party dependencies into their own vendor chunk(s) and application code into a different chunk, each named with a content hash so the browser can cache them independently and long-term (Cache-Control: immutable-style headers plus a hashed filename). Done well, a deploy that only changes application code invalidates just the app chunk's hash — the vendor chunk's hash, and therefore its cache entry, is untouched, so returning visitors re-download only what actually changed instead of the entire bundle.

Example

// webpack splitChunks, roughly
optimization: {
  splitChunks: {
    cacheGroups: {
      vendor: { test: /[\\/]node_modules[\\/]/, name: "vendor" },
    },
  },
}

Follow-ups

  • What defeats this strategy silently? A single dependency bump that lands in the same vendor chunk as everything else, invalidating the whole chunk's hash for an unrelated one-line version bump.
  • Is more granular splitting (one chunk per dependency) always better for caching? Not once you factor in per-request overhead; the practical sweet spot groups dependencies by how often they change together, not maximal separation.

Wrong answer

"Just put everything in one bundle with a content hash, caching handles the rest." A single hashed bundle means any change — app code or a dependency patch — invalidates the entire download for every returning visitor, which is exactly the problem vendor splitting exists to avoid.

Why do barrel files (a single index.ts re-exporting an entire module tree) hurt bundle size in practice, even with a modern bundler?senior

Importing one named export from a barrel still requires the bundler to resolve and evaluate the barrel module itself, which re-exports everything — and if any of those re-exported modules have module-level side effects the bundler can't prove are safe to skip, it has to include them defensively rather than risk breaking behavior. In large component libraries this can pull in dozens of unrelated components' code, and CSS-in-JS or global registration side effects, just to use one small utility, and it also slows down build-time module resolution because the bundler has to walk the whole re-export graph for every import.

Example

A UI library with export * from "./Button"; export * from "./Modal"; … in its index.ts: importing only Button from the package's root can still drag in Modal's code if the bundler can't safely eliminate it, inflating a "just the button" import far beyond its real size.

Follow-ups

  • What's the direct fix as a consumer? Deep-import the specific module (import Button from "lib/Button") instead of the package root, bypassing the barrel entirely.
  • What's the fix as a library author? Ensure modules are genuinely side-effect-free and accurately mark "sideEffects": false (or list the exceptions) in package.json so bundlers can safely tree-shake through the barrel.

Wrong answer

"Bundlers tree-shake perfectly now, so barrel files don't matter." Static analyzability doesn't remove the side-effect-safety problem; real-world component libraries with CSS imports or registration code at module scope routinely defeat tree-shaking through a barrel even in modern tooling, which is a documented, recurring bundle-size bug class, not a solved one.

Is shipping separate "modern" and "legacy" bundles (module/nomodule, or a browserslist-driven differential build) still worth the complexity?senior

It depends entirely on your actual legacy-browser traffic share: a modern bundle (targeting evergreen browsers, skipping most transpilation and polyfills) is meaningfully smaller and faster to parse than one compiled down for old engines, and the <script type="module"> / nomodule pattern lets capable browsers fetch only the modern bundle while older ones fall back — but maintaining two build outputs, two sets of source maps, and testing both paths is real, ongoing cost. If legacy-browser traffic is a rounding error (common for many consumer web apps now that evergreen browsers dominate), a single modern build stops being a risk; if you have material traffic on older engines (some enterprise/embedded contexts still do), the differential build earns its cost.

Example

<script type="module" src="app.modern.js"></script>
<script nomodule src="app.legacy.js"></script>

Follow-ups

  • How would you actually decide, rather than guess? Real analytics on browser/engine versions in your traffic, not an assumption — the answer differs wildly between a consumer SaaS and an internal enterprise tool.
  • What's the lower-effort middle ground? A single build targeted at a well-chosen "modern" baseline (browserslist config) instead of the lowest common denominator, without maintaining two full output pipelines.

Wrong answer

"Differential serving is legacy advice, nobody needs it anymore" (or its mirror, "always ship both, it's best practice"). Both skip the actual analysis — this is a traffic-composition question with a real cost on either side, not a settled universal rule.

Your org is considering module federation / a microfrontend architecture to let independent teams ship independently. What performance trade-offs would you flag before signing off?principal

Module federation trades build-time bundling guarantees for runtime composition: shared dependencies (a framework, a design system) now have to be resolved and deduplicated across independently-deployed remotes at runtime, and a naive setup either duplicates that shared code per remote (bloating total payload) or introduces a runtime dependency-resolution step that adds its own latency and failure modes. It also weakens the caching and code-splitting guarantees a single build can make, since the host has less visibility into what each remote will actually load, and a slow or failing remote can degrade the whole shell's experience unless isolated carefully with fallbacks. The trade-off can be worth it for genuine team-autonomy needs at scale, but it's a real performance cost, not a free architectural upgrade, and should be sized against how much team independence is actually blocked by a monorepo/single-build alternative.

Example

Three teams each shipping a remote that specifies React as a shared dependency: without careful version alignment and singleton configuration, a user can end up downloading React two or three times across remotes — the exact bundle bloat module federation was supposed to avoid.

Follow-ups

  • What would make you say no to this proposal? If the actual driver is deployment cadence, not genuine technical isolation needs — a well-organized monorepo with independent CI/CD pipelines often gets the same autonomy without the runtime composition cost.
  • What's the minimum you'd require before approving it? A shared-dependency versioning policy enforced in CI, a fallback/error-boundary story per remote, and a performance budget measured on the composed page, not each remote in isolation.

Wrong answer

"Module federation is the modern way to do microfrontends, so it's the right call for team independence." Treating it as a default rather than a trade-off skips exactly the shared-dependency and runtime-composition costs that make it a real architectural bet, not a strict upgrade.

How would you decide whether to migrate a large, mature webpack build to Vite/esbuild-based tooling?principal

Separate the two axes the tools actually differ on: development experience (esbuild/Vite's native-ESM dev server gives near-instant cold start and HMR, versus webpack's bundle-then-serve dev mode, which is the most immediately visible win) and production bundle characteristics (both can produce comparable, well-optimized output with enough configuration, so the production-size argument for migrating is usually weaker than the DX argument). The real cost is migration risk on a mature build: custom webpack loaders/plugins, complex code-splitting configs, and legacy-browser output requirements built up over years don't port over for free, and a large team's day-to-day dev-server speed improvement has to be weighed against the migration effort and the risk of subtly changing production output during the switch.

Example

A team with a straightforward webpack config, no exotic custom loaders, and slow local dev iteration (30s+ rebuilds) has a clean case: DX win, low migration risk. A team with heavily customized module-federation and legacy-transpilation webpack configs built over years has a much higher-risk migration where the production-output gap needs careful validation before the switch is worth it.

Follow-ups

  • What would you measure before and after, to prove the migration was worth it? Cold-start and HMR latency for dev experience, and production bundle size/CWV impact for the shipped output — not just "it feels faster."
  • Would you do a full-team switch or a gradual one? Gradual where the tooling allows it (e.g. running both build pipelines against the same output for a release or two) to de-risk the production-output comparison before fully committing.

Wrong answer

"Vite/esbuild is strictly faster, migrate immediately." Dev-server speed and production bundle quality are separate questions, and "strictly faster" ignores the real migration cost on a mature, customized build — a principal-level answer sizes the trade-off against the specific codebase, not tool reputation.

05 Caching, HTTP/2-3 & CDNs

Screeners here check whether you know the caching headers that actually ship in every production app; deeper questions probe the transport-layer reasons HTTP/2 and HTTP/3 exist, and at senior+, whether you can design and debug a multi-layer caching strategy (browser, CDN edge, service worker) that stays correct under frequent deploys.

Docs: MDN — HTTP caching

Explain the main Cache-Control directives, and the difference between no-cache and no-store.screener

max-age=N lets a cache serve the response for N seconds without asking the server. immutable tells the browser the resource will never change at that URL, skipping revalidation entirely even on a hard refresh — the right pair for content-hashed filenames. must-revalidate forbids serving stale content once max-age expires without checking the server first. The commonly confused pair: no-cache still allows caching, but forces a revalidation check with the server on every use before serving it; no-store forbids caching the response at all, anywhere — the right choice for genuinely sensitive, one-time data.

Example

Cache-Control: public, max-age=31536000, immutable   # hashed asset
Cache-Control: no-cache                               # HTML shell, always revalidate
Cache-Control: no-store                                # e.g. a one-time auth token response

Follow-ups

  • Why does that naming feel backwards? Historically inherited from HTTP/1.0-era semantics; it trips up almost everyone once, which is exactly why interviewers ask it.
  • What's stale-while-revalidate for? It lets a cache serve a stale response immediately while it revalidates in the background, trading strict freshness for a fast response on every request.

Wrong answer

"no-cache means don't cache it." That's no-store; confusing the two either weakens caching for security-sensitive data (thinking no-cache is enough) or breaks a page by forcing a network round trip on every request for content that should be cacheable.

How does content-hash-based cache-busting let you set an effectively infinite cache lifetime and still ship updates instantly?screener

Build tooling names each asset with a hash of its contents (app.9f2ab1.js), so the filename only changes when the content changes. That means the asset can be served with max-age=31536000, immutable safely — the browser will never need to re-check it, because a genuinely new version simply has a new URL. Freshness moves entirely to the reference: only the small, never-long-cached HTML (or a manifest) that points at the current hashed filename needs to update on deploy, and that one small file is cached with a short or no lifetime instead.

Example

<!-- index.html: short/no cache -->
<script src="/app.9f2ab1.js" defer></script>
<!-- app.9f2ab1.js: max-age=31536000, immutable -->

Follow-ups

  • What breaks if the HTML itself is also cached with a long max-age? Users can get stuck on an old HTML shell referencing hashed assets that a subsequent deploy has already deleted from the server/CDN, causing broken loads until the HTML finally expires.
  • How does this interact with a service worker? The service worker's own update check (and its cache of the HTML shell) becomes the actual freshness gate, so its update lifecycle needs the same care as the HTML's cache headers.

Wrong answer

"Just cache everything with a long max-age and cache-bust with a query string like ?v=2 when you deploy." Query-string busting works for the asset itself but is manual and error-prone at scale compared to automatic content hashing, and some caches (especially some CDN/proxy configurations) treat the query string inconsistently, which content-hashed paths avoid entirely.

What problem did HTTP/2 multiplexing actually solve, and what problem did it leave unsolved that HTTP/3 addresses?mid

HTTP/1.1 could only have one outstanding request per TCP connection (browsers worked around it with 6–8 parallel connections per origin, which is why domain sharding existed), so HTTP/2 multiplexed many concurrent request/response streams over a single connection, removing the connection-count ceiling and the overhead of opening many TCP+TLS handshakes. What it didn't solve is transport-level head-of-line blocking: all those streams still ride one TCP connection, so a single lost packet stalls every stream behind it in TCP's in-order delivery, even though the application layer thinks of them as independent. HTTP/3 runs over QUIC instead of TCP, where each stream has independent loss recovery, so one dropped packet only blocks the stream it belongs to.

Example

On a lossy mobile connection, an HTTP/2 page loading 20 resources over one TCP connection can have all 20 stall behind a single retransmit; the same page over HTTP/3 only stalls the one stream whose packet was lost.

Follow-ups

  • Does HTTP/2's HPACK header compression matter here too? It's a separate, real win (smaller repeated headers across many requests) but orthogonal to the head-of-line blocking issue.
  • Is QUIC TCP or UDP-based? UDP-based, which is precisely what lets it implement its own per-stream loss recovery instead of inheriting TCP's connection-wide ordering guarantee.

Wrong answer

"HTTP/2 solved head-of-line blocking by multiplexing requests." Multiplexing solved application-level queuing (only one request at a time), not transport-level head-of-line blocking from packet loss on the shared TCP connection — the two are commonly conflated and the distinction is exactly what motivated HTTP/3.

Compare cache-first, network-first and stale-while-revalidate as service-worker caching strategies — when would you use each?mid

Cache-first serves from cache if present, only hitting the network on a cache miss — best for immutable, content-hashed assets where "in cache" already means "current." Network-first always tries the network first, falling back to cache only on failure — best for content that must be fresh whenever possible (an API response, a live feed), with the cache purely as an offline fallback. Stale-while-revalidate serves the cached response immediately for speed, then fetches an update in the background for next time — a good default for content that's fine slightly stale but should self-heal quickly, like a navigation shell.

Example

self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => {
      const network = fetch(event.request).then((res) => {
        caches.open("v1").then((c) => c.put(event.request, res.clone()));
        return res;
      });
      return cached || network; // stale-while-revalidate shape
    })
  );
});

Follow-ups

  • Which strategy fits hashed JS/CSS bundles? Cache-first — a hit is definitionally current, so there's no reason to touch the network at all.
  • What's the risk of network-first with no timeout? A slow or hanging network request can block the fallback from ever kicking in, defeating the whole point of having an offline path.

Wrong answer

"Just use stale-while-revalidate for everything, it's the best of both worlds." It's a reasonable default, not a universal one — content-hashed assets waste a background network request for nothing under it, and genuinely must-be-fresh data (a price, a stock level) can show visibly wrong stale data if it's the strategy used there.

How do ETag/Last-Modified conditional requests work, and what do they save versus a plain re-fetch?mid

When a cached response's max-age has expired but the cache still has it, the browser can revalidate instead of blindly re-downloading: it sends If-None-Match with the stored ETag (or If-Modified-Since with the stored Last-Modified date). If the resource hasn't actually changed, the server replies 304 Not Modified with no body at all, and the browser reuses its cached copy — saving the full response payload while still confirming freshness with a request round trip.

Example

GET /styles.css
If-None-Match: "a1b2c3"

HTTP/1.1 304 Not Modified
ETag: "a1b2c3"

Follow-ups

  • Why prefer ETag over Last-Modified? An ETag is a content fingerprint, so it correctly detects "unchanged" even if a file's modified timestamp changed without its content actually differing (a common false-positive with Last-Modified alone).
  • If assets are already content-hashed and immutable, do you still need ETag? Not for those — immutable skips revalidation entirely; ETag matters for resources you can't give a permanently-fresh URL, like the HTML shell or an API response.

Wrong answer

"A 304 response means nothing was cached." It means the opposite — the cached copy was validated as still correct and reused; the round trip happened, but the (often much larger) body didn't need to be re-sent.

Why did browsers remove support for HTTP/2 Server Push, and what replaced the use case it was meant to solve?senior

Server Push let a server proactively send resources (a stylesheet, a script) before the client asked for them, aiming to skip a round trip for known-needed subresources. In practice it caused real problems — pushing resources the browser already had cached (wasted bandwidth, since push happened before the server could know), and interacting poorly with the browser's own prioritization and connection-coalescing logic — and measured wins were inconsistent to negative. Chrome removed support, and the ecosystem converged on Link: <url>; rel=preload response headers (or equivalent early hints) as a lighter-weight way to get the same "start fetching this sooner" benefit, letting the browser (which actually knows its cache state) decide whether to act on the hint rather than having the server unconditionally push bytes.

Example

103 Early Hints responses now let a server send preload links before the final response is ready, achieving the "start the subresource fetch earlier" goal without pushing a body the client might not need.

Follow-ups

  • Is Server Push still part of the HTTP/2 spec? Yes at the protocol level, but with no major browser client support left, it's effectively dead in practice for browser use cases (CDNs may still use push internally for other purposes).
  • How does 103 Early Hints avoid the cache-waste problem push had? It's still just a hint the browser evaluates against its own cache before fetching, rather than an unconditional push of bytes the client didn't ask for.

Wrong answer

"HTTP/2 Server Push is still the recommended way to speed up subresource delivery." It's deprecated in every major browser; recommending it in a current interview is exactly the kind of stale, unmaintained knowledge this topic is designed to surface.

A CDN cache key misconfiguration around the Vary header can cause cache poisoning or a cache-hit-rate collapse. Explain how, both ways.senior

Vary tells caches which request headers make responses meaningfully different, so the cache key should include them. Omit a header that actually changes the response (e.g. serving different HTML by Accept-Language without Vary: Accept-Language), and the cache can serve one user's language variant to a user who requested another — a correctness bug, and if it's user-specific enough, a real cache-poisoning/privacy issue. Conversely, over-including headers in Vary (varying on something like a full User-Agent string, or an unbounded header like Cookie) explodes the number of distinct cache entries for what's actually the same content, collapsing the hit rate because almost every request looks like a cache miss against a near-infinite key space.

Example

Vary: Accept-Language   # correct: language-specific responses cached correctly
Vary: Cookie             # dangerous: near-unique per user, hit rate collapses

Follow-ups

  • How would you diagnose a sudden hit-rate collapse after a deploy? Check whether a new Vary header (or a new, more granular value of an existing one) shipped alongside the deploy, by diffing response headers before and after.
  • What's the safer alternative to varying on Cookie for user-specific content? Split the response so the cacheable, shared part is served from the CDN and the genuinely per-user part loads separately (client-side or via a nested request) rather than making the whole page's cache key user-specific.

Wrong answer

"Vary is just a minor header, it doesn't affect caching behavior much." It directly determines the cache key; getting it wrong is one of the most common causes of both real production cache-poisoning incidents and silent cache-hit-rate collapse after a deploy.

Design a caching strategy across the browser cache, CDN edge cache and a service worker for an app that deploys multiple times a day, without users seeing stale content or losing most of the caching benefit.principal

Split by mutability, not by layer: content-hashed static assets (JS/CSS/images) get long, immutable caching at every layer — browser, CDN, and service-worker cache-first — since a new deploy simply produces new hashed URLs and never invalidates old ones. The HTML shell (and any manifest/entry point) is the one thing that must stay cheap to invalidate: short or no browser cache, a CDN cache with a short TTL plus instant purge-on-deploy capability, and a service worker that checks for a new version on each activation rather than serving a cached shell indefinitely. The service worker's own update lifecycle needs explicit handling — skipWaiting/clientsClaim or a user-facing "update available" prompt — so a deploy doesn't leave some tabs running an old shell against new hashed-asset URLs that may eventually get evicted server-side.

Example

Deploy 47 ships app.7f3a.js; deploy 48 ships app.9c1d.js and a new index.html pointing at it. The CDN purges only the HTML's short-TTL cache entry on deploy; every previously-cached hashed asset anywhere stays valid and untouched, so returning users re-fetch only the small HTML and the one changed chunk.

Follow-ups

  • How long do you keep old hashed assets available server-side? At least as long as the longest browser cache lifetime plus a safety margin, so a tab that's been open across a deploy can still fetch an asset its stale-but-still-running JS references.
  • What's the failure mode if the service worker isn't handled carefully? A user can get stuck on an old shell indefinitely if the service worker keeps serving its cached HTML and never checks for updates, effectively pinning them to a stale deploy.

Wrong answer

"Set a short max-age on everything so users always get fresh content." That sacrifices almost all of the caching benefit for assets that never needed to be re-validated in the first place; the actual lever for freshness-on-demand is the URL changing (via content hash), not a short expiry on everything.

A CDN-fronted production site starts serving stale content to a subset of users right after a deploy. How do you investigate?principal

Narrow "a subset of users" first: is it geography-correlated (a specific edge PoP didn't get purged, or purge propagation is still in progress), request-shape-correlated (a specific Vary-relevant header value whose cache entry wasn't invalidated), or client-side (their browser or a service worker is holding an old cached shell independent of what the CDN now serves)? Check CDN purge/invalidation logs for completeness and propagation status across PoPs first, since partial or delayed purge propagation is the most common real cause; if the CDN confirms it's serving current content everywhere, the problem has moved client-side, and the service worker's update lifecycle or the browser's own cache headers are the next suspects.

Example

A purge request that only invalidates the default cache key but not variants keyed by a language header: users on the majority-language variant see the update immediately, while a locale-specific variant continues serving the pre-deploy cached response until its natural TTL expires.

Follow-ups

  • What's the fastest way to confirm CDN vs client-side? Fetch the resource directly from an edge PoP (bypassing the browser cache, e.g. via curl with cache-control headers set to force revalidation) and compare against what affected users report seeing.
  • How do you prevent a recurrence? Purge by tag/surrogate-key covering all Vary-relevant variants on deploy, and monitor purge propagation completion as a deploy gate rather than assuming it's instantaneous everywhere.

Wrong answer

"Tell affected users to clear their browser cache." That only addresses the client-side branch of the investigation and skips actually determining whether the CDN itself is the source — and if it is, telling users to clear their cache does nothing since the CDN would keep serving the same stale response on their next request anyway.

06 Images & fonts

Images and fonts are where most real pages carry their heaviest bytes and their most avoidable layout shifts, so this sub-area is asked constantly and rewards concrete, current knowledge of formats and loading attributes over general principles. Principal-level questions push into pipeline design for many contributors and multi-metric trade-offs.

Docs: web.dev — Serve responsive images

How does srcset/sizes work, and why is it better than serving one large image and letting CSS scale it down?screener

srcset lists multiple resolutions of the same image with their intrinsic widths; sizes tells the browser how wide the image will actually be laid out at different viewport widths. The browser combines the two — before it even builds the render tree — to pick the smallest candidate that's still sufficient for the real display size and the device's pixel density, so a phone downloads a phone-sized file instead of the same multi-megabyte asset a 4K desktop gets. Scaling a single large image down with CSS still forces every visitor to download that large image's full bytes, regardless of how small it's ultimately displayed.

Example

<img src="photo-800.jpg"
     srcset="photo-400.jpg 400w, photo-800.jpg 800w, photo-1600.jpg 1600w"
     sizes="(max-width: 600px) 100vw, 50vw"
     alt="…">

Follow-ups

  • What does the browser use device pixel ratio for here? To pick a higher-resolution candidate on a high-DPI screen even at the same CSS display size, so text/detail in the image stays sharp.
  • What's <picture> for, versus plain srcset? Art direction and format negotiation — serving a genuinely different crop or format per condition, not just a different resolution of the same image.

Wrong answer

"Just serve the biggest version and let the browser/CSS resize it, it looks the same." It looks the same but costs every user the largest file's full download — the whole point of responsive images is not downloading bytes nobody will see at that size.

Why do explicit width/height (or CSS aspect-ratio) on an image prevent layout shift?screener

Without a known intrinsic size, the browser can't reserve the image's box in layout until the file has actually downloaded enough to reveal its dimensions, so surrounding content initially renders as if the image occupies zero space and then jumps when it loads — a classic, entirely avoidable layout shift. Declaring width and height (browsers compute the correct aspect ratio from those two attributes automatically since 2020) lets the browser reserve the right-sized box on the very first layout pass, before a single byte of the image has arrived.

Example

<img src="hero.avif" width="1600" height="900" alt="…">
<!-- browser reserves a 16:9 box immediately, no shift when it loads -->

Follow-ups

  • Does this work for responsive/fluid-width images too? Yes — combined with height: auto in CSS, the browser still derives the correct aspect ratio from the attributes and scales the reserved box with the container.
  • What about images with unknown dimensions, like user uploads? Store and serve the original dimensions alongside the URL at upload time specifically so this can't regress later.

Wrong answer

"Just set a fixed CSS height on the container to stop the shift." A fixed height that doesn't match the image's actual aspect ratio either crops/distorts the image or leaves whitespace, and doesn't scale correctly across breakpoints the way width/height-derived aspect ratio does.

Compare AVIF, WebP and JPEG for a real production image pipeline.mid

AVIF generally compresses smallest for equivalent visual quality, especially at lower bitrates, and supports wide color gamut and HDR, but it's the slowest to encode and support, while broad, still trails WebP/JPEG at the very old-browser tail. WebP is a well-supported middle ground — smaller than JPEG at equivalent quality, fast to encode, supported essentially everywhere in current browsers — and remains the pragmatic default when AVIF's encode cost or edge-case support gap isn't worth managing. Plain JPEG (or PNG for graphics needing lossless/transparency without WebP) is still the universal fallback for the rare client that supports neither.

Example

<picture>
  <source srcset="photo.avif" type="image/avif">
  <source srcset="photo.webp" type="image/webp">
  <img src="photo.jpg" alt="…">
</picture>

Follow-ups

  • Why not always pick AVIF and stop there? Encode time at scale (relevant for on-demand image pipelines under load) and a small but real gap in decode support/performance on lower-end devices are real operational costs, not just a browser-support checkbox.
  • How would you choose automatically instead of hand-picking per image? Content negotiation via the Accept request header at an image CDN/edge layer, serving the best format each client actually advertises support for.

Wrong answer

"Always use AVIF, it's the newest and smallest." Newest-and-smallest ignores encode cost at scale and the residual support/decode-performance gap; a pipeline decision should be based on your actual traffic's client capabilities and your encoding budget, not format recency alone.

Walk through the font-display values and when you'd pick each.mid

auto leaves the browser's default behavior (a short invisible-text block period, then swap). block hides text up to ~3s waiting for the font, then shows it — guarantees the intended typeface but risks invisible text and a late layout shift on slow connections. swap shows a fallback font immediately and swaps in the real font whenever it arrives, with effectively no block period — good when text must be visible immediately and a metrics-matched fallback (see the rendering-path unit) controls the shift. fallback is a short block then a short swap window, after which it commits to the fallback if the font still hasn't arrived. optional gives the browser full discretion to skip the swap entirely if the font isn't ready fast enough (typically judged by connection speed), which avoids any layout shift from a late swap at the cost of some users never seeing the custom font on that page view.

Example

@font-face {
  font-family: "Brand";
  src: url("/brand.woff2") format("woff2");
  font-display: optional;
}

Follow-ups

  • Which value would you use for the LCP element if it's a text block? Usually optional or a carefully metrics-matched swap — block directly delays the LCP paint of that text.
  • Does font-display alone prevent layout shift? No — it controls timing/visibility, not metrics matching; pair it with a fallback that matches the real font's metrics to actually prevent the shift.

Wrong answer

"Always use swap, it's the safest default." swap without a metrics-matched fallback is one of the most common causes of visible layout shift from font loading — it's a reasonable default only paired with that fix, not a universal safe choice on its own.

loading="lazy" on images — how should it be used, and what's the well-documented pitfall?mid

It's a native, zero-JS way to defer fetching images that are off-screen until the user scrolls near them, which is a real, easy win for image-heavy pages (long articles, product grids) — apply it to everything below the initial viewport. The pitfall is applying it to an above-the-fold image, especially a likely LCP candidate: field research has shown pages that lazy-load their hero image have measurably worse LCP than those that don't, because it delays the fetch of exactly the resource the page most needs to start loading immediately.

Example

<img src="hero.avif" fetchpriority="high" alt="…"> <!-- above the fold: never lazy -->
<img src="item-42.avif" loading="lazy" alt="…">      <!-- far below the fold -->

Follow-ups

  • Is there a middle ground for images just below the fold? They'll load a bit later than eager ones regardless, but the browser's lazy-loading heuristic already accounts for viewport proximity reasonably well — manual fine-tuning rarely beats leaving it to the browser except for the fold boundary itself.
  • Does loading="lazy" work without JavaScript? Yes — it's a native HTML attribute, no observer or script required, which is part of why it replaced most hand-rolled lazy-load libraries.

Wrong answer

"Lazy-load every image on the page to save bandwidth." Lazy-loading the LCP candidate is a direct, well-documented LCP regression — "more lazy-loading is always better" is exactly the mistake the guidance explicitly warns against.

Variable fonts vs shipping several static font files — what's the actual trade-off?senior

A variable font packs a continuous range of weights (and sometimes width/slant) into one file, so a page using regular, medium and bold of the same family downloads one file instead of three separate ones — a clear win when a design genuinely uses several weights of the same family. The trade-off is that a variable font's single file is larger than any one static weight, so a page using only one weight of a family is better served by that single static file; and variable fonts add rendering complexity (variation axes, sometimes inconsistent hinting) that occasionally causes rendering differences across engines that a static file doesn't.

Example

A design system using four weights of one typeface across a large app: one ~120KB variable font likely beats four separate ~40–60KB static files once weight variety is real. A marketing page using only "Bold" of that same family is better off with the single bold static file, not the larger variable one.

Follow-ups

  • Can you subset a variable font to reduce its size? Yes — restricting the variation range you actually use (e.g. weight 400–700 instead of the full 100–900) and subsetting to the character set you actually need both shrink it meaningfully.
  • Does this decision interact with caching? Yes — one shared variable font cached once across every page that uses any weight of it can beat several static files each cached per weight, if page-to-weight overlap is high across the site.

Wrong answer

"Variable fonts are always smaller since it's one file instead of many." One file isn't automatically smaller than the sum of what you actually use — it depends on how many weights/axes a given page really needs versus what the variable font packs in for the full range.

Self-hosting fonts vs a third-party font CDN like Google Fonts — what are the real performance and privacy trade-offs?senior

A third-party font CDN used to have a caching argument — if enough sites used the exact same hosted URL, users might already have it cached — but browsers now partition the cache per top-level site specifically to prevent cross-site tracking via shared cache timing, so that cross-site cache-sharing benefit is gone in every modern browser. What's left is a real cost: an extra DNS lookup and connection to a third-party origin (mitigated but not eliminated by preconnect), a dependency on that third party's uptime and latency, and a privacy consideration — the third party sees a request (with the visitor's IP and referrer) for every page load, which is a genuine data-sharing concern in privacy-regulated contexts. Self-hosting removes the extra origin, lets you set your own long-lived caching and combine it with subsetting/preloading precisely, and avoids sending visitor data to a third party at all, at the cost of you owning font file updates and delivery.

Example

A self-hosted woff2 preloaded from the same origin as the HTML avoids the connection-setup cost of a separate Google Fonts request entirely, and sidesteps any question about whether font requests constitute third-party data sharing under GDPR-style regulation.

Follow-ups

  • Is the caching argument for shared font CDNs still valid at all? No, not since browsers moved to double-keyed/partitioned HTTP caching specifically to prevent this kind of cross-site cache inference — it's outdated advice still repeated in older articles.
  • What's a real reason to still use a third-party font CDN? Convenience and automatic format/subsetting negotiation the CDN handles for you, if the extra connection and privacy considerations are acceptable for the context.

Wrong answer

"Use Google Fonts because the font will already be cached from other sites." This was true before cache partitioning became standard across major browsers; repeating it today is a specific, checkable sign of stale knowledge.

Design an image pipeline for a large content site where hundreds of contributors upload arbitrary original images, and the site needs to serve optimized, responsive images across many contexts.principal

Never serve a contributor's original upload directly: store it as the source of truth, then generate (or transform on-demand at an image CDN/edge layer, cached after first request) every size/format variant the site actually needs, keyed by a stable identifier plus the requested transformation parameters. Format selection should be automatic via content negotiation on the Accept header (AVIF/WebP/JPEG fallback chain) rather than authored per image, and responsive breakpoints should be generated from a small, deliberately chosen set of widths shared across templates, not ad hoc per page, so the CDN's transformation cache gets real reuse instead of a unique variant per page layout. Contributors should never need to think about any of this — the pipeline's job is to make an arbitrary, possibly huge, possibly wrongly-oriented or wrongly-formatted upload safe and fast automatically, including basic validation (max dimensions, stripping EXIF/orientation issues) at ingest.

Example

<img src="https://cdn.example.com/img/abc123?w=800&fmt=auto" … >
<!-- CDN decides AVIF/WebP/JPEG from Accept header, resizes on first request, caches the result -->

Follow-ups

  • How do you keep the transformation cache from exploding with unique variants? A curated, finite set of allowed width/quality parameters rather than accepting arbitrary values straight from page CSS, so requests collapse onto a small number of cacheable variants.
  • What's the failure mode if you skip ingest-time validation? A contributor's 40-megapixel unrotated phone photo becomes the "original" for every downstream transform, and orientation bugs or absurd source sizes propagate into every generated variant.

Wrong answer

"Ask contributors to resize and optimize their images correctly before uploading." That's neither enforceable nor scalable across hundreds of contributors with varying tools and skill levels, and it's exactly the kind of manual process an automated pipeline exists to remove.

You need to eliminate font-loading layout shift and improve LCP on a text-heavy site at the same time. Some of the obvious fixes for each pull in opposite directions — how do you reconcile them?principal

The tension: the fastest path to a good LCP for text is often to paint with a fallback font immediately (swap, or accepting the fallback) rather than waiting for the web font at all, but an unmatched fallback then causes the shift you're also trying to eliminate the moment the real font swaps in. The reconciliation is to make the fallback itself metrics-matched (via size-adjust/ascent-override/descent-override or a generated matching fallback) so the LCP-critical first paint happens immediately with the fallback, and the later swap to the real font causes no measurable shift because the box never changes size — getting both metrics right simultaneously instead of trading one for the other. Preloading the actual font file (so the swap, when it happens, happens as early as possible) is a complementary third lever that shortens the window during which the fallback is shown at all, without being required for either fix to work.

Example

A headline styled with a metrics-matched local fallback plus font-display: swap and a rel="preload" for the real woff2: LCP measures against the fallback's immediate paint, and CLS stays at zero because the swap doesn't change any box dimensions.

Follow-ups

  • Is there a tool that generates the matched fallback automatically? Yes — several font-metric-override generators (and some framework font-loading integrations) compute the override values from the two fonts' metrics automatically rather than hand-tuning them.
  • What if no fallback can be metrics-matched closely enough? Consider font-display: optional for that specific text so the browser can simply skip the swap on slow connections, avoiding the shift at the cost of occasionally not showing the custom font at all.

Wrong answer

"Pick one metric to prioritize since you can't have both." Treating this as an either/or trade-off misses that metrics-matched fallbacks solve the actual conflict directly — a principal-level answer finds the fix that satisfies both, not the one that sacrifices one for the other.

07 DevTools & Lighthouse

Interviewers use this sub-area to check that you actually profile things rather than guess: can you record and read a real trace, know what Lighthouse's score does and doesn't mean, and reason about throttling accuracy. Principal-level questions move into building measurement infrastructure (RUM, Lighthouse CI) rather than just using the tools ad hoc.

Docs: Chrome DevTools — Performance panel

Walk through recording a performance trace in DevTools and what you look for on the main-thread track.screener

Open the Performance panel, hit record (ideally with CPU/network throttling enabled to approximate a real device), perform the interaction or reload you're profiling, then stop. The main-thread flame chart shows nested call stacks over time; you're scanning for wide bars (long-running functions), red-flagged entries over 50ms (long tasks), and clusters of "Recalculate Style"/"Layout" entries that indicate forced synchronous work. The Summary panel for a selected range breaks time into Loading/Scripting/Rendering/Painting/Idle buckets, which tells you which category to dig into before you go hunting in the flame chart itself.

Example

A trace showing a single 400ms yellow (scripting) bar right after a button click, with no rendering activity until it finishes, is a textbook long task blocking the next frame — exactly the INP-relevant pattern this unit exists to catch.

Follow-ups

  • What does a purple bar in the flame chart usually mean? Rendering work — layout or style recalculation — as opposed to yellow (scripting) or green (painting).
  • How do you find what triggered a specific long task? Click into it in the flame chart to see its call stack, which names the function and often the source file/line responsible.

Wrong answer

"Just look at the total load time DevTools reports." A single aggregate number tells you nothing about where the time went; the whole value of a trace is the breakdown by phase and call stack, which is what actually points at a fix.

What does the Lighthouse performance score actually measure, and how is it computed?screener

It's a weighted composite of several lab metrics from one simulated run — historically including First Contentful Paint, Largest Contentful Paint, Total Blocking Time, Cumulative Layout Shift and Speed Index — each scored against a log-normal curve calibrated from real-world performance data, then combined with fixed weights (TBT and LCP typically weighted heaviest) into the single 0–100 score. It is explicitly a lab score from a single deterministic run under a fixed throttling profile, not a measurement of what your real users experienced.

Example

A page can score 95 in Lighthouse and still have a poor field LCP at p75, because the lab run's fixed conditions don't represent the actual distribution of devices and networks your traffic uses — the gap this unit's Core Web Vitals section covers in depth.

Follow-ups

  • Which metrics get the most weight? Total Blocking Time and Largest Contentful Paint typically dominate the weighting, which is why fixing main-thread blocking usually moves the score the most.
  • Does Lighthouse include INP directly? It doesn't simulate real user input the way field INP is measured; Total Blocking Time is Lighthouse's lab proxy for responsiveness.

Wrong answer

"The Lighthouse score is basically your Core Web Vitals score." It's a related but distinct lab composite with its own metric set and weighting; treating it as interchangeable with field CWV is the single most common confusion in this sub-area.

How do you use the Coverage tab to find unused JS/CSS, and what do you do with that information?mid

The Coverage tab (via the Command Menu) records which bytes of loaded JS and CSS actually executed/applied during a session, showing a per-file percentage and a red/green highlighted view of exact used vs unused ranges. It's most useful for finding whole modules or large code paths that are shipped but never run in the flow you tested — a strong candidate for code-splitting, a stale dependency that's no longer needed, or a CSS framework where only a small fraction of its rules are ever matched.

Example

Recording coverage for a typical user session on a dashboard reveals a charting library at 8% used — most of it is code paths for chart types the app never renders — a clear candidate for a lighter-weight alternative or a more surgical import.

Follow-ups

  • Does "unused" during one recorded session mean truly dead code? Not necessarily — it means unused for that session's interactions; a feature only reachable via a different flow will show as unused even though it's needed elsewhere, so coverage should inform, not dictate, removal.
  • How does this connect to code-splitting? Large unused chunks in a coverage report are exactly the code that should move behind a dynamic import() so it's not shipped to sessions that never use it.

Wrong answer

"Delete anything Coverage shows as unused." Coverage reflects one recorded session's code paths, not the whole app's real usage; deleting based on a single session risks removing code that's genuinely needed by a flow you didn't happen to exercise while recording.

How accurate is DevTools' simulated CPU/network throttling compared to a real low-end device, and what's the practical implication?mid

Simulated throttling slows down network timing fairly well but only approximates CPU slowdown by applying a fixed multiplier to script execution time on your actual (often fast, developer-grade) machine — it doesn't reproduce the different cache hierarchies, thermal throttling, or JIT behavior of genuinely weaker silicon, so it systematically understates real low-end-device cost, especially for GC pauses and JIT warm-up. The practical implication is that a page that looks acceptable under simulated "Mid-tier mobile" throttling can still perform meaningfully worse on the actual low-end devices in your real traffic, so lab numbers under simulated throttling should be treated as a floor, not a guarantee, and validated against field data or a real device when the numbers are close to a threshold.

Example

A page with heavy GC churn passes comfortably under DevTools' 4x CPU slowdown in a fast development laptop, but shows visibly janky scrolling on an actual budget Android device, where GC pauses cost proportionally more than the flat multiplier assumes.

Follow-ups

  • What's a better validation step when the stakes are high? Test on an actual representative low-end device (or a device lab/cloud testing service), not just simulated throttling.
  • Does network throttling have the same limitation? Less so — simulated network conditions are a closer approximation than simulated CPU, though they still don't capture real-world variance like packet loss or connection instability.

Wrong answer

"4x CPU throttling in DevTools is equivalent to testing on a real low-end phone." It's a rough, execution-time-only approximation that misses GC, thermal and architectural differences; treating it as equivalent to real-device testing is a common and consequential mistake for teams that ship regressions their lab numbers never caught.

When would you reach for the User Timing API (performance.mark/performance.measure) instead of relying on built-in Web Vitals?senior

Built-in metrics (LCP, INP, CLS) capture generic, browser-defined moments; they say nothing about app-specific milestones an interviewer's product actually cares about — "time to interactive dashboard," "time until search results are visibly ready," "time to first meaningful row in a data grid." Custom marks/measures around those milestones let you correlate a business-relevant moment with the standard metrics and with RUM data, and they show up directly in the Performance panel's timeline for easy correlation during profiling, and can be piped into your own analytics/RUM pipeline the same way Web Vitals are.

Example

performance.mark("search-results-start");
// … render results …
performance.mark("search-results-end");
performance.measure("search-results", "search-results-start", "search-results-end");

Follow-ups

  • Do custom marks replace Core Web Vitals reporting? No — they complement them; CWV remain the standardized signal for cross-site comparison and Google's page-experience assessment, custom marks are for your own product-specific insight.
  • How do you keep custom marks from becoming noise? Tie each one to an actual decision you'd make differently based on it — a mark nobody looks at in a dashboard is dead instrumentation.

Wrong answer

"Custom timing marks are redundant once you have Web Vitals." Web Vitals intentionally don't know anything about your specific product's meaningful moments; for anything beyond generic load/responsiveness/stability, custom instrumentation is the only way to measure what actually matters to your users.

You wire Lighthouse into CI as a merge gate and it starts failing builds intermittently on unrelated PRs. How do you fix the pipeline without just loosening the thresholds?senior

Lighthouse runs are inherently noisy — shared CI runner CPU contention, network variance to whatever it's testing against, and even browser startup jitter all shift lab metrics run to run — so a single-run gate against a tight threshold is expected to flip on noise alone, independent of any real regression. The fix is running multiple times per PR and gating on a median (or best-of-N) rather than a single sample, running against a stable, isolated target (a deployed preview build on consistent infrastructure, not a shared, variable CI runner) and, where possible, using a fixed hardware/throttling profile deliberately looser than your production monitoring thresholds so CI is a coarse regression check, not the source of truth for whether a real user's experience changed.

Example

Switching from "fail if score < 90 on one run" to "fail if the median of 5 runs regresses by more than a fixed delta from the base branch's median" removes most single-run noise while still catching a genuine regression a PR introduces.

Follow-ups

  • Should CI Lighthouse gates ever block a merge on an absolute score? Rarely a good idea — comparing against the base branch's own recent numbers is more robust to environment-specific noise than a fixed absolute target.
  • What's the complementary check you'd still want in production? Field RUM/CrUX monitoring, since a CI lab gate can't catch regressions that only show up under real traffic and device diversity.

Wrong answer

"Just raise the failure threshold until it stops complaining." That papers over the noise by making the gate less sensitive everywhere, including to real regressions, instead of fixing the actual source of variance in how the check is run.

You have a trace with a long task, layout thrashing, and third-party script activity all overlapping in the same few hundred milliseconds. How do you prioritize what to fix first?principal

Don't fix in the order you noticed them — establish causality first: expand the flame chart's call stacks to see whether the long task's own code is what's triggering the layout thrashing (e.g. a loop reading offsetHeight after mutating styles), whether the third-party script is what's causing the long task in the first place, or whether all three are actually independent and just happen to overlap by coincidence of timing. Fix root causes before symptoms: a long task caused by a first-party layout-thrashing loop is fixed by batching reads/writes, not by trying to "optimize" the third-party script that merely happened to run nearby; a third-party script that's actually the trigger needs isolation (a worker, deferred loading, or removal) rather than trying to fix layout code that's a downstream victim.

Example

Expanding the call stack shows the long task is your own code, inside it a loop alternates el.style.width = … with el.offsetWidth reads across 200 elements (forced synchronous layout each iteration), and a third-party pixel-tracking script's unrelated task merely happens to run in the same recorded window — fixing the read/write batching resolves the actual long task; the third-party script needs no action at all despite being visually adjacent in the trace.

Follow-ups

  • How do you distinguish coincidental overlap from causation quickly? Reproduce with the third-party script blocked (or the app code short-circuited) and see which change actually removes the long task from the trace.
  • What's the risk of fixing in "trace order" instead? Spending effort on a symptom (the third-party script) while the actual root cause (your own thrashing loop) ships unfixed and keeps regressing under slightly different conditions.

Wrong answer

"Fix whichever one is visually the widest bar in the trace." Width alone doesn't tell you which is cause and which is effect, or which is even the same execution path — a principal-level answer establishes causality first, since fixing the wrong one leaves the actual problem untouched.

Would you build an internal RUM pipeline, rely solely on CrUX, or both? Walk through the trade-off.principal

CrUX is free, requires no instrumentation, and is exactly what Google's page-experience signal uses — but it's aggregated at origin/URL granularity over a 28-day rolling window, has a minimum-traffic threshold below which a URL simply isn't reported, and gives you no ability to segment by your own business dimensions (logged-in vs anonymous, plan tier, feature flag cohort) or correlate a regression with a specific deploy in near-real-time. An internal RUM pipeline costs real engineering investment (instrumentation, storage, dashboards) but gives you same-day visibility, arbitrary segmentation, and the ability to tie a regression to a specific release — the thing you actually need to debug quickly rather than wait weeks for CrUX's rolling window to reflect a fix. In practice most mature teams run both: CrUX (or PageSpeed Insights on top of it) as the outside-in, standardized comparison point, and RUM as the fast, internal, segmentable signal that actually drives day-to-day engineering decisions.

Example

A regression shipped Tuesday shows up in your own RUM dashboard, segmented by release, within hours; the same regression wouldn't visibly move CrUX's 28-day rolling aggregate for weeks, by which time the team has already shipped and validated a fix through RUM alone.

Follow-ups

  • Is CrUX's traffic threshold a real limitation in practice? Yes for lower-traffic pages/sites — below a certain volume of eligible Chrome users, a URL or even a whole origin simply has no CrUX data at all, at which point internal RUM is the only field signal available.
  • What's the minimum viable version of internal RUM? The web-vitals JS library sending its results to any analytics endpoint you already have — a small first step that already gives same-day, segmentable field data.

Wrong answer

"CrUX is Google's official data so it's all you need." CrUX is a valuable, standardized signal but its granularity, latency and lack of business-specific segmentation make it insufficient on its own for actually driving fast, targeted engineering decisions — treating it as sufficient is a common blind spot at exactly the scale where fast regression detection matters most.

08 Rendering & compositing

This sub-area checks whether you understand what happens after layout — paint and compositing — and can reason about GPU layers, the properties that are cheap to animate versus the ones that force a full reflow. It comes up whenever an interview turns to animation jank or scroll performance specifically, rather than load-time metrics.

Docs: Chrome DevTools — rendering & performance

Why are transform and opacity considered "cheap" to animate compared to properties like width or top?screener

Animating transform or opacity can be handled entirely on the compositor thread, on layers already rasterized onto the GPU — the browser just moves or blends existing bitmaps, skipping layout and paint entirely for every frame of the animation. Animating width, top, or similar layout-affecting properties forces layout recalculation (and often paint) on every single frame, which runs on the main thread and competes with everything else happening there.

Example

A sidebar that slides in via transform: translateX() animates smoothly even while the main thread is busy with other JS; the same slide-in implemented by animating left visibly stutters under the same main-thread load.

Follow-ups

  • Does this mean layout properties should never be animated? Not never, but it's the first thing to change when an animation is janky — swapping to a transform-based equivalent is usually the highest-leverage fix available.
  • Is opacity always compositor-only? Only when the element is already promoted to its own layer; without that, the browser may still need to repaint, though it's still cheaper than a layout-affecting property.

Wrong answer

"All CSS properties cost about the same to animate, it's just a style change." Which pipeline stage a property change re-triggers — layout, paint, or composite-only — differs by property, and that's precisely what determines whether an animation can hit a smooth 60fps.

What is layout thrashing, and how do you fix code that causes it?screener

Layout thrashing happens when code alternates writes (changing styles/DOM) with reads of layout-dependent properties (offsetHeight, getBoundingClientRect(), etc.) inside a loop — each read forces the browser to synchronously flush any pending layout work to give an up-to-date answer, so alternating read/write/read/write forces a full synchronous layout recalculation on every iteration instead of once. The fix is batching: do all the reads first, store the values, then do all the writes, so layout is computed once instead of once per element.

Example

// thrashing: read after write, every iteration
els.forEach(el => { el.style.width = "10px"; console.log(el.offsetHeight); });

// fixed: batch reads, then writes
const heights = els.map(el => el.offsetHeight);
els.forEach((el, i) => { el.style.width = "10px"; });

Follow-ups

  • What DevTools signal points at this? Repeated "Forced reflow" / "Recalculate Style" entries stacked in the flame chart within a single function's execution.
  • Does this only happen in loops? The loop just makes it obvious and expensive; even a single interleaved read/write pair forces one extra synchronous layout that batching would avoid.

Wrong answer

"Reading layout properties is always free, it's just a getter." Properties like offsetHeight force a synchronous style/layout flush if one is pending — treating them as free reads is exactly what causes thrashing in the first place.

What does promoting an element to its own compositor layer actually do, and what's the risk of overusing it?mid

Promotion (via will-change: transform, a 3D transform, or other layer-triggering properties) tells the browser to rasterize that element separately from the rest of the page, so it can be moved, faded or transformed on the compositor thread without repainting its siblings. This helps exactly the animations described above — but each layer consumes GPU memory, and on memory-constrained devices (especially mobile) creating dozens of unnecessary layers can cause worse performance than not promoting at all, through increased memory pressure and more compositing work per frame.

Example

Applying will-change: transform to every card in a long scrollable list "just in case" creates hundreds of GPU layers simultaneously, which can measurably slow scrolling on a memory-constrained phone — the opposite of the intended effect.

Follow-ups

  • What's the disciplined way to use will-change? Apply it shortly before the animation starts and remove it after, rather than leaving it on statically for elements that aren't actively animating.
  • How do you see current layers in DevTools? The Layers panel shows each composited layer and its memory cost, which is the direct way to catch over-promotion.

Wrong answer

"Add will-change liberally to anything that might animate, it can only help." Layer promotion has a real memory and compositing cost; applying it broadly and permanently is a documented anti-pattern that can regress scroll and animation performance on constrained devices.

How would you diagnose janky scrolling on a page that has no obvious animations running?mid

Scroll jank without an explicit animation is usually one of: a scroll or wheel event listener doing synchronous work on the main thread (blocking the compositor's ability to keep up with scroll input), a sticky/fixed element with an expensive box-shadow or backdrop-filter that has to repaint every frame as it scrolls into a new position, or layout-affecting styles (like a resize-dependent calculation) recomputing on every scroll tick. Recording a Performance trace while scrolling and checking whether the main thread stays busy during scroll frames — versus the compositor handling it independently — tells you which category you're in.

Example

A non-passive scroll listener that calls event.preventDefault()-eligible logic (or just does heavy synchronous computation) on every scroll event forces the browser to wait for that handler before it can composite the next scroll frame, producing visible stutter even though nothing is "animating."

Follow-ups

  • What's the first thing to check about a scroll listener specifically? Whether it's registered with { passive: true }, which tells the browser it won't call preventDefault() and lets scrolling proceed without waiting on the handler.
  • What repaint-heavy CSS is a common hidden culprit? backdrop-filter or large blurred box-shadows on an element that repaints as it moves, which is expensive per frame even with no JS involved at all.

Wrong answer

"If nothing is animating, scroll jank must be a browser bug." Scroll jank almost always traces to a specific main-thread listener or expensive repaint, both of which show up clearly in a recorded trace — treating it as unexplainable skips the actual diagnostic step.

Explain paint containment (contain: paint / contain: layout) and when it's worth adding.senior

The contain property tells the browser that a subtree's layout/paint won't affect anything outside its box, which lets the browser skip recalculating ancestors or unrelated siblings when that subtree changes — scoping the blast radius of a style or content change to just the contained element. It's worth adding to independent, frequently-updating widgets (a live chat panel, a ticking counter, a chart that re-renders on data updates) embedded in a larger page, so their updates don't force the browser to re-check layout across the whole document on every change.

Example

.live-widget {
  contain: content; /* layout + paint + style + size */
}

Follow-ups

  • How does this relate to content-visibility: auto? content-visibility: auto implies containment and additionally skips rendering work entirely for off-screen content — containment alone doesn't skip work, it just scopes it.
  • What's the risk of applying it too broadly? If the contained element's true visual size depends on content that containment now hides from layout calculations, you can get incorrect sizing unless you also specify an explicit size or use contain-intrinsic-size.

Wrong answer

"Containment just means the element can't overflow its box." That's a visual-overflow concept unrelated to CSS contain; containment is specifically about isolating layout/paint recalculation scope for performance, not clipping visual overflow.

You have a data-visualization dashboard with hundreds of DOM-based chart elements that becomes unresponsive when the user pans/zooms. Canvas, SVG, or DOM+CSS — how do you decide?senior

DOM+CSS gives you the easiest accessibility, styling and event handling, but each element carries real layout/style/paint cost, and hundreds of them recomputing on every pan/zoom frame is exactly the scaling wall you're hitting. SVG keeps per-shape structure (useful for hit-testing individual data points and CSS styling) but still costs a DOM node and paint per element, so it scales better than plain DOM but not indefinitely. Canvas has no per-element DOM cost at all — you're drawing pixels directly — so it scales to very large element counts, at the cost of losing free accessibility, needing manual hit-testing for interactivity, and needing your own re-render logic. For hundreds of simple shapes with frequent full-scene redraws (pan/zoom), canvas is usually the right trade at this specific scale; for tens of interactive, individually-styled elements, SVG or DOM remains simpler and is often fast enough.

Example

A financial dashboard with 2,000 individually positioned DOM markers becomes unresponsive on pan because each pan frame recalculates layout/paint for all 2,000 nodes; redrawing the same data as canvas paths on each frame instead removes that per-node DOM cost entirely, at the cost of writing custom hit-testing for tooltips.

Follow-ups

  • What do you lose moving to canvas that you have to rebuild? Accessibility (screen-reader semantics), CSS styling/animation, and browser-native hit-testing/event dispatch — all become custom work.
  • Is there a middle ground? Rendering the bulk of static/simple markers to canvas while keeping a small number of interactive, accessible DOM overlays for the currently-focused elements only.

Wrong answer

"Canvas is always faster, just rewrite the whole dashboard in canvas." The right choice depends on element count, interactivity/accessibility requirements, and update frequency — a blanket rewrite trades away real DOM/SVG benefits (accessibility, easy styling) that may not need to be sacrificed at a smaller scale.

Field data shows real users experiencing jank during scroll on a page that scores well in every lab tool you've tried. How do you find what lab testing is missing?principal

Lab tools typically profile a fixed scenario (page load, a scripted interaction) on a fixed device/network profile — they usually don't reproduce the exact combination of real content length, real third-party scripts active at that moment, and the actual low-end device distribution in your traffic, any of which can produce scroll-specific jank that a load-focused lab run never exercises. Start from field signals that can localize it: RUM breakdowns by device class/OS (isolating whether it's low-end-device-specific), correlating with which third-party scripts were active in the affected sessions, and checking whether the jank correlates with page/content length (a symptom of unbounded DOM size or un-virtualized long lists that only shows up with real, larger production content, not a short lab fixture).

Example

Segmenting RUM by device tier shows the jank is concentrated on low-end Android devices with a specific ad-network script active — a combination no lab test that runs on a single throttling profile without that specific third-party script loaded would ever surface.

Follow-ups

  • What's a lab-testing change that would have caught this earlier? Testing with production-representative content length/DOM size and with real third-party scripts present, not a stripped-down or synthetic test fixture.
  • What field API would you reach for to get real per-session detail? The Event Timing / Long Animation Frames APIs, or a session-replay tool correlated with performance marks, to see what was actually happening on affected real sessions.

Wrong answer

"If lab tools show green, the page is fine and the field reports must be noise." Lab tools test a fixed, limited scenario; a real gap between clean lab results and a real field complaint is a signal that the lab scenario doesn't represent actual usage, not that the complaint is unfounded.

09 Third-party scripts

Third-party code — analytics, ads, tag managers, chat widgets — is a top real-world cause of performance regressions that first-party engineering doesn't fully control, so this comes up whenever an interviewer wants to know if you can isolate, budget and negotiate around code you didn't write and can't simply delete.

Docs: web.dev — Loading third-party JavaScript

What makes third-party scripts a disproportionate performance risk compared to first-party code of the same size?screener

You don't control their release cadence, their internal implementation, or when they change behavior — a third-party vendor can ship a heavier version of their script at any time with no warning and no code review on your side. They also frequently make their own network requests (analytics beacons, further script loads), run on your page's main thread competing directly with your own code, and in aggregate a page often has many of them simultaneously, so the combined cost is easy to underestimate by looking at any single one in isolation.

Example

A tag-management container that itself loads a dozen further third-party tags means auditing "one script tag" in your HTML actually means auditing a dynamically-changing dependency tree you have no visibility into at review time.

Follow-ups

  • What's a practical way to keep visibility into that risk? Ongoing monitoring (RUM segmented by which tags are active, or a recurring audit) rather than a one-time review, since the content can change without any deploy on your side.
  • Do all third parties carry equal risk? No — render-blocking synchronous scripts in the document head carry far more risk than an async-loaded, deferred analytics beacon; risk should be assessed per script's loading pattern, not treated uniformly.

Wrong answer

"Third-party scripts are risky mainly because of their file size." Size is a factor, but the bigger risk is loss of control — unreviewed, unversioned code that can change behavior at any time and often triggers its own further requests, independent of its initial download size.

How do async and defer change the risk profile of a third-party script tag, and when would you use each?mid

A plain synchronous <script src="..."></script> in the document blocks HTML parsing entirely until it downloads and executes — the worst option for a third party. async downloads in parallel with parsing but executes as soon as it's ready, potentially interrupting parsing at an arbitrary point; it's appropriate for independent scripts (most analytics) with no ordering dependency on other scripts or the DOM. defer also downloads in parallel but guarantees execution only after parsing completes and in document order relative to other deferred scripts; it's the safer default when a script needs the DOM to exist or needs to run after another deferred script.

Example

<script async src="https://analytics.example.com/tag.js"></script>

Follow-ups

  • Which is the safer general default for an unfamiliar third party? defer, since it never interrupts parsing at an arbitrary point and preserves execution order, which avoids a class of subtle bugs async can introduce.
  • Does either option avoid main-thread contention once the script runs? No — both only change when/how it's fetched and scheduled relative to parsing; once it executes, it still runs on the main thread and can still produce a long task.

Wrong answer

"async and defer both just make a script non-blocking, use whichever." They differ in execution timing and ordering guarantees in ways that matter for correctness, not just performance — picking the wrong one for a script with an ordering dependency is a real, recurring bug source.

Explain the resource-hint and isolation options (facade pattern, sandboxed iframe, fetchpriority) for reducing a heavy but required third-party widget's impact.mid

A facade pattern defers the real heavy widget (a video embed, a chat widget) behind a lightweight static placeholder that only loads the full third-party code on user interaction, so most visitors never pay its cost at all. A sandboxed <iframe> isolates a third party's DOM, CSS and (with a distinct origin) much of its script execution from your main document, containing layout thrashing or style conflicts, though it doesn't fully isolate main-thread contention if the iframe is same-process. fetchpriority="low" (or explicit preconnect/deprioritization) tells the browser this resource is less urgent than your critical first-party assets, competing less aggressively for bandwidth during the busiest loading window.

Example

A YouTube embed replaced with a static thumbnail image plus a play button that only injects the real iframe embed on click is the canonical facade pattern — visitors who never click never load YouTube's actual embed script at all.

Follow-ups

  • Does putting a script in an iframe fully solve main-thread contention? Not fully — browsers can still share process/thread resources depending on site-isolation policy, so an iframe helps mainly with style/DOM isolation and origin-based process separation, not a full guarantee of main-thread independence.
  • When is a facade pattern not appropriate? When the widget is core to the page's primary content and needs to be visible/interactive immediately — deferring something users need on first paint just moves the cost to a worse-perceived moment.

Wrong answer

"Just put every third-party embed in an iframe and the main page is safe." Iframes help with style/DOM isolation but aren't a complete guarantee against shared main-thread cost, and reflexively iframing everything (including things needed immediately) can hurt perceived load instead of helping it.

You're asked to add a new marketing tag to every page via the tag manager. How do you evaluate and gate its performance impact before approving?senior

Treat it like any other dependency addition: measure its actual cost in isolation (network payload, main-thread execution time, and any further requests it triggers) using a real trace, not the vendor's own claims; check its loading pattern (does it insert synchronously, does it block anything critical); and evaluate it against an existing performance budget rather than case-by-case intuition, so unrelated stakeholders can't each add "just one more tag" without a consistent bar. Where the business need is real but the measured cost is too high, negotiate loading conditions (defer it, load it only after a Core Web Vitals-safe point, or behind a consent/interaction gate) rather than a binary accept/reject.

Example

A proposed heatmap tool measured at 180ms of main-thread execution and its own two additional third-party requests gets approved only to load after the page's LCP element has painted, via the tag manager's trigger conditions, rather than firing immediately on page load alongside everything else.

Follow-ups

  • What ongoing control do you need once it's approved? A recurring audit or automated alerting (since tag-manager content can change without your review) and a hard performance budget the tag manager or CI enforces, not a one-time approval.
  • What's the organizational failure mode this guards against? Tag-manager sprawl — dozens of tags added by different stakeholders over time with no consistent performance review, which is one of the most common real-world sources of CWV regression at mid-size and large companies.

Wrong answer

"If marketing/legal needs it, approve it and optimize elsewhere to compensate." That treats performance budget as infinitely elastic and every new tag as a given; a real gate evaluates and negotiates the specific tag's cost and loading conditions rather than accepting it unconditionally.

You have zero control over a required third-party vendor's script and it's the single largest main-thread cost on your page. What are your actual options?principal

When you can't change the script itself, the remaining levers are all about when and how it runs relative to everything else: load it as late as possible (after your own critical content and metrics-relevant elements have already rendered), gate it behind a real user signal (visibility, interaction, idle time via requestIdleCallback) rather than eagerly on load, isolate it in a sandboxed iframe to contain any layout/style side effects even if main-thread execution cost remains, and negotiate directly with the vendor — contractually or via their own performance-conscious loading options if they offer any (many ad/analytics vendors now provide lighter or deferred loading modes precisely because this complaint is common). If none of that gets the cost down enough and the vendor is genuinely mandatory (a payment processor, a legal-compliance script), the realistic answer is to budget its cost explicitly into your Core Web Vitals targets rather than pretend you can fully eliminate it, and be transparent with stakeholders that a chunk of your performance budget is permanently allocated to a dependency outside engineering's control.

Example

A mandated payment-fraud-detection script that can't be removed or modified gets deferred to load only once the checkout form is actually visible (rather than on initial page load across the whole site), cutting its impact on every page that isn't checkout while still meeting the compliance requirement where it's actually needed.

Follow-ups

  • Is "just don't use that vendor" a real answer in an interview? Sometimes worth mentioning as a strategic escalation, but a strong answer engages with the constraint as given rather than sidestepping it — the interviewer is testing what you do inside real business constraints.
  • How do you communicate this trade-off to non-engineering stakeholders? Frame it in the metrics they care about — "this vendor costs us N ms of INP budget sitewide, deferring it to only the checkout flow recovers most of that on every other page" — rather than an abstract technical complaint.

Wrong answer

"There's nothing you can do about a vendor's own script." Loading conditions, gating, isolation and scope-limiting (only where actually needed) are all real levers even when the script's own code is completely out of your control — treating it as unfixable skips all of them.

10 Mobile & network conditions

The least-frequently-asked sub-area in this bank, but it still surfaces as a sanity check that you don't only reason about performance from a fast-office-Wi-Fi, high-end-device point of view — the majority of the world's web traffic is neither.

Docs: web.dev — Adaptive loading

What is adaptive loading, and what signals would you use to implement it?screener

Adaptive loading means shipping a different (typically lighter) experience to users on constrained devices or networks, rather than one-size-fits-all. The Network Information API (navigator.connection.effectiveType, saveData) and device-memory signals (navigator.deviceMemory) are the standard signals: a page might skip autoplay video, serve lower-resolution images, or defer non-critical features when effectiveType reports a slow connection or the user has explicitly enabled Data Saver.

Example

if (navigator.connection?.saveData || navigator.connection?.effectiveType === "2g") {
  // skip autoplay, serve a lower-res hero image
}

Follow-ups

  • Is browser support for these APIs universal? No — Network Information API support varies significantly by browser (notably weaker in Safari), so it should be treated as a progressive enhancement signal, not a guaranteed one.
  • What's the simplest adaptive-loading win with no API at all? Respecting prefers-reduced-motion and serving responsive images via srcset, which already adapt to viewport/density without any explicit network signal.

Wrong answer

"Adaptive loading just means responsive CSS breakpoints." Responsive layout adapts visual presentation to viewport size; adaptive loading specifically adapts what is fetched/executed based on device and network capability, which is a distinct (and largely orthogonal) concern.

Why can the same page feel fast on a fast Wi-Fi connection but slow on a real mobile network, even at similar reported bandwidth?mid

Bandwidth is only one factor; mobile networks typically have much higher and more variable round-trip latency, which disproportionately hurts pages with many sequential round trips (render-blocking resources, request waterfalls, redirect chains) since each round trip's fixed latency cost compounds. Real mobile conditions also include connection instability (brief drops, cell-tower handoffs) that a synthetic "throttle to X Mbps" test doesn't reproduce at all, and radio-layer wake-up latency on cellular can add meaningful delay to the very first request that a Wi-Fi test never pays.

Example

Two pages transfer the same total bytes at the same simulated bandwidth, but the one making 15 sequential round trips (uncombined requests, a redirect chain, render-blocking resources loaded one after another) pays 15x the per-request latency penalty, which is far more punishing on high-latency mobile than on low-latency Wi-Fi even at identical bandwidth.

Follow-ups

  • What's the practical lever this points to? Reducing the number of sequential round trips (via resource hints, HTTP/2 multiplexing, bundling critical resources) matters more on real mobile networks than bandwidth optimization alone.
  • Does simulated network throttling in DevTools capture latency variance? It approximates a fixed latency/bandwidth profile but not the instability (drops, handoffs) real cellular connections have, similar to the CPU-throttling gap covered in the DevTools unit.

Wrong answer

"If bandwidth is similar, network performance should be similar." Latency, round-trip count, and connection stability all matter independently of raw bandwidth, and mobile networks are systematically worse on exactly those dimensions even when a bandwidth number looks comparable.

A feature works well in your testing but field data shows it performing badly specifically for users on lower-end Android devices. What would you check first?senior

Segment the RUM data by device/OS to confirm the pattern is real and isolated (not confounded with, say, a specific browser version or region with its own network characteristics), then look specifically at CPU-bound costs — JS execution time, GC pauses, layout/paint cost — since low-end Android devices are disproportionately CPU- and memory-constrained relative to their network conditions, which is a different bottleneck than what most developer/test hardware reproduces. The DevTools CPU-throttling caveat from earlier in this bank applies directly here: your own testing on developer-grade hardware, even throttled, tends to understate exactly this class of regression.

Example

A new client-side data-transformation feature adds 150ms of scripting cost that's invisible on a flagship test device but blows past the INP budget on a two-generations-old Android phone with a much slower CPU and smaller CPU cache, which RUM segmented by device model would surface immediately.

Follow-ups

  • What's a concrete mitigation once confirmed? Move the expensive work off the main thread (a Web Worker) or behind adaptive-loading logic that gives constrained devices a lighter code path, rather than a uniform experience for all devices.
  • How would you validate a fix before shipping again? Test on an actual representative low-end device (or a cloud device-testing service), not just simulated throttling on developer hardware, given the known gap between the two.

Wrong answer

"If it worked in testing, the field regression is probably a fluke." Device-segmented field data showing a consistent, isolated pattern is a real signal, not noise; the fact that it didn't reproduce in testing points at a gap in the test environment (device class), not a flaw in the field data.

Your product has a genuinely global, device-diverse user base. How would you set performance budgets and targets given that diversity, rather than picking one number?principal

A single global target either overshoots for your most-constrained users (setting a budget that flagship-device users easily clear but that's unreachable on the low end, silently leaving a large minority of users with a poor experience the aggregate metric hides) or undershoots ambition for capable users. The principled approach segments budgets by real traffic composition — CrUX or RUM broken down by device/connection tier per market — and sets a tiered target: a stricter, achievable budget validated specifically against representative low-end devices/networks for the tiers that matter (often weighted by revenue or strategic market importance, not just raw traffic share), with monitoring that alerts per-segment rather than only on a blended global average that can mask a regression concentrated in one segment.

Example

A blended global p75 LCP that looks healthy can hide a genuinely poor experience concentrated in one large, low-end-device-heavy market; segmenting the target and the alerting by device/market tier surfaces that gap instead of averaging it away.

Follow-ups

  • What's the risk of over-segmenting budgets? Too many segment-specific targets becomes unmanageable and dilutes accountability; the practical answer picks a small number of meaningful tiers (e.g. "flagship," "mid-range," "low-end/2G") rather than one budget per device model.
  • How do you keep this from becoming an excuse to ignore low-end users? Explicitly tie the low-end tier's budget to a business metric (market size, revenue potential) so it has organizational weight, rather than treating it as an aspirational nice-to-have with no real enforcement.

Wrong answer

"Set one global performance budget based on the median device and move on." A single blended target masks exactly the segment-specific regressions and gaps that matter most for a genuinely diverse user base, which is the core problem a principal-level answer is expected to address head-on.

11 Judgment calls

These are open-ended, no single-correct-answer prompts an interviewer uses at senior/principal level to see how you actually think under ambiguity and organizational constraint, not whether you know a fact. Each collapsed answer below describes what a strong response demonstrates and which trade-offs it names unprompted — use them to rehearse your own reasoning out loud, not to memorize a script.

A VP wants the Lighthouse score to hit 100. Engineering knows the real bottleneck is a third-party script nobody controls. How do you handle the conversation?

A strong answer separates the metric from the goal: explains clearly (in business terms, not jargon) why the Lighthouse score and real user experience aren't the same thing, quantifies the actual gap and its real cost (using field CWV data, not the lab score), and reframes the conversation around the metric that actually matters to users and to the business rather than simply agreeing to chase 100. It names the trade-off unprompted: that "optimizing to satisfy a lab score" and "optimizing the actual user experience" can diverge, and that spending engineering effort gaming the former at the expense of the latter is a real organizational risk worth naming directly, even to a VP.

Your team has a hard performance budget, but the design team wants a large, high-fidelity hero image with a subtle looping background animation on every page. Where do you land?

A strong answer doesn't treat this as engineering-vs-design; it looks for the actual overlap — can the visual goal be achieved with a cheaper technique (a CSS-only animation on compositor-safe properties instead of a video loop, a well-compressed AVIF instead of an oversized PNG, an image that's the LCP element getting explicit priority hints) before treating budget and design intent as opposed. It names the real trade-off unprompted: that "no" and "yes" are both wrong answers to a design ask stated in isolation from its performance cost, and that the productive move is proposing a specific alternative that hits both goals, with the budget's actual numbers as the shared language for the negotiation.

You inherit a codebase with no performance monitoring at all. You have one sprint to establish a baseline before committing to any optimization work. What do you actually do?

A strong answer resists the urge to start optimizing immediately and treats measurement as the actual first deliverable: wiring up the web-vitals library (or checking existing CrUX coverage) to get field data flowing, running Lighthouse/PageSpeed Insights for an immediate lab baseline, and identifying the two or three highest-traffic pages to focus on rather than trying to instrument everything at once. It names the trade-off unprompted: that optimizing without a baseline means you can't tell whether any change helped, so establishing measurement — even imperfect, even just CrUX to start — is higher-value in the first sprint than any specific fix, however obvious that fix looks.

A junior engineer proposes rewriting a slow feature from scratch to fix its performance. Your instinct is that it's fixable incrementally. How do you handle it?

A strong answer takes the underlying signal seriously (a rewrite instinct often means the current code really is hard to reason about) while separating that from the specific proposed solution, and asks for the actual profiling data behind the claim — where does a trace actually show the time going — before agreeing or disagreeing with the fix. It names the trade-off unprompted: a rewrite carries real risk (regression surface, timeline, losing accumulated edge-case handling) that an incremental, profiler-guided fix usually doesn't, and that trade-off should be made explicitly and with data, not deferred to instinct on either side.

Your CWV dashboard shows LCP regressing slowly over several months with no single obvious cause — no big deploy, no new dependency. How do you approach this?

A strong answer recognizes this as death-by-a-thousand-cuts and treats it differently from a sharp regression: it looks for gradual, additive causes — incremental image/asset growth, a slowly-growing DOM or component tree, small dependency version bumps accumulating, or organic content growth (more items on a page, more embedded widgets) — using historical bundle-size and asset-size tracking over the same window, not just a single before/after diff. It names the trade-off unprompted: that this failure mode requires ongoing budget enforcement (size-limit checks in CI, recurring audits) rather than a one-time fix, since nothing single is provably "the" regression and the only durable fix is preventing the slow accumulation going forward.

Leadership wants to advertise "we improved page speed by 40%" based on a lab test. Your RUM data shows a much smaller real-world improvement. What do you say?

A strong answer doesn't just say "the lab number is wrong" — it explains precisely why lab and field diverge (fixed conditions vs. real device/network diversity, a single scenario vs. aggregated real sessions) and proposes what claim would actually be both accurate and still compelling, using the field number instead. It names the trade-off unprompted: overstating an improvement using a favorable lab number risks credibility (with press, with users who compare it to their own experience) in a way that's a real cost, not just a pedantic technical correction, and frames the accurate number as the safer and still-genuine story to tell.

You're the most senior engineer on a team where nobody else has deep performance expertise. How do you scale performance awareness without becoming the bottleneck who reviews every PR?

A strong answer thinks in terms of guardrails and defaults rather than personal review capacity: automated budgets in CI (bundle-size limits, a Lighthouse CI gate), a small number of documented patterns/anti-patterns the team can self-check against, and lightweight, repeatable training (a short internal doc, a recorded walkthrough of one real regression and how it was found) rather than becoming the single point of review. It names the trade-off unprompted: automation and documentation scale further than any one person's attention, but they miss the nuanced, principal-level judgment calls (like several elsewhere in this section) that still need a human with real expertise — so the goal is raising the team's floor broadly while reserving personal review for genuinely ambiguous cases.

A performance fix would meaningfully improve Core Web Vitals but requires a noticeably larger, more complex codebase (e.g. moving to a more granular code-splitting architecture, or a caching layer with real invalidation logic). How do you weigh the trade-off?

A strong answer treats this explicitly as a maintainability-vs-performance trade-off rather than assuming performance always wins: it sizes the actual user/business impact of the metric improvement against the real ongoing cost of the added complexity (more code to maintain, a new class of bugs like cache-invalidation issues, onboarding cost for new engineers), and looks for a smaller, less complex version of the fix that gets most of the benefit before committing to the most complex option. It names the trade-off unprompted: performance work that meaningfully increases long-term maintenance burden or bug surface is a real cost that should be weighed against the metric gain, not treated as free because the metric moved.

Two teams disagree on whether a shared component library's recent update caused a performance regression. Both have data supporting their view. How do you resolve it?

A strong answer doesn't referee based on whose data "feels" more credible — it looks for what's actually different between the two datasets (different pages, different time windows, different device/traffic segments, lab vs field) that could explain the disagreement, and proposes a specific, controlled comparison (the same page, same time window, before/after the specific version bump, ideally via a feature flag or gradual rollout) that would settle it with evidence both teams would accept. It names the trade-off unprompted: resolving a data disagreement by authority or opinion erodes trust in data-driven decisions going forward, while investing the time to find a controlled comparison protects the team's ability to use data credibly on the next disagreement too.

12 Design exercises

Principal-level interviews increasingly replace a Q&A round with a short design exercise: a realistic, under-specified scenario you're expected to scope with clarifying questions before proposing a solution. Each exercise below gives the prompt, the clarifying questions a strong candidate asks before diving in, and a collapsed outline of a strong solution with the trade-offs it should surface.

Exercise 1

Design a performance monitoring and alerting strategy for a mid-size e-commerce site (checkout flow included) that currently has no RUM and relies only on ad hoc Lighthouse runs before releases.

Clarifying questions a strong candidate asks first: What's the current traffic volume and device/geography mix? Is there an existing analytics pipeline the RUM data could piggyback on, or does this need its own infrastructure? What's the team's on-call/incident-response maturity — would alerts actually get acted on? Is checkout specifically flagged as higher-priority than the rest of the site, and does it have its own conversion-rate data that could be correlated with performance?

Strong solution outline

Phase the rollout rather than building everything at once: start with the web-vitals library reporting to whatever analytics endpoint already exists (fast, cheap, gets real field data flowing in days, not months), segmented at minimum by page type (checkout vs. browse vs. product) and device class from day one so checkout's numbers are never hidden inside a sitewide blended average. Layer alerting on top only once a baseline exists — alert on p75 regressions against a rolling historical baseline per segment, not a fixed absolute threshold, to avoid noise from natural variance; route checkout-specific alerts with higher urgency given its direct revenue link. Keep Lighthouse CI as a pre-release lab gate (catching regressions before they reach users) explicitly complementary to, not a replacement for, the field RUM system, and correlate performance regressions with the existing conversion-rate data to build the business case for continued investment.

Trade-offs a strong answer names

Building segmentation and alerting thresholds well takes real iteration time (naive absolute thresholds will misfire), and there's a real cost/complexity trade-off in how much custom instrumentation (beyond stock Web Vitals) to add versus how fast the team needs signal — a strong answer explicitly sequences "get basic field data flowing fast" ahead of "build the fully mature, segmented, correlated system" rather than trying to ship the end state on day one.

Exercise 2

A content-heavy news site's homepage renders 150+ article cards, each with an image, and the page becomes sluggish to scroll on mobile a few seconds after load. Design a fix.

Clarifying questions a strong candidate asks first: Are all 150+ cards in the DOM at once, or is this already paginated/infinite-scroll? Are the images already using srcset/responsive sizing, or full-resolution originals? Is the sluggishness present immediately or does it build up over time (suggesting a leak rather than a one-time cost)? What does the Performance panel actually show as the dominant cost — scripting, layout, or paint?

Strong solution outline

Assuming all 150+ cards are in the live DOM: apply content-visibility: auto with a reasonable contain-intrinsic-size estimate to off-screen cards so the browser skips layout/paint work for content nowhere near the viewport, which directly targets a scroll-jank-from-DOM-size problem without a full rewrite. Pair this with responsive images (srcset/sizes, modern formats) and explicit width/height/aspect-ratio on every card image, both to cut payload and to prevent layout shift as images load in. If profiling shows the sluggishness building up over time rather than being present immediately, treat it separately as a likely memory leak (event listeners or observers attached per card and never cleaned up) using the DevTools heap-snapshot technique, since that's a different bug class from a one-time rendering cost and needs a different fix (cleanup logic, not content-visibility).

Trade-offs a strong answer names

content-visibility: auto requires a reasonable size estimate or you get visible layout jumps as content is measured on scroll into view, and virtualizing the list (only rendering DOM nodes for visible cards) would give a stronger performance guarantee but at meaningfully more implementation and maintenance complexity than a CSS-only fix — a strong answer names that virtualization is the "better but more expensive" alternative and justifies starting with the cheaper CSS-based fix first, escalating only if it's insufficient.

Exercise 3

Your company is launching in three new markets, two of which have predominantly low-end Android devices and unreliable 3G/4G connectivity. Design the front-end architecture changes you'd propose before launch.

Clarifying questions a strong candidate asks first: Is this a new build or an existing app being extended to these markets? What's the current bundle size and main-thread cost baseline? Is offline/flaky-connectivity tolerance a hard requirement (e.g. does checkout need to survive a dropped connection), or just "be fast under bad conditions"? Are there existing CDN points of presence near these markets, or is that also a gap?

Strong solution outline

Address network and CPU constraints as two distinct problems. For network: aggressive code-splitting and a lean, well-cached critical path (minimize render-blocking resources, use resource hints deliberately, verify CDN presence or add points of presence near the new markets to cut round-trip latency), plus a service worker with a cache-first or stale-while-revalidate strategy for repeat visits so flaky connectivity doesn't mean a fully broken repeat experience. For CPU: adopt adaptive loading using navigator.connection/deviceMemory signals to serve a deliberately lighter code path (fewer simultaneous animations, simpler layout, deferred non-critical features) to detected low-end/low-bandwidth sessions rather than the same experience as flagship markets, and validate on actual representative low-end devices rather than simulated throttling alone, given the known gap between the two. Set market-specific performance budgets and field-monitoring segments for these markets from day one, rather than folding them into a single global average that would hide exactly the gap this launch needs visibility into.

Trade-offs a strong answer names

Building and maintaining an adaptive-loading branch (a genuinely lighter experience, not just a throttled one) is real ongoing engineering investment with its own testing surface, and a service-worker caching strategy adds complexity (cache invalidation on deploy) that has to be designed deliberately, not bolted on late — a strong answer treats this as an architecture decision to make before launch, not a follow-up optimization pass after users in these markets already have a bad first impression.

13 Night-before cheat sheet

The ten questions across this whole bank most likely to come up, each reduced to a one-sentence answer — a last skim before you walk in, not a substitute for the full self-quiz above.

  1. Critical Rendering Path, in order? Parse HTML to DOM, parse CSS to CSSOM, combine into the render tree, compute layout (geometry), paint (pixels), then composite layers to the screen.
  2. Why does CSS block rendering by default? The browser can't safely paint any element until it knows the final styles that apply to it, so it withholds rendering until CSSOM is complete unless you explicitly mark a stylesheet non-blocking.
  3. LCP / INP / CLS, one line each? LCP is time to render the largest visible content element; INP is the worst (98th-percentile) delay between a user interaction and the next visual update; CLS is a unitless score for unexpected layout movement, summed per session window.
  4. What are INP's three subparts? Input delay (before the handler starts), processing duration (the handler itself), and presentation delay (until the next frame paints).
  5. Lab vs field data, in one line? Lab tools (Lighthouse) run one synthetic scenario under fixed conditions; field data (CrUX/RUM) aggregates real users' actual devices, networks and sessions.
  6. What's a long task? Any main-thread task running 50ms or longer, which blocks input responsiveness and is the direct mechanical cause of most INP problems.
  7. Why does ESM tree-shake better than CommonJS? ESM's import/export are static and analyzable at parse time, so a bundler can prove which exports are unused; CommonJS's dynamic require calls generally can't be proven safe to drop.
  8. Cache-Control: no-cache vs no-store? no-cache still caches the response but forces revalidation before reuse; no-store forbids caching it at all.
  9. Why does loading="lazy" on an above-the-fold image hurt LCP? It defers the fetch of the very element the LCP metric is timing, which measurably delays LCP versus eagerly loading it — lazy-load only below-the-fold images.
  10. Why are transform/opacity cheap to animate? Both can run entirely on the compositor thread against already-rasterized layers, skipping layout and paint on every frame, unlike properties such as width or top.
