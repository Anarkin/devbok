Web performance & browser platform

cheatsheet · Chrome/Edge 152 · Core Web Vitals (LCP/INP/CLS) · released 2026-09-08

What's on this card: the browser's rendering pipeline and what actually moves each Core Web Vital, resource hints and bundler-level code splitting, HTTP caching and transport, images and fonts, JS memory and main-thread cost, and the DevTools/Lighthouse workflow for finding all of it — framework-agnostic, so React/Angular-specific rendering tricks are out of scope by design. It reflects Chrome/Edge 152 and the current Lighthouse 13.x DevTools panel, with INP (not FID) as the interactivity Core Web Vital and Long Animation Frames as its diagnostic partner. Verified 2026-09-08: Vite 8 (2026-03-12) shipped Rolldown as its single default Rust bundler, Next.js 16 (2025-10-22) made Turbopack the default bundler for dev and build, and Chrome quietly re-enabled JPEG XL behind a flag around version 145 after removing it outright in 2023 — both that and Speculation Rules remain non-Baseline, so treat them as progressive enhancement, not a safe default.

Chrome/Edge 152 INP replaced FID · 2024-03-12 LoAF: Chrome 123+ Vite 8: Rolldown default Turbopack default: Next.js 16 verified 2026-09-08

01Rendering pipeline & critical path

docs: MDN — critical rendering path
HTML parsing
a streaming tokenizer builds the DOM incrementally; the preload scanner reads ahead of the parser for <img>/<link>/<script src> even while it's blocked on something else
CSSOM
every discovered stylesheet is render-blocking: the render tree can't be built until all of them have downloaded and parsed, however far the HTML parser has already gotten
Render tree
DOM ∩ CSSOM, visible nodes only — display:none is excluded, visibility:hidden is included (it still takes up space)
Layout (reflow)
computes the box geometry of every render-tree node; anything that changes size or position triggers it, for that node and everything downstream
Paint
rasterizes pixels into layers; triggered by anything that changes appearance without moving boxes (colour, shadow, background)
Composite
layers are combined on the GPU by a separate compositor thread — transform/opacity changes skip layout and paint entirely and go straight here
<script>, default
parser-blocking: HTML parsing halts, the script downloads and executes synchronously, then parsing resumes
defer
downloads in parallel with parsing, executes in document order, right before DOMContentLoaded
async
downloads in parallel, executes the instant it arrives regardless of order — briefly blocks the parser at that moment
type="module"
deferred by default; add async to a module script to keep async semantics instead
DOMContentLoaded vs load
DOMContentLoaded fires once the DOM is parsed, with no wait for images/stylesheets/subframes; load waits for every subresource
requestAnimationFrame
runs immediately before the next paint — the only reliable place to read layout once, then write, exactly once per frame
<link rel="stylesheet" href="critical.css">
<script src="app.js" defer></script>
<script type="module" src="widgets.js"></script>
<script src="analytics.js" async></script>

One blocking script beats every optimization below it. A synchronous <script> placed before your stylesheet stops the parser dead until it runs, whether or not it touches the DOM — order in the <head> is not cosmetic.

02Core Web Vitals & how to move each

docs: web.dev — Web Vitals
LCP
time to render the largest above-the-fold element (image, poster, block text); good ≤2.5s, poor >4s, scored at the 75th percentile of visits
LCP subparts
TTFB + resource load delay + resource load duration + render delay — DevTools' Performance panel breaks a trace into exactly these four
Moving LCP
preload the LCP resource with fetchpriority="high", never loading="lazy" it, cut render-blocking CSS above the fold, push TTFB down with edge/CDN caching
INP
replaced FID as the interactivity Core Web Vital on 2024-03-12; the worst (high-percentile) interaction's input delay + processing time + presentation delay, across the whole visit
Moving INP
good ≤200ms, poor >500ms; break up long tasks, yield with scheduler.yield(), keep handlers cheap, avoid layout reads inside them
CLS
sum of impact-fraction × distance-fraction for every unexpected shift in a session window; good ≤0.1, poor >0.25
Moving CLS
size every <img>/<video>, reserve space for ads/embeds with aspect-ratio or min-height, never inject content above existing content, watch web-font swap shifts
Long Animation Frames
frame-level successor to Long Tasks (Chrome 123+); attributes a slow interaction's time to the actual scripts and render work that caused it
Diagnostic-only metrics
TTFB, FCP — not scored themselves, but TTFB is usually the single biggest lever on LCP
Field vs lab
field/RUM (CrUX, real users, 75th percentile) is what Search actually uses; lab (Lighthouse, one run, Total Blocking Time as an INP proxy) is for debugging before there's traffic to measure
web-vitals library
wraps the raw PerformanceObserver entry types into the same numbers CrUX reports, plus an attribution build that names the offending element/script
import { onLCP, onINP, onCLS } from 'web-vitals/attribution';

onLCP(({ value, attribution }) => log('LCP', value, attribution.element, attribution.timeToFirstByte));
onINP(({ value, attribution }) => log('INP', value, attribution.interactionTarget, attribution.longAnimationFrameEntries));
onCLS(({ value, attribution }) => log('CLS', value, attribution.largestShiftTarget));

Lab tools can't measure INP directly. A synthetic Lighthouse run has no real user interaction, so it reports Total Blocking Time as a proxy — treat an INP number from anywhere but RUM/CrUX or a real session as an estimate.

03Resource hints & speculative loading

docs: MDN — Speculation Rules API
preload
<link rel="preload" as="…" href="…"> fetches a same-page critical resource at high priority — as is mandatory or the browser drops the priority boost
preconnect
DNS + TCP + TLS to a cross-origin host you know you'll fetch from soon; the browser caps useful preconnects around 4-6, the rest are wasted work
dns-prefetch
DNS resolution only — the cheap fallback for third-party origins you're not certain you'll use
modulepreload
preloads an ES module and, in Chromium, its static import graph — not just the one file
prefetch
low-priority fetch for the next likely navigation, cached for reuse when it happens
fetchpriority
high/low/auto on <img>, <link>, <script> and fetch() — put it on the one true bottleneck resource, not several; diluted priority helps nothing
Speculation Rules API
<script type="speculationrules"> declares prefetch/prerender rules by URL pattern; replaces the old Chrome-only <link rel="prerender">
Speculation Rules status
experimental, not Baseline, Chromium-only — never target sign-out, cart-mutation or analytics URLs; a prerendered page fully executes its JS
loading="lazy" / decoding="async"
native lazy-load/async-decode for below-the-fold <img>/<iframe> — never combine either with the LCP image
Early Hints (103)
the server sends preconnect/preload hints in an interim response while still computing the real one, so the browser starts fetching during backend think-time
Back/forward cache
instant nav from a frozen page snapshot; Cache-Control: no-store, open BroadcastChannels/WebSockets and unload listeners all block it — use pagehide/visibilitychange instead
<script type="speculationrules">
{
  "prerender": [{ "where": { "href_matches": "/products/*" }, "eagerness": "moderate" }],
  "prefetch":  [{ "where": { "not": { "href_matches": "/logout" } }, "eagerness": "conservative" }]
}
</script>
<link rel="preload" as="image" href="/hero.avif" fetchpriority="high">

04Bundling & code splitting

docs: Vite — features & code splitting
import()
the only code-splitting primitive; every major bundler turns a dynamic import into its own chunk automatically
Tree-shaking
static ESM analysis drops unused exports; mark a package "sideEffects": false so bundlers can shake it aggressively
Chunk strategy
route-level splitting first, then one shared vendor chunk, then split further only where a flame chart actually shows it matters
Rolldown Vite 8 · 2026-03
Rust rewrite of Rollup; Vite 8 ships it as the single default bundler for both dev and build, 10-30× faster than the old esbuild(dev)/Rollup(build) split — needs Node 20.19+/22.12+
Rspack
Rust, webpack-config-compatible — a drop-in for an existing webpack loader/plugin setup that wants Rust-speed without a config rewrite
Turbopack Next.js 16 · 2025-10-22
Rust, built into Next.js; default bundler for dev and build since 16.0 — incremental, caches down to the function level, persists to disk between runs
esbuild
still the fastest single-purpose transform/minify step; several tools still shell out to it even where Rolldown/Rspack own the module graph
Module Federation
runtime composition of independently built and deployed bundles (webpack/Rspack) — the actual mechanism behind most "micro-frontend" architectures
Minification
esbuild/SWC/Terser for JS; Lightning CSS for CSS — minify, nest and autoprefix in one Rust pass
Source maps
ship a hidden source map to your error tracker, never to the client — full source maps in production is a common accidental leak of unminified logic
Bundle analysis
rollup-plugin-visualizer, webpack-bundle-analyzer, or DevTools' Coverage panel (unit 09) to see what's actually shipped versus used
// route-level split — every bundler above turns this into its own chunk
const openAdminPanel = () => import('./AdminPanel.js').then(m => m.render());
button.addEventListener('click', openAdminPanel, { once: true });

05Caching, compression & transport

docs: MDN — HTTP caching
max-age
seconds the response is fresh for — no revalidation needed anywhere in that window
immutable
never revalidate, even on reload — for content-hashed assets only (app.3f2a1c.js), never for HTML
no-cache
always revalidate with the server (ETag/Last-Modified) before use — despite the name it can cache, just never without asking first
no-store
never cache at all, and it disables bfcache on that navigation — reserve for genuinely sensitive responses
stale-while-revalidate
serve the stale copy immediately, refetch in the background — smooths perceived latency for content that's fine slightly stale
Validators
ETag (strong/weak) or Last-Modified; a 304 response has no body, just headers — the cheapest possible cache hit
Fingerprint + long cache
hash the filename, cache the asset a year with immutable; the HTML referencing it stays no-cache
Service worker strategies
cache-first (static shell), network-first (API data), stale-while-revalidate (everything in between) — Workbox packages all three
HTTP/2
one TCP connection, multiplexed streams, HPACK header compression; server push is deprecated and removed from every major browser
HTTP/3 (QUIC)
UDP-based, no transport-level head-of-line blocking, faster repeat-visit setup (0-RTT); broad support since Chrome 87 / Firefox 88 / Safari 16
Compression
Brotli beats gzip by roughly 15-20% on text at similar CPU cost; pre-compress static assets at build time, compress HTML/API responses dynamically
CDN / edge
cache static assets and, increasingly, run SSR/API logic at edge PoPs to cut the network leg out of TTFB entirely
Cache-Control: max-age=31536000, immutable   # /assets/app.3f2a1c.js
Cache-Control: no-cache                      # /index.html
Cache-Control: no-store                      # /api/session

06Images & fonts

docs: MDN — image file type guide
AVIF
best compression, roughly 50% smaller than JPEG at equal quality; no progressive rendering; Chrome 85+, Firefox 93+, Safari 16.1+
WebP
the safe universal modern default — ~25-35% smaller than JPEG, supports animation and alpha, effectively universal support
JPEG XL
lossless+lossy, progressive, HDR; Safari shipped it (17+), Chrome removed it in 2023 then quietly re-enabled it behind #enable-jxl-image-format around version 145 — still not Baseline, ship a fallback
<picture> + srcset/sizes
format fallback via <picture><source type>; resolution switching via srcset/sizes on a single format
Art direction
<picture><source media="…"> swaps the whole image, not just the resolution, per breakpoint
loading="lazy"
every below-the-fold <img>/<iframe>; pair with decoding="async" so decode doesn't block the main thread
Image CDNs
on-the-fly resize/format/quality via URL params (?format=avif&width=800) instead of pre-generating every variant at build time
font-display
swap (fallback then swap, may shift layout) or optional (only use the web font if already cached — zero shift risk); avoid the default block on text-heavy pages
Metric overrides
size-adjust/ascent-override/descent-override in @font-face tune the fallback to match the web font's metrics and remove swap-induced CLS
Variable fonts
one file covers a whole weight/width axis range via font-variation-settings, replacing 4-9 static weight files
WOFF2
the only format worth shipping today; subset to the actual character set/script in use to shrink further
Preloading fonts
<link rel="preload" as="font" type="font/woff2" crossorigin> on the one font rendering visible text first — preloading every weight defeats the point
@font-face {
  font-family: "Inter";
  src: url("/inter-var.woff2") format("woff2-variations");
  font-weight: 100 900;
  font-display: optional;
  size-adjust: 100.2%;
  ascent-override: 90%;
}

07JS execution cost & memory

docs: Chrome for Developers — Long Animation Frames
Parse + compile cost
every byte shipped costs time before a single line executes; V8's bytecode cache only helps repeat visits, not the first one
Main-thread breakdown
DevTools' bottom-up view splits a trace into Loading / Scripting / Rendering / Painting / System — fix whichever dominates, not whichever is easiest
Long tasks
anything over 50ms on the main thread blocks input; PerformanceObserver with entryTypes: ['longtask'] or 'long-animation-frame' surfaces them
scheduler.yield()
cooperatively yields mid-task and resumes at user-visible priority — the modern replacement for the setTimeout(fn, 0) chunking hack
scheduler.postTask()
schedules work at an explicit priority (user-blocking/user-visible/background), replacing ad-hoc requestIdleCallback/setTimeout priority guessing
isInputPending()
lets a long synchronous loop check whether it should yield right now instead of finishing the current batch first
Detached DOM nodes
the #1 real leak: a removed node stays alive because a closure, listener or cache still references it — heap snapshots flag these explicitly as "Detached"
Forgotten subscriptions
setInterval, ResizeObserver/IntersectionObserver, and event listeners that outlive the view that created them
WeakMap/WeakRef
associate metadata with an object, or hold a reference to it, without keeping it alive past its natural lifetime
FinalizationRegistry
runs a cleanup callback after GC reclaims an object — never rely on when, only that it eventually will
Web Workers / OffscreenCanvas
move CPU-bound parsing, diffing or drawing off the main thread entirely, rather than chunking it on-thread
WASM
for hot numeric/codec/image paths — compression, video processing — where even optimized JS is the bottleneck
async function processAll(items) {
  for (const item of items) {
    handle(item);
    if (navigator.scheduling?.isInputPending()) await scheduler.yield();
  }
}

08Rendering & compositing idioms

docs: MDN — CSS containment
contain: layout paint
a subtree's layout/paint can't affect, or be affected by, anything outside it — shrinks the browser's invalidation scope
contain: strict
layout + paint + size + style in one declaration, the strongest isolation available
content-visibility: auto
skips layout/paint entirely for off-screen subtrees; pair with contain-intrinsic-size or the element collapses to zero height and shifts everything else (CLS)
Compositor-only animation
animating transform/opacity runs on the compositor thread, skipping layout and paint; animating top/left/width does not
will-change
pre-promotes an element to its own layer right before an animation starts; leaving it on permanently wastes GPU memory on every such element
Layout thrashing
reading (offsetWidth, getBoundingClientRect) then writing in a loop forces a synchronous layout on every iteration — batch all reads, then all writes
Forced synchronous layout
a layout-triggering read right after a DOM write invalidates the browser's own batching and computes layout immediately, on the spot
View Transitions API
document.startViewTransition(updateDOM) animates between two DOM states in one call, same-document since 2024; cross-document (MPA) view transitions followed later and need an opt-in on both pages
@container queries
style based on an ancestor's size, not the viewport; broadly supported now, and the containment they imply also limits recalculation scope
Passive listeners
{ passive: true } on scroll/touchstart lets the compositor start scrolling before your handler even runs
.card { content-visibility: auto; contain-intrinsic-size: 320px 240px; }

09DevTools & Lighthouse profiling

docs: Chrome for Developers — Lighthouse
Performance panel
record a trace, read the flame chart top-down or the bottom-up/call-tree views by total vs self time
Insights sidebar
auto-generated findings per recorded trace — render-blocking requests, LCP breakdown, third-party cost — start here before hand-reading the flame chart
LoAF in the trace
long frames are called out directly with per-script attribution, no manual Long Tasks correlation needed
Network panel
waterfall plus a priority column; the "initiator" column traces exactly what requested a resource and why
Custom throttling
round-trip time and packet loss are now configurable alongside bandwidth — closer to real mobile conditions than the old fixed presets
Coverage panel
Ctrl/Cmd+Shift+P → "Show Coverage"; red bytes are shipped-but-unused JS/CSS, the fastest way to justify a code-split
Memory panel
heap snapshot (take, act, take, diff by retained size) or an allocation-instrumentation timeline to catch a leak growing in real time
Lighthouse CLI
lighthouse <url> --view for a local report; lighthouse-ci to gate PRs on a budget
Lighthouse categories
v13's "Agentic Browsing" category, surfaced through the PSI API, audits llms.txt and AI-agent readability alongside the classic Performance/Accessibility/SEO set
PageSpeed Insights
Lighthouse (lab) numbers next to real CrUX (field) numbers for the same URL, side by side
WebPageTest
multi-location, multi-connection runs with a filmstrip and full waterfall — the tool for "why is it slow there, not here"
bfcache tester
DevTools' Application panel has a dedicated "Back/forward cache" section that names the exact API or header blocking it
lighthouse https://example.com --view --preset=desktop
lighthouse https://example.com --output=json --output-path=./report.json --chrome-flags="--headless"

10Idioms & gotchas

docs: web.dev — fast load times

Idioms worth keeping

Measure, then optimize
a Lighthouse score chased without a LoAF trace or heap-snapshot root cause is optimizing the wrong thing
Ship the LCP resource first
one correct fetchpriority="high" preload beats a dozen speculative optimizations elsewhere on the page
Budget, don't guess
a performance budget (bytes, TTFB, INP) enforced in CI catches a regression before a user does
Feature-detect the experimental
Speculation Rules, cross-document View Transitions and scheduler.yield() are none of them universal — check support, don't assume it
Treat third-party scripts as untrusted
sandbox in an iframe, load via a facade, or move to a worker — you can't performance-fix code you don't own
RUM is the source of truth
Lighthouse is for debugging; CrUX/RUM at the 75th percentile is what actually gets scored and ranked

Gotchas, one line each

  • loading="lazy" on the LCP image is the single most common self-inflicted LCP regression.
  • A CDN cache hit can still count toward TTFB if the edge revalidates on every request — check Age/X-Cache, don't assume.
  • will-change left on indefinitely after an animation ends keeps consuming GPU memory for nothing.
  • console.log(bigObj) keeps retaining that object for the life of the DevTools session — a classic false-positive "leak" in a heap diff.
  • IntersectionObserver/ResizeObserver callbacks run on the main thread — a heavy callback still costs INP even though the observer itself is cheap.
  • Domain sharding is a pre-HTTP/2 trick; on HTTP/2+ it just adds redundant TLS handshakes and hurts.
  • Cache-Control: no-store silently disables bfcache — reach for no-cache or a short max-age if you need both freshness and instant back-nav.
  • A <link rel="preload"> for a resource the page doesn't use within a few seconds is a wasted download, and Lighthouse flags it as such.
  • Minifying already-minified vendor bundles a second time in your own build step burns CI time for near-zero byte savings.
  • font-display: swap trades flash-of-invisible-text for flash-of-different-metrics — it can cause the exact CLS it was meant to avoid.
  • A service worker's cache.addAll() install step fails entirely if even one URL in the list 404s.
  • Preconnecting to more origins than the browser's connection budget allows just gets the excess ones silently dropped.
  • CLS session windows can span a client-side route change — a shift right after a "new page" in an SPA still counts against the same session.
  • requestIdleCallback gives no guaranteed deadline under load — scheduler.postTask/scheduler.yield give actual priority control instead.
  • A synchronous <script> placed before your stylesheet blocks the parser regardless of what either one actually does.
