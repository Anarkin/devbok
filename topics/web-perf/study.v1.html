Web performance & browser platform

study · no single version — a rolling platform · snapshot 2026-09-08 · Core Web Vitals (LCP/INP/CLS) stable · Vite 8.1

There is no release to pin this topic to: it is the intersection of shipping browser engines, W3C/WHATWG specs at different maturity stages, and a tool ecosystem that turns over every year. What is genuinely current right now: Core Web Vitals are LCP, INP and CLS, all stable and scored at the 75th percentile of real-user data — INP replaced First Input Delay as the responsiveness metric in March 2024, and Google reviews stable-metric definitions at most once a year, so the last real churn is already 18+ months behind us. The tooling underneath moved much faster: Vite 8 (March 2026) shipped Rolldown, a Rust rewrite unifying the old esbuild-for-dev/Rollup-for-build split into one bundler with reported 10–30× build-time drops, and Vite 8.1 followed in June 2026. The View Transitions API — same-document since Chrome 111 (2023) and Safari 18 (2024) — finally became genuinely cross-browser when Firefox shipped it in version 144 in 2026, which matters because cross-document (MPA) transitions were flatly impossible before this API existed. Two cautionary tales for anyone tempted to chase the newest format: JPEG XL remains disabled in Chrome and Firefox with only partial Safari support since 17.0, five years after its standardisation — a reminder that "better on paper" and "safe to ship" are different questions — while Speculation Rules (prerendering the next page before the click) and scheduler.yield() (cooperative main-thread yielding) are both shipped and effective, but Chromium-only and not yet Baseline. One scoping note stated once: this guide treats bundling, code splitting and componentisation at the framework-agnostic level — the module graph, not a specific framework's compiler — since React- and Angular-specific mechanics are assumed to live elsewhere.

01 The rendering pipeline & the main thread

Docs: MDN — Populating the page: how browsers work · web.dev — Critical rendering path · Chrome — RenderingNG architecture

Every performance number you will ever chase — LCP, INP, CLS, a janky scroll, a slow click — is a symptom of the same six-stage pipeline doing more work than the frame budget allows. Learn the pipeline once and you can derive the fix for almost anything: parse → style → layout → paint → composite, with JavaScript able to interrupt and re-trigger any of the first four. The browser's whole performance strategy is "do the least amount of this pipeline necessary to get correct pixels on screen", and every optimisation technique in this guide — critical CSS, transform instead of top, virtualised lists, code splitting — is a specific way of skipping stages.

The six stages, and what each one is actually for

Parse: the HTML parser tokenises bytes into a DOM tree incrementally, as bytes arrive — it does not wait for the whole document. A <script> without async/defer blocks this parser dead: the spec requires the browser to fetch and execute it before continuing, because the script might call document.write. Style: CSS is parsed into the CSSOM, and every rule is matched against every DOM node to produce each element's computed style — CSS is render-blocking by default because the browser cannot compute this without the full stylesheet (an element's `color` could be overridden by a rule three-quarters of the way down the file). Layout (Chrome's internal name: LayoutNG): walks the DOM+CSSOM combination — the render/layout tree, which skips display:none nodes entirely but keeps visibility:hidden ones — and computes the geometry: exact pixel box for every node. Paint: records the actual drawing instructions (rectangles, text, borders) into one or more layers as a display list. Composite: the compositor thread — not the main thread — takes those painted layers, rasterises them into GPU textures, and assembles the final frame, applying transforms and opacity as a GPU operation with zero DOM involvement.

The one distinction that unlocks everything else

Some CSS properties (width, top, margin, anything that changes geometry) force layout, then paint, then composite — a full pipeline run. Others (transform, opacity, and with containment, filter) can be composited directly on the GPU with no layout and no repaint at all, because moving or fading a pre-rasterised texture is a transform on already-painted pixels. This is why every performance guide tells you to animate transform: translateX() instead of left: it is not a style preference, it is the difference between doing 1 pipeline stage per frame and doing 3, and at 60fps you have 16.7ms per frame to do all of it before the user perceives lag.

Forced synchronous layout — the bug you will actually write

The pipeline is normally lazy: the browser batches every style write in a JS task and runs layout once, right before paint. But reading certain properties — offsetHeight, getBoundingClientRect(), getComputedStyle() — demands an up-to-date, pixel-accurate answer right now. If you wrote a style change and then immediately read a layout property, the browser cannot answer from stale geometry, so it runs layout synchronously, on the spot, mid-script. Do that inside a loop — write, read, write, read — and you get layout thrashing: N elements, N forced synchronous layouts, each one recomputing the geometry of the whole tree, not just your element.

// Thrashes: every iteration writes a style, then reads a layout property,
// forcing a synchronous layout recalculation before the read can return.
boxes.forEach(box => {
  const h = box.offsetHeight;       // read - forces layout if a write is pending
  box.style.height = (h * 2) + "px"; // write - invalidates layout again
});

// Fixed: separate the read phase from the write phase (the "FastDOM" pattern).
// One layout for the whole batch instead of one per element.
const heights = boxes.map(box => box.offsetHeight); // all reads first
boxes.forEach((box, i) => {
  box.style.height = (heights[i] * 2) + "px";        // all writes second
});

What changed recently: decomposing the main thread's work

The old Long Tasks API (any main-thread task over 50ms) only told you a task was slow, not why. Chrome 123 (March 2024) shipped the Long Animation Frames (LoAF) API — PerformanceObserver entries of type long-animation-frame — which breaks a slow frame down into its actual pipeline stages: render delay, script duration (attributed to the specific script and function), style/layout duration, and presentation delay. That decomposition exists because INP (unit 04) made "which stage of the pipeline is slow" a metric people are paid to answer, and Long Tasks alone couldn't say. It is Chromium-only and not yet Baseline, but it is the tool a lead engineer actually opens first when INP regresses in the field.

Interview trap

"Reflow" and "repaint" are used as if repaint always follows reflow, and as if requestAnimationFrame runs off the main thread because it sounds asynchronous. Neither is true. A repaint can happen with zero layout (a colour change), and rAF callbacks run on the main thread, synchronously, right before the browser's internal style/layout/paint step for that frame — that is precisely why heavy work inside a rAF callback still blocks the next paint. The main thread and the compositor thread are genuinely different threads; only compositor-only changes (transform/opacity) escape the main thread entirely.

Gotcha

will-change and blind layer promotion are not free. Every composited layer costs GPU memory and a raster pass; promoting dozens of elements "to be safe" (a common cargo-cult fix) can make scrolling worse by exhausting layer memory and forcing the compositor to manage far more textures than it has budget for. Promote the handful of elements that actually animate, not the page.

Try it — 20 minutes, two exercises

1. Cause and cure layout thrashing. Write a loop that resizes 200 divs by reading offsetHeight then writing style.height inside the same iteration. Record it in DevTools Performance. Then fix it with the read/write batching pattern above and record again.

2. Animate the same thing two ways. Animate one box's position with left in a rAF loop, and an identical box with transform: translateX(). Open the Rendering tab, enable "Layer borders" and "Paint flashing", and watch which box repaints on every frame and which one doesn't.

Expected outcome

Exercise 1: the thrashing version shows a sawtooth of purple (layout) and green (paint) blocks in the Performance flame chart, one pair per element — often visibly longer than 50ms total; the batched version shows one layout block for the entire loop. Exercise 2: the left box repaints every frame (visible paint-flash overlay); the transform box paints once, gets its own compositor layer, and every subsequent frame is composite-only — the CPU cost drops to near zero for that element.

Interview Q&A · the rendering pipeline

Walk me through what happens between "browser receives HTML" and "pixels on screen".

Bytes arrive and are tokenised into a DOM tree incrementally by the HTML parser — it does not wait for the whole document, which is why streaming matters. In parallel, CSS is parsed into the CSSOM; a render-blocking stylesheet must finish before the browser will paint anything, because any rule anywhere in it could still apply to any node. The browser combines DOM and CSSOM into a render/layout tree — skipping display:none nodes — then runs layout to compute exact geometry, paint to record drawing instructions into layers, and composite to rasterise and assemble those layers into the final frame on the compositor thread. JavaScript can interrupt this at almost any point: a blocking script pauses parsing, and a style write followed by a layout read forces layout to run early.

Why is CSS render-blocking but images are not?

Because computing an element's final style requires the complete cascade — a selector later in the stylesheet, or in a stylesheet still downloading, can still override what you'd otherwise render, so painting before CSS finishes risks a visible flash of incorrectly styled content. An image, by contrast, occupies a box whose dimensions the layout can already reserve (especially with explicit width/height or aspect-ratio); the pixels can arrive later and simply fill that box without invalidating anything else on the page. That asymmetry is exactly why critical CSS extraction is a real optimisation and "critical image extraction" isn't a phrase anyone uses.

What's the actual difference between the render tree, the layout tree and the accessibility tree?

The DOM is the full document structure. The CSSOM is the parsed stylesheet rules. Chrome's layout tree (historically called the "render tree") is DOM nodes merged with their computed styles, with display:none subtrees excluded entirely — they don't get a box, a size, or a paint record. visibility:hidden nodes stay in the layout tree with a box that occupies space but paints nothing. The accessibility tree is a separate, parallel structure built from the DOM plus ARIA semantics, consumed by assistive technology — it is not part of the visual pipeline at all, which is why an ARIA change can't cause a layout shift.

Why do transform and opacity skip layout and paint, and what makes an element eligible?

Because a transform is a coordinate-space operation applied to an already-rasterised texture, and opacity is a blend applied at composite time — neither changes any other element's geometry or requires new pixels to be drawn. For the browser to do this, the element typically needs its own compositor layer (promoted automatically when animated, or forced with will-change: transform); once promoted, the main thread hands the compositor a texture once, and every subsequent frame's translate/scale/rotate/fade happens on the GPU with no JavaScript and no main-thread involvement at all — which is also why these animations keep running smoothly even while the main thread is busy with something else.

What is a forced synchronous layout, and why does it hurt more in a loop?

It's the browser being forced to run layout early, mid-script, because you read a geometry-dependent property (offsetHeight, getBoundingClientRect, getComputedStyle) after a pending style write, and only an up-to-date answer is acceptable. A single forced layout is often cheap. The problem is a loop that alternates write-then-read per element: each iteration invalidates the layout the previous write just computed, so the browser can't batch anything — you pay for N full layout passes instead of one. The fix is always the same shape: separate all the reads from all the writes.

Is requestAnimationFrame off the main thread? What actually runs there?

No — rAF callbacks run synchronously on the main thread, scheduled to fire right before the browser's next style/layout/paint step, which is exactly why they're the right place for visual updates and the wrong place for anything slow. Confusing this with the compositor thread is a common interview slip: the compositor thread is where composite-only transform/opacity animations run without touching the main thread at all, and it has no relationship to rAF beyond both existing "per frame".

What is RenderingNG, and why should I know Chrome rewrote its rendering architecture?

RenderingNG is the multi-year (2019–2023ish) rewrite of Chrome's rendering pipeline into a set of independently-testable, incrementally-computed stages — LayoutNG for layout, CompositeAfterPaint for how layers are decided, BlinkNG for the paint/style infrastructure. The interview-relevant takeaway isn't the project name, it's what it enabled: layout and paint invalidation became far more granular (changing one element doesn't force a full-tree recompute the way it sometimes used to), and compositing decisions moved out of the main thread's critical path. It's also a useful signal that "the pipeline" is not a fixed spec — every engine keeps re-architecting the same six conceptual stages for speed.

What is the Long Animation Frames API and why did we need it if Long Tasks already existed?

Long Tasks (any main-thread task >50ms) tells you that something was slow but not what inside it was slow — one 200ms task could be one giant script or ten small ones plus a slow layout. LoAF, shipped in Chrome 123 (March 2024) as a new PerformanceObserver entry type, decomposes a slow frame into render delay, per-script duration with attribution, style/layout duration, and presentation delay. It exists because INP debugging needs to answer "was this slow because of my event handler, a third-party script, or a layout thrash?", and Long Tasks structurally cannot answer that.

Does every DOM write cause layout? What actually gets deferred?

No — the browser batches style/attribute/class writes within a single synchronous JS task and defers layout until it's actually needed, either because the task ends and the browser wants to paint, or because your code forces it early by reading a geometry property. Multiple writes to the same element in the same task collapse into the final state; the browser doesn't re-layout after every line. This is the behaviour layout thrashing defeats — by reading a layout property mid-task, you remove the browser's ability to batch.

You inherit a page with visibly janky scrolling. What's your first move?

Record a Performance trace while reproducing the jank, then look at three things in order: whether the main thread is busy during scroll (a scroll-linked effect or an unthrottled scroll listener doing layout reads), whether elements that should be composited actually have their own layer (Rendering tab → layer borders), and whether the frame is dominated by paint rather than composite (paint flashing). Nine times out of ten it's a scroll handler reading getBoundingClientRect() synchronously, or a "clever" parallax effect animating top instead of transform. I'd fix the biggest main-thread cost first, then confirm the fix by checking that the relevant frames dropped from the "Style/Layout" purple band into pure compositor "Composite" activity.

02 The critical path: what blocks first paint

Docs: web.dev — Critical rendering path · MDN — rel=preload · MDN — fetchpriority

Unit 01 gave you the pipeline; this unit is about the resource graph that feeds it. The critical path is the minimum chain of network round-trips the browser must complete before it can paint anything meaningful — and every request on that chain that could have started earlier, or that didn't need to be there at all, is pure latency you're choosing to pay. The mental model that generalises: the browser discovers resources by parsing HTML top-to-bottom, so anything the parser can't see yet (a font referenced only inside a CSS file, an image referenced only inside JS) starts its network request one full round-trip later than it could have — this is the single biggest lever in this unit, and resource hints exist purely to collapse that delay.

What actually blocks paint

Two resource types are render-blocking by default: <link rel="stylesheet"> (any rule anywhere in it might apply — unit 01) and a classic, synchronous <script> in <head> (it might call document.write, so the parser must stop and wait). Everything else is a choice: a stylesheet with media="print" only blocks print rendering, not screen; a script with defer downloads in parallel and executes after parsing finishes but before DOMContentLoaded; a script with async downloads in parallel and executes the instant it's ready, potentially interrupting the parser mid-stream. The legacy pattern — "put CSS in <head>, put JS at the bottom of <body>" — was a manual workaround for not having defer; the modern equivalent is <script defer> anywhere in <head>, which gets you early discovery (the parser sees it sooner) without blocking.

<!-- Classic: blocks the parser the moment it's encountered -->
<script src="analytics.js"></script>

<!-- async: downloads in parallel, executes ASAP, order vs other scripts not guaranteed -->
<script src="analytics.js" async></script>

<!-- defer: downloads in parallel, executes in document order, right before DOMContentLoaded -->
<!-- The right default for any script that touches the DOM but isn't needed for first paint -->
<script src="app.js" defer></script>

<!-- module scripts are deferred by default - no attribute needed -->
<script type="module" src="app.mjs"></script>

Critical CSS: shipping only the styles the first paint needs

A large stylesheet is render-blocking in its entirety even if 90% of its rules apply to content below the fold. Critical CSS inlines just the above-the-fold rules in a <style> block in <head> and loads the rest asynchronously — typically <link rel="preload" as="style" onload="this.rel='stylesheet'">, the "loadCSS" pattern, so the full sheet downloads without blocking and swaps in once ready. Extraction is almost always automated at build time — tools render the page, record which rules actually painted, and split the sheet — because doing it by hand rots the moment a component changes. (One tool lineage worth knowing by name if it comes up: Google's own critters plugin, previously used inside Next.js, was deprecated in 2023; Beasties is the actively maintained community continuation of the same approach.) The trade-off is real: inlined critical CSS can't be cached across pages the way an external sheet can, so it's a bet that the first-paint win outweighs the re-download cost on the second page view.

Interview trap

"Just add preload to everything important" is the most common wrong answer in this unit. Preload doesn't create bandwidth — it reorders who gets the existing bandwidth first, on a connection that is itself finite. Over-preloading (a common mistake after a well-meaning audit) can delay the actual LCP resource by making it compete with five things that got preloaded "just in case", each stealing priority. Preload is for the one or two resources you can prove are on the critical path and are currently discovered late — not a blanket policy.

Gotcha

async and defer are not interchangeable "make it not block" options — they have opposite execution-order guarantees. Two async scripts can execute in either order depending on which finishes downloading first; two defer scripts always execute in document order. A script that depends on another script loaded earlier in the page will break intermittently — often only in production, under different network conditions — if it's marked async when it needed defer's ordering guarantee.

Try it — 25 minutes, two exercises

1. Read the waterfall. Open DevTools Network on any real site, sort by start time, and find the first image or font request that starts more than one round-trip after the HTML. Trace its "Initiator" chain — it's almost always discovered through a CSS file or a JS bundle. Add a preload for it (via a local override or just reasoning about where it'd go) and predict how much earlier it would start.

2. Break the ordering guarantee on purpose. Write two inline-adjacent <script src> tags where the second uses a global variable the first defines, mark both async, and refresh repeatedly on a throttled connection. Then switch both to defer and repeat.

Expected outcome

Exercise 1: a font or background image referenced only inside CSS typically starts 200–800ms later than the earliest possible time, purely because the parser had to reach and parse the CSS file first — that gap is exactly what preload removes. Exercise 2: with async, the page intermittently throws a "variable is not defined" error, more often under throttling because network variance changes which script wins the race; with defer the error never occurs, because document order is guaranteed regardless of download speed.

Interview Q&A · the critical path

What makes a resource render-blocking, and what doesn't?

By default, an external stylesheet and a classic synchronous script in <head> block rendering — CSS because any rule in it could still apply, scripts because they might call document.write and must run before parsing continues. Images, fonts, and scripts marked defer or async don't block paint. You can also make a stylesheet non-blocking for the current context with a conditional media attribute (e.g. media="print" doesn't block screen rendering), which the browser still downloads at low priority but doesn't wait on.

Explain the difference between async and defer precisely.

Both let the script download without blocking the parser, but they differ in when and in what order they execute. async scripts execute the instant they finish downloading, which can interrupt parsing and gives no ordering guarantee relative to other async scripts. defer scripts always execute in document order, after parsing completes but before DOMContentLoaded fires. Use async for independent scripts with no DOM dependency and no dependency on each other (most analytics tags); use defer — the safer default — for anything that touches the DOM or depends on script order.

When would preload actually make performance worse?

When it's applied broadly rather than to the one or two resources genuinely on the critical path and genuinely discovered late. Every preloaded resource competes for the same finite bandwidth and the same HTTP/2 or HTTP/3 connection priority scheme as the resource that actually determines LCP; preloading five "just in case" assets can measurably delay the real LCP candidate. The tell in a trace is a preloaded resource finishing well before it's used, while the actual LCP image starts later than it would have without the competition.

What is critical CSS, and why does it need a build step rather than hand-authoring?

It's the subset of a page's CSS that's actually needed for the content visible without scrolling, inlined directly in <head> so the browser can paint without waiting for the full external stylesheet, which then loads asynchronously and swaps in. It needs automation because "which rules paint above the fold" changes with every component edit, every viewport size, and every A/B test; hand-maintained critical CSS silently rots — either missing new above-the-fold rules (visible flash) or bloating with rules that no longer apply. Tools render the page and observe what actually painted, which is the only reliable source of truth.

What's the trade-off of inlining critical CSS?

Inline styles can't be cached independently — they re-download as part of the HTML on every navigation, whereas an external stylesheet is cached once and reused across the whole site. So it's a bet: you're trading a small, repeated cost (a few KB of inline CSS on every page load) for a large, one-time win (not blocking on a render-blocking external file for the very first paint). It pays off most on cold, single-page-view-heavy traffic — landing pages, search results — and pays off less on an app where the same shell is reused across many navigations and the external sheet is already warm in cache.

What's the difference between preload and prefetch, and when is prefetch the wrong tool now?

preload is "I need this resource on this page, right now, at high priority, and the parser just hasn't reached the reference yet." prefetch is "I predict the user will need this on the next page, so fetch it at low priority when bandwidth is free." Prefetch has always been resource-level (one image, one script); for whole-document navigation prediction, the Speculation Rules API (unit 12) supersedes it by actually prerendering the destination page, which is a strictly bigger win than prefetching its subresources one at a time.

How does fetchpriority interact with the browser's own priority heuristics?

The browser already assigns a default priority per resource type (CSS very high, the first few images fairly high, below-fold images low, etc.) based on years of heuristics about what usually matters. fetchpriority="high" or "low" overrides that heuristic for a specific resource — most usefully on the LCP image when it happens to be something the heuristic under-prioritises (a background image, or an image far down the DOM that's actually the biggest above-fold element), and on large below-fold assets you want out of the LCP resource's way. It's a hint, not a guarantee, and it composites with — doesn't replace — loading="lazy" and resource ordering.

Why does the position of a script tag in the document matter less than it used to?

The old advice — "put scripts at the bottom of <body>" — existed because classic scripts blocked the parser wherever they appeared, so moving them below the visible content limited what they could delay. defer makes position mostly irrelevant: a deferred script in <head> is discovered earlier (better — the download starts sooner) but still executes at the same point, right before DOMContentLoaded, regardless of where in the document it sits. The only remaining reason to place a script at the bottom is a legacy codebase that hasn't adopted defer/modules yet.

What is 103 Early Hints and what problem does it solve that preload in the HTML can't?

Early Hints is an interim HTTP response (status 103) a server can send before it has finished computing the final HTML response — for example while a slow backend is assembling a page — containing Link headers with preload/preconnect hints. The browser acts on them immediately, starting connections and downloads for the page's known-fixed assets (CSS, fonts, the logo) while the server is still working, instead of waiting for the full HTML to arrive and parsing it before discovering anything. It only helps when there's meaningful server think-time to hide behind — a static site with an instant response has nothing for Early Hints to overlap with.

A page's LCP image starts loading 900ms into the page load. Where do you look first?

The Network panel's "Initiator" column for that image request — it tells you whether the browser discovered it directly from HTML (good, should start near time zero) or via CSS or JavaScript (each hop adds a round-trip of pure discovery latency before the fetch even begins). If it's a CSS background-image or a JS-set src, that's the 900ms explained, and the fix is a direct <link rel="preload" as="image" fetchpriority="high"> in the HTML so the browser can start the fetch on first parse instead of waiting for CSS or script execution to reveal it.

03 LCP: loading, dissected

Docs: web.dev — Largest Contentful Paint · web.dev — Optimize LCP · MDN — LargestContentfulPaint

Largest Contentful Paint is the render time of the largest image or text block visible in the viewport when the page first loads — it is a proxy for "does this feel loaded", scored good at ≤2.5s, poor above 4s, at the 75th percentile of real visits. The reason it's the "largest" element and not the first one is deliberate: the first thing to paint is often a header or background colour, which tells the user almost nothing; the largest element is usually the thing they came for — a hero image, the main headline, the first product photo. LCP can still update as bigger elements appear (a hero image replacing a placeholder), but it stops counting entirely at the first user interaction — an interaction is a signal the user has already decided the page is usable, so further "loading" after that point is a different problem, not LCP's.

The four sub-parts — this is the mental model that lets you diagnose LCP without guessing

The LCP timer decomposes into four phases, and Lighthouse and CrUX both report them individually because each has a completely different fix:

PhaseWhat it measuresTypical fix
TTFBTime to first byte of the documentServer/CDN latency, edge caching, avoid origin round-trips
Resource load delayTime from TTFB to the browser starting the LCP resource's fetchFix late discovery: preload, move the reference earlier in HTML, avoid CSS/JS-only discovery
Resource load timeHow long the fetch itself takesCompression, modern formats (unit 08), CDN, HTTP/3, right-sized images
Element render delayTime from resource-ready to actually paintedRemove main-thread blocking (long tasks, layout thrash) between load and paint

Most real regressions live in exactly one of these four, and "optimise LCP" as a generic instruction is a smell — a lead engineer names the sub-part. A CDN migration attacks TTFB. A <link rel="preload"> attacks resource load delay. AVIF/responsive images attack resource load time. Deferring a huge synchronous script that runs right when the image is ready attacks element render delay.

Text can be the LCP element too

LCP isn't image-only: a large headline rendered directly from HTML/CSS (no image) is a valid LCP candidate and is usually fast, because text painting has no network fetch phase at all — it's bounded almost entirely by TTFB and render-blocking CSS/fonts. This is why "just make the hero a headline, not an image" is a legitimate LCP tactic, not a cop-out: fewer phases means fewer places to lose time. The trap is a headline set in a custom web font with no font-display strategy — the text technically "exists" but the browser may block its paint on the font (unit 09), reintroducing a network dependency you thought you'd removed.

What changed recently

LCP itself hasn't been redefined since it became a Core Web Vital — Google's policy is at most one stable-metric change per year, and the last structural addition was the sub-part breakdown surfaced in Chrome DevTools and CrUX, which turned "LCP is high" from a single number into an actionable diagnosis. What has moved is the tooling around it: modern bundlers and frameworks increasingly auto-inject fetchpriority="high" and preload hints for detected hero images (several meta-frameworks do this by default now), which is the ecosystem catching up to a technique that used to require manual instrumentation.

Interview trap

"LCP is about image optimisation" is an incomplete answer that misses roughly half the real-world fixes. In audits, resource load delay — late discovery — is at least as common a cause as resource load time, and it's fixed with zero image work: just a preload tag or moving the reference earlier in markup. Candidates who jump straight to "compress the image, use WebP" without asking "when does the fetch even start?" are solving the wrong sub-part half the time.

Gotcha

A carousel/slider with multiple full-bleed images is a classic hidden LCP killer: the browser may pick a different slide's image as the LCP candidate than the one visible after JS runs, because LCP is evaluated from the initial paint, and slider libraries frequently render all slides in the DOM and hide the rest with visibility or transform tricks that don't remove them from consideration. Render only the active slide's image (or use content-visibility: hidden, which does exclude it), and preload specifically the one that will actually be visible first.

Try it — 20 minutes, two exercises

1. Decompose your own LCP. Open PageSpeed Insights or Lighthouse on a real page you control, find the LCP element, and read off its four sub-part timings. Identify which single sub-part is largest, and make one change that targets only that sub-part.

2. Break LCP on purpose. Take a fast page and add a synchronous, CPU-heavy script (a tight loop of a few hundred milliseconds) that runs right after the hero image tag. Watch LCP move even though the image itself didn't change.

Expected outcome

Exercise 1: on most real sites, resource load delay is non-trivial (100–500ms) because the LCP image is discovered from a component library's rendered markup rather than static HTML — adding fetchpriority="high" plus a direct preload typically closes most of that gap immediately, visible as the "Discovery time" bar shrinking in the Lighthouse LCP breakdown. Exercise 2: LCP increases by roughly the duration of the blocking script, demonstrating that "resource load time" was never the bottleneck — element render delay was, because the main thread was busy when the image was ready to paint.

Interview Q&A · LCP

Define LCP precisely, including when it stops being measured.

LCP is the render timestamp of the largest image or text block within the viewport, measured from navigation start, reported at the 75th percentile of real visits, with "good" at 2.5 seconds or less. It can change as the page loads and larger elements appear — a placeholder swapped for a real hero image, for instance — but the browser freezes it at the first user interaction (click, tap, keypress) or scroll, because an interaction means the user has already engaged with the page as loaded, so continued loading afterward is no longer a "how long until usable" signal.

What are the four sub-parts of LCP and why does the split matter more than the total?

TTFB, resource load delay (time until the browser starts fetching the LCP resource), resource load time (the fetch itself), and element render delay (time from resource-ready to actually painted). The split matters because each has an unrelated fix — server latency, discovery/preload, image weight/format, and main-thread blocking respectively — so "LCP is 4 seconds" tells you almost nothing actionable while "resource load delay is 1.8 of those 4 seconds" tells you exactly what to do next: fix discovery, not compression.

Can a page have a fast LCP with a heavy hero image? How?

Yes, if the other three phases are near-zero: fast TTFB from an edge cache, zero discovery delay because the image is referenced directly in HTML with a high fetch priority (no CSS/JS indirection), and no main-thread contention at the moment it finishes decoding. A moderately large but well-served AVIF, preloaded and undelayed, frequently beats a tiny image that's discovered late through a client-rendered component — weight is only one of four variables, and often not the dominant one.

Why can text be a better LCP element than an image, and when is that not true?

Text has no fetch phase — it paints as soon as CSS/fonts allow, so it removes the resource-load-time variable entirely, which is why text-led heroes tend to have very fast, very stable LCP. It stops being true when the text depends on a web font with blocking or poorly-configured font-display: the browser may hold the paint (or the font's fallback swap creates its own visible delay), reintroducing a network dependency that behaves a lot like an image's load phase, just smaller and easy to overlook.

How do carousels and sliders typically break LCP measurement?

Slider libraries commonly keep every slide's image in the DOM and hide the inactive ones with CSS that still allows layout/paint consideration (opacity, transform, absolute positioning off-screen) rather than display:none or content-visibility: hidden. The browser can then nominate a slide that isn't the one the user actually sees first as the LCP candidate, giving a misleading measurement, or conversely delay the true first-visible slide's paint because the browser is busy laying out slides nobody sees yet. The fix is to genuinely remove inactive slides from the render consideration, not just visually hide them.

How does fetchpriority interact with LCP specifically, and where does it help most?

fetchpriority="high" raises a resource above the browser's default heuristic priority for its type, which matters most when the LCP element is something the browser's heuristics under-rate — a background image set via CSS, an image far down in DOM order that's visually first, or an image competing against several other high-priority requests on the same connection. It attacks resource load delay and load time simultaneously by winning contention earlier; it does nothing for TTFB or element render delay, which is why fixing LCP is rarely a single-attribute job.

Your LCP is fine in the lab (Lighthouse) but poor in the field (CrUX). Why might that be?

Lab tools run once, under fixed network/CPU conditions, usually on a fast connection with a warm or synthetic cache; field data (CrUX, RUM) aggregates real devices, real network variance, real cache states, and — critically — real interaction timing across the actual user base, at the 75th percentile, which by definition includes a lot of worse-than-lab conditions. Common causes of the gap: a large real-user population on slow mobile connections or older devices, A/B tests or personalisation that change which element is largest for real users, or third-party scripts (ads, chat widgets) present in production but excluded from a synthetic run.

What's the relationship between LCP and preloading, and where's the failure mode?

Preloading the LCP resource collapses resource load delay to near zero by starting its fetch as soon as the browser parses the preload tag rather than whenever the element referencing it is discovered — often a meaningful win on its own. The failure mode is preloading the wrong resource, or too many resources: if the actual LCP element turns out to be something else (common with responsive layouts where the LCP candidate differs by viewport), the preload was wasted bandwidth that may have delayed the real candidate instead of helping it.

How would you explain to a team why "just optimise the image" tickets keep not moving the LCP metric?

Because they're targeting one of four independent sub-parts, and if the regression actually lives in TTFB or discovery delay, image work can shrink the file by 80% and LCP barely moves — the fetch was never the bottleneck. I'd get the team looking at the sub-part breakdown in the same PageSpeed Insights or CrUX report they're already using, so "optimise LCP" tickets become "reduce resource load delay for the homepage hero" tickets — specific enough that whoever picks it up knows whether they're an infra person, a markup person, or a JS person.

What are common causes of a good LCP number in synthetic testing that doesn't reflect the real experience?

Testing on desktop/fast-network profiles when most real traffic is mid-tier mobile on 4G; testing a cold, empty cache repeatedly rather than the mix of warm and cold caches real users have; testing without third-party scripts that are present in production and consume main-thread time right when the LCP element is ready to paint; and testing a URL that isn't representative — the homepage is fast, but the actual entry pages from search or ads carry a different template with a heavier hero. Field data at realistic percentiles is the check against every one of these blind spots.

04 INP: responsiveness, dissected

Docs: web.dev — Interaction to Next Paint · web.dev — Optimize INP · MDN — scheduler.yield()

Interaction to Next Paint replaced First Input Delay as the official responsiveness Core Web Vital in March 2024 — the single most important recent structural change in this entire topic, and worth understanding why it happened, because the reasoning is reused constantly in interviews. FID only measured the delay before an event handler started running; it said nothing about how long the handler itself took, or how long it took the browser to paint the result afterward. A page could have a perfect FID and still feel broken — button presses that visibly do nothing for half a second — because FID was structurally blind to everything after the handler began. INP measures the full round-trip: from the user's interaction (click, tap, keypress) to the next frame the browser actually paints, taking the worst interaction of the session (with a high-percentile exemption for pages with many interactions), scored good at ≤200ms, poor above 500ms.

The three phases of every interaction

PhaseWhat it isTypical fix
Input delayTime from the physical interaction to the event handler startingBreak up main-thread work already running (long tasks blocking the queue)
Processing timeThe event handler(s) actually executingDo less work synchronously; yield mid-handler; move work off-thread
Presentation delayTime from handler completion to the next paint being presentedAvoid forced layout right before paint; reduce style/layout cost of the DOM update

Field data consistently shows processing time as the dominant phase in most real regressions — the handler itself is doing too much synchronous work — which is why "break up long tasks" and "yield to the main thread" are the two phrases you'll hear most in INP guidance.

Yielding: the actual technique, not just the buzzword

A JS task that runs for 300ms straight blocks every other pending task — including the browser's own paint scheduling and other interactions — until it finishes; the event loop cannot pre-empt a running task. "Yielding" means voluntarily breaking a long piece of work into chunks and returning control to the event loop between them, so the browser can paint, or handle another interaction, before you continue. The APIs for this range from the ancient (setTimeout(fn, 0), which works but is deprioritised and imprecise) to the current, Chromium-only scheduler.yield(), which returns a promise, resumes as a prioritised continuation (not just "whenever", like setTimeout does), and composes with scheduler.postTask()'s explicit priority levels.

// Bad: one huge synchronous task - blocks every interaction for its full duration
function renderRows(rows) {
  rows.forEach(row => appendRow(row)); // 5,000 rows, ~400ms, uninterruptible
}

// Better, no new APIs required: yield every N items with setTimeout
async function renderRowsChunked(rows) {
  for (let i = 0; i < rows.length; i += 50) {
    rows.slice(i, i + 50).forEach(appendRow);
    await new Promise(r => setTimeout(r, 0)); // hands control back to the event loop
  }
}

// Modern, Chromium-only: scheduler.yield() resumes as a prioritised continuation,
// so the rest of the work doesn't get starved behind lower-priority tasks
async function renderRowsScheduled(rows) {
  for (let i = 0; i < rows.length; i += 50) {
    rows.slice(i, i + 50).forEach(appendRow);
    if (globalThis.scheduler?.yield) await scheduler.yield();
    else await new Promise(r => setTimeout(r, 0)); // fallback for non-Chromium
  }
}

What changed recently

Beyond the FID→INP swap itself, the diagnostic tooling built specifically for INP is the recent story: the Long Animation Frames API (Chrome 123, March 2024, unit 01) attributes slow frames to specific scripts instead of an opaque "long task"; Total Blocking Time in Lighthouse (a lab proxy correlated with, but not identical to, INP) gets its script attribution from the same underlying data; and scheduler.yield()/scheduler.postTask() give code an actual API to act on that attribution instead of the historical hack of nesting setTimeout calls and hoping. None of these are Baseline yet — they're Chromium-first, which is a recurring pattern in this topic: Chrome ships the diagnostic and the fix API together, other engines catch up on a longer timeline.

Interview trap

Confusing INP with "how fast is my JavaScript" in general. A page can have plenty of background JS (analytics, polling, animations) and still have excellent INP if none of it runs synchronously during an interaction; conversely a page with very little total JS can have terrible INP if the one handler that runs on every click does a synchronous re-render of a huge list. INP is specifically about work that happens inside the interaction-to-paint window, not aggregate script weight — that's a different metric (Total Blocking Time correlates better, but even TBT is a lab proxy, not the field metric itself).

Gotcha

INP reports the worst interaction of the session (with a percentile exemption on pages with unusually many interactions, so one freak outlier among thousands doesn't dominate) — not the average and not the first. A page can look perfectly snappy for nine interactions and have one modal-open handler that does a synchronous fetch-and-render, and that one interaction sets the page's INP for the whole session. Optimising the "average" click handler while ignoring the rare-but-heavy one is a common and costly mistake.

Try it — 25 minutes, two exercises

1. Feel a long task. Add a button whose click handler runs a synchronous loop for ~400ms (e.g. a busy-wait or a large synchronous array operation), then rapidly click elsewhere on the page while it's running. Observe what doesn't respond.

2. Fix it with yielding. Rewrite the handler using the chunked pattern above (with or without scheduler.yield), and repeat the same rapid-click test.

Expected outcome

Exercise 1: every other interaction — a hover state, a second button, even scrolling — freezes for the task's entire duration; DevTools Performance shows one uninterrupted "Task" block with nothing else able to run inside it, and the Long Animation Frames entry (if you inspect it) attributes the whole delay to your function. Exercise 2: the same total work now completes with the page staying responsive to other interactions in between chunks — visible in the trace as many small tasks with paint opportunities between them, and a dramatically lower recorded INP for the page.

Interview Q&A · INP

Why did Core Web Vitals replace FID with INP instead of just adjusting FID's threshold?

Because FID measured the wrong span of time entirely — the delay before a handler starts — and no threshold adjustment fixes a metric that's blind to the handler's own execution time and to how long it takes to paint the result afterward. A page could have near-zero FID and still feel unresponsive for hundreds of milliseconds after every click, which is precisely the experience users complain about, so the metric had to change shape, not just calibration. INP measures start-to-next-paint, which is the thing users actually perceive.

What are the three phases of an interaction and which one dominates in practice?

Input delay (interaction to handler start), processing time (the handler executing), and presentation delay (handler end to next paint). Field data across most real sites shows processing time as the largest contributor in the majority of poor-INP cases — the handler itself is doing too much synchronous work, most commonly re-rendering more of the DOM than the interaction actually requires, or running a synchronous computation that could be chunked or deferred.

Why does INP take the "worst" interaction rather than an average?

Because a single terrible interaction is exactly the kind of experience users remember and complain about, even if every other click on the page was instant — averaging would hide it entirely. There's a percentile exemption for pages with an unusually large number of interactions in a session (so one statistical outlier among thousands of clicks doesn't unfairly tank the score), but the core design intentionally surfaces the worst case rather than smoothing it away, because "mostly fast, occasionally frozen" is a real and painful user experience.

What does it mean to "yield to the main thread", and why doesn't setTimeout(fn, 0) fully solve it?

Yielding means voluntarily breaking work into chunks and returning control to the event loop so pending higher-priority work — user input, paint — gets a chance to run before you continue. setTimeout(fn, 0) does yield, but it queues the continuation as a normal low-priority macrotask with browser-imposed timer clamping and no priority signal, so under load it can be starved behind other work or delayed more than intended. scheduler.yield() resumes as a continuation that inherits sensible priority and is designed specifically for this pattern, which is the practical reason it's replacing the setTimeout(0) hack where it's available.

Give an example of processing time being the bottleneck and how you'd fix it, without reaching for a framework-specific API.

A search-as-you-type box that re-renders a 2,000-item filtered list synchronously on every keystroke: processing time balloons because the handler does the full filter-and-render before yielding. Framework-agnostically, you'd debounce the expensive re-render (not the keystroke itself — the input should still feel instant), and/or chunk the render into batches with a yield between them so the browser can paint intermediate progress and stay responsive to further typing, rather than committing to one uninterruptible synchronous pass over the whole list.

Can INP be poor even with very little total JavaScript on the page?

Yes — INP cares about work that happens synchronously inside the interaction-to-paint window, not aggregate script weight. A page with a tiny JS payload but one click handler that does a synchronous layout-forcing DOM read/write cycle across a large list can have worse INP than a JS-heavy page whose handlers are all small and yield appropriately. This is why "reduce your JS bundle size" is an LCP/loading-time fix more than an INP fix — INP is about the shape of your event handlers, not their total download weight.

How do Long Animation Frames help you fix INP that Long Tasks couldn't?

Long Tasks tells you a task exceeded 50ms; LoAF entries add render delay, per-script attribution (which function, which source), and the style/layout portion of the frame. When triaging a poor INP interaction, that attribution is the difference between "something on this page is slow" and "this specific analytics script's synchronous initialisation is eating 180ms of your interaction budget" — the second is an assignable, fixable ticket, the first is a guess.

How would you explain to a team that "our JS bundle is small, why is INP bad" is the wrong question?

Bundle size affects how much code has to be downloaded and parsed before it can run at all — a loading-time concern that shows up in LCP and TTI-adjacent metrics — but INP only cares about what runs synchronously between an interaction and the next paint, regardless of how big the file it came from was. I'd point them at the specific interaction trace: a 40KB bundle with one handler that does sync layout thrashing on every click will post a worse INP than a 400KB bundle whose handlers are all small and yield-friendly. The fix is about handler shape, not bundle weight, so the investigation has to start in the Performance panel, not the bundle analyzer.

What's the difference between Total Blocking Time (Lighthouse) and INP (field)?

TBT is a lab metric computed from a single scripted run with no real user interactions at all — it sums the blocking portion of long tasks between First Contentful Paint and Time to Interactive as a proxy for how bad responsiveness would likely be. INP is measured from actual user interactions in the field and is the real Core Web Vital that affects ranking and reflects genuine experience. TBT correlates reasonably well with INP in aggregate and is useful in CI because it needs no real users, but a page can have great TBT and still get a real user interaction that posts a poor INP the lab run never exercised.

A dashboard shows INP regressed after a recent release with no obvious new heavy handler. How do you investigate?

I'd start with the CrUX/RUM breakdown by interaction target and device class — a regression concentrated on one component (say, a newly-added modal) points directly at the change, while a broad regression across every interaction points at something systemic like a new third-party script initialising on every page or a global event listener added at the wrong scope. Then I'd reproduce with a Performance recording focused on that interaction and read the LoAF attribution to confirm which script is actually consuming the processing-time budget, rather than guessing from the diff.

05 CLS: stability, dissected

Docs: web.dev — Cumulative Layout Shift · web.dev — Optimize CLS · MDN — aspect-ratio

Cumulative Layout Shift measures unexpected movement of visible elements — good at ≤0.1, poor above 0.25 — and it is the Core Web Vital most directly caused by not knowing a dimension in advance. Every CLS bug reduces to the same root cause: the browser laid something out, then had to redo that layout because new information arrived (an image's real dimensions, a font's real metrics, an ad's real size, an API response), and the redo pushed existing content to a new position after the user had already started looking at, or reaching for, the old one. The fix for every CLS bug is therefore the same shape too: reserve the space before you know the content, so the "redo" never has anything to move.

The formula, and why it's not just "did anything move"

A layout shift's score is impact fraction × distance fraction: impact fraction is how much of the viewport the shifting elements occupy (before and after, unioned), distance fraction is how far the largest shifted element moved, as a fraction of viewport height/width. This is why a tiny element jittering by a few pixels barely registers, while a full-width banner injecting itself above the fold and pushing everything down by 200px registers heavily — both dimensions matter, and CLS deliberately ignores shifts caused directly by user interaction (a menu expanding on click) because those are expected, not "unexpected".

What changed recently: entry animations without a CLS penalty

Historically, animating an element into the layout — a toast notification sliding in, a dropdown appearing — required either JavaScript orchestration or accepting a layout shift the instant display: none flipped to visible. CSS @starting-style, Baseline since August 2024, solves this cleanly: it lets you define the "before" state for an element transitioning from display: none (or newly added to the DOM) so the transition animates smoothly from that starting style, without a script and — done correctly, reserving space rather than inserting abruptly — without the layout jump that used to make entry animations a common, hard-to-notice source of CLS.

Interview trap

"CLS is just about images" undersells the metric badly. In real audits, web fonts (FOUT — the fallback-to-webfont swap changing line length and wrapping) and late-injected third-party content (consent banners, ads that resolve after the initial layout) are extremely common CLS culprits that have nothing to do with images, and both are frequently invisible in a quick lab test because the lab run's font is already cached or the ad network responds unusually fast in a synthetic environment.

Gotcha

A shift caused within 500ms of a genuine user interaction (a click, a tap) is explicitly excluded from CLS by spec, because expanding an accordion or opening a menu should move content — that's the point of the interaction. But this exemption is narrower than people assume: a shift caused by an async operation that a click merely triggered — like a fetch that resolves 800ms later and then reflows the page — falls outside that window and counts in full, even though a human would still trace it back to "the thing I clicked".

Try it — 20 minutes, two exercises

1. Cause it, see it, fix it. Build a page with three <img> tags with no width/height and a slow network throttle. Watch the layout jump as each image loads using DevTools' Layout Shift Regions overlay (Rendering tab → "Layout shift regions"). Add correct dimensions and repeat.

2. Compute a shift by hand. For one deliberately-caused shift, estimate impact fraction (roughly, % of viewport the before+after region covers) and distance fraction (shift distance ÷ viewport height), multiply them, and compare your estimate to the number DevTools reports.

Expected outcome

Exercise 1: without dimensions, each image's arrival visibly shoves subsequent content downward, and the overlay highlights the shifted regions in real time; with dimensions set, the layout is stable from first paint and the overlay shows nothing, because the box existed before the pixels did. Exercise 2: your hand-computed estimate should land within a reasonable range of DevTools' number — the exercise is mainly to make the formula concrete rather than an abstract "0.1 is good" rule you've memorised without understanding.

Interview Q&A · CLS

Give the CLS formula and explain both terms with a concrete example.

Impact fraction × distance fraction. Say a 300px-tall banner slides in above a full-width article: impact fraction is the union of the area occupied before and after the shift, as a fraction of the viewport — here, close to the full viewport width and a meaningful chunk of its height. Distance fraction is how far the largest moved element travelled, divided by the viewport's larger dimension — if the article text moved down by 300px on a 800px-tall viewport, that's 0.375. Multiply the two and you get the shift's score; several such shifts across the page's lifetime sum to the cumulative score.

Why does CLS exclude shifts caused by user interaction, and what's the exact boundary?

Because an accordion expanding on click, or a menu opening, is content moving in a way the user explicitly requested and expects — penalising that would push developers toward avoiding legitimate, useful interaction patterns. The spec draws the boundary at a 500ms window following a genuine input event; a shift inside that window attributed to the interaction is excluded, but a shift caused by an async operation that resolves later — even one the click triggered — falls outside the window and counts normally.

How do web fonts cause layout shift, and how do you fix it without abandoning the custom font?

FOUT (flash of unstyled text) swaps a fallback font for the web font once it loads; if their metrics — average character width, line height, x-height — differ meaningfully, the same text wraps differently and reflows everything below it. The fix is matching the fallback's rendered metrics to the web font's using @font-face descriptors like size-adjust, ascent-override, and descent-override (often generated by a tool that measures both fonts), so the fallback occupies effectively the same box the web font will — the swap still happens, but nothing moves when it does.

What is @starting-style and how does it prevent CLS in entry animations?

It's a CSS rule, Baseline since August 2024, that defines an element's starting state for a transition when the element is newly shown (going from display:none to visible, or newly inserted into the DOM) — previously impossible to animate smoothly without JavaScript, because there was no "before" state to transition from once the element already existed in the DOM. Used correctly — animating opacity/transform within a space already reserved in the layout, rather than an element that itself changes the document's flow — it lets things like toasts and dropdowns animate in without the layout jump that ad-hoc display toggling used to cause.

A page passes CLS in Lighthouse but fails in the field (CrUX). What's a likely explanation?

Ads, consent banners, and other third-party content frequently resolve differently — or not at all — in a lab run versus production, either because the lab environment blocks third-party requests, the ad network responds unusually fast in a controlled test, or the consent banner only appears for real users in regulated geographies. Lighthouse also runs once, cold, on a fixed profile, while field data captures the full spread of real network conditions under which "arrives late enough to shift already-rendered content" becomes far more common.

How do you reserve space for content whose height you genuinely don't know until a fetch completes?

Render a skeleton or placeholder sized to the realistic final height — not an arbitrary small box — so the transition from skeleton to real content is a content swap within a stable box rather than a height change. Where the real height genuinely varies a lot (e.g. comment threads of wildly different length), set a sensible min-height for the loading state and accept that some variance in the final settle is unavoidable, while still eliminating the worst case of a placeholder collapsing from a token height to hundreds of pixels of real content.

Does a CSS transform-based animation ever count toward CLS?

No — CLS specifically measures shifts in an element's layout position (the geometry the layout stage computes), and a transform is a compositor-only visual offset that never touches layout at all (unit 01). An element sliding across the screen via transform: translateX() doesn't move any other element's box and isn't a layout shift by definition, which is one more reason transform is the right tool for movement you actually want, versus the incidental movement CLS is designed to punish.

What's the difference between CLS and a "jank" complaint in general?

CLS specifically measures cumulative unexpected layout movement — content ending up somewhere the user didn't intend it to be. "Jank" is a broader, informal term for visibly stuttering frames, which is usually a symptom of the main thread being too busy to hit the 60fps/16.7ms budget consistently (a rendering-pipeline problem, unit 01) rather than of anything moving to a new final position. A page can be janky (stuttery scrolling) with zero CLS, and a page can have a real CLS problem (a late-loading ad shoving content down once) while otherwise scrolling perfectly smoothly.

How would you audit a large site for CLS sources systematically, rather than element by element?

I'd start from CrUX/RUM's attribution data if available — most real-user monitoring tools report which specific elements caused the largest shifts in the field, which is far more representative than a handful of manual page loads. Where that's unavailable, I'd group by cause category rather than by page: run the Layout Shift Regions overlay across the main templates, and check each of the four usual suspects — unsized media, web fonts, late third-party content, and async-loaded content blocks — because fixing one systemic cause (say, adding aspect-ratio defaults to the image component) typically resolves the same bug across dozens of pages at once.

Can a single-page app with no full navigations still accumulate meaningful CLS?

Yes, and often more than a traditional site — CLS accumulates across the page's entire lifetime, not just initial load, so a long-lived SPA session with route changes, live data updates, and dynamically inserted UI (toasts, live notification badges, infinite-scroll content) can rack up shifts an equivalent server-rendered multi-page site never has the session length to accumulate. This is one reason "soft navigation" measurement (unit 12) matters: without it, a SPA's CLS budget is effectively the whole session, and every dynamic insertion is a candidate to reserve space for upfront.

06 Bundling & code splitting

Docs: Vite — code splitting · Vite blog — announcing Vite 8 · MDN — dynamic import()

This unit is framework-agnostic on purpose: the underlying question — "how much JavaScript does the browser have to download, parse and execute before it can do anything useful" — is identical whether the bundler is Vite, webpack, esbuild, or something newer, and the answer is always some combination of splitting (don't ship code the current page doesn't need) and deferring (ship it, but not on the main thread's critical path). React/Angular-specific splitting patterns (route-based lazy loading, `React.lazy`, Angular's route-level `loadChildren`) are covered where those topics live; what belongs here is the platform mechanism underneath all of them: the ES module graph, dynamic `import()`, and what a bundler actually does with that information.

Why bundle at all, and why split it back apart

Bundling exists because many small files each cost a request — historically expensive under HTTP/1.1's low connection-concurrency limits, and still not free under HTTP/2/3 (unit 07) because each file still costs parse/compile overhead and a round trip through the module graph resolution. Splitting exists because the opposite failure — one giant bundle containing every route, every rarely-used feature, every admin-only screen — means every visitor downloads, parses, and (for module-level code) executes code for screens they may never open. The goal is one bundle per thing that's actually needed together: a shared vendor chunk for framework code every route uses, and separate chunks per route or per rarely-used feature, loaded via dynamic import() exactly when needed.

// Static import: part of the initial graph, bundled into the main chunk,
// downloaded and parsed whether or not this code path ever runs.
import { renderChart } from "./chart.js";

// Dynamic import: its own chunk, fetched on demand - the bundler sees this
// syntax and automatically creates a split point here, no extra config needed
// in most modern bundlers.
button.addEventListener("click", async () => {
  const { renderChart } = await import("./chart.js");
  renderChart(data);
});

What a bundler is actually optimising when it "chunks"

DecisionTrade-off

Route-based splittingSmaller initial bundle vs. a network round-trip (waterfall) when navigating to an unvisited route

Tree-shaking specifically depends on the bundler being able to prove an export is unused — which requires ES module syntax (static, analyzable import/export) rather than CommonJS (require(), whose dynamic nature makes usage analysis unreliable). A library shipped only as CommonJS, or one with import-time side effects the bundler can't rule out, forces the bundler to keep code "just in case" — this is why "does it have an ESM build" is a real, practical question when choosing a dependency, not pedantry.

What changed recently: the bundler landscape converging on Rust

Vite 8 (March 2026) unified its dev-server and production-build pipelines onto Rolldown, a Rust-based bundler — previously Vite used esbuild for dev (fast, but with different module resolution semantics than what shipped to production) and Rollup for the production build, a split that occasionally caused dev/prod behavioural mismatches. Rolldown replaces both with one engine, claimed at 10-30x faster builds than the previous Rollup-based production path. Vite 8.1 (June 2026) continued that line, and @vitejs/plugin-react v6 moved off Babel onto Oxc (also Rust) for its transforms. The requirement floor moved too: Node 20.19+ or 22.12+. The broader pattern, not specific to Vite: JS-ecosystem tooling has been steadily migrating its performance-critical inner loop (parsing, transforming, bundling, minifying) to Rust/Go, because a bundler written in JS pays the same parse/execute tax it's trying to save its users from.

Interview trap

"Just lazy-load everything" is not free splitting — every dynamic import() that only resolves after a user action introduces a network round-trip (plus parse/execute time) exactly when the user is waiting for that action to complete. Over-splitting a page into dozens of tiny on-demand chunks can make an interaction feel slower than one moderately-sized bundle that was already warm in cache. The right question isn't "can this be split" but "is this code needed rarely enough, and is the split large enough, that the round-trip cost is smaller than the cost of shipping it to everyone upfront."

Gotcha

A "successful" code-split that still imports a shared utility module from both the main chunk and a lazy chunk can end up duplicating that utility's code in both chunks if the bundler's chunk-graph analysis doesn't recognise the shared dependency — inflating total downloaded bytes across a session even though each individual chunk looks appropriately small. Checking a bundle analyzer's chunk overlap (not just each chunk's size in isolation) is how this actually gets caught; "my main bundle got smaller" doesn't prove the split helped in aggregate.

Try it — 25 minutes, two exercises

1. Split and measure. Take any small app with a heavy, infrequently-used feature (a chart library, a rich-text editor) and convert its import from static to dynamic import(). Compare the initial bundle's parse/compile time in DevTools Performance before and after.

2. Find duplicated code across chunks. Run whatever bundle-analyzer plugin your toolchain offers (most modern bundlers have one) and look for the same module appearing in more than one chunk. If you find one, add it to a shared/vendor chunk explicitly and re-measure total transferred bytes.

Expected outcome

Exercise 1: the initial bundle's script-evaluation time in the Performance panel drops by roughly the evaluation cost of the library you removed, and the "Scripting" portion of the timeline for first load shrinks visibly; the library's own chunk only appears in the trace once the feature is actually used. Exercise 2: it's common on a first pass to find at least one shared helper duplicated across two or more route chunks — moving it into an explicit shared chunk should reduce total bytes transferred across a full-session crawl of the app, even though no single chunk's minified size changes dramatically.

Interview Q&A · bundling & code splitting

What's the practical difference between bundling and code splitting, and why do you need both?

Bundling combines many source modules into fewer delivered files, solving the "too many small requests" problem. Code splitting deliberately creates more than one bundle so that not all code has to be downloaded upfront, solving the opposite problem — one bundle containing everything a large app might ever need. They're complementary: you bundle within a route/feature to minimize request count, and split across routes/features so unrelated code doesn't ship to everyone. Neither alone is the answer; an app with only bundling ships too much upfront, an app with only splitting (one module per request) pays request overhead needlessly.

How does dynamic import() actually create a split point — what is the bundler looking for?

Bundlers statically scan the module graph for the import() function-call syntax (distinct from the static import declaration) and treat each call site as a boundary: the imported module and everything it exclusively depends on gets extracted into its own chunk, fetched only when that line of code actually executes. Because it returns a promise, the calling code naturally handles the network delay with await or .then() — the language feature and the bundling optimisation are the same mechanism, not a bundler-specific convention layered on top.

Why does tree-shaking work reliably with ESM but not with CommonJS?

ESM's import/export bindings are static — resolvable at build time without running any code, so a bundler can prove with certainty which exports are ever referenced and delete the rest. CommonJS's require() and module.exports are just function calls and object mutations that could, in principle, do anything (conditional requires, computed property access, side effects at require-time) — the bundler can't prove an export is unused without risking breaking behaviour it can't fully analyse, so it conservatively keeps more than strictly necessary. This is a large part of why "ships an ESM build" matters when choosing a dependency for bundle-size-sensitive code.

What did Vite 8 actually change, and why does it matter beyond "faster builds"?

Vite 8 (March 2026) unified dev and production onto one bundler, Rolldown (Rust), replacing the previous split of esbuild for dev and Rollup for production. Beyond raw speed (claimed 10-30x over the old Rollup production path), unifying the engine removes a whole class of "works in dev, breaks in prod" bugs caused by esbuild and Rollup having subtly different module resolution and transform semantics — a real, if under-discussed, pain point of the previous architecture. It's part of a broader ecosystem shift of build tooling's performance-critical core moving to Rust/Go rather than JS.

Give a concrete example of over-splitting making performance worse.

A settings page split into six separate lazy chunks, one per settings tab, each 3KB — a user who opens the settings page and clicks through several tabs now pays six network round-trips (each with its own request/parse overhead) for content that combined is smaller than a single typical route chunk. Bundled together as one "settings" chunk loaded once when the page opens, the same content would cost one request and no further round-trips while switching tabs the user was always going to visit anyway.

How would you decide whether a large third-party library deserves its own chunk?

By usage frequency and size: if most sessions never touch the feature that needs it (a PDF export button, an admin-only chart), splitting it out is close to free — those sessions save the full download/parse cost, and the rare sessions that do use it pay one round trip for a feature they're already committed to using. If nearly every session uses it and it's small, splitting adds a round trip for no real benefit; if it's used by most sessions but is very large, the calculus shifts back toward splitting so it doesn't block the initial critical path even for the majority who need it eventually but not immediately.

What's chunk duplication and how does it happen even when each individual chunk analyzer report looks fine?

It happens when a module is imported from two or more independent chunks and the bundler's chunk graph doesn't hoist it into a shared chunk — each importing chunk gets its own copy of that module's code. Each chunk's size in isolation looks reasonable, but the total bytes actually transferred across a session (main chunk + route A + route B, say) is inflated by the duplicated module. Spotting it requires looking at cross-chunk overlap in a bundle analyzer, not just each chunk's individual size — a check many teams skip because it's not the default view most analyzer UIs open to.

Why does a route-based split sometimes make the *initial* page slower rather than faster?

If the split boundary is drawn incorrectly — say the initial route's own code ends up depending on a chunk that also has to load before first render, effectively serializing two round trips instead of one — the split adds latency rather than removing it. This is common when a "shared" chunk is defined too eagerly and ends up on the critical path for the very first paint; the fix is checking the actual load waterfall for the initial route, not just trusting that "we added code splitting" automatically improved things.

How does HTTP/2 or HTTP/3 multiplexing change the bundling-vs-splitting calculus versus HTTP/1.1?

Under HTTP/1.1's low per-origin connection concurrency, many small files queued behind each other, making aggressive bundling into fewer, larger files a clear win regardless of unused code shipped. Under HTTP/2/3 multiplexing (unit 07), many small requests over one connection no longer serialize the same way, which weakens (but doesn't eliminate — parse/compile and per-request overhead are still real) the pure "fewer files is always better" argument, and strengthens the case for finer-grained splitting since the request-count penalty for more files is much smaller than it used to be.

What's a good first question to ask when auditing an unfamiliar app's bundle for size problems?

"What's actually in the initial chunk that isn't needed for the first render" — a bundle analyzer's treemap view answers this directly by size, and it's common to find entire admin panels, rarely-used chart libraries, or polyfills for browsers the site doesn't actually need to support, sitting in the main chunk purely because nobody drew a split boundary around them. I'd fix the biggest, easiest wins first (an obviously-unused-on-this-route dependency) before reaching for a wholesale restructuring of the app's route/chunk architecture.

Does code splitting help LCP, INP, both, or neither, and why?

Primarily LCP-adjacent metrics (and general loading performance): a smaller initial bundle means less to download and parse before the page can render and become interactive, which factors into resource load time and, for JS that runs before paint, element render delay. It can also help INP indirectly — less JS parsed and executing upfront means less main-thread contention during early interactions — but splitting doesn't fix a poorly-written event handler; a lazy-loaded chunk with a synchronous, unyielding handler inside it will still post a bad INP once it runs, splitting or not.

07 Caching, HTTP/2-3 & delivery

Docs: MDN — Cache-Control · web.dev — HTTP cache · MDN — HTTP/2

Nothing you do in units 01-06 matters on a repeat visit if the browser has to re-fetch everything anyway — caching is the highest-leverage, cheapest-to-implement lever in this entire guide, and it's also the one most commonly configured wrong, because the failure mode (stale content shown to a user) is scarier than the failure mode of caching too little (a slightly slower repeat visit), so teams reflexively under-cache. The transport layer underneath — HTTP/2, HTTP/3 — changed the economics of "how many files" in ways that reshape decisions from unit 06, and it's worth understanding both together.

Cache-Control: the directives that actually matter

DirectiveMeans
no-storeNever cache this response at all, anywhere
no-cacheCache it, but revalidate with the server before every use (misleadingly named — it does cache)
private / publicWhether shared caches (CDNs, proxies) may store it, or only the browser
max-age=NFresh for N seconds from response time — no network request at all until it expires
immutableThis exact URL's content will never change — skip revalidation entirely even on a hard refresh

The pattern that gets the most mileage out of these: pair a long max-age (a year, effectively forever) with immutable on assets whose URL contains a content hash — app.a1b2c3.js — and a build step that changes the filename whenever the content changes. This turns "how long can I safely cache this" from a judgment call into a tautology: the URL is immutable by construction, so caching it forever is always correct, and a new deploy simply references new URLs. HTML documents themselves usually get the opposite treatment — no-cache (revalidate every time) or a short max-age — because they're the entry point that has to reflect the latest deploy, and they're cheap to revalidate (a small file, often a 304 Not Modified response).

# Cache-busted, content-hashed static assets: cache forever, never revalidate
location ~* \.[a-f0-9]{8}\.(js|css)$ {
  add_header Cache-Control "public, max-age=31536000, immutable";
}

# The HTML entry point: always revalidate, so a deploy is visible immediately
location = /index.html {
  add_header Cache-Control "no-cache";
}

ETag and Last-Modified: revalidation without a full re-download

When a cached response needs revalidation (no-cache, or an expired max-age), the browser doesn't have to blindly re-download — it sends the cached response's ETag (an opaque content fingerprint) back as If-None-Match, or its Last-Modified timestamp as If-Modified-Since. If the server's current version matches, it replies 304 Not Modified with no body at all — the round-trip still happens, but the payload doesn't, which is why "revalidate" and "re-download" are not the same cost.

The one that surprises people: bfcache doesn't obey no-cache

The back/forward cache (bfcache) preserves an entire page — DOM, JS heap, everything — in memory when the user navigates away, so that hitting back or forward restores it instantly with zero network activity, no re-parse, no re-render. This is not the HTTP cache and does not consult Cache-Control at all: a page can be marked no-cache or even effectively no-store for HTTP purposes and still be served whole from bfcache on a back navigation, because bfcache is restoring a live, already-constructed page, not re-fetching a resource. This has real correctness implications (a logged-out banking session restored from bfcache showing stale sensitive data) which is why certain page behaviours — an unload handler, specific headers — can opt a page out of bfcache eligibility entirely.

What changed recently: the transport layer

HTTP/2 (mainstream since the mid-2010s, still the baseline most sites should assume) introduced multiplexing — many requests and responses interleaved over a single TCP connection — which directly weakened the old "domain sharding" and "minimize file count above all else" advice from the HTTP/1.1 era, where each origin got a small fixed number of parallel connections and every extra file queued behind them. HTTP/3, built on QUIC (UDP-based, not TCP), removes a subtler problem HTTP/2 still had: head-of-line blocking at the transport layer — under HTTP/2, a single lost packet stalls every multiplexed stream on that TCP connection until it's retransmitted, because TCP guarantees strict byte-order delivery; QUIC's streams are independent at the transport level, so one dropped packet only stalls the one stream it belonged to. This matters most on lossy connections — mobile networks, congested wifi — where HTTP/2's head-of-line blocking was invisible on a lab connection but real in the field.

Interview trap

Treating no-cache as "don't cache" — it's arguably the single most misread HTTP header name in the entire stack. no-cache means "cache it, but you must revalidate with the server before using the cached copy each time" — the opposite of what the name suggests to most people on first read. The directive that actually means "don't cache" is no-store. Confusing the two either leaves performance on the table (unnecessarily re-downloading a resource you could have revalidated cheaply) or, worse, actually caches something sensitive that should have been no-store.

Gotcha

Multiplexing HTTP/2 gave you doesn't mean "file count no longer matters" — it removed the connection-concurrency penalty, not the per-request overhead (server processing, TLS record framing, and for JS specifically, parse/compile cost that's unrelated to transport at all). Teams sometimes over-correct after adopting HTTP/2 by abandoning bundling entirely and shipping hundreds of tiny modules unbundled, then are surprised performance didn't improve — the transport layer only ever solved one part of the "many small files" cost.

Try it — 20 minutes, two exercises

1. Watch a 304 happen. Load any site with proper cache headers, then reload. In the Network panel, find a request that returns status 304 and compare its "Time" column to a full 200 response for a similar-sized resource. Check the request headers for If-None-Match.

2. Check your own bfcache eligibility. Navigate to a page you control, then away from it, then hit back. In DevTools' Application panel, look for "Back/forward cache" diagnostics (or use chrome://process-internals/the Lighthouse bfcache audit) to see whether the page was restored from bfcache or reloaded, and if reloaded, what blocked it.

Expected outcome

Exercise 1: the 304 response completes far faster than the 200 despite the same round-trip distance, because no body is transferred — the "Size" column shows only response headers, often under 1KB, versus the resource's full size on the 200 response. Exercise 2: many real sites fail bfcache eligibility for reasons visible in the diagnostic — an unload event listener is the single most common blocker, still present in a lot of analytics/tracking code written before bfcache eligibility was a consideration.

Interview Q&A · caching & delivery

Explain the difference between no-cache and no-store precisely — this trips people up constantly.

no-store means exactly what it sounds like: never persist this response anywhere, always fetch fresh. no-cache is the misleadingly-named one — it permits caching the response, but requires revalidating with the origin server (typically via a conditional request using ETag/If-None-Match) before the cached copy may be used, every time. In practice no-cache often costs little more than a round trip for a 304, while no-store costs the full download every single time — very different performance profiles despite similarly cautious-sounding names.

What makes the "content-hash filename + immutable" pattern work so well, and what does it require of your build?

It converts a caching decision that would otherwise require guessing an expiry into a tautology: the URL itself encodes the content, so if the content changes, the URL changes, and the old URL's cached copy — correctly — never needs to be invalidated because nothing at that exact URL ever changes. It requires the build to (a) compute a hash from file contents, (b) bake that hash into the emitted filename, and (c) rewrite every reference to that file (HTML, other JS, CSS) to the new hashed name — which is exactly what a bundler's asset pipeline does automatically, and precisely why hand-rolled static sites that skip this step tend to either under-cache everything or ship stale assets after a deploy.

Why does the HTML entry point usually get short or no caching while its JS/CSS gets cached for a year?

The HTML file is the one artifact whose URL doesn't change on deploy (it's just /index.html or /), so if it were cached aggressively, users would keep loading an old shell referencing old, possibly-deleted asset URLs after a new deploy. Its own download cost is small and cheap to revalidate (often just a 304), so there's little to gain and a real correctness risk to lose by caching it long — the asymmetry (tiny, must-be-fresh HTML pointing at large, safely-immutable hashed assets) is a deliberate, standard pattern, not an oversight.

Does clearing Cache-Control headers guarantee a back navigation re-fetches the page?

No — bfcache is a separate mechanism from the HTTP cache and doesn't consult Cache-Control at all; it can restore an entire already-rendered page, including its JS execution state, purely from memory on a back/forward navigation regardless of what caching headers said. What does control bfcache eligibility is a different set of factors — certain APIs held open (some WebSocket/IndexedDB patterns), an unload event listener, or an explicit Cache-Control: no-store on the navigation response itself in some browsers' implementations — none of which is the same lever as tuning asset caching.

What specific problem does HTTP/2 multiplexing solve that domain sharding used to work around?

Under HTTP/1.1, browsers opened a small fixed number of parallel TCP connections per origin (historically six), so a page with many resources on one domain queued requests behind that limit; "domain sharding" — deliberately serving assets from several subdomains — worked around it by multiplying the effective connection budget, at the cost of extra DNS lookups and TLS handshakes per shard. HTTP/2 multiplexes many logical streams over a single connection, removing the concurrency ceiling that sharding was compensating for — which is why sharding is now actively counterproductive under HTTP/2/3: it recreates per-shard connection overhead for no remaining benefit.

What is head-of-line blocking, and how does HTTP/3 differ from HTTP/2 on this specifically?

It's the situation where one lost or delayed unit of data stalls data that's otherwise ready to be delivered, because the transport guarantees strict in-order delivery. HTTP/2 multiplexes many streams over one TCP connection, but TCP itself still guarantees byte-order delivery for the whole connection — so one dropped packet blocks every multiplexed stream until it's retransmitted, even streams whose data already fully arrived. HTTP/3 runs over QUIC (UDP-based) with independent per-stream delivery guarantees, so a lost packet only stalls the one stream it belongs to, not the other concurrent requests sharing the connection — a meaningful win specifically on lossy networks.

A resource is served with max-age=31536000 but the team needs to push an urgent fix to it right now. What are the options?

If the URL is content-hashed (the immutable pattern), the correct fix is simply deploying new content under a new hash — the old cached copy becomes irrelevant because nothing references its URL anymore, no cache-busting trick needed. If the URL is not hashed and was cached long-lived by mistake, the practical options are all imperfect: append a cache-busting query string to every reference (works, but requires touching every referencing page), or wait out the cache lifetime, or in the worst case use a CDN's cache-purge API if available — which is exactly the scenario the hashed-filename pattern exists to make permanently unnecessary.

Why can a lab performance test on a fast, low-latency connection hide an HTTP/2 vs HTTP/3 difference that shows up in the field?

Head-of-line blocking and connection-level retransmission costs only bite meaningfully when packet loss or congestion is actually happening; a clean lab connection with near-zero loss rarely triggers the scenario HTTP/3 improves on, so both protocols look equivalent in that environment. Real mobile networks, congested public wifi, and long-distance routes have materially higher loss rates, which is exactly where HTTP/3's independent stream delivery shows a measurable improvement over HTTP/2 — a gap invisible until you test under realistic network conditions or look at field percentiles.

Does adopting HTTP/2 mean you no longer need to bundle JavaScript?

No — multiplexing removes the connection-concurrency penalty for many parallel requests, but it doesn't remove per-request server processing overhead, TLS record framing overhead, or (critically, and unrelated to transport entirely) the parse and compile cost of many separate small JS files versus fewer larger ones. Some teams over-correct after adopting HTTP/2 by abandoning bundling altogether, shipping hundreds of unbundled modules, and are surprised the win didn't materialize — the calculus in unit 06 changed at the margin, not the conclusion that some bundling is usually still worthwhile.

How would you diagnose whether a slow repeat visit is a caching problem versus something else?

Check the Network panel's "Size" column on the reload — a value like "(disk cache)" or "(memory cache)" for the bulk of requests means caching is working and the slowness lives elsewhere (likely main-thread JS execution, unit 01/04); actual byte counts on a reload for resources that should be long-cached means the cache headers aren't doing their job, worth checking Cache-Control and whether the asset's URL is even cache-bustable in the first place. I'd separate "did it come from cache" from "was execution slow even with a cached asset" before assuming caching is the culprit.

08 Images: formats, sizing, priority

Docs: MDN — responsive images (srcset/sizes) · caniuse — AVIF · MDN — loading

Images remain the single largest byte category on most real pages by a wide margin, and unlike JS, most image bytes are pure waste rather than functionality — a 4000px photo served to a 400px thumbnail slot is bytes the user's device decodes and discards. This unit is the "reduce what actually gets sent" complement to unit 03's "reduce the delay before sending it" — LCP cares about both, and they're solved independently.

Right-sizing: srcset and sizes, not just "compress the file"

A single <img src> forces every device — a phone and a 4K monitor alike — to receive the same file. srcset offers the browser several resolutions of the same image; sizes tells it how large the image will actually render at different viewport widths, so the browser (not the server, not a guess) picks the smallest sufficient candidate for the device it's actually running on.

<img
  src="/photo-800.jpg"
  srcset="/photo-400.jpg 400w, /photo-800.jpg 800w, /photo-1600.jpg 1600w"
  sizes="(max-width: 600px) 100vw, 50vw"
  width="800" height="533"
  alt="…">
<!-- A phone in a narrow viewport downloads the 400w file; a wide-viewport
     desktop rendering this image at half its width downloads the 800w file -
     the 1600w file is reserved for genuinely large renders (or high-DPI). -->

Priority and laziness: loading, decoding, fetchpriority together

loading="lazy" defers an off-screen image's fetch until it's near the viewport — correct for almost every image below the fold, and actively harmful on the LCP candidate itself, since delaying its fetch is precisely the resource-load-delay problem from unit 03. decoding="async" tells the browser it may decode the image off the main thread's critical rendering path, so a large image's decode doesn't block presenting other already-ready content. These compose with fetchpriority (unit 02) rather than replace it: fetchpriority="high" on the LCP image plus default lazy-loading on every other image is the standard, sane combination for a typical content page.

What changed recently: automatic format negotiation shifting to the platform

Content-negotiated image delivery — serving AVIF to browsers that support it and JPEG to those that don't, from one URL — used to require either server-side user-agent sniffing (fragile, cache-unfriendly) or manual <picture> markup for every image. CDN-level automatic format negotiation (via the Accept request header, which reliably advertises supported image formats) has become the default behaviour of most major image CDNs, shifting the format-selection problem from "something developers hand-author per image" to "something the delivery layer handles once, for every image" — markup-level <picture> remains necessary when you don't control the CDN or need art-direction (different crops per viewport), not just format switching.

Interview trap

"Just use WebP/AVIF for everything" skips the actual skill being tested, which is sizing, not format. A correctly-sized JPEG (matching the actual render dimensions, reasonable quality setting) frequently beats an incorrectly-oversized AVIF — format gains are real but typically 20-50%, while serving the right resolution instead of a 4x-too-large one is often a 70-90% reduction. Interviewers listening for "modern format" as the whole answer are testing whether you reach for the flashy lever before the boring, bigger one.

Gotcha

loading="lazy" on the LCP element is a surprisingly common self-inflicted wound, usually introduced by a component library that lazy-loads every image by default, including whichever one happens to land above the fold on a given page. Because the effect (a delayed fetch) looks identical in the trace to a slow network, it's easy to spend time on network/CDN theories before noticing the actual loading attribute value on the LCP candidate — checking that attribute should be one of the first things you look at, not a last resort.

Try it — 20 minutes, two exercises

1. Measure the sizing gap. Find a large photographic image on a real page rendered at a modest on-screen size (check its rendered width in DevTools' Elements panel box model). Compare its natural/intrinsic dimensions (also shown there) to its rendered dimensions, and estimate the wasted bytes ratio.

2. Compare formats on the same source image. Export one photo as JPEG, WebP, and AVIF at matched visual quality (not matched settings — eyeball comparable quality), and compare file sizes.

Expected outcome

Exercise 1: it's common to find images rendered at well under half their intrinsic resolution — DevTools' own "Improvements" or image-related audits in Lighthouse flag this directly as "properly size images" when the gap is large enough to matter. Exercise 2: at matched visual quality, AVIF typically produces the smallest file, WebP next, JPEG largest — the exact margins vary a lot by image content (AVIF's advantage is usually largest on photographic content with fine detail, smaller on simple graphics).

Interview Q&A · images

What problem does srcset + sizes solve that a single optimized image file can't?

A single file, however well-compressed, is still one fixed resolution — correct for exactly one device/viewport combination and wasteful for every other. srcset offers multiple resolution candidates and sizes tells the browser how large the image will actually render across breakpoints, so the browser's own logic (which knows the actual device pixel ratio and viewport width at load time, information the server doesn't reliably have) picks the smallest sufficient candidate — solving the "one size serves everyone" waste at the resolution axis, independent of and complementary to format choice.

Why is JPEG XL a useful example to bring up even though you shouldn't use it in production?

Because it demonstrates that format adoption isn't purely a technical-merit contest — JPEG XL had genuinely strong compression and feature credentials, yet ended up disabled in two major engines and only partially supported in a third, which is the opposite outcome technical quality alone would predict. The generalizable lesson for a lead engineer is procedural: always verify current actual multi-browser support before depending on a format in production, rather than assuming a technically superior spec will inevitably win adoption — vendor decisions and ecosystem momentum matter as much as the codec itself.

What's the difference between loading="lazy" and decoding="async", and are they related?

loading="lazy" controls when the fetch happens — deferring the network request itself until the image nears the viewport. decoding="async" controls where the decode happens relative to other rendering work — hinting that the browser may decode this image's pixel data without blocking presentation of other already-ready content. They address different costs (network timing vs. main-thread decode timing) and commonly appear together, but neither implies the other — an eagerly-loaded image can still be marked decoding="async", and a lazily-loaded one still benefits from it once its deferred fetch eventually resolves.

How would you explain to a team why their AVIF migration didn't move Lighthouse's score much?

I'd check whether the actual bottleneck was format or sizing — if the images were already being served at roughly correct dimensions, switching format captures the 20-50% typical compression gain, which is real but modest against a page with other larger issues (render-blocking resources, unoptimized fonts). If the images are still being served oversized relative to their rendered dimensions, the format switch captured a fraction of the available savings — sizing is very often the bigger lever, and a format-only migration without addressing srcset/sizes leaves most of the win on the table.

Why shouldn't SVG be used for photographic content, even though it's "just markup" and can compress well?

SVG describes vector shapes and paths — it has no efficient representation for continuous photographic detail (gradients of arbitrary complexity, noise, texture), so encoding a photo as SVG either requires embedding a raster image inside it anyway (gaining nothing) or produces enormous, slow-to-parse markup trying to vector-approximate something inherently raster. SVG's real strength — infinite scalability with tiny file size — only holds for genuinely vector content: icons, logos, line art, illustrations with flat colour regions.

What's the risk of applying loading="lazy" indiscriminately across a component library's image component?

Whatever image happens to render above the fold on a given page — often the LCP candidate — gets its fetch deferred exactly like every off-screen image, directly harming the metric that matters most on that page. Because it's set as a library default rather than a per-usage choice, the bug can be invisible in the component's own tests (which may not render it above the fold) and only surface on specific pages where that instance happens to be the hero — exactly the kind of context-dependent bug that's easy to introduce and hard to notice without checking the LCP candidate's actual attributes directly.

How does device pixel ratio (DPR) factor into responsive image decisions?

A "400px-wide" CSS box on a 3x-DPR phone screen actually has 1200 physical pixels to fill, so serving a literal 400px-wide image would look visibly blurry on that device despite being "correctly sized" in CSS-pixel terms. srcset's width descriptors (400w) combined with sizes let the browser account for DPR automatically when picking a candidate — it's evaluating "how many physical pixels does this slot need" using both viewport width and the device's actual pixel ratio, which a naive single-image approach or manual DPR-only (x-descriptor) markup handles less precisely across the full range of real viewport widths.

Should format negotiation happen at the CDN/server layer or in HTML markup — how do you decide?

If you control a CDN or image service that does content negotiation via the Accept header, that's usually the lower-maintenance choice — one URL, correct format served automatically per requesting browser, no per-image markup to maintain. Markup-level <picture> remains necessary specifically when you need art direction (genuinely different image crops or compositions per viewport, not just format/resolution swaps) or when you don't have that CDN layer available — the two approaches solve overlapping but not identical problems, and a mature setup often uses CDN negotiation for format/resolution and markup only where art direction is genuinely needed.

A page's LCP is an image that's already AVIF, correctly sized, and preloaded — but LCP is still slow. What's left to check?

At that point the image itself is very unlikely to be the bottleneck — I'd go back to the four LCP sub-parts (unit 03): is TTFB slow (server/CDN latency unrelated to the image), is there main-thread contention delaying the actual paint after the image is ready (element render delay — a blocking script running right when the image arrives), or is the image simply not the actual largest element the browser considers (a slider/carousel issue, or a text block that's genuinely larger). Having exhausted format/sizing/priority, the remaining causes live outside the image itself.

Why is "properly size images" one of the most consistently high-impact Lighthouse audits across real-world sites?

Because unlike many optimisations that require architectural change, mismatched image dimensions are usually a pure implementation bug — a CMS or component not passing through the actual rendered size, a design that changed without updating the export size — with no functional trade-off to fixing it: the user-visible result is identical, only the wasted bytes disappear. That combination (large potential savings, no downside, and a very common root cause across unrelated codebases) is exactly why it shows up disproportionately in aggregate Lighthouse data compared to fixes that involve real trade-offs.

09 Fonts & the FOIT/FOUT trade-off

Docs: MDN — font-display · web.dev — font best practices · MDN — size-adjust

Every web font strategy is a negotiation between three things the browser can't have simultaneously for free: show text immediately (in a fallback), show text in the correct font, and never move anything once it's shown. Pick two. Unit 05 already covered the layout-shift half of this trade-off; this unit is about the other half — the actual choice of when text becomes visible at all, which is entirely what font-display controls.

font-display: naming the trade-off explicitly

ValueBehaviourTrade-off

There is no value that gives you "instant, correct-font, no-shift" simultaneously — that combination is only achievable if the font is already loaded before the text needs to render at all, which is exactly what preloading (unit 02) is for: <link rel="preload" as="font"> starts the font's fetch as early as possible, shrinking the window during which any of these trade-offs actually bites.

@font-face {
  font-family: "Inter";
  src: url("/inter-var.woff2") format("woff2");
  font-display: swap; /* the sane default for body text: never invisible */
}

/* The size-adjust trio: tune the *fallback* font's metrics to match the
   web font's, so the swap in `swap` mode doesn't reflow anything (unit 05) */
@font-face {
  font-family: "Inter Fallback";
  src: local("Arial");
  size-adjust: 107%;
  ascent-override: 90%;
  descent-override: 22%;
}
body { font-family: "Inter", "Inter Fallback", sans-serif; }

Subsetting and variable fonts: shrinking what has to load at all

A full font file contains glyphs for every character the typeface supports — often far more than a given page uses (many scripts' worth of Unicode coverage, when the page is only ever rendered in one language). Subsetting strips unused glyphs at build time, sometimes cutting a file to a fraction of its original size. Variable fonts solve a different, additive-feature problem: instead of separate font files for regular/bold/italic/every-weight-in-between (each a full separate download), one variable font file encodes the entire weight/style axis and the browser renders any point along it via CSS (font-weight: 550 is valid, not just 400/700) — often smaller in total than even two or three static weights combined, and it eliminates the multi-request problem entirely for a typeface used across several weights.

What changed recently: matching fallback metrics is now a solved, tooling-assisted problem

Manually computing size-adjust/ascent-override/descent-override values by trial and error used to be a genuinely tedious, imprecise exercise. Automated fallback-matching (measuring a web font's actual metrics and generating matched override values for a chosen system fallback) has become a standard, expected feature of the modern font-loading tooling landscape — several build-time tools and font-loading libraries now generate these descriptors automatically, moving "zero-shift font swap" from an expert-only technique to close to a default. The underlying CSS capability itself is well-established Baseline; what changed is the tooling making it practical to use correctly without hand-tuning percentages by eye.

Interview trap

Assuming font-display: swap is strictly "better" than block because FOIT sounds worse than FOUT in the abstract. For genuinely brand-critical text — a logo wordmark, an icon font where the fallback renders as literal garbage characters instead of icons — a brief invisible period can be the objectively better user experience than visibly-wrong content flashing before the correct version arrives. The right choice depends on what the fallback actually looks like, not a blanket rule; an icon font falling back to random Unicode glyphs is a case where block (or preloading aggressively enough that neither state is ever seen) beats swap.

Gotcha

Preloading a font with <link rel="preload" as="font"> without the crossorigin attribute silently fails to connect to the actual @font-face fetch — fonts are fetched in "anonymous" CORS mode by the CSS engine regardless of same-origin status, so a preload without crossorigin creates a second, uncoalesced request instead of priming the one the font engine will actually use. The preload appears to work (no console error, the network tab shows a request) while doing nothing useful — this is one of the more common "I added the optimisation and nothing changed" bugs in this entire topic.

Try it — 20 minutes, two exercises

1. See all four font-display values. Load the same web font under block, swap, fallback, and optional on a throttled connection (slow 3G), and note when text becomes visible and whether it visibly swaps under each.

2. Break, then fix, the preload. Add a font preload without crossorigin, confirm in the Network panel that two separate requests for the same font URL appear (or that the preload shows as unused). Add crossorigin and confirm it drops to one coalesced request.

Expected outcome

Exercise 1: block shows a clearly invisible period before any text appears; swap shows fallback text immediately, visibly reflowing once the web font arrives; fallback and optional sit between these, with optional most likely to simply keep the fallback if the network is slow enough. Exercise 2: without crossorigin, DevTools' "Coverage" or a close look at the Network panel shows the preloaded resource marked as unused by the actual font fetch; adding crossorigin collapses it to a single request that the preload genuinely accelerates.

Interview Q&A · fonts

Explain FOIT vs FOUT and which font-display values produce each.

FOIT (flash of invisible text) is a period where text that would otherwise be visible is hidden while the browser waits for a web font — produced by font-display: block for its initial window, and briefly by fallback and optional. FOUT (flash of unstyled text) is text rendered immediately in a fallback font, then visually swapped once the web font loads — produced by swap, and eventually by fallback if the font arrives within its swap window. Neither is universally correct; the choice depends on how bad the fallback looks and how layout-shift-sensitive the surrounding content is.

Why doesn't any font-display value give you instant, correct-font, zero-shift simultaneously?

Because those three properties are only jointly achievable if the correct font is already available the instant text needs to render — which is a loading-order problem, not a rendering-mode problem. font-display only controls what happens during the window before the font is ready; it can't make the font arrive faster. The only way to actually get all three is to shrink that window to zero via preloading (so the font is ready before it's needed) or a self-hosted, small, subsetted font that loads fast enough in practice that the trade-off rarely bites — font-display is damage control for the window that remains.

What do size-adjust, ascent-override, and descent-override actually fix?

They adjust a fallback font's effective metrics — its overall scale and vertical extents — to match a web font it will eventually be swapped for, so that when swap mode performs the swap, the fallback was already occupying essentially the same box the web font will occupy: same line height, same approximate character width, same wrapping. Done well, the visual "flash" of the wrong font still happens (the letterforms genuinely change), but the layout doesn't move — solving the CLS half of FOUT (unit 05) without abandoning the immediate-visibility benefit of swap.

How do variable fonts reduce total bytes versus loading several static weights?

A variable font encodes an entire continuous axis (weight, and sometimes width/slant/optical size) in one file using shared outline data with per-axis deltas, rather than storing complete, largely-redundant glyph outlines for every discrete weight separately. For a typeface used at three or more weights, one variable font file is frequently smaller in total than the sum of that many static files, while also unlocking CSS-level fine control (font-weight: 550) that static files never offered at all — a rare case where "fewer requests" and "smaller total bytes" and "more design flexibility" all point the same direction simultaneously.

Why does subsetting matter even for a typeface only ever displayed in English?

A full font file typically ships with Unicode coverage for far more scripts and symbols than a single-language page uses — Cyrillic, Greek, extended Latin diacritics, ligatures, and glyph variants a Latin-only English page never renders. Subsetting strips everything outside the actual character set the page needs, which for typefaces with broad Unicode ambitions can be a very large percentage of the file — pure savings with zero visual difference, as long as the subset genuinely covers every character the content actually uses (a real risk: subsetting too aggressively and clipping a character that shows up later, like an em dash or a currency symbol).

What breaks when you preload a font without the crossorigin attribute, and why?

Font resources are always fetched by the CSS engine in anonymous-mode CORS, regardless of whether the request is actually cross-origin — this is a spec quirk specific to fonts, not shared by images or scripts. A <link rel="preload" as="font"> without crossorigin creates a request with different credentials mode than the one the font engine will issue, so the browser treats them as two distinct cache entries rather than coalescing them — the preload fires, appears to succeed, and does nothing to speed up the actual font that gets used, which is a frustrating, silent failure mode with no console warning in most browsers.

When would font-display: optional be the right choice over swap?

When the custom font is a nice-to-have rather than a legibility or brand requirement, and you'd genuinely rather skip it than accept any layout instability or extra network cost on a slow connection — optional gives the browser explicit permission to abandon the font fetch if conditions are poor, keeping the fallback permanently for that page view rather than swapping in late. It's a reasonable default for decorative display type used sparingly, and a poor choice for body text or brand-critical headings where showing the correct font eventually still matters more than avoiding a delayed swap.

Your team ships an icon font. What's the specific risk font-display: swap creates that doesn't apply to text fonts, and what would you recommend instead?

An icon font's fallback glyphs are typically the raw Unicode code points the icon font remaps — meaning a fallback render isn't "text in a slightly different but still readable typeface", it's random, meaningless characters or boxes where icons should be, which is a much worse user-visible failure than ordinary FOUT. I'd recommend aggressive preloading to shrink the exposure window, and lean toward font-display: block (a brief invisible period) over swap for icon fonts specifically, or better, migrate away from icon fonts toward inline SVG icons, which sidesteps this entire class of problem.

How would you decide whether a font should be self-hosted or loaded from a third-party font service?

Self-hosting gives full control over caching headers, preloading, subsetting, and — importantly — removes an extra DNS lookup/connection to a third-party origin that a hosted service (however fast) always adds. Third-party services offer convenience and, for some providers, automatic optimisation (subsetting, format negotiation) without build-pipeline work. For a performance-sensitive production site I'd lean self-hosted with a proper preload and subsetting pipeline, and reserve a hosted service for prototypes or low-stakes projects where the setup cost of self-hosting isn't justified yet.

Can a font ever be the LCP element itself, or does it only ever affect the LCP of something else?

A font is never itself the LCP candidate — LCP measures an image or text-block element, not a resource type — but it very commonly gates when a text LCP candidate can paint: if the text element's font hasn't loaded and font-display is in an invisible (FOIT) state, the browser can't paint that text yet, which directly extends the text element's render timestamp. This is exactly the failure mode described in unit 03's text-hero discussion — a headline that should be LCP-fast because it has no image fetch phase, undone by a blocking font with no display strategy.

10 Memory leaks & long-lived pages

Docs: Chrome DevTools — fix memory problems · MDN — WeakRef · MDN — AbortController

Every unit so far has been about the first few seconds of a page's life. This one is about what happens over the next hour: SPAs, dashboards, and any page a user keeps open across many route changes or long sessions can accumulate memory that JavaScript's garbage collector will never reclaim — not because GC is broken, but because something is still, deliberately or accidentally, holding a reference. A "memory leak" in JS is never really the language leaking; it's the program refusing to let go.

How JS garbage collection actually decides what to keep

V8 (and other engines) use mark-and-sweep, reachability-based collection: starting from a set of roots (global objects, currently-executing call stacks), the collector walks every reference it can find and marks everything reachable; anything unmarked afterward is garbage and gets swept. This means a memory leak is never "the GC failed to run" — it's always "something reachable from a root still points at an object that should have been abandoned." The practical corollary: if you can find the reference chain keeping an object alive, you've found the bug; there is no other kind of leak in JS.

The four patterns that cause almost every real leak

PatternWhy it leaksFix
Forgotten event listenersA listener added to a long-lived target (window, document) closes over a component's scope; the component is "removed" but the listener still references itRemove the listener on teardown; or use AbortController's signal to auto-remove
Detached DOM nodesA node removed from the document tree but still referenced from JS (a cached lookup, a closure) can't be collected — it's "detached" but reachableNull out cached references on teardown; avoid caching nodes longer than needed
Uncancelled timers/intervalsA running setInterval keeps its callback's closure — and everything that closure references — alive indefinitelyclearInterval/clearTimeout on teardown, always paired with the call that started them
Growing caches/closures with no evictionA Map or object used as an ad-hoc cache that only ever grows (e.g., keyed by a stream of unique IDs) accumulates foreverBounded caches (LRU), or WeakMap/WeakRef when the key's lifetime should govern the entry's lifetime
 
// Leaks: the listener closes over `state`, and nothing ever removes it -
// every time this component "unmounts" without cleanup, `state` (and
// anything it references) is kept alive by window's listener list forever.
function mountBad(state) {
  window.addEventListener("resize", () => updateLayout(state));
}

// Fixed: AbortController ties the listener's lifetime to an explicit signal -
// one abort() call removes it, no separate removeEventListener bookkeeping
// to forget.
function mountGood(state) {
  const controller = new AbortController();
  window.addEventListener("resize", () => updateLayout(state), {
    signal: controller.signal,
  });
  return () => controller.abort(); // call this on teardown
}

WeakRef and WeakMap: letting the GC decide, on purpose

A normal Map holds a strong reference to its keys and values — an entry survives as long as the Map does, regardless of whether anything else in the program still cares about that key. A WeakMap holds its keys weakly: if nothing else references a given key object, the entry is eligible for collection even though the Map itself is still alive, which is exactly the right behaviour for "metadata attached to an object for as long as that object exists, and not one moment longer" — a DOM-node-to-associated-data cache is the canonical example. WeakRef generalises the same idea to a single reference rather than a whole collection, for the rarer cases where you need to hold something without that hold itself being the reason it survives.

What changed recently: measuring memory in production, not just in DevTools

Memory profiling used to be almost entirely a local, manual DevTools activity — heap snapshots taken by a developer, on their machine, on a page they suspect is leaking. The Performance.measureUserAgentSpecificMemory() API (and, more broadly, growing production memory-monitoring support in RUM tooling) moved part of this into the field: sites can now sample actual memory usage from real user sessions over time, which is the only way to reliably catch a slow leak that takes an hour of real usage to become noticeable — a length of session no manual DevTools investigation reproduces by default. This mirrors the same pattern seen elsewhere in this guide: a diagnostic that used to require a developer manually reproducing a problem becomes an always-on field signal.

Interview trap

Treating "memory usage went up" as proof of a leak. Memory naturally grows as a session does more — more DOM nodes rendered, more data cached deliberately, more images decoded — and normal garbage collection is lazysawtooth that never returns to baseline — each GC cycle reclaims some memory, but the floor between cycles keeps climbing over time, which is a fundamentally different shape than one big number going up.

Gotcha

Detached DOM nodes are often invisible in a naive read of a heap snapshot because the snapshot correctly shows them as "still referenced" — the mistake is assuming a reference automatically means the reference is intentional. A node removed from document.body is detached from the visible page but can be kept alive indefinitely by something as innocuous as a cached querySelector result stored in a closure that outlives the component. DevTools' heap snapshot comparison view (taking a snapshot, doing an action that should free memory, taking another, and diffing) is the tool that actually surfaces this — a single snapshot alone rarely tells the story.

Try it — 25 minutes, two exercises

1. Grow and diagnose a leak. Build a page with a button that "mounts" and "unmounts" a component; give the mount function an event listener on window that's never removed. Click mount/unmount repeatedly, take heap snapshots before and after several cycles, and use the comparison view to find the growing count of retained objects.

2. Fix it and confirm. Rewrite the same component using AbortController as shown above, repeat the mount/unmount cycle, and confirm the heap snapshot comparison shows no growth this time.

Expected outcome

Exercise 1: the heap snapshot comparison after several mount/unmount cycles shows a growing count of your component's closure/state objects that should have been freed — DevTools' "Objects allocated between snapshots" view will point directly at the retaining event listener when you inspect one object's retainer chain. Exercise 2: the same test on the fixed version shows the retained count stay flat across cycles, confirming the fix actually addressed the root cause rather than just delaying the symptom.

Interview Q&A · memory leaks

What is reachability-based garbage collection, and why does it mean there's technically no such thing as JS "leaking" memory?

The collector starts from a set of roots (globals, active call stacks) and marks every object reachable by following references from there; anything left unmarked is swept as garbage. This means an object is never kept alive by accident from the engine's perspective — it's always kept alive because something reachable from a root genuinely still points to it. What developers call a "memory leak" is really "I intended for nothing to reference this anymore, but something still does" — a logic bug about references, not a flaw in the collector.

Name the four most common real-world causes of JS memory leaks and one fix for each.

Forgotten event listeners on long-lived targets (fix: remove on teardown, ideally via AbortController's signal); detached DOM nodes still referenced from a closure or cache (fix: null out cached references when the node is removed); uncancelled timers/intervals whose callback closures stay alive (fix: always pair setInterval/setTimeout with a matching clear call on teardown); and unbounded caches or maps that only grow (fix: bound them with an eviction policy, or use WeakMap when entries should live only as long as their key does).

What's the actual difference between Map and WeakMap, and when does that difference matter?

Map holds strong references to both its keys and values, so an entry survives exactly as long as the Map itself does, regardless of whether the key object is used anywhere else. WeakMap holds keys weakly, so an entry becomes eligible for collection once nothing else references that key, even while the WeakMap itself remains alive. It matters whenever you're attaching metadata "for the lifetime of some other object" — a DOM node, a component instance — where you specifically want the entry to disappear automatically when that object goes away, rather than requiring you to remember to delete it manually.

How do you distinguish healthy memory growth from an actual leak on a memory graph?

Healthy usage rises with activity and drops meaningfully when garbage collection runs, producing a sawtooth pattern whose floor stays roughly flat over time — GC cycles reclaiming what's actually unreachable. A leak produces the same sawtooth shape superficially, but the floor between GC cycles keeps climbing across many cycles — each collection reclaims some memory but never returns to the previous baseline, because something genuinely unreachable-in-intent is still reachable-in-fact. Looking at one point in time, or even one GC cycle, can't distinguish these; you need the trend across several cycles.

Why can a single mount/unmount cycle look completely clean in a heap snapshot, while a leak is still real?

A single leaked listener or closure might retain only a small, easily-overlooked amount of memory — invisible against the noise of a snapshot's total size. The bug only becomes measurable after many repetitions (many route changes, many modal opens/closes) accumulate the same small leak repeatedly, which is exactly why the standard diagnostic technique is deliberately repeating the suspected action several times and comparing snapshots across repetitions, rather than trusting a single before/after pair.

What does AbortController buy you over manually calling removeEventListener, beyond less code?

It centralises cleanup for potentially many listeners (and, since browsers extended the pattern, other cancelable operations like fetch) behind one abort() call and one signal, removing the failure mode where a component adds several listeners and a maintenance change removes the cleanup code for one of them but not the others. It also composes: the same signal can be passed to multiple addEventListener calls and a fetch request together, so tearing down a component's entire set of external subscriptions is one call rather than a checklist that has to be kept in sync by hand.

Can a memory leak affect INP or other responsiveness metrics, not just eventually crash the tab?

Yes — before a leak gets severe enough to exhaust memory outright, a bloated heap increases garbage collection frequency and duration, and a GC pause is main-thread work like any other; a large, long GC pause running exactly when a user interacts can itself show up as a slow interaction in a LoAF trace or a poor INP measurement. A slow memory leak in a long-lived SPA session is a plausible, if indirect, explanation for INP that degrades the longer a user stays on the page, which is a pattern worth checking specifically in session-duration-segmented RUM data.

Why is production memory monitoring (via an API like measureUserAgentSpecificMemory) valuable when DevTools heap snapshots already exist?

Because many real leaks only become large enough to notice after far longer sessions, and with far more varied user behaviour, than a developer manually reproducing a suspected leak locally typically covers. Field memory monitoring samples real sessions over their actual, often much longer, lifetimes and across the actual diversity of user flows, catching slow leaks that only manifest after usage patterns a manual local test never happens to exercise — the same "lab can't see everything field sees" principle that applies to Core Web Vitals applies here too.

A dashboard app that's kept open all day gets sluggish by the afternoon. Where do you start?

I'd take heap snapshots hours apart during a real long session (or reproduce the timescale by repeating the app's typical actions — polling, route switches, data refreshes — many times locally) and diff them, looking specifically for a category of object whose count keeps climbing rather than plateauing. Given it's a dashboard, polling intervals and live-updating charts are prime suspects: a chart library re-subscribing to data on every update without unsubscribing the previous listener is an extremely common real-world version of this exact bug.

Does removing a DOM node from the page (element.remove()) guarantee its memory is freed?

No — removing a node from the document detaches it from the visible tree, but detachment and reachability are independent; if any JS reference still points to that node (a variable, a closure, an entry in some cache), the node and everything it in turn references remains fully alive in memory despite being invisible and absent from the page. This is precisely why "detached DOM node" appears as its own distinct, commonly-flagged category in heap snapshot tools — it's a specific, recognisable symptom of exactly this mistake, common enough to warrant dedicated tooling support.

11 Measuring: RUM, CrUX, Lighthouse, DevTools

Docs: Chrome — Chrome UX Report (CrUX) · Chrome — Lighthouse · web.dev — field measurement best practices

Every earlier unit assumed you already know a number is bad. This unit is about where that number comes from, and it's the most consequential single distinction in the whole topic: lab data (Lighthouse, a local DevTools trace) is a single, controlled, reproducible run, and field data (CrUX, RUM) is an aggregate of real users' real experiences. They answer different questions — "how does this page perform under these fixed conditions" versus "how do real users actually experience this page" — and a lead engineer's most valuable diagnostic instinct is knowing, immediately, which one a given disagreement is telling the truth about.

RUM: your own field data, not just Google's

CrUX only covers origins with enough real Chrome traffic to be statistically meaningful, and it only reports Google's chosen metric set, at Google's chosen granularity. Real User Monitoring — a script that runs in production and reports actual Core Web Vitals (via the same underlying browser APIs CrUX uses) plus whatever custom metrics matter to your product — gives you the same "real users, real conditions" grounding as CrUX but with your own segmentation (by page template, by user cohort, by A/B test arm, by release version) and without the traffic-volume floor CrUX requires before it'll report anything at all.

// The web-vitals library's underlying approach: PerformanceObserver on the
// standard, browser-native Core Web Vitals entry types - this is roughly
// what any RUM vendor's script does under the hood.
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    sendToAnalytics({
      name: "LCP",
      value: entry.startTime,
      element: entry.element?.tagName, // attribution: which element was it
    });
  }
}).observe({ type: "largest-contentful-paint", buffered: true });

Reading a Lighthouse report like an engineer, not a scorer

The single 0-100 performance score is the least useful number in the report for actually fixing anything — it's a weighted composite that obscures which metric is driving it. The useful parts are underneath: each Core Web Vital's individual value and, for LCP specifically, its sub-part breakdown (unit 03); the "Diagnostics" section's specific, addressable audits (render-blocking resources, unused JS, properly-size-images); and the treemap/waterfall views that show exactly what's on the critical path. Chasing the composite score number directly, rather than the specific metric or audit driving it down, is a common junior mistake that a lead engineer should redirect immediately.

What changed recently: INP proxies and LoAF-driven attribution reaching lab tools

Because INP has no clean lab equivalent (it fundamentally requires real user interactions), lab tooling's answer has been to get better at attributing why a page would likely score poorly rather than trying to fake the metric itself — Total Blocking Time remains the standard proxy, but the Long Animation Frames data (unit 01/04) now feeds richer per-script attribution into Lighthouse's diagnostics and DevTools' Performance panel, letting a lab session point at the specific function likely to cause a poor field INP even without a real user interaction to measure. This is the general trend across this whole unit: lab tooling can't replace field measurement for INP, but it's gotten much better at predicting where a field regression will come from.

Interview trap

Treating a single Lighthouse run as ground truth and shipping a "fix" based on one report, without re-running it several times. Lighthouse's lab results have real run-to-run variance — from CPU throttling variability, from a machine's background load, from network jitter even under simulated throttling — and a single run's LCP can differ from another run on the identical, unchanged code by a meaningful margin. The professional habit is running it several times (or using a tool that automates repeated runs) and looking at the median or range, not a single number, especially before concluding a change helped or hurt.

Gotcha

CrUX data lags real deployments by design — it aggregates a rolling 28-day window, so a fix shipped yesterday won't be visible in the public CrUX dashboard for weeks, and even then it'll be diluted by the weeks of pre-fix data still in the window. Teams that check CrUX the day after a performance fix and conclude "it didn't work" are measuring the wrong tool for that timescale — RUM (your own, with no aggregation lag) is the right tool for "did yesterday's deploy help," and CrUX is the right tool for "what's our actual, settled field standing over the last month."

Try it — 20 minutes, two exercises

1. Compare lab and field for the same page. Run Lighthouse on a real page you have field data for (via PageSpeed Insights, which shows both a lab report and CrUX field data for the same URL side by side, when the URL has enough CrUX traffic). Note any metric where they disagree meaningfully.

2. Run Lighthouse five times. Run it on the same page, same settings, five times in a row, and record the LCP each time. Compute the range.

Expected outcome

Exercise 1: INP-adjacent measures are the most likely to disagree, since the lab side is only ever a TBT-based proxy while the field side is the real metric across real interactions and real device diversity — a wide gap there is normal and expected, not a sign either number is "wrong." Exercise 2: even on an unchanged page, LCP typically varies by a meaningful margin (often tens to a couple hundred milliseconds, more on a busy machine) across five runs, which alone should be reason enough to distrust any single-run comparison.

Interview Q&A · measuring performance

What's the fundamental difference between lab and field performance data, and why can't one replace the other?

Lab data (Lighthouse, a DevTools trace) is a single run under fixed, simulated conditions — reproducible and great for debugging and CI gating, but blind to the diversity of real devices, networks, and user behaviour. Field data (CrUX, RUM) aggregates real users' real experiences — the actual ground truth for ranking and real experience, but with far less attribution detail about *why* a number is what it is. Lab can't replace field because it can't capture real-world variance; field can't replace lab because a single aggregated field number gives you nowhere near enough detail to know what to fix.

Why does CrUX (and Core Web Vitals generally) use the 75th percentile rather than an average?

An average can be dragged down by a small number of catastrophic outliers while hiding a broad, moderate problem affecting many users, or conversely look fine while a meaningful chunk of real visits have a bad experience the mean smooths away. The 75th percentile directly answers "what's the experience for the typical bad-but-not-worst-case visit" — a page only scores "good" if at least three-quarters of real visits genuinely met the threshold, which is a much more honest bar for a metric meant to represent typical user experience, not just average-case performance.

Your Lighthouse report shows a great LCP but your RUM dashboard shows a mediocre one for the same page. What do you trust, and why?

The RUM number, for the purpose of understanding actual user experience — it reflects the real distribution of devices, networks, and conditions your actual users have, which a single simulated lab run structurally cannot capture. I wouldn't discard the Lighthouse number though — I'd use it as a debugging tool to understand the mechanism (which sub-part, which resource) once I trust the RUM number is telling me there's a real problem to chase, likely on a device/network profile the lab's default simulation doesn't represent well (older phones, real mobile networks, real third-party script behaviour).

Why is Total Blocking Time only an approximation of INP, and where does the approximation break down most?

TBT sums the blocking portion of long tasks between First Contentful Paint and a computed "Time to Interactive" point in a single scripted run with zero real user interactions — it's inferring "responsiveness would probably be bad" from main-thread busyness, not measuring an actual interaction's start-to-paint time. It breaks down most for pages whose real interactions happen to land during idle main-thread periods the lab run doesn't reproduce, or conversely pages that look busy in a synthetic run but where real users rarely interact during the busy window — TBT and INP correlate well in aggregate across many sites but can diverge substantially for any one specific page.

What's the risk of chasing a single Lighthouse performance score number as a team's primary KPI?

The composite score is a weighted blend of several metrics with a scoring curve that isn't linear or intuitive, so a team can meaningfully move the underlying metrics that matter (say, reduce actual LCP by 500ms) and see a smaller score change than expected, or vice versa chase score points via changes that help a heavily-weighted metric without improving real user experience much. It also completely obscures run-to-run lab variance behind one clean-looking number, encouraging overconfidence in noise. The healthier KPI set is the individual Core Web Vitals themselves, ideally from field data, not the single blended lab score.

How would you set up a CI performance gate given that lab data has real run-to-run variance?

Run Lighthouse (or an equivalent) multiple times per CI run rather than once, and gate on a median or a percentile across those runs rather than a single value, with a threshold that has some tolerance rather than a hard exact-value regression check — a single-run gate will produce enough false-positive failures from pure noise that teams start ignoring or bypassing it, which defeats the purpose. I'd also keep the CI environment as consistent as possible run-to-run (dedicated runners, consistent throttling profile) to minimize the variance the gate has to tolerate in the first place.

A site has too little traffic to appear in CrUX. What's the alternative for getting field data?

Your own RUM: instrument the page with the standard Core Web Vitals PerformanceObserver entry types (or a library that wraps them) and report to your own analytics endpoint — this gives real field data regardless of traffic volume, without CrUX's minimum-traffic reporting floor, and with the ability to segment by whatever dimensions actually matter to the product (page template, user cohort, release version) that CrUX's origin-level aggregation doesn't offer at all.

Why might a fix deployed yesterday not be visible yet in the public CrUX dashboard?

CrUX reports a rolling 28-day aggregation window by design, intended to smooth out day-to-day noise and represent a stable recent trend rather than reacting to every single deploy — a fix from yesterday is one day's worth of data diluted by 27 days of pre-fix data still inside that window, and won't dominate the aggregate until much more of the window has rolled past the fix date. This is exactly why your own RUM (which you can query without that lag or aggregation window) is the right tool for "did yesterday's change help," while CrUX is the right tool for the settled monthly trend.

What attribution detail does a real-user LCP entry give you, and how do you use it beyond just the timestamp?

The LargestContentfulPaint performance entry includes not just the timing but the actual element reference (when same-origin/available) and its size — enough, when reported through RUM, to answer "which specific element is the LCP candidate for real users on this page," which can differ from what you'd assume from just looking at the page, especially on responsive layouts where the LCP candidate genuinely differs by viewport or A/B variant. Segmenting real LCP data by which element was reported, not just the aggregate timing, is how you catch a carousel or personalization issue (unit 03) that a single manual check might miss.

How do you decide, as a lead, which of lab or field data to trust when a stakeholder asks "did the redesign help performance"?

I'd frame it in two stages: use lab data (a controlled before/after Lighthouse comparison, run several times each) to confirm the redesign's mechanism actually changed what we intended — a genuinely smaller bundle, a genuinely faster LCP path — because that's the reproducible, attributable signal. Then wait for enough real field data (RUM immediately, CrUX once the 28-day window has meaningfully turned over) to confirm real users actually experienced the improvement, because that's the number that answers the stakeholder's real underlying question and the number that affects ranking. Neither stage alone fully answers "did it help."

12 Speculative loading & navigation

Docs: Chrome — Speculation Rules API · MDN — View Transitions API · MDN — @starting-style

Every earlier unit optimised a single navigation. This unit is about the navigation you haven't made yet — predicting it, and making the transition to it feel instant or at least visually continuous rather than a hard cut to blank. It's also the unit with the least cross-browser agreement in this entire guide: both major techniques here are currently Chromium-led, at different points on the path to broader support, and calling that out explicitly is more valuable than pretending otherwise.

Speculation Rules: prerendering a likely-next page before the user clicks

The old tool for this, <link rel="prerender">, was blunt and was deprecated years ago. The Speculation Rules API replaces it with a declarative JSON block naming URL patterns to prefetch or fully prerender, plus the conditions that trigger it — most usefully "eagerness": "moderate" (prerender once the user hovers or touches-down on a matching link, not merely on page load) which balances "start early enough to feel instant" against "don't prerender every link on the page and waste bandwidth/battery on navigations that never happen." A fully prerendered page is rendered completely, off-screen, in advance — activating it on actual click is close to instant, because there's no fetch, parse, or render left to do; the browser just swaps in a page that already exists.

<script type="speculationrules">
{
  "prerender": [{
    "where": { "href_matches": "/articles/*" },
    "eagerness": "moderate"
  }]
}
</script>
<!-- Chromium-first, not Baseline: unsupported browsers simply ignore this
     block entirely - it's a strict progressive enhancement, never a
     required navigation path. -->

View Transitions: making the swap itself feel continuous

Even a genuinely fast navigation can feel abrupt if the old page just disappears and the new one pops in with no visual continuity. The View Transitions API captures a snapshot of the old state, lets the new state render, and cross-fades (or, with more explicit control, morphs specific named elements) between them — same-document transitions (single-page-app route changes) have been supported since Chrome 111/Safari 18 for a while now; the genuinely new capability is cross-document transitions — a full, traditional multi-page navigation with a full server round-trip — which requires opt-in via a @view-transition CSS rule on both the departing and arriving pages. Firefox shipping this in 2026 is what actually makes cross-document view transitions a realistic, cross-browser technique rather than a Chromium-only party trick — previously only same-document (SPA) transitions had that broader reach.

/* Opt a traditional, full-navigation MPA into cross-document transitions -
   both the current page and the destination page need this rule. */
@view-transition {
  navigation: auto;
}

/* Optional: name a specific element so it morphs between pages rather than
   just cross-fading the whole viewport - e.g. a product thumbnail that
   should visually "become" the full image on the next page. */
.product-thumb {
  view-transition-name: product-hero;
}

@starting-style, revisited: the glue for transitions on newly-rendered content

Unit 05 introduced @starting-style for CLS-free entry animations; it's equally relevant here because a page arriving via a prerendered/speculated navigation, or a view transition's incoming state, is exactly the kind of "newly shown" content that needs a defined starting point to animate from — the same CSS feature serves both this unit's navigation-feel concern and unit 05's stability concern, because they're really the same underlying capability (defining a "before" state for something new) applied to different problems.

What changed recently, and the honest caveat

The headline change is Firefox 144 shipping View Transitions in 2026, upgrading cross-document view transitions from a Chromium-only capability to a genuinely cross-browser one — a meaningful moment because cross-document transitions were previously impossible to rely on for any site that needed to support non-Chromium browsers without a completely separate, unstyled fallback experience. Speculation Rules remains Chromium-only and is not Baseline as of this writing; treat every code sample in this unit as progressive enhancement, verify current support before depending on either feature for a critical path, and never assume a specific "supported everywhere" status without checking a current compatibility source — support tables move continuously and this guide's snapshot will age.

Interview trap

Assuming prerendering is "just prefetching, but more." Prefetching (unit 02) downloads a resource; prerendering actually renders the destination page — full DOM construction, style, layout, potentially even running its JS — in a hidden, inactive state. That's a categorically bigger commitment of CPU, memory, and battery per speculative navigation, which is exactly why eagerness controls exist and why "prerender everything" is a much worse default than "prefetch everything" would already be (and even blanket prefetching, unit 02, is a bad default) — over-aggressive prerendering can visibly tax a low-end mobile device for navigations that never happen.

Gotcha

A prerendered page's JavaScript can run before the user ever sees it — including side effects like analytics pageview events, or anything that assumes "this code running means the user is looking at this page right now." A page that fires an analytics event unconditionally on load will double- or falsely-count views for prerendered-but-never-activated navigations unless it specifically checks the Page Lifecycle API's prerendering state (or the equivalent activation event) before firing anything with real-world side effects.

Try it — 20 minutes, two exercises

1. Set up speculation rules and watch it prerender. Add a Speculation Rules block for a set of internal links on a page you control, then in Chrome DevTools' Application panel, look for the "Prerendering" / "Speculative loads" section while hovering a matching link, and confirm a prerender actually starts.

2. Add a cross-document view transition. Add the @view-transition rule to two pages of a small multi-page site, navigate between them, and compare the visual feel to the same navigation with the rule removed.

Expected outcome

Exercise 1: DevTools shows a prerendered document appear (in a supporting browser) shortly after hover, and clicking through activates it near-instantly compared to a cold navigation to a non-speculated link on the same page — a clearly perceptible difference in a side-by-side comparison. Exercise 2: with the rule present, navigating between the two pages cross-fades rather than hard-cutting to blank-then-content; removing the rule restores the default abrupt navigation, making the contribution of this one CSS rule obvious even without any JavaScript involved.

Interview Q&A · speculative loading & navigation

What's the actual difference between prefetching a resource and prerendering a page?

Prefetching downloads bytes for later use — a resource sits in cache, nothing is parsed, rendered, or executed yet. Prerendering constructs the entire destination page in a hidden, inactive rendering context — DOM built, styles applied, layout computed, and its JavaScript potentially already running — so that activating it on actual navigation is close to instantaneous because essentially no work remains. Prerendering is strictly more expensive per speculative navigation, which is exactly why it needs an eagerness/trigger model rather than being applied to every link by default.

Why did get replaced rather than kept?

It offered no way to express confidence or triggering conditions — a page either requested prerendering for a URL or didn't, with no notion of "only when the user seems likely to actually go there" (hover, touch-down) versus "unconditionally, the moment this page loads." That all-or-nothing model made it too easy to waste resources on speculative navigations that mostly didn't happen. The Speculation Rules API's declarative eagerness levels and URL-pattern matching give developers the missing knob to balance "start early enough to feel instant" against "don't prerender everything indiscriminately."

What real user-facing bug can prerendering introduce if a page doesn't account for it?

Any code that assumes "this script executing means a real user is currently viewing this page" can fire prematurely during prerendering — most commonly an analytics pageview event, but also anything with a genuine side effect (starting a session timer, incrementing a view counter). The fix is checking the page's prerendering state (via the Page Lifecycle API) and deferring side-effectful code until the page is actually activated, rather than assuming script execution and user visibility are the same moment — an assumption that was safe before speculative prerendering existed and isn't anymore.

Explain what a cross-document view transition actually requires versus a same-document one.

A same-document transition (SPA route change) happens entirely within one already-loaded page and JS context, so the API can directly orchestrate the old-state-snapshot/new-state-render/cross-fade sequence in script. A cross-document transition spans an actual full navigation — a new document, a new request/response cycle, potentially a different server response — so both the departing and arriving documents must independently opt in via the @view-transition CSS rule; there's no shared JS context to coordinate it imperatively, which is why it's a CSS-level opt-in rather than a script API call.

Why does Firefox shipping View Transitions in 2026 matter more for cross-document than same-document transitions specifically?

Same-document transitions have had reasonably broad support for a while (Chrome and Safari both shipped them within a similar timeframe some years back), so an SPA using them already reached most real users well before this. Cross-document transitions were the genuinely Chromium-exclusive gap — a traditional multi-page site couldn't rely on them for any meaningfully cross-browser audience. Firefox's addition specifically closes that remaining gap, making cross-document view transitions the first point at which a classic server-rendered multi-page site can use this technique as more than a Chromium-only enhancement.

What's the relationship between @starting-style (unit 05) and this unit's navigation techniques?

Both rely on the same underlying CSS capability: defining an explicit "before" state for content that's newly appearing, so a transition has something concrete to animate from. Unit 05 uses it to avoid layout shift when dynamically-inserted content animates in; this unit's relevance is that content arriving via a prerendered activation or a view transition's incoming state is exactly this same category of "new" content — the feature isn't specific to either use case, it's a general building block that both a stability concern and a navigation-feel concern happen to need.

How would you decide which pages on a site are good candidates for Speculation Rules prerendering?

High-confidence next-navigation targets with low prerender cost and low false-positive rate: a paginated list's "next page" link, a search results page's top results, or an article page's clearly-most-likely related link — places where hovering genuinely predicts a click with reasonable reliability, and where the destination page isn't so heavy that a wrong guess wastes significant resources. I'd avoid blanket rules across every link on a page, especially link-dense pages like navigation menus, where hover-to-click conversion is low and the wasted-render cost multiplies across many simultaneously-hovered candidates.

Does prerendering skip the server round-trip entirely, or just hide its cost?

It doesn't skip it — the browser still makes a full request to the server and waits for a full response, exactly as a normal navigation would; what changes is *when* that round-trip happens relative to the user's click. By starting it on hover/touch-down instead of on click, the round-trip's latency is absorbed into the time the user spends deciding to click and moving their finger/cursor, rather than appearing as visible wait time after the click — the network cost is identical, only its visibility to the user changes.

A team wants to add Speculation Rules to a page with many outbound (cross-origin) links. What's different about that case?

Cross-origin prerendering is more restricted than same-origin — browsers apply additional restrictions (and historically required explicit signals from the target origin, since a site doesn't necessarily want to be silently prerendered by another site linking to it) precisely because prerendering executes the target's JS, which is a meaningfully different trust boundary than the target simply agreeing to be fetched. Any team implementing this should specifically check current cross-origin prerendering rules and required opt-in signals rather than assuming the same rules that work for same-origin links apply unchanged.

Why is this unit's "what changed recently" framed with an explicit caveat about checking current support, more so than other units?

Because both of this unit's core techniques are, as of this snapshot, at the leading edge of cross-browser convergence rather than settled Baseline features — Speculation Rules remains Chromium-only with no committed timeline elsewhere, and cross-document View Transitions only just gained a second major engine. That combination — genuinely useful, actively evolving, not yet universal — is exactly the situation where a fact stated confidently today is most likely to be stale soon, so calling out "verify current support before depending on this" here is more load-bearing advice than it would be for, say, CSS `aspect-ratio` (unit 05), which has been stable and universal for years.

13 The big Q&A

Everything that is genuinely important but does not belong to a single building block: architecture calls, production debugging, tooling and process, legacy reality and the judgment questions that decide a lead interview.

Architecture and platform decisions

How do you decide between SSR, SSG and CSR for a new product, from a performance angle specifically?

I start from the content's actual volatility and the audience's actual network conditions, not from framework fashion. Static generation wins whenever content changes at build-time cadence — marketing pages, docs, most blog content — because it gives the best possible TTFB (a CDN edge serving a pre-built file) with nothing left to compute per request. Server rendering earns its cost when content is genuinely per-request (personalised, authenticated, frequently changing) and you still want a fast, complete first paint rather than an empty shell — the cost is server/edge compute and a TTFB that's now doing real work. Client-side rendering is the right default only for genuinely app-like experiences behind a login, where the user has already paid the first-load cost once and every subsequent interaction matters more than any single page's first paint. Most real products are a mix by route, not one answer for the whole app.

Where should a performance budget live — per-route, per-app, or per-component?

Per-route for the metrics that are inherently page-level (LCP, CLS — they describe one navigation), and per-component or per-dependency for the things that compose across routes (bundle size of a shared library, weight of a design-system component). A single app-wide LCP budget hides the fact that your marketing homepage and your data-heavy dashboard have completely different achievable targets and completely different audiences' device/network mix — treating them identically either sets an unreachable bar for the dashboard or a meaninglessly loose one for the homepage. I'd set route-level budgets grounded in each route's actual CrUX segment, and separately track shared-dependency weight in CI so one library upgrade can't silently blow every route's budget at once.

Third-party scripts (analytics, tag managers, chat widgets, ads) are often the single biggest performance cost on a real page. How do you actually govern that?

Treat every third-party script as a cost with an owner and a renewal date, the same way you'd treat a paid vendor contract, because that's functionally what it is. Concretely: load everything non-essential with async/defer or behind a facade that delays the real load until interaction (a chat widget behind a click, a video embed behind a poster image); route tag-manager-injected scripts through a governance process rather than letting any team add one directly, because tag managers are exactly how a single "just one snippet" request turns into a dozen uncontrolled scripts over a year; and put a real budget on total third-party weight and long-task time, measured in CI or synthetic monitoring, so a new addition has to displace an existing one rather than being pure addition. The organisational lever (a review gate) usually matters more than any single technical fix here.

What's the actual performance cost of moving to micro-frontends or module federation, and when is it worth paying?

Composing independently-deployed pieces at runtime almost always costs more bytes and more coordination than one monolithic build would, for the same delivered feature set — shared dependencies risk duplication across remotes unless carefully deduped, and runtime composition adds its own orchestration overhead before any of the actual feature code runs. It's worth paying specifically when the organisational problem it solves (independent teams shipping independently, without a shared release train) is costing you more in velocity than the performance overhead costs users — which is a real trade-off, not a free architectural upgrade, and one a lead should be explicit about rather than adopting the pattern for its own sake. I'd want a shared-dependency strategy and a cross-remote performance budget in place before, not after, the first remote ships.

Do you set separate performance budgets for mobile and desktop, and why or why not?

Yes, and treating them as one budget is a common, easy-to-miss mistake — mobile devices have a wider spread of CPU capability than desktops do (a mid-range Android phone versus a high-end one is a much bigger gap than laptop-to-laptop), and mobile networks have meaningfully worse median latency even where bandwidth looks adequate on paper. CrUX and most RUM tooling already segment by device/connection type, so the data to set realistic, separate targets exists; the mistake is testing and demoing on a fast office wifi connection with a developer machine and generalising that experience to "the app is fast," when the actual median real user, especially on a product with real emerging-market or budget-device traffic, is on a meaningfully slower combination of both.

How much should CDN/edge investment matter compared to application-level optimisation?

It's foundational rather than optional — TTFB is the first term in LCP's sub-part breakdown (unit 03), and every optimisation downstream of a slow TTFB is fighting from behind before a single byte of your actual page has arrived. A good CDN with edge caching, HTTP/3 support, and points of presence near your actual user base is close to a fixed cost you pay once and every page benefits from; application-level work (bundling, images, fonts) is where the marginal, page-specific gains live after that foundation is solid. I'd never accept "our app is well-optimised" as a claim without first checking TTFB across the actual geographic and network distribution of real users, because a great application sitting behind a slow edge still measures badly in the metric that matters.

Debugging and diagnosis in production

A performance regression only reproduces for real users, not on your machine or in CI. Where do you start?

I'd segment the RUM data first, before touching any code — by device tier, connection type, geography, and release version, looking for which segment actually shows the regression rather than assuming it's universal. Developer machines and CI runners are almost always faster and more homogeneous than the real user population, so a regression that's specific to low-end devices, a particular network condition, or a particular browser will simply never appear locally. Once the segment is identified, I'd try to reproduce it directly — CPU/network throttling profiles matching that segment, a real device if one's available — because a reproduction you can see in a trace beats theorising from aggregate numbers alone.

How do you connect a performance metric to a business metric well enough to get resourcing for a fix?

Correlate first, on your own data, rather than citing an industry benchmark as if it transfers directly — the actual conversion-per-100ms relationship is genuinely different across products, and a stakeholder trusts a chart of your own funnel against your own LCP distribution far more than someone else's case study. I'd segment real sessions by their actual LCP (or INP) bucket and look at conversion, bounce, or task-completion rate across those buckets, holding other variables as constant as reasonably possible — the goal isn't lab-grade causal proof, it's a defensible, specific-to-us number that turns "the app feels slow" into "sessions in our slowest quartile convert at X% versus Y% for our fastest," which is the sentence that actually secures a budget.

Users report the app "feels slow" but every metric you're tracking looks fine. What's missing?

Almost always one of two things: you're not measuring the actual interaction users are complaining about (a metric suite covering page load says nothing about a slow in-app search-as-you-type experience, which needs its own custom timing, not just Core Web Vitals), or your dashboard is showing an aggregate that hides the affected segment (a slow experience for 8% of sessions on a specific older device tier can be invisible in a p75 view dominated by everyone else). I'd ask the reporting users directly what specifically feels slow, try to reproduce their exact flow and device/network profile, and check whether a custom RUM measurement exists for that specific interaction at all — the gap is very often "we're measuring the wrong thing," not "the metrics are lying."

How do you tell whether a slow experience is your code's fault versus the network or the browser?

A trace (DevTools Performance panel, or a RUM tool with equivalent attribution) settles this quickly by showing where time actually went: a long stretch of "waiting" before any of your JS runs points at network/TTFB; a long stretch of scripting/main-thread activity with your own function names in the flame chart is your code; a long, unattributed gap during navigation with no network activity and no script running is often the browser doing its own work (parsing a very large stylesheet, for instance) that a shallow read might misattribute. The discipline is resisting the instinct to guess from the symptom alone and instead reading the actual attribution the tooling gives you before proposing a fix — proposing a code fix for a network problem, or vice versa, wastes a cycle either way.

Tooling, process and measurement

How would you evaluate RUM vendors for a team that doesn't have one yet?

Past the obvious (does it measure the real Core Web Vitals via the standard browser APIs, not a proprietary approximation), I'd weigh: segmentation flexibility — can you slice by release version, cohort, and custom dimensions that matter to your product, not just the vendor's defaults; sampling and cost at your actual traffic volume, since 100% capture is rarely necessary or affordable at scale; how attribution is presented — does it point at a specific element or script, or just report a number; and genuinely, how easy it is to correlate with your own business metrics and deployment events, since the value of RUM is largely in the correlations you can draw, not the raw dashboard. I'd run a real trial against a known-good and a known-bad page before committing, rather than trusting a vendor's own case studies.

What does a genuinely effective performance CI gate look like, given lab data's inherent variance (unit 11)?

Multiple runs per gate, not one — gating on a median or a percentile across several repeated runs with a tolerance band, because a single-run threshold generates enough noise-driven false failures that teams start ignoring or disabling the gate, which is worse than not having one. I'd gate on a small set of things that genuinely predict user experience — bundle size deltas for shared chunks, a lab LCP/TBT check on a few representative pages, not an attempt to gate every metric on every route — and make the failure message point at the specific regression (which dependency grew, which resource became render-blocking) rather than just a red X, so a developer can act on it without re-deriving the cause themselves.

When do you need synthetic monitoring in addition to RUM, if RUM already tells you the real user experience?

RUM only reports on traffic that actually happens — it's silent on a page nobody's visited yet (pre-launch), and it can't isolate a single change's effect from all the other noise (varying user mix, varying network conditions) happening simultaneously in the real traffic stream. Synthetic monitoring (scheduled, controlled runs against production, or Lighthouse in CI) fills exactly that gap: a controlled, repeatable signal you can trust for "did this specific deploy regress this specific metric," available before real traffic even arrives. The two are complementary, not substitutes — synthetic for controlled, attributable signal; RUM for the real, aggregate, ground truth.

What belongs on a performance-focused PR review checklist?

Concrete, checkable things rather than vague "did you think about performance": does a new dependency measurably grow a shared bundle (checked against a bundle-size CI report, not eyeballed); does any new image ship without explicit width/height or without going through the existing responsive-image pipeline; does a new above-the-fold element risk becoming an unintended LCP candidate; does a new script tag lack async/defer without a stated reason; does a new event listener or timer have a corresponding teardown. The goal is a checklist specific enough that a reviewer who hasn't read this entire guide can still catch the most common regressions from the list alone.

Legacy reality and organizational friction

You inherit a legacy app with genuinely poor Core Web Vitals and no dedicated time budgeted for performance. Where do you start?

I'd get real field data first (RUM if it exists, CrUX if the traffic qualifies, or a quick Lighthouse pass across the highest-traffic routes if neither exists yet) rather than guessing, because "poor Core Web Vitals" could mean wildly different root causes and a wrong first guess burns credibility fast. Then I'd look specifically for high-leverage, low-risk fixes that don't need dedicated project time — a missing fetchpriority or an accidental loading="lazy" on the LCP element, a render-blocking script that could trivially become defer, an image pipeline gap — because those can often land inside normal feature work rather than requiring a separate initiative. Anything that does need dedicated time, I'd frame with the business-metric correlation from the debugging section above, not just "the numbers are bad," to actually secure the budget for the harder structural fixes.

How do you convince leadership that performance matters when nobody's actively complaining?

Absence of complaints is not absence of cost — a slow experience mostly produces silent abandonment, not a support ticket, so "nobody's complaining" is frequently exactly what a real performance problem looks like from the inside. I'd bring field data (CrUX/RUM) showing where the actual distribution sits relative to the "good" thresholds, and pair it with either an internal correlation (the business-metric approach above) or credible external evidence for the same relationship in a comparable product category — framed as "here's the population of users we can't see because they left before converting," not as an abstract technical quality argument, which is a much harder sell to a non-technical stakeholder.

A big performance push improved the metrics six months ago, and they've quietly regressed since. How do you stop that cycle repeating?

A one-off push without a standing gate is treating a process problem as a project — the regression is entirely predictable, because nothing structurally prevents it from recreating the exact same issues one dependency upgrade or one new feature at a time. The fix is converting the push's findings into permanent CI budgets (bundle size ceilings, a lab LCP/TBT check) and a lightweight recurring review of the field dashboard, not just a one-time cleanup — the goal is that a regression gets caught within a pull request or a release, not rediscovered eighteen months later by a second big push covering the same ground.

Who should actually own performance on a team with no dedicated performance role?

Distributed ownership with one accountable point, in my experience, beats both extremes — a single owner for every regression across every team doesn't scale and becomes a bottleneck and a blame target, while genuinely no owner means the CI gates above never get maintained and slowly rot. I'd want each feature team accountable for their own routes against the shared budgets, with one person (often a senior/lead) owning the shared infrastructure — the CI gates themselves, the RUM dashboard, the cross-cutting third-party governance — the same distributed-with-a-steward pattern that tends to work for other cross-cutting quality concerns like accessibility or security.

Judgment and scenarios

Product wants to ship a heavy third-party embed (a video widget, a chat widget) that will visibly hurt LCP or INP. What do you do?

I wouldn't frame it as a veto — it's a trade-off the business is entitled to make, but an informed one, which is my actual job to ensure. I'd quantify the specific cost (measured, not estimated — add the embed on a branch, measure the actual LCP/INP delta) and present real mitigation options alongside the raw ask: load it behind a facade that only pulls the real widget in on interaction, defer it below the fold, or negotiate a lighter integration with the vendor. If product still wants the heaviest version after seeing the real cost and the cheaper alternatives, that's their call to make with full information — what I'd push back on is shipping it silently, without anyone having seen the actual number first.

You have exactly one sprint dedicated to performance work. How do you decide what to fix first?

Rank by (real-user impact) × (fix confidence) ÷ (effort), not by what's most interesting to fix. I'd start from field data to find the metric and segment actually failing thresholds for real traffic volume — fixing a metric that's already comfortably "good" for the vast majority of sessions wastes the sprint on invisible gains. Within the failing metric, I'd prioritise fixes with a clear, well-understood mechanism (a known LCP sub-part bottleneck, a known unbounded third-party cost) over speculative ones, because a sprint is too short to spend on an uncertain diagnosis. And I'd deliberately leave time to actually verify the fix against field data before declaring victory, rather than assuming a lab improvement transfers.

A stakeholder asks for a direct performance comparison against a specific competitor's site. How do you handle that request well?

Carefully, because a naive comparison (running both sites through the same lab tool once) is genuinely misleading — different pages have different content weight and different legitimate reasons to differ, and a single lab run has real variance (unit 11) that can flip a close comparison either way. I'd run both several times and report a range, be explicit about what's actually comparable (equivalent page types, not homepage-vs-homepage if the content density differs wildly), and where possible pull public CrUX data for both origins as a field cross-check rather than relying purely on a lab snapshot — the goal is giving the stakeholder a genuinely defensible answer, not a flattering one that falls apart under scrutiny.

When is it correct to tell a team "this is fast enough, stop optimizing here"?

When the metric is comfortably within "good" thresholds for the actual real-user distribution across the segments that matter, and further gains would come at a real cost — engineering time better spent elsewhere, or a code-simplicity trade-off that isn't worth it for a metric already meeting the bar. Performance work has diminishing and eventually negative returns like anything else: shaving another 50ms off an LCP that's already at 1.8s field p75 is a much worse use of a sprint than fixing an actual 4-second LCP on a different route, and a lead's job includes saying so explicitly rather than letting perfectionism default to "always more optimisation," which starves genuinely under-served pages of the same attention.

How do you build a lasting performance culture rather than a series of one-off hero projects?

Make the fast path the default path rather than relying on vigilance: a component library whose defaults are already performant (correct image handling, no accidental render-blocking), CI budgets that catch regressions before merge rather than in a retrospective audit, and a visible, shared dashboard so performance is an ambient, always-visible signal rather than something anyone has to go looking for. The hero-project pattern happens precisely when none of that infrastructure exists, so improvement only comes from an individual's occasional focused effort — investing once in the paved road and the gates is what turns "someone cares enough to fix it periodically" into "the system prevents most of the problem by default," which is the only version of this that survives someone leaving the team.

14 Night-before cheat sheet

Sentences to say out loud until they are yours. Each one compresses a unit above; if you can say it and then defend it for two minutes, you are ready.

  1. The rendering pipeline is parse → style → layout → paint → composite, and the main thread is one queue for everything. Layout and paint are expensive and can't be skipped once triggered; transform and opacity are the two properties that can animate on the compositor alone, skipping both. Reading a layout property (offsetHeight) right after writing one forces a synchronous recalculation — layout thrashing — inside a loop this becomes the single most common self-inflicted jank bug.
  2. The critical path is everything that must arrive and run before first paint. CSS is always render-blocking by default; a synchronous <script> in <head> blocks parsing until it downloads and runs, which async and defer both fix differently — defer preserves document order and waits for DOMContentLoaded, async runs the instant it's ready, out of order. preload raises priority for something the parser hasn't discovered yet; preconnect only pays for a connection you're about to use, never speculatively for everywhere you might.
  3. LCP has four sub-parts, and "LCP is slow" is not a diagnosis until you know which one. TTFB, resource load delay, resource load time, and element render delay — a fast TTFB with a slow overall LCP usually means the LCP resource wasn't discoverable early (no preload, hidden behind JS) or something else is blocking the render after it arrived. Good is ≤2.5s at the 75th percentile of real-user data, not a lab average.
  4. INP replaced First Input Delay in March 2024 because FID only measured the wait before processing started, not the whole interaction. INP covers input delay, processing time, and presentation delay end to end, and reports the (near-)worst interaction of the session, not an average. Long Animation Frames (Chrome 123) attribute exactly which script caused a bad interaction; scheduler.yield() is the modern, Chromium-only way to break up a long task without a setTimeout(0) hack. Good is ≤200ms at p75.
  5. CLS is impact fraction × distance fraction, summed per shift, with a 500ms grace window after real user interaction. Images without width/height or aspect-ratio, web fonts swapping in a different size, and late-injected content above existing content are the three real-world causes worth naming by name. @starting-style (Baseline since August 2024) lets a newly-inserted element animate in from a defined starting state without ever being laid out at its final size first. Good is ≤0.1.
  6. Bundling and code-splitting is a trade-off between fewer requests and less unused code, and framework-specific splitting sits on top of this module-graph layer, not instead of it. Dynamic import() is the primitive every framework's lazy-loading builds on; ESM's static structure is what makes real tree-shaking possible, which CommonJS's dynamic require largely defeats. Vite 8 (March 2026) unified dev and build on Rolldown, a Rust bundler, replacing the old esbuild-dev/Rollup-build split with reported 10-30× build speed gains; Vite 8.1 followed in June 2026.
  7. Cache-Control's directives mean specific, different things: no-store forbids caching outright, no-cache means cache-but-always-revalidate, and immutable plus a content-hashed filename is what actually earns a year-long max-age safely. ETags enable 304 revalidation, saving the body transfer but not the round trip. HTTP/2 multiplexing made domain sharding actively counterproductive; HTTP/3's QUIC fixes multiplexing's remaining transport-level head-of-line blocking, which HTTP/2 still has at the TCP layer under packet loss. The back/forward cache is governed by its own eligibility rules, not by Cache-Control.
  8. For images, sizing is almost always the bigger lever than format — 70-90% waste from wrong dimensions dwarfs the 20-50% gain from switching format. srcset/sizes let the browser pick the right resolution for its own viewport and DPR; AVIF and WebP both have broad support today, JPEG XL is stalled (disabled in Chrome and Firefox) and is a lesson in checking real support, not a recommendation. Never lazy-load the LCP image; pair it with fetchpriority="high" instead.
  9. font-display names an unavoidable three-way trade-off between instant, correct, and shift-free — pick two. swap is the sane default for body text (FOUT, never invisible); block can be the right call for a brand-critical wordmark or an icon font whose fallback glyphs are meaningless. size-adjust/ascent-override/descent-override tune a fallback to match the web font's metrics so the eventual swap doesn't shift layout. Preloading a font without crossorigin silently fails to coalesce, because fonts always fetch under anonymous CORS.
  10. JS memory leaks are always a reachability bug, never a GC failure — mark-and-sweep only frees what nothing still points to. The four patterns worth naming: forgotten event listeners, detached DOM nodes still referenced from a closure, uncancelled timers, and unbounded caches; AbortController centralises listener cleanup behind one signal. The actual signature of a leak is a sawtooth whose floor climbs across GC cycles, not a single rising number — a healthy page's memory also rises and falls.
  11. Lab and field data answer different questions and neither replaces the other. Lab (Lighthouse, a trace) is reproducible and good for debugging and CI gates but blind to real device/network diversity; field (CrUX at a 28-day rolling window, your own RUM) is the real experience and what ranking actually uses, scored at p75 specifically because a mean hides or is skewed by outliers. Total Blocking Time is only ever a lab proxy for INP, not the real metric — a single Lighthouse run has real run-to-run variance, so never trust one run alone.
  12. Speculation Rules and cross-document View Transitions are both genuinely useful and both still settling. Speculation Rules prerenders — full render, potentially running JS — a likely-next page before the click, which is why eagerness levels exist and why "prerender everything" is a worse default than even blanket prefetching; a prerendering page's JS can fire before the user ever sees it, so anything with a real side effect must check the Page Lifecycle API's prerendering state first. Firefox 144 shipping View Transitions in 2026 is what made cross-document transitions a real cross-browser technique rather than a Chromium-only one — verify current support before depending on either for anything critical.
  13. A performance culture beats a performance hero. A paved road (sane defaults in the component library, CI budgets that catch a regression before merge, a visible field dashboard) prevents the same class of bug from recurring the way a one-off audit never does; a fix that isn't backed by field data and re-checked against field data after shipping is a guess dressed as a result. Measure the metric that's actually failing for real users, at the percentile that's actually scored, and stop optimising a metric that's already comfortably good — that restraint is as much a sign of seniority as the optimisation itself.
