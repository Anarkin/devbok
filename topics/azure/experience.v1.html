01The 200 ms that lived in the SNAT table

Senior Performance problem diagnosed

(a) Worked example EXAMPLE — replace with your own

A checkout API on App Service Linux, three P2v3 instances, .NET on the isolated worker model. Median latency was 41 ms and had been for a year. The p99 was 9 seconds, and once or twice an hour a burst of requests failed outright with SocketException: Connection timed out reaching an external card processor and, less often, Azure SQL. It looked like the payment provider was flaky, and for two weeks that is what we told everyone, because the failures clustered and the provider had a status page with the occasional yellow dot on it.

What killed that theory was a graph. I plotted failures against traffic and they did not correlate with request rate at all — they correlated with elapsed time since the last scale event. Failures started roughly four minutes after each deployment and then came in waves. That shape is the fingerprint of SNAT port exhaustion, and once you have seen it once you never mistake it again. App Service instances reach the public internet through a shared load balancer that source-network-address-translates outbound flows. Each instance gets a preallocated block of ephemeral ports — 128 by default, more as you scale out — and a closed TCP flow does not return its port immediately; it sits in a timed-wait state for four minutes. So the ceiling is not "connections", it is "new outbound connections per four minutes", and when you cross it the platform does not queue, it drops.

The App Service Diagnostics blade has a SNAT detector that says this in plain English, and I had never opened it. It showed the instances pinned at their allocated port count. The cause was one line of code, repeated in four services: using var client = new HttpClient(...) inside the request handler. Disposing an HttpClient does not close the socket politely and re-creating it per request defeats connection pooling entirely, so every checkout opened a fresh TCP connection to the processor, used it for 60 ms and left a port in TIME_WAIT. At about 40 requests per second per instance that is 9,600 ports every four minutes against an allocation of a few hundred.

The fix had three parts and only one of them was code. First, IHttpClientFactory with a typed client and an explicit PooledConnectionLifetime, so sockets are pooled but still rotate often enough to pick up DNS changes — the classic pair of bugs, socket exhaustion and stale DNS, are the two ends of the same dial. Second, we put Azure SQL and Storage behind private endpoints, because traffic to a private endpoint stays inside the virtual network and never touches the SNAT pool at all; that removed roughly a third of our outbound flows in an afternoon without a code change. Third, for the traffic that genuinely has to leave — the card processor — we enabled regional VNet integration and attached a NAT Gateway to the delegated subnet. A NAT Gateway gives you 64,512 SNAT ports per attached public IP, a deterministic egress address the processor could allowlist, and a much better idle-timeout story. The p99 went from 9 s to 260 ms and the failures stopped.

What I would do differently: I would have opened the diagnostics detector on day one instead of day fourteen, and I would not have let "scale out to five instances" stand as a fix for a week. It did reduce the errors, which is exactly what made it dangerous — it bought more port allocation per instance and hid a bug that would have come back at the next traffic step. I have a rule now: if scaling out fixes a latency problem and CPU was never above 30 percent, you have not fixed anything, you have bought silence.

// Before: a new socket per request. Dispose does not free the port; it enters TIME_WAIT for ~4 minutes.
public async Task<Receipt> ChargeAsync(Payment p) {
    using var http = new HttpClient { BaseAddress = new Uri("https://api.processor.example") };
    return await http.PostAsJsonAsync("/charge", p).Result();   // also blocking on .Result: a second bug
}

// After: pooled connections, bounded lifetime (DNS rotation), one handler for the process.
builder.Services.AddHttpClient<ProcessorClient>(c => c.BaseAddress = new Uri("https://api.processor.example"))
    .ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler {
        PooledConnectionLifetime  = TimeSpan.FromMinutes(2),   // recycle so DNS changes are honoured
        PooledConnectionIdleTimeout = TimeSpan.FromSeconds(90),
        MaxConnectionsPerServer   = 64,
    })
    .AddStandardResilienceHandler();                            // retry + circuit breaker, bounded

(d) Follow-up drill chain

Why did scaling out temporarily make it better?

Because the SNAT port allocation is per instance, so more instances means a larger aggregate pool, and the same request rate spread over more instances means fewer new flows per instance per four-minute window. That is why it is such a treacherous mitigation: the graph goes green, the bug is untouched, and you have coupled your correctness to your instance count. My rule is that a latency fix that only works because of capacity, with CPU and memory flat, is a mitigation with a deadline on it. I will take it to get through the night, and I will say so explicitly in the incident channel so nobody closes the ticket.

If you put everything behind private endpoints, does the problem go away?

For Azure-to-Azure traffic, yes, because those flows never touch the platform SNAT pool. It does nothing for genuine internet egress — third-party APIs, webhooks, package feeds — which is where a NAT Gateway earns its keep. Private endpoints also bring their own costs: an hourly charge plus data processing per endpoint, a private IP in your subnet, and a DNS problem, because the resource's public FQDN must resolve to the private IP through a linked private DNS zone. Get the DNS wrong and you do not get an error, you get traffic silently going out over the public path, which is worse than a failure because nobody notices.

At what scale does the NAT Gateway answer stop working?

One public IP gives 64,512 SNAT ports, and they are consumed per destination endpoint, so the practical ceiling depends on how many distinct destinations you talk to and how short-lived your flows are. Past that you attach a public IP prefix to get several addresses and the gateway spreads flows across them — at which point your third party's allowlist has to accept a range, which is often a commercial conversation rather than a technical one. The other ceiling is architectural: a NAT Gateway is a zonal resource, so a single gateway is a single-zone dependency for your egress, and in a zone-redundant design you need one per zone with subnets aligned to zones. That is the trade I care most about at Staff level, because it turns a performance fix into an availability decision.

What did you trade away by pooling connections aggressively?

Freshness and blast radius. A long-lived pooled connection will happily keep talking to an IP that DNS has moved away from — the classic failure when a partner fails over or a load balancer rotates — which is exactly why PooledConnectionLifetime exists and why I set it to a couple of minutes rather than infinite. Pooling also concentrates failure: if the pool is saturated, requests queue inside the client instead of failing fast, so I pair it with a bounded connection count, a sensible timeout and a circuit breaker. Without those, the failure mode changes from "some requests error" to "every request waits", which is much harder to diagnose and much worse for callers.

How would you stop this happening in the other forty services?

Three passes. A static one: a Roslyn analyser or a simple repository-wide search for new HttpClient outside a factory registration, which is imperfect but ranks the review queue in an hour. A platform one: put internal dependencies behind private endpoints by default in the landing-zone templates so most services never touch the SNAT pool, and make VNet integration plus NAT Gateway the default shape for anything with third-party egress. And a detection one: an alert on the App Service SocketOutboundAll counter and a scheduled query over the SNAT detector across the subscription, so we find the next one from telemetry rather than from a customer.

Would you have designed it differently from the start, knowing the cost?

Mostly, yes, but not by over-engineering: regional VNet integration and private endpoints for stateful Azure dependencies are cheap to adopt on day one and expensive to retrofit, so that is my default now. I would not have put a NAT Gateway in the first sprint of a green-field service — it is real money and a zonal design decision — but I would have written down which egress goes where, because the thing that actually hurt us was that nobody could say, from memory, what talked to the internet. The retrofit was two weeks; the decision it replaced would have taken an hour at design time.

02The partition key we chose a year too early

Staff Hard architectural trade-off

(a) Worked example EXAMPLE — replace with your own

A multi-tenant B2B product on Cosmos DB for NoSQL. One container, partition key /tenantId, chosen in week three by people who were right at the time: every query in the product filtered by tenant, so every read was a single-partition read, and single-partition reads on Cosmos are the fastest thing in the catalogue. Eighteen months later we had 900 tenants, 40,000 RU/s provisioned, and one tenant — an enterprise pilot that had gone extremely well — with more documents than the next two hundred combined.

The symptom was 429 TooManyRequests for that one customer, at 11 a.m. their time, while the account-level RU consumption chart sat at 34 percent. That gap is the whole lesson. Cosmos spreads provisioned throughput evenly across physical partitions. With, say, eight physical partitions and 40,000 RU/s provisioned, each physical partition gets 5,000 RU/s and no more, no matter how idle its neighbours are. A logical partition also cannot exceed 20 GB, and it cannot be split — the storage limit is per logical partition key value. So a single large tenant is a hard ceiling on both throughput and storage that no amount of money removes. The metric that shows this is normalized RU consumption, which is the maximum across partitions, not the average; ours was pinned at 100 percent on one partition for two hours a day.

The genuinely hard part was that the partition key is immutable. You cannot alter it. Changing it means a new container and a migration, and we had a live product on the old one. We put three options in front of the team. Move the whale to its own container or account — cheapest, done in a week, and it makes the tenant list a routing table you now have to maintain forever. A synthetic key such as tenantId_bucket — spreads the whale, but every query has to fan out across buckets, and you have just made the fast path slower for the 899 tenants who were fine. Or hierarchical partition keys, generally available for Cosmos DB for NoSQL, which let you declare up to three levels — /tenantId, then /entityType, then /date — so Cosmos can split a large tenant across physical partitions while a query that supplies only the first level still routes efficiently by prefix.

We chose the hierarchical key and migrated with the change feed: new container, a change-feed processor backfilling history, dual writes for eleven days, a shadow-read comparison job that replayed a sample of production queries against both containers and diffed the results, then a config flip per tenant starting with internal tenants. We also turned on burst capacity, which lets a partition draw on up to five minutes of accumulated idle throughput at up to 3,000 RU/s — that alone removed most of the remaining 429s on the smaller tenants during their morning spikes. The whale went from 429-ing daily to never; the p99 read stayed at 6 ms; and provisioned throughput actually came down to 30,000 RU/s on autoscale because we were no longer over-provisioning the whole account to keep one partition alive.

What I would do differently: I would have asked, in week three, "what happens when one tenant is a hundred times the median?" — not to pick a different key then, because /tenantId genuinely was correct for the traffic we had, but to write down the trigger for revisiting it. We had no trigger, so the review happened when a customer complained instead of when the data distribution changed. I now put a partition-skew alert on any partitioned store on day one: it is one scheduled query and it buys you six months of warning.

(d) Follow-up drill chain

Why not just provision more RU/s?

Because provisioned throughput is divided evenly across physical partitions, so buying more capacity to fix one hot partition means paying for capacity on every other partition that was already idle — and it does nothing at all about the 20 GB logical-partition storage limit, which is the ceiling that eventually stops writes. In our case the account was at 34 percent while one partition was at 100 percent; multiplying spend by three would have taken that partition to a bit more headroom and the bill to three times the size. I would rather pay for a migration once than pay a skew tax monthly forever.

What did hierarchical partition keys cost you?

A container migration and a permanent constraint on query shape: reads that do not supply at least the first level fan out across every physical partition, so the RU charge and the tail latency of those queries get worse, not better. It also makes the second and third levels a decision you cannot walk back, which means the sub-key has to match how the data is actually queried, not how it is conceptually organised. And it is a Cosmos-for-NoSQL feature, so it is one more place where a "we could move to another database" conversation becomes materially harder. I would still take it, but I would not pretend it is free.

At what scale does the whole design break?

Two ceilings. The first is per-partition: about 10,000 RU/s and 50 GB per physical partition, with a logical partition still capped at 20 GB, so a single tenant that needs more than that in one logical key needs to be split in the model — by time, by entity type, by sub-account — regardless of what the partition key says. The second is cross-partition query volume: once your read pattern genuinely needs to scan across tenants for analytics, Cosmos is the wrong engine for that half of the workload and I would move it to the analytical store via mirroring or the change feed rather than making the transactional container serve both. The failure mode of ignoring that is a query that costs 40,000 RUs and takes out the customer-facing path.

How did you get the team to agree, given two people had strong preferences?

I did not run it as a debate, I ran it as a written comparison: the three options, each with the migration cost in engineer-weeks, the effect on p99 for the 899 healthy tenants, the operational surface afterwards, and what would have to be true for that option to be wrong. Once it was on one page the argument stopped being about taste, because the synthetic-key option visibly slowed down every tenant who was not the problem. I also gave the person who preferred separate accounts a real win — we kept their approach as the documented escape hatch for any future tenant above a threshold, because they were right that some customers eventually need physical isolation for reasons that are commercial rather than technical.

What would you do differently now?

Set the revisit trigger at design time and alert on it: a scheduled query on the per-partition metrics that fires when the largest logical partition exceeds, say, ten times the median or half the storage limit. That is a two-hour job that would have given us six months of notice. I would also model the first tenant migration as a product feature rather than an incident response — per-tenant relocation is a capability a multi-tenant system needs anyway, for compliance, residency and enterprise deals — so building it under pressure was the expensive part, not the partition key itself.

03One zone went away and we found out we were zonal

Staff Production incident / outage

(a) Worked example EXAMPLE — replace with your own

07:52 on a Tuesday. Error rate went from 0.02 percent to 31 percent and stayed there. Not 100 percent — 31 — which is the number that tells you it is not a deploy and not a dependency, it is a slice of your capacity. Azure Service Health showed an availability-zone-level event in our region affecting a subset of compute and storage. We had designed for this. We had, in the architecture document, the phrase "zone redundant". What we actually had was a system in which four things were quietly zonal, and I had signed off on every one of them.

The four: an AKS node pool created before we knew better, with all its nodes in zone 1; the NAT Gateway from story 01, which is a zonal resource and had been created with --zone 1 by someone copying our own runbook; a Premium SSD managed disk attached to a stateful workload, pinned to the zone it was created in because a zonal disk cannot be attached from another zone; and a Standard public IP created as zonal rather than zone-redundant. Everything else — the Standard Load Balancer, Front Door, Azure SQL with zone redundancy enabled, ZRS storage — behaved perfectly. That is the thing worth internalising: zone redundancy is per resource, not per region and not per subscription, and a design is only as zone-redundant as its least redundant hop.

I took incident command, which mostly meant refusing to let six people debug in parallel. We mitigated before we diagnosed: cordoned and drained the zone-1 node pool, scaled the zone-2 and zone-3 pools out to absorb it, and pointed egress at a second NAT Gateway that existed in zone 2 because a colleague had built it for a migration and never removed it. Pure luck, and I said so in the postmortem, because luck that is not labelled as luck becomes a design assumption. Error rate was back under 1 percent at 08:41. The stateful workload with the zonal disk stayed down until the zone recovered at about 14:00; we made a deliberate decision not to restore it from snapshot into another zone, because the restore would have taken longer than the estimated recovery and would have forked our data. Writing down that reasoning at 09:15, while it was still a live decision, was the single most useful thing I did all day — it is what made the postmortem a discussion rather than an argument.

The remediation was not "make everything zone-redundant". It was a policy and an inventory. We wrote an Azure Resource Graph query that lists every resource in the estate with its zones property and flags the zonal ones, ran it as a weekly report, and added an Azure Policy in deny mode for new public IPs and NAT Gateways that are zonal in production subscriptions. For the stateful workload we moved from a zonal Premium SSD to ZRS-backed disks, which cost more per GB and have slightly different performance characteristics — a trade we made explicitly and wrote down. Time to detect went from 6 minutes to 40 seconds after we added a per-zone error-rate dimension to the dashboard, which sounds trivial and was the most valuable change of all: 31 percent means nothing until you can see it is 100 percent of one third.

What I would do differently: I would have run a game day. We had never once tested the assumption. Azure Chaos Studio has a zone-down experiment that would have found three of those four resources in an afternoon, and the fourth — the copied runbook — would have been found by reading the runbook, which is free.

(d) Follow-up drill chain

Why not fail over to the paired region?

Because the blast radius was one zone, and a regional failover would have converted a partial, self-healing outage into a full data-plane migration with a real risk of data divergence and a failback problem afterwards. Regional failover is the right answer when the failure is regional, when your RPO tolerance is met by the replication you actually have, and when you have rehearsed it — for us the database was zone-redundant, so the surviving zones already had the data. My rule is that failover is a decision about which risk you prefer, so I want two numbers before I make it: estimated time to recovery in place, and rehearsed time to recover elsewhere. If I do not have the second number, I do not have a DR plan, I have a diagram.

What does zone redundancy actually cost, and when is it not worth it?

It is roughly a price premium on the storage and the compute you make redundant — ZRS disks and storage cost more per GB than LRS, zone-redundant SQL and App Service plans carry an uplift, and you generally need a minimum instance count, so the smallest deployments pay proportionally the most. It also costs a little latency for synchronous cross-zone writes, which matters for chatty stateful workloads. It is not worth it for genuinely stateless batch work that can simply be re-run, for non-production, or for a system whose availability target is met without it — I would rather spend that money on the one dependency whose loss actually breaks the product. What I will not accept is accidental zonality, which is what we had: the cost was paid in an outage rather than in an invoice.

At what scale does the "spread pods across zones" answer stop being enough?

When state enters the picture. Node spread is easy — availabilityZones on the pool plus topology spread constraints on the workload — but a persistent volume backed by a zonal disk anchors its pod to a zone, so a StatefulSet that survives a zone loss needs ZRS-backed volumes or replication at the application layer, and the scheduler needs to know. It also breaks when your capacity assumption is wrong: if losing a zone means the remaining two must absorb 50 percent more load, you need either 50 percent headroom or an autoscaler fast enough to get it, and in a zone incident the region is often capacity-constrained for exactly the SKU you want. That is the connection to story 18 — availability plans that assume capacity is always purchasable fail on the day everyone else is failing over too.

How did you stop this recurring across teams you do not manage?

By making it structural rather than social. The Resource Graph inventory runs weekly and lands in a channel with names attached, so it is a conversation rather than a scolding. Azure Policy in deny mode on production subscriptions stops new zonal public IPs and NAT Gateways being created at all, with an exemption process that requires an owner and a review date. And the landing-zone Bicep modules — the ones most teams copy — got the zone-redundant defaults, because the highest-leverage place to fix a copy-paste failure is the thing being copied. Policy without a paved road is a tax; a paved road without policy drifts.

What would you have caught in a game day, specifically?

Three of the four resources, directly: an Azure Chaos Studio zone-down experiment on a pre-production environment that mirrors production would have shown egress failing when zone 1 went away, and the stateful pod failing to reschedule. The fourth — a zonal resource created by copying our own runbook — is a documentation defect, and the honest fix is that runbooks that contain --zone 1 should not exist. I would run it quarterly, in business hours, with a stated abort condition, and I would count "we learned nothing" as a passing result rather than a wasted day.

04Sixty services, no more connection strings

Staff Migration / platform upgrade

(a) Worked example EXAMPLE — replace with your own

We had roughly sixty deployable units across four environments, and every one of them authenticated to Azure SQL, Storage, Service Bus and Key Vault with a secret. The secrets were in Key Vault, which everybody treated as the finish line, and they were not: a Key Vault full of storage account keys is a single place from which every one of those keys can be read, and none of them had ever been rotated, because rotating a storage key means finding every consumer first. The trigger was an audit finding, but the honest trigger was that a contractor had left three months earlier and nobody could say with confidence which secrets they had seen.

The target state was no secrets at all in the application path: managed identity for every Azure-to-Azure call, Entra ID tokens instead of keys, and RBAC as the authorisation model. The mechanism is simple to state and full of sharp edges. A system-assigned managed identity is created with the resource and dies with it, so it is perfect for a single app and useless for anything that needs the identity to exist before the compute does. A user-assigned managed identity is a resource in its own right, so you can grant it roles at deployment time, share it across a scale set or a set of Container Apps, and — importantly for us — keep the grant when the app is recreated. We standardised on user-assigned for anything in production, one identity per service, named after the service.

Then the per-service work. Storage was the easiest and the most satisfying: assign Storage Blob Data Contributor at the container scope, switch the SDK from a connection string to new BlobServiceClient(uri, credential), and finally set allowSharedKeyAccess: false on the account, which is the step that actually makes the migration real — until you flip that flag, the keys still work and someone is still using them. Service Bus was the same shape with Azure Service Bus Data Sender and Receiver. Key Vault we moved from access policies to the RBAC permission model, which is the modern default and lets one mental model cover the whole estate rather than two.

Azure SQL was the hard one, because there is no portal button that grants an application access to a database. The grant lives inside the database: you connect as an Entra administrator and run CREATE USER [name] FROM EXTERNAL PROVIDER, then add role memberships — which means database DDL in your deployment pipeline, per environment, for sixty services. We got that wrong first: sixty principals meant sixty scripts and a permanent maintenance burden. The fix was to create Entra security groups per role (sql-orders-reader, sql-orders-writer), grant the group in the database once, and put managed identities into groups — so onboarding a new service became a group membership, not a schema change. Group membership takes a few minutes to propagate into a token, which is a genuine operational property you have to explain to people, because "I granted it and it still says login failed" is the number one support ticket of this migration.

We ran it as a strangler, not a big bang. Every service got a dual-auth window: the code took the token path if a feature flag was on and fell back to the connection string if it failed, with a metric on which path was used. When a service had run at 100 percent token path for a week, we deleted its secret and, once every consumer of an account was clean, disabled shared-key access on the resource. Eleven weeks, sixty services, four rollbacks — three of them the same cause, which was a user-assigned identity not yet propagated to a freshly created Container App revision. The measurable result: 140 secrets deleted, key rotation for the surviving four reduced from a two-day coordination exercise to an automated job, and the audit finding closed. The unmeasurable one is better: the question "who can read this data?" became a query against role assignments rather than an archaeology project.

(d) Follow-up drill chain

How did developers work locally once the secrets were gone?

Their own Entra identity, granted the same data-plane roles in the development subscription only, resolved through the CLI credential — so the code path is identical and the difference is which principal the token belongs to. That gives you real RBAC in development, which catches missing role assignments before production instead of after. The two costs are honest ones: developers need role assignments of their own, which is a small ongoing administrative load best handled with a group, and a broken local sign-in now looks like an application bug, so the error message has to name the credential type it tried. I would not solve it with a shared development service principal, because that is a secret again, and it is the one everyone commits.

You granted at container scope for Storage. Why not resource group?

Because scope is the only knob that limits blast radius, and a role assignment at resource-group scope gives that identity the same data access to every account in the group, including ones created later by someone else. Container scope means a compromised service reaches exactly the data it was designed to reach. The cost is more role assignments to manage — and there is a real ceiling on assignments per subscription — which is why the rule I actually enforce is: narrow scope for data-plane roles, groups for anything that would otherwise be repeated per service, and never a subscription-scoped data role in production. When the assignment count gets uncomfortable, the answer is fewer, better-shaped resources, not wider grants.

At what scale does per-service managed identity stop being practical?

It strains in two places. First, role assignments are capped per subscription in the low thousands, and a large estate with narrow scopes burns through them faster than people expect — the mitigation is group-based assignment and, at real scale, Azure ABAC conditions so one assignment covers a pattern of blobs rather than one container each. Second, token acquisition itself: every process now fetches and caches tokens, and a badly configured client that requests a token per call will find the throttling limits of the identity endpoint at high concurrency, which shows up as intermittent 429s that look like the downstream service failing. The SDK credentials cache and refresh for you, so the fix is nearly always "stop constructing a new credential per request" — the same class of bug as story 01, in a different costume.

What did you trade away?

Debuggability and portability. A connection string is a self-contained artefact you can paste into a tool and test in ten seconds; a token flow depends on the identity being attached, the role having propagated, the resource accepting Entra auth and the network path allowing it, so a failure has four candidate causes instead of one. We paid that down with a startup self-check that resolves a token and performs one trivial data-plane call, logging exactly which step failed. The portability cost is real too: the code now assumes Azure's identity model, so a hypothetical move elsewhere is more work. I judged that acceptable because we were already deep in Azure-specific services, but I would not pretend it is neutral.

How do you prove the old keys are no longer used before deleting them?

Storage diagnostic logs record the authentication type per request, so a KQL query over StorageBlobLogs grouped by AuthenticationType tells you whether anything still authenticates with a shared key, and over what window. I want two clean weeks including a month-end, because the thing that breaks is always the monthly job nobody owns. Then I disable shared-key access rather than deleting the key first — it is instantly reversible, so if something does break the recovery is one property flip and not a rotation. Only after that does the key rotation itself become routine.

05"We should just run Kubernetes"

Senior Technical disagreement with a colleague

(a) Worked example EXAMPLE — replace with your own

Nine services, one team of six, everything on App Service and one Function App. A strong senior engineer proposed moving the lot onto AKS. His arguments were not bad ones: he wanted per-service resource limits, a consistent deployment model, sidecars for the OpenTelemetry collector, and — the real driver, which took a while to surface — he wanted the team to have skills that were portable outside this company. I disagreed, and the disagreement mattered because he was the person who would have built it and he was not wrong about the problems, only about the remedy.

What I did first was stop arguing about Kubernetes and write down what we were actually trying to buy. Five things: isolation between services, a uniform deploy, scale-to-zero for the six services that get almost no traffic, sidecars, and a skills story. Then we scored the options against those five rather than against taste. Azure Container Apps gives you all of the first four — it is a managed environment built on AKS that you do not administer, with KEDA-based scaling including genuine scale to zero, Envoy ingress with revisions and traffic splitting, sidecar containers in a pod-like unit, and Dapr if you want it. AKS gives you all five plus everything else, and in exchange you own the cluster: version upgrades on Kubernetes' release cadence, node images, the ingress controller, the CNI decision, the cost of a platform on-call. App Service was already fine for the three services with steady traffic, and Premium v4 had just landed with meaningfully faster hardware.

The number that ended the discussion was not a benchmark, it was a rota. AKS supports roughly the three most recent minor versions, and Kubernetes ships three minors a year, so a cluster you do not upgrade goes unsupported inside a year and Azure will eventually upgrade it for you. That is a recurring commitment: read the release notes, test the API deprecations, drain and roll the node pools, and own the consequences when a controller you installed is not compatible. We estimated a day a month at best, plus the incidents. On a team of six shipping a product roadmap, a day a month is four percent of the engineering capacity, permanently, to buy things Container Apps already gave us. And the ingress question made it concrete rather than theoretical: upstream Ingress NGINX ended maintenance in March 2026, Microsoft is patching critical CVEs for the AKS app routing add-on only through November 2026, and AKS 1.36 now defaults new Automatic clusters to the Gateway API instead. That is exactly the kind of migration a six-person product team absorbs badly and a managed platform absorbs for you.

So the decision was: keep App Service for the steady three, move the six spiky ones to Container Apps, keep the Function App on Flex Consumption, and write down the conditions under which we would revisit AKS — a real need for DaemonSets or node-level access, a workload needing GPUs or specific node SKUs, a second team sharing the platform, or Container Apps blocking us on something we could name in advance. I asked him to own the Container Apps migration and to write the revisit criteria, which mattered: he was not overruled, he was given the decision to revisit with evidence. Six months later two of the criteria had been hit for a machine-learning workload, and we ran that one workload on AKS — deliberately, in isolation, with him leading it, which was a much better outcome than either of our original positions.

It was a legitimate motivation and it was invisible in the technical debate, so we spent a week arguing about sidecars when the real question was how someone grows. 06The job that wrote to the wrong subscription

Mid Nasty debugging session

(a) Worked example EXAMPLE — replace with your own

A nightly reconciliation job wrote a summary file to blob storage. One morning the file was missing from the production container, and a colleague on another team asked, in a completely unrelated channel, why a file named reconciliation-2026-08-14.json had appeared in their storage account. Same file name. Different subscription. Different Entra tenant boundary in our organisation's layout. That is the kind of bug that makes your stomach drop, because for about twenty minutes the only explanation anyone could offer was "something is very wrong with Azure".

Nothing was wrong with Azure. The job used DefaultAzureCredential, which is a chain: it tries a sequence of credential types in order — environment variables, workload identity, managed identity, developer tooling such as Visual Studio, the Azure CLI, Azure PowerShell and the Azure Developer CLI — and uses the first one that produces a token. On the production container the chain resolved to the managed identity, correctly, every night for a year. That week we had moved the job temporarily onto a self-hosted build agent while a network change was in flight, and that agent had a logged-in Azure CLI session belonging to a human who happened to have Contributor on a different subscription. The chain skipped past managed identity — there was none on that VM — and landed on AzureCliCredential. The storage account name came from configuration that had been templated with a default, and the default resolved to a name that existed in the other subscription. Two ordinary mistakes multiplied.

What made it findable was the storage diagnostic logs. Every data-plane operation on a storage account is logged with the caller's object id, the authentication type and the source address. One KQL query against the receiving account showed a write authenticated with an Entra token belonging to a user principal, from an IP in our build subnet, at 02:14. From there it was five minutes: match the object id to the person, ask what ran on that agent, read the credential chain in the SDK documentation, and the whole thing collapses into an obvious story. The lesson I actually took is not about credentials at all — it is that I had spent twenty minutes theorising before I looked at an audit log that answers "who did this" definitively. Now that is my first move, always.

The fixes were small and there were three. First, pin the credential in anything non-interactive: ManagedIdentityCredential with an explicit client id in production, or DefaultAzureCredential with the developer credentials explicitly excluded, so a job can never silently fall back to a human's identity. Second, make the destination explicit and fail closed — the job now asserts at startup that the resolved storage account and subscription match the expected values and exits non-zero if not, which is four lines of code and would have prevented the whole incident. Third, remove standing Contributor from human accounts on production-adjacent subscriptions and put them behind Privileged Identity Management, so that even a stray CLI session has read-only rights until someone deliberately elevates.

What I would do differently: look at the audit log first, and treat "it works on the build agent" as an unanswered question rather than a relief. Any credential system whose behaviour depends on the ambient environment will eventually resolve to something you did not intend, and the correct defence is to be explicit rather than to be careful.

(d) Follow-up drill chain

Why is DefaultAzureCredential fine for local development and risky in production?

Because its entire value is that it adapts to its environment, and adaptation is exactly what you do not want in a non-interactive job. Locally it means one code path works for everyone regardless of whether they use the CLI, Visual Studio or azd. In production it means the credential your process gets depends on what happens to be installed and logged in on the host, so a change in hosting — a build agent, a container base image, a debugging session left open — silently changes who you are. It also makes startup slower and failures vaguer, because a failure is the aggregate of seven attempts. My rule: DefaultAzureCredential behind a development flag, an explicit credential type everywhere else.

The write succeeded. Whose authorisation failure is that?

Ours, structurally. A human with standing Contributor on a subscription is a role assignment nobody reviews, and the incident is the proof that it was too broad — the CLI session was the trigger, not the cause. The durable fixes are just-in-time elevation through Privileged Identity Management so standing access is read-only, access reviews so assignments expire rather than accumulate, and narrow data-plane roles so even an elevated human does not automatically get write access to application data. I would not frame it as the colleague's mistake in a postmortem, both because it is not true and because that framing is how you stop hearing about incidents.

What if the file had contained personal data?

Then it stops being an engineering incident and becomes a disclosure decision that is not mine to make alone, and the clock starts immediately. Practically: preserve the evidence before deleting anything, because the diagnostic logs are the only proof of scope and they have a retention window; establish who could have read it in the interval using the read operations in those same logs, not by reasoning about permissions; and escalate to whoever owns data protection the same day with the facts you have, including what you cannot determine. The engineering instinct is to delete the file and fix the bug, and doing that first destroys the evidence you will be asked for.

At what scale does the startup assertion approach stop working?

It works fine as a per-service guard, but it is opt-in code, so at estate scale you are relying on sixty teams remembering. The platform-level version is to make the wrong thing impossible: separate subscriptions per environment with no cross-subscription role assignments, network isolation so a production data plane is not reachable from a build subnet at all, deny policies on resource creation outside the expected pattern, and deployment identities that are scoped to exactly one environment. The assertion is the cheap fix you ship on the day; the isolation is the fix that scales. If I could only have one, I would take the isolation, but the assertion is the one you can ship before lunch.

07From 12 nodes to 400 for a launch weekend

Staff Scaling challenge

(a) Worked example EXAMPLE — replace with your own

A consumer-facing launch with a televised advert at a known time on a Saturday. Marketing's forecast was 40x our normal peak for about ninety minutes. Normal peak was twelve nodes on AKS. The interesting problem was not "can the application handle it" — we load-tested that — it was that every layer scales at a different speed, and the slowest one is the one that defines your outage.

We measured each layer's time-to-capacity rather than guessing. Horizontal Pod Autoscaler reaction: about 30 seconds to decide, then bounded by pod start time. Pod start time: 95 seconds, almost all of it pulling a 1.2 GB image onto a node that did not have it. Cluster autoscaler: it will not even ask for a node until pods are unschedulable, then VM provisioning plus node registration plus image pull is three to five minutes. Azure SQL scaling: a service-tier change is minutes and involves a brief failover. And the one that nearly ended us: subscription quota. Regional vCPU quota is per VM family, and we had 350 vCPUs of a family we were about to need 1,600 of. A quota increase is a request, not an API call you can rely on at 21:00 on a Saturday.

The plan had five parts. Quota first, three weeks ahead, in writing, for two VM families in two zones so that a shortage of one SKU did not stop us — that request took nine days to be fully approved, which is the single most useful fact in this story. Second, we shrank the container image from 1.2 GB to 210 MB with a proper multi-stage build and a chiselled runtime base, taking pod start from 95 s to 22 s; nothing else we did bought as much for as little. Third, we pre-scaled: the cluster autoscaler is reactive by design, so for a known event we scheduled the node pools to a floor of 260 nodes an hour before and set the HPA minimum high, accepting several hundred pounds of idle compute as insurance. Fourth, we made a spot node pool carry the elastic tail with a taint and a toleration only on the stateless workers, so an eviction storm could cost us throughput but never correctness. Fifth, we ran a genuine dress rehearsal with Azure Load Testing against production on the previous Tuesday at 03:00, at 100 percent of the forecast, and it failed — Front Door was fine, the app was fine, and Azure SQL hit its worker-thread ceiling because a per-request connection pattern in one service opened four times as many connections as we expected.

That rehearsal is the reason the launch worked. We fixed the connection pattern, moved read traffic to a read replica, and on the night peaked at 396 nodes with a p99 of 480 ms and a 0.3 percent error rate, almost all of it in the first ninety seconds while the last pods came up. What I would do differently: I would use Node Auto Provisioning today. I would still pre-scale for a known event, because no autoscaler beats knowing the time the advert airs, and I would still shrink the image, because pod start time is the multiplier on everything else.

(d) Follow-up drill chain

Why pre-scale instead of trusting the autoscaler?

Because autoscalers are reactive by construction: the cluster autoscaler does not request a node until pods are already unschedulable, so the first users of a spike pay for the provisioning latency with errors. When the arrival time is known — an advert, a sale, a market open — that latency is pure downside and buying capacity in advance is cheap insurance. When arrival is unpredictable, reactive scaling plus a sensible floor is right, and the lever that matters is reducing time-to-capacity rather than reacting sooner. The mistake I see most often is treating the autoscaler as an availability control rather than a cost control; it is fundamentally a cost control that happens to add capacity.

Spot instances in a launch-critical path. Defend that.

They were not in the critical path — they were the tail. Spot nodes carried stateless workers behind a queue, tainted so nothing else could land there, with the on-demand pool sized to handle the full sustained load on its own; spot was there to absorb the peak more cheaply and to give the autoscaler somewhere to go if the on-demand family ran short. The failure mode is eviction with 30 seconds of notice, which for a queue consumer costs you an in-flight message that gets redelivered, and nothing more, provided the consumer is idempotent. I would never put a stateful workload, an ingress controller or anything with a long start-up on spot, and I would not use spot at all if the workload could not tolerate losing a third of its capacity in a minute.

At what scale does this whole approach break?

At the point where the region itself is the constraint rather than your subscription. Quota is a subscription-level allowance against regional capacity that is genuinely finite, so at large enough scale you are not asking for a limit increase, you are asking whether the capacity exists — which is why the answer at that tier is multi-family SKU flexibility, reservations or capacity reservations for the base load, and being multi-region for the peak rather than multiplying one region. It also breaks when scale-up stops being linear: at several hundred nodes you start to hit control-plane and networking limits, per-node pod density limits, IP address exhaustion in the subnet if you are using a non-overlay CNI, and the cluster autoscaler's own decision latency grows. That is where I would split into multiple clusters rather than one very large one.

What did the insurance cost, and would you buy it again?

Roughly four thousand pounds of idle compute for six hours, plus about three engineer-weeks of preparation. Against a televised advertising spend two orders of magnitude larger, that is not a close call, and I would say so to a CFO in exactly those terms. What I would push back on is buying the same insurance every week out of habit: after the launch we deliberately let the floor fall back and let the autoscaler do its job, because permanent pre-scaling is how a one-off insurance premium turns into a permanent line item nobody re-examines. The discipline is to attach an expiry date to the temporary capacity when you create it.

How would you shorten pod start time further?

Beyond image size, the levers are registry-side and node-side. Artifact streaming on a premium Azure Container Registry lets a node start a container before the whole image is local, which helps most for large images; geo-replicating the registry into the same region as the cluster removes a cross-region pull; and pre-pulling the image onto nodes as part of the pool's bootstrap means a scale-out node is warm on arrival. On the application side, readiness probes with sensible initial delays stop traffic arriving before warm-up finishes, and trimming start-up work — lazy connections, no synchronous configuration fetches, ReadyToRun or native AOT for .NET — turns 22 seconds into single digits. The order matters: image size first, because it improves every other number.

(a) Worked example EXAMPLE — replace with your own

I found it in a pull request review, which is the least dramatic way to find a security problem and by far the cheapest. Someone was adding a container to an existing storage account and the Bicep diff showed publicNetworkAccess: 'Enabled' — not new, just newly visible. That account held exported customer reports. I checked the deployment history: the property had flipped eleven days earlier, in a change whose commit message was "fix pipeline". A build agent had lost network line-of-sight after a subnet change, and the fastest way to make the pipeline green had been to open the account to the internet.

Two things saved us, and it is worth being precise about which is which. Anonymous blob access was disabled at the account level (allowBlobPublicAccess: false), so nothing was readable without credentials — that is a genuine control. The account also had a hard-to-guess name, which is not a control at all, and I said so out loud in the review, because in the two hours that followed at least two people offered it as reassurance. Open to the internet with authentication required is a real exposure: it means every account key and every SAS token ever issued is now usable from anywhere, and shared-key access was still enabled on that account.

So the first job was not to fix it, it was to size it. Storage diagnostic logs give you every data-plane request with the source IP, the authentication type and the status code. That query took fifteen minutes and changed the conversation completely — "we were exposed and nothing touched it" is a very different meeting from "we were exposed". The fix had three layers. Immediately: publicNetworkAccess: 'Disabled', a private endpoint for the build agents, and the pipeline's actual network problem solved properly. Microsoft Defender for Cloud already had this as a recommendation and nobody read recommendations; a deny policy is read by the deployment, at deployment time, by a machine.

I would also stop accepting "fix pipeline" as a commit message on infrastructure, which sounds petty and is actually the root cause: the change was invisible because it was described as maintenance.

Why is a hard-to-guess resource name not a control?

Because storage endpoints are enumerable in ways that do not depend on guessing: certificate transparency logs, DNS, code and configuration in repositories, error messages, SDK telemetry, and the simple fact that names appear in URLs shared by humans. It is also a control that degrades silently — you never find out it has failed until it has. I treat obscurity as a rate limiter on opportunistic scanning and nothing more, and I am careful to say that in the room, because the moment a team accepts obscurity as security, it starts making other decisions on the same basis.

At what scale does the deny-policy approach start to hurt?

When exemptions outnumber compliance. Deny policies work beautifully for a small set of high-value invariants and become an obstruction when someone tries to encode fifty of them, at which point teams route around governance by asking for subscription-level exemptions that never expire. My rule is a handful of denies for boundary properties that would be catastrophic — public network access, anonymous blob access, disabled soft delete, public IPs on production databases — with everything else in audit mode feeding a report. Policy assignment also has real costs at scale: evaluation latency on large deployments, remediation tasks that need managed identities, and the fact that a deny arriving after resources exist is a migration project, not a switch.

What did you trade away by disabling public network access?

Convenience, and a real amount of it. Every tool that used to reach the account from a laptop — Storage Explorer, a support script, a data-science notebook, a partner's upload job — now needs a network path, which in practice means private endpoints plus DNS plus, for humans, a VPN or a jump host. That is genuinely worse for the people doing legitimate work, and if you do not plan for it they will invent workarounds you like less, such as copying data out to somewhere reachable. So the honest version is that we spent about a week building the paved paths — a private-endpoint-enabled bastion for support, a documented process for partner uploads via a SAS with a short expiry — and the control only held because those existed.

How would you catch the next boundary change before eleven days pass?

Three layers, none of which is a person reading recommendations. Prevention: the deny policy, so the change cannot happen in production at all. Detection: an Activity-log alert on writes to the specific properties that define a boundary — network access, firewall rules, role assignments, key rotation — routed to the owning team's channel with the actor's name in it, which turns an audit into a conversation within minutes. And review: a code-owners rule so that a diff touching those properties requires a second, specific reviewer. The pattern generalises: for anything that is a boundary, make it deny-by-default, alert on change, and require a named reviewer.

(a) Worked example EXAMPLE — replace with your own

Three environments that were supposed to be identical and were not. About four hundred resources, no infrastructure-as-code except a handful of ARM templates that had drifted so far they no longer deployed. The symptom that made it a project rather than a grumble: a release failed in production because a Service Bus subscription had a filter that staging did not, and the bug had been invisible for four months.

I did not start by writing templates. I started by making the drift measurable, because "our environments differ" is an opinion and "they differ in 61 specific properties" is a plan. An Azure Resource Graph query exported every resource with its type, SKU, tags and a handful of key properties per environment; a small script diffed them by logical name. Sixty-one differences, of which nine were deliberate (sizes), fourteen were accidental and harmless, and thirty-eight were genuine risks — different TLS minimum versions, a missing firewall rule, two resources that existed only in production, retention settings that varied from 7 to 400 days. That list was the entire justification for the work and I never had to argue for the project again.

Then the approach. Not a big-bang rewrite, and explicitly not az bicep decompile on an exported ARM template, which produces something that technically deploys and that nobody can maintain — I tried it for one resource group and threw it away after an hour. Instead: write clean Bicep per resource group, using Azure Verified Modules where one existed rather than hand-rolling, then use what-if against the live environment until it reported no changes. That last part is the whole trick. The template is not correct when it deploys; it is correct when deploying it changes nothing. We worked resource group by resource group, lowest-risk first, and each one ended with a green what-if and a real deployment that was a no-op.

Two decisions I would defend. First, .bicepparam files per environment rather than long parameter lists, so the diff between staging and production is one readable file and the deliberate differences are visible in code review — that alone would have caught the Service Bus filter. Second, deployment stacks rather than plain deployments for the resource groups we finished. A stack tracks the resources a template owns, so a resource removed from the template is actually deleted, and it can deny-delete resources outside the pipeline; that closes the loop that ordinary ARM deployments leave open, where a hand-made resource persists forever because nothing knows it should not exist. It also made me nervous, and rightly: a deployment stack with the wrong delete behaviour is a tool for removing production. We ran every stack in detachAll mode for a month, read what it would have deleted, and only then moved the safe ones to deleteAll.

Eleven weeks, roughly 340 of the 400 resources under code. The remaining sixty are the honest part of the story: a legacy VM pair with hand-installed software, two resources owned by another team, and a handful of things that exist for reasons nobody could reconstruct. We tagged them iac=excluded with an owner and a reason, because an explicit exclusion list is infinitely better than a pretence of full coverage. Environment drift went from 61 differences to 9 deliberate ones, and the environment-parity check now runs weekly in CI and fails loudly.

(d) Follow-up drill chain

Why not just decompile the exported ARM templates?

Because you get a machine-shaped artefact: every property expanded including the defaults, literals where parameters belong, resource ids hard-coded, no modules, and no expression of intent. It deploys, which is seductive, and then the first person who needs to change it cannot tell which of two hundred properties matter. What does a deployment stack give you that a plain deployment does not, and what does it cost?

It gives you lifecycle rather than convergence: a normal ARM or Bicep deployment in incremental mode adds and updates but never removes, so anything created by hand or left over from a previous template lives forever. A stack tracks the set of resources it manages, so removing a resource from the template removes it from Azure, and deny-settings stop anyone deleting or modifying managed resources outside the pipeline. The cost is that you have handed a template the power to delete production. That is why the sequence matters — detachAll first, read the plan for a month, then enable deletion only for resource groups where you are confident the template is complete — and why I would never enable it on a resource group that still contains hand-made resources.

At what scale does hand-written Bicep stop scaling?

Around the point where you are copying modules between repositories to keep teams consistent. Below that, per-team Bicep with shared verified modules is fine and pleasantly boring. Above it, you need a platform layer: a module registry with versioning and a release process, subscription vending so new environments arrive correctly shaped, policy as the backstop for what modules cannot enforce, and a decision about whether teams write templates at all or consume a self-service catalogue. That is the landing-zone conversation in story 15, and the reason it is a separate story is that the platform version of this work fails for organisational reasons rather than technical ones.

What did you trade away?

Speed, for about a quarter. Anything that used to take ten minutes in the portal now takes a pull request, and for a while that made people slower and slightly resentful — which is a real cost, not a cultural failing. We bought some of it back by keeping the portal legitimate for reading and for non-production experimentation, and by making the templates good enough that the common changes were one line. The other trade is a subtler one: with a stack denying deletes, the emergency path is now harder, so we wrote and rehearsed the break-glass procedure for removing the deny settings, because a control you cannot bypass in an incident will be bypassed badly at 3 a.m.

How do you keep it from drifting back?

The weekly parity check is the main thing: the same Resource Graph diff, run in CI, failing when unexplained differences appear, with the deliberate ones listed in a file that requires a review to change. Deployment stacks with deny-delete stop the most common regression, which is someone fixing something in the portal at 2 a.m. and never telling anyone. And I care a lot about making the code path faster than the portal path for routine work, because drift is a symptom of friction — if adding a queue takes a day through the pipeline and a minute in the portal, drift is the rational choice and no amount of policy will beat that arithmetic.

10Teaching a team to read its own telemetry bill

Senior Mentoring / levelling someone up

(a) Worked example EXAMPLE — replace with your own

A mid-level engineer on my team was asked to "reduce the monitoring cost" and came back a week later with a proposal to turn off Application Insights on two services. It would have worked, in the sense that the bill would have gone down and we would have gone blind on two of the six things that page us. The interesting part of the mentoring was not teaching her about Log Analytics; it was that she had solved the problem as stated instead of the problem underneath, and she had done it alone because she did not know she was allowed to push back on the framing.

So we did it together, in three sessions of an hour. The first session was one query: which tables, from which resources, are producing the bytes. On our workspace, AppTraces was 71 percent of ingestion, and 80 percent of that was a single information-level log line inside a retry loop in one service. Nobody had known that, including me, and it is the single most common finding in this exercise — telemetry cost is almost never spread evenly, it is one or two sources.

The second session was the pricing model, because that is what turns a finding into options. Log Analytics bills per GB ingested at three table plans: Analytics at about $2.30/GB, Basic at about $0.50/GB and Auxiliary at about $0.05/GB, with about 30 days of retention included and cheaper long-term retention after that; commitment tiers discount Analytics ingestion only. Basic and Auxiliary trade capability for price — limited query surface, no alerts on some plans, different retention behaviour — so the design question is not "how much telemetry" but "which telemetry needs to be alertable and joinable, and which only needs to be searchable when something has already gone wrong". That reframing is the entire lesson, and once she had it she generated better options than my proposal.

The third session was the mechanism: data collection rule transformations, which let you drop or reshape records at ingestion, before you pay for them — a KQL transformation in the DCR that filters the noisy trace, projects away three fat columns nobody queries, and routes verbose diagnostic tables to a Basic-plan table instead of Analytics. Plus sampling in the Application Insights SDK, which is a different lever with a different trade: sampling keeps the shape of your data and loses individual records, transformation loses whole categories and keeps the rest complete. Getting her to articulate that difference out loud was the moment I stopped worrying about the outcome.

She shipped it: ingestion down 62 percent, cost down about $2,900 a month, and — the number I cared about — no reduction in alert coverage, verified by replaying the previous quarter's incidents against the new configuration to confirm every one of them would still have fired. She also wrote a page called "what we log and why" that is now the first thing a new service's pull request is checked against.

What I would do differently: I gave her the first query rather than teaching her to find it, which meant the second time she had a cost question she came to me. The next time I did this with someone I sat on my hands and let them navigate the pricing documentation, which took forty minutes and was visibly more uncomfortable and produced someone who did not need me afterwards. Mentoring efficiency and mentoring effectiveness are frequently opposites.

How did you know the reduced telemetry was still enough?

We tested it against history rather than against opinion: take the previous quarter's incidents, and for each one ask whether the alert that fired would still fire and whether the investigation queries would still return what was needed under the new configuration. Two failed that test — both relied on a column we were about to project away — so we kept the column and dropped a different one. When would you not use a DCR transformation?

When the data has any chance of being needed for audit, security investigation or a regulatory obligation, because the transformation is destructive at ingestion — those records never exist, and no amount of paying later brings them back. For that class I would move the plan to Basic or Auxiliary instead, where the price drops by roughly an order of magnitude and the data is still there, at the cost of query and alerting capability. I am also wary of transformations that encode business logic, because a KQL error in a DCR fails silently and nobody notices until an investigation comes up empty. Keep them simple, review them like code, and alert on a sudden drop in a table's volume.

At what scale does per-team telemetry tuning stop being the right approach?

Once you have more than a handful of teams, tuning per team produces inconsistency that costs more than it saves — different retention, different severity conventions, alerts that cannot be correlated across services. The scaled version is a platform decision: standard DCRs and table plans defined centrally, a shared schema convention, a default sampling policy in the shared telemetry library, and per-team cost visibility so the incentive lands where the spending happens. That last part is the important one; teams optimise what they can see, and a single shared workspace with no per-team attribution guarantees that nobody optimises anything. The counter-pressure is that a workspace per team makes cross-service queries painful, so the usual answer is one workspace with rigorous resource attribution, not many.

Then I made the framing explicit and treated it as a gap in what she had been told, not in her judgement, because it genuinely was: nobody had ever explained that "reduce the cost" came with an unstated constraint. Technically, throughput scales with units and with multi-region deployment on the premium tiers, so the ceiling is high — but a single instance is a single blast radius for policy changes and for the certificate store, and one team's bad policy can affect everyone's traffic. Organisationally, the pain arrives around the point where several teams need to publish and change APIs independently, and everything queues behind one configuration surface. That is what workspaces are for — they let teams own their own APIs and policies within a shared gateway — and past that, separate instances per domain with a shared front door. I would not split for throughput; I would split for autonomy and blast radius.

The partner wanted all 140 operations exposed. How did you win that?

I did not argue about the number, I showed the log. Ninety days of gateway analytics showed 31 operations with any traffic at all, and for each of the remaining 109 I could say the date it was last called, which for most was never. Then I made the offer easy to accept: the 109 stay documented and can be re-enabled within a day on request, so nothing is lost, and in exchange the surface we have to secure, test and monitor drops by three quarters. The commercial argument sealed it — a smaller surface meant we could commit to the mTLS date, and their programme cared about the date more than about theoretical access. If they had said no, I would have shipped the 31 first and the rest after, which is the same plan with a worse name.

What if the deadline had been five weeks rather than ten?

Then I would have gone to the contract rather than to the team, because at five weeks the honest options are to reduce what is promised or to change the date, and pretending otherwise produces a quiet failure two days before the deadline. Concretely: I would have proposed shipping mTLS and the WAF for the single highest-value partner first, with a written, dated plan for the rest, and asked whether that satisfied the annex — often it does, because the annex is about a control existing rather than about every partner being onboarded. What I would not do is take the five weeks and hope, and I would say that in an interview in exactly those words, because the failure mode being tested here is the engineer who agrees to an impossible date to avoid an uncomfortable conversation.

12The resource group somebody deleted

Staff Data-loss / corruption scare

(a) Worked example EXAMPLE — replace with your own

16:40 on a Thursday. A cleanup script intended for a decommissioned sandbox ran with a subscription context it had inherited rather than been given, and deleted a resource group containing an Azure SQL database, a storage account with about 8 TB of document blobs, a Key Vault and a Service Bus namespace. It was not production — it was the pre-production environment that three teams used for integration testing and that, it turned out, held the only copy of a partner test corpus that had taken two months to assemble. The first ten minutes were the worst part of my year.

They were also the most important, and what saved us was a decision rather than a keystroke: stop everything, and do not recreate anything with the same names. That instinct is worth internalising because it is counter-intuitive under pressure — everybody's reflex is to start rebuilding, and several of Azure's recovery paths are blocked the moment a resource with the same name exists in the same place. I put one person on communications, took the recovery myself, and wrote a plain-text log of every command in a shared document as I ran it.

What came back, and how. Key Vault was trivial and was designed to be: soft delete is on by default and cannot be turned off, so the vault was recoverable with its secrets and keys intact, and purge protection meant nobody could have hard-deleted it even deliberately. Azure SQL came back from automated backups — a deleted database is restorable within the retention window, and because the logical server had gone too, we recreated the server with the same name in the same resource group first and then restored, landing about four minutes behind the deletion point. Storage was the tense one: a deleted storage account can be recovered within a short window, but only if no account with the same name has been created in the same resource group in the meantime — which is exactly why the "do not rebuild" instruction mattered. It came back. Service Bus did not, because there is no soft delete for a namespace; we recreated it from Bicep in eleven minutes, and lost the messages in flight, which for a test environment was noise.

Total recovery, four hours and ten minutes. The uncomfortable finding in the postmortem was that we had been lucky twice: lucky that the storage account name had not been recreated, and lucky that the retention window on SQL backups had been left at the default rather than reduced for cost, as had been proposed in a spreadsheet three months earlier and never actioned. Neither was a control. The controls we then built were four: CanNotDelete resource locks at the resource-group level on every environment that anyone depends on, including non-production, because the lock is what actually stops a script; deployment credentials scoped to a single subscription with no cross-subscription role assignments; a break-glass procedure for removing a lock that requires elevation through PIM and posts to a channel; and — the one I insisted on — a genuine backup, in a separate subscription, of the two datasets that were irreplaceable, because soft delete is not backup. Soft delete protects you from deletion for a window. It does not protect you from corruption, from ransomware, from a bad migration that quietly rewrites data, or from a deletion nobody notices for six weeks.

What I would do differently: I would have treated "the only copy of a two-month test corpus lives in a pre-production environment" as a production risk when I first heard about it, which was months earlier. The severity of data is a property of the data, not of the environment label on the resource group.

(d) Follow-up drill chain

Why is geo-redundant storage not a backup?

Because replication is faithful: a delete or a corrupting write is replicated to the secondary as diligently as a good one, usually within seconds. Redundancy protects against infrastructure failure — a disk, a datacentre, a region — and against nothing that originates in your own application or your own hands, which is where the overwhelming majority of data loss actually comes from. A backup is defined by being a point-in-time copy you can return to, ideally in a different security boundary so that whoever can delete the data cannot delete its history. I use the test question "could the identity that can write this data also destroy every copy of it?" — if yes, you have redundancy, not backup.

Locks on non-production too? That sounds like friction.

It is friction, and it is the right amount. A resource-group lock does not stop deploying into the group, it stops deleting the group and its resources, so day-to-day work is unaffected and the only people who notice are the ones doing something destructive — which is exactly the population you want to slow down. The genuine cost is on teardown of genuinely temporary environments, which is why our ephemeral environments (story 17) are explicitly excluded and deleted by their own pipeline. The other honest cost is that locks can block legitimate operations in surprising ways, so the break-glass path has to be documented and rehearsed, or people start removing locks pre-emptively and you end up worse than before.

At what scale does this recovery approach stop working?

It works for one resource group and it does not scale to a subscription-wide event. Recovering four resources by hand took four hours; recovering four hundred would take days and would exceed the recovery windows for several of them, because those windows are measured in days and the operations are not parallel. Past a certain estate size the answer has to be infrastructure that redeploys from code in minutes — which is the argument for stories 09 and 15 — plus backup vaults with tested restores for the data, plus separation so that no single credential can reach every environment. The uncomfortable corollary is that a full-estate recovery drill is expensive and almost nobody runs one, so most organisations, including good ones, do not actually know their recovery time.

How did you handle the person who ran the script?

Privately first, immediately, to say that they were not in trouble and that I needed them for the next hour because they knew what the script had touched. Then in the postmortem, no name — not out of squeamishness, but because the name is not a cause: a script that could inherit a subscription context, a credential with delete rights across environments, and a resource group with no lock are causes, and every one of them is a system property. I have seen the alternative, and the cost is permanent: once one person is named in a postmortem, the next person to make a mistake will spend an hour deciding whether to mention it, and that hour is the most expensive hour in the whole incident.

What would you have done if the storage account had not come back?

Accepted the loss quickly and moved to reconstruction, rather than spending days on recovery theatre. Practically: establish what could be regenerated and what could not, get the regeneration started in parallel with any remaining recovery attempt, and tell the affected teams the truth within the hour, with an estimate. The two-month test corpus was the irreplaceable part, so the reconstruction plan would have been a prioritised subset — the twenty percent that covered the integration paths people actually test — rather than a faithful rebuild. And I would have raised the severity, because "pre-production data is gone and three teams cannot integrate for a fortnight" is a delivery incident even though it is not a customer-facing one.

I spent a week not designing anything. I asked four questions of five people. What availability are we contractually committed to, and to whom? What is the tolerable data loss, in seconds, for each capability, and who decided that? What actually happened in our last three incidents? And what is the trigger — is this a customer asking, a regulator asking, a board asking, or a news article? The answers were clarifying and, as usual, not what anyone expected. One enterprise contract committed us to 99.95 percent monthly and a four-hour recovery objective. Nothing in writing anywhere specified an RPO. Our last three incidents were, in order: a bad deployment, a bad deployment, and a certificate expiry — none of which a second region would have helped with, and the first two of which a second region would have made worse by doubling the surface for a bad release. And the trigger was the news article.

Then the technical reality, which is the part worth teaching. Active-active is a data problem wearing a traffic problem's clothes. Sending traffic to two regions is easy — Front Door does it with health probes and weighted routing. Having two regions accept writes is where the design lives. Cosmos DB supports multi-region writes with conflict resolution, but conflict resolution is a business decision, not a configuration setting: last-write-wins on a timestamp will silently discard a customer's change, and a custom resolution policy means writing merge logic for every entity and being certain about it. Azure SQL does not do multi-region writes at all: an auto-failover group is asynchronous replication with a readable secondary, so it is active-passive with a non-zero RPO and a failover measured in minutes to an hour. So "active-active" for our stack would have meant either moving the transactional store to Cosmos with per-entity conflict semantics, or partitioning customers by region so each region owns its own writes — a stamp model, genuinely good, and a rewrite of tenant routing, identity and reporting.

I put three options in front of the director, each with a cost, an RTO, an RPO and a list of what it would not protect against. The one we chose was a warm standby in a second region: infrastructure deployed from the same templates, database geo-replicated through a failover group, Front Door with a health-probe-driven origin group, no traffic in normal operation, and — the part that made it real — a rehearsed failover every quarter with a stopwatch. Measured RTO after the second rehearsal was 35 minutes; RPO under five seconds for the database and a couple of minutes for object storage. Cost was about 1.3 times single-region, against roughly 2.4 for a true active-active with the rewrite. And we spent a fifth of the money that would have gone to region two on the thing that actually caused our incidents: progressive delivery and automated rollback, which is story 19.

What I would do differently: I would have written the availability decision record in week one instead of week four. The document that says "here is what we commit to, here is what it costs, here is what we explicitly do not protect against" is worth more than the architecture, because it is what stops the same conversation restarting after the next news article — and it did restart, six months later, and the document ended it in ten minutes.

(d) Follow-up drill chain

Why is active-active mostly a data problem?

Because routing traffic to two regions is a solved, configurable thing, and accepting writes in two places is a distributed-systems problem you have to design around. The moment two regions can write the same logical entity you own conflict detection and resolution, and the default resolution — last write wins by timestamp — is a silent data-loss policy dressed as a setting, because it will discard a real user's real change and never tell anyone. Custom resolution means merge semantics per entity, which is real domain work. The way out that actually scales is partitioning ownership so that only one region can write a given entity — regional stamps, tenant pinning, or a single-writer region with read replicas — and at that point you are trading global write availability for correctness, deliberately, which is the honest version of the trade.

Your warm standby does not protect against a bad deployment. Is that not the same money for less coverage?

It is less coverage for the failure mode that has never hit us and full coverage for none of the ones that have, which is exactly why I would not have spent more. A second region protects against losing a region; it does nothing about a bad release, and if you deploy to both regions from the same pipeline it faithfully propagates the bad release to your recovery site. That is why the money we did not spend went into progressive delivery, health-gated rollout and automated rollback: for the same budget it addressed two of our last three incidents. The general principle I would defend in any interview is that resilience spend should follow observed failure distribution first and imagined failure distribution second, and that the second is where most architecture diagrams live.

At what point would you actually build active-active?

When one of four things is true: a contractual or regulatory recovery objective that a failover cannot meet — anything under roughly ten minutes with real data-loss limits forces it; a scale where a single region cannot serve the load or the latency, so you are multi-region for performance and get availability as a by-product; a data-residency requirement that already forces per-region data ownership, in which case stamps are nearly free architecturally; or a business where the cost of one hour of downtime exceeds the annual cost of the second region by a wide margin, which is a calculation someone in finance should do, not me. Absent those, I would rather have one region that is genuinely zone-redundant, deploys safely, and has a rehearsed recovery, than two regions that have never been tested.

How do you rehearse a failover without risking production?

Incrementally, and on a schedule that is announced rather than surprising. We started by failing over in a production-shaped pre-production environment with the same templates, which finds the mechanical problems — DNS TTLs, certificates missing in region two, a private DNS zone not linked, a managed identity that has no role assignment in the secondary subscription. Then a planned production failover in a low-traffic window with a stopwatch and an abort criterion, which is where you learn that your RTO is 35 minutes and not the 15 in the diagram. The failback is the part everyone skips and it is usually harder than the failover, because the secondary has diverged. Once that is boring, unannounced drills become reasonable; I would not start there.

The director wanted active-active. How did you say no without being the person who blocks things?

By never saying no to the outcome, only pricing the options for it. I brought three designs, all of which were real, with costs and measured recovery numbers, and I was explicit that active-active was achievable and what it would take — including the rewrite, which was the fact he did not have. Then I asked what availability the business wanted to commit to, which moved the decision to where it belonged. He chose the warm standby himself, which is a much better outcome than my choosing it, and six months later when the topic came back after another outage in the news, he answered it without me. The general pattern: make the trade-off visible and hand the decision to the person who owns the money, rather than defending a position.

(a) Worked example EXAMPLE — replace with your own

We found it during a review when someone noticed a firewall rule that should have been unnecessary. That is the single most important thing to understand about private endpoints: the network change and the DNS change are separate, and getting only the first one gives you a false sense of privacy rather than an error.

My instinct was to escalate about the queue. Neither of those requires a human to type the record. They require control over the shape of what gets created.

So we built the automation together and they owned it: an Azure Policy with a deployIfNotExists effect that, whenever a private endpoint is created in a spoke, automatically creates its private DNS zone group pointing at the correct centrally-owned zone in the hub, chosen from a mapping the networking team maintains. Lead time for a new private endpoint went from 5.4 days to zero. Their ticket volume dropped by about 40 percent, which mattered more to them than it did to us. And we added a detection for the silent-failure mode: a synthetic check per environment that resolves each private endpoint's FQDN and alerts if the answer is not in our private ranges, which has since caught two genuine misconfigurations that nobody would otherwise have noticed for months.

I lost three weeks building a case about queue times, when the actual solution required understanding their risk model. (d) Follow-up drill chain

Why does a missing DNS record produce a working connection rather than a failure?

Because the public name never stops resolving. A resource with a private endpoint keeps its public FQDN, which CNAMEs to the privatelink name; if a private DNS zone is linked to your VNet it answers with the private IP, and if it is not, resolution falls through to Azure's public DNS and you get the public IP. Unless the resource's public network access is disabled, the connection then succeeds over the internet path. That is why I treat "private endpoint created" as half a change: the other half is disabling public network access on the resource, which converts the silent failure into a loud one. Doing both is what makes the control real; doing only the first is how organisations end up with an architecture diagram that is confidently wrong.

Why deployIfNotExists rather than just giving your team permission to write records?

Because the risk the networking team held was not about who typed the record, it was about conflicting or malformed records breaking resolution for everyone — DNS is a shared namespace and a bad entry is a multi-team outage. Granting write access to a shared zone distributes that risk to every team; a policy that creates exactly the right record from the endpoint's own properties eliminates the failure mode entirely, because there is no free-text step. It also keeps ownership honest: they still own the zones, the mapping and the policy, so when something is wrong there is one place to look. The cost is that policy remediation is asynchronous and occasionally needs a remediation task re-run, which is a much smaller problem than a five-day queue.

At what scale does hub-and-spoke DNS become the bottleneck itself?

Around the point where you have hundreds of spokes and multiple regions, because zone links are per virtual network and there are limits on how many links a zone can carry, and because a single hub becomes a regional single point of failure for name resolution. The answers at that scale are Azure DNS Private Resolver deployed per region with rulesets rather than forwarder VMs, zones linked through a well-defined automation rather than by hand, and, for very large estates, splitting DNS by environment or business unit with clear delegation. There is also an on-premises dimension: hybrid resolution through ExpressRoute needs inbound and outbound resolver endpoints and conditional forwarding, and that is where most large migrations discover their DNS design cannot be an afterthought.

The networking team could have said no. What was your fallback?

Two, and I had both ready. The lesser one: batch our requests, so instead of a ticket per endpoint we submitted a predictable weekly set with a template they could apply mechanically — worse for us, much better than the status quo, and it would have made the automation case for me within two months by showing how mechanical the work was. The escalation one, which I would have used only after the automation was refused with a reason I could not address: take the measured lead time and the silent-failure finding to both our managers as a delivery risk with a number attached, not as a complaint. I would not have gone around them by creating zones in our own subscription, even though we could have — that wins this quarter and poisons the next three.

By encoding properties of the workload rather than properties of the org chart. Why not buy the savings plan first — it is the biggest single number?

Because a commitment is priced against your current consumption, so buying before rightsizing means committing to three years of the waste you are about to remove, and then either paying for unused commitment or being unable to shrink. The other reason is that commitments constrain architecture: if you have committed heavily to one VM family and then want to move a workload to Container Apps or to a newer SKU, you are paying twice unless the commitment is flexible. How do you avoid cost cutting that becomes an availability incident?

Test the change against history rather than against opinion. For telemetry that meant replaying the last quarter's incidents to confirm every alert would still fire and every investigation query would still return — two failed, so we kept what they needed. For capacity it means never removing headroom without knowing your peak-to-average ratio and your autoscale lead time, which is the story-07 lesson. And for scheduling it means a documented exception path, because the first time someone genuinely needs an environment at 22:00 and cannot get one, the whole policy loses consent. I also treat cost changes as changes: they get a rollout, an owner and a rollback, because a resized SKU is a production change even though it looks like an invoice line.

It also becomes a discipline problem rather than a project: cost per unit of business value, tracked over time, with each team owning theirs. Anyone can find money once; the difference at principal level is building the thing that keeps finding it without you.

Two. Three teams shared two integration environments and booked them in a spreadsheet. The measurable consequence was that the median pull request sat for 3.1 days, most of which was waiting for an environment, and the unmeasurable one was worse: because environments were scarce, people batched changes, and batched changes are harder to review and riskier to deploy. I wanted per-pull-request environments, created on push and destroyed on merge.

The tool was the Azure Developer CLI — azd — over the Bicep we already had from story 09. What azd adds is a project-level definition that ties services to infrastructure and a named-environment concept, so azd up provisions and deploys and azd down removes, from a laptop or from CI, with the same definition. Under it we used a deployment stack per environment, which matters more than it sounds: teardown of a stack removes exactly what the stack owns, so an ephemeral environment cannot leave orphans behind, and orphans are what kill this idea financially. Predictable: cost, solved with a nightly reaper that deletes environments older than 48 hours regardless of pull request state, plus a budget alert per environment; quota, because forty simultaneous environments each with a SQL database is a different quota profile than two, and we hit the storage-account-per-subscription limit before anything else; and data, solved by a seed script rather than by copying production, which took a week and was the right call for reasons that had nothing to do with engineering. (d) Follow-up drill chain

Why deployment stacks rather than just deleting the resource group?

Deleting the resource group works and is what most people do, and it fails in two ways that matter here. First, it deletes everything in the group whether or not the environment created it, so a shared component that happens to live there — a DNS record, a role assignment, a key — goes too. Second, some resources persist beyond the group in ways that surprise you: soft-deleted Key Vaults hold the name for the retention period, so the next environment with the same name fails to provision until you purge, and a stack's teardown handles that explicitly. The stack also gives you a truthful inventory of what the environment owns, which is what lets the reaper be aggressive without being dangerous.

What stops forty ephemeral environments becoming a security problem?

Three things, and they are all boundaries rather than rules. They live in their own subscription, with no role assignments into production and no network path to it, so the blast radius of anything created there ends at that subscription. They have no production data — a seed script, never a copy — which removes the largest risk entirely and, incidentally, makes the whole thing much easier to justify to a data-protection reviewer. And the pipeline identity that creates them is federated per repository and per environment, scoped to that subscription only, so a compromised workflow in one repository cannot provision into anyone else's space. The residual risk is that the pipeline can now create infrastructure at will, which is why there is a budget alert and a hard reaper.

At what scale does the shared-shell compromise break down?

When infrastructure changes become as frequent as application changes. The shell exists because provisioning API Management and a SQL server takes minutes and those things rarely change per pull request; the moment a team is regularly changing them, the shared shell becomes a shared bottleneck again — one pull request's infrastructure change breaks everyone else's environment, which is exactly the problem we set out to remove. The escape hatch we built is a flag that provisions a full standalone environment for the pull requests that need it, at the cost of the 19 minutes. It also breaks on quota: past a few dozen concurrent environments you start meeting per-subscription limits on storage accounts, private endpoints and role assignments, and the fix is a pool of subscriptions rather than a bigger one.

Someone says this is over-engineering for three teams. Answer them.

They might be right, and the way to settle it is the arithmetic rather than the principle. Against that, the build was about three weeks and the run cost is a few hundred pounds a month with the reaper. If the numbers had been ten pull requests a month, I would not have built it, and I would have said so; the honest version of this story includes the fact that I checked before starting rather than after. What I would not accept is the argument that shared environments are fine because they have always been fine — that is the batching cost being invisible, not absent.

Senior On-call firefighting

(a) Worked example EXAMPLE — replace with your own

Twenty-three pages in seven days, eleven of them between midnight and 06:00. The first one, at 02:10 on the Tuesday, was a scale-out failing with ZonalAllocationFailed: the node pool asked for eight more machines of a particular VM size in zone 2 and Azure said no. We had quota — I checked, because that is everybody's first assumption — and quota is not capacity. Quota is your permission to allocate; capacity is whether the hardware is free in that region and that zone at that moment. You can have 2,000 vCPUs of quota and still be unable to start one machine.

At 02:10 the fix is not architectural, it is triage: I added a second node pool of a different VM family in the same cluster, tainted nothing, and let the autoscaler use it. Different family, different capacity pool, capacity available, service recovered in about eleven minutes. Then the same thing happened on Thursday in a different zone, and on Friday the spot node pool from story 07 was evicted almost entirely within four minutes, which is the correct behaviour of spot capacity and is nonetheless very unwelcome at 04:40. By Friday I had stopped treating each page as an incident and started treating the week as one.

The genuinely useful work happened on the Saturday, and it was not technical. I went through all twenty-three pages and sorted them into three piles: five were real, customer-affecting problems that a human needed to decide about; twelve were conditions the system could have resolved by itself; and six should never have paged anyone — a disk-space alert on a node the autoscaler was about to replace, a certificate-expiry warning with 45 days of runway, two duplicate alerts for the same condition from different tools. That distribution is, in my experience, entirely typical, and it is the argument for spending on-call follow-up time on the alert set rather than on the underlying systems.

What we changed. For capacity: the node pools became multi-family and the cluster moved to Node Auto Provisioning, which chooses instance types from the SKUs that fit the pending pods and can fall back across families automatically — that single change would have prevented the Tuesday and Thursday pages entirely. For the workloads that genuinely could not tolerate an allocation failure we used on-demand capacity reservations, which reserve capacity for a specific SKU in a specific zone whether or not you are running instances; they cost money for exactly that guarantee, so we bought them for the minimum viable core and not for the elastic tail. For spot: a lower maximum share of total capacity and a proper eviction handler that drains gracefully. And for the alert set: the six that should not page became tickets, the twelve auto-resolvable ones got remediation — automatic node replacement, a queue-depth-driven scale rule instead of a page, a certificate renewal job — and only the five real ones stayed as pages. The following month's on-call rotation took four pages.

What I would do differently: I would have escalated the week itself on the Wednesday rather than the Saturday. I absorbed it, which felt like being reliable and was actually hoarding information — my manager did not know the rotation was that bad until it was over, and the person on call the following week inherited a system I had already learned how to survive. Now I raise the pattern, not just the incidents, and I do it while I am tired rather than after I have recovered.

(d) Follow-up drill chain

Explain the difference between quota and capacity as if to a junior engineer.

Quota is a limit on your subscription — how many vCPUs of a given family you are permitted to have running in a region. Capacity is whether the physical hardware for that SKU is currently free in that region and zone. Raising quota is a request to Microsoft's billing and limits system and it grants permission; it does not reserve anything, so an allocation can still fail the moment after the increase is approved. The practical consequences: quota problems are predictable and should be monitored as a metric with headroom, capacity problems are not predictable and the defence is flexibility — multiple SKU families, multiple zones, and a capacity reservation for the part of the workload that genuinely cannot wait.

When are on-demand capacity reservations worth it?

When the cost of not being able to allocate exceeds the cost of paying for idle capacity — which is a narrower set of workloads than people assume, because you pay for the reservation whether or not you use it, at close to on-demand rates. I would reserve for the minimum core that must always be able to start: the baseline of a customer-facing service, the disaster-recovery capacity you need to be able to fail over into, a GPU SKU that is chronically constrained, or a workload pinned to one SKU for licensing reasons. I would not reserve for the elastic tail, which is exactly what SKU flexibility and spot are for. The mistake I have seen is reserving the peak rather than the floor, which converts a rare availability risk into a permanent cost.

At what scale do allocation failures become a design constraint rather than an incident?

Once your scale-out steps are large enough that they cannot be satisfied from spare capacity in a single zone — roughly when a single event asks for tens of machines of one family. At that point SKU flexibility stops being an optimisation and becomes a requirement: the workload must be able to run on two or three families, which constrains what you can assume about local NVMe, network bandwidth, or specific instruction sets, and it has to be tested on all of them. It also changes the multi-region conversation, because the honest reason to be in two regions at very large scale is often capacity rather than availability. And it interacts badly with a zone incident, when everyone in the region is asking for the same replacement capacity at the same moment.

Twelve of twenty-three pages were auto-resolvable. Why had nobody automated them?

Because each one individually looked cheap to handle manually, and nobody had ever aggregated them. That is the general failure: the cost of an alert is paid in five-minute increments by whoever is on call, and it never appears in a plan. The mechanism I now use is a standing on-call review at the end of every rotation where the outgoing engineer classifies every page into the three buckets, and anything in the "machine could do this" bucket becomes a ticket with the on-call engineer's name on it and time allocated in the next sprint. It is unglamorous and it is the highest-return reliability work I know, because it compounds: each automated page is paid once and saved forever.

On the Wednesday, to my manager and in the team channel: "this rotation has taken eleven pages in two days, seven of them overnight, and the cause is capacity rather than anything we have changed — I need someone to take Thursday night, and we need to book time for the follow-up before the next rotation starts." That is three facts and two asks, and it takes thirty seconds. What I actually did was survive it, which meant my manager could not make a resourcing decision, the next person inherited undocumented workarounds, and I was worse at my job for a week afterwards. I have come to think that quietly absorbing operational pain is one of the more common failure modes in senior engineers, because it is rewarded in the short term and it hides exactly the signal the organisation needs.

19A pipeline that could deploy but not un-deploy

Staff CI / test / reliability improvement

(a) Worked example EXAMPLE — replace with your own

Our deployment pipeline was, by the standards of the conversation people usually have, good: everything in code, automated tests, one-click deploy, deployments several times a day. And it had no reverse gear. Rolling back meant reverting the commit and running the full pipeline again — 22 minutes on a good day — so the mean time to recover from a bad release was about 40 minutes including the time to decide. Over a quarter we had four bad releases, which is 160 minutes of self-inflicted customer impact, and every one of them had been detectable within 90 seconds of the first instance taking traffic.

The reframing that unlocked it was separating deploy from release. Deploying is putting code on infrastructure; releasing is letting user traffic reach it. If those are the same event, your only rollback is another deploy. If they are separate, rollback is a routing change measured in seconds. On Azure we had two mechanisms for that and used both. For the App Service workloads, deployment slots: deploy to the staging slot, warm it up with a real health path, swap, and — the part people forget — the previous version is now sitting in the staging slot, so rolling back is swapping again, which takes seconds and requires no build. For the container workloads behind Front Door, weighted origin groups: bring up the new revision, shift 5 percent of traffic, watch, then 50, then 100, with the old revision still running and receiving nothing.

Then the hard part, which is always the database. A slot swap or a traffic shift is not a rollback if the new version has already changed the schema, because the old version cannot read it. So we adopted expand and contract as a rule with teeth: a migration may only add nullable columns, new tables and new indexes; the code writes to both old and new shapes for a release; the column is dropped in a later, separate release once nothing reads it. That means every schema change takes three releases instead of one, which people hated for about a month and then stopped noticing. It is the single most important thing in this story, because it is what makes every other rollback mechanism real rather than theoretical.

Behaviour changes that could not be expressed as separate deployments went behind flags in Azure App Configuration, with the feature-flag provider refreshing on a sentinel key so a flag flip takes effect within seconds without a restart. And the last piece was automation: an availability test plus an error-rate alert on the new revision, wired to trigger the swap-back or reset the Front Door weights automatically if the error rate exceeded a threshold within the first ten minutes. We tested it deliberately by releasing a version that returned 500s on one endpoint, on a Tuesday afternoon, with everybody watching.

Mean time to recover from a bad release went from about 40 minutes to 90 seconds, and the change nobody predicted was the effect on behaviour: deployment frequency went up by roughly half, because the cost of being wrong had collapsed. That is the argument I would make to any organisation that thinks progressive delivery is a luxury — it does not just reduce the impact of failures, it changes how much risk people are willing to take on ordinary work.

(d) Follow-up drill chain

Why is a slot swap not a rollback?

Because it only reverses the code, and a release is code plus schema plus data plus anything that left the building. If the new version added a non-nullable column, the old version's inserts now fail; if it wrote records in a new shape, the old version may not be able to read them; if it published messages on a new contract, consumers have already processed them. So the swap gives you a fast reverse for the half of the release that lives in your process, and expand/contract, backward-compatible message contracts and idempotent consumers are what make the other half reversible. When something genuinely cannot be reversed — an email sent, a payment taken, a third-party record created — I want that isolated behind a flag and released separately, so the irreversible surface of any one release is as small as possible.

Three releases to add a column. How do you defend that overhead?

With the arithmetic and with the alternative. The overhead is a few minutes of extra thought per migration and a couple of extra deployments, and deployments are cheap precisely because of the rest of this work. The alternative is that every schema change is a release that cannot be rolled back, which means every one of them requires a heavier process — a change window, a database backup step, a longer approval — and that is a far bigger tax paid on a far higher volume of changes. There is also a hidden benefit that sells it internally: backward-compatible migrations are what make zero-downtime deployment possible at all, so the same discipline removes the maintenance window nobody liked. I would drop the rule only for a system with a genuinely single instance and an accepted downtime window.

At what scale does automated rollback become dangerous?

When the signal it acts on is noisier than the failure it protects against, which happens sooner than people expect. An error-rate trigger on a low-traffic service will fire on three failed requests from a broken client; a latency trigger will fire during a routine cache warm-up; and an automated rollback in the middle of a data migration can leave you in a worse state than the bad version. So I bound it: automated action only within a defined window after a release, only on a metric with enough volume to be statistically meaningful, only when the reverse action is itself safe, and always with a loud notification so a human knows it happened. Outside that window it raises a page and a human decides. The failure mode I am guarding against is an automation that flaps between two versions at 3 a.m. while everyone assumes it is helping.

How did you convince people to spend a sprint on this rather than on features?

By pricing the status quo. Four bad releases in a quarter, roughly 40 minutes each, is over two and a half hours of customer impact that we were choosing to accept, plus the invisible cost that people batched changes and deployed cautiously because reversing was expensive. I put that next to the estimate — about three weeks across two people — and framed it as buying back the ability to move fast rather than as reliability work, because "we will ship more often" funds more easily than "we will fail more gracefully". The deployment-frequency number afterwards is what made the argument permanently, and I make a point of measuring it now precisely so that the next investment of this kind has evidence behind it.

What about the background workers and queue consumers?

They are the part that most rollback stories quietly ignore, and they need their own rules. A consumer must tolerate both message versions during a release, which means additive message contracts and consumers that ignore unknown fields, and it must be idempotent, because a rollback mid-flight means some messages are processed by both versions. For long-running jobs we drain rather than kill: the old revision stops taking new work and finishes what it has, which means a deployment is not instantaneous and that is fine. And anything that is genuinely not safe to run in two versions at once — a scheduled reconciliation, a batch that writes aggregates — gets a leader election or a flag that ensures exactly one version is active. The general rule I use is that if two versions of the code cannot safely run simultaneously for ten minutes, you do not have a rollback plan, you have a hope.

Two of those three premises were wrong and the deadline was not one of them. Why not push back on the date as well?

Because the date came from a lease, not from a preference, and pushing on an immovable constraint spends credibility for nothing — worse, it makes every subsequent objection sound like reluctance. The useful move is to accept the constraint loudly and early, which buys you the standing to renegotiate the content, and then to be precise about what fits inside it. Where I would push on a date is when it is arbitrary and the cost of hitting it is a corner that will be cut somewhere invisible: then I say exactly which corner, and let the person who owns the date choose. Rehosting an end-of-support operating system to the cloud — defend that.

It is not ideal and it was the right call under a lease expiry, because the alternative was to combine a datacentre exit with twenty-two operating-system upgrades in the same seven months, which is how you miss both. What I would not accept is running unsupported software with no patch path and no scheduled remediation — the ESU coverage is a bridge with an end date, and I made sure the end date was in the plan and not just in my head.

At what point does rehosting become the wrong default?

When there is no hard external date, because then the calculation changes completely: rehosting imports your operational burden — patching, backups, capacity, operating-system lifecycle — into an environment where you now also pay a cloud margin for it, and the payback comes only if you follow through with modernisation afterwards, which most organisations do not once the urgency is gone. Without a deadline I would sequence differently: retire aggressively, repurchase the commodity workloads, replatform the ones where a managed service removes real operational cost, and rehost only what remains. The other trigger is scale — at a few hundred machines rehosting is a tooling exercise, and at several thousand the sheer weight of unmodernised estate becomes a permanent cost centre that is much harder to unwind later.

Not as a correction. I showed the naive number first — 1.9 times the current run rate — as the thing I was worried about, so the problem belonged to both of us rather than to him. The framing that made it work was that both numbers were true depending on how we executed, which is genuinely the case: lift and shift really is more expensive if you lift the sizes too. I also gave him something to say to his own stakeholders, which is a thing engineers forget — a senior person needs a version of the story they can repeat, and if you do not supply one they will use the original.

Now I insist on a two-day technical spike per replatform candidate before it goes in the plan, and I keep at least one candidate in the rehost bucket as a hedge, so that a surprise costs me a modernisation opportunity rather than a date.

These are the prompts that are not tied to one story. Each answer names which of your prepared stories to deploy and what the interviewer is listening for. The story numbers refer to the units above — replace them with the numbers of your own equivalents as you build them, because the point of this section is to make sure a single well-prepared story can serve four different questions.

Failure & ownership

Tell me about a time you were wrong about a technical decision.

Deploy: story 02 (a partition key that was right and became wrong) or story 15 (a programme you championed and cancelled). They want: a decision that was reasonable on the information available, an honest account of what changed, and a change of method rather than a resolution to be more careful. The strongest version is one where you were wrong about your own proposal, because that is rarer and less defended. Avoid the disguised humblebrag — "I was wrong to trust my colleague" is not an answer to this question.

Walk me through your biggest production incident.

Deploy: story 03 (zone event, incident command) or story 18 (a bad week rather than a bad hour). They want: a timeline with real times, the mitigate-before-diagnose decision, one clear decision-maker, and a postmortem whose actions are controls rather than intentions. Lead with impact in business terms — "31 percent of requests failing for 49 minutes" — not with the technology. Separate what you designed from what was luck, out loud; that single sentence moves you a level.

Tell me about a time you caused an outage or lost data.

Deploy: story 12 (deletion and recovery) or story 06 (a job writing where it should not). They want: ownership without theatre, composure in the recovery, and a system-level fix. If the mistake was someone else's, own the system that allowed it rather than naming them — interviewers notice both the blame and the absence of blame. Say what you would have lost if the recovery had failed; that is the question they are heading towards anyway.

What is the most expensive mistake you have made in the cloud?

Deploy: story 16 (the orphan sweep is full of other people's expensive mistakes, so tell one of your own) or story 17 (the ephemeral environments left running before the reaper existed). They want: proportion and self-awareness. Small honest numbers beat large vague ones. The follow-up is always "how would you catch it now", so have the control ready: a budget alert, an anomaly detection rule, a tag policy, a nightly reaper.

Conflict & influence

Tell me about a technical disagreement with a colleague.

Deploy: story 05 (Kubernetes) or story 09 (how you handled the person who preferred a different IaC approach). They want: a disagreement where the other person was substantially right about something, explicit criteria replacing preference, and evidence that the relationship survived. The killer detail is what you gave them — ownership, the revisit criteria, a documented escape hatch. Never tell a version where you were simply right and they came round.

How do you push back on someone more senior than you?

Deploy: story 20 (the December deadline) or story 13 (the active-active request). They want: the structure — accept the constraint that is genuinely fixed, ask for a bounded piece of analysis rather than arguing from opinion, and bring two numbers rather than one. Mention that you gave them a version of the story they could repeat to their own stakeholders; that detail is unusual and it signals someone who has operated at that altitude.

Tell me about influencing a team you had no authority over.

Deploy: story 14 (the private DNS zone) or story 17 (the second team adopting ephemeral environments). They want: understanding the other team's risk model, offering a better mechanism rather than an exception, and taking work off their plate. The anti-pattern they are screening for is escalation as a first move, and the second is going around the team, which wins once and costs you for years.

Tell me about a time you were overruled. What did you do?

Deploy: whichever of your stories genuinely ended that way — most people have one and skip it. They want: disagree-and-commit executed properly: you argued once with evidence, you recorded the concern and its trigger, you then implemented the decision well rather than half-heartedly, and you did not say "I told you so" when it went wrong. If it went right, saying so is very strong; if it went wrong, describing how you raised it without triumph is stronger still.

Leadership & mentoring

How do you grow the people around you?

Deploy: story 10 (the telemetry bill) and, for a second example, whoever you handed ownership to in story 05 or 15. They want: a capability the person now has, not a task you helped with; a moment where you deliberately withheld an answer; and their result attributed to them. At principal level they also want to hear you growing more than one person at a time — a review ritual, a written standard, a paved path.

How do you decide what your team should build versus adopt versus buy?

Deploy: story 05 (managed platform versus AKS) and story 15 (cancelling subscription vending). They want: total cost of ownership including the recurring operational cost, not the build estimate; a frequency argument — automating something that happens fifteen times a year is vanity; and an honest account of what the managed option later cost you. Naming the ecosystem-churn risk, as in the ALZ-Bicep deprecation, is a strong, specific detail.

How do you run an incident?

Deploy: story 03 (zone event) with the decision log, and story 12 (recovery sequencing). They want: roles separated — commander, comms, hands on keyboard; mitigation before diagnosis; one decision-maker; a written decision log while it is live; and a communication cadence. The senior detail is knowing when not to act: choosing to wait out a recovery rather than fail over, with the two numbers that justified it.

Ambiguity & prioritisation

Tell me about a project where the requirements were unclear or changed.

Deploy: story 13 (active-active) or story 11 (scope negotiation under a contractual date). They want: that you went and found the requirement rather than designing to the ask, that you asked what has actually gone wrong historically, and that you left an artefact — a decision record — so the question does not come back. Interviewers hear a lot of "we clarified with stakeholders"; the specific four questions you asked are what make it real.

How do you decide what not to do?

Deploy: story 15 (cancelling your own programme) and story 11 (the dependency table). They want: a repeatable method — which original problem does this solve, at what cost, what happens if we do not — and at least one example of stopping something with sunk cost in it. The trap is a candidate who has only ever prioritised by asking a product manager.

How do you make a decision without enough information?

Deploy: story 03 (fail over or wait, decided live) or story 20 (a three-week bounded assessment before committing). They want: a bias for cheap, reversible information — a bounded spike, a rehearsal, a query — and clarity about which decisions are one-way doors. Partition keys, region topology and management-group hierarchies are one-way; SKUs and scaling rules are not. Being able to classify a decision that way out loud is a strong senior signal.

Tell me about a time you had to say a plan was not achievable.

Deploy: story 11 (the ten-week annex) — and specifically the "what if it had been five weeks" version. They want: that you said it early, with the alternative attached, and that you did not simply agree and hope. The strongest form names the specific corner that would be cut and hands the choice to whoever owns the consequence.

Operations, risk & security

How do you decide when a risk is acceptable?

Deploy: story 08 (accepting bounded exposure with evidence) and story 16 (the savings you declined). They want: a repeatable shape — named owner, written rationale, compensating control, review date — and an example of accepting something rather than fighting it. Being able to name a saving or a shortcut you refused, and why, is what makes the accepted risks credible.

You have just inherited a noisy on-call rotation. What do you do in the first month?

Deploy: story 18. They want: classify every page into real / auto-resolvable / should-not-page before changing anything; delete or downgrade the third category immediately, because it is free; automate the second; and only then work on the systems. The leadership half is raising the pattern while it is happening rather than absorbing it, and booking the follow-up time before the next rotation starts.

How do you think about security in cloud infrastructure?

Deploy: story 04 (identity as the perimeter), story 08 (boundary properties and deny policies), story 06 (standing access and just-in-time elevation). They want: identity first, blast radius second, detection third — and the recognition that the highest-value control is usually the one that makes a misconfiguration impossible rather than visible. Naming the difference between a real control and a comforting one, as with resource-name obscurity, lands well.

Values & motivation

Why cloud infrastructure? Why Azure specifically?

Deploy: whichever story genuinely hooked you — for many people it is the first time a platform decision visibly changed what a team could do, as in story 19 where deployment frequency rose because rollback got cheap. They want: authentic motivation and no clichés about "scale". For the Azure half, an honest answer is usually about the ecosystem you work in — identity, the .NET and data stack, enterprise governance — rather than a claim that one hyperscaler is better. Saying what you find genuinely worse about it is more persuasive than a sales pitch.

How do you keep current in a platform that changes weekly?

Deploy: be specific and dated. The AKS release notes on GitHub as the primary source rather than blogs; the Azure Updates retirement feed, because retirements are the changes that create work — the 30 September 2026 retirements of Azure Virtual Desktop (classic) and the NVv3/NVv4 VM series are on my calendar; the Gateway API becoming the AKS default in 1.36 as Ingress NGINX winds down; and the Log Analytics table plans, which changed how we spend. They want: primary sources, a habit rather than a newsletter list, and one thing you changed at work because of something you read.

Where do you think this is going?

Deploy: story 05 (managed platforms) and story 04 (identity). They want: a view with reasoning rather than a trend list. A defensible one: the interesting boundary has moved from the network to identity, so the question "which principal, at what scope" is replacing "which subnet"; managed platforms keep absorbing the parts of Kubernetes most teams never wanted, which makes "do we run a cluster" an economic question rather than a technical one; and cost has become a first-class design constraint rather than a monthly surprise, because the levers — table plans, autoscaling, commitments, SKU flexibility — are all architectural. Say what you are unsure about; certainty about the future reads as inexperience.

22Night-before cheat sheet

10 speakable rules read this last

Ten sentences to read the night before, and to say out loud once each so they are in your mouth rather than on the page.

  1. Open with the situation in one line, then stop. "A multi-tenant API on Cosmos DB where one customer had outgrown its partition" buys you thirty seconds of full attention; three minutes of company background spends it.
  2. Say the impact in business terms within the first minute. "Thirty-one percent of requests failing for forty-nine minutes" or "one customer's checkout was down every morning at eleven" is worth more than any amount of Azure vocabulary.
  3. Quantify both ends. p99 before and after, pages before and after, cost before and after, time to detect before and after. Cloud stories drift into architecture-diagram vagueness faster than any other kind, and numbers are the anchor that stops it.
  4. Name the failure domain, always. Instance, zone, region, subscription, control plane, identity. Half of the good follow-up questions in an Azure interview are really asking "do you know which one you were in", and answering it unprompted saves you the drill.
  5. Separate mitigation from fix, out loud. "Scaling out made it green and did not fix anything" is a sentence that marks a level. So is "we chose to wait rather than fail over, and here are the two numbers that made that right".
  6. Separate "I" from "we" deliberately. Say what you personally decided, wrote or argued, and hand the rest to the team by name. Interviewers are calibrated for inflation on exactly this and they will drill it with "and what did you do?"
  7. Own the failure in the same breath as the fix. The two weeks blaming a vendor, the runbook that said --zone 1, the programme you championed and killed, the estimate that was three weeks optimistic. A cloud story with no mistake in it sounds rehearsed, because real cloud work is full of them.
  8. Name the trade-off, never just the control. Every answer should contain a sentence shaped like "that bought us X and cost us Y" — zone redundancy costs money and latency, private endpoints cost convenience and DNS, pooled connections cost freshness, managed platforms cost control. Controls without costs signal someone who has read about this rather than run it.
  9. Have two recent, checkable facts ready and use each once. AKS moving to the Gateway API by default in 1.36 as Ingress NGINX maintenance ends, with critical patches for the app routing add-on only through November 2026; the Log Analytics table plans at roughly $2.30, $0.50 and $0.05 per GB; Bicep Azure Verified Modules replacing classic ALZ-Bicep, removed in February 2026; the 30 September 2026 retirements. One fact, used once, dated correctly — not a recital.
  10. Finish every story with what you would do differently, as a change of method. Not "I would be more careful" but "I open the platform's own diagnostics before forming a theory", "I write the revisit trigger down when I make the decision", "I escalate the pattern while I am still tired".

The last check before you walk in. Pick five stories from the coverage table that are genuinely yours, and for each one be able to say in ten seconds: the situation, the number, the failure domain, the trade-off, and the thing you would do differently. Five stories you can tell cold beat twenty you half-remember — and because the same four mechanisms recur across all of them (identity as the perimeter, the failure domain, undeclared infrastructure, the bill as a design document), five well-understood stories will answer far more than five questions.
